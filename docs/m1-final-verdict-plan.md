### 確定の判定の測り方（束がそろったあと）

1. 流れている絵の回（2,000 回）と、止まっている画面の回（2,000 回）。**両方が、同じ線を満たすこと**（12 / 24 / 47 ms と、2 回以上遅れ 15.4%）。ADR 0002 に、今日の日付で足した。

## 3. 「負荷があるほうが速い」件

関門のあとの参考の回で、両方の PC に負荷をかけると、差が 2.3〜2.7 ms 小さくなった。見立ては、「負荷がないと CPU が休んでいて、起きるのに時間がかかる」。確かめる順番：

1. **どちらの PC が効いているかを分ける**：ホストだけに負荷の回と、Mac だけに負荷の回（500 回ずつ）。候補のビルドのまま。
2. **Mac の側の候補**（1 つずつ入れて、前と後で比べる）：
   - ビューアーを、端末からではなく、アプリとして起動する（計測の回は、もうそうなっている。試用の窓は、端末から起動している）。
   - 復号、表示、入力のスレッドに、対話用のいちばん高い QoS を付ける。
   - 遅れに厳しい作業だと、OS に伝える（`NSProcessInfo` の `beginActivity` の `latencyCritical`）。
3. **ホストの側の候補**：
   - 通り道のスレッドの優先度（音の rlimit の試しと一緒に）。
   - 入力が届いた直後だけ、眠らずに待つ。
   - 深い眠りを止める口（`/dev/cpu_dma_latency`）を、映している端末がいるあいだだけ使う。root の設定が要るなら、インストーラーの仕事として、案に書く。
4. 比べるもの：差の 3 つの値、「2 回以上遅れ」の割合、絵の出方のむら。
5. 効いたものだけを、束に入れる。

## 4. 絵の出方のむら（「かくつき」）

持ち主は、当てるテストの数えない回（打たずに、見た目だけで答えた回）で、「微妙なかくつき」を感じている。調べること：

- 中継の窓で、フレームが画面に出る間隔のばらつき（記録から出せる）。手元の窓と比べる。
- 「2 回以上遅れ」の入力（関門の数値の回で 8.9%）が、どの区間で遅れているか。
- コンポジターが、フレームを 1 回ぶん待たせること（関門の数値の回で 1 回、基準の回で 0 回）。
- ビューアーを、アプリとして起動した形と、端末から起動した形で、比べる（音のプレーヤーでは、起動のしかたで、再生の処理の時間が 10 倍ちがった）。

## 6. 窓の大きさを途中で変えること（端をつまんで変える、広げる）

**今週の公開には、入れない案。**

- いまの作り：中継の絵の大きさは、セッションを開くときに決まり、途中で変えられない。変えるには、コンポジターの出力の大きさを変え、エンコーダーを作り直し、新しい大きさをクライアントに伝える、という 3 つが要る。どれも、まだない。
- 見積もり：3〜4 日（コンポジターの差分、ホスト、クライアント、切り替えのあいだの絵の扱い、計測）。フレームの通り道に手が入るので、入れるなら、数値の回をやり直すことになる。
- 束と同じ週に入れると、束が延びる。確定の判定のあとに回す。
- 使う人向けの文書に、制約として書く：「窓の大きさは、開くときに決まる。途中で変えるには、開き直す。閉じる、しまうは、手元の窓と同じに効く。広げるボタンは、効かない」。
- 開くときの大きさを、選べるようにする（`istesso open --size`）ことは、小さい。束の 2 に入れる。
