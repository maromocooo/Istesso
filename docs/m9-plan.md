# M9 の進め方：配布と公開の下ごしらえ

M9 は、Mac の署名・公証つき pkg と、Ubuntu の .deb を作り、公開する段階です（[milestones.md](milestones.md)、R-12）。この文書は、その下ごしらえです。**何も入れず、本物の証明書で署名せず、公開もしていません。** 用意したものは `packaging/` にあります（[README](../packaging/README.md)）。

読むときの注意：

- 「提案」と書いたものは、私の提案です。決まったことではありません。
- 持ち主がすでに決めたことは、「決定」と書いて、そのまま載せました。
- Apple の画面や Ubuntu の細かい仕様は、この文書を書いた Mac の上で確かめていません。自信のないところは「要確認」と書きました。
- 計測のコード、暗号、入力の経路には、手を入れていません（遅延の計測は要りません）。

## 0. 決定済みのこと

| こと | 内容 |
|---|---|
| 署名 | 個人の証明書（Apple Developer Program の Developer ID）と公証。証明書には会員の名前が入る。**その名前は、コード、スクリプト、文書、コミット、CI のログのどこにも書かない。** スクリプトは、環境変数かハッシュで証明書を指す |
| 鍵 | 署名は持ち主の Mac で、持ち主の鍵で行う。鍵と証明書は、リポジトリにも CI にも入れない |
| 許可 | 利用者が与えた許可（画面収録、アクセシビリティ、ローカルネットワーク）は、更新しても残す |
| 今日の発見 | 実行ファイルがリンカーの署名だけのバンドル、または実行ファイルのビルド UUID がほかのプログラムと同じバンドルは、ローカルネットワークの許可が正しく覚えられない。バンドル全体に署名する。識別子はバンドル ID と同じにする。Info.plist を封印する。分かりやすい実行ファイル名にする。置き場所を固定する |
| Linux の root | 下の 2.3 の 4 つ（udev、limits、圧縮枚数、CPU の眠り） |
| ライセンス | `MIT OR Apache-2.0`。GPL・AGPL は入れない。第三者のライセンス文は、パッケージに同梱する（`third-party-licenses/`。`m7-usb-devices` ブランチにある） |

## 1. macOS

### 1.1 アプリのバンドル（提案）

| 項目 | 内容 |
|---|---|
| 名前 | `Istesso.app` |
| バンドル ID | `dev.istesso.app`（提案。名前の決定、M9 の最後の項目、で変わりうる。変えると許可が引き継がれないので、**公開の前に決めて、あとで変えない**） |
| 実行ファイル | `Contents/MacOS/istesso`（コマンドラインの `istesso` と同じもの。`CFBundleExecutable` もこの名前）。バンドルの実行ファイルが 1 つなので、許可は、このバンドルに付く |
| 署名 | バンドル全体に署名する。識別子はバンドル ID。ハードンドランタイムとタイムスタンプ付き。`Info.plist` を封印する。`--deep` は使わない。`build-pkg.sh` が、署名のあとに識別子と封印を確かめる |
| ビルド UUID | ほかのプログラムと同じにならないように、バンドルに入れる実行ファイルは、それ専用にビルドする（今日の発見への対策。別のバイナリをコピーして名前だけ変えない。確かめ方は 1.5） |
| クライアントとホスト | いまは 1 つのバンドルに、クライアントとエージェントを入れる。Mac ホスト（M4：画面の取り込み、VideoToolbox）は、画面収録とアクセシビリティの許可が要る。許可の理由は ADR に書く（AGENTS.md）。**ホストを別のバンドルにするかは、M4 の結果で決める**（要決定。別にすると許可の画面が 2 つになる。同じにすると、クライアントだけの人にも不要な許可の案内が出ないようにする工夫が要る） |
| entitlements | 画面収録と VideoToolbox は、ハードンドランタイムでも entitlement が要らない、とみている。**要確認**（署名したビルドで確かめる。`ISTESSO_ENTITLEMENTS` で渡せる） |

### 1.2 置く場所（提案）

| 場所 | 中身 | 持ち主 |
|---|---|---|
| `/Applications/Istesso.app` | バンドル | root:wheel（pkg が作る） |
| `/Library/LaunchAgents/dev.istesso.agent.plist` | launchd のエージェント | root:wheel、0644 |
| `/usr/local/bin/istesso` | バンドルの実行ファイルへのシンボリックリンク | root |
| `~/Library/Application Support/istesso/` | 端末の鍵、ペアリング済みの一覧（`istesso-agent` の `paths.rs` で決まっている） | 利用者。**pkg は触らない** |
| `~/Library/Caches/istesso/` | 作り直せるもの | 利用者 |

`/Applications` に固定するのは、許可がバンドルの場所と署名に結びつくためです。pkg は、バンドルを「再配置しない」設定で作ります（`BundleIsRelocatable` を false）。ビルドのフォルダーなど、別の場所にあるコピーに、勝手に上書きされないようにするためです。

### 1.3 常駐（launchd。提案）

| 項目 | 内容 |
|---|---|
| ラベル | `dev.istesso.agent` |
| 種類 | ユーザーごとの LaunchAgent（`/Library/LaunchAgents`）。LaunchDaemon にしない。画面収録とローカルネットワークの許可は、ログインしたセッションに属するため。鍵も利用者のフォルダーにある |
| 起動 | ログイン時（`RunAtLoad`）。`LimitLoadToSessionType` は `Aqua`。エラーで終わったら 10 秒おいて再起動（`KeepAlive` の `SuccessfulExit` が false）。正常終了（0）は、止めたままにする |
| 実行するもの | `/Applications/Istesso.app/Contents/MacOS/istesso agent`。`AssociatedBundleIdentifiers` でバンドルに結びつける |
| 優先度 | `ProcessType` は `Interactive`（遅延が大事なため） |
| ログ | ファイルは作らない。標準エラーは統合ログへ。ペアリングコード、鍵、トークンは出さない（AGENTS.md） |
| 止め方 | その場で止める：`launchctl bootout gui/$(id -u)/dev.istesso.agent`。次のログインから止める：`launchctl disable gui/$(id -u)/dev.istesso.agent`。外す：`uninstall.sh` |
| 入れたとき | pkg の preinstall が、ログインしている人のエージェントを止める。postinstall が、同じ人のエージェントを起動する。ほかのユーザーは、次のログインで起動する。どちらも、失敗しても入れる処理を止めない |

ホストの Mac は、人がログインしたままにする形です（M4 の決定）。ログイン前のホストは、いまの範囲に入りません。

### 1.4 更新で許可を失わないために（提案）

許可は、バンドル ID と、署名の「指定要件」（Developer ID と Team ID を含む）に結びつきます。更新の決まりは次のとおりです。

1. バンドル ID を変えない。Team ID（同じ証明書の持ち主）を変えない。
2. 毎回、同じ場所（`/Applications/Istesso.app`）に、バンドル全体に署名したものを入れる。
3. 署名なしのバンドル、アドホック署名のバンドルを、利用者の手元に出さない。
4. 実行ファイルの名前を変えない。
5. 古いバンドルを消してから新しく作らない。pkg が、場所はそのまま、中身を上書きする。

リリースごとの確認（署名したビルドで、Mac の実機。AGENTS.md の「実機で確かめる」）：

- 1 つ前の版を入れ、画面収録、アクセシビリティ、ローカルネットワークを与える。
- 新しい版を、pkg で上から入れる。許可の画面が、もう一度出ないこと。`istesso doctor` で許可の状態が同じであること。
- 別の端末に、エージェントから届くこと。

### 1.5 pkg の作り方（`packaging/macos/build-pkg.sh`）

流れ：バンドルを作業用フォルダーに複製 → 署名（環境変数があれば）→ launchd の plist とシンボリックリンクを足す → `pkgbuild`（再配置しない）→ `productbuild`（署名は環境変数があれば）→ 公証とステープル（`ISTESSO_NOTARY_PROFILE` があれば）。署名の指定がなければ、署名なしで作り、そう表示します。

ビルド UUID の確認（署名したビルドでやる。提案）：`dwarfdump --uuid` で、バンドルの実行ファイルの UUID が、ほかの配布物と重ならないことを見る。重なるときは、ビルドし直す。

## 2. Ubuntu

### 2.1 `.deb` の中身（提案）

| 場所 | 中身 |
|---|---|
| `/usr/bin/istesso` | コマンドラインとエージェント |
| `/usr/lib/systemd/user/istesso-agent.service` | ユーザーユニット（有効にはしない） |
| `/usr/lib/udev/rules.d/70-istesso-usb.rules` | 対応 USB 機器を、グループ `plugdev` に開く |
| `/etc/security/limits.d/40-istesso.conf` | グループ `istesso` に、リアルタイム優先度と nice だけを許す（conffile。利用者が直したものは、更新で上書きしない） |
| `/usr/share/doc/istesso/` | `LICENSE-MIT`、`LICENSE-APACHE`、`copyright`、`third-party-licenses/` |

Docker は必須にしません（R-12）。ホストのコンポジターなどの部品（M1 以降）は、できたときに足します。

### 2.2 systemd（提案：ユーザーユニット）

ホストの前には、ふつう誰もいません。それでも**システムユニットにしない**理由は 3 つです。

1. 端末の鍵とペアリング済みの一覧が、その利用者のフォルダーにある。
2. 映像と音の部品（コンポジター、PipeWire）が、その利用者のユーザーサービスである。
3. システムユニットにすると、利用者名を決め打ちにする必要がある。

誰もログインしていなくても動くようにするのは、`loginctl enable-linger <利用者>` です。これは root の仕事で、利用者を知っているのは持ち主だけなので、パッケージは行いません（2.3 の表の最後）。持ち主が、1 回、次の 2 行を実行します。

```sh
sudo loginctl enable-linger <利用者>
systemctl --user enable --now istesso-agent.service
```

止め方：`systemctl --user stop istesso-agent.service`（無効にするのは `disable`）。正常終了は再起動しない。エラーで終わったら、5 秒おいて再起動する。

### 2.3 root が要るもの（インストーラーの仕事）

| # | もの | 置く場所 | 理由 | 誰がやるか |
|---|---|---|---|---|
| 1 | USB 機器の udev の決まり（グループの形） | `/usr/lib/udev/rules.d/70-istesso-usb.rules` | 機器の口（`/dev/hidraw*`）は root だけが開ける。`uaccess` は、その PC の前でログインしている人にしか効かず、ホストでは効かない。グループ `plugdev`（ホストの利用者がすでに入っている）に与える。1 回の導入で済む | `.deb` |
| 2 | リアルタイム優先度と nice の上限 | `/etc/security/limits.d/40-istesso.conf`（グループ `istesso`、`rtprio 95`、`nice -19` だけ） | 取り込みと送り出しを、ほかの仕事に遅らされないため。ディストリビューションの `pipewire` グループの設定は使わない。あれは固定できるメモリの上限（`memlock`）も決めており、`pipewire` グループの人と一緒になって下げないため。**この設定が、ユーザーサービスにも読まれることは、M2 の観察による**（M2 の計画の手順 6。実機での確認は M2 の流れ） | `.deb` がファイルを置き、グループを作る。**利用者をグループに入れるのは、持ち主**（`sudo gpasswd -a <利用者> istesso`） |
| 3 | GPU が同時に圧縮できる枚数 | `/etc/istesso/encoder-sessions`（数字 1 つ） | GPU の上限を超えると、圧縮が途中で失敗するため。**映像が流れていないときに、1 回だけ数え、その数から 2 を引いた数**にする。数えられなければ 8。2 以下なら 1 | `.deb` の postinst。数える小さなプログラム（`/usr/libexec/istesso/count-encoder-sessions`。名前は提案。**まだない**）があれば、それを呼ぶ。なければ 8 を書く。すでにファイルがあれば、上書きしない |
| 4 | CPU を深い眠りに入れない（`/dev/cpu_dma_latency`） | なし（**注意書きだけ**） | 機器を表示するセッションのあいだ、CPU の眠りからの復帰が、遅延に出るかもしれない。`/dev/cpu_dma_latency` は、開いて値を書き、開いたままにするあいだだけ効く。開けるには権限の設定が要るかもしれない。**要確認**（実機で、効果があるときに限って、別に決める） | いまは何もしない |
| 5 | ユーザーサービスを、ログインなしで動かす | `loginctl enable-linger` | 2.2 のとおり | 持ち主（1 行） |

### 2.4 パッケージの処理がすること、しないこと

| する（postinst） | しない |
|---|---|
| グループ `istesso` を作る（なければ） | 誰かをグループに入れる |
| udev の決まりを読み込み直す（`udevadm control --reload-rules`） | サービスを有効にする、起動する。linger を有効にする |
| `/etc/istesso/encoder-sessions` を、なければ書く | 利用者のフォルダー、鍵、ペアリング済みの一覧に触れる |
| | カーネルや電源の設定を変える。何かをダウンロードする |

| する（postrm） | しない |
|---|---|
| 削除と purge で、udev の決まりを読み込み直す | グループ `istesso` を消す |
| purge で、`/etc/istesso/encoder-sessions` を消す | 利用者の鍵とペアリング済みの一覧を消す |

### 2.5 リポジトリ（提案）

R-12 は、署名つきのリポジトリを求めています。署名の鍵（リリース用の GPG 鍵）は、持ち主の手元に置き、リポジトリにも CI にも入れません。`.deb` 自体には署名せず、リポジトリの `Release` ファイルに署名します（`apt` の標準の形）。リポジトリを作る道具（`reprepro` か `aptly` など）と、置く場所（静的なファイルの置き場）は、まだ決めていません。要決定（5 の 3）。

## 3. Apple 側で、持ち主がやること

次の手順は、公開されている Apple の手順についての私の知識で書いています。**画面の名前は変わることがあります。** 「要確認」のところは、いまの画面で確かめてください。この Mac では、何も確かめていません（鍵とキーチェーンには触れていません）。

### 3.1 手順

1. **Apple Developer Program に入る。** Apple ID（二要素認証つき）で、developer.apple.com の Program の案内から、個人（Individual）として申し込む。年会費がかかる（金額は、いまの案内で確かめる）。承認まで、数日かかることがある。要確認：個人のときの表示名（証明書に載る名前）の扱い。**この名前を、どこにも書かない。**
2. **署名の要求（CSR）を作る。** Mac の「キーチェーンアクセス」→ メニュー「証明書アシスタント」→「認証局に証明書を要求…」。メールアドレスと名前を求められるが、**証明書に載る**ので、公開してよいものだけを入れる（要確認：ここで入れた名前が、証明書の表示にそのまま使われるか）。「ディスクに保存」を選ぶ。秘密鍵は、この Mac のログインキーチェーンにできる。
3. **証明書を 2 つ作る。** developer.apple.com の Account → 「Certificates, IDs & Profiles」→ 「Certificates」→ 「+」。種類は **Developer ID Application**（バンドルへの署名用）と **Developer ID Installer**（pkg への署名用）。それぞれに、手順 2 の CSR を渡す。要確認：Developer ID の証明書は、いまの画面で「Software」の下にあるか、作れるのは Account Holder（個人なら本人）だけか、CSR のあとに出る「Profile Type」（G2 Sub-CA）の選択肢。
4. **証明書を入れる。** ダウンロードした `.cer` をダブルクリックして、ログインキーチェーンに入れる。2 つとも、秘密鍵と対になって見えること。
5. **鍵のバックアップ。** キーチェーンアクセスで、証明書（秘密鍵つき）を `.p12` に書き出す。強いパスフレーズをかけ、パスワードマネージャーのパスフレーズと一緒に、**リポジトリの外**（持ち主の暗号化したバックアップ）に置く。Mac を失うと、同じ証明書での署名ができなくなり、許可が引き継げなくなる（1.4）ため、これは大事。
6. **証明書をハッシュで指す。** `security find-identity -v -p codesigning` で、Application 証明書の行の、40 桁の 16 進数を控える。Installer 証明書は、`-p codesigning` では出ないことがある。そのときは `-p basic` で探す（要確認）。**この出力には名前が入る。出力を、チャット、issue、ログに貼らない。** 控えるのはハッシュだけ。
7. **公証の資格情報を作る。** 下の 3.2 のどちらか。
8. **公証の資格情報を、キーチェーンに保存する。** `xcrun notarytool store-credentials "istesso-notary" --key <.p8 のパス> --key-id <キー ID> --issuer <発行者 ID>`。プロファイル名（`istesso-notary`）は、自由に決めてよい。保存されるのは、ログインキーチェーンの中。
9. **スクリプトに教える。** 下の 3.3 の環境変数を、そのシェルだけに設定する（`~/.zshrc` に書くなら、リポジトリの外のファイルにする）。
10. **署名なしで一度通す。** `packaging/macos/build-pkg.sh` を、環境変数なしで動かして、pkg ができること。そのあと、環境変数を付けて、署名つきで 1 回作り、`pkgutil --check-signature` と、`spctl --assess --type install` で確かめる。

### 3.2 公証の資格情報：どちらにするか

| | App Store Connect の API キー（提案） | アプリ用パスワード |
|---|---|---|
| 作る場所 | App Store Connect → 「ユーザとアクセス」→ 「統合」→ 「App Store Connect API」→ チームキー（要確認：個人のアカウントでの表示と、必要なロール） | appleid.apple.com → サインインとセキュリティ → アプリ用パスワード |
| コマンドに出るもの | キー ID、発行者 ID、`.p8` ファイル | **Apple ID のメールアドレス**、チーム ID、パスワード |
| 漏れたとき | そのキーだけを失効できる。権限が公証に限られる（ロールを小さくする） | Apple ID に結びつく。取り消しは、そのパスワードだけ |

提案は **API キー** です。理由は、コマンドと設定に、持ち主のメールアドレスと名前が出ないこと（名前を書かない決定に合う）、キーを個別に失効できることです。`.p8` は、作った直後に 1 回だけダウンロードできます（要確認）。なくしたら、作り直します。`.p8` は、リポジトリの外に置きます。使うのは、手順 8 の 1 回だけです。個人のアカウントでキーが使えない場合は、アプリ用パスワードにします（その場合も、保存は `store-credentials` で、スクリプトにはプロファイル名だけが渡る）。

### 3.3 環境変数

| 変数 | 中身 | どこに置くか |
|---|---|---|
| `ISTESSO_SIGN_APP_IDENTITY` | Developer ID Application のハッシュ | 持ち主のシェル。ハッシュは秘密ではないが、名前は含まない形で |
| `ISTESSO_SIGN_INSTALLER_IDENTITY` | Developer ID Installer のハッシュ | 同上 |
| `ISTESSO_NOTARY_PROFILE` | `store-credentials` のプロファイル名 | 同上。資格情報の本体は、キーチェーンの中 |
| `ISTESSO_ENTITLEMENTS` | 任意。entitlements のファイル | 同上 |

CI には、これらも、鍵も、証明書も渡しません（決定）。CI がやるのは、署名なしのビルドと検査までです。署名は、持ち主の Mac で、CI が作ったバンドルを取り込んで行います。**この受け渡しの形は、まだ決めていません**（5 の 4）。

## 4. 持ち主が決めること（最初のリリース）

### 4.1 自動更新

| | 内容 |
|---|---|
| 要るもの | (1) 更新の一覧（フィード）を置く場所。(2) 更新の署名。Developer ID の署名とは別に、更新ファイルへの署名の鍵が要る（Mac は Sparkle の EdDSA のような形。Ubuntu は `apt` の署名）。(3) クライアントが、定期的に確かめて、署名を検証する仕組み |
| 提案する形 | Ubuntu は `apt` がそのまま更新の仕組み（`unattended-upgrades` を使うかは、利用者の選択）。Mac は、まず「新しい版があります」を知らせるだけにし、入れるのは利用者が pkg を開く |
| 危険 | 更新の鍵が漏れると、全員の PC で、他人のコードが動く。更新の途中で、セッションが切れる。クライアントとホストの版が合わなくなる（プロトコルの互換）。確かめるとき、IP アドレスと版が、フィードの置き場に知られる |
| 含める場合 | 最初のリリースの前に、フィードの置き場、更新の鍵（持ち主の Mac。バックアップは 3.1 の 5 と同じ扱い）、検証のコード、互換の決まりを作る。M9 が延びる。セキュリティの面で、外部レビュー（4.2）の対象に足す |
| 含めない場合 | 最初の版は、手で入れ直す。許可は、1.4 のとおり残る。新しい版は、利用者が pkg を開く、`apt upgrade` をする。**私の見方：含めない。** 範囲がせまいうちに、署名と許可の引き継ぎだけを確かにしたい。更新の鍵は、あとから足せる（ただし、最初の版に、更新を確かめる部分が入っていないと、古い版は自分で更新できない。それは受け入れる） |

### 4.2 ペアリング部分の外部レビュー

| | 内容 |
|---|---|
| 対象になるもの | `istesso-pair`（SPAKE2 の使い方、鍵の導き方 HKDF、コードの試行回数の制限、確認の手順）、`istesso-link`（Noise の設定、端末の鍵の固定と失効、権限の分け方）、鍵とコードをメモリや記録に残さないこと、制御チャンネルの読み取り部分（壊れた入力への強さ）。設計は ADR 0006 と 0007 |
| ふつうの範囲の決め方 | 「プロトコルの設計と、その実装の読み合わせ」が基本。対象のコード行数と、仕様の文書（ADR）を渡し、レビューする人が何日使うかを決める。範囲の外（OS、依存クレートの中身）は、はっきり書く。結果は、指摘の一覧と、直したあとの確認 |
| 時間と費用 | **粗い推測です。見積りをとったわけでも、調べたわけでもありません。** 一般に聞く話から：対象が数千行の暗号の部分なら、レビュー自体が 1〜3 週間、予約まで数週間から数か月、費用は数万ドル規模、と考えている。依頼先、範囲、地域で大きく変わる。実際の見積りを、2〜3 か所からとって決める。オープンソースの監査を助ける団体があるとも聞くが、条件は未確認 |
| 含める場合 | 最初のリリースの前に頼む。直す時間が、日程に入る。公開の文書に「外部レビュー済み」と書ける。依頼のあいだ、暗号の部分を凍結する（M5 以降の変更が待つ） |
| 含めない場合 | 最初のリリースには、「未レビュー」と、はっきり書く。ペアリングを使う範囲を、同じ LAN に限る（R-13 の VPN の条件）まま。M9 は早く進む。レビューは、あとでも頼める。**私の見方：含める。** 暗号の部品は借り物（RustCrypto、snow）でも、組み合わせた手順は自作で、組み合わせの誤りは、書いた本人には見つけにくい。公開は、そのあとにする |

## 5. 今は範囲の外のこと、未決のこと

### 範囲の外

- 本物の証明書での署名、公証の提出、公開、リポジトリの作成（この段階は、スクリプトと文書だけ）。
- Windows（M10）、AURA クライアント（Android XR）。
- Mac ホスト専用のバンドルと、ログイン前のホスト（M4 の結果を待つ）。
- GStreamer、Wolf のコンポジターなど、ホストの部品の同梱（できたときに足す）。
- `count-encoder-sessions`、udev の決まりを機器の一覧から作る仕組み（`m7-usb-devices` の関数）。
- `.dmg`、Homebrew、AppImage。

### 未決（持ち主への 1 つの一覧）

| # | 聞くこと | 私の提案 |
|---|---|---|
| 1 | 自動更新を、最初のリリースに含めるか（4.1） | 含めない |
| 2 | ペアリングの外部レビューを、最初のリリースの前にするか（4.2） | 含める。見積りは 2〜3 か所から |
| 3 | Ubuntu のリポジトリの置き場と道具。リリース用の GPG 鍵の保管 | 持ち主の手元の鍵。道具は `reprepro` か `aptly` |
| 4 | 署名つきのビルドを、CI が作ったバンドルから、持ち主の Mac でどう作るか（受け渡しの形） | 持ち主の Mac が、CI の成果物を取り込んで、`build-pkg.sh` を動かす |
| 5 | バンドル ID（`dev.istesso.app`）と、アプリの名前。変えると許可が引き継がれない | 名前の決定と一緒に、公開の前に決める |

## 6. 確かめたこと

2026-11-17、Mac の上だけで確かめました（結果は [packaging/README.md](../packaging/README.md) の最後）。`.pkg` はダミーのバンドルで署名なしのまま作り、インストールしていません。`.deb` は構文の確認と、偽の `dpkg-deb` での中身の確認だけです。署名、公証、ログイン時の起動、更新で許可が残ることは、**まだ確かめていません**。
