# 暗号化した映像の経路：動作の確認と、最初の見立て

- 日付：2026-11-17（01:17〜01:40）
- コミット：972ed0e（`istesso-media`、ホストのスクリプト、ビューアー、集計の道具）。この記録は、次のコミット
- 目的：映像を、暗号化と認証つきの経路（[ADR 0015](../adr/0015-media-transport.md)。制御チャンネルと同じ通信路を、映像のための TCP の接続で使う）で、2 台の実機のあいだに通す。フレームが欠けずに届き、復号され、窓に出ること、キーフレームの求めと、ビューアーの起動し直しが働くことを確かめる。あわせて、暗号化していない UDP の経路と並べて、どこにどれだけ時間がかかっているかの、最初の見立てを取る。
- 結論：**通った。** 2 分のあいだ、ホストが送ったフレームは、順番どおりに全部届き、全部が復号されて、窓に渡った。キーフレームは、つないだときに 1 枚出るだけで、見る側から求める必要はなかった。ビューアーを強制終了して 1 秒後に起動し直すと、つないでから 85 ms で最初の絵が出た。**1 台の時計の中で測れる区間では、暗号化した経路は、UDP の経路より遅くなかった**（ホスト：中央値 0.33 ms と 0.32 ms。Mac：0.14〜0.15 ms と 0.27 ms）。

## これは、遅延の計測ではない

- **合格ラインの指標（手元の窓との差）は、測っていない。** 画面での計測（`istesso-screen-probe`）を使っていない。入力も送っていない。絵が画面に出た時刻は、見ていない。
- **Mac の側のプログラムは、どれもシェルから起動した**（優先度 20。アプリとして起動すると 46 前後）。今夜は、同じ Mac でほかの流れの長い試験が動いていて、新しいアプリのバンドルを `open` で起動すると、macOS がローカルネットワークの許可を作り直し、その試験の接続が切れると分かったため。シェルから起動したプログラムは、タイマーとスレッドの起き上がりが遅れる（[README](README.md) の「Mac で計測するプログラムの起動のしかた」）。**Mac の側の時間は、上限として読む。**
- 窓は、内蔵ディスプレイの左上の隅に、430×180 ポイントで出した（3440×1440 の絵を縮めて出している）。前面に固定していない。判定の置き方（外部ディスプレイの全体に等倍）ではない。
- 2 台の上では、ほかの流れ（音の長い試験、人が試すための窓の経路）が動いていた。静かな状態ではない。
- 判定は、人の合図で、画面での計測と合わせて、別に測る。

## 結果

### フレームの数

| 回 | ホストが圧縮 | 相手に送った | Mac に届いた | VideoToolbox に渡した | 復号した | 窓に渡した | 連番の飛び | キーフレーム（うち、見る側が求めた） |
|---|---|---|---|---|---|---|---|---|
| 暗号化（01:26） | 10,253 | 10,201 | 10,200 | 10,200 | 10,200 | 10,200 | 0 | 2（0） |
| UDP（01:28） | 10,248 | — | 10,200 | 10,199 | 10,199 | 10,199 | 欠け 0 回 | 2（1） |
| 暗号化、起動し直し（01:30） | 10,253 | 10,102 | 5,092 と 5,008 | 5,092 と 5,008 | 5,092 と 5,007 | 5,092 と 5,007 | 0 | 3（0） |
| 暗号化、受信スレッドの優先度を上げた（01:33） | 10,241 | 10,192 | 10,190 | 10,190 | 10,189 | 10,189 | 0 | 2（0） |
| UDP（01:35） | 10,234 | — | 10,185 | 10,184 | 10,184 | 10,184 | 欠け 0 回 | 2（1） |
| 暗号化（01:37） | 10,260 | 10,198 | 10,197 | 10,197 | 10,197 | 10,197 | 0 | 2（0） |

- 暗号化した経路では、ホストは、相手がつながっていて、キーフレームを受け取ったあとのフレームだけを送る。「相手に送った」と「届いた」の差の 1〜2 枚は、ビューアーを止めた瞬間に、途中にあったフレームである。
- キーフレームの 2 枚は、パイプラインの最初の 1 枚と、ビューアーがつないだときの 1 枚。暗号化した経路では、**見る側は 1 度も求めていない**（つないできた相手には、ホストが、求められなくても出す）。UDP の経路では、見る側が始めに 1 回求めている。
- 接続がその場で受け取りきらなかったフレームは、どの回も 0 枚。

### エンコーダーを出てから、VideoToolbox に渡すまで

1 台の時計の中で閉じる区間だけを並べます。2 台の時計は、比べていません。単位は ms、「中央値 / 95% / 99%」。

| 区間 | 時計 | 暗号化（01:26） | 暗号化（01:37） | UDP（01:28） | UDP（01:35） |
|---|---|---|---|---|---|
| 圧縮が済んでから、ライブラリーに渡すまで（UDP：最初のパケットを渡すまで） | ホスト | 0.217 / 0.419 / 0.484 | 0.219 / 0.412 / 0.473 | 0.157 / 0.294 / 0.344 | 0.154 / 0.295 / 0.358 |
| 渡してから、封をして書き終えるまで（UDP：最後のパケットを渡すまで） | ホスト | 0.108 / 0.192 / 0.239 | 0.108 / 0.193 / 0.231 | 0.160 / 0.346 / 0.413 | 0.159 / 0.343 / 0.406 |
| **ホストの合計** | ホスト | **0.325** / 0.600 / 0.683 | **0.329** / 0.595 / 0.663 | **0.318** / 0.632 / 0.709 | **0.314** / 0.633 / 0.713 |
| 最初のバイトから、1 フレームを読んで開け終えるまで（UDP：最後のパケットまで） | Mac | 0.119 / 0.294 / 0.610 | 0.124 / 0.341 / 0.756 | 0.190 / 0.560 / 0.777 | 0.156 / 0.574 / 0.946 |
| そこから、VideoToolbox に渡すまで | Mac | 0.022 / 0.044 / 0.098 | 0.024 / 0.046 / 0.104 | 0.050 / 0.170 / 0.377 | 0.096 / 0.228 / 0.498 |
| **Mac の合計** | Mac | **0.142** / 0.335 / 0.702 | **0.149** / 0.384 / 0.891 | **0.267** / 0.648 / 0.981 | **0.269** / 0.715 / 1.365 |
| 復号（VideoToolbox に渡してから、絵が返るまで） | Mac | 2.96 / 3.64 / 5.05 | 3.02 / 3.74 / 5.23 | 2.43 / 3.51 / 4.42 | 3.05 / 3.66 / 4.89 |
| 絵が返ってから、窓のレイヤーに渡すまで | Mac | 0.34 / 0.70 / 1.54 | 0.35 / 0.70 / 1.47 | 0.18 / 0.58 / 1.22 | 0.37 / 0.74 / 1.63 |

- **ホスト**：合計は、中央値で 0.01 ms しか違わない。暗号化した経路は、Python のスクリプトがライブラリーを呼ぶ前後（バッファーの取り出しと写し）で 0.06 ms 余分にかかり、封をして書くところで、パケットに分けて渡すより 0.05 ms 短い。裾（95%、99%）は、暗号化した経路のほうが、わずかに短い。
- **Mac**：暗号化した経路のほうが、中央値で 0.12 ms 短い。GStreamer の中でパケットを組み直して、アクセスユニットに切り直す仕事がなくなり、ライブラリーが 1 フレームを 1 つのかたまりで渡すためである。開封そのものは、この大きさのフレームで 0.015 ms（下の「封と開封」）。
- 復号と、窓に渡すまでは、経路によらないはずの区間で、回ごとに 0.5 ms ほど動いている（01:28 の UDP の回だけが短い）。シェルの優先度で動かしたためのばらつきと見ている。**この 2 行から、経路の優劣は読めない。**
- 2 台のあいだ（ホストが渡してから、Mac に最初のバイトが届くまで）は、時計を比べないので、値としては出せない。同じ 5 秒のうちでいちばん速かったフレームより、どれだけ余分にかかったか、だけを見た：暗号化した経路で中央値 0.22〜0.23 ms、95% 0.58〜0.68 ms。UDP の経路で中央値 0.31〜0.44 ms、95% 0.83〜1.04 ms。Mac の受信スレッドが起きるまでの時間が、ここに入っている。

### フレームの届く間隔

| 回 | 中央値 | 95% | 99% | 最大 | 23.5 ms（更新 2 回ぶん）を超えた回数 | 50 ms を超えた回数 |
|---|---|---|---|---|---|---|
| 暗号化（01:26） | 11.78 ms | 12.64 ms | 13.90 ms | 25.0 ms | 2 | 0 |
| 暗号化（01:37） | 11.77 ms | 12.79 ms | 14.66 ms | 24.3 ms | 6 | 0 |
| UDP（01:28） | 11.78 ms | 12.71 ms | 14.20 ms | 24.0 ms | 4 | 0 |
| UDP（01:35） | 11.77 ms | 12.93 ms | 14.31 ms | 35.0 ms | 6 | 0 |

違いは見えない。23.5 ms を超えた回は、どちらの経路にも同じくらいあり、ホストが書き込みを待たされた回（`queued`）は 0 なので、TCP の再送ではない（ADR 0015 の「データグラムに移る条件」の 2 つ目には、当たらない）。コンポジターがフレームを 1 回ぶん待たせた回と見ている（[M1 の計画](../m1-plan.md) の手順 5 の表）。確かめていない。

### ビューアーを強制終了して、起動し直す（01:30 の回）

1 分たったところで、ビューアーを `kill -KILL` で止め、1 秒後に起動し直した。

- ホストは、止まったことにすぐ気づき、次のフレームから、誰にも送らなくなった（送らなかったのは 101 フレーム、1.19 秒ぶん。止めていた 1 秒と、起動にかかった時間）。ホストのパイプラインは、動き続けた。
- 起動し直したビューアーは、起動から 4 ms でつながり、ホストは、求められなくてもキーフレームを 1 枚出した（71 kB）。**つないでから 10.5 ms で、そのキーフレームが届き、85 ms で最初の絵が出た。** あいだの 67 ms は、VideoToolbox の準備（復号のセッションを作る時間）で、最初のキーフレームの復号は 8 ms。
- 起動し直したあとの 59 秒は、5,008 フレームが連番どおりに届き、止める前と同じ値だった（Mac の合計：中央値 0.158 ms）。
- 見る側がキーフレームを求めた回数は、0。古い接続は、ホストの側で「接続が閉じられた」として片付いた。

### 受信スレッドの優先度を上げる（01:33 の回）

ビューアーに `ISTESSO_RECEIVE_REALTIME` を付けて、受信と復号のスレッドを、音のスレッドと同じ種類の優先度（time constraint）で動かした。

| 区間（Mac） | 付けない（01:26、01:37） | 付けた（01:33） |
|---|---|---|
| Mac の合計：中央値 | 0.142、0.149 ms | 0.137 ms |
| 95% | 0.335、0.384 ms | 0.277 ms |
| 99% | 0.702、0.891 ms | 0.370 ms |
| 最大 | 6.2、4.9 ms | 1.2 ms |
| 2 台のあいだの、余分にかかった時間の 99% | 1.52、2.28 ms | 0.63 ms |

中央値は変わらず、**遅い側の裾が短くなる。** ただし、ビューアーをシェルの優先度で動かした上での値で、アプリとして起動したときにも同じだけ効くかは、分からない。朝に、判定と同じ起動のしかたで比べる。既定では、付けない。

### 封と開封にかかる時間

通信路の 2 つの端を、ネットワークを通さずにメモリーの上でつなぎ、フレームに封をする時間（ヘッダーを付け、ChaCha20-Poly1305 で封をして、ソケットに渡す形にするまで）と、開ける時間を測った（`cargo run --release -p istesso-media --example seal-bench`。2,000 フレームずつ）。単位は µs、中央値（99%）。

| フレームの大きさ | Mac（M4）：封 | Mac：開封 | ホスト：封 | ホスト：開封 |
|---|---|---|---|---|
| 7.5 kB（判定の文字の絵） | 15（31） | 15（31） | 6.5（23） | 6.3（22） |
| 45 kB（難しい絵、30 Mbps） | 70（75） | 72（76） | 23（25） | 23（25） |
| 140 kB（難しい絵、100 Mbps。通信路のメッセージ 3 つ） | 216（226） | 219（230） | 71（76） | 70（74） |

- Mac の値は、アプリとして起動して取った（00:59 ごろ。この記録の中で、アプリとして起動したのは、これだけ）。シェルから起動した 2 回は、同じ値の回と、約 2 倍かかった回があった（7.5 kB で 30 µs）。
- 判定の絵では、**封と開封を合わせて、2 台で約 0.02 ms。** 余裕（0.7 ms）に対して、小さい。
- Mac がホストの 3 分の 1 の速さなのは、暗号のクレート（RustCrypto の `chacha20`）が、Mac では、どの CPU でも動く書き方のほうを使うため（NEON を使う書き方は、ビルドのときに指定しないと入らない）。難しい絵で開封を縮めたくなったら、ここに手がある。変えていない。

## わかったこと

- 暗号化した経路は、2 台の実機のあいだで働く。ペアリングで固定した鍵で、相手を確かめてから送っている。
- 1 台の時計で測れる区間では、UDP の経路より遅くない。ホストは同じ、Mac は 0.12 ms 短い。**ただし、合格ラインの指標に何 ms 効くかは、まだ分からない。** 2 台のあいだの時間と、画面に出るまでの時間を、測っていないため。
- 有線の 2 分 × 4 回では、TCP が再送を待った跡は、なかった。
- つなぎ直しは、85 ms で絵が戻る。その大半は、VideoToolbox の準備である。

## まだ確かめていないこと

- **遅延の判定。** 画面での計測を使って、UDP の経路と、同じ日に同じ置き方で比べる（ADR 0015 の「データグラムに移る条件」の 1 つ目と 2 つ目は、その値で見る）。
- **Mac の側の値を、アプリとして起動して取り直すこと。** いまの値は、上限である。ビューアーをアプリとして起動するには、ローカルネットワークの許可が要る（暗号化した経路では、ビューアーのほうからホストへつなぎに行く）。許可を尋ねられたら、人が答える。
- `scripts/m1-step3-breakdown.py` の、暗号化した経路の集計。画面での計測の記録が要るので、実際の回では動かしていない（UDP の記録を、暗号化した経路の形に書き直したもので、動くことだけを見た）。
- 難しい絵（`--picture hard`。フレームが 45 kB）と、Wi-Fi。
- 見る側が 2 台のとき。
- 受信スレッドの優先度を上げることの効き目（アプリとして起動したとき）。

## 動かし方

ホスト（`tmux` の中で。`GST_PLUGIN_PATH` は、これまでと同じ）：

```sh
cargo build --release -p istesso-media
python3 -u scripts/m1-step3-host.py --to-channel 47831 --size 3440x1440 --fps 85 --frames cuda \
    --no-input --render-node /dev/dri/renderD129 --log host-frames.jsonl
```

`--no-input` は、同じホストで、人が試すための窓の経路が動いているときに付ける（入力を受け取るソケットを、取り上げないため）。

ISTESSO_CHANNEL=<ホストの有線のアドレス>:47831 macos/gst-viewer/build/gst-viewer \
