## 4. 起きたことと、直したこと

### 4.1 Finder の確認が 2 回出た（1 回目、18:25:51 ごろと 18:25:54 ごろ）

- 出たもの：「URL x-istesso-dev-trial://open/alpha を開くデフォルトのアプリケーションが設定されていません」。人が 2 回とも取り消した。
- わけ：Opener を、受け取る側（Main）の URL の仕組みが使える状態になったかを確かめずに呼んだ。Main は 2 秒前に起動していたが、確かめていなかった。あとで分かったこと：一時フォルダーの包みは `in-temp-dir` の印が付き、識別子からは見つからない（2 の表）。URL の既定のアプリにもならなかったと考える（**考え**。確かめていない）。
- 直したこと：2 回目は、URL を使わず、アプリのあいだの知らせ（`NSDistributedNotificationCenter`）で頼んだ。LaunchServices に探させないので、確認は出ない。呼ぶ前に、受け取る側が動いていることを `lsappinfo` で確かめた。
- これからの決まり：画面に窓や確認が出る手順は、先に協調役に伝え、人に知らせてから行う。呼ぶ前に、受け取る側の登録を読むだけで確かめ、受け取る側の名前が出たときだけ呼ぶ。

## 5. 文書とコードから考えたこと（試していない）

- **Dock と ⌘Tab の 1 項目は、プロセス 1 つ**：2 の `Foreground` と、3 の 1、2 から、そう見える。`NSApplication.ActivationPolicy` の文書は「`regular` は Dock に出る」と書いているが、⌘Tab には触れていない。
- **名前は、包みの `Info.plist` から来る**：3 の 4 と 2 の記録から。動いているあいだに替える公開の口は、見つけていない。だから、アプリの名前で出すには、アプリごとの包みが要る。**アイコンは、動いているあいだに替えられる**（3 の 2）。
- **ローカルネットワークの許可**（TN3179）：許可はコードの署名で見分ける。アプリが起動した補助のプログラムの通信は、そのアプリのものとして扱う。その場の署名では、見分けが確かでない。UUID が同じだと、おかしな動きになることがある。持ち主の条件（下の 6）は、アプリごとの包みが**ネットワークに触れない**ことなので、この問題は避けられる。Unix ドメインソケットは、TN3179 の「ローカルネットワーク」（ブロードキャストのできる口の IP のネットワーク）の外と読める（**読み取り**）。
- **IOSurface**：Apple の文書は、IOSurface を「プロセスの境目を越えて分けられるフレームバッファー」と書き、「複雑な画像の展開と描画を別のプロセスに移すのに、よく使われる」と書いている。`IOSurfaceCreateXPCObject`（XPC で渡す）は、文書にある。Mach ポートで渡す関数（`IOSurfaceCreateMachPort` など）は、名前を一覧で確かめていない。
- **Gatekeeper**：手元で作ったファイルには隔離の印が付かない（2 の `xattr`）ので、起動のときに Gatekeeper の確かめは出ないと考える。今日の試しでも、Gatekeeper の確認は出ていない（人の答え 6）。`com.apple.provenance` が、これから何に使われるかは分からない。

## 6. C の見積もり（持ち主の条件で）

持ち主の条件：**アプリごとの包みは、ネットワークに触れない。** 接続を持つのは、メインのプロセス 1 つ。アプリごとのプロセスは、絵と入力を、メインと手元でやり取りする。

### 6.1 受け渡しの形と、足される遅れ（考え。測っていない）

| 形 | 絵 | 入力 | 1 フレームに足される遅れ（考え） | 作りの変わり方 |
|---|---|---|---|---|
| **H1：圧縮した絵を渡し、子が展開する** | メインが受けて（復号して）、圧縮したままの絵を、共有メモリーの輪に書き、子を起こす。子が VideoToolbox で展開して、層に出す | 子が受けたイベントを、共有メモリーの輪か Unix ソケットでメインへ。メインの入力のスレッドが送る | 書き写し（1 フレーム数十〜数百 KB。数 µs〜十数 µs）と、子を起こす時間（数十 µs。混んでいるときは、それより長くなりうる） | 展開と表示のコードは、いまの試作と同じものを子で使える。関門を通ったコードを変えずに済む |
| **H2：展開した絵を渡す** | メインが展開して、IOSurface（はじめに作った輪を、XPC か Mach ポートで 1 回渡す）の番号だけを子に知らせる。子は層の中身をその面にする | H1 と同じ | 知らせ 1 回（数十 µs と考える）。絵は書き写さない | 展開をメインに、表示を子に分ける。表示の時刻合わせ（いつ層を替えるか）が、プロセスをまたぐ |
| H3：表示もメインが行い、子の窓に描かせる | 公開の口では、ほかのプロセスの窓の中に層を出す方法を見つけていない（`CALayerHost` は公開されていない） | — | — | 勧めない |

- 入力の受け渡しは、関門のときの形（ビューアーが手元のソケットに書き、別のプログラムが読んで送る）に、ほぼ戻る。関門は、その形で通った。ADR 0018 は、その受け渡しを 1 回減らすために 1 つのプロセスにした。**ADR 0018 の「並ぶこと」の計測（試作と自前のクライアントを、同じ日に比べる）の、入力の区間の差が、そのまま「受け渡し 1 回の値段」になる。** 別に測る前に、その結果を使える。
- **小さな計測の形**（0.5〜1 日。どの Mac でもよい。ネットワークなし）：親と子の 2 つのプログラム。親が 120 Hz で時刻を書いた「絵」（H1：100 KB の塊。H2：IOSurface の番号）を送り、子が受けた時刻を記録する。逆向きに、子が 1 kHz で「入力」を送る。手段ごと（Unix データグラムソケット、共有メモリーとセマフォ、Mach メッセージ、XPC）に、静かなときと、CPU に負荷をかけたときの 50、95、99 パーセンタイル。そのあと、本物の差は、画面での計測（`macos/screen-probe`）で、1 つのプロセスと分けた形を比べる。

### 6.4 局所の入口の守り（持ち主の条件、2026-11-17 19:08）

C では、メインのアプリに、同じ Mac のプロセスのための入口ができる。持ち主の条件：

- **確かめた包みだけ**が、絵を受け、入力を送れる。メインは、つないできたプロセスのコードのハッシュ（CDHash）を、その包みを作った、署名したときに記録したものと比べる。違えば断り、その包みを作り直す（Chromium と同じ形。[m3-launcher.md](../m3-launcher.md) の 7.4）。
- 包みが届くのは、**自分のセッションだけ**。ほかのアプリの絵にも、入力にも、セッションの一覧にも届かない。

**相手の身元の確かめ方**（提案。下の根拠は、どれも**読んだことからの考え**で、試していない）

| 段 | すること |
|---|---|
| 1. 入口 | H1（6.1）では、Unix ドメインソケット。置き場所は、ADR 0010 の 13 と同じく、本人しか入れないランタイムディレクトリ（0700）。H2（IOSurface を渡す）では、Mach ポートの口が要る（IOSurface の Mach ポートは、Unix ソケットでは運べない） |
| 2. 相手の監査トークン | Unix ソケットでは、つながったときに `getsockopt(LOCAL_PEERTOKEN)` で、相手の `audit_token_t` を取る。Mach メッセージでは、受けるときに監査の付け足し（`MACH_RCV_TRAILER_AUDIT`）を頼み、メッセージごとに送り手のトークンを読む |
| 3. トークンから署名へ | `SecCodeCopyGuestWithAttributes` に `kSecGuestAttributeAudit` でトークンを渡し、相手のコードの対象を得る。`SecCodeCheckValidity` で、動いているコードがいまも正しいかを確かめる |
| 4. ハッシュの比べ | `SecCodeCopySigningInformation` で CDHash を読み、メインの記録（包みごとに、作ったとき、署名し直したときの CDHash と、その包みのアプリ）と比べる。違えば、つなぎを閉じ、包みを作り直す |
| 5. 権利をつなぎに結ぶ | 記録から、その包みのアプリが決まる。つなぎは、そのアプリの、そのつなぎで開いたセッション 1 つにだけ結ぶ。包みは、セッションの ID を名乗らない（名乗っても使わない）。使える頼みは、「自分のセッションの絵を受ける」「入力を送る」「窓を閉じる、アプリを終える」だけ。一覧、ほかのセッション、つなぐ、ほかのアプリを開く、は口に無い |

**プロセス番号（pid）で確かめると、なぜ危ないか、監査トークンで何が変わるか**（考え）

- pid は、プロセスが終わると、ほかのプロセスに使い回される。「pid を得る」と「その pid のコードを確かめる」のあいだに、相手が終わり、別のプロセスが同じ pid を得ると、別のプロセスのコードを確かめてしまう。攻める側は、pid を一回りさせて、終わったばかりの正しいプロセスのふりができる。Apple の開発者フォーラムで、Apple の技術支援の担当者が、この理由で pid ではなく監査トークンを使うよう勧めている（スレッド 72881、652363、665018、849029。`LOCAL_PEERTOKEN` は macOS 13 から使える、とスレッド 850777）。
- 監査トークンは、pid に加えて、その pid の「代」を表す値を持つので、使い回された pid とは食い違い、確かめが失敗する（と理解している。exec したときも代が変わるかは、**確かめていない**）。
- トークンは、つながったときのもの。そのあとで、確かめたプロセスが、ソケットのファイル記述子を、ほかのプロセスに渡すことはできる（`SCM_RIGHTS`）。それは見分けられない。だから、包みのコードが、記述子を渡さないこと（下の、コードを固定すること）に頼る。

**その場の署名で、ライブラリーの確かめを切った起動の部品だから、何を固定するか**

起動の部品は、どのライブラリーでも読める（T1 の (c)）。だから、起動の部品の CDHash だけでは足りない。次の全部を固定する。

| # | 固定するもの | どうやって |
|---|---|---|
| 1 | 起動の部品のコードと、`Info.plist`（どのアプリの包みか、フレームワークの場所） | CDHash。`Info.plist` とリソースは、署名に封じられるので、CDHash が同じなら、中身も同じ |
| 2 | ほかから入り込まれないこと | Hardened Runtime を付ける。付ける権利は「ライブラリーの確かめを切る」だけにし、`DYLD_` の環境変数を許す権利や、デバッガーを許す権利は付けない（考え：これで、環境変数でのライブラリーの差し込みと、ほかのプロセスからの書き換えが止まる） |
| 3 | 読むフレームワーク | 場所は `Info.plist`（1 で固定）に書き、環境変数や引数からは取らない。起動の部品は、読む前に、フレームワークの署名が Istesso の Developer ID のチームの要件を満たすかを確かめる（`SecStaticCodeCheckValidity` と要件）。確かめてから読むまでのあいだに、ファイルを替えられる隙は残る。Istesso.app は `/Applications` にあり、公証したアプリは、ほかのチームからの書き換えから守られる（WWDC22）、と考える |
| 4 | つなぐ前の、メインの側の確かめ | 上の表の 2〜4。加えて、メインは、包みを作ったときに、その包みが読むはずのフレームワークの場所を記録しておく |
| 5 | 版 | 包みに版を書き（1 で固定）、メインの版と合わなければ、メインが断って作り直す |

**脅威の覚え書きに載せること**

1. C では、メインに、同じ Mac のプロセスのための入口ができる（絵を受ける、入力を送る）。同じユーザーのほかのプロセスが、包みのふりをして、ほかのアプリの画面を見たり、入力を入れたりすることが脅威である。
2. 守り：入口は 0700 のディレクトリ。相手の身元は監査トークンから（pid は使わない）。CDHash を記録と比べる。つなぎは、包みのアプリの、1 つのセッションにだけ結ぶ。一覧やほかのセッションの口は無い。
3. 残る隙：(a) 包みがファイル記述子をほかへ渡すこと（包みのコードを固定して防ぐ）。(b) フレームワークを確かめてから読むまでの、ファイルの差し替え。(c) 同じユーザーが、包みとその記録を、両方とも書き換えられる場合（記録はメインだけが書く場所に置くが、同じユーザーの権限で書ける場所である）。(d) root、またはデバッガーの権利を持つプロセスは、どれも防げない。
4. ライブラリーの確かめを切ることは、起動の部品が何でも読めることを意味する。だから、起動の部品は、読むものを自分で確かめ、どこから読むかを外から受け取らない。
5. 包みはネットワークに触れない（持ち主の条件）。包みのローカルネットワークの許可は、ないままにする。

## 8. B の見積もり

- B の包み（開くだけ）は、S3 の包みと同じものの、窓を持たない形である。包みを作る、直す、消す道具は、C と同じものを使える。だから、B を先に作っても、むだにならない。
- 頼み方：本番の Istesso は `/Applications` にあるので、URL の仕組みも使えるはずだが（**考え**）、試しでは一時フォルダーのせいで確かめられなかった。勧めるのは、ADR 0010 の 13 と同じ形の **Unix ソケット**（ランタイムディレクトリ、0700）に「開いて」と書くこと。URL も、アプリのあいだの知らせも、ほかのプロセスから同じ頼みを出せてしまう。Istesso が動いていなければ、包みが Istesso を起こしてから書く。
- 手間：2 日（包みの道具 1.5 日。そのうち、C と共通のもの）。Spotlight で見つかるか、Dock に置いて残るかは、別の回（`~/Applications/Istesso Dev/` に包み 1 つ。人に先に知らせる）で確かめる。

## 9. 推し

1. **最初の版は A**（決まっている）。
2. **次に B**（2 日）。包みの道具は C と共通なので、C に進むときにも使える。Spotlight の回は、B を作る前に 1 回。
3. **C は、確定の判定のあと**に、受け渡しの小さな計測（0.5〜1 日）の結果を見て決める。ADR 0018 には、7 の表の右の列（いま、しておくと楽になること）だけを、いま入れてもらう。手間は小さく、C を選ばなくても、作りがきれいになる。

## 10. T1：その場の署名の起動の部品が、別に署名したフレームワークを読めるか（19:03）

[m3-launcher.md](../m3-launcher.md) の 7.5 の T1。小さな C のプログラム（起動の部品の代わり）が、フレームワーク（`TrialCore.framework`。関数 1 つ）を `dlopen` する。どちらも、その場の署名（チームなし）で、別々に署名した。包みにしない。シェルから直接動かした（窓なし、登録なし、ネットワークなし）。

**道具で見たこと**（`codesign -d -v` の出力と、プログラムの出力）

| 起動の部品の署名 | 結果 |
|---|---|
| (a) その場の署名だけ（`flags=0x2(adhoc)`） | 読めた（`trial core loaded`） |
| (b) その場の署名 ＋ Hardened Runtime（`flags=0x10002(adhoc,runtime)`）、権利なし | **読めない**。`dlopen` の答え：`code signature … not valid for use in process: mapping process and mapped file (non-platform) have different Team IDs` |
| (c) (b) ＋ 権利 `com.apple.security.cs.disable-library-validation` | 読めた |

フレームワークも起動の部品も、`TeamIdentifier=not set` だった。

**考えたこと**（試していない）

- Hardened Runtime を付けると、ライブラリーの確かめが掛かり、チームの違うもの（ここでは、チームのないもの同士）を読めない。Chromium の shim が、その場の署名に Hardened Runtime と「ライブラリーの確かめを切る」権利を付けているのは、これに当たる（7.4）。
- 本番の形（その場の署名の起動の部品が、**Developer ID で署名した**フレームワークを読む）でも、(a) と (c) は読めると考える。(b) は読めない。確かめるのは、Developer ID の版ができてからの T1'。
- 権利でライブラリーの確かめを切ると、起動の部品は、どのフレームワークでも読める。ほかのものを読まされないように、本体は、包みを作ったときの CDHash を記録し、つないできた包みを確かめる（Chromium と同じ形）。読むフレームワークの場所は、包みの中の書き換えられる値ではなく、本体の場所から決める。

## 11. 受け渡しの小さな計測（20:42〜20:49）

[m3-launcher.md](../m3-launcher.md) の 7.6。1 つのプログラムが自分を `fork` し、子が送り、親が受ける。窓なし、包みなし、ネットワークなし。協調役が、その間、システムのメディア解析のプロセスを止めていた。人は Mac から離れていた。

**道具で見たこと**（プログラムの出力。片道の時間。µs）

| 手段 | 向き | 静か：中央値 / 95% / 99% | 負荷（10 コア全部に回る仕事）：中央値 / 95% / 99% |
|---|---|---|---|
| Unix データグラムソケット | 絵（120 Hz、100 KB を書き写す） | 31 / 160 / 254 | 135 / 1602 / 2560 |
| 共有メモリーの輪と、アドレスで起こす合図（`os_sync_wait_on_address`） | 絵（同） | 35 / 57 / 197 | 34 / 1578 / 2485 |
| Unix データグラムソケット | 入力（1 kHz、64 B） | 12 / 21 / 37 | 9 / 1264 / 2276 |
| 共有メモリーの輪と、同じ合図 | 入力（同） | 9 / 16 / 30 | 6 / 1161 / 2170 |

- 1 つの回は 45 秒（絵 5,401、入力 45,001）。負荷のときの共有メモリーの入力は 40,317 で、受け手が遅れたあいだの入力が、まとめて読まれた（輪の最新だけを読む作りのため）。
- **Mach メッセージと IOSurface の手段は、測れなかった。** 1 秒の試し運転で、どちらも終わらなかった（20:42 の 1 回目）。私の計測のプログラムの不具合と考える（大きなメッセージをそのまま載せた作り、受け手に時間の限りがない）。止めたプロセスは、番号で終わらせた。そのあと、2 つの手段だけに減らして、全部の回に時間の限りを付けて、測り直した（20:43〜20:49）。

**考えたこと**（測っていない）

- 静かなときは、どちらの手段も、1 フレームに足される時間は、中央値で数十 µs、99% で 0.2 ms ほど。60〜120 Hz のフレームの間（8〜17 ms）に比べて小さい。
- 負荷のときの長い裾（95% で 1.2〜1.6 ms）は、受け手が CPU を取れるのを待つ時間と考える。計測のプログラムは、ふつうの優先度で動き、さらにエージェントのシェルから起動したので、低い優先度を受け継いでいる。本物のクライアントは、遅れに厳しい作業として宣言し、高い QoS で動く（ADR 0018）。その条件では、測っていない。
- C に使うなら：**共有メモリーの輪と、アドレスで起こす合図**（H1。圧縮した絵を書き写す）。静かなときの 95% と 99% がいちばん小さく、入力も同じ口で運べる。輪のファイル記述子は、6.4 の Unix ソケットで、確かめた包みにだけ渡す。
- この計測が示さないこと：高い QoS での値。IOSurface（H2）と Mach メッセージ。展開と表示を含めた、画面に出るまでの差（`macos/screen-probe` で、1 つのプロセスと比べる要がある）。本物の絵の大きさの揺れ。長い時間の振る舞い。

**同じ時間に動いていたもの**

- 測ったのは 20:43:15〜20:49:19（20:42 の 1 回目は、上のとおり、2 つの手段の試し運転で止まった）。システムのメディア解析は、20:42:25〜20:50:09 のあいだ、止めてあった。
- 計測の合図は free だった（遅延の計測ではない）ので、合図で遠ざけたものは、ない。この Mac では、同じ時間に、ほかの流れのビルドとテストの関門（20:43 ごろに終わった）、協調役の非公開の情報の確かめと `git push`、記録の書き込み（20:43 ごろ）、ほかの流れの絵のファイルの読み込み、夜の音の試験（署名した音のアプリが鳴らしていて、取り込みが動いていた。2 台とも）が動いていた。持ち主の試しの窓は、20:50 まで止めてあった。
- だから、この節の「静か」は、何も動いていない Mac ではない。

**持ち主の決定**（2026-11-17）：ローカルの受け渡しで、入力は、順に、欠けずに届かなければならない。「受け手が最新の 1 つだけを読む」形は、入力には使わない（キーが落ちる。この計測の負荷の回で、入力が 45,001 のうち 40,317 しか届かなかったのは、このため）。絵は、最新だけを読んでよい。高い優先度での測り直しと、IOSurface の形は、最終の判定のあとにする。
