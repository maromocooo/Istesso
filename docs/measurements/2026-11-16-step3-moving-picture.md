# 手順 3：動く絵で測る（文字のスクロール、1720×720 と 3440×1440）

- 日付：2026-11-16
- コミット：この記録と同じコミット（`scripts/m1-step3-host.py --vbv` を足したコミット）。テストアプリの動く絵は 6e68a1f
- 目的：これまでの絵は一面の灰色で、圧縮したフレームが 63 バイトにしかならなかった。判定は、文字がスクロールする絵と 3440×1440 で行うことになった（[ADR 0002](../adr/0002-latency-first.md)）。その絵と解像度で、いまの経路がどう動くかを見る。

## 条件

| 項目 | 値 |
|---|---|
| ホスト | Ubuntu 24.04、RTX 4090、GStreamer 1.24.2。フレームは CUDA のメモリーでエンコーダーに渡す（[記録](2026-11-16-step3-gpu-frames.md)） |
| クライアント | MacBook Air（M4）、macOS 26.5.1。VideoToolbox で復号（[記録](2026-11-16-step3-videotoolbox.md)） |
| 接続 | ホストは有線。Mac は Wi-Fi（5 GHz 帯のチャンネル 44、共有の機能は元の設定。[記録](2026-11-16-wifi-channel-44.md)） |
| 解像度とフレームレート | 1720×720 と 3440×1440、85 fps。3440×1440 の絵は、Mac では 1720×720 の窓に縮めて出した |
| クライアントのディスプレイ | 外部（3440×1440、84.96 Hz）。2 つの窓は前面に出さずに起動 |
| テストアプリの絵 | `--picture text`：色つきの文字が 1 秒に 240 ポイントの速さで流れ、中央の四角が入力で灰色を切り替える。1 秒に 85 回描き直す（`--fps 85`）。手元の窓は 600×400 |
| コーデックとビットレート | H.265、30 Mbps（固定ビットレート）、キーフレームは 170 フレームごと |
| エンコーダーの設定 | `preset=p1 tune=ultra-low-latency zero-reorder-delay=true b-frames=0 rate-control=cbr`。レート制御のバッファー（`vbv-buffer-size`）は、既定と 353 kbit（1 フレームぶん＝30 Mbps ÷ 85）の 2 通り |
| 経路 | RTP を UDP で。暗号化なし。パケットを失ったときの回復なし |

## 測り方

[README.md](README.md) の「内訳の計測」のとおり、500 回ずつです。

| 回 | 絵 | 解像度 | レート制御のバッファー | 時刻（JST） |
|---|---|---|---|---|
| A | 灰色 | 1720×720 | 既定 | 14:55:05〜14:59:07 |
| B | 文字 | 1720×720 | 既定 | 14:59:19〜15:03:22 |
| C | 文字 | 1720×720 | 353 kbit | 15:19:46〜15:23:47 |
| D | 文字 | 3440×1440 | 既定 | 15:03:40〜15:14:44（途中で打ち切り） |
| E | 文字 | 3440×1440 | 353 kbit | 15:15:18〜15:19:18 |

99 パーセンタイルは、500 回なので判断に使いません。Mac が Wi-Fi なので、どれも判定には使えない値です。

D では、285 回の入力のうち、中継した窓が映したのは 52 回でした。ホストは 85 fps でフレームを送り、Mac にもフレームは届いていますが、打ち切る 1 分前の時点で、復号できたのは約 52,700 フレームのうち約 3,060 フレームでした。キーフレームが 700〜1,000 パケットにもなり、そのどこかが欠けると、VideoToolbox は次のキーフレーム（2 秒後）まで何も出せません。復号できたのは、キーフレームが無事に届いた 19 回の、そのあとの 170 フレームずつです。

### 内訳（平均）

| 区間 | A：灰色 | C：文字、1720×720 | E：文字、3440×1440 |
|---|---|---|---|
| ネットワーク（行きと帰り） | 4.6 ms | 5.8 ms | 6.3 ms |
| アプリ | 0.9 ms | 1.1 ms | 5.1 ms |
| コンポジター（確定から、フレームが出るまで） | 8.0 ms | 9.1 ms | **14.8 ms** |
| 色の変換、圧縮、パケット | 1.2 ms | 1.3 ms | 2.8 ms |
| フレームが届く（最初のパケットから最後まで） | 0.1 ms | 0.8 ms | 0.9 ms |
| 復号 | 1.7 ms | 1.9 ms | 2.5 ms |
| 描くまで | 0.3 ms | 0.3 ms | 0.3 ms |
| 描いてから、画面に出るまで | 18.3 ms | 17.7 ms | 17.6 ms |
| 合計（入力を送ってから、画面に出るまで） | 35.0 ms | 38.0 ms | 50.3 ms |

入力を映したフレームは、平均で、A が 0.4 kB（パケット 2 個）、C が 29 kB（26 個）、E が 33 kB（30 個）でした。同じ時間の `ping` の往復は、どの回も中央値 3.8〜4.1 ms です。

手元の窓の追加遅延の中央値は、文字の絵でも 17.3〜17.5 ms で、灰色の絵（17.3 ms）と変わりません。

## わかったこと

1. **動く絵にすると、中央値の差は 16.6 ms から 19.7 ms に、3.1 ms 増えました（1720×720）。** 増えたのは、ネットワーク（+1.3 ms）、コンポジター（+1.1 ms）、フレームが届くまで（+0.8 ms）です。フレームが 30 パケットになり、毎フレーム絵が変わるためです。復号は 0.2 ms しか増えていません。
2. **キーフレームが、灰色の絵では見えなかった問題でした。** 既定の設定では、キーフレームが 1720×720 で 321 kB、3440×1440 で 869 kB になります。ふつうのフレームの 7〜25 倍です。3440×1440 では、それがパケットの欠けにつながり、映像がほとんど止まりました。
3. **レート制御のバッファーを 1 フレームぶんにすると、キーフレームもふつうのフレームと同じ大きさに収まります**（42 kB と 70 kB）。3440×1440 が映るようになり、1720×720 でも 95 パーセンタイルが 26.5 ms から 24.0 ms に下がりました。以後の計測は、この設定を基本にします。
4. **3440×1440 の動く絵では、中央値の差が 27.4 ms で、合格ライン（12 ms）の 2 倍あまりです。** いちばん大きいのはコンポジターの 14.8 ms です。次に描くまでの待ち（平均 5.9 ms）に加えて、描き始めてから出すまでに約 9 ms かかっています。
5. **その 9 ms には、テストアプリの作りが効いています。** テストアプリは CPU で描き、毎フレーム 20 MB を共有メモリーでコンポジターに渡します。コンポジターは、それを毎回 GPU に上げます。テストアプリ自身の応答も 5.1 ms かかっています（この分は、指標では引かれます）。GPU で描くふつうのアプリでは、受け渡しに画素の写しが要りません。判定の前に、テストアプリを GPU で描く形にするのがよさそうです。

読むときの注意：

- キーフレームを小さくすると、キーフレームのときだけ絵が粗くなります。画質は測っていません。パケットを失ったときにだけキーフレームを送る仕組みがあれば、定期的なキーフレームそのものが要らなくなります。この経路には、まだその仕組みがありません。
- 3440×1440 の絵は、Mac では半分の大きさの窓に縮めて出しています。等倍で出したときの値は、測っていません（手元の窓と並べる置き方が決まっていない）。
- ビットレートは、どちらの解像度でも 30 Mbps のままです。3440×1440 に見合うビットレートは、決めていません。
