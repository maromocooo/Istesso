# 入力の受け渡しを、プログラムごとに分ける。遅れた入力は、どこで遅れたか

- 日付：2026-11-17（0:04〜0:08）
- コミット：1c64dfa（時刻の記録を入れたもの）と、この記録のコミット（内訳を入力ごとに書き出す `--per-input`）
- 目的：
  1. 仮の判定（[記録](2026-11-16-m1-provisional-verdict.md)）で 1.9 ms だった「入力の経路とネットワーク」を、プログラムごとに分ける（[M1 の計画](../m1-plan.md) の手順 5、余裕を取り戻す順番の 1）。
  2. 更新 2 回以上遅れて見えた入力が、どこで遅れたかを見る。Mac の受信の側で、スレッドが遅れて起こされていないかを確かめる（音の計測では、受信スレッドが 10〜26 ms 遅れて起こされることがあった）。
- 結論：
  - **入力の受け渡しで、プログラムの中と、プログラムどうしの受け渡しに使っているのは、平均 0.74 ms**（Mac の中 0.22 ms、ホストの中 0.52 ms）。残りの 1.0 ms は、ネットワークの行き帰り（往復の中央値 0.56 ms）と、測れていない部分。自前のクライアントとホストにして取り戻せるのは、0.3〜0.4 ms ほど、と見ています。
  - **2 回以上遅れた入力は、Mac の受信、復号、描画では遅れていません。** 遅れて起こされた、と読める入力は、2,500 回のうち 1 回。遅れの元は、2 つの窓の描く拍と画面の更新の、巡り合わせ（手元の窓がたまたま早く、中継した窓がたまたま次の更新を待った）と、ホストのコンポジターがフレームを 1 回ぶん待たせた場合（仮の判定で、2,000 回のうち 22 回）です。
  - **2 回以上遅れる入力の割合は、同じ置き方でも、回によって動きます。** 仮の判定では 3.15%、この回では 10.0%（500 回のうち 50 回）でした。「10% を超えたら不合格」の条件（[ADR 0002](../adr/0002-latency-first.md)）は、巡り合わせしだいで、内側にも外側にも出ることがあります。

## 条件

仮の判定と同じ置き方、同じ設定です。違うのは、回数（500 回）と、時刻の記録を付けたことだけです。

| 項目 | 値 |
|---|---|
| ホスト | Ubuntu 24.04、RTX 4090（ドライバー 590.48.01）、GStreamer 1.24.2。有線（2.5 Gbps）。コンポジターは修正を当てたもの |
| クライアント | MacBook Air（M4）、macOS 26.5.1。電源につないだ状態。有線（1 Gbps）。VideoToolbox で復号 |
| ディスプレイ | 外部、3440×1440（拡大なし）、85.00 Hz |
| 絵 | 動く文字、3440×1440、毎秒 85 枚。4:4:4、上限 30 Mbps、キーフレームは求められたときだけ |
| 入力 | 人が打ったキーと同じ経路：プローブ → `istesso input relay`（アプリとして起動、優先度 46）→ 制御チャンネル（有線のアドレスどうし）→ ホストのエージェント → 経路のプログラム → コンポジター → テストアプリ |
| 時刻の記録 | `istesso input relay --timings` と `istesso agent --input-timings`。この回のあいだだけ。終わってから、エージェントは記録なしで起動し直した |
| 経路の往復（ping） | 中央値 0.56 ms、95% 1.14 ms |
| Wi-Fi | 入っていたが、経路には使っていない |
| ほかに動いていたもの | 2 台とも、ビルド、試験、音の再生はなし（始める前に確かめた）。手で試すための窓は、止めてから測った |

## 結果

### 手元の窓との差

| 指標 | 中央値 | 95% | 99% |
|---|---|---|---|
| 追加遅延の、手元の窓との差 | 10.52 ms | 11.23 ms | 12.58 ms |
| 追加遅延（中継した窓） | 28.45 ms | 34.61 ms | 38.55 ms |
| 追加遅延（手元の窓） | 17.94 ms | 23.38 ms | 25.97 ms |

500 回なので、99 パーセンタイルは判断に使いません。500 回とも、両方の窓に見えました。キーフレームの求めは、始めの 1 回だけ。パケットの欠けは 0 回。コンポジターが描き始めた回数は、どの 1 秒でも 85 回まで。

入力 1 回ごとに見ると：手元の窓と同じ更新で見えたものが 23 回（4.6%）、1 回遅れが 427 回（85.4%）、2 回以上遅れが 50 回（10.0%）。

- 「残り」に入っているもの：ネットワークの行き（入力）と帰り（映像の最初のパケット）、ホストのエージェントが受信して復号するまで、2 台の機械の中の通信の処理、時刻の突き合わせの誤差。ping の往復の中央値が 0.56 ms なので、ネットワークの外に 0.4〜0.5 ms ほどが残ります。ここは、まだ分けられていません。
- 2 台の時計は、突き合わせていません。それぞれの機械の中で、同じ時計の値どうしを引いています。中継のコマンドとエージェントの時刻は、時刻（日付と時刻）で書かれるので、同じ機械のフレームの記録にある対応表で、その機械の時計に直しています。
- **自前のクライアントとホストで短くできそうなのは**、Mac の中の受け渡し（0.22 ms。プローブと中継が別のプロセスであるぶん。本物の使い方では、窓のプログラムが直接送る）と、ホストの中の、エージェントから経路のプログラムへの受け渡し（0.18 ms）です。合わせて 0.3〜0.4 ms。コンポジターからアプリまでの 0.30 ms は、アプリの側の受け取りを含むので、残ります。

### 2 回以上遅れた入力は、どこで遅れたか

内訳を、入力ごとに書き出し、「手元の窓と同じ更新」「1 回遅れ」「2 回以上遅れ」に分けて、区間ごとの平均を比べました。右の列は、「2 回以上遅れ」から「1 回遅れ」を引いた値です。

仮の判定（2,000 回。同じ更新 236、1 回遅れ 1,701、2 回以上遅れ 63）：

| 区間（平均） | 同じ更新 | 1 回遅れ | 2 回以上遅れ | 差 |
|---|---|---|---|---|
| 入力の経路とネットワーク | 1.87 ms | 1.93 ms | 2.02 ms | +0.09 ms |
| アプリ（入力から描き終えるまで） | 6.46 ms | 6.16 ms | 7.32 ms | +1.16 ms |
| **コンポジター** | 1.08 ms | 1.14 ms | **4.73 ms** | **+3.60 ms** |
| 色の変換と圧縮 | 4.03 ms | 4.04 ms | 4.08 ms | +0.03 ms |
| フレームが届く | 0.16 ms | 0.18 ms | 0.24 ms | +0.06 ms |
| 復号 | 3.42 ms | 3.46 ms | 3.53 ms | +0.07 ms |
| 復号してから描くまで | 0.55 ms | 0.55 ms | 0.57 ms | 0.00 ms |
| **描いてから、画面に出るまで** | 12.77 ms | 18.25 ms | **22.44 ms** | **+4.20 ms** |
| （手元の窓の追加遅延） | 22.65 ms | 17.28 ms | **14.15 ms** | **−3.13 ms** |

この回（500 回。同じ更新 23、1 回遅れ 427、2 回以上遅れ 50）：

| 区間（平均） | 同じ更新 | 1 回遅れ | 2 回以上遅れ | 差 |
|---|---|---|---|---|
| 入力の経路とネットワーク | 1.63 ms | 1.73 ms | 2.05 ms | +0.32 ms |
| アプリ（入力から描き終えるまで） | 8.27 ms | 5.76 ms | 7.54 ms | +1.78 ms |
| コンポジター | 1.06 ms | 1.13 ms | 1.66 ms | +0.53 ms |
| 色の変換と圧縮 | 4.03 ms | 4.08 ms | 4.11 ms | +0.03 ms |
| フレームが届く | 0.21 ms | 0.23 ms | 0.20 ms | −0.03 ms |
| 復号 | 3.16 ms | 3.14 ms | 3.30 ms | +0.15 ms |
| 復号してから描くまで | 0.42 ms | 0.44 ms | 0.43 ms | 0.00 ms |
| **描いてから、画面に出るまで** | 10.93 ms | 17.24 ms | **22.80 ms** | **+5.56 ms** |
| （手元の窓の追加遅延） | 22.86 ms | 18.16 ms | **13.31 ms** | **−4.84 ms** |

- **Mac の受信、復号、描画の区間は、遅れた入力でも変わりません**（差は 0.2 ms 以内）。
- スレッドが遅れて起こされたなら延びるはずの区間（入力の経路とネットワーク、届く、復号、描くまで）の合計が、中央値より 5 ms 以上長かった入力は、仮の判定で 2,000 回のうち 1 回（最大 13.8 ms）、この回で 0 回（最大 9.3 ms）。**音で見えた 10〜26 ms の遅れは、映像の経路には、ほとんど出ていません。** ただし、これは、いまの記録からの読み取りです。受信スレッドが起こされるまでの時間そのものは、測っていません（カーネルがパケットを受けた時刻が要ります。自前のクライアントで取ります）。
- **遅れの元は 2 つ**、と読めます。
  1. 巡り合わせ：2 回以上遅れた入力では、手元の窓が、いつもより 3〜5 ms 早く見えていて、中継した窓のフレームは、描いてから画面に出るまでを 4〜6 ms 長く待っています。中継した窓が遅いだけでなく、手元の窓がたまたま早かった入力が、この山に入っています。
  2. コンポジターの待ち：仮の判定では、コンポジターがフレームを 5 ms 以上長く待たせた入力が 22 回ありました（最大 13.3 ms。更新 1 回ぶん）。1 秒に 85 回までの数え方に当たったフレームを、次の拍まで待たせる決まりによるもの、と見ています。この回では 3 回。
- 2 つのテストアプリは、別々の時計で、毎秒 85 回描いています。その足並みは、計測のあいだに少しずつずれるので、山の割合は、回によって、また 1 回の計測の中でも動きます。

カメラでの計測：行っていません。

## わかったこと、次にすること

- 入力の受け渡しは、自前のクライアントとホストで 0.3〜0.4 ms 縮む見込み。残りの 0.4〜0.5 ms は、どこにあるかを、自前のクライアントとホストで時刻を取って確かめます。
- 映像の受信スレッドを、音と同じようにリアルタイムの扱いにしても、「2 回以上遅れ」の割合は、ほとんど変わらない、と見ています。試すこと自体は安いので、自前のクライアントで入れて、測ります。
- コンポジターが 1 回ぶん待たせる場合を減らせるかは、候補として残します（仮の判定で、入力の 1.1%）。作業は、まだ始めていません。
- **「2 回以上遅れが 10% を超えたら不合格」の条件は、数え方を決め直す必要がありそうです。** 同じ置き方で、3.15% と 10.0% が出ました。決めるのは人です。

## 再現のしかた

1. [仮の判定](2026-11-16-m1-provisional-verdict.md) と同じ置き方で、中継のコマンドに `--timings <ファイル>`、ホストのエージェントに `--input-timings <ファイル>` を付けて測る。
2. `scripts/m1-step3-breakdown.py … --relayed-inputs keys --relay-timings <ファイル> --agent-timings <ファイル>` で、入力の受け渡しの表が出る。
3. `--per-input <ファイル>` を付けると、入力ごとの内訳が 1 行ずつ書き出される。これを、`istesso measure compare` と同じ引き算（中継した窓の追加遅延 − 手元の窓の追加遅延）を更新の回数に丸めた値で分けて、区間ごとに平均する。
