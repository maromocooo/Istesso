`gstreamer1.0-plugins-bad` の候補は 1.24.2-1ubuntu4（universe）で、中に `libgstnvcodec.so` と `libgstvideoparsersbad.so` があることを、パッケージの一覧で確かめました。

人に頼んだ作業：

```sh
sudo apt install gstreamer1.0-plugins-bad tmux iw
```

このパッケージは依存として libx265 などのライブラリも入れます。このプロジェクトが使うのは `nvcodec` と `videoparsersbad` だけで、x265 は使いません（[components.md](../components.md)）。

#### 導入のあと（同日 08:40）

**NVENC は GStreamer から使えます。ただし、使えるのは新しいほうの要素 `nvcudah265enc` だけです。**

| 要素 | 結果 |
|---|---|
| `nvh265enc`（古い実装） | 動かない。どのプリセットを選んでも `Selected preset not supported` で止まる。この要素が使う古いプリセットを、いまのドライバー（590.48.01）が受け付けないため、と見ている |
| `nvcudah265enc`（新しい実装） | 動く。プリセットは p1〜p7 と `tune` の組み合わせで選ぶ |
| `nvav1enc` | この版の GStreamer（1.24.2）にはない。AV1 を比べるには、新しい GStreamer が要る |

`nvcudah265enc` で、実時間で流れてくる 85 fps の映像を 10 秒ぶん圧縮しました。設定は `preset=p1 tune=ultra-low-latency zero-reorder-delay=true b-frames=0 rate-control=cbr bitrate=20000 gop-size=-1` です。

| 解像度 | フレーム | 出力 | かかった時間 |
|---|---|---|---|
| 1920×1080 | 850（I が 1、P が 849、B なし） | H.265 Main、21.8 Mbps | 10.7 秒 |
| 3440×1440 | 850（I が 1、P が 849、B なし） | H.265 Main | 12.7 秒 |

3440×1440 では実時間に追いついていません。テスト用の映像（ノイズ）を CPU で作る部分が遅い可能性があり、エンコーダーの限界かどうかは分けていません。手順 3 で、実際の取り込みから測ります。

1フレームあたりの圧縮の時間は、まだ測っていません。

クライアントには GStreamer が入っていません。手順 3 で受信側を GStreamer の要素で組むなら、そのときに要ります。

## 測り方

[README.md](README.md) の「経路そのものの遅れ」のとおりです。集計は `scripts/ping-stats.py` で行いました。パーセンタイルは、その割合以上の標本が収まる最小の値です。

| 回 | 経路 | 時刻（JST） | 指定した間隔 | 実際の間隔（平均） |
|---|---|---|---|---|
| 1 | クライアント → ホスト | 00:36:34〜00:44:58 | 0.2 秒 | 0.28 秒 |
| 2a | クライアント → ルーター | 00:49:15〜00:53:19 | 0.2 秒 | 0.27 秒 |
| 2b | ホスト → ルーター（2a と同時） | 00:49:15〜00:53:36 | 0.2 秒 | 0.20 秒 |
| 3 | クライアント → ホスト | 00:58:26〜01:01:33 | 1 秒 | 1.10 秒 |

- macOS の `ping` は、指定より長い間隔で送りました。同じ条件で自分自身に送ると往復 0.05 ms だったので、この伸びは往復時間の値には入っていません。原因は、エージェントのシェルから起動したプログラムの優先度が低いことだと見ています（[手順 1 の記録](2026-11-16-step1-tools.md)）。
- 2回目は、どちらの電波区間が遅れを作っているかを分けるための計測です。3回目は、ホストが受信するまでの間が空いたときに、ホストの Wi-Fi の省電力で遅れが増えるかを見るための計測です。
- 計測のあいだ、このための通信は `ping` だけにしました。ほかの機器やアプリの通信は止めていません。

## 結果

| 回 | 経路 | 回数 | 欠落 | 最小 | 中央値 | 95% | 99% | 最大 | 遅い応答の割合 |
|---|---|---|---|---|---|---|---|---|---|
| 1 | クライアント → ホスト | 1800 | 0 | 4.9 ms | **8.3 ms** | **94.8 ms** | **252.0 ms** | **381.7 ms** | 22.3% |
| 2a | クライアント → ルーター | 900 | 0 | 2.4 ms | 4.0 ms | 68.5 ms | 93.0 ms | 279.6 ms | 17.1% |
| 2b | ホスト → ルーター | 1300 | 0 | 1.3 ms | 4.4 ms | 6.7 ms | 63.5 ms | 164.0 ms | 2.9% |
| 3 | クライアント → ホスト | 170 | 0 | 5.3 ms | 8.0 ms | 96.4 ms | 237.2 ms | 262.7 ms | 19.4% |

「遅い応答」は、中央値の 2 倍（中央値 + 5 ms のほうが大きければそちら）を超えたものです。

1回目では、16 ms を超えた応答が 22.6%、50 ms を超えた応答が 14.6% ありました。暫定の合格ライン（追加遅延の 95 パーセンタイルで 16 ms 以下）は、いまの経路では転送だけで超えます。

### 跳ねは決まった間隔で出ている

遅い応答が戻ってきた時刻を、いろいろな周期で折りたたみました。値は、毎回同じ位相にそろっていれば 1、ばらばらなら 0 に近づきます（2a は偶然でも 0.08 程度）。

| 周期 | 1回目 | 2a（クライアント → ルーター） |
|---|---|---|
| アクセスポイントのビーコン（100 TU ＝ 102.4 ms） | 0.09 | 0.09 |
| 64 TU（65.5 ms） | 0.54 | 0.94 |
| 512 TU（524.3 ms） | 0.66 | 0.91 |
| 1024 TU（1048.6 ms） | 0.03 | 0.06 |
| 比較用：384 TU、500 TU | 0.06、0.07 | 0.04、0.07 |

遅い応答は **512 TU（約 524 ms）の周期** にそろっています。1 TU は 1.024 ms で、16 TU の倍数は AWDL（AirDrop などが使う、Apple の機器どうしの直接通信）の時間の刻みです。遅い応答の遅れは 0〜90 ms にほぼ均等に散らばっていて、「524 ms ごとに約 90 ms、通信できない時間がある」と読めます。90 ÷ 524 ＝ 17% で、2a の遅い応答の割合と合います。

これとは別に、**約 61 秒おきに、2〜6 秒続く大きな遅れ**（100〜380 ms）がありました。

### 原因

**1. クライアントの Wi-Fi が、AWDL のために別のチャンネルへ移っている。**

- 2a のとおり、クライアントとルーターの間だけで同じ跳ねが出ます。同じ時刻のホストとルーターの間（2b）には出ません。
- クライアントのカーネルのログに、AWDL の状態が出ています。AWDL は有効で、ふだんの状態（`Infra Priority`）では、16 個の枠のうち 5 GHz 帯のチャンネル 44 に 2 枠、2.4 GHz 帯のチャンネル 6 に 1 枠を使い、アクセスポイントのチャンネル（6 GHz 帯の 53）にいる時間は 78% と記録されています。

  ```text
  AWDL ON:[infra(53) 78%] [sdb:0] (6/44/44) [53' 0 44 0 0 0 0 0 6 0 44 0 0 0 0 0] Infra Priority
  ```

- 約 61 秒おきの大きな遅れは、AWDL の状態が `Data`、`Idle`、`AWDL Fast Discovery` に変わる時刻と重なります。このときアクセスポイントのチャンネルにいる時間は、それぞれ 48%、60%、24% まで下がります。1回目で 110 ms を超えた 13 区間のうち 10 区間が、この時間帯でした。
- 状態が変わるきっかけは、ユニバーサルコントロールです。ログでは、`rapportd` が約 61 秒おきに、ユニバーサルコントロールのための AWDL の接続を作り直していて、その時刻が状態の変わる時刻と一致します（近くに AWDL の相手が 1 台いる）。AirDrop の設定は「すべての人」でした。

**2. ホストは 5 分おきにスキャンしている。**

`wpa_supplicant` のログに、5 分おきに `WNM: Preferred List Available`（アクセスポイントからの、別の接続先の提案）が出ています。NetworkManager が記録している最後のスキャンの時刻も、これと一致します。その直後の 2〜6 秒、往復時間が最大 165 ms ほどに伸びます（00:39:47 と 00:49:48 の2回を、計測と突き合わせて確認）。ホストの信号の強さが 46/100 と低めなことと関係していそうですが、確かめていません。

**3. ホストの Wi-Fi の省電力は、この計測では見えなかった。**

NetworkManager の設定は省電力が有効（`wifi.powersave = 3`）です。ただ、送る間隔が 0.28 秒でも 1.1 秒でも、遅い応答はビーコンの周期にそろいませんでした（3回目で 0.16、偶然でも 0.17 程度）。いまは変えません。`iw` が入れば、実際の状態を読めます。

**4. 原因がわからないもの。**

1回目の 00:38:37 からの 3 秒間（最大 350 ms）と、00:43:10 の 1 回（147 ms）は、上のどれとも重なりません。

### 跳ねを除いた、もとの遅れ

電波区間の往復は、どちらも中央値で約 4 ms です（2a が 4.0 ms、2b が 4.4 ms）。足すと 8.4 ms で、1回目の中央値 8.3 ms と合います。いまは1つのパケットが電波を2回通っているので、ホストを有線にすれば、もとの遅れは約半分になる見込みです。

## わかったこと

- いまの Wi-Fi の経路は、95 パーセンタイルが約 95 ms です。合格ラインの 16 ms を、映像を流す前から超えています。
- 主な原因は、クライアント（Mac）の AWDL です。m1-plan.md が予想したとおり、決まった間隔の跳ねは Mac 側にありました。有線の接続は AWDL の影響を受けません。
- ホスト側の電波区間は、5 分おきのスキャンを除けば安定しています（95 パーセンタイル 6.7 ms）。
- 跳ねがなくても、電波を2回通る分で中央値が 8 ms あり、16 ms の半分を使います。

次に行うこと：

1. **AWDL を一時的に止めて測り直す**（人が実行）。`sudo ifconfig awdl0 down` のあと、同じ計測をして、跳ねが消えることを確かめます。macOS が自動で戻すことがあるので、計測の前後に `ifconfig awdl0` の `status` を見ます。戻すには `sudo ifconfig awdl0 up` です。
   - 追記（同日 08:36）：08:32:54 に `sudo ifconfig awdl0 down` を実行したところ、63 秒後の 08:33:57 に macOS が AWDL を戻しました（ログでは、AirDrop の探索の再開と同時）。1回止めるだけでは足りないので、計測のあいだは `sudo sh -c 'while :; do ifconfig awdl0 down; sleep 1; done'` で止め続けます。
2. 効果を確かめたら、対処を選びます（人が決める）。候補は次のとおりです。
   - ユニバーサルコントロール、AirDrop、AirPlay レシーバー、Handoff を切る。どれが効くかは、1つずつ切って測ります。
   - Mac を有線にする（アダプターが要る）。
   - ルーターのチャンネルを AWDL と同じ 5 GHz 帯のチャンネル 44 にして、移動を減らす。Mac は 6 GHz 帯ではなく 5 GHz 帯でつなぐことになります。
3. ホストを有線にできるなら、電波区間が1つ減り、5 分おきのスキャンもなくなります。
4. ~~ホストに `gstreamer1.0-plugins-bad` を入れてもらい、NVENC を確かめます。~~ 済み（上の「導入のあと」）。手順 3 では `nvcudah265enc` を使います。
5. 接続を変えたら、この計測をやり直します（README.md）。
