# 手順 2：既存の配信ソフトでの基準（Sunshine と Moonlight、Wi-Fi）

- 日付：2026-11-16
- コミット：1cb938a
- 目的：この機材で、成熟した実装がどこまで届くかを知る。合格ラインを数値で決めるための材料にする（[m1-plan.md](../m1-plan.md) の手順 2）。

## 条件

| 項目 | 値 |
|---|---|
| ホスト | Ubuntu 24.04、RTX 4090（ドライバー 590.48.01）、Sunshine 2026.914.233613。デスクトップは X11、3440×1440、240 Hz |
| クライアント | MacBook Air（M4）、macOS 26.5.1、Moonlight 6.2.0。`open` で起動（ふつうの優先度） |
| 接続 | 2台とも Wi-Fi（6 GHz 帯）。Mac の AWDL は止め続け、計測のあいだに戻らなかったことをログで確かめた。経路の往復は中央値 7.2 ms、95 パーセンタイル 16.1 ms（[記録](2026-11-16-wifi-path-awdl-off.md)） |
| 解像度とフレームレート | 1720×720、85 fps。ホストの 3440×1440 の画面を、Sunshine が縮めて送る。Mac では窓で表示 |
| クライアントのディスプレイ | 外部（3440×1440、84.96 Hz）。手元の窓と中継した窓を、このディスプレイに並べた |
| コーデックとビットレート | H.265、30 Mbps |
| エンコーダーの設定 | Sunshine の既定（NVENC）。取り込みは X11 |
| 経路 | 映像は Sunshine と Moonlight の経路。入力は合成の入力（UDP）で、Moonlight の入力の経路は通っていない |

読むときの注意：

- **取り込みは、Sunshine の説明で「いちばん遅い」とされる X11 の方法です。** このホストでは、ほかの方法が自動では使えませんでした（m1-plan.md の手順 2）。ホストの処理時間は、その分だけ不利な値です。
- 解像度は、画面全体（3440×1440）ではなく 1720×720 です。手元の窓を同じディスプレイに並べるためです。

## 測り方

[README.md](README.md) の「画面での計測」のとおりです。手元のテストアプリ（600×400 の窓）と、ホストのテストアプリ（全画面）に、同じ入力を 500 回、200〜400 ms の間隔で送りました（乱数の種は 20261116）。

Moonlight の設定を 2 通り測りました。

| 回 | Moonlight の V-sync | 時刻（JST） | 計測中のできごと |
|---|---|---|---|
| A | なし（`--no-vsync`） | 09:44:45〜09:47:49 | なし |
| B | あり（既定） | 09:48:46〜09:51:49 | 最初の 10 秒に、ホストの Wi-Fi のスキャン（5 分おきに起きるもの）が重なった |

## 結果

| 回 | 回数 | 中央値 | 95% | 99% | 最大 |
|---|---|---|---|---|---|
| A：V-sync なし | 500 | **24.3 ms** | **60.6 ms** | 76.4 ms | 147.0 ms |

A では、更新 1 回ぶん以内が 23.8%、2 回ぶん以内が 63.2% でした。

## わかったこと

1. **成熟した実装でも、この条件では、手元の窓より中央値で画面更新 2 回ぶん（24 ms）遅れます。** 95 パーセンタイルでは 5 回ぶん（61 ms）です。
2. **暫定の合格ライン（追加遅延の 95 パーセンタイルで 16 ms 以下）は、いまの定義のままでは、手元のアプリでも満たせません。** 手元の窓でも、アプリがフレームを確定してから画面に出るまでに、中央値で 18 ms、95 パーセンタイルで 28 ms かかっています。macOS が窓を合成して画面に出すまでの時間で、画面更新 1〜2 回ぶんです。追加遅延の定義にはこの「表示待ち」が入るので、中継の時間が 0 でも 18 ms になります。合格ラインは、**手元の窓との差**で決めるのがよさそうです。
3. **Moonlight の V-sync は、差を 23 ms 広げます。** 既定（あり）では、フレームが待ち行列で平均 16 ms 待ちます。なしでは 0.3 ms です。基準としては、なしのほう（A）を使います。
4. **A の内訳で大きいのは、ホストの処理（平均 11.4 ms）です。** Moonlight の統計を足すと、ホストの処理 11.4、ネットワークの片道 3.5、復号 2.7、描画 0.8 で、約 18 ms になります。差の中央値 24 ms との残り約 6 ms は、入力の片道と、ホストの画面に出てから取り込まれるまでの時間とみています（分けては測っていません）。自前の実装がいちばん縮めやすいのは、ホストの処理です。
5. **裾を作っているのはネットワークです。** B の 100 ms を超えた 20 回のうち 17 回は、ホストの Wi-Fi のスキャンの 10 秒間でした。

合格ラインを決めるための材料として、A の値を並べます。決めるのは人です。

| 指標 | 成熟した実装（A） | 中継が 0 のとき |
|---|---|---|
| 手元の窓との差（中央値 / 95%） | 24.3 ms / 60.6 ms | 0 / 0 |
| 入力を送ってから画面に出るまで（中央値 / 95%） | 45.6 ms / 82.4 ms | 21.3 ms / 31.1 ms |

次に行うこと：

- 合格ラインを「手元の窓との差」で決め直すかどうかを決める（人）。決めたら、ADR 0002、`requirements.md`、README.md の定義を直す。
- ホストを有線にして、同じ計測をやり直す。裾がどこまで縮むかを見る。
- カメラ（240 fps）で 1 回、数値が体感と合っているかを確かめる。
- 画面全体の解像度（3440×1440）での値は、手元の窓の置き場所を工夫して別に測る。
