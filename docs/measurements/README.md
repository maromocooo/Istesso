# 遅延の計測

映像・入力・音の経路に手を入れる変更では、変更の前後をここに記録します（[AGENTS.md](../../AGENTS.md)）。

## 測るもの

```text
追加遅延 ＝ 往復時間 − アプリ自身の応答時間
```

- **往復時間**（クライアントの時計で測る）：入力を送り出した時刻から、その入力に反応したフレームを画面に出した時刻まで。
- **アプリ自身の応答時間**（ホストの時計で測る）：入力をアプリに渡した時刻から、アプリが次のフレームを確定した時刻まで。

どちらの区間も1台の時計の中で閉じているので、2台の時計を合わせる必要がありません。

原因を探すために、内訳も記録します。

| 区間 | 時計 | 内容 |
|---|---|---|
| 取り込みと圧縮 | ホスト | フレームの確定から、圧縮したデータを送り出すまで |
| 復号 | クライアント | 受信から、復号が終わるまで |
| 表示待ち | クライアント | 復号の終わりから、画面に出るまで（次の画面更新を待つ時間を含む） |
| 転送（往復） | 両方 | 往復時間から上の3つとアプリの応答時間を引いた残り。`ping` の値と見比べる |

### 合格ライン

[ADR 0002](../adr/0002-latency-first.md) で決めています。手元で動かしたテストアプリの窓と、中継したテストアプリの窓を同じディスプレイに並べ、同じ入力を同時に与えて、それぞれの追加遅延を測ります（下の「画面での計測」）。比べるのは、**中継した窓の値から手元の窓の値を、同じ分位どうしで引いた差**です。

| 分位 | 差（中継した窓 − 手元の窓） |
|---|---|
| 中央値 | 12 ms 以下 |
| 95 パーセンタイル | 24 ms 以下 |
| 99 パーセンタイル | 47 ms 以下 |

- 判定の条件は、2台とも有線、クライアントのディスプレイが 85 Hz、中継する絵が 3440×1440、テストアプリが動く絵（文字のスクロール）。中継する側は、毎秒 85 枚を超えるフレームを出さない（数えるのは、コンポジターが描き始める回数）。計測は 2,000 回以上で、2 つの窓を前面に出して測る。そのあいだ Mac には触らないので、始める前に知らせる。中継の窓は画面いっぱいに出し、手元の窓をその隅に重ねる。
- 圧縮は、H.265 の 4:4:4、キーフレームは求められたときだけ、上限 30 Mbps。画質の条件（明るさと色の SSIM、Mac の画面での色の差）を満たすこと。受信側が自分でキーフレームを求められる状態で測り、途中で求めた回数と、絵が止まっていた時間を記録する。計測は、最初のキーフレームからの回復（6〜7 秒）が済んでから始める（ADR 0002）。
- 小さい窓、一面の灰色の絵、Wi-Fi、ほかのリフレッシュレートで測った値は、参考として記録する。
- ふだんの計測は 500 回以上で、中央値と 95 パーセンタイルを見る。99 パーセンタイルは、2,000 回以上の計測でだけ判断に使う。
- ふだんの計測では、2 つの窓を同じ状態（どちらも前面に出さない）で測る。手元の窓の追加遅延の中央値がいつもの値から 2 ms 以上ずれた回は、やり直す。
- 入力ごとの差（同じ入力で、中継した窓が何 ms あとに出たか）と、それを画面更新の回数で数えた値は、参考として記録する。判定には使わない。

| `scripts/m1-step3-host.py` | 手順 3 の送信側。パイプラインを動かし、フレームごとに、コンポジターを出た時刻、圧縮が終わった時刻、ネットワークへ渡した時刻を書き出す。フレームの渡し方（`--frames memory\|cuda`）、ビットレート、キーフレームの間隔（`--gop`。-1 で、求められたときだけ）、エンコーダーのレート制御のバッファー（`--vbv frame`）、色の間引き（`--chroma 420\|444`）を選べる。ストリームには、絵が sRGB であることを書く（`--colour srgb`。既定）。`--key-requests` で、受信側からの求めに応じてキーフレームを出す。`--lose <秒>` は、その間隔で 1 フレームぶんのパケットをわざと捨てる（欠けたときの動きを見るため） |
| `scripts/m1_encoder.py` | エンコーダーの設定を 1 か所に書いたもの。上の送信側と、下の画質の計測が、同じ設定を使うためにある |
| `istesso measure frames`、`istesso measure quality` | テストアプリの動く絵を、同じものを何度でも作り（`frames`）、圧縮して戻した絵と比べる（`quality`）。明るさと色の SSIM、明るさの PSNR を、フレームごとに出す |
| `scripts/m1-quality.py` | ホストだけで、テストアプリの絵をエンコーダーに通して復号し、上の道具で比べる。ビットレート、色の間引き、キーフレームの間隔を振った表を出す（下の「画質の計測」） |
| `scripts/patches/gst-wayland-display-render-on-commit.patch` | 手順 3 のコンポジターに当てる実験用の修正。アプリが新しい絵を確定したら、決まった間隔を待たずに描いて出す。どの 1 秒にも、フレームレートより多くは描かない |

### テストアプリ

```sh
cargo build --release -p istesso-flash
target/release/istesso-flash --log host.jsonl
```

- どのキーでも、マウスのどのボタンでも、色が切り替わります。Esc で終わります。
- 絵は 2 種類あります。
  - `--picture text`（既定）：色つきの文字が下から上へ流れ続け、窓の中央の四角が 2 つの灰色を切り替えます。エディターやターミナルを使っているときの画面に近く、どのフレームも前のフレームと違います。**判定は、この絵で行います。** 流れる速さは `--scroll <1秒あたりのポイント数>`（既定は 240。0 で止まる）、描き直す回数は `--fps <1秒あたりの回数>`（既定はディスプレイのリフレッシュレート）で変えられます。
  - `--picture grey`：窓全体を灰色で塗り、入力のたびに切り替えます。圧縮したフレームは数十バイトにしかならず、中継にとっていちばん楽な絵です。**いちばん良い場合の参考値**を取るときに使います。
- 計測の道具が見るのは、窓の中央です。どちらの絵でも、中央の約 20 ピクセル四方は灰色のどちらかです。
- 動く絵では、入力への反応を、次に描くフレームに入れます（`--answer next-frame`。既定）。描く回数は `--fps` のままで、増えません。ふつうのアプリと同じ動きです。次のフレームまで待つ時間は、アプリ自身の応答時間として記録され、追加遅延からは引かれます。`--answer at-once` は、入力のたびに、その場でもう 1 枚を描きます。灰色の絵と、止まった文字（`--scroll 0`）では、いつもその場で描きます。
- `--stroke <ピクセル>` は、文字の線の太さです。既定は 2 ポイントで、ふだんの大きさの文字にあたります。1 にすると、線が 1 ピクセルの細かい文字になり、色を間引く中継にとっていちばん厳しい絵になります。
- `--draw gpu` は、OpenGL で描きます。コンポジターには、GPU の上にあるバッファーがそのまま渡ります。絵は、CPU で描くもの（`--draw cpu`。既定）と同じです。**ホストの側では `--draw gpu` を使い、手元では CPU で描きます**（ADR 0002）。CPU で描くと、コンポジターが毎フレームの画素を GPU に上げることになり、3440×1440 では 1 フレーム 20 MB になります。
- 文字の絵は、どの PC でも、起動するたびに同じです。
- `--log` を付けると、入力ごとに「入力が届いた時刻」と「その入力を映したフレームを確定した時刻」を、その PC の時計で1行ずつ書き出します。この差が、アプリ自身の応答時間です。
- `--borderless` は、枠とタイトルバーをなくします。配信用の仮想コンポジターの中では、窓の枠はクライアントが描くので、これを付けます。
- `--listen <アドレス>:47811` を付けると、UDP で届く**合成の入力**も受けます。キーを押す代わりに、計測する側が番号つきの小さなパケットを送る仕組みです。入力を注入する仕組みができる前に、経路を1本通して測るために使います。**暗号化も認証もしていません。信頼できるネットワークでの計測にだけ使い、製品には残しません。**

### ログ

1行に1つの JSON です。時刻は、書いた PC の時計で数えた、起動からのナノ秒です。2台の時計を比べることはありません。

```json
{"kind":"header","side":"host","tool":"istesso-flash","version":"0.0.1","started_unix_ms":1794759850920,"clock_origin_unix_ns":1794759850920684667,"picture":"text"}
{"kind":"host","id":0,"source":"network","input_ns":260074349,"commit_ns":260359948}
{"kind":"client","id":0,"sent_ns":1000000,"received_ns":9000000,"decoded_ns":11000000,"shown_ns":18000000}
```

| 行 | 時計 | 時刻 |
|---|---|---|
| `host` | ホスト | `input_ns`：入力をアプリに渡した。`commit_ns`：アプリがフレームを確定した。`sent_ns`：圧縮したデータを送り出した（取り込みがあるときだけ） |
| `client` | クライアント | `sent_ns`：入力を送り出した。`received_ns`：フレームを受信した。`decoded_ns`：復号が終わった。`shown_ns`：画面に出した |

両側の行は `id` で対にします。ホスト名、ユーザー名、アドレスは書きません。

`header` の `clock_origin_unix_ns` は、そのログの時計が 0 だったときの時刻（Unix 時刻、ナノ秒）です。**同じ PC** で同時に動いた 2 つのプログラムのログを、1本の時間軸に並べるために使います（例：ホストのテストアプリと、ホストのパイプライン）。相手のログには、その PC の単調時計と時刻の組（`{"kind":"clock","mono_ns":…,"unix_ns":…}`）を書いておき、原点を 1 度だけ単調時計に直します。そこから先は時刻を使いません。macOS では、時刻が単調時計に対して 100 万分の 19 ほどずれていくためです（3 分で約 3 ms）。2台の時計を比べるためのものではありません。

`header` の `picture` は、テストアプリが出していた絵（`text` か `grey`）、`draw` は描き方（`cpu` か `gpu`）です。

```sh
istesso measure report --host host.jsonl --client client.jsonl
```

対になった入力から、追加遅延と内訳の中央値、95 パーセンタイル、99 パーセンタイル、最大値を出します。片側にしかない入力は数だけを表示し、計算には入れません。

クライアント側のログは、いまは `istesso-screen-probe` が外から書きます。自前の受信側（手順 3 以降）は、受信と復号の時刻も入れて、中から書きます。

### Mac で計測するプログラムの起動のしかた

コーディングエージェントのシェルから直接起動したプログラムは、優先度が低い状態（`ps -M` の PRI が 20）で動きます。ふつうのアプリは 46 前後です。この状態では、タイマーが遅れ、応答時間の遅い側の裾が伸びます（[2026-11-16 の記録](2026-11-16-step1-tools.md)）。

クライアント側で遅延に関わるプログラム（テストアプリ、配信ソフト、受信側）は、`.app` にして `open` で起動するか、人がターミナルから起動してください。テストアプリは次のようにします。

```sh
cargo build --release -p istesso-flash
scripts/macos-app.sh target/release/istesso-flash "Istesso Flash" dev.istesso.flash target/release
open -n -g "target/release/Istesso Flash.app" --args --listen 127.0.0.1:47811 --position=100,100
```

`istesso-screen-probe` は例外で、エージェントのシェルから起動して構いません。記録するのはシステムが付けた画面更新の時刻で、自分の動きの速さは値に入りません。

`open` で起動したプログラムは、macOS の「ローカルネットワーク」の許可を持つまで、LAN へパケットを送れません（受け取ることはできます）。`gst-viewer` がキーフレームを求めるときに、これに当たります。送れないときは、`No route to host` と標準エラーに出ます。許可は、macOS が出す確認に人が答えるか、システム設定の「プライバシーとセキュリティ」→「ローカルネットワーク」で、人が出します。ターミナルから起動したプログラムは、ターミナルの許可で送れます。

2026-11-16 に調べたこと（macOS 26.5）：

- **一覧には、`gst-viewer` という名前で載ります。** 「Istesso Gst Viewer」ではありません。`scripts/macos-app.sh` が作る `.app` には、まとまりとしての署名がなく、実行ファイルにリンカーが付けた仮の署名（ad hoc）だけがあります。macOS は、その署名の識別子（実行ファイルの名前）と、実行ファイルの場所で、アプリを見分けています。バンドル ID（`dev.istesso.gst-viewer`）では見分けていません。
- **起動元のターミナルの許可としては、扱われません。** `open` で起動したアプリの親は launchd で、アプリ自身の許可になります。
- **署名は、ビルドのたびに変わります**（ハッシュと、実行ファイルの UUID）。識別子と場所は変わらないので、許可は残ります。ビルドし直したあとの最初の起動では、はじめの 0.15 秒ほど（50 ms おきの求めで 3 回）送信が失敗し、そのあと通ります。macOS が、新しい UUID を許可済みのアプリのものとして覚え直すあいだです。2 回目からは、失敗しません。
- 確かめるには、システムのログを見ます：`/usr/bin/log show --last 1m --predicate 'subsystem BEGINSWITH "com.apple.networkextension" AND eventMessage CONTAINS "gst-viewer"'`。

## 測り方

### 経路そのものの遅れ（最初と、接続を変えたときに行う）

映像を流す前に、2台の間の往復時間の分布を測ります。以後の数値は、この分布と見比べて読みます。

1. クライアントからホストへ `ping` を 0.2 秒おきに 5 分以上流す。あとで周期を調べられるように、受信した時刻を付ける（macOS は `ping --apple-time -i 0.2 -c 1800 <ホスト>`、Linux は `ping -D -i 0.2 -c 1800 <ホスト>`）。
2. 中央値、95 パーセンタイル、99 パーセンタイル、最大値を出す。`scripts/ping-stats.py <ping の出力>` で集計できる。
3. 跳ねが決まった間隔で出ていないかを見る。`ping-stats.py` は、遅い応答が戻った時刻が、アクセスポイントのビーコンの周期（102.4 ms）や AWDL の時間の刻み（16 TU の倍数）にそろっているかも表示する。出ていれば、映像より先に原因を調べる（[m1-plan.md](../m1-plan.md) の「ネットワーク」）。
4. 跳ねがあるときは、クライアントからルーターへ、ホストからルーターへも同じように流して、どちらの区間で出ているかを分ける。

### 入力の経路だけの計測（道具か接続を変えたときに行う）

映像を通す前に、入力の経路と道具を確かめます。

1. ホストでテストアプリを `--listen` 付きで動かす。
2. クライアントで `istesso measure inputs --to <ホスト>` を実行する。200〜400 ms の間隔で 500 回、合成の入力を送る。
3. 「transfer, both ways」（転送の往復）が、同じ時間帯の `ping` の分布と合っていることを確かめる。「app response」が、テストアプリ自身の応答時間になる。

### 画面での計測（手元の窓との差。経路か設定を変えたときに行う）

手元で動かしたテストアプリの窓と、中継したテストアプリの窓を、Mac の同じディスプレイに並べ、同じ入力への反応を画面から読みます。配信ソフトの中を知らなくても測れるので、既存の配信ソフトにも自前の実装にも同じ方法が使えます。

1. ホストでテストアプリを全画面で動かす（`--fullscreen --draw gpu --listen <アドレス>:47811 --log host.jsonl`）。配信ソフトで、その画面を Mac に窓で映す。
2. Mac でテストアプリを `open -n -g` で起動する（`--listen 127.0.0.1:47811 --log local.jsonl --position=X,Y`）。中継の窓と同じディスプレイに、重ならないように置く。2 つのテストアプリには、同じ絵（`--picture`）と同じ `--fps` を指定する。
3. Mac で道具を動かす。200〜400 ms の間隔で、両方のテストアプリに同じ入力を送る。回数は、ふだんは 500 回（既定）、判定のときは 2,000 回（`--count 2000`。約 10 分かかる）。

   ```sh
   swift build -c release --package-path macos/screen-probe
   macos/screen-probe/.build/release/istesso-screen-probe \
       --local 127.0.0.1:47811 --relayed <ホスト>:47811 \
       --local-log probe-local.jsonl --relayed-log probe-relayed.jsonl
   ```

4. 2つの窓の追加遅延と、その差を出す。`host.jsonl` はホストから持ってくる。

   ```sh
   istesso measure compare --local probe-local.jsonl --relayed probe-relayed.jsonl \
       --local-app local.jsonl --relayed-app host.jsonl --refresh-hz 85 --local-usual 17.3
   ```

   はじめに出る「Relayed over local, percentile by percentile」が、合格ラインの指標です。分位ごとに、ラインに収まったか（`within`）、超えたか（`over`）も出ます。2,000 回に満たない計測では、99 パーセンタイルは値だけを出し、判定しません。`--local-usual` には、手元の窓の追加遅延の、いつもの中央値を渡します。2 ms 以上ずれていると「measure again」と出るので、その回はやり直します。そのあとの「For reference」は、入力ごとの差と、画面更新の回数で数えた値です。内訳を見るときは、`istesso measure report --host host.jsonl --client probe-relayed.jsonl` を使います。

気をつけること：

- 2つの窓は同じディスプレイに置く。ディスプレイが違うと、ディスプレイの差を測ってしまう。道具は、違うディスプレイのときは測らずに止まる。
- 道具が見るのは、それぞれの窓の中央。ほかの窓をかぶせない。中継側の窓は、既定では Moonlight の窓を探す。ほかの窓にするときは `--relayed-window` で指定する。
- Mac が Wi-Fi なら、共有の機能を設定で切って、AWDL を止めておく（[切り方と確かめ方](2026-11-16-wifi-sharing-off.md)）。それでも、近くの機器に求められると AWDL は戻る。計測のあいだ AWDL が動かなかったことをカーネルのログで確かめ、動いていたら、そのあいだに送った入力を外して集計する。
- 手元の窓と中継した窓は、同じ状態で測る。ふだんは、どちらも `open -n -g` で、前面に出さずに起動する。前面に出すと、そのとき人が打っていたキーをテストアプリが受け取り、色が切り替わる。受け取ってしまったキーは、`istesso measure compare` が数を表示して、計算から外す。
- 判定の回だけは、2 つの窓を前面に出して測る。そのあいだ Mac には触れないので、始める前に、Mac を使っている人に知らせて、返事を待つ。
- Moonlight は、マウスカーソルのあるディスプレイに窓を出す。起動のときだけ、カーソルを目的のディスプレイに置く。
- 道具を変えたときは、手元のテストアプリを 2 つ並べて（ポートと `--title` を変える）、差が 0 になることを確かめる。
- テストアプリは、計測のたびに起動し直す。入力の番号は毎回 0 から始まるので、1つのログに 2 回ぶんが入ると、2 回目が 1 回目の値と対になる。`istesso measure compare` と `istesso measure report` は、番号の重なりを見つけると警告する。
- 合格ラインの指標は、手元の窓の値にも左右される。手元の窓の追加遅延の中央値が、いつもの値から 2 ms 以上ずれた回は、やり直す。いつもの値は、機材と絵で変わるので、記録に書いておく。MacBook Air の外部ディスプレイ（85 Hz）で、前面に出さない 600×400 の窓、灰色の絵のときは 17.3 ms（17.1〜17.4 ms、4 回）。

測れるのは、画面更新 1 回の刻みまでです。ディスプレイのパネルと入力機器の遅れ、配信ソフト自身の入力の経路は入りません（ADR 0008）。

### 内訳の計測（手順 3 の経路。どこに時間がかかっているかを知りたいときに行う）

「画面での計測」に、フレームごとの記録を足します。入力ごとに、その入力を最初に映したフレームを、コンポジターから画面まで追います。

1. ホストで、`gst-launch-1.0` の代わりに `scripts/m1-step3-host.py --to <Mac のアドレス> --log host-frames.jsonl` でパイプラインを動かす（`GST_PLUGIN_PATH` は同じ）。いまの基本の形は、`--frames cuda` を足したもの。圧縮の設定は、決まったもの（4:4:4、キーフレームは求められたときだけ、30 Mbps、レート制御のバッファーは 1 フレームぶん）が既定になっている。4:2:0 にするときは `--chroma 420`、決まった間隔でキーフレームを出すときは `--gop <フレーム数>`。`--frames cuda` には、`cuda` つきでビルドしたコンポジターのプラグインが要る（[記録](2026-11-16-step3-gpu-frames.md)）。動く絵では、`--vbv` を付けないと、キーフレームが数百パケットになって欠ける（[記録](2026-11-16-step3-moving-picture.md)）。
2. Mac で、`gst-viewer` の 7 番目の引数に記録の置き場所を足す。8 番目の引数に、キーフレームの求めを送るポート（映像のポートの次。既定の映像なら 5005）を足す。これがないと、キーフレームを求められたときだけ出す送信側（既定）からは、絵が出ない。パイプラインには、見る要素に名前を付ける（`udpsrc name=net`、`avdec_h265 name=dec`、`glimagesink name=sink`）。VideoToolbox で復号するときは、`h265parse` のあとを `video/x-h265,stream-format=hvc1,alignment=au ! appsink name=vt sync=false` にする。
3. 「画面での計測」のとおりに測る。同じ時間帯の `ping` と見比べたいときは、計測のあいだ `ping --apple-time -i 0.2 <ホスト>` も流す。
4. 集計する。

   ```sh
   scripts/m1-step3-breakdown.py --probe-relayed probe-relayed.jsonl --host-app host.jsonl \
       --host-frames host-frames.jsonl --client-frames client-frames.jsonl \
       --probe-local probe-local.jsonl --local-app local.jsonl --ping ping.txt
   ```

区間は、足すと「入力を送ってから画面に出るまで」になるように切ってあります。見積もりは入りません。そのあとの「Stream」に、フレームの数とビットレート、キーフレームの数と出どころ、受信側が求めた回数、パケットが欠けた回数と、そのたびに絵が止まっていた時間が出ます。判定の記録には、これも書きます。

| 区間 | 時計 | 内容 |
|---|---|---|
| ネットワーク（行きと帰り） | 両方 | クライアントで測った「入力を送ってから、フレームの最初のパケットが届くまで」から、ホストで測った「入力が届いてから、パケットを渡すまで」を引いた残り。`ping` の往復時間と見比べる |
| アプリ | ホスト | 入力が届いてから、フレームを確定するまで |
| コンポジター | ホスト | フレームの確定から、その色のフレームがコンポジターを出るまで |
| 圧縮、パケットにする | ホスト | コンポジターを出てから、ネットワークへ渡すまで |
| フレームが届く、復号、描画 | クライアント | 最初のパケットから最後のパケットまで、復号が終わるまで、表示の要素が描くまで |
| 窓の合成と表示 | クライアント | 描いてから、画面に出るまで |

読むときの注意：

- 灰色の絵（`--picture grey`）では、圧縮したフレームは 1 kB に満たず、パケット 2 個で届きます。圧縮、転送、復号にかかる時間は、いちばん小さい場合の値です。ふだんの画面に近い値は、動く絵（既定）で測ります。
- フレームを GPU の外に出さない経路では、ホストでフレームの色を読めません。そのときは、Mac で最初に新しい色を映したフレームから、逆にたどって集計します。両方でたどれる回では、同じフレームに行き着くことを確かめてあります。
- 記録を取ること自体の影響は、取らない回と追加遅延を見比べて確かめます。

### 画質の計測（圧縮の設定を変えたときに行う）

遅延は、画質と引き換えに小さくできます。そこで、遅延の値には、同じ設定での画質の値を並べて記録します（ADR 0002）。

テストアプリの動く絵は、どの PC でも、何度作っても同じです。そこで、送った絵を取り込む代わりに、同じ絵を作り直して比べます。ホストだけで測れ、Mac は要りません。

```sh
# ホストで。手順 3 の送信側と同じエンコーダーに、同じ絵を通す
scripts/m1-quality.py --size 3440x1440 --bitrate 30000 --chroma 420,444 --gop 170,-1
```

```text

                        kbit         frame kB  mean    5%      min     mean    5%      min         mean
4:2:0     30000  170     353    26.6       72  0.9951  0.9899  0.7615  0.9628  0.9370  0.8994      42.5
       key frame at 850: brightness 0.7758, back within 0.01 of the usual value after 7 frames (82 ms)
       key frame at 1020: brightness 0.7615, back within 0.01 of the usual value after 7 frames (82 ms)
       （略）
4:4:4     30000   -1     353     4.8       15  0.9996  0.9996  0.9996  0.9991  0.9990  0.9990      47.7
```

- 1,700 フレーム（20 秒）を通し、はじめの 850 フレーム（10 秒）は集計から外します（`--count`、`--skip`）。はじめのキーフレームのあと、エンコーダーが絵を直し終えるまでに 6〜7 秒かかるためです（そのとき映っていた文字が、窓の外へ流れ出るまでの時間）。短く切ると、ビットレートが実際の配信の 3 倍に出ます（[記録](2026-11-16-quality.md)）。
- **SSIM** は、元の絵とどれだけ同じ形をしているかを 0 から 1 で表す値です（1 が同じ）。明るさと、色（2 つの色差の平均）について、全フレームの平均、悪いほうから 5% のフレームの値、いちばん悪いフレームの値を出します。色は、間引かれる前の細かさで比べます。色を 4 分の 1 に間引く 4:2:0 の損が、ここに出ます。
- 「key frame at …」は、キーフレームでどこまで落ちて、何フレームで戻ったかです。
- `--no-codec` は、圧縮をせずに、色の変換だけを往復させます。圧縮がどれだけ良くても、この値は超えられません（8 ビットの上限）。
- `--scale 1` は、線が 1 ピクセルの文字の絵です（テストアプリの `--stroke 1`）。`--key-at <フレーム>` は、その番号でキーフレームを求めます。パケットが欠けたときにクライアントが求めるのと同じ動きです。
- `--crops <置き場所> --crop-frames <番号>` で、絵の一部を PNG に書き出します。数字がどう見えるかを、目で確かめるときに使います。
- 復号は、ホストの GPU（`nvh265dec`）で行います。H.265 は、同じストリームからは同じ絵が出るように決まっているので、Mac の復号の代わりになります（ソフトウェアの `avdec_h265` と、値が一致することを確かめてあります）。**Mac が、その絵をどういう色で画面に出すかは、この方法では分かりません。** それは、止めた絵を中継して、窓を取り込んで比べます（[記録](2026-11-16-quality.md) の「Mac の画面に出る色」）。
- GStreamer のソフトウェアの色変換（`videoconvert`）は、戻すときに最大で 5 レベルずれます。圧縮の損と混ざるので、この道具は、戻す変換も GPU（`cudaconvert`）で行います。

### ソフトウェアでの計測（常に行う）

1. ホストでテストアプリを動かす。入力のたびに窓全体の色が切り替わる。
2. クライアントから入力を送り、復号したフレームの色が変わった最初のフレームを「反応したフレーム」とする。
3. 入力の間隔は 200〜400 ms の間でばらつかせる。一定の間隔だと、画面更新の周期と同期して偏った値になる。
4. 500 回以上（判定のときは 2,000 回以上）測り、中央値、95 パーセンタイル、99 パーセンタイル、最大値を出す。

### カメラでの確認（節目ごとに行う）

ソフトウェアの計測にも、画面での計測にも、入力機器とディスプレイの遅れが入りません。数値が体感と合っているかを、カメラで確かめます。回数を稼ぐのは画面での計測に任せ、カメラは確認に使います。

1. 240 fps で、キーを押す指と画面を同じ画角に収めて撮る。
2. 押してから画面が変わるまでのコマ数を数える。1コマは約 4.2 ms。
3. 20 回以上数え、平均と最大を出す。
4. 中継したときと、中継なしで直接操作したときの**差**を見る。絶対値には機器の遅れが含まれるので、差だけが追加遅延に対応する。
