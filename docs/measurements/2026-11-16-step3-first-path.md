# 手順 3：既製の部品でつないだ最初の 1 本

- 日付：2026-11-16
- コミット：1f48c0d
- 目的：自前のコードを書く前に、予定している方式（仮想コンポジター → NVENC → RTP → Mac で復号して窓に出す）でどの数値が出るかを知る（[m1-plan.md](../m1-plan.md) の手順 3）。

## 条件

| 項目 | 値 |
|---|---|
| ホスト | Ubuntu 24.04、RTX 4090（ドライバー 590.48.01）、GStreamer 1.24.2。仮想コンポジターは gst-wayland-display（`1301f86`）で、NVIDIA の GPU で描画 |
| クライアント | MacBook Air（M4）、macOS 26.5.1、GStreamer 1.28.9（Homebrew）。`macos/gst-viewer` を `open` で起動（ふつうの優先度） |
| 接続 | ホストは有線（2.5 Gbps）、Mac は Wi-Fi（6 GHz 帯）。AWDL は止め続け、計測のあいだ戻らなかった。経路の往復は中央値 3.3 ms、95 パーセンタイル 7.1 ms（[記録](2026-11-16-path-host-wired.md)） |
| 解像度とフレームレート | 1720×720、85 fps |
| クライアントのディスプレイ | 外部（3440×1440、84.96 Hz）。手元の窓と中継した窓を並べた |
| コーデックとビットレート | H.265 Main、30 Mbps（固定ビットレート） |
| エンコーダーの設定 | `nvcudah265enc preset=p1 tune=ultra-low-latency zero-reorder-delay=true b-frames=0 rate-control=cbr gop-size=170`。コンポジターの出力（RGBx）を `cudaupload` と `cudaconvert` で GPU に上げて NV12 にしている |
| 経路 | RTP（`rtph265pay`、MTU 1200）を UDP で送る。暗号化なし。入力は合成の入力（UDP） |
| 受信側 | `rtph265depay ! h265parse ! avdec_h265 max-threads=1`（ソフトウェアの復号）、いちばん新しいフレームだけを残す `queue`、`glimagesink sync=false` |

パイプラインの全体は m1-plan.md の手順 3 にあります。

## 測り方

[README.md](README.md) の「画面での計測」のとおりです。11:12:04 から 11:15:16（JST）に、500 回、200〜400 ms の間隔で測りました（乱数の種は 20261116）。ホストのテストアプリは、仮想コンポジターの中で、出力いっぱい（1720×720）に広がっています。

比べる相手は、同じ日に同じ条件（ホストは有線、AWDL は停止、同じディスプレイ、同じ解像度）で測った [Sunshine と Moonlight の基準](2026-11-16-step2-baseline-host-wired.md)の、V-sync なしの回です。

## 結果

### 手元の窓との差

| 対象 | 平均 | 中央値 | 95% | 99% | 最大 |
|---|---|---|---|---|---|
| **既製の部品の 1 本** | **17.4 ms** | **11.8 ms** | **23.5 ms** | **35.3 ms** | 141.2 ms |
| Sunshine と Moonlight | 23.3 ms | 19.1 ms | 53.3 ms | 66.6 ms | 84.9 ms |

画面更新の回数（1回 11.8 ms）で数えると、次のとおりです。

| 遅れた更新の回数 | 0 | 1 | 2 | 3 | 4 以上 | 平均 |
|---|---|---|---|---|---|---|
| 既製の部品の 1 本 | 18 | 245 | 228 | 7 | 2 | 1.48 回 |
| Sunshine と Moonlight | 43 | 154 | 173 | 56 | 74 | 2.00 回 |

| 収まった割合 | 1 回ぶん以内 | 2 回ぶん以内 | 3 回ぶん以内 |
|---|---|---|---|
| 既製の部品の 1 本 | 52.6% | **98.2%** | 99.6% |
| Sunshine と Moonlight | 39.4% | 74.0% | 85.2% |

### 追加遅延（往復時間 − アプリ自身の応答時間）

| 対象 | 中央値 | 95% | 99% | 最大 |
|---|---|---|---|---|
| 既製の部品の 1 本 | 37.4 ms | 47.2 ms | 52.0 ms | 167.0 ms |
| Sunshine と Moonlight | 37.9 ms | 71.7 ms | 81.7 ms | 112.1 ms |
| 手元の窓（中継なし） | 17.9 ms | 23.5 ms | 26.9 ms | 164.9 ms |

アプリ自身の応答時間は、ホストで中央値 0.7 ms、手元で 3.0 ms でした。

取り込みと圧縮、復号、表示待ちの内訳は、まだ測っていません。カメラでの計測も、まだ行っていません。

## わかったこと

1. **予定している方式は、既製の部品を並べただけで、成熟した実装に並びます。裾は大きく良くなります。** ふつうのとき（中央値）の追加遅延は 37.4 ms と 37.9 ms で、ほぼ同じです。95 パーセンタイルは 47 ms と 72 ms で、25 ms 短くなっています。手元の窓との差が画面更新 2 回ぶん以内に収まった割合は、98% と 74% です。
2. **この先へ進める見込みがあります。** 手元の窓との差は、中央値で更新 1 回ぶん、95 パーセンタイルで 2 回ぶんでした。ただ、1 回ぶん以内に収まったのは 52.6% で、中央値は 1 回と 2 回の境目にあります。平均は 1.5 回ぶん（17 ms）です。
3. **最大の 141 ms は、Mac 側の一時的な停止です。** 同じ入力で、手元の窓も 168 ms かかっています。

読むときの注意：

- **手元の窓との差は、この回のほうが約 2 ms 有利に出ています。** ホストのテストアプリの応答が 0.7 ms で、基準のとき（2.8 ms）より速いためです。基準では、テストアプリが 3440×1440 の全画面でした。アプリの応答時間を引いた追加遅延のほうが、公平な比べ方です。
- **基準のほうは、実際より良く見えている可能性があります。** Moonlight の V-sync なしでは、差が画面更新の整数倍にならない入力が 500 回中 418 回ありました。画面に実際に出るのが次の更新だとすると、基準の値は最大で更新 1 回ぶん大きくなります。カメラで確かめる点です。
- 復号はソフトウェアです。GStreamer の VideoToolbox 用の要素が使えなかったためです（m1-plan.md）。
- 暗号化も、パケットを失ったときの回復もありません。2 秒ごと（170 フレームごと）にキーフレームを入れています。

次に行うこと：

- 内訳を測る。ホストでは、フレームの確定から送り出しまで。Mac では、受信から復号、表示まで。
- 設定を 1 つずつ変えて比べる（m1-plan.md の手順 3）。見込みが大きいのは、コンポジターが決まった間隔（85 fps）で描いている待ち時間と、GPU への上げ直しです。
- 合格ラインを決める。
