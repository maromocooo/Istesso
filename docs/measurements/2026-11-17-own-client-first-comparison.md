**この回は、音の夜の試験が動いている夜に、Mac でシステムのデーモンが 1 コアを使い続けているあいだに測った。読めるのは、試作と自前のクライアントの差だけである。ここの値を、静かな条件で測った値（関門の判定、再起動の確かめ）と、比べてはいけない。**

- 日付：2026-11-17、19:21〜19:38（日本時間）。本線が測った。この記録は、4 回の生の記録から、数え直して書いた
- 比べたもの：A＝試作（ビューアーと中継を、アプリとして起動。関門の判定の形）。B＝自前のクライアント（計測用のビルド `Istesso Dev Measure`、コミット a932a60、ビルドの UUID C18B23E1-…。切り替えは、全部「切」）
- 順番：A1、B1、A2、B2。500 入力ずつ。ホストの側は、4 回とも同じ（関門の判定の候補 8965510）
- 結論：**この 4 回では、A と B の差は、見つからない。あるとも、ないとも、言えない。** 入力ごとの差の平均で、B − A ＝ +0.13 ms（標準誤差 0.23 ms）。クライアントの中の区間（入力、復号、待ち行列、描くまで）は、0.01〜0.04 ms の差で並んでいる。「同じ」と言うには、入力が足りない（下の「次の比べ」）

## 決めてあった読み方で読む

決めてあったこと：A1 と A2 の差を「揺れ」とする。読むのは、中央値と 95%。

- 揺れ（A1 と A2）：中央値で 0.26、95% で 0.26（10.53 と 10.79）。
- **95%**：B1 10.62、B2 10.80。どちらも、A の 2 回（10.53、10.79）の幅の中か、0.01 外。**並んでいる。**
- **中央値**：B1 10.14 は、A の幅（10.50〜10.76）より 0.36 下。B2 10.95 は、0.19 上。**B の 2 回は、A の幅を、上と下からはさんでいる。** B の 2 回どうしの差は 0.81 で、A の 0.26 より大きい。
- **この読み方では、決まらない。** B は、A より速いとも、遅いとも、言えない。

**物差しが、小さすぎた。** A の 1 組（0.26）を揺れとしたが、同じものを 2 回測ったときの「中央値の差」は、たまたまでも、もっと動く。4 回の入力を、くじのように引き直して数えた（ブートストラップ）：

| | たまたまの動き（1 標準偏差） |
|---|---|
| 1 回の「差：中央値」 | 0.35〜0.45 ms |
| 2 回の「差：中央値」どうしの差 | 0.5〜0.6 ms |
| 1 回の、入力ごとの差の平均 | 0.23 ms |
| 2 回の、その平均どうしの差 | 0.32 ms |

- A1 と A2 の 0.26 は、たまたま小さかった（0.4 標準偏差）。B1 と B2 の 0.81 は、1.6 標準偏差で、珍しくない。
- 中央値は、画面の更新 1 回ぶん（11.76 ms）の段の上に乗っているので、平均より、よく動く。**次からは、入力ごとの差の平均と、その標準誤差で読む**のがよい（提案）。

## B の 2 回は、なぜ 0.8 違ったか

**見えたこと**（生の記録から）：

| | A1 | A2 | B1 | B2 |
|---|---|---|---|---|
| 手元の窓：中央値 | 17.63 | 17.90 | 18.06 | 17.78 |
| 手元の窓：平均 | 17.69 | 17.94 | 17.96 | 17.84 |
| リレー先の窓：中央値 | 28.39 | 28.40 | 28.19 | 28.72 |
| リレー先の窓：平均 | 28.36 | 28.24 | 28.34 | 28.68 |
| 区間「描いてから、映るまで」の平均 | 17.74 | 17.62 | 17.71 | 17.93 |

- A：リレー先の窓の中央値は、同じ（28.39、28.40）。手元の窓だけが、0.27 動いた。差は 0.26。
- B：リレー先の窓が +0.53、手元の窓が −0.28。**逆向きに動いたので、足して 0.81 になった。**
- B2 のリレー先の窓が遅いぶん（平均で +0.33）のうち、+0.22 は、「描いてから、映るまで」（画面の更新を待つ時間）にある。クライアントの中の区間は、復号 +0.07、描くまで +0.06、入力 +0.02。
- B2 では、手元の窓の入力が、更新 1 回の中に、均等に落ちなかった（8 つに分けた最後の所に 88。道具は「NOT evenly」と言った）。ほかの 3 回は、均等。

**考えたこと**：片方の側のせい、とは言えない。手元の窓も、リレー先の窓も、たまたまの幅（平均で 0.23、中央値で 0.2〜0.4）の中で動き、B では、それが逆向きに重なった。B2 の遅いぶんは、主に、画面の更新との位相（どちらのプログラムも、決めていない）にある。B の 2 回は、Mac の負荷も、A より 0.6 高かった。これが効いたかどうかは、この 4 回からは、分からない。

## 次の比べ（提案）

「同じか、違うか」を決めるには：

1. **読むものを、入力ごとの差の平均と、その標準誤差にする。** 中央値と 95% は、これまでどおり出すが、決めるのには使わない（段の上に乗っていて、動きすぎる）。
2. **入力を増やす。** 1 入力のばらつきは 5.07 ms。B − A の標準誤差は、1 つの側が 1,000 入力で 0.23 ms、2,300 入力で 0.15 ms、5,100 入力で 0.10 ms。「0.3 ms の差があれば、見つける」なら、1 つの側に 2,300 入力（たとえば、A B A B で 1,200 ずつ。約 35 分）。「0.2 ms 以内で同じ」と言うなら、1 つの側に 5,100 入力（たとえば、A B A B A B で 1,700 ずつ。約 75 分）。
3. **交互に測る**（A B A B …）。負荷や位相のゆっくりした動きが、片方に寄らないように。
4. **Mac を、静かにしてから。** この回は、デーモンが 1 コアを使っていた。B の回だけ、負荷が高かった。
5. **切り替えは、`keys-qos` から。** 計測の入り口のスレッドを、製品の窓のスレッドと同じ扱いにする。入力の区間の +0.035 ms が、消えるか、残るかが分かる。そのあと、`input-qos`、`picture-qos`、`latency-critical`、`picture-realtime` を、1 つずつ。区間の平均は、500 入力でも 0.01 ms まで読めるので、切り替えの効き目は、区間で読む（全体の差で読むには、入力が足りない）。

## 測っていないこと

- 静かな Mac での値。この回の値は、どれも、負荷のある Mac のものである。
- 切り替え（`--wake`）を入れた形。全部「切」だけを測った。
- 人が、本物のキーを打つ道（窓のイベントから）。計測のキーは、計測の入り口から入る（ADR 0018）。窓のイベントの道は、確定の判定のあとの、参考の回。
- 2,000 入力の回（99% を読める回）。
- B の 2 回で Mac の負荷が高かったわけ。
- 作り直した直後の、最初の起動の遅れ（はじめの試みが落とされるぶん）。計測は、絵と入力が開いてから始めた。
