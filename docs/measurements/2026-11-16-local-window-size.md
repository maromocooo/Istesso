# 手元の窓の値は、窓の大きさで変わるか

- 日付：2026-11-16
- コミット：bfe30a3（コードの変更なし）
- 目的：判定では、3440×1440 の中継の窓を画面いっぱいに出し、600×400 の手元の窓をその隅に重ねて測る。手元の窓が小さいことで、比べる相手として有利にも不利にもなっていないかを確かめる。あわせて、その置き方で道具が両方の窓を読めるかを見る。

## 条件

| 項目 | 値 |
|---|---|
| ホスト | 使っていない |
| クライアント | MacBook Air（M4）、macOS 26.5.1。テストアプリを 2 つ、どちらも Mac の上で動かした |
| 接続 | なし（何も中継していない） |
| 解像度とフレームレート | 1 つ目の窓は 600×400。2 つ目の窓は 600×400、1720×720、3440×1440（画面いっぱい、枠なし） |
| クライアントのディスプレイ | 外部（3440×1440、84.96 Hz）。どの窓も前面に出さずに起動した |
| テストアプリの絵 | 動く絵（文字のスクロール）、CPU で描く、1 秒に 85 回、入力にはその場で答える |

## 測り方

[README.md](README.md) の「画面での計測」と同じ道具で、2 つの窓に同じ入力を 300 回ずつ送りました。1 つ目の窓（いつもの手元の窓）を「手元」、2 つ目の窓を「中継」として道具に渡しています。2 つ目の窓が 3440×1440 のときは、その上に 1 つ目の窓が重なります。

| 2 つ目の窓 | 時刻（JST） |
|---|---|
| 600×400 | 15:58:03〜16:00:20 |
| 1720×720 | 16:00:21〜16:02:38 |
| 3440×1440 | 16:02:52〜16:05:11 |

## 結果

追加遅延（往復時間 − アプリ自身の応答時間）です。

| 2 つ目の窓 | 2 つ目の窓（中央値 / 95%） | いつもの窓（中央値 / 95%） | 差（中央値 / 95%） | 2 つ目の窓のアプリの応答（中央値） | 2 つ目の窓のアプリの CPU |
|---|---|---|---|---|---|
| 600×400 | 17.6 / 23.1 ms | 18.1 / 22.9 ms | −0.5 / +0.2 ms | 2.9 ms | 27% |
| 1720×720 | 17.9 / 23.0 ms | 17.6 / 23.1 ms | +0.4 / −0.1 ms | 7.1 ms | 46〜49% |
| 3440×1440 | 18.5 / 22.8 ms | 17.4 / 23.0 ms | +1.1 / −0.2 ms | 17.1 ms | 93〜97% |

どの回も、300 回すべてが両方の窓に映りました。

カメラでの計測：行っていません。

## わかったこと

- **手元の窓の追加遅延は、窓の大きさでほとんど変わりません。** 中央値の差は、同じ大きさどうしで −0.5 ms、1720×720 で +0.4 ms、3440×1440 で +1.1 ms でした。95 パーセンタイルの差は、どれも 0.2 ms 以内です。
- 3440×1440 の +1.1 ms は、テストアプリが追いついていない影響かもしれません。その大きさでは、CPU で 1 フレームを描くのに 17 ms かかり、1 秒に 85 回を保てていません。
- **画面いっぱいの窓の隅に、小さい窓を重ねる置き方で測れます。** 道具は、両方の窓の中央を読めました。
- 判定では、600×400 の手元の窓を、比べる相手としてそのまま使います。
