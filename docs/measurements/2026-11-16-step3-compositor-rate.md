# 手順 3：コンポジターのフレームレートを上げる（設定の比較 1）

- 日付：2026-11-16
- コミット：この記録と同じコミット（コードの変更なし）
- 目的：[内訳の記録](2026-11-16-step3-breakdown.md)で、いちばん大きかったのは、コンポジターが次に描くまでの待ち（平均 5.9 ms）だった。既製の部品のまま、コンポジターのフレームレートを画面更新の 2 倍、3 倍にして、この待ちがどれだけ縮むかを見る。

## 測り方

## わかったこと

1. **コンポジターのフレームレートを 2 倍にすると、合格ラインの指標の中央値が 21.4 ms から 15.1 ms に下がりました。** 95 パーセンタイルも 23.8 ms から 17.3 ms です。ラインの 12 ms まで、あと 3.1 ms です。
2. **コンポジターの待ちは、見込みどおりに縮みました。** ホストだけの計測で、確定から出るまでの平均が 8.9 ms から 5.8 ms（2 倍）、4.7 ms（3 倍）になりました。フレームの間隔の半分ずつ（5.9、2.9、2.0 ms）と、描き始めてから出すまでの約 3 ms を足した値です。
3. **Mac の側も約 2 ms 速くなりました。** 復号が 0.8 ms、表示の要素が描くまでが 0.5 ms、画面に出るまでが 0.8 ms 縮んでいます。仕事の間隔が詰まって、処理が速い状態のまま続くためとみていますが、確かめていません。85 fps で流すときも、受信側を休ませない工夫で同じ分が縮む可能性があります。
4. **この手は、画素数が増えると使えません。** 3440×1440 では、コンポジターが 1 フレームを出すのに約 10 ms かかるので（[内訳の記録](2026-11-16-step3-breakdown.md)）、100 fps あたりが上限です。フレームレートを上げるほど、遅れるフレームも増えています（255 fps で 0.5%）。
5. **代わりに払うもの**は、2 倍の数のフレームの圧縮、送信、復号です。テストアプリの絵（一面の灰色）ではフレームが 63 バイトなので、帯域への影響は見えていません。ふつうの画面では、同じビットレートを 2 倍の数のフレームで分けることになります。

自前の実装（手順 4）への意味：

- 決まった間隔で描くのをやめて、アプリが新しい絵を出したときにすぐ描けば、待ちは 0 に近づきます。170 fps にして得た 3.2 ms より大きく、85 fps のままで取れるはずの分です（待ちの平均は 5.9 ms）。
- 既製の部品のままでも、170 fps にするだけで、中央値はラインまで 3.1 ms のところに来ました。Mac を有線にする分と、フレームを GPU の外に出さない分が、まだ残っています。

読むときの注意：

- A と C は、約 30 分あけて測っています。そのあいだに変えたのは、フレームレートだけです。
- C の 99 パーセンタイルの差（29.4 ms）は、A（27.6 ms）より大きい値です。650 回の 99 パーセンタイルは、遅いほうの 7 回で決まります。C では、ネットワークの 99 パーセンタイルが 22.2 ms、最大が 69.8 ms でした（A は 16.5 ms と 36.9 ms）。
- テストアプリの絵が一面の灰色なので、圧縮の設定（プリセット、キーフレームの間隔、ビットレートの制御）を変えても、いまの計測では差が出ません。それらを比べるには、圧縮しにくい絵を出せるテストアプリが先に要ります。

次に行うこと：

- コンポジターの出力を GPU の上のまま（DMABuf）エンコーダーに渡せるかを確かめる。
- テストアプリに、ふつうの画面に近い絵を出すモードを足してから、圧縮の設定を比べる。
- Mac を有線にしたら、85 fps と 170 fps の両方を測り直す。
