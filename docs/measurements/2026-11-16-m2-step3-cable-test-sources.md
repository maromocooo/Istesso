# M2 手順 3 の手前：2 台のあいだを、テスト用の音源で通す

- 日付：2026-11-16
- コミット：dca057f（両方の PC で、この版をビルドした）
- 目的：ホストの取り込み（PipeWire のクライアント）は、まだない。その前に、次の 2 つを確かめる。
  1. 何も入れずに取り込みの代わりをさせる形（[m2-plan.md](../m2-plan.md) の「手順 3 のつなぎ」）が、ホストを元のままにしておけるか。
  2. 音のデータが、2 台のあいだを有線で通るか。届く間隔、いちばん長い停止、時計のずれ、遅延はどれだけか。

**音は出していません。** Mac の機器には無音を渡し、渡すはずだった音を調べています。ホストでは、何も鳴らしていません（1 では、機器につながっていない仮の出力先を作っただけ。2 では、サウンドシステムを使っていません）。

## 条件

| 項目 | 値 |
|---|---|
| 音源 | Ubuntu 24.04（PipeWire 1.0.5、WirePlumber 0.4.17）。`istesso audio serve` |
| 出口 | MacBook Air（M4、macOS 26）。内蔵の出力、48 kHz、1 回に 512 フレーム。`istesso audio play`。機器には無音を渡す |
| 経路 | 有線（Mac の側は USB の有線 LAN アダプター）。ping の往復は、10 回で 0.42〜0.91 ms、平均 0.62 ms |
| 端末の鍵 | この試験のために、両方の PC の作業用の場所に作ったもの（`ISTESSO_CONFIG_DIR`）。互いにペアリングし、ホストの側の作業用の一覧でだけ、音の権限を与えた。人のペアリングと鍵には触っていない |
| ホストでの優先度 | `nice -n 10`（映像の作業の邪魔をしないため）。負荷は 2.8 前後だった |
| Mac での起動 | エージェントのシェルから。`open` で起動したアプリは、ローカルネットワークに出られないためである。受信のスレッドは、低い優先度で動いた。Core Audio のスレッドは、起動のしかたによらずリアルタイムの優先度で動く |

**どちらの端も、わざと不利な優先度で動かしています。** 下の「停止」の数値は、その条件でのものです。

## 1. つなぎの評価

試した形：`pw-cli` で、機器につながっていない仮の出力先（`support.null-audio-sink`）を作る。そこに流れた音を GStreamer（`pulsesrc` → `fdsink`）で読み、生の PCM をパイプで `istesso audio serve --source stdin` に渡す。仮の出力先には、何も流していません（流すプログラムが出力先を見つけられないと、既定の出力から鳴るおそれがあるため）。取り込んだのは無音です。

| 確かめたこと | 結果 |
|---|---|
| 既定の出力先が変わらない | 変わらない。`wpctl status` と既定の出力先の設定を、前・最中・後で比べた。違いは、仮の出力先がある間の 1 行だけ |
| 音が出ない | 出ていない |
| 終わったあとに、仮の出力先が残らない | 残らない。ただし `pw-cli` は、入力が終わっても終了しない。1 回目は、気づいて止めるまで約 2 分、動き続けていた（`ps` で実行中の状態。CPU を使い続けていたとみられる）。2 回目からは、時間を決めてシグナルで止めた |
| **あとに何も残らない** | **残る。** セッションマネージャー（WirePlumber）が、状態のファイル（`restore-stream`）に 8 行を書いた。仮の出力先の名前で 4 行、読み取ったプログラム（`gst-launch-1.0`）の名前で 4 行。中身は、音量 1.0 とミュートなし（既定の値と同じ）とチャンネルの並び |

**結論：この形は、もう使いません。** 「あとに何も残らない」という条件を満たさないためです。

- 残った 8 行は、同じ名前の出力先か、同じ名前のプログラムが次に現れたときに、同じ既定の値を当てはめるだけのものです。いまの音の出方には、影響しません。`gst-launch-1.0` の 4 行が前からあったものかどうかは、わかりません。
- ファイルには手を付けていません。音の作業の場所の外にあり、セッションマネージャーが動いたまま書き直しても、上書きされるためです。消すかどうかは、人が決めます。
- この形は、数値も製品の経路を表しません。取り込んだ時刻が、パイプを通ったあとの時刻になるためです。上流で止まっても、出口からは遅れに見えず、再開の位置がずれます。60 秒の 1 回では、補正が −307〜+106 ppm の範囲で振れました。

その 1 回の値（待ち時間の目標 60 ms、60 秒）：受け取った 11283 パケットは、送ったものとすべて同じ。届く間隔は、中央値 5.36 ms、95 パーセンタイル 7.46 ms、99 パーセンタイル 11.29 ms、最大 63.9 ms。途切れ 1 回（21 ms）。

**本物の取り込みでも、同じことが起きるはずです。** こちらのプロセスが作る仮想の出力先も、セッションマネージャーが名前で覚えます。出力先の音量を覚えるのは、セッションマネージャーのふつうの動きですが、覚えさせない指定（`state.restore-props`）が効くかどうかを、取り込みを書くときに確かめます。

## 2. テストの正弦波を、ホストから Mac へ

ホストで `istesso audio serve --source tone`（997 Hz、−12 dBFS、1 パケット 256 フレーム。タイマーで刻む。サウンドシステムは使わない）、Mac で `istesso audio play`（待ち時間の目標 40 ms、90 秒）。

| 項目 | 値 |
|---|---|
| 受け取ったパケット | 16913。送ったものと、すべて同じ。抜け 0 |
| 届く間隔：中央値 | 5.45 ms |
| 同：95 パーセンタイル | 6.40 ms |
| 同：99 パーセンタイル | 7.43 ms |
| 同：最大（いちばん長い停止） | 49.7 ms |
| 途切れ | 4 回（合わせて 58.7 ms）。4 回とも、同じ 1 秒のあいだ（始めてから 47〜48 秒） |
| 飛ばし | 0 |
| 渡すはずだった音：大きさ | −12.00 dBFS |
| 同：音の谷 | 1（67.5 ms。上の途切れ） |
| 同：波形の飛び（クリック） | 0 |
| 同：音程（公称との差） | 平均 −0.3 ppm、−68.9〜+69.3 ppm |
| 待ち時間（いちばん速いパケット。1 秒ごとの値） | 39.19〜40.66 ms |
| **取り込みから機器に渡すまで：中央値** | **46.5 ms** |
| 同：95 パーセンタイル、99 パーセンタイル | 47.0 ms、47.2 ms |
| 2 台の時計の差の測り方 | 時刻の問い合わせ 16 往復。いちばん短い往復は 0.59 ms（誤差は ±0.3 ms 以内） |
| 補正の覚えた時計の差 | +7.4 ppm（ホストのシステムの時計と、Mac の機器の時計。90 秒では、まだ落ち着ききっていない） |
| 機器が引き取りに来る時刻（渡す時刻の何 ms 前か） | 10.56〜11.63 ms、平均 11.16 ms |

## わかったこと

1. **経路は、2 台のあいだで通る。** 認証と暗号化を通して、受け取ったパケットは、送ったものと 1 つ残らず同じだった。
2. **遅延は、計画の目標（有線で中央値 50 ms 以下）に収まった。** 待ち時間 40 ms で、取り込みから機器に渡すまでが 46.5 ms。Mac の中だけで測った値（46.9 ms）と変わらない。ただし、音源はテスト用の正弦波である。本物の取り込みでは、測り直す。
3. **90 秒に 1 度、約 50 ms 止まった。** 待ち時間 40 ms のうち、遅れたパケットのために使えるのは約 12 ms なので、67.5 ms の穴になった。前後はフェードで、クリックはなかった。どちらの端で止まったのかは、わからない。ホストの側は、`nice` を付けた、タイマーで刻むスレッド。Mac の側は、低い優先度の受信のスレッドである。**待ち時間の目標を決めるには、どちらの端も不利にしていない条件で、測り直す必要がある**（本物の取り込みと、ふつうの優先度で起動した再生）。
4. **1 度の停止が、途切れ 4 回に数えられた。** 模擬では、50 ms の停止 1 つは、途切れ 1 回になる（`istesso audio simulate --stall 60:0.05`）。実機では、停止が続けて起きたのか、再開の判断が実際の届き方に合っていないのか、まだ分けられていない。
5. **音程は、計画の目安（50 ppm 以内）を超えた。** 始まりと再開を含む 90 秒で、±69 ppm（0.12 セント）動いた。実機では、いちばん速いパケットの待ち時間が、1 秒ごとに 0.3〜0.6 ms ほど動く。補正は、待ち時間の 1 ms のずれを 100 ppm に変えるので、その分だけ振れる。模擬には、このゆっくりした揺れが入っていない。模擬で検査している上限（落ち着いたあとで 50 ppm）は、模擬した乱れについてのものである。作りとしての上限（0.1%、1 秒に 100 ppm）は、実機でも変わらない。聞こえる大きさではないが、実機での上限は、まだ示せていない。本物の取り込みで測り直し、要るなら、待ち時間をならす時間を長くする。

## まだ測っていないこと

- 本物の取り込み（PipeWire の仮想の出力先）。ビルドに要るパッケージは、この記録のあとでホストに入った。
- どちらの端も、ふつうの優先度で動かした場合。Mac で `.app` として起動するには、その `.app` にローカルネットワークの許可が要る。
- 44.1 kHz の機器、Wi-Fi、8 時間、耳で聞く確認。

## 再現のしかた

```sh
# 両方の PC で、作業用の場所に鍵を作る（ISTESSO_CONFIG_DIR）。互いにペアリングし、
# ホストの側で istesso peers allow <出口の名前> audio を実行する。

# ホスト
istesso audio serve --source tone --bind <有線のアドレス> --port 47822 --seconds 97 --ledger sent.txt

# Mac
istesso audio play <有線のアドレス>:47822 --peer <音源の名前> --latency-ms 40 --seconds 90 \
    --record played.f32 --ledger received.txt --report report.json
istesso audio compare sent.txt received.txt
```
