# 計測の入力を、本来の経路に通す（制御チャンネル → コンポジター → アプリ）

- 日付：2026-11-16
- コミット：この記録と同じコミット（プローブの `--relayed-keys`、`istesso measure compare --relayed-inputs keys`、`istesso input relay --address --keep-trying`、ホストのスクリプトの `key_in`）
- 目的：これまでの計測は、入力を、ホストのテストアプリへ UDP で直接送っていた。判定の入力は、人が打ったキーと同じ経路を通す、と決まった。その形を作り、直接送る形と比べる。
- 結論：**本来の経路を通すと、入力の区間が平均 0.7 ms 延びる。** 85 Hz・2 台とも有線・3440×1440 で、差は中央値 11.14 ms、95 パーセンタイル 11.20 ms（500 回）。判定の値ではない（500 回、窓は前面に出していない）。

## 入力の通り道

| | これまで | 本来の経路 |
|---|---|---|
| Mac | プローブが、UDP でホストのテストアプリへ送る | プローブが、キーを押した・離したというイベントを、手元のソケットへ書く。`istesso input relay` が受け取る |
| ネットワーク | 暗号化なし。番号つき | 制御チャンネル（`istesso-link`。暗号化と認証つき）で、ホストのエージェントへ |
| ホスト | テストアプリが、自分のソケットで受け取る | エージェントが、アプリを映しているプログラムへ渡す。コンポジターが、キーボードのキーとしてアプリへ送る |
| テストアプリ | 番号つきの入力として記録 | キーが押された、として記録（番号は、届いた順） |

- キーには番号がないので、集計のときに、テストアプリの記録の「キー」を届いた順に数え直して、プローブの番号と対にします（`istesso measure compare --relayed-inputs keys`）。ほかの誰もそのアプリにキーを打たないこと、送った数と届いた数が同じであることが前提です。集計は、届いた数を表示します。
- アプリがキーを受け取るには、コンポジターの中でそのアプリの窓が選ばれている必要があります。計測の前に、同じ経路で 1 回クリックを送ります。
- **`istesso input relay` は、アプリとして起動します**（`open` で。包みは `Istesso Input.app`）。エージェントのシェルから直接起動すると、優先度が低く、入力が遅れます（[README.md](README.md)）。アプリとして起動すると、優先度は 46 でした。初めて起動したとき、macOS が「ローカルネットワーク」の許可を人に尋ねます。答えるまでホストへつなげないので、`--keep-trying` で、つながるまで試し続けます。
- ホストは、有線と Wi-Fi の 2 つのアドレスで覚えられています。入力がケーブルを通るように、`--address` でホストの有線のアドレスを指定し、つながった接続の両端が有線のアドレスであることを、計測のたびに確かめます。
- 手元の窓のテストアプリへは、これまでどおり、プローブが直接送ります。

## 条件

[作り直したコンポジターの修正の記録](2026-11-16-step3-pacing.md) の「Mac まで通した値」と同じです（2 台とも有線、ディスプレイ 85.00 Hz、3440×1440、動く文字の絵、4:4:4、キーフレームは求められたときだけ、上限 30 Mbps、コンポジターは作り直した修正）。Mac の有線のアダプターは、この回から LAN の IPv4 アドレスを持っています（映像は、ケーブルの上の IPv6 のまま）。

## 結果（500 回、21:54〜21:57）

500 回とも、キーとしてテストアプリに届き、2 つの窓の両方で見えました。

| 指標 | 本来の経路（中央値 / 95% / 99%） | 直接送る形（中央値 / 95% / 99%）※ |
|---|---|---|
| **追加遅延の、手元の窓との差（合格ラインの指標）** | **11.14 / 11.20 / 16.14 ms** | 9.75 / 10.74 / 11.34 ms |
| 合格ライン | 12 / 24 / 47 ms | |
| 追加遅延（中継した窓） | 28.51 / 34.14 / 39.59 ms | 27.91 / 34.07 / 41.05 ms |
| 追加遅延（手元の窓） | 17.38 / 22.94 / 23.45 ms | 18.16 / 23.33 / 29.71 ms |

※ 同じ晩の 21:11 の回（[記録](2026-11-16-step3-pacing.md)）。

- 中継した窓の中央値は、27.91 ms から 28.51 ms（+0.6 ms）。**差の中央値が 1.4 ms 動いたうち、0.8 ms は手元の窓の値の違いです**（18.16 ms と 17.38 ms。今回は、いつもの値の 17.3 ms に近い）。手元の窓の値は、回ごとに 0.5 ms ほど動きます。
- 500 回なので、99 パーセンタイルは判断に使いません。

内訳（平均）：

| 区間 | 本来の経路 | 直接送る形 |
|---|---|---|
| **入力がアプリに届くまでと、最初のパケットが戻るまで** | **1.69 ms**（中央値 1.63、95% 2.35、99% 3.18） | 0.97 ms（中央値 0.87、95% 1.46） |
| うち、ホストの中（キーをコンポジターに渡してから、アプリが受け取るまで） | 0.31 ms（中央値 0.27、95% 0.52、99% 0.86、最大 3.31） | — |
| コンポジター（確定からフレームが出るまで） | 1.36 ms | 1.32 ms |
| 色の変換と圧縮 | 4.06 ms | 4.04 ms |
| パケットにして渡す | 0.17 ms | 0.16 ms |
| フレームが届く | 0.20 ms | 0.22 ms |
| 復号 | 3.07 ms | 3.01 ms |
| 復号してから、描くまで | 0.37 ms | 0.35 ms |
| 合計（中継のために足される区間） | 10.92 ms | 10.07 ms |

- **入力の区間は、0.97 ms から 1.69 ms（+0.72 ms）。** そのうち 0.31 ms が、ホストの中でコンポジターからアプリへ渡る時間です。残りの約 0.4 ms が、Mac の中継のコマンド、制御チャンネル（暗号化）、ホストのエージェントと、アプリを映しているプログラム（Python）を通る時間です。
- ほかの区間は、変わっていません。
- コンポジターを出たフレームは毎秒 84.9 枚。途中でキーフレームを求めた回数は 0、パケットの欠けは 0 回。更新 1 回ぶん以内に収まった入力は 96.4%。

カメラでの計測：行っていません。

## わかったこと

- **判定は、この形で測ります。** 入力が、暗号化と認証つきの制御チャンネルと、コンポジターを通ります。
- **中央値は 11.1 ms で、合格ライン（12 ms）まで 0.9 ms です。** 手元の窓の中央値は、今夜の 85 Hz の 3 回で 17.4〜18.2 ms でした。中継した窓が今回と同じ 28.5 ms なら、差は 10.3〜11.1 ms になります。判定（2,000 回、窓は前面）は、置き方が違うので、測ってみないと分かりません。
- 入力の区間の 0.4 ms（Mac とホストの、プロセスの受け渡し）は、自前のクライアントとホストでは、受け渡しの回数が減ります。

## 再現のしかた

1. ホストで、決めた設定の経路と、テストアプリ、`istesso agent` を動かす。
2. Mac で、`open -n -g "Istesso Input.app" --args input relay --to <端末> --socket <ソケット> --address <ホストの有線のアドレス> --keep-trying 20`。
3. 同じソケットへ、クリックを 1 回書く（`pointer_at`、`button`）。
4. `istesso-screen-probe --local 127.0.0.1:47811 --relayed-keys <ソケット> ...`。
5. `istesso measure compare ... --relayed-inputs keys` と、`scripts/m1-step3-breakdown.py ... --relayed-inputs keys` で集計する。
