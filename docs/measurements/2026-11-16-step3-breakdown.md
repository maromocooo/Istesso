## 測り方

[README.md](README.md) の「内訳の計測」のとおりです。12:09:06 から 12:12:55（JST）に、500 回、200〜400 ms の間隔で測りました（乱数の種は 20261116）。同じ時間に、Mac からホストへ `ping` を 0.2 秒おきに流しました（650 回）。

入力ごとに、その入力を最初に映したフレームを、ホストのコンポジターから Mac の画面まで追っています。500 回すべてを追えました。区間は、足すと「入力を送ってから画面に出るまで」になるように切ってあり、見積もりは入っていません。

ホストのテストアプリの時計と、ホストのパイプラインの時計は、同じ PC の同じ単調時計です。テストアプリのログにある原点の時刻（`clock_origin_unix_ns`）で、1本の時間軸に並べました。計測のあいだ、ホストの時刻と単調時計のずれは 0.004 ms しか動いていません。

- 最小は 2.5 ms で、3 ms から 15 ms のあいだに、ほぼ均等に散らばっています。幅は 11.8 ms で、フレームの間隔（11.76 ms）と同じです。

後ろの時間が何で決まるかを見るために、ホストだけで、解像度を変えて測りました（12:13 から 12:18、合成の入力をホスト自身から 300 回ずつ。映像は開いていないポートに送り、Mac は関わっていません。はじめの 10 回ほどは、窓が出る前に入力が届いたので除いています）。

## わかったこと

1. **コンポジターの待ちは、実測で平均 9.2 ms でした。見積もり（5.9 ms）より 3.3 ms 長い値です。** 「次に描くまでの待ち」は見積もりどおりで、0〜11.8 ms に均等に散らばり、平均 5.9 ms です。見積もりに入っていなかったのは、描き始めてからフレームを出すまでの約 3.3 ms です。
2. **どこにあるか分からなかった約 4 ms は、ほぼこの 3.3 ms でした。** 残りは、Mac で描いてから画面に出るまでが見積もりより 0.9 ms 長いことと、ネットワークの 0.8 ms です。ネットワークは、中央値では `ping` と 0.2 ms しか違いません。平均が見積もりより多いのは、ときどき遅れるパケットで平均が中央値より大きくなる分（`ping` でも平均は 3.6 ms）と、`ping` にない両側の起こされ待ちとみています。
3. **描き始めてから出すまでの時間は、画素数とともに増えます。** 1720×720 で約 3.3 ms、3440×1440 では約 10 ms です。出たあとの「GPU へ上げて圧縮する」も、1.8 ms から 4.7 ms に増えます。画面全体の解像度では、ホストの中だけで、待ちを除いて約 15 ms かかる計算です。フレームを GPU の外に出さなければ、この仕事はなくなります。
4. **GStreamer の窓は、手元の窓より画面に出るのが遅い。** 描いてから画面に出るまでが平均 18.8 ms で、手元の窓（フレームの確定から 17.3 ms）より 1.5 ms 長い値です。その手前の「表示の要素が描くまで」にも 1.6 ms かかっています。
5. **裾を作っているのは、表示の刻み、コンポジターの待ち、ネットワークの順です。** 遅い 25 回は、画面更新を 1 回逃した分（+5.7 ms）、コンポジターの待ちが長かった分（+3.9 ms）、ネットワーク（+3.1 ms）で遅くなっています。圧縮と復号は、裾にほとんど効いていません。

中継した窓と手元の窓の差（平均で 18.7 ms）を、区間に分けると次のとおりです。

| 区間 | 平均 | 自前の実装での見込み |
|---|---|---|
| コンポジターが次に描くまでの待ち | 5.9 ms | 画面が変わったときにすぐ描けば、なくなる |
| コンポジターが描き始めてから出すまで | 3.3 ms | フレームを GPU の外に出さなければ、大半がなくなる（見込み。測っていない） |
| ネットワーク | 4.0 ms | Mac を有線にすると縮む（測っていない） |
| GPU へ上げる、色の変換、圧縮、パケット | 1.9 ms | GPU へ上げ直す分（[最初の記録](2026-11-16-step3-first-path.md)で 0.9 ms）がなくなる |
| 復号 | 2.4 ms | ソフトウェアの復号。VideoToolbox を直接使う（Moonlight では 2.7 ms だった） |
| フレームが届くまで、待ち行列、表示の要素が描くまで | 1.9 ms | 自前の描画で縮む（見込み） |
| 描いてから画面に出るまでの、手元の窓との違い | 1.5 ms | 窓への出し方を選べる（見込み） |
| アプリの応答と、入力がアプリに届くまでの違い | −2.2 ms | 手元のテストアプリのほうが遅い（2.8 ms と 0.8 ms）。合格ラインの指標では引かれる |

合格ラインの指標の中央値は、いま 19.5〜21.4 ms で、ラインは 12 ms です。縮める必要があるのは 7.5〜9.4 ms です。待ちの 5.9 ms と、Mac を有線にして縮む分（3 ms 前後とみていますが、測っていません）を合わせて、ちょうどラインのあたりです。余裕を作るには、コンポジターが描き始めてから出すまでの 3.3 ms と、クライアントの描画まわりの 3 ms あまりにも手を入れる必要があります。どれも、作って測るまでは見込みです。

読むときの注意：

- **テストアプリの絵は、一面の灰色です。** 入力を映したフレームは平均 0.4 kB で、パケット 2 個で届きました。ふつうのアプリの画面では、フレームが大きくなり、圧縮、転送、復号にかかる時間が増えます。ここでの値は、その下限です。
- **計器の影響は、回ごとのばらつきと区別できていません。** 中継した窓の追加遅延の中央値は、計器ありで 38.5 ms、計器なしの 2 回で 37.3 ms と 37.8 ms です。ホストの「出てから送り出すまで」は 1.9 ms で、計器なしで測った値（2.1 ms）より長くなっていません。
- **手元の窓の値が、これまでの回より約 1 ms 小さくなっています**（中央値 17.1 ms。これまでは 17.9 ms と 18.3 ms）。この回から、手元の窓を前面に出さずに起動しています。起動のしかたの違いによるものかどうかは、確かめていません。合格ラインの指標の中央値がこの回だけ約 2 ms 大きいのは、半分がこの違いです。
- **1 回目は、終わりの 20 秒に AWDL が戻りました**（12:01:50 からの回。[記録](2026-11-16-wifi-sharing-off.md)）。そのあいだに送った 49 回を除いた 451 回の内訳は、この記録の値と 0.4 ms 以内で一致しています（コンポジター 8.9 ms、ネットワーク 3.9 ms、描いてから画面に出るまで 19.1 ms。どれも平均）。
- コンポジターの「描き始め」の時刻そのものは、外から見えません。「描き始めてから出すまで」は、確定から出るまでの時間のいちばん短いところと、平均から待ちの平均を引いた残りから出しています。

次に行うこと：

- 設定を 1 つずつ変えて比べる（m1-plan.md の手順 3）。はじめに、コンポジターの出力を GPU の上のまま（DMABuf）でエンコーダーに渡せるかを確かめる。画素を運ぶ仕事がなくなるかどうかが、いちばん大きい。
- Mac を有線にしたら、同じ内訳を取り直す。
