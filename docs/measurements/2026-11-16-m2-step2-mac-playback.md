# M2 手順 2：Mac で、音を出さずに再生の側を動かす

- 日付：2026-11-16
- コミット：a36c9fe（`istesso audio`）。途中の版で測って直したところは、下の「測りながら直したこと」に書いた
- 目的：出口の側（受信、待ち行列、ずれ補正、Core Audio への受け渡し）を、本物の機器の時計で動かす。経路で音が変わらないこと、途切れの数、待ち時間、遅延を見る。

**音は出していません。** 機器には無音を渡し、渡すはずだった音を調べています。機器の設定（サンプルレート、バッファーの大きさ、音量、既定の出力）は、前後で同じです（`istesso audio outputs` で確かめた）。ホストは使っていません。

## 条件

| 項目 | 値 |
|---|---|
| 機材 | MacBook Air（M4、macOS 26.5.1）。内蔵の出力、48 kHz、1 回に 512 フレーム（10.7 ms） |
| 機器が申告する遅れ | 60 フレーム＋安全のための余裕 48 フレーム（合わせて 2.25 ms） |
| 送る側 | 同じ Mac の中の `istesso audio serve --source tone`。997 Hz の正弦波、−12 dBFS、48 kHz、2 チャンネル、1 パケット 256 フレーム。**タイマーで刻む**（機器の時計ではない） |
| 受ける側 | `istesso audio play 127.0.0.1:…`。機器には無音を渡す |
| 経路 | 127.0.0.1 の TCP。`istesso-link` の通信路（Noise XX）。no-delay |
| 端末の鍵 | この試験のために作ったもの。作業用の場所に置き、互いにペアリングして、送る側で `istesso peers allow … audio` を実行した。人のペアリングには触っていない |
| 起動のしかた | 小さな `.app` にして `open -n -g` で起動（ふつうの優先度）。比べるために、1 回だけエージェントのシェルから起動した |

送る側と受ける側は、別の時計で動きます（システムの時計と、機器の時計）。ただし同じ Mac の中なので、差は小さいはずです。

## わかったこと

1. **経路では、音は変わらない。** どの回も、受け取ったパケットは、送ったものと 1 つ残らず同じだった（両側でパケットごとの指紋を取って比べる。`istesso audio compare`）。
2. **受ける側は、動く。** 待ち時間を 100 ms にした 90 秒では、途切れも飛ばしもなく、待ち時間は目標から 0.7 ms 以内、渡すはずだった音は −12.0 dBFS の正弦波のままで、谷もクリックもなかった。
3. **途切れたのは、送る側のタイマーのせいである。** テストの音は、タイマーで刻むスレッドが作る。それがときどき止まる（この回では最大 68 ms）。待ち時間が 40 ms のとき、遅れたパケットのために使えるのは約 12 ms なので（下の表）、それより長く止まるたびに途切れた。途切れのたびに、音はフェードで終わり、フェードで始まり、待ち時間は目標に戻った。クリックは 1 つもなかった。本物の取り込みは、サウンドシステムの時計で刻まれるので、こうは止まらないはずである。2 台での短いテストで確かめる。
4. **待ち時間の目標 40 ms の内訳。** この Mac の内蔵の出力では、次のとおりだった。

   | 使いみち | 長さ |
   |---|---|
   | 機器が、渡す時刻より先に引き取りに来る分 | 11.1 ms |
   | 機器が 1 回に引き取る分（512 フレーム） | 10.7 ms |
   | フェードのために手元に残す分（225 フレーム） | 4.7 ms |
   | リサンプラー | 1.4 ms |
   | 残り：パケットが遅れてよい分 | 約 12 ms |

5. **遅延。** 取り込みから機器に渡すまでは、待ち時間に、パケット 1 つぶん（5.3 ms）と、経路と送る側の処理（約 1.5 ms）を足した長さになる。待ち時間 40 ms で 46.9 ms だった。耳に届くまでには、機器が申告する遅れ（2.25 ms）がさらに足される。
6. **エージェントのシェルから起動した送る側は、使えない。** シェルから起動したプログラムは優先度が低く、タイマーが 20 ms ほどに延びる。パケットは 20 ms おきに 4 つずつ固まって届いた。遅延に関わるプログラムを `.app` にして `open` で起動する、という M1 の決まりは、音にも当てはまる。受ける側で遅延に関わるのは Core Audio のスレッドで、これは起動のしかたによらず、リアルタイムの優先度で動いていた。
7. **音程。** 待ち時間 100 ms の回で、音程は公称から −36〜+48 ppm の範囲で動いた（平均は −0.2 ppm）。送る側のタイマーが 0.5 ms ほど揺れ、補正がそれを追うためである。模擬での上限（50 ppm）の中にある。

## 測りながら直したこと

実機で動かして、はじめて見つかったものです。どれも、試験を足したうえで直しました。

| 見つけたこと | 直し方 |
|---|---|
| 機器が動き始めた直後の時刻印は、当てにならない。最初の時刻印と、そのあとの時刻印が、150 ms ほど食い違った（機器が動き出すまでの時間とみている）。最初の時刻印で再生を始めたため、すぐに 150 ms ぶんを飛ばすことになった | 引き取りが、同じ間隔で 3 回続くまで、再生を始めない |
| 待ち行列が少しずつ空になるとき、最後に残った数フレームだけでフェードしていた（録った音にクリックが 1 つあった） | フェードに要る分を、手元に残しておく。それを割り込みそうになったら、その時点でフェードして終える |
| 途切れのあとの再開を、遅れて届いたパケットに合わせていた。その分だけ待ち時間が長くなり、補正が何秒もかけて取り戻していた（音程が最大 680 ppm 動いた） | パケットがどれだけ遅れたかを、取り込みの時刻と届いた時刻から見て、遅れていないパケットの待ち時間が目標になるように始める |
| 受ける側の機器を開いているあいだに、接続の中にパケットがたまっていた | 受信を、機器より先に動かす。たまった分は、始めるときに 1 度だけ捨てる |
| 聞き手がいないあいだ、送る側のリングがいっぱいになり、捨てた数に数えられていた | 聞き手がいないあいだは、取り込んだ音をためない。数えるのは、送っている最中に捨てた分だけにする |

## まだ測っていないこと

- 2 台のあいだ。ホストの取り込み（PipeWire）は、ビルドに要るパッケージを待っている（[m2-plan.md](../m2-plan.md)）。
- 44.1 kHz の機器（USB のオーディオインターフェース）での再生。模擬では確かめた（[手順 1 の記録](2026-11-16-m2-step1-simulated-clocks.md)）。実機では、まだ開いていない。
- 耳で聞く確認。人に知らせてから、1 回だけ行う。

## 再現のしかた

```sh
# 送る側と受ける側の鍵を、作業用の場所に作る（ISTESSO_CONFIG_DIR で分ける）。
# 互いにペアリングし、送る側で音の権限を与える。
istesso audio serve --bind 127.0.0.1 --port 47822 --source tone --seconds 96 --ledger sent.txt
istesso audio play 127.0.0.1:47822 --peer <送る側の名前> --latency-ms 100 --seconds 90 \
    --record played.f32 --ledger received.txt --report report.json
istesso audio compare sent.txt received.txt
```

どちらも `.app` にして `open -n -g` で起動します。127.0.0.1 だけを使うので、ローカルネットワークの許可は要りません。
