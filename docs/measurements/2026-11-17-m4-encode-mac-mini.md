# Mac mini のエンコーダー：圧縮にかかる時間（ホストだけ）

- 日付：2026-11-17（Mac mini の時計で 09:37〜09:55）
- コミット：この記録と同じコミット（`crates/istesso-host-macos` と、その `examples/vt-bench.rs`）
- 目的：[M4 の計画](../m4-plan.md) の手順 2。Mac のエンコーダー（VideoToolbox）が、判定と同じ大きさの絵（3440×1440、毎秒 85 枚、H.265 の 4:4:4）を、1 フレームにつき何 ms で圧縮するかを知る。Linux のホストの値（`m1-latency` の系列のブランチにある記録 `2026-11-16-encode-split.md`）と比べる。
- 結論：
  - **Mac mini（Apple M4）のハードウェアのエンコーダーは、4:4:4 を持っている。** プロファイルの一覧に `HEVC_Main444_AutoLevel` があり、出てきたストリームの `general_profile_idc` は 4 だった。
  - **3440×1440、毎秒 85 枚で、1 フレームの圧縮は、中央値 8.8 ms。** Linux のホスト（RTX 4090）は、色の変換と合わせて 4.07 ms なので、**約 4.7 ms 長い。**
  - **エンコーダーの「リアルタイム」の指定（`RealTime`）を入れると、3 倍遅くなる**（中央値 28.7 ms）。入れないほうが速い。この指定は、外した。
  - 半分の大きさ（1720×720）なら、3.0 ms。
  - **画質は、測っていない。** ADR 0002 の 3 つの条件を満たすかどうかは、まだ分からない。

## 条件

| 項目 | 値 |
|---|---|
| ホスト | Mac mini（Apple M4、メモリー 16 GB）、macOS 26.7.1 |
| ホストの状態 | 人がログインしていて、**画面はロック中、ディスプレイはスリープ中**。ディスプレイは 1280×720 の 60 Hz（この計測は、ディスプレイを使わない） |
| プログラム | `vt-bench`。**Air でビルドして（Rust 1.93、release）、Mac mini の作業用のフォルダーへ写して、SSH から実行した。** Mac mini には、コンパイラーがまだない。優先度は 31（ふつうの値） |
| 絵 | プログラムが作る、動く文字（1 フレームに 3 行ぶん流れる）。3440×1440、毎秒 85 枚、BGRA。**`istesso-flash` の絵ではない**（そのクレートが、まだ `main` にないため）。同じ種類の絵を、ここで描いている |
| 経路 | 絵を、メモリーの上の画像（IOSurface つき）に描く → VideoToolbox の H.265 のエンコーダー（ハードウェアを必須にした）。窓の取り込みは、通っていない |
| エンコーダーの設定 | プロファイル `HEVC_Main444_AutoLevel`、並べ替えなし、キーフレームは最初だけ、平均のビットレートと上限を 30 Mbps、毎秒 85 枚と伝える、速さを優先（`PrioritizeEncodingSpeedOverQuality`）、sRGB と伝える。`RealTime` は、入れない |
| 送り先 | なし。圧縮したフレームは、数えて捨てる |
| 測ったもの | 45 秒ぶん。始めの 5 分の 1 を除いた 3,060 フレームの全部。時刻は、絵を描き終えてエンコーダーに渡した時と、エンコーダーがフレームを出した時 |
| ほかに動いていたもの | 人のログインのセッション。09:36 ごろまで、Mac mini では、開発用のツールのインストールが動いていた。計測は、それが終わってから始めた。始めたときの負荷の平均（1 分）は 1.4〜3.5 |

## 結果

### 決めた設定（BGRA をそのままエンコーダーに渡す）

同じ設定で、45 秒を 4 回。

| 区間 | 平均 | 中央値 | 95% | 99% | 最大 |
|---|---|---|---|---|---|
| 絵を渡してから、圧縮が済むまで（1 回目） | 8.86 ms | 8.76 ms | 9.00 ms | 9.16 ms | 37.36 ms |
| 同じ（2 回目） | 8.85 ms | 8.83 ms | 9.03 ms | 9.16 ms | 9.40 ms |
| 同じ（3 回目） | 8.80 ms | 8.77 ms | 8.98 ms | 9.10 ms | 9.73 ms |
| 同じ（4 回目） | 8.82 ms | 8.79 ms | 9.01 ms | 9.14 ms | 9.40 ms |

- 圧縮したフレームは、平均 9.0 kB（毎秒 85 枚で、約 6 Mbps。上限の 30 Mbps には届いていない）。
- 落としたフレーム、失敗したフレームは、なし。エンコーダーは、ハードウェアで動いている、と答えた。
- 1 回目の最大（37 ms）は、1 フレームだけ。原因は調べていない。

### 色の変換を、別の段に分けた場合

Linux の記録と同じ分け方にするために、BGRA から 4:4:4 への変換を、先に別に行った（VideoToolbox の、絵を変換する機能）。

| 区間 | 平均 | 中央値 | 95% | 99% | 最大 |
|---|---|---|---|---|---|
| 絵を渡してから、色の変換が済むまで | 2.06 ms | 2.06 ms | 2.12 ms | 2.17 ms | 6.82 ms |
| 色の変換が済んでから、圧縮が済むまで | 8.69 ms | 8.69 ms | 8.85 ms | 8.97 ms | 9.55 ms |
| 合わせて | 10.75 ms | 10.75 ms | 10.95 ms | 11.09 ms | 16.16 ms |

- 変換を別にすると、2 ms 増える。BGRA をそのまま渡したほうが速い（8.8 ms）。エンコーダーの中の変換は、ほとんど時間を取っていない、と読める。
- **圧縮そのものは、約 8.7 ms。**

### Linux のホストとの比較

| | 色の変換 | 圧縮 | 合わせて（中央値） |
|---|---|---|---|
| Linux のホスト（RTX 4090。2026-11-16 の記録） | 0.16 ms | 3.91 ms | 4.07 ms |
| Mac mini（Apple M4。決めた設定） | エンコーダーの中 | — | 8.8 ms |

絵と、測り始めの位置が、同じではない（下の「読むときの注意」）。それでも、差（約 4.7 ms）は、測り方の違いより大きい。

| 半分の大きさ（1720×720） | 3.00 ms | 3.45 ms | |
| 4:2:0 | 8.70 ms | 9.01 ms | 4:4:4 と変わらない。フレームは 30.9 kB と大きくなった（理由は調べていない） |

### 短い試し（6〜20 秒ずつ。参考）

設定を 1 つずつ変えた。回数が少ないので、目安として読む。

| 変えたもの | 中央値 | メモ |
|---|---|---|
| 毎秒 30、60、120 枚（`RealTime` なし） | 9.0、8.9、8.8 ms | 枚数では、ほとんど変わらない |
| 毎秒 10 枚（`RealTime` なし） | 13.1 ms | 遅くなる。間が空くと、エンコーダーが休むのかもしれない。確かめていない |
| `RealTime` を入れて、毎秒 10、30、60、85、120 枚 | 18.1、18.3、17.8、27.5、21.2 ms | どの枚数でも遅い |
| 速さの優先を外す | 13.7 ms | 遅くなる。フレームは小さくなる（5.4 kB） |
| 低遅延のレート制御（`EnableLowLatencyRateControl`） | 70.5 ms | 大きく遅くなる。BGRA をそのまま渡すと、プロファイルが Main（4:2:0）に変わった。使わない |
| `MaximizePowerEfficiency`、`Quality`、`SpatialAdaptiveQPLevel`、`MaximumRealTimeFrameRate`、`NumberOfSlices`、`EnableMCTF`、`SAOMode`、`PerceptualQualityOptimization`、`EnableMultiReferenceP`、`Priority`、`LowMemory` | 変わらない | `RealTime` を入れた状態で試した。27 ms 台のまま。このうち、公開のヘッダーにない名前（エンコーダーが自分の一覧に出しているもの）は、試しただけで、製品には入れない |

| `LookAheadFrames` を 0 | — | エンコーダーの準備が失敗した |

## 判定への見込み（見積もり。測った値ではない）

- M1 の仮の判定は、Linux のホストで、手元の窓との差の中央値が 11.14 ms だった（合格ラインは 12 ms）。
- ほかの区間が同じだとすると、Mac のホストは、圧縮だけで約 4.7 ms 長い。**3440×1440、毎秒 85 枚では、合格ラインを超える見込みである。**
- 窓の取り込みにかかる時間は、まだ測っていない（許可が要る）。Linux のコンポジターの区間（1.3 ms）より長ければ、さらに増える。
- 半分の大きさなら、圧縮は 3.0 ms で、Linux の同じ大きさの値が分かれば比べられる（まだ並べていない）。

## 読むときの注意

- **絵が違う。** Linux の記録は、テストアプリの絵。ここは、同じ種類の絵を、別に描いたもの。
- **測り始めが違う。** Linux の記録は、コンポジターが絵を出した時から。ここは、絵を描き終えて渡した時から。
- **エンコーダーだけの値である。** 窓の取り込み、送り出し、ネットワーク、復号は、入っていない。
- **1 台、1 回の計測である。** Mac mini の 1 台で、同じ朝に測った。ほかの Mac（Mac Studio など）では、違う値になる。
- **画質を測っていない。** 速さを優先する設定が、画質をどれだけ下げるかは、分かっていない。ADR 0002 の条件（明るさと色の SSIM、色の差）は、同じエンコーダーで別に測る必要がある。

カメラでの計測：行っていません（画面に出る前の区間だけを測っているため）。

## 再現のしかた

```sh
# Air で（計測の合図が free のときだけ）
cargo build -p istesso-host-macos --release --example vt-bench
# できた target/release/examples/vt-bench を、Mac mini の作業用のフォルダーへ写して、そこで
./vt-bench --seconds 45                        # 決めた設定
./vt-bench --seconds 45 --convert-first        # 色の変換を別の段に
./vt-bench --seconds 45 --set RealTime=true    # 「リアルタイム」を入れる
./vt-bench --seconds 45 --width 1720 --height 720
./vt-bench --seconds 45 --chroma 420
./vt-bench --seconds 2 --list-properties       # エンコーダーが受け付ける設定の名前
```

1 回に 1 つだけ動かします。2 つ重ねると、値が崩れます（重ねてしまった回が 2 つあり、捨てました）。
