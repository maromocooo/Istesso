# コンポジターの修正の作り直し：フレームコールバックで描くアプリと、85 Hz・有線での値

- 日付：2026-11-16
- コミット：この記録と同じコミット（作り直した修正ファイル、テストアプリの `--when-told`、ホストのスクリプトの `--render-on-commit`）
- 目的：コンポジターの修正（アプリが確定したら描く。描き始めは毎秒 85 回まで）を、元のプロジェクトに提案できる形に作り直す（[ADR 0009](../adr/0009-host-compositor.md)）。既定では元の動きのまま、設定で切り替える。テストを付ける。作り直しても遅くなっていないことを、測って確かめる。
- 結論：
  - **これまでの修正（v2）は、フレームコールバックで描くアプリでは壊れていた。** フレームが 2〜3 ms おきに固まって出たあと、最長 0.6 秒止まる。本物のアプリの多くは、この描き方をする。テストアプリは自分で間隔を刻むので、これまでの計測には出ていなかった。
  - **作り直した修正（v3）では、どちらの描き方のアプリでも、フレームが等間隔に出る。** コールバックで描くアプリの絵は、確定してから中央値 1.9 ms で出ていく（元の動きでは 11.6 ms）。
  - **85 Hz・2 台とも有線・3440×1440 で、差は中央値 9.75 ms、95 パーセンタイル 10.74 ms**（500 回。v2 は 10.43 ms と 10.99 ms）。判定の値ではない（500 回、窓は前面に出していない）。

## 2 種類のアプリ

| 描き方 | 例 | テストアプリでの指定 |
|---|---|---|
| **自分で間隔を刻む。** タイマーで描き、描いたらすぐ渡す | これまでのテストアプリ。自前の描画ループを持つアプリ | `--fps 85`（これまでどおり） |
| **言われたら描く。** コンポジターが「次のフレームを描いてよい」と知らせる（`wl_surface.frame`）のを待ってから渡す | ほとんどのアプリ。垂直同期つきの OpenGL のアプリ、ブラウザ | `--fps 500 --when-told`（`--draw gpu` と一緒に） |

v2 は、フレームを描くたびに「描いてよい」と知らせていました。言われたら描くアプリは、知らされるとすぐ描いて確定し、v2 はそれをすぐ描いて、また知らせます。この繰り返しがアプリの描く速さで回るので、1 秒ぶんの 85 枚が 0.2〜0.3 秒で出てしまい、残りの時間は「毎秒 85 回まで」の決まりで止まります。

## v3 の決まり

1. 絵が変わったら（アプリが確定した、ポインターが動いた）、フレームをすぐ描く。何も変わらなければ、フレーム 2 枚ぶんの時間で、そのまま出す。
2. どの 1 秒にも、フレームレートより多くは描き始めない。この決まりで 1 ms を超えて待つことになるフレームは、次の絵に順番を譲る（待たせた絵と次の絵が続けて出ると、1 秒後にまた同じことが起きるため）。
3. **アプリへの「描いてよい」の知らせは、フレームとは別の拍で出す。** アプリが確定したときに知らせるが、フレームの間隔に 1 回まで。言われたら描くアプリは、間隔ごとに 1 回確定することになり、その絵は、届いたときに出ていく。
4. 既定では入らない。要素のプロパティ `render-on-commit` で入れる。切ってあれば、元の動きのまま。

テスト：決まりそのものの単体テストが 12 本（言われたら描くアプリと、自分で刻むアプリを模して動かす）、本物の Wayland クライアントをつないだテストが 4 本。元のプロジェクトのテスト 19 本と合わせて、35 本が通っています。

途中で試して、採らなかった形：フレームどうしの間隔を決まりで保つ形（間隔の半分までの早出しを許す）。言われたら描くアプリは等間隔になりましたが、自分で刻むテストアプリで、確定からフレームが出るまでが中央値 2.2 ms から 4.5 ms に、95 パーセンタイルが 3.3 ms から 13.1 ms に延びました。一度遅れた拍が、戻らなくなるためです。

### 条件

| 項目 | 値 |
|---|---|
| ホスト | Ubuntu 24.04、RTX 4090（ドライバー 590.48.01）、GStreamer 1.24.2 |
| 絵 | テストアプリの動く絵（文字のスクロール）、1280×720、毎秒 85 枚。テストアプリは GPU で描画 |
| フレームの渡し方 | メインメモリー経由（フレームの中央の色を読んで、入力を映したフレームを見つけるため） |
| コンポジター | 元のコミット（1301f86）に、v2 の修正を当てたもの、v3 の修正を当てたもの。「元の動き」は、v3 でプロパティを切った状態 |
| 入力 | ホストの中から 150 回ずつ（`istesso measure inputs`） |
| 同時に動いていたもの | 本物のアプリの試用の経路（別のコンポジターとエンコーダー）が、同じ GPU で動いていた |

### 結果（21:06〜21:11）

フレームの間隔は、コンポジターの要素を出るところで見た値です（85 枚ぶんの間隔は 11.76 ms）。

| コンポジター | アプリ | 毎秒 | 間隔（5% / 中央値 / 95% / 最大） | 間隔の半分より近い / 1.5 倍より遠い / 5 倍より遠い |
|---|---|---|---|---|
| 元の動き | 自分で刻む | 85.0 | 11.01 / 11.77 / 12.51 / 16.51 ms | 0 / 0 / 0 |
| v2 | 自分で刻む | 85.0 | 10.41 / 11.76 / 13.21 / 21.58 ms | 47 / 47 / 0 |
| **v3** | 自分で刻む | 84.9 | 10.88 / 11.76 / 12.65 / 23.74 ms | 0 / 5 / 0 |
| 元の動き | 言われたら描く | 85.0 | 11.01 / 11.76 / 12.52 / 15.89 ms | 0 / 0 / 0 |
| v2 | 言われたら描く | 85.1 | **1.62 / 2.64 / 23.50 / 639.83 ms** | **3497 / 420 / 47** |
| **v3** | 言われたら描く | 84.8 | 10.87 / 11.79 / 12.74 / 17.18 ms | 0 / 0 / 0 |

（フレームは、どの回も約 3,940 枚）

| コンポジター | アプリ | アプリ：入力から確定まで（中央値） | コンポジター：確定からフレームが出るまで（中央値 / 95%） |
|---|---|---|---|
| 元の動き | 自分で刻む | 6.6 ms | 8.55 / 9.83 ms |
| v2 | 自分で刻む | 5.8 ms | 2.23 / 5.12 ms |
| **v3** | 自分で刻む | 6.4 ms | **2.18 / 3.26 ms** |
| 元の動き | 言われたら描く | 28.6 ms | 11.64 / 12.42 ms |
| v2 | 言われたら描く | 31.6 ms（平均 62 ms、95% 362 ms） | 測れない（150 回のうち 74 回で、入力を映したフレームが見つからない） |
| **v3** | 言われたら描く | 29.9 ms | **1.87 / 2.98 ms** |

- **v2 と、言われたら描くアプリ**：フレームの間隔の中央値が 2.64 ms、最大が 640 ms。3,991 の間隔のうち 3,497 が間隔の半分より近く、47 がフレーム 5 枚ぶんより遠い。絵が早送りのあと止まる、という動きです。
- **v3 と、言われたら描くアプリ**：間隔は 10.9〜12.7 ms（5%〜95%）にそろい、絵は確定の 1.9 ms あとに出ます。元の動きでは、確定してから次の拍まで 11.6 ms 待っていました。
- **v3 と、自分で刻むアプリ**：中央値は v2 と同じ（2.2 ms）、95 パーセンタイルは 5.1 ms から 3.3 ms。近すぎる間隔がなくなり、遠い間隔が 5 回あります（決まりの 2 で、順番を譲ったフレーム）。
- 言われたら描くアプリは、アプリの側で入力から確定までに約 29 ms（フレーム 2.5 枚ぶん）かかっています。描いてから、知らされるのを待って渡すためで、どのコンポジターでも同じです。追加遅延の計算では引かれる区間ですが、本物のアプリの体感には入ります。
- コンポジター自身が数えた「描き始め」は、v3 の 2 回とも、どの 1 秒にも 85 回まででした（ログに 1 行出る）。要素を出るところで数えると、どの回も 86 枚の 1 秒があります。描くのにかかる時間が、毎回同じではないためです。
- どの回にも、確定からフレームが出るまでが 350〜390 ms の入力が 1 回ずつありました（元の動きの回にもある）。平均には使っていません。原因は調べていません。

## Mac まで通した値（85 Hz、2 台とも有線）

### 条件

| 項目 | 値 |
|---|---|
| ホスト | 上と同じ。有線（2.5 Gbps） |
| クライアント | MacBook Air（M4）、macOS 26.5.1。VideoToolbox で復号 |
| 接続 | 2 台とも有線（[有線の記録](2026-11-16-step3-cable.md) と同じ形。往復の中央値 0.4〜0.5 ms、95% 0.8〜1.0 ms） |
| 解像度とフレームレート | 3440×1440、毎秒 85 枚まで。動く文字の絵。フレームは GPU の中（CUDA） |
| クライアントのディスプレイ | 外部（3440×1440、拡大なし）、**85.00 Hz** |
| コーデックとビットレート | H.265（Main 4:4:4、8 ビット）。上限 30 Mbps、実際は 5.1〜5.2 Mbps |
| エンコーダーの設定 | 決めた設定（[ADR 0002](../adr/0002-latency-first.md)）。キーフレームは求められたときだけ。レート制御のバッファーは 1 フレームぶん |
| 経路 | RTP を UDP で。暗号化なし。キーフレームの求めは、受信側が自分で送る |
| 窓 | 中継した窓は 860×360 に縮めて表示、手元の窓は 600×400。どちらも前面に出さずに起動し、ほかの窓より上に固定 |

### 結果（500 回ずつ。v3 は 21:11〜21:16、v2 は 21:16〜21:20）

| 指標 | v3（中央値 / 95% / 99%） | v2（中央値 / 95% / 99%） |
|---|---|---|
| **追加遅延の、手元の窓との差（合格ラインの指標）** | **9.75 / 10.74 / 11.34 ms** | 10.43 / 10.99 / 11.31 ms |
| 合格ライン | 12 / 24 / 47 ms | |
| 追加遅延（中継した窓） | 27.91 / 34.07 / 41.05 ms | 27.96 / 34.11 / 35.92 ms |
| 追加遅延（手元の窓） | 18.16 / 23.33 / 29.71 ms | 17.53 / 23.12 / 24.61 ms |

500 回なので、99 パーセンタイルは判断に使いません。手元の窓の中央値は、いつもの値（17.3 ms）から 0.86 ms と 0.23 ms 上でした（やり直しの目安の 2 ms 以内）。**2 本の差（0.68 ms）は、ほぼ手元の窓の値の違いです。** 中継した窓の値は、中央値も 95 パーセンタイルも 0.05 ms 以内で同じでした。

内訳（平均）：

| 区間 | v3 | v2 |
|---|---|---|
| ネットワーク（行きと帰り） | 0.97 ms | 1.12 ms |
| **コンポジター（確定からフレームが出るまで）** | **1.32 ms**（中央値 1.14、95% 1.51、99% 12.77） | 1.68 ms（中央値 1.38、95% 4.20、99% 6.70） |
| 色の変換と圧縮 | 4.04 ms | 4.05 ms |
| パケットにして渡す | 0.16 ms | 0.17 ms |
| フレームが届く | 0.22 ms | 0.20 ms |
| 復号 | 3.01 ms | 3.11 ms |
| 復号してから、描くまで | 0.35 ms | 0.38 ms |
| 合計（中継のために足される区間） | 10.07 ms | 10.71 ms |
| 描いてから、画面に出るまで | 17.89 ms | 17.46 ms |

- **コンポジターの区間は、平均 1.68 ms から 1.32 ms、95 パーセンタイル 4.20 ms から 1.51 ms になりました。** v2 では、一度遅れたフレームの遅れが、1 秒ごとに繰り返し出ていました。v3 では、そういうフレームが順番を譲るので、繰り返しません。代わりに、100 回に 1〜2 回、フレーム 1 枚ぶん待つ入力があります（99 パーセンタイル 12.77 ms）。
- 入力を映したフレームは、平均 7.4〜7.5 kB、8 パケット。途中でキーフレームを求めた回数は 0、パケットの欠けは 0 回。
- コンポジターを出たフレームは、v3 で毎秒 84.9 枚、v2 で 85.0 枚。
- 更新 1 回ぶん以内に収まった入力は、どちらも 93.8%。

画質（同じ設定を、ホストの同じエンコーダーに通した値）：4.8 Mbps、明るさの SSIM 0.9996 / 0.9996 / 0.9996、色の SSIM 0.9991 / 0.9990 / 0.9990、PSNR 47.7 dB。

カメラでの計測：行っていません。

## わかったこと

- **判定は、v3 で測ります。** テストアプリでは v2 より遅くならず、本物のアプリで壊れないのは v3 だけです。
- **85 Hz・有線で、差の中央値は 10 ms 前後です。** 合格ライン（12 ms）まで 2 ms ほどあります。Wi-Fi のときは 15.5 ms でした。
- **判定のテストアプリは、自分で間隔を刻む作りです。** 言われたら描くアプリでは、アプリの側の待ち（約 29 ms）が加わります。これは手元の Mac で動かしても同じ種類の待ちがあるので、追加遅延には数えていませんが、「言われたら描く」形でも測れるようになったので、判定のあとに参考として測ります。
- 「描いてよい」の知らせを、次のフレームの直前まで遅らせると、言われたら描くアプリの絵が新しくなります（アプリが、遅く描き始める）。関門のあとの課題にします。

## 再現のしかた

- 修正の当て方とビルド：`scripts/patches/gst-wayland-display-render-on-commit.patch` の先頭。テストは `cargo test -p wayland-display-core`。
- ホストだけの比較：`scripts/m1-step3-host.py --frames memory --size 1280x720 --no-input --no-key-requests`（`--render-on-commit` か `--no-render-on-commit`）でコンポジターを動かし、その中でテストアプリを起動する（`--fps 85`、または `--fps 500 --when-told`）。`istesso measure inputs` で入力を送り、テストアプリの記録と、フレームの記録の `frame_out`（中央の明るさつき）を突き合わせる。
- Mac まで通した値：[有線の記録](2026-11-16-step3-cable.md) の「再現のしかた」。
