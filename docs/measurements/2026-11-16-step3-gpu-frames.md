# 手順 3：フレームを GPU の外に出さずにエンコーダーへ渡す（設定の比較 2）

- 日付：2026-11-16
- コミット：この記録と同じコミット（`scripts/m1-step3-host.py --frames cuda` を足したコミット）
- 目的：[内訳の記録](2026-11-16-step3-breakdown.md)で、コンポジターが描き始めてからフレームを出すまでの時間（1720×720 で約 3.3 ms、3440×1440 で約 10 ms）と、エンコーダーの手前で GPU に上げ直す時間は、画素数とともに増えることが分かった。判定は 3440×1440 で行うので、フレームをメインメモリーに出さず、GPU の上のまま渡して、この時間をなくせるかを見る。
- 結論：**CUDA のメモリーで渡す形で動きます。** ホストの中の時間は、1720×720 で 1.9 ms、3440×1440 で 4.6 ms 縮みました。DMABuf と OpenGL で渡す形は、絵が更新されないままです。

## 条件

| 項目 | 値 |
|---|---|
| ホスト | Ubuntu 24.04、RTX 4090（ドライバー 590.48.01）、GStreamer 1.24.2、gst-wayland-display（`1301f86`） |
| クライアント | MacBook Air（M4）、macOS 26.5.1。通しの計測にだけ使った |
| 接続 | ホストは有線。Mac は Wi-Fi（5 GHz 帯のチャンネル 44。[記録](2026-11-16-wifi-channel-44.md)） |
| 解像度とフレームレート | 1720×720 と 3440×1440、85 fps |
| クライアントのディスプレイ | 外部（3440×1440、84.96 Hz） |
| コーデックとビットレート、エンコーダーの設定、経路 | [最初の 1 本の記録](2026-11-16-step3-first-path.md)と同じ |

変えたのは、コンポジターからエンコーダーまでの区間です（`scripts/m1-step3-host.py --frames memory|cuda|dmabuf`）。

```text
memory： waylanddisplaysrc ! video/x-raw（RGBx、メインメモリー） ! cudaupload ! cudaconvert ! NV12（CUDA） ! nvcudah265enc
cuda：   waylanddisplaysrc ! video/x-raw(memory:CUDAMemory)（BGRA） ! cudaconvert ! NV12（CUDA） ! nvcudah265enc
dmabuf： waylanddisplaysrc ! video/x-raw(memory:DMABuf) ! glupload ! glcolorconvert ! RGBA（OpenGL） ! cudaupload ! cudaconvert ! NV12（CUDA） ! nvcudah265enc
```

`cuda` の形は、コンポジターのプラグインを `cuda` のフィーチャーを有効にしてビルドすると使えます。固定しているコミット（`1301f86`）にある機能で、これまでのビルドでは無効でした。

```sh
CARGO_TARGET_DIR=target-cuda cargo build --release -p gst-plugin-wayland-display -p wayland-display-core --features cuda
```

ビルドには `gstreamer-cuda-1.0`（`libgstreamer-plugins-bad1.0-dev` に入っている）が、実行には NVIDIA のドライバーの `libcuda.so.1` が要ります。どちらも、このホストには入っていました。

## 結果

### ホストだけ（灰色の絵）

13:59 から 14:06 に、合成の入力をホスト自身から 300 回ずつ送って測りました。映像は開いていないポートに送り、Mac は関わっていません。フレームの色を GPU の上では読めないので、色が変わったフレームは、圧縮したフレームの大きさで見分けています（灰色の絵では、色が変わったフレームだけが数倍の大きさになる）。キーフレームに重なった数回は除いています。

| フレームの渡し方 | 解像度 | 確定から出るまで（最小 / 中央値 / 平均 / 95%） | 出てから圧縮が終わるまで（中央値） | 入力が届いてから、ネットワークへ渡すまで（中央値 / 平均 / 95%） |
|---|---|---|---|---|
| メインメモリー経由 | 1720×720 | 2.3 / 9.0 / 9.1 / 14.6 ms | 1.8 ms | 11.9 / 12.0 / 17.5 ms |
| **CUDA** | 1720×720 | 1.5 / 8.1 / 7.9 / 13.0 ms | 1.0 ms | **10.0 / 10.1 / 15.3 ms** |
| メインメモリー経由 | 3440×1440 | 9.5 / 16.7 / 16.1 / 21.3 ms | 4.8 ms | 22.9 / 22.3 / 27.2 ms |
| **CUDA** | 3440×1440 | 4.1 / 11.9 / 12.0 / 20.3 ms | 2.6 ms | **17.5 / 17.7 / 26.1 ms** |

「確定から出るまで」には、次に描くまでの待ち（平均 5.9 ms）が入っています。それを引くと、描き始めてから出すまでは、1720×720 で 3.2 ms から 2.0 ms、3440×1440 で 10.2 ms から 6.1 ms になりました。

3440×1440 の CUDA の回では、フレームの間隔の 1.5 倍より遅れたフレームが 8,234 のうち 35 ありました（メインメモリー経由では 3）。テストアプリの応答も、中央値で 1.3 ms から 2.6 ms に伸びています。原因は調べていません。

### DMABuf と OpenGL で渡す形

12:44 から 12:53 に試しました。パイプラインはエラーなく動き、OpenGL はデスクトップのセッションなしで NVIDIA の GPU の上で動きますが（`GST_GL_PLATFORM=egl`、`GST_GL_WINDOW=surfaceless`）、**映像が最初の絵のまま変わりません。** ホストだけで合成の入力を 300 回送っても、圧縮したフレームの大きさは 1 度も変わらず、Mac まで通しても、中継した窓は 30 回の入力に 1 度も反応しませんでした。どこで絵が止まっているかは、調べていません。CUDA の形が動いたので、この形は追っていません。

### Mac まで通した値（灰色の絵、1720×720）

[README.md](README.md) の「内訳の計測」のとおりです。Mac は 5 GHz 帯のチャンネル 44 で、共有の機能は元の設定のままです（[記録](2026-11-16-wifi-channel-44.md)）。2 つの窓は、前面に出さずに起動しました。復号はソフトウェアです。

| フレームの渡し方 | 時刻（JST） | 回数 | 追加遅延の、手元の窓との差（中央値 / 95% / 99%） | 中継した窓の追加遅延（中央値 / 95% / 99%） | 手元の窓（中央値） |
|---|---|---|---|---|---|
| メインメモリー経由 | 14:17〜14:49 | 4,540 | 21.1 / 25.4 / 28.5 ms | 38.8 / 48.6 / 54.9 ms | 17.7 ms |
| **CUDA** | 14:51〜14:54 | 500 | **19.4 / 23.6 ms**（99% は 26.2 ms。500 回なので判断に使わない） | 37.3 / 46.9 / 52.4 ms | 18.0 ms |

内訳（平均）：

| 区間 | メインメモリー経由 | CUDA | 差 |
|---|---|---|---|
| ネットワーク（行きと帰り） | 4.7 ms | 4.9 ms | +0.2 ms |
| アプリ | 0.8 ms | 0.9 ms | +0.1 ms |
| **コンポジター（確定から、フレームが出るまで）** | 9.0 ms | 8.1 ms | **−0.9 ms** |
| **GPU へ上げる、色の変換、圧縮** | 1.8 ms | 1.0 ms | **−0.8 ms** |
| パケットにして渡す、フレームが届く | 0.2 ms | 0.2 ms | 0.0 ms |
| 復号、待ち行列、描くまで | 4.3 ms | 4.3 ms | −0.1 ms |
| 描いてから、画面に出るまで | 18.8 ms | 18.6 ms | −0.2 ms |
| 合計 | 39.7 ms | 38.1 ms | −1.6 ms |

CUDA の形では、ホストでフレームの色を読めません。入力ごとに、Mac で最初に新しい色を映したフレームから逆にたどって集計しています（500 回すべてたどれた）。

カメラでの計測：行っていません。

## わかったこと

1. **フレームを GPU の外に出さない形は、既製の部品だけで組めます。** コンポジターのプラグインを `cuda` つきでビルドし直すだけでした。デスクトップのセッションも要りません。
2. **縮むのは、画素をメインメモリーへ運んで戻す時間です。** 1720×720 で、コンポジターが 0.9 ms、圧縮までが 0.8 ms 縮み、Mac まで通した中央値の差は 21.1 ms から 19.4 ms になりました。
3. **画素数が増えるほど効きます。** ホストだけの計測で、3440×1440 では 4.6 ms 縮みました。判定の解像度では、この形でないと、ホストの中だけでフレームの間隔（11.8 ms）を超えます。
4. **3440×1440 では、まだ約 6 ms が「描き始めてから出すまで」に残っています。** テストアプリは CPU で描いて、共有メモリーでコンポジターに渡します。コンポジターは、その 20 MB を毎回 GPU に上げています。GPU で描くふつうのアプリには、この時間はかからないはずですが、確かめていません。
5. 以後の計測は、CUDA の形を基本にします。
