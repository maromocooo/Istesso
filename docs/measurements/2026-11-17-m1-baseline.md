# M1：新しい測り方での基準の回と、いちばん新しい形の回（2,000 回ずつ）

- 日付：2026-11-17（11:52〜12:24）
- 種類：**基準の回**（足並みを毎回ずらす測り方での、最初の 2,000 回）と、続けて測った**いちばん新しい形の回**。どちらも、確定の判定ではありません（当てるテスト、自前のクライアントが、まだです）
- 結果：どちらの回も、3 つの値が合格ラインの内側。新しい形は、基準の回より悪くなっていない（中央値どうしの差で 0.29 ms 小さい）
- この回で決まったこと：「2 回以上遅れ」の上限を、**15.4%** に 1 回だけ決め直した（[ADR 0002](../adr/0002-latency-first.md)）

## 2 つの回の違い

| | 基準の回 | いちばん新しい形の回 |
|---|---|---|
| 映像の経路 | RTP を UDP で。暗号化なし（計測用） | 暗号化と認証つきの通信路（制御チャンネルと同じ作り。ADR 0015） |
| カーソル | ホストが絵の中に描く | クライアントが描く |
| コンポジター | `render-on-commit` の差分だけ | 差分 4 つ（`render-on-commit`、カーソル、窓の知らせ、別に出る窓の直し） |
| ビューアー | 本線のビルド | 新しい形のブランチ（`m1-dialog-windows`）のビルド |
| テストアプリ、入力の経路、エンコーダーの設定、窓の置き方、プローブ | 同じ | 同じ |

## 条件（2 つの回に共通）

| 項目 | 値 |
|---|---|
| ホスト | Ubuntu 24.04、RTX 4090、GStreamer 1.24.2。有線（2.5 Gbps） |
| クライアント | MacBook Air（M4）、VideoToolbox で復号。電源につないだ状態 |
| 接続 | 2 台とも有線（Mac は 1000BASE-T）。往復は、基準の回のあいだ、中央値 0.61 ms、95% 0.92 ms。Wi-Fi は入っていたが、経路には使っていない。終わりにも、有線のままだった |
| 絵 | 3440×1440、描き始めは毎秒 85 回まで。テストアプリの動く絵（文字のスクロール）。H.265（4:4:4、8 ビット）、上限 30 Mbps、実際は 4.8 Mbps。キーフレームは求められたときだけ |
| クライアントのディスプレイ | 外部（3440×1440、拡大なし）、85.00 Hz |
| 入力の経路 | 人が打ったキーと同じ経路（プローブ → 入力の中継 → 制御チャンネル → ホストのエージェント → コンポジター → テストアプリ） |
| **測り方** | **2 つのテストアプリが、入力に答えたフレームのたびに、次のフレームを無作為にずらす**（`--shift-beat`。種は、基準の回が 20261117 と 20262117、新しい形の回が 20261118 と 20262118）。プローブの種は、どちらも 20261116 |
| 優先度 | ビューアーも入力の中継も、アプリとして起動（46） |
| ホストの音のスレッド | ふつうの優先度（午前の比較のあとで、元に戻してある） |

### 同時に動いていたもの

- 始める前に、2 台の上でビルド、試験、音のプログラムが動いていないことを、スクリプトが確かめた。ほかの作業は、計測の合図（[AGENTS.md](../../AGENTS.md)）で止まっていた。計測のあいだ、Mac には誰も触れていない。
- 始める直前（11:52）の負荷：Mac は、CPU の空きが 84%（画面の描画が 1 コアの 46%、ほかは 13% 以下）。ホストは、空きが 99%（デスクトップの描画が 15%、ほかは 9% 以下）。
- 別のプロジェクトのデスクトップアプリが、ホストで動いていた（19 のプロセスで、1 コアの 15%）。Mac の側は、終了してあった。
- **ホストのブラウザーは、この回の前に閉じてある。** 仮の判定（2026-11-16）と、音の夜の回のときは、ホストのデスクトップでブラウザーが動画を復号し続けていた（1 コアの 1.3 倍ほど）。その点で、この回は、仮の判定より静かな状態である。
- 終わった直後（12:24）に、Mac でシステムのプロセス `duetexpertd`（macOS が、使い方からアプリの提案などを作る係）が、1 コアの 80% を使っていた。いつ動き始めたかは、分かっていない。次の回からは、回の途中の負荷も、10 秒ごとに記録する。
- AWDL（Mac どうしの無線の仕組み）は、計測のあいだ、動いていた（記録に 261 行）。除かずに、そのまま測った。

## 結果

入力は、どちらの回も、2,000 回すべてが両方の窓に出ました。予行（20 回ずつ）も、すべて出ました。

| 指標 | 基準の回 | 新しい形の回 | 合格ライン |
|---|---|---|---|
| **差の中央値** | **10.49 ms** | **10.20 ms** | 12 ms |
| **差の 95%** | **11.28 ms** | **10.49 ms** | 24 ms |
| **差の 99%** | **11.79 ms** | **11.27 ms** | 47 ms |
| 追加遅延（Istesso の窓）：中央値 / 95% / 99% | 28.76 / 34.39 / 35.33 ms | 28.36 / 33.57 / 34.79 ms | — |
| 追加遅延（手元の窓）：中央値 / 95% / 99% | 18.27 / 23.11 / 23.54 ms | 18.16 / 23.07 / 23.52 ms | — |

- 「差」は、同じパーセンタイルどうしの、Istesso の窓から手元の窓を引いた値（合格ラインの指標）。
- 中央値は、どちらも「境界」（11.6〜12.4 ms）の外で、内側。
- 余裕は、中央値で、基準の回が 1.5 ms、新しい形の回が 1.8 ms。

### 入力 1 回ごと

| | 基準の回 | 新しい形の回 |
|---|---|---|
| 手元の窓と同じ更新で見えた | 327 回（16.4%） | 381 回（19.1%） |
| 更新 1 回ぶん遅れた | 1,468 回（73.4%） | 1,457 回（72.8%） |
| **2 回以上遅れた** | **205 回（10.25%）** | **162 回（8.1%）** |

- **上限の決め直し**：測る前に決めてあった決まり（基準の回の割合の 1.5 倍を、小数第 1 位に切り上げる。1 回だけ）で、10.25% × 1.5 = 15.375% → **15.4%**。これより多ければ、不合格。もう動かさない。
- 新しい形の回は、この上限の内側（8.1%）。基準の回は、上限を決めるための回なので、この条件では判定しない。
- 測る前の、かんたんな見積もり（拍が無作為なら 10〜11%）と、基準の回の値は合っている。

### 足並みは、均されていた

画面の更新 1 回ぶんを 8 つに分けて、入力がいくつずつ入ったか（均等なら 250 ずつ）。

| | 基準の回 | 新しい形の回 |
|---|---|---|
| 手元の窓 | 236 221 257 199 223 308 276 280 | 222 230 288 168 234 319 251 288 |
| Istesso の窓 | 257 252 261 239 229 265 243 254 | 243 242 253 238 246 260 277 241 |
| 2 つの差 | 265 227 279 193 267 243 262 264 | 263 249 245 236 244 284 243 236 |

どれも、均等な数の 0.6 倍から 1.4 倍のあいだにある（道具の判定は、3 行とも「均されている」）。古い測り方の 2 回では、「2 つの差」が 2〜3 の区切りに固まっていた。

### 参考：区切りごとの重みをそろえた値

8 つの区切りに入った数（193〜308 回）は、まったくの偶然よりは幅がある。手元の窓では、2 つの回とも、4 つ目の区切りが少なく（199 回と 168 回）、6 つ目から 8 つ目が多い（276〜319 回）。同じ形が 2 回出ているので、偶然ではなく、測り方にくせが残っている、と見ている（原因は、確かめていない）。

そこで、入力 1 回ごとに「その区切りに入った数の逆数」の重みを付けて、3 つの値を計算し直した（窓ごとに、その窓の追加遅延で区切る）。**判定の値は、変えない。** 重みなしの値が、判定の値である。

| | 基準の回：中央値 / 95% / 99% | 新しい形の回：中央値 / 95% / 99% |
|---|---|---|
| 測ったまま（判定の値） | 10.49 / 11.28 / 11.79 ms | 10.20 / 10.49 / 11.27 ms |
| 区切りの重みをそろえた値 | 11.15 / 11.30 / 11.74 ms | 10.62 / 10.56 / 11.31 ms |
| 動いた幅 | +0.66 / +0.02 / −0.04 ms | +0.42 / +0.07 / +0.04 ms |

- **95% と 99% は、ほぼ同じ。中央値は、0.4〜0.7 ms 大きくなる。** 手元の窓の中央値が、数の多い区切りに引っぱられているためである。
- 重みをそろえても、どちらの回も、合格ラインの内側（中央値で 12 ms 未満）で、「境界」（11.6〜12.4 ms）の外にある。ただし、余裕は、基準の回で 0.85 ms、新しい形の回で 1.38 ms に縮む。
- 中央値の差を 0.5 ms の幅で比べるときは、この幅（0.4〜0.7 ms）が、足並みの偏りだけで動きうることを、頭に置く。

## 区間ごと（平均）

| 区間 | 基準の回 | 新しい形の回 |
|---|---|---|
| 入力がアプリに届くまでと、最初のデータが戻るまで | 2.06 ms | 1.43 ms |
| テストアプリ（入力から描き終わりまで） | 6.02 ms | 5.97 ms |
| コンポジター（確定からフレームが出るまで） | 0.97 ms | 0.98 ms |
| 色の変換と圧縮 | 4.01 ms（変換 0.11、圧縮 3.90） | 4.01 ms（変換 0.11、圧縮 3.89） |
| 渡す（パケットにする／暗号化して通信路に書く） | 0.11 ms | 0.17 ms |
| フレームが届く | 0.14 ms | 0.16 ms（開けるまでを含む） |
| 復号 | 3.29 ms | 3.25 ms |
| 復号してから、描くまで | 0.49 ms | 0.50 ms |
| 描いてから、画面に出るまで | 17.80 ms | 17.87 ms |
| 全部（入力を送ってから、画面に出るまで） | 34.89 ms | 34.35 ms |

- **暗号化で増えたのは、渡すところの 0.06 ms と、届くところの 0.02 ms。** 見込みどおり、小さい。
- **「入力がアプリに届くまでと、最初のデータが戻るまで」が、新しい形で 0.63 ms 短い。理由は、まだ確かめていない。** この区間は、ネットワークの行きと帰りを含む。基準の回の映像は IPv6 の UDP、新しい形は IPv4 の TCP で、帰りの道が違う。2 つの PC の時計の合わせ方が効いている可能性もある。新しい形のほうが速い、と言い切る前に、ここを分けて測る。
- コンポジターがフレームを更新 1 回ぶん（12 ms ほど）待たせた入力は、基準の回が 0 回、新しい形の回が 1 回（2,000 回のうち。仮の判定では 22 回）。3〜5 ms 待った入力が、ほかに 5 回と 6 回ある。
- 新しい形の回で、ビューアーは 1 度つなぎ直している（はじめの 1 回が「届かない」で失敗し、自分でつないだ。計測の前の、待ち時間のあいだのこと）。接続は、計測の終わりまで切れていない。
- キーフレームは、どちらの回も 2 枚（はじめの 1 枚と、求めた 1 枚）。パケットの欠けは 0。

## 仮の判定（2026-11-16）と比べて

| | 仮の判定 | 基準の回 |
|---|---|---|
| 測り方 | 拍をずらさない | 拍を毎回ずらす |
| 差の中央値 / 95% / 99% | 11.30 / 11.83 / 14.87 ms | 10.49 / 11.28 / 11.79 ms |
| 2 回以上遅れ | 3.15% | 10.25% |
| ホストのブラウザー | 動いていた | 閉じてある |

- 2 つは、測り方も、ホストの静かさも違うので、「0.8 ms 速くなった」とは読めない。基準の回の値が、これからの比べる相手になる。
- 「2 回以上遅れ」が増えたのは、測り方のため（古い測り方は、たまたま遅れの出にくい拍の間隔に当たっていた）。

## 確かめられていないこと

- 新しい形での、当てるテスト。
- 新しい形の「入力の区間が 0.63 ms 短い」理由。
- 手元のカーソルを、人がポインターを動かして見たときの遅れ（この計測は、キーの入力だけ）。
- 映像の受信スレッドをリアルタイムにする切り替え（入れずに測った）。
- Wi-Fi での値（公開の前に測る。線は ADR 0015）。

## 再現のしかた

計測は、作業用のスクリプトで走らせた（リポジトリには入れていない。`scripts/try.sh` と同じ部品を、計測の置き方で起動する）。比べる道具は `istesso measure compare --refresh-hz 85`、区間ごとの値は `scripts/m1-step3-breakdown.py`。新しい形は、ブランチ `m1-dialog-windows` のホストのスクリプト（`--to-channel`、`--cursor`）とビューアー（`ISTESSO_CHANNEL`）を使う。記録の名前は、`baseline-115327` と `baseline-newest-120914`。
