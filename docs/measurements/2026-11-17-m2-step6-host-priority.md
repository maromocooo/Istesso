# M2：ホストのサウンドシステムの優先度を上げて、前後を比べる

- 日付：2026-11-17
- コミット：2d6bdf7（両方の PC）
- 目的：ホストの取り込みの周期が飛ぶこと（8 時間の確認では 1 時間に 6.5 回）と、そのときのクリック（1 時間に 3 回）が、ホストのサウンドシステムの優先度のせいかどうかを、再起動なしで確かめる。
- 結果：**優先度を上げても、減らなかった。** 上げる前の 30 分に、周期の遅れ 5 回、クリック 3 回。上げたあとの 30 分に、遅れ 11 回、クリック 10 回。

**音は出していません。** Mac の機器には無音を渡し、ホストでは、テストの正弦波（−60 dBFS）を、仮想の出力先にだけ流しています。

## 条件

| 項目 | 値 |
|---|---|
| 動かし方 | 1 時間を 1 回で流し、途中で、持ち主がホストで 1 行を実行した |
| 始めた時刻 | 09:38:30（音源は 09:38:24 から）。終わりは 10:38:35（3600 秒） |
| 優先度を上げた時刻 | **10:07:58**（音源が始まってから 1774 秒）。ホストで 5 秒おきに見ていた値が、変わった時刻 |
| 上げたもの | 持ち主の PipeWire の、処理のスレッド 1 つ。ふつうの時分割（`SCHED_OTHER`、優先度 0）から、リアルタイム（`SCHED_FIFO`、優先度 20）へ |
| こちらの取り込みと、テストの正弦波のスレッド | 始めから、リアルタイム（`SCHED_RR`、優先度 20）だった。こちらのプログラムが、PipeWire の「リアルタイムを求める」設定で動くようにしてからは、RTKit が優先度を貸している |
| 待ち時間の目標 | 60 ms |
| 1 回の処理 | 256 フレーム、48 kHz、PipeWire のタイマーのドライバー |
| Mac の再生 | シェルから起動（低い優先度のプロセス）。受信のスレッドと機器のスレッドは、リアルタイム |
| 経路 | 有線 |
| 同時に動いていたもの | 持ち主の試用の窓（Mac：ビューアーと入力の受け渡し。ホスト：映像の配信、アプリ、エージェント）。別のプロジェクトのデスクトップのアプリ（両方の PC。09:35 には、Mac で 1 コアの 3 分の 2、ホストで 15% ほどを使っていた）。Mac では、ほかの作業の、低い優先度のビルド。ホストでは、ビルドはなかった。ホストの負荷は 3.0 前後 |

実行した行（持ち主が、ホストで）：

```sh
sudo chrt -f -p 20 $(ps -L -o tid=,comm= -p $(pgrep -u "$USER" -f '^/usr/bin/pipewire$') | awk '$2=="pw-data-loop"{print $1}')
```

元に戻す行（PipeWire を再起動しても、戻る）：

```sh
sudo chrt -o -p 0 $(ps -L -o tid=,comm= -p $(pgrep -u "$USER" -f '^/usr/bin/pipewire$') | awk '$2=="pw-data-loop"{print $1}')
```

**この記録を書いた時点で、優先度は上がったままです**（10:39 に読んだ値は `SCHED_FIFO`、優先度 20）。戻すかどうかは、持ち主が決めます。

## わかったこと

1. **サウンドシステムのスレッドの優先度を上げても、取り込みの周期の遅れは、なくならなかった。** 上げたあとの 30 分に、11 回あった。上げる前の 5 回より多い。
2. **比べ方として言えるのは、「なくならない」までである。** 30 分ずつでは、数が少ない。8 時間の確認での割合（1 時間に 6.5 回）から見込まれるのは、30 分に 3 回ほどで、5 回と 11 回の差は、偶然でも起こりうる。「上げると悪くなる」とは言えない。「上げれば直る」は、今回の値とは合わない。
3. **前と後が、同じ静かさだったとは言えない。** 上げる前の 5 回は、はじめの 4 分に集まっていて、そのあとの 25 分は 0 回だった。上げたあとは、26 秒のあいだに 4 回続いたところがある。同時に動いていたものの負荷を、半分ずつに分けては、記録していない。
4. **遅れは、いつも 1 周期ぶん（5.3 ms）か、2 周期ぶんである。** 周期の始まりが遅れたというより、こちらの取り込みが、その周期に加われなかった（その周期ぶんの音を受け取っていない）とみるほうが、合う。そのとき、テストの正弦波の側も同じ周期を休んでいれば、音はつながり、休んでいなければ、1 周期ぶんが失われて、クリックになる。**原因は、サウンドシステムのスレッドではなく、こちらの 2 つのプログラムと、サウンドシステムとのやり取りの側にある見込みである。** まだ、確かめていない。PipeWire は、周期に間に合わなかった回数をノードごとに数えているので、次の計測で、それを読む。
5. **Mac の飛ばしは、こちらの処理が遅れたためだった。** 機器が音を引き取りに来なかった 12 度は、機器の「間に合わなかった」という知らせ 12 回と、数が合う。こちらの処理（機器のスレッドの中）には、最長で 22.9 ms かかっていた。ふだんは 1 ms ほどである。ただし、この回の再生は、シェルから起動した、低い優先度のプロセスだった。自分の許可を持つ `.app` として起動した場合の値は、まだ取っていない。
6. **遅れを少しずつ取り戻す仕組みは、実機で動いた。** 周期が 16 回遅れた（合わせて 90.7 ms）が、取り込みから機器に渡すまでは、はじめの 10 分と終わりの 10 分とで 0.3 ms しか違わない。途切れは 0 回。周期が遅れてもクリックにならなかった 1 分では、音程の下がり方は −175 ppm までで、前の晩の −500 ppm より小さい。Mac の機器が来なかったあとには、たまった分を取り戻すために、音程が +950 ppm ほどまで上がった 1 分がある。

## 次にすること（どれも、まだしていない）

- ノードごとの「間に合わなかった回数」を、計測の終わりに読む（`pw-top`）。こちらの取り込み、テストの正弦波、ドライバーの、どれが数えられているかで、4 の見立てを確かめる。
- 処理の周期を長くした場合（512、1024 フレーム）に、遅れとクリックが減るかどうか。
- Mac の再生を、自分の許可を持つ `.app` として起動して、こちらの処理にかかる時間と、機器が来なかった回数を取り直す。
- ホストの優先度を、上げたままにするか、戻すか。今回の値からは、上げておく理由は出ていない。
