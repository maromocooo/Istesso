# M2 手順 3・4：本物の取り込みで、2 台のあいだを通す

- 日付：2026-11-16
- コミット：この記録と同じコミット（`istesso audio serve --source pipewire`）
- 目的：ホストの取り込み（PipeWire の仮想の出力先）を、実機で動かす。そこに流した音が Mac まで届くこと、ホストの音の設定が前後で変わらないこと、届く間隔・いちばん長い停止・時計のずれ・遅延を見る。

**音は出していません。** Mac の機器には無音を渡し、渡すはずだった音を調べています。ホストでは、テストの音を、どの機器にもつながっていない経路にだけ流しています（下の「テストの音の流し方」）。

はじめの 3 回は、Mac の再生を低い優先度で動かしています（エージェントのシェルから起動）。ふつうの優先度での 6 回と、そこで分かった停止の原因は、「ふつうの優先度での計測と、停止の原因」に書きました。**結論：停止は、Mac の受信のスレッドが待たされて起きていた。そのスレッドを、機器のスレッドと同じ種類の優先度で動かすようにしたあとは、待ち時間 40 ms の 85 秒 3 回で、途切れは 0。**

### テストの音の流し方

- 仮想の出力先は、`istesso audio serve --source pipewire` が作る（`media.class = Audio/Sink`、優先順位は最低）。
- そこへ流す音は、997 Hz の正弦波、**−60 dBFS**。ホストに入っている `pw-cat` に、WAV ファイルを再生させた。
- `pw-cat` は、自動ではどこにもつながない指定（`--target 0`）で、仮想の入力の種類のノード（`Audio/Source`、優先順位は最低）として起動し、仮想の出力先の入力に、`pw-link` で手でつないだ。つないだあと、リンクが仮想の出力先だけに向いていることを確かめている。ほかの機器に音が届く経路はない。
- テストのあいだ、ホストではほかに何も鳴っていなかった（動いているドライバーは 0）。そのため、この 2 つのノードは、PipeWire のタイマーのドライバー（Dummy-Driver）で動いた。1 回の処理は 256 フレーム、48 kHz（`pw-cat` が 256 フレームを求めた。仮想の出力先の側からは、何も求めていない）。

## わかったこと

1. **本物の取り込みで、音は Mac まで届く。** アプリが仮想の出力先に流した音が、認証と暗号化を通して、1 パケットも変わらずに届いた。渡すはずだった音は、流したとおりの −60 dBFS の正弦波だった。
2. **遅延は、待ち時間に約 1.2 ms を足した長さになる。** 待ち時間 40 ms で、取り込みから機器に渡すまでが 41.2 ms。計画の目標（有線で中央値 50 ms 以下）に収まる。テスト用の正弦波のとき（46.5 ms）より短いのは、仮想の出力先には、1 回の処理ぶんの音が、処理の始まりにそろっているからである。マイクのように、最後のフレームを待つ必要がない。取り込んだ時刻は、処理の始まりの時刻（PipeWire の時計）にしている。
3. **再生の側が機器を開いているあいだに、音源が音を捨てていた（1 回め）。** 機器を開くのに 2 秒近くかかることがあり、そのあいだ受信が始まっていなかった。接続の中にパケットがたまって音源の送信が待たされ、音源は、決めたとおりに古い音を捨てた。受信を、機器を開く前に始めるように直した。2 回めでは、音源は何も捨てていない。
4. **待ち時間 40 ms では、途切れた。100 ms では、途切れなかった。** 85 秒のあいだに、20〜41 ms の停止が 1〜2 度あった。待ち時間 40 ms のうち、遅れたパケットのために使えるのは約 12 ms なので、そのたびに途切れた（フェードで終わり、フェードで始まる。クリックはない）。待ち時間 100 ms（遅れてよい分は約 72 ms）の 3 回めでは、35 ms の停止が 1 度あったが、途切れなかった。どちらの端で止まったのかは、まだ分けられていない。Mac の受信は低い優先度で動いていて、ホストの側にも、次の 5 がある。**停止の原因を確かめてなくすことが、8 時間の確認より先である。**
5. **ホストのサウンドシステムは、リアルタイムの優先度で動いていない。** PipeWire のデーモンの処理のスレッドも、こちらの取り込みのスレッドも、ふつうの時分割のクラスで動いていた（リアルタイムの優先度の上限が 0）。負荷がかかると、処理が遅れうる。これは、ホストのいまの設定であり、こちらからは変えていない。理由と、直す 1 行は、下の「ホストのサウンドシステムが、リアルタイムの優先度で動いていない理由」に書いた。
6. **音程は、±94 ppm まで動いた。** 始まりと再開を含む 85 秒の値である。計画の目安（50 ppm）と、模擬で検査している上限を、どちらも超えている。聞こえる大きさではない（0.16 セント）が、**実機での上限は、まだ示せていない。** 途切れのあとの再開のたびに補正が振れることと、いちばん速いパケットの待ち時間が 1 秒ごとに 0.3 ms ほど揺れることが、原因とみている。
7. **時計の差は、まだ読めない。** 補正が覚えた値は −0.6〜−0.9 ppm だが、85 秒では落ち着かない。長い計測で見る。

### 停止の原因

- **ホストでも、経路でもない。** パケットは、ホストを、いつも取り込みから 2〜4 ms のうちに出ている。TCP は、再送も、送信の待ちも、起こしていない。
- **Mac の受信のスレッドが、待たされていた。** 6 回めで、途切れた時刻は、Mac のプロセスが 16〜26 ms 待たされた時刻と重なった（始めてから 10.0 秒、55.4 秒、81.4 秒）。ふつうのスレッドは、この Mac で、1 分に数回、10〜26 ms 待たされている。5 回めの 216 ms も、同じ種類のものとみている（その回は、待たされた時間を測っていない）。
- はじめの 3 回（低い優先度）の停止も、同じ場所だった。

### 直したこと

- **Mac の受信のスレッドを、機器のスレッドと同じ種類の優先度（時間の制約つきのリアルタイム）で動かす。** 受信のスレッドは、音の経路の一部である。それが 20 ms 待たされれば、音が 20 ms 遅れる。権限は要らない。7〜9 回めでは、プロセスのほかのスレッドは同じように待たされ続けたが、パケットの遅れは 5 ms 以内になり、途切れは 0 だった。
- ペアリング一覧の読み直しを、送るスレッドから、別のスレッドに移した。ファイルを読むあいだ、音を待たせないためである。今回の停止の原因ではなかった（読み直しは 0.23 ms 以内）が、音を送るスレッドがファイルを読むべきではない。

### 残っていること

- **音程。** 途切れのない 3 回で、−48.8〜+40.4 ppm。目安の 50 ppm に、ぎりぎり収まった。4 回めは −51.5 ppm まで動いた。85 秒は、補正が落ち着く前の時間を含む。**実機での上限は、まだ示せていない。** 長い計測で見る。
- **3 回、合わせて 4 分あまりの結果である。** 8 時間のあいだに、もっと長い停止が、どちらかの端で起きないとは言えない。8 時間の確認は、そのためにある。
- ホストのサウンドシステムは、リアルタイムの優先度で動いていない（次の節）。今回の停止の原因ではなかった。ホストの側の値は、持ち主の試用の窓が動いている状態で、上の表のとおりだった。

## ホストのサウンドシステムが、リアルタイムの優先度で動いていない理由

何も変えずに調べた結果です。

| 調べたこと | 結果 |
|---|---|
| RTKit（リアルタイムの優先度を、上限つきで貸す仕組み） | 入っていて、動いている（rtkit 0.13）。この起動のあいだに、ログイン画面のユーザーのプロセスと、持ち主のデスクトップのアプリ 1 つには、優先度を与えている |
| RTKit が応じる相手（polkit の既定） | その PC の前のセッションだけ（動いているものと、控えのもの）。それ以外（SSH など）には、応じない |
| 持ち主の PipeWire | ユーザーのサービス管理（systemd の `user@`）の中で、起動の 10 秒後から動いている（lingering が有効）。**その PC の前のセッションには、属していない。** 処理のスレッドは、ふつうの時分割のクラスで、nice 値は 0 |
| 上限の設定 | リアルタイムの優先度の上限は 0（デスクトップのセッション、SSH、ユーザーのサービス管理の、どれも）。PipeWire のパッケージは、`pipewire` グループに上限を与えるファイル（`/etc/security/limits.d/25-pw-rlimits.conf`：rtprio 95、nice −19、memlock 4 GB）を入れているが、そのグループには誰も入っていない |
| 断られた記録 | **ログには、ない。** RTKit、polkit、PipeWire のどのログにも、断ったという行がない。PipeWire 1.0.5 は、頼んだ時点で「もらえた」と記録するが（ログを詳しくして確かめた）、スレッドの優先度は変わっていない。RTKit に SSH から直接頼むと、`Access denied` が返る |
| こちらの取り込みのスレッド | 同じ。リアルタイムの優先度を求める設定（PipeWire の `client-rt.conf`）で動かすように直したが、このホストでは、上の理由で効かない |

つまり、**このホストでは、PipeWire がリアルタイムの優先度をもらう道が、2 つとも閉じています。** RTKit は、その PC の前のセッションにしか応じません。持ち主の PipeWire は、起動の直後から、どのセッションにも属さずに動いています。上限で与える道は、グループに誰も入っていないので、使えません。ホストの前に誰も座っていないのがふつう、という使い方では、RTKit の道は当てにできません。

調べるあいだに残ったもの：PipeWire のログを詳しくして 6 秒動かした試験の 1 行が、ユーザーのジャーナルに残りました（こちらのプログラムの名前で、「リアルタイムにできなかった」という内容）。設定や状態のファイルは、変わっていません。

### 直す 1 行（質問として出す。実行していない）

```sh
sudo adduser <ユーザー名> pipewire     # そのあと、再起動する
```

- **何をするか：** PipeWire のパッケージが用意している `pipewire` グループに、ユーザーを入れる。パッケージの説明（`/usr/share/doc/pipewire/README.Debian.gz`）にある方法である。再起動のあと、そのユーザーの PipeWire は、RTKit を通さずに、自分でリアルタイムの優先度（88）を設定できる。その PC の前に誰もいなくても、SSH だけでも、効く。上限は、ユーザーのサービス管理にも、SSH のログインにも、PAM が与えるからである（`/usr/lib/pam.d/systemd-user` と `/etc/pam.d/sshd` に `pam_limits` がある）。
- **ほかに何が変わるか：** そのユーザーの**すべての**プログラムが、リアルタイムの優先度（95 まで）、高い優先の nice 値（−19 まで）、4 GB までのメモリーの固定を、使えるようになる。RTKit の安全装置（優先度の上限 20、暴走したスレッドを元に戻す見張り）を、通らなくなる。リアルタイムのスレッドが暴走すると、機械の反応が悪くなりうる（カーネルは、ほかの処理のために 5% を残す）。パッケージの説明も、この点を警告している。
- **元に戻すには：** `sudo deluser <ユーザー名> pipewire` を実行して、再起動する。
- **インストーラー（M9）では：** 音のサービスを動かすユーザーに、同じ上限を与える必要がある。lingering も要る（このホストでは、すでに有効）。

**この行は、実行しないと決まっています（2026-11-16）。** 再起動は、ほかの作業を全部止め、カーネルも新しくなるためです。上の計測で、停止の原因は Mac の側にあり、ホストの優先度ではないと分かりました。いまは、この変更は要りません。長い計測で、ホストの側の停止が見つかったときに、次の「再起動なしで確かめる行」から始めます。

### 再起動なしで、優先度が原因かどうかを確かめる行（実行していない）

動いている PipeWire の処理のスレッドと、こちらの取り込みのスレッドの優先度を、その場だけ上げます。`sudo` の行は、持ち主が実行します。

```sh
# 持ち主の PipeWire の、処理のスレッド
sudo chrt -f -p 20 $(ps -L -o tid=,comm= -p $(pgrep -u <ユーザー名> -x pipewire) | awk '$2 == "pw-data-loop" {print $1}')
# こちらの取り込み（istesso audio serve を動かしているあいだに）
sudo chrt -f -p 20 $(ps -L -o tid=,comm= -p $(pgrep -u <ユーザー名> -n -x istesso) | awk '$2 == "pw-data-loop" {print $1}')
```

- 何が変わるか：その 2 つのスレッドだけが、リアルタイムの優先度 20（RTKit が貸すのと同じ値）で動く。ほかのプログラムの上限は、変わらない。設定のファイルは、何も書かれない。
- 元に戻すには：`sudo chrt -o -p 0 <スレッドの番号>`。何もしなくても、そのプロセスが終われば（PipeWire を再起動するか、PC を再起動すれば）元に戻る。
- 前後で測るもの：取り込みの周期のいちばん長い間隔、取り込みから取り上げまで、いちばん遅れたパケットの遅れ、途切れの数（85 秒を 3 回ずつ）。いまは、前の値がすでに決まった間隔のとおりなので、差は出ない見込みである。

### 再起動のあとで、確かめ直すこと（音のぶん）

グループに入れることになったときは、再起動でカーネルも新しくなります。音については、次を確かめ直します。

1. 機能 `pipewire` を付けたビルドが通る（`cargo build -p istesso-cli --features pipewire`）。
2. 持ち主の PipeWire と WirePlumber が、ログインしなくても動いている（lingering）。処理のスレッドが、リアルタイムのクラスになっている（`ps -L -o cls,rtprio,comm -p <PipeWire の番号>`）。
3. `istesso audio serve --source pipewire` で仮想の出力先ができ、既定の出力先が変わらない。終わったあとに、何も残らない。
4. 短い計測（[m2-try.md](../m2-try.md) の手順）：パケットがすべて同じ、途切れ 0、取り込みの周期の間隔、取り込みから機器に渡すまでの中央値が、この記録の値から変わっていない。
5. セッションマネージャーの状態のファイルが、試験の前後で同じ（残っている 8 行のほかに、増えていない）。


## ホストの前に誰も座っていない状態

この記録の計測は、どれも、持ち主がデスクトップにログインした状態のホストに、SSH でつないで行いました。「起動した直後（ログイン画面のまま、SSH だけ）」の状態では、まだ動かしていません。

- 取り込みが使う PipeWire は、ユーザーのサービス管理の中で動いていて、デスクトップのログインには頼っていない（lingering が有効なので、ログインしなくても動いている）。
- その状態では、サウンドカードは、ログイン画面の側のものになる。持ち主の PipeWire からは、機器が見えないはずである。仮想の出力先は、機器がなくても、PipeWire のタイマーのドライバーで動く（この記録の計測と同じ）。
- 動くはずだが、確かめていない。ホストがその状態のときに、確かめる。
- 取り込みは、サウンドカードを使わない。サウンドカードのデバイスは、持ち主がデスクトップにログインしているときだけ開ける（ユーザーは `audio` グループに入っていない）が、音源の側には要らない。Linux を音の出口にするとき（まだ作っていない）には、要る。

インストーラー（M9）が用意するもの（音源の側）：

| 用意するもの | 理由 |
|---|---|
| ユーザーの lingering | ログインしなくても、ユーザーの PipeWire と、音のサービスが動くように |
| 音のサービス（ユーザーの systemd のユニット） | いまは、手で起動するコマンド |
| リアルタイムの優先度の上限（`pipewire` グループか、それと同じ上限を与えるファイル） | RTKit は、その PC の前のセッションにしか応じない。入れるかどうかは、効果を確かめてから決める |
| Linux を出口にするとき：サウンドカードを開く権限（`audio` グループなど） | デスクトップにログインしていないと、デバイスを開けない |

Mac の側では、受信のスレッドの優先度は、プログラムが自分で設定します。常駐させるとき（launchd）は、背景のプロセスとして扱われて待たされないように、種類の指定（`ProcessType`）を確かめます。

## まだ測っていないこと

- Mac の再生を、ふつうの優先度で動かした場合。`.app` として起動し、ローカルネットワークの許可をもらう必要がある。上の 4 と 6 は、そのうえで測り直す。
- 待ち時間の目標を上げた場合（60 ms、100 ms）に、途切れが 0 になるか。
- 1 回の処理が長い場合（アプリが何も求めないと 1024 フレームかそれ以上）。
- ホストでほかの音が鳴っているとき。仮想の出力先は、そのとき動いている機器のドライバーと同じ周期で動くことになる。
- 44.1 kHz の機器、Wi-Fi、8 時間、耳で聞く確認。

## 再現のしかた

```sh
# ホスト（作業用の場所の鍵で）。テストの 2 つのノードには device.routes=1 を付ける。
istesso audio serve --source pipewire --bind <有線のアドレス> --port 47822 --seconds 99 \
    --ledger sent.txt --node-name istesso-audio-test --node-description "Istesso audio test" \
    --node-property device.routes=1
pw-cat --playback --target 0 --latency 256 \
    -P '{ media.class = "Audio/Source" device.routes = 1 priority.session = 0 node.name = "istesso-audio-test-tone" }' \
    tone.wav        # 997 Hz、−60 dBFS、48 kHz、2 チャンネル、32 ビット
pw-link istesso-audio-test-tone:capture_FL istesso-audio-test:playback_FL
pw-link istesso-audio-test-tone:capture_FR istesso-audio-test:playback_FR

# Mac
istesso audio play <有線のアドレス>:47822 --peer <音源の名前> --latency-ms 40 --seconds 85 \
    --record played.f32 --ledger received.txt --report report.json
istesso audio compare sent.txt received.txt
```

前後で `wpctl status` と、セッションマネージャーの状態のファイルを比べます。
