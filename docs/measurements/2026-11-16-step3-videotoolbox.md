# 手順 3：VideoToolbox で直接復号する（設定の比較 3）

- 日付：2026-11-16
- コミット：892aadf（`macos/gst-viewer` に VideoToolbox の経路を足したコミット）
- 目的：これまでの受信側は、ソフトウェアで復号し（1 フレーム 2.4 ms）、GStreamer の表示の要素で描いていた（1.6 ms）。GStreamer の VideoToolbox 用の要素はフレームをためるので使えなかった。VideoToolbox を直接使い、復号した絵をそのまま窓に渡すと、どれだけ縮むかを見る。自前のクライアント（手順 4）が行う予定のやり方である。

## 条件

| 項目 | 値 |
|---|---|
| ホスト | Ubuntu 24.04、RTX 4090、GStreamer 1.24.2。フレームは CUDA のメモリーでエンコーダーに渡す（[記録](2026-11-16-step3-gpu-frames.md)） |
| クライアント | MacBook Air（M4）、macOS 26.5.1、GStreamer 1.28.9。`macos/gst-viewer` |
| 接続 | ホストは有線。Mac は Wi-Fi（5 GHz 帯のチャンネル 44、共有の機能は元の設定。[記録](2026-11-16-wifi-channel-44.md)） |
| 解像度とフレームレート | 1720×720、85 fps。灰色の絵 |
| クライアントのディスプレイ | 外部（3440×1440、84.96 Hz）。2 つの窓は前面に出さずに起動 |
| コーデックとビットレート、エンコーダーの設定、経路 | H.265、30 Mbps。[最初の 1 本の記録](2026-11-16-step3-first-path.md)と同じ |

受信側の 2 つの形：

```text
これまで：     udpsrc ! rtph265depay ! h265parse ! avdec_h265 max-threads=1 ! queue（最新の 1 枚だけ） ! glimagesink sync=false
VideoToolbox： udpsrc ! rtph265depay ! h265parse ! video/x-h265,stream-format=hvc1,alignment=au ! appsink name=vt
```

VideoToolbox の形では、GStreamer は受信と H.265 の切り出しまでを受け持ちます。`gst-viewer` が、届いたフレームをその場で 1 枚ずつ VideoToolbox に渡し、返ってきた絵（デコーダーの持つサーフェス）を、写さずに窓のレイヤーに渡します。

## 測り方

[README.md](README.md) の「内訳の計測」のとおり、500 回ずつです。

| 回 | 復号 | 時刻（JST） |
|---|---|---|
| A | ソフトウェア | 14:51:27〜14:54:53 |
| B | VideoToolbox | 14:55:05〜14:59:07 |

## 結果

| 指標 | A：ソフトウェア | B：VideoToolbox |
|---|---|---|
| 追加遅延の、手元の窓との差（中央値 / 95%） | 19.4 / 23.6 ms | **16.6 / 20.0 ms** |
| 　参考：99%（500 回なので判断に使わない） | 26.2 ms | 21.1 ms |
| 中継した窓の追加遅延（中央値 / 95% / 99%） | 37.3 / 46.9 / 52.4 ms | 34.2 / 43.1 / 48.1 ms |
| 手元の窓の追加遅延（中央値） | 18.0 ms | 17.6 ms |
| 受信側の CPU の使用率（1 コアを 100% として） | 47%（同じ日の別の回） | 9% |

内訳（平均）：

| 区間 | A：ソフトウェア | B：VideoToolbox | 差 |
|---|---|---|---|
| ネットワーク、アプリ、コンポジター、圧縮、パケット | 15.1 ms | 14.7 ms | −0.5 ms |
| フレームが届く | 0.1 ms | 0.1 ms | 0.0 ms |
| **復号（最後のパケットから、復号の終わりまで）** | 2.4 ms | 1.7 ms | **−0.8 ms** |
| **待ち行列と、描くまで** | 1.8 ms | 0.3 ms | **−1.6 ms** |
| 描いてから、画面に出るまで | 18.6 ms | 18.3 ms | −0.3 ms |
| 合計 | 38.1 ms | 35.0 ms | −3.1 ms |

手元の窓は、フレームの確定から画面に出るまでが平均 17.5 ms でした。VideoToolbox の形で描いてから画面に出るまで（18.3 ms）は、それより 0.8 ms 長い値です。

カメラでの計測：行っていません。

## わかったこと

1. **VideoToolbox を直接使うと、中央値の差が 19.4 ms から 16.6 ms に、95 パーセンタイルが 23.6 ms から 20.0 ms に下がりました。**
2. **効いたのは、復号よりも描画です。** 復号は 0.8 ms、描くまでは 1.6 ms 縮みました。GStreamer の表示の要素は、絵を OpenGL に上げて色を変換してから描きます。デコーダーのサーフェスをそのまま窓に渡せば、その仕事がなくなります。
3. 受信側の CPU の使用率は、5 分の 1 になりました。
4. 画面に出るまでの時間は、まだ手元の窓より 0.8 ms 長い値です。窓への出し方（レイヤーに渡すタイミング）に、まだ工夫の余地があります。
5. 以後の計測は、VideoToolbox の形を基本にします。

読むときの注意：

- 灰色の絵での値です。動く絵での値は、[別の記録](2026-11-16-step3-moving-picture.md)にあります。
- `gst-viewer` は、復号に失敗すると、次のキーフレームまで何も出しません。パケットを失ったときに作り直してもらう仕組みは、まだありません。
