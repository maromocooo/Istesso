# M4 の進め方：Mac をホストにする

M4 は、Mac のアプリを、別の Mac の窓として使えるようにする段階です。受け入れ条件は「Mac Studio のアプリを MacBook Air の窓として、M1 と同じ合格ラインで使える」です（[milestones.md](milestones.md)）。今週は、Mac Studio の到着を待たずに、**Mac mini（ホスト）と MacBook Air（クライアント）の2台**で進めます（2026-11-16 に決定）。

この文書は、実機の上で作業する人とコーディングエージェントのための手順書です。前半は準備の一覧、後半は手順と確かめ方です。規約は先に [AGENTS.md](../AGENTS.md) を読んでください。

この段階のねらいは、**Mac Studio の到着を待たずに確かめること**です。決めごとで判断がつかないところは、ねらいに合うほうを選びました（[milestones.md](milestones.md) の「今週の進め方」）。選んだところは、「6. 決まったことと、まだ決まっていないこと」に、もとにしたねらいと一緒に書いてあります。

読むときの注意：

- **実機で動かしたものは、少しだけです。** Mac mini では、読むだけの調査と、エンコーダーの計測をしました（2026-11-17。3.9 と、手順 2）。画面の取り込みと、入力の注入は、まだ1回も動かしていません（許可が要るため）。Air では、読むだけの調査（`sw_vers`、`system_profiler`、`istesso doctor`）をしました。「見込み」「未確認」と書いたところは、手順の中で確かめます。
- Apple の API について書いたことは、2026-11-16 に Apple の公開の文書で確かめた範囲です。出どころは「9. 参照した文書」にあります。**H.265 の 4:4:4 についてだけは、同じ日に Air のエンコーダーに直接尋ねた結果を書いています**（手順 2）。
- ADR 0008 と 0009（`m1-latency` ブランチ）、ADR 0010（`m3-app-manager` ブランチ）、ADR 0011（`m2-audio` ブランチ）と、M1 の計測の記録は、まだ `main` にありません。この文書では、リンクにせずに番号で指します。

## 1. 確かめること

1. Mac mini のアプリ1つを、Air の窓1枚として出して操作できる。
2. 追加遅延と画質が、M1 と同じ合格ラインに収まる（[ADR 0002](adr/0002-latency-first.md)。数値は `m1-latency` ブランチで決まったもの）。
3. どの窓がリモートかを当てるテストで、当てられない。
4. そのアプリの音が、選んだ音の出口から鳴る（[ADR 0005](adr/0005-audio-service.md)）。
5. 足りない OS の許可を、`istesso` が案内する（R-12）。
6. Mac mini に人がログインしてあれば、画面をロックした状態でも、スリープから起こした直後でも、使える。再起動のあとに1回ログインが要ることは、制約として書いてある（2026-11-16 の決定。4.4）。

## 2. ほかの流れとの関係

| 相手 | 関係 |
|---|---|
| M1（遅延の検証） | 関門は外さない。**待つのは、M4 の判定（手順 8）だけにする。** 準備と手順 0〜7 は、M1 の判定を待たずに、並行で進める。手順 0〜2（調査、取り込み、圧縮）は、Mac だけの部分である。手順 3 から先は、M1 のいまの受信側を、そのまま使う。M1 が構成を見直すことになったときに作り直すのは、送り出しの部分で、取り込み、圧縮、入力は残る |
| M1 の計測 | Air は M1 のクライアントでもある。実機で遅延を測っているあいだは、M4 のビルドと試験を止める（`m1-latency` ブランチの決まり）。計測の時間は、M1 が先 |
| M3（アプリマネージャー） | セッションの始め方は ADR 0010 に従う。ホストの側は「ランナー」というプログラムで、標準入出力に1行ずつの JSON を受ける。ADR 0010 は、Mac のアプリの起動と窓の扱いを M4 で見直すと書いている（6. の 9） |
| M2（オーディオ） | Mac の音の取り込みは、M2 の逆の向き（Mac の音をほかの PC から出す）と同じ部品になる。分担は 6. の 10 |
| M5（隔離） | Mac の専用ユーザーのセッションから配信できるかは、[ADR 0003](adr/0003-isolation.md) が M4 で確かめると書いている。今週は、ふだんのユーザーで進める（7.）。[ADR 0014](adr/0014-dedicated-user-in-practice.md)（提案）は、ホスト専用の Mac を、専用ユーザーでログインして使う形にしている |

## 3. 準備

人がやることを先に並べます。エージェントに任せられることは、そう書いてあります。

### 3.1 役と体制

| 役 | 機材 | いまの状態 |
|---|---|---|
| ホスト | Mac mini（Apple M4、メモリー 16 GB、macOS 26.7.1） | 調べた（2026-11-17。3.9）。コンパイラーがまだなく、有線 LAN はつながっていない |
| クライアント | MacBook Air（M4、macOS 26.5.1、Xcode 26.6、Rust 1.93） | M1 のクライアントとして動いている。外部ディスプレイは 3440×1440 の 85 Hz、有線 LAN のアダプターつき |

M1 と同じく、Air の上でコーディングエージェントを動かし、Mac mini へは SSH でつなぎます。

| エージェントに任せること | 人がやること |
|---|---|
| Mac mini でのビルドと実行、ログの収集（SSH が通ったあと） | Mac mini の最初の設定、ケーブルの接続 |
| 調査用の小さなプログラムと、計測 | macOS の許可のダイアログへの応答（管理者のパスワードが要る） |
| 記録、ADR と文書の更新 | 「6.2 まだ決まっていないもの」の決定 |
| 判定の計測を始める前に、人に知らせる | 当てるテスト。判定の計測のあいだ、Mac に触らない |

### 3.2 手元に用意する物と、知らせてほしいこと

用意する物：

- [ ] Mac mini 用の LAN ケーブルと、ルーターかスイッチの空いている口。
- [ ] Mac mini の最初の設定に使う、画面、キーボード、マウス。
- [ ] Mac mini の映像のケーブル（HDMI など）と、外部ディスプレイの空いている入力（3.5 の表）。
- [ ] Air の MagSafe の電源と、いま使っている有線 LAN のアダプター。

新しく買うと決まっている物は、ありません。ダミープラグが要るかどうかは、手順 0 の結果で分かります。

Mac mini について、知らせてほしいこと：

- [ ] 機種（「この Mac について」。Apple シリコンか、何年のものか）と、macOS のバージョン（`sw_vers`）。
- [ ] 映像の出力を、何につなげるか（3.5 の表の3つから）。
- [ ] その Mac mini を、ふだん誰かが使っているか。使っていなければ、ホスト専用にできる（4.2 の 1）。
- [ ] FileVault が入っているか（`fdesetup status`）と、自動ログインの状態（`sysadminctl -autologin status`）。どちらも、記録するだけで、変えない（4.4）。
- [ ] Apple Developer Program に入っているか（6. の 7）。

macOS のバージョンの目安：

| バージョン | 理由 |
|---|---|
| 14.2 以上（必須） | アプリの音を取る Core Audio のタップが、ここから（ADR 0005）。取り込みに子の窓を含める指定も、ここから |
| 15 以上 | ローカルネットワークの許可が、Mac ではここから入った。画面収録の許可を定期的に確かめ直す動きも、この版から（報道による） |
| Air と同じ系（いまは 26 系） | 片方で分かったことが、もう片方にそのまま当てはまる。違うときは、記録にバージョンを書く |

Intel の Mac mini だと、エンコーダーが別物になります。その場合は、先に知らせてください。この文書は、Apple シリコンを前提に書いています。

### 3.3 Mac mini：設定と、入れるもの

人がやること（Mac mini の前で）：

- [ ] 最初の設定を済ませる。画面、キーボード、マウスが要る。
- [ ] 有線 LAN をつなぐ（内蔵の LAN の口）。
- [ ] 「システム設定」の「共有」で、「リモートログイン」（SSH）を入れる。Air の公開鍵を登録する。あとの操作のために、「画面共有」も入れておくと、Air から画面を見て、許可のダイアログに応えられる。

眠りと、画面のロックについて：**Mac mini の設定は、変えません。** 配信しているあいだに眠ると、絵が止まります。画面をロックした状態で動くことは、受け入れ条件です（4.4）。そこは、手順 7 で確かめます。遅延を測る手順 1〜6 のあいだだけ、エージェントが `caffeinate` を動かして、眠りと、画面が消えること（その先のロック）を止めます。権限は要りません。止めれば、元に戻ります。効くかどうかは、手順 0 で確かめます。Mac mini の FileVault は、切りません（4.4）。

入れるもの。SSH が通ったあとは、エージェントに任せられます。ただし、Xcode と Homebrew のインストールは、サインインや管理者のパスワードが要るので、人がやります。ほかに権限の要るものが出たら、エージェントがコマンドを提示します。

| 入れるもの | 何のため | Air |
|---|---|---|
| Xcode。ビルドだけなら Command Line Tools（`xcode-select --install`）でも足りる見込み（未確認） | Swift と Objective-C のコード（取り込み、圧縮、入力）をビルドする。Xcode があると、役割表に `xcode_build` が付く | 済（26.6） |
| Rust（stable、1.85 以上） | `istesso` とテストアプリのビルド | 済（1.93） |
| リポジトリの複製 | ビルドのもと | 済 |
| `istesso`（`cargo install --path crates/istesso-cli --locked`） | 役割表、ペアリング、エージェント | 済 |
| テストアプリ（`istesso-flash`）と計測の道具（`m1-latency` ブランチ） | 遅延の計測 | 済 |
| GStreamer（Homebrew） | 手順 3 で、送り出しに既製の部品を使う場合だけ。LGPL なので動的リンクで使う（[components.md](components.md)） | 済 |

入れないもの：Sunshine、Moonlight、xpra。Mac を配信する実装を含みますが、GPL です。比較の対象として動かすことはあっても、コードは読みません（AGENTS.md）。

### 3.5 つなぎ方

判定の条件は「2台とも有線、クライアントのディスプレイは 85 Hz」です（ADR 0002）。Air の USB-C の口は2つなので、使い道は決まっています。

```text
 ┌───────────────┐  映像（下の表の、どれか）
 │ Mac mini       ├──────────────────────────┐
 │ （ホスト）      │                           ▼
 │   内蔵の LAN ──┼──┐                ┌────────────────┐
 └───────────────┘  │                │ 外部ディスプレイ  │
                 ┌──┴─────┐          │ 3440×1440       │
                 │ ルーター │          └───────▲────────┘
                 │ スイッチ │                  │ USB-C その1（直接。85 Hz）
                 └──┬─────┘          ┌───────┴────────┐
                    │ 有線            │ MacBook Air     │
                    └─ LAN アダプター ─┤ （クライアント）  │
                       USB-C その2    │ 電源は MagSafe   │
                                     └────────────────┘
```

- **Air の USB-C その1：ディスプレイに直接つなぐ。** ハブを通すと、ディスプレイが 60 Hz になった（M1 の記録）。
- **Air の USB-C その2：有線 LAN のアダプター。** いまつないであるものを、そのまま使う。
- **Air の電源は MagSafe でつなぐ。** USB-C の口を使わない。これで、Air の口は埋まる。ほかの機器を Air に挿す余地はない。
- Mac mini は、内蔵の LAN の口でつなぐ。Wi-Fi は切るか、計測では有線のアドレスだけを使う（3.7）。
- 2台を Thunderbolt のケーブルで直接つなぐ形は、使わない。基準の対象は自宅の有線 LAN で、Air の口も足りない。

Mac mini の映像の出力を、何につなぐか：

| つなぎ先 | 最初の設定 | 計測での意味 |
|---|---|---|
| 外部ディスプレイの空いている入力（HDMI か DisplayPort） | できる | ホストの画面が 3440×1440、85 Hz 以上で動けば、判定と同じ絵を出せる見込み。ディスプレイが Air の入力を映しているあいだも、Mac mini から「つながっている」と見えるかは、機材しだい（未確認）。**まず、これを試す** |
| ダミープラグ（HDMI の口に挿す、画面のふりをする小さな部品） | できない（別に画面が要る） | 出せる解像度とリフレッシュレートは、部品しだい。買う前に、手順 0 の結果を見る |
| 何もつながない | できない | macOS が自分で用意する画面は 1920×1080 になる、という報告がある（未確認）。そのままでは、3440×1440 の絵は出せない。仮想ディスプレイを作る形（4.3 の B）なら、要らない見込み |

なぜホストの画面が効くか：macOS では、アプリの絵は、その窓が載っている画面の解像度とリフレッシュレートで作られる見込みです（4.2 の 2。手順 1 で確かめます）。

### 3.6 OS の許可：何を、なぜ求めるか

「システム設定」の「プライバシーとセキュリティ」にある項目です。

| 許可 | どの Mac で | 何のために | 出し方と注意 |
|---|---|---|---|
| 画面収録とシステムオーディオ録音 | Mac mini | アプリの窓の絵を読む（ScreenCaptureKit）。これがないと、絵が1枚も取れない | 管理者の認証が要る。macOS 15 以降は、許可を定期的に確かめ直す画面が出る（2024 年の報道では、月に1回。26 系での動きは、実機で確かめる） |
| 同上 | Air | 計測の道具が、2つの窓の中央の明るさを読む（ADR 0008）。製品には入れない | 出してある |
| アクセシビリティ | Mac mini | 1. キーボードとマウスの入力を、アプリに届ける（CGEvent）。2. アプリの窓を動かす、大きさを変える、前面に出す。3. 形によっては、メニューを読む（4.3） | 管理者の認証が要る。Air には要らない |
| システムオーディオ録音のみ | Mac mini | アプリの音を取る（Core Audio のタップ。ADR 0005） | 最初に録り始めたときに、macOS が尋ねる。プログラムに説明文（`NSAudioCaptureUsageDescription`）が要るので、アプリの形（バンドル）にする必要がある見込み |
| ローカルネットワーク | 両方 | LAN の相手につなぐ。mDNS で相手を見つける | ターミナルや SSH から起動したコマンドには、macOS が自動で許す。アプリとして起動するもの（Air の受信側）と、launchd のエージェントには、人の許可が要る。ユーザーごとに別に持つ |

求めないもの：root、フルディスクアクセス、入力監視。クライアントの Air は、自分の窓に来たキーとマウスを送るだけなので、入力のための許可は要りません。

注意：

- **AGENTS.md は、権限の要る処理を増やすときに、理由を ADR に残すよう求めています。** ADR 0008 が扱うのは、計測のための画面収録だけで、「製品には入れない」と書いてあります。Mac ホストのための許可には、別の ADR が要ります（6. の 1）。上の表は、その下書きです。**ADR ができるまで、Mac mini で画面収録とアクセシビリティを使うコードは書きません。**
- 許可は、プログラムの署名に結び付きます。署名なし（その場かぎりの署名）でビルドすると、ビルドのたびに別のプログラムとみなされて、許可が消えます。開発のあいだは、起動するターミナルに許可を出す形から始めます（ADR 0008 と同じ理由）。ただし、そのターミナルから起動したものは、どれも画面を読めて、入力を送れるようになります。あとで、決まった署名の付いたアプリに移します（6. の 1 と 7）。**製品では、使う人にターミナルを使わせません。** 署名したアプリが、最初の起動のときに、許可を案内します（手順 7）。
- 許可のダイアログは、遠くから押せないことがあります。人が、Mac mini の前か、macOS の「画面共有」で応えます。
- SSH から起動したプログラムが、画面を読めて、入力を送れるかは、分かりません（手順 0 で確かめる）。だめなら、Mac mini のターミナルで起動します。

### 3.7 ペアリング

2台とも、同じ LAN に有線でつないでから行います。

```sh
# Mac mini：コードと、Air で打つコマンドが表示される
istesso pair host

# Air：表示されたコマンドをそのまま実行する（アドレスは、Mac mini の有線のもの）
istesso pair join <Mac mini のアドレス> <コード>

# 両方で、エージェントを動かしたままにする
istesso agent

# Air から
istesso hosts
```

- [ ] `istesso hosts` に、Mac mini が「動いている」と出る。
- [ ] 相手のアドレスが、有線のものになっている。Wi-Fi のアドレスが選ばれていたら、`istesso peers address <名前> <有線のアドレス>` で指定する。
- コードとアドレスとホスト名は、記録や公開する文書に書きません。
- 新しくペアリングした端末の権限は「閲覧」と「操作」です（[ADR 0006](adr/0006-pairing.md)）。音を試す段階で、音の権限を別に与えます。

### 3.9 Mac mini の調査と、準備の一覧（2026-11-17）

SSH から、読むだけで調べました（Mac mini の時計で 09:22〜09:36）。

| 項目 | 分かったこと |
|---|---|
| 機種、OS | Mac mini（Apple M4）、メモリー 16 GB、macOS 26.7.1。Air（26.5.1）と同じ系 |
| ログインの状態 | 人がログインしている。画面はロック中、ディスプレイはスリープ中。M4 が動くべき状態（4.4）そのものである |
| FileVault、自動ログイン | FileVault は入っている。自動ログインは切れている。どちらも、変えない |
| 眠り | 人が動かしている `caffeinate` で、眠りが止まっている。ネットワークから起こす設定は、入っている。画面のロックは、1 時間で掛かる設定 |
| 省エネ | 低電力モードは、切れている（`pmset -g` の `lowpowermode 0`。13:35 に読んだ。朝の計測のときには読んでいない） |
| エンコーダーの数 | ハードウェアのビデオエンコーダーは、1 つ（I/O Registry に、`AppleAVE2Driver` が 1 つだけある。13:35 に読んだ）。ProRes の部品は、別に 1 つある |
| 共有 | SSH と、画面共有が入っている |

#### 許可の出し方（人の一覧。2026-11-17）

ADR 0017 の採用の条件 1 のとおり、Mac mini のいまのユーザーで進めます。人が「許可を出した」と言うまで、許可を使うコードは動かしません。許可を受けるのは、確認のプログラム「Istesso Lock Check」1 つだけです（ターミナルや SSH の入口には、まだ出しません）。

| 手順 | 画面 | 許可を受けるもの | これで動かせるもの |
|---|---|---|---|
| 1 | （ロックを外す前に）エージェントが、Mac mini で Istesso のプログラムが 1 つも動いていないことを確かめて、知らせる。人は、それを聞いてからロックを外す | — | パスワードを打つあいだ、画面を読むものが何もない |
| 2 | 「システム設定」>「プライバシーとセキュリティ」>「画面収録とシステムオーディオ録音」。上の段（画面とシステムオーディオ）の「+」を押す | 「Istesso Lock Check」。作業用のフォルダー `~/.cache/istesso-m4-wip/` の中にある。隠れたフォルダーなので、選ぶ画面で ⌘⇧G を押して、その場所を打つ。管理者のパスワードが要る。「終了して再度開く」と聞かれたら「あとで」（動いていない） | 手順 0b の取り込みの側。取り込みの速さの確認（手順 1 の初め）。仮想ディスプレイの小さな試し（4.3 の B） |
| 3 | 同じ「プライバシーとセキュリティ」>「アクセシビリティ」の「+」 | 同じ「Istesso Lock Check」 | 手順 0b の入力の側（何も打ち込まないキー F13、ポインターの移動、クリックを、そのプログラムの自分の窓へ送る） |
| 4 | 「システム設定」を閉じる。画面をロックして、離れる | — | エージェントに「許可を出した」と伝える。ここから、エージェントが手順 0b を始める（ロックを外してもらう場面は、0b の手順で、そのつど知らせる） |

注意：

- 許可は、そのプログラムの、いまのビルドに結び付きます（署名がその場かぎりのため）。**許可を出したあとは、このプログラムを作り直しません。** 作り直すときは、先に知らせて、2 と 3 をやり直してもらいます。いま Mac mini にあるのは、2026-11-17 14:05（Mac mini の時計）に写したビルドです（古いビルドは、同じフォルダーで名前を変えて残してあります。許可を出すのは、名前が「Istesso Lock Check」のものだけ）。
- 手順 1 から先の Rust のプログラム（取り込みを測る、1 本通す）に、どの形で許可を出すかは、手順 0b の答え（SSH から起動したものが画面を読めるか、を含む）が出てから決めて、同じ形の表で、もう一度渡します。
- 音の録音の許可（手順 6）と、ローカルネットワークの許可は、この表に入っていません。要るときに、別に渡します。

## 4. macOS で「1アプリ = 1仮想ディスプレイ = 手元の1窓」は何を意味するか

R-02 は、アプリごとに仮想ディスプレイを割り当てると決めています。Linux のホストでは、そのとおりの形で動いています。macOS では、同じ形にならないところがあります。

### 4.1 Linux との違い

| | Linux のホスト（いま動いている形。ADR 0009） | macOS のホスト |
|---|---|---|
| アプリの絵の出どころ | アプリごとに専用のコンポジターを起動する。出力の大きさとフレームレートは、クライアントの窓に合わせて決める | ログインしているセッションの画面。macOS が合成したものを、ScreenCaptureKit で読む |
| 仮想ディスプレイ | コンポジターの出力が、それにあたる | 公開の API では作れない |
| 入力 | コンポジターに直接渡す。アプリごとに、別のポインターとフォーカスを持つ | セッションに、カーソルが1つ、フォーカスが1つ。入力を注入すると、ホストの本物のカーソルが動く |
| メニュー | 窓の中にある | 画面のいちばん上のメニューバーにある（窓の外） |
| 誰もデスクトップにログインしていないとき | 動く見込み。デスクトップのセッションとは別に動く | 動かない。アプリは、ログインしているセッションの中でしか動かない。再起動のあとに、1回ログインが要る（4.4） |
| 権限 | root は要らない | 画面収録、アクセシビリティ、音の録音。どれも人の操作が要る |

### 4.2 できることと、できないこと

公開の API でできること（文書で確かめた。実機での確認は、これから）：

- アプリの窓1枚だけを取り込む。または、ある画面のうち、アプリ1つの窓だけを取り込む。ほかのアプリの窓は、絵に入らない。
- カーソルを絵から外す。クライアントが手元で描ける（R-02）。
- アプリの音だけを取る。取っているあいだ、ホストのスピーカーから鳴らさないこともできる。
- アプリの窓の位置と大きさを、外から変える（アクセシビリティの許可が要る）。

正直に言って、できないこと：

| # | できないこと | 起きること |
|---|---|---|
| 1 | アプリごとに、別のカーソルとフォーカスを持たせる | ホストの Mac を、配信中に人が直接使うと、カーソルとキー入力を取り合う。2台のクライアントが、同じ Mac の別々のアプリを同時に操作することもできない。**Mac のホストは、1人が1台を使う形になる** |
| 2 | 公開の API で、仮想ディスプレイを作る | 絵の解像度、拡大率、リフレッシュレートは、ホストの画面のものになる。クライアントの窓に合わせて変えられない |
| 3 | 誰もログインしていない Mac で、アプリを動かす | アプリは、ログインしているセッションの中でしか動かない。**再起動のあとは、人が1回ログインするまで、ホストとして使えない。** 今回の制約である（4.4） |
| 4 | OS の許可のダイアログを、中継した窓から押す | 人が、その Mac の前か、macOS の「画面共有」で応える。安全のための仕組みなので、回り道は作らない |
| 5 | 許可を、人の操作なしに保ち続ける | 画面収録は、定期的に確かめ直される（3.6）。ホスト専用の Mac では、気づかないうちに絵が止まるおそれがある。避けるための Apple の許可（VNC アプリ向け）は、申請が要る（6. の 7） |
| 6 | トラックパッドのジェスチャー（ピンチ、スワイプ）を注入する | 公開の方法が見当たらない。スクロールとクリックとドラッグは送れる |

分かっていないこと（手順 1 と 4 で確かめる）：ほかの窓に隠れた窓、最小化した窓、別の操作スペースにある窓を取り込めるか。メニュー、ポップアップ、保存のパネルが絵に入るか。パスワードの入力欄に、注入したキーが届くか。画面がロックされているあいだ、取り込みと入力がどうなるか（4.4）。カーソルの形を読めるか（読むための API は、Apple の文書の上では macOS 27.0 までになっている）。

### 4.3 選べる形

| | A：窓を切り出す | B：アプリごとに仮想ディスプレイを作る |
|---|---|---|
| やり方 | アプリの窓を、ホストの画面に置いたまま、その窓だけを取り込む | クライアントの窓と同じ大きさ、同じリフレッシュレートの画面を作り、アプリの窓をそこへ動かして、画面ごと取り込む |
| API | 公開のものだけ | 仮想ディスプレイを作る部分が、**非公開の API**（`CGVirtualDisplay`）。Apple の文書にない |
| R-02 との関係 | 仮想ディスプレイはない。「1アプリ = 手元の1窓」だけを満たす | 言葉どおりに満たす |
| 絵の大きさとリフレッシュレート | ホストの画面で決まる。3440×1440 の 85 Hz で測るには、ホストの画面がそれを出せること | クライアントに合わせられる見込み（未確認） |
| メニューバー | 窓の外にあるので、絵に入らない。別に運ぶ仕組みが要る（メニューバーの帯を一緒に取り込むか、メニューを読んで手元のメニューバーに出す） | 画面ごと取り込むので、絵に入る見込み（未確認） |
| メニュー、ポップアップ、2枚目の窓 | 子の窓を含める指定がある。どこまで入るかは、確かめる | その画面に出るものは、入る |
| 壊れやすさ | OS の更新に強い | OS の更新で、予告なく動かなくなり得る。Mac App Store には出せない。公証（M9）に通るかは、未確認 |
| 権限 | 画面収録、アクセシビリティ | 同じ |

どちらでも変わらないもの：4.2 の「できないこと」の 1、3、4、5、6。

もう1つ、**C：ログインしているセッションの画面を、丸ごと1つ出す**形があります。R-02 の形ではありませんが、いちばん単純で、取り込みと圧縮の数値を取るのに使えます。macOS の「画面共有」と同じ形なので、基準として比べる相手にもなります。

**進め方：手順 1〜3 は A と C で測る。手順 5 は、A で先に作る。その間に B を小さく試して、B を製品に入れるかどうかを ADR で決める（6.2 の 2）。** B の決定を待って止まるところは、作りません。理由は3つあります。

1. 取り込みと圧縮の数値は、どの形でも要る。A と C は、決定を待たずに測れる（ねらい：待たずに確かめる）。
2. B を採っても、動かなくなったときの戻り先として A が要る。A を先に作っても、むだにならない。
3. B は、R-02 に合い、メニューと解像度の問題をまとめて解く見込みがある。ただし、非公開の API に製品を載せることになる。これは、このプロジェクトでまだ決めたことのない種類の危うさで、ねらいからは決まらない。人が決める。

決めるときの物差しは、背景から来ます。使い手は開発者に限らないので、導入のかんたんさと、説明なしで使えることを重く見ます。

| 物差し | A：窓を切り出す | B：仮想ディスプレイを作る |
|---|---|---|
| 導入に、余分な物が要らない | ホストの Mac に、画面をつなぐか、ダミープラグを挿すことになるかもしれない（手順 0 で分かる） | 要らない見込み |
| 説明なしで使える | メニューを運ぶ仕組みができるまで、メニューが使えない | メニューが絵に入る見込み |
| 入れたあとで、急に動かなくならない | 公開の API なので、強い | OS の更新で止まり得る。公証に通らなければ、導入そのものができない |

### 4.4 誰も座っていないホスト

2026-11-16 に、2つのことが決まりました。

1. **ホストは、画面の前に誰も座っていない状態がふつうである。** 各流れの受け入れ条件に、「ホストを起動した直後（ログイン画面のまま、SSH だけ）の状態で動く」を足す。動かないものは、理由と、インストーラー（M9）が何を入れれば動くかを書く。
2. **Mac のホストは、今回は、「人がログインしておく」形にする。** ねらいは、導入した人に、ディスクの暗号化を切らせる作りを、既定にしないことである。Mac mini の FileVault は、切らない。

Mac のホストでは、1 の条件を、次のように読み替えます。

- **ログイン済みで、画面をロックした状態で、動くこと。**
- **スリープから起こした直後の状態で、動くこと。**

今回の制約：**Mac のホストは、再起動のあとに、人が1回ログインするまで、使えません。** 理由は2つあります。Mac のアプリは、誰かがログインしているセッションの中でしか動きません。FileVault が入っている Mac は、起動のあと、人が解除するまで、ディスクを読めません。ログインするまでのあいだ、その Mac は、ほかの端末から、止まっているホストと同じに見えます（その Mac にしかないアプリに「！」が付く）。

分かっていることと、Mac mini で試すこと：

| Mac の状態 | 今回の扱い | 分かっていること | Mac mini で試すこと |
|---|---|---|---|
| ログインしていて、画面がロックされている | **動くこと（条件）** | アプリは動き続ける。取り込みが続くか、入力がアプリに届くかは、分かっていない。この文書の前の版は「できない」と書いていたが、確かめていなかった | ロック中に、窓の取り込みが続くか。入力が、アプリに届くか、ロックの画面に行くか。ロック中に、新しいアプリを開けるか |
| ログインしていて、眠っていた。起こした直後 | **動くこと（条件）** | ネットワークから起こせる（設定しだい）。起きたあとは、ロックされた状態か、ロックのない状態になる | ネットワークから起こせるか。起きた直後に、窓が開くか。眠る前に開いていた窓に、戻れるか |
| 再起動した直後。ログイン画面、または FileVault の解除待ち | 動かない（制約） | 上のとおり。Apple シリコンの macOS 26 以降では、リモートログインを入れてあれば、FileVault を SSH で解除できる（Apple の文書）。解除しても、ログインは別に要る | 試さない。再起動したら、人が1回ログインする |

条件の状態で動かないものが見つかったら、理由と、インストーラーが何を入れれば動くかを、記録に書きます。たとえば、ロック中に取り込みが止まると分かったら、何を設定すれば続くかを調べて、使う人が失うものと一緒に書きます。

インストーラー（M9）が入れるもの、伝えること：

- ホストの役の部分（エージェント、取り込み、入力、音）を、ログインのときに起動するように登録する。権限は要らない。
- 配信しているあいだは、眠らせない（権限は要らない）。使っていないあいだは、眠ってよい。ネットワークから起こす設定を、案内する。
- 導入のときに、「再起動のあとは、1回ログインしてください」と伝える。Istesso は、ディスクの暗号化を切らない。切るようにも勧めない。

自動ログインについて：macOS には、起動のときに、決めたユーザーで自動的にログインする設定があります。これを入れると、再起動のあとのログインが要らなくなります。ただし、FileVault を切らないと使えません（Air で確かめた）。その Mac を持ち去られると、中身を読まれます。**使う人が、自分で選べる設定です。Istesso は、この設定を入れませんし、勧めません。今回は、試しません。**

ログイン画面を中継して、手元の窓からログインする形は、将来の項目に残しました（[milestones.md](milestones.md)）。ログイン画面の中で root で動く部品が要り、パスワードが中継の経路を通るので、取りかかる前に ADR が要ります。

### 4.5 絵の大きさ：ホストの画面が、上限になる

**制約：公開の API では、Mac のホストが出せる絵の大きさは、そのホストの画面が選べるいちばん大きいモードまでである。** 大きい画面をつなぐほかに手がないかを、公開の API の範囲で調べました（2026-11-17）。非公開のインターフェースは、候補に入れていません。

| 候補 | 使えるか | 理由と、出どころ |
|---|---|---|
| 画面のモードを、大きいものに切り替える（HiDPI のモードを含む） | 使える。ただし、その画面が持っているモードまで | macOS は、画面ごとに、選べるモードの一覧を持っている。見た目の大きさの 2 倍の画素で描くモード（HiDPI）もある。Mac mini のいまのディスプレイでは、いちばん大きくて 2048×1152 だった（`examples/displays.rs` で読んだ）。切り替えは、使う人の画面の設定を変えることになる |
| 窓を、画面より大きくして、窓だけを取り込む | **分からない。試す価値がある** | 窓だけを取り込むフィルターは、画面に関係なく窓を取る、という名前である。一方で、タイトルバーのある窓は、自分で画面の中に収まる、と Apple の文書にある。アプリの窓を外から画面より大きくできるか、はみ出た部分が絵に入るかは、文書にない。画面の外にある窓は、フレームが届きにくい、という報告が 1 件ある（返事なし）。確認のプログラムに、自分の窓で試す項目を入れた（`--oversize`） |
| 取り込みの出力を、大きく指定する（拡大） | 使えない | 出力の大きさは指定できるが、引き伸ばすだけで、絵の中身は増えない |
| ディスプレイをつながない | 使えない見込み | macOS が自分で用意する画面は 1920×1080 になる、という報告がある（未確認）。それより大きくは、ならない |
| HDMI のダミープラグ | 使える（API ではなく、部品） | 画面のふりをする小さな部品。出せるモードは、部品しだい。大きい画面より安いが、買い物が要る |
| ほかの機器を、画面として使う（AirPlay、Sidecar） | 実用にならない | 相手の機器が要る。絵が、もう 1 回、別の仕組みで圧縮される |
| ドライバーとして、仮想の画面を作る（DriverKit） | 使えない | Apple の個別の許可が要る、とされる（未確認）。各自がビルドする OSS では、取れない |
| 仮想ディスプレイを作る非公開の API | 候補に入れない | 4.3 の B。入れるかどうかは、人が決める（6.2 の 2） |

読み取れること：

- 大きい画面を持っていない人のホストでは、絵は、その画面のいちばん大きいモードまでになる。クライアントの窓がそれより大きいときは、引き伸ばして映すか、余白を付けることになる。
- 「窓を画面より大きくする」が動けば、この制約は外れる。許可がそろったら、手順 0b の中で確かめる。
- **大きさだけでなく、毎秒の枚数も、ホストの画面で頭打ちになるかもしれない**（2026-11-17 に人が挙げた点）。Mac mini の画面は、いま 60 Hz である。取り込みが画面のリフレッシュレートで頭打ちになるなら、判定の毎秒 85 枚は、85 Hz 以上の画面か、仮想ディスプレイ（4.3 の B）がないと出せない。そのときは、B は便利なものではなく、**前提**になる。確かめ方は、手順 1 の初めの「取り込みの速さ」。
- 役割表（`istesso doctor`）に、ホストが出せるいちばん大きい絵を載せる。起動先を選ぶときと、使う人に伝えるときに使う。

### 4.5b 配信のあいだ、ディスプレイを点けておく（設計。2026-11-17）

手順 0b で、ロック中でもディスプレイが点いていれば取り込めること、スリープすると、物の画面でも仮想ディスプレイでも何も届かないことが分かった（[記録](measurements/2026-11-17-m4-capture-locked-mac-mini.md)）。だから、端末がセッションを映しているあいだは、ホストがディスプレイを点けておく。

| こと | 決め方 |
|---|---|
| 主張 | `IOPMAssertionCreateWithName` の `PreventUserIdleDisplaySleep`（`caffeinate -d` と同じ）。名前は「Istesso: a device is shown a session」。権限も sudo も要らない |
| 点けるとき | 最初の端末が、セッションを映し始めたとき（`FrameSink::viewed` が真になったとき）。眠っているディスプレイは、この主張では点かないので、そのときだけ「使っている」の合図（`IOPMAssertionDeclareUserActivity`。`caffeinate -u` と同じ）を 1 回出す |
| 外すとき | 最後の端末が離れて 10 秒たったとき。プログラムが終われば、OS が外す（主張は、出したプロセスに結び付く） |
| ロック | 変えない。点いたディスプレイには、ロックの画面だけが映る見込み。**アプリの中身が映らないことを、人が見て確かめる**（今夜の手順の 1）。映るなら、この設計は使えない |
| 電力 | 物のディスプレイが点いたままになる。その電力（ふつうのモニターで十数〜数十 W。見積もり）は、Mac からは読めない。Mac mini 自身の増え方も、sudo がないと読めない。物のディスプレイをつながないホスト（仮想ディスプレイの形）で要るかは、ケーブルを抜く手順で分かる |
| 切る設定 | 起こしておく形（6.1b の F）と同じ設定で切れるようにするかは、決めていない |

### 4.6 ロックした画面のうしろ：文書にあることと、ほかの人の報告

Mac のホストは、「ログイン済みで、画面をロックした状態」で動くことが条件です（4.4）。公開の文書が何を言っているかを調べました（2026-11-17）。

| 問い | Apple の文書 | ほかの人の報告（確かめていない） |
|---|---|---|
| ロック中に、窓の絵を取り込めるか（ScreenCaptureKit） | **書かれていない。** フレームワークの文書も、見本のコードの説明も、ロックにも、ディスプレイのスリープにも触れていない | ディスプレイがスリープしているあいだは、窓の静止画を取れない、と Apple の技術者が開発者フォーラムで答えている（1 回だけ取る機能についての答え。流れで取る場合には触れていない）。同じ質問者は、窓の中身を自分で描き出す方法なら取れた、と書いている |
| ロック中に、入力を届けられるか（CGEvent） | **書かれていない。** イベントを送る機能の文書は、ロックにも、ログイン画面にも触れていない | ロック画面では動いた、ログイン画面（ログアウトしたあと）では動かなかった、という報告がある。ログインの前は、信用されていないアプリは窓の仕組みにつなげない、という記録もある。ロック中に送った入力が、うしろのアプリに届くのか、ロックの画面に届くのかを書いたものは、見つからなかった |
| スリープから起こした直後 | 書かれていない | 見つからなかった |
| ログイン画面での取り込み | 書かれていない | ログイン画面の中で動く部品からなら、macOS 14.4 以降でできる、と Apple の技術者が答えている（将来の項目の、ログイン画面の中継にあたる） |

つまり、**条件が成り立つかどうかは、文書からは分からない。実機で確かめるしかない。** そのための確認が、手順 0b です。

成り立たなかったときに、要るものと、その引き換え：

| 分かったこと | 代わりに要るもの | 引き換え |
|---|---|---|
| ロック中は、取り込みが止まる | 配信しているあいだ、画面をロックさせない（眠りを止めるのと同じ仕組みで、ロックまでの時間を止める）。使っていないあいだは、ロックしてよいが、次に使い始めるときに、人がロックを外す必要が出る | ホストの Mac の前を通った人が、画面を見られる。使い始めに、人の手が要るなら、「誰も座っていないホスト」の条件を満たさない |
| ロック中は、入力がうしろのアプリに届かない | 同じ | 同じ |
| ディスプレイがスリープすると、取り込みが止まる | 配信しているあいだ、ディスプレイをスリープさせない（権限は要らない） | 画面が点いたままになる。ディスプレイをつないでいないホストでは、関係がない |
| 起こした直後は、数秒、絵が出ない | 待つ。手元の窓に「起こしています」と出す | 使い始めが、数秒遅れる |
| どれも成り立たず、ロックを外したままにするしかない | Mac のホストは、「ロックしない Mac」に限る、と要件に書く。それを選ぶのは、使う人 | 「ログイン済みで、画面をロックした状態で動く」という条件（4.4）を、満たせなくなる。人に決め直してもらう |

## 5. 手順

手順ごとに、結果を `docs/measurements/` に記録します。ホスト名、アドレス、ユーザー名は書きません。

記録の条件には、いつも次を書きます（2026-11-17 に決まった）：

- Mac の状態（ログイン、ロック、ディスプレイのスリープ）と、省エネの設定（低電力モードが入っているか。`pmset -g` の `lowpowermode`。読むだけ）。
- **つなぎ直しの回数。** 絵、入力、音のそれぞれが、計測のあいだに何回つなぎ直したか。あとで作る窓にも出す。**0 でない回があったら、その値を使う前に、人に知らせる。** 経路がまだない計測（エンコーダーだけ、など）では、「経路なし」と書く。

### 手順 0：準備と調査

許可の要らない範囲だけを調べます。

- 両方の Mac で `istesso doctor` を実行し、3.8 の表と比べる。
- 2台の間の往復時間の分布を、有線のアドレスで測る（[measurements/README.md](measurements/README.md) の「経路そのものの遅れ」）。
- Mac mini の画面を調べる（`system_profiler SPDisplaysDataType`）。映像の出力のつなぎ先ごとに、選べる解像度とリフレッシュレートを記録する。Air の入力に切り替えたあとも、同じかを見る。
- Mac mini で起動したプログラムの優先度を見る（`ps -M`）。SSH から、ターミナルから、`open` からの3通り。Air では、エージェントのシェルから起動したものが低い優先度で動き、時刻がずれた（M1 の記録）。
- 誰も座っていない状態にかかわる設定を、読むだけで調べる（4.4）：FileVault（`fdesetup status`）、自動ログイン（`sysadminctl -autologin status`）、眠りと、ネットワークからの起床（`pmset -g`）、画面のロックまでの時間。どれも変えない。

確かめ方：

- [ ] 役割表が、3.8 の表のとおりである。
- [ ] 経路の往復が、M1 の有線の値（ネットワークの区間が平均 1.0 ms）と同じ程度である。
- [ ] ホストの画面を 3440×1440、85 Hz 以上で動かせるかどうかが、分かっている。
- [ ] Mac mini の、眠りとロックの設定が、記録にある。ネットワークから起こせる設定になっているかが、分かっている。

### 手順 0b：ロックしたまま動くか（許可がそろったら、いちばん先に）

Mac のホストの前提（4.4）を確かめます。ここが成り立たないと、前提が変わるので、ほかの確認より先に行います。準備の一覧（3.9）の 4 と 5 が要ります。

道具は `macos/lock-check`（Swift）です。**ビルドはしてありますが、まだ1回も動かしていません**（動かすには、許可が要るため）。

- 自分の窓を 1 枚開く。窓は、0.5 秒ごとに色を変える。
- その窓だけを取り込む（ScreenCaptureKit）。取り込んだ絵のまん中の色が、窓の色のとおりに変わっていくかを見る。
- その窓に、何も打ち込まないキー（F13）と、ポインターの移動と、クリックを送る（CGEvent）。窓がそれを受け取ったかを見る。パスワードの欄には、何も入らない。
- Mac の状態（ロック、ディスプレイのスリープ、起こした直後）を自分で見分けて、状態ごとに 1 回ずつ試す。答えを、作業用のフォルダーの `lock-check-report.txt` に書く。
- 許可がないときは、何も取り込まず、何も送らず、どの許可が足りないかを書く。許可を求める問いは、`--ask` を付けて起動したときにだけ出す。

進め方（人の合図のあとで）：

1. Air で `macos/lock-check/build.sh` を実行して、できたアプリを Mac mini の作業用のフォルダーへ写す（済み。2026-11-17 14:05 に、取り込みの速さと仮想ディスプレイの確認を足したビルドに替えた。許可を出したあとは、作り直さない）。
2. 人が、3.9 の「許可の出し方」の表のとおりに、許可を出す。人が「許可を出した」と言うまで、3 から先は始めない。
3. 人が、ロックを外したままにしておく（パスワードを打ち終えてから）。エージェントが、Mac mini で、アプリを `open` で起動する。ロックしていない状態が、まず試される（道具そのものの確認。5 秒ほど）。
4. 人が、画面をロックする。そのまま 10 秒待つ。ディスプレイがスリープするまで待つ（いまの設定で 10 分）。
5. Mac mini を眠らせて、起こす。眠らせるのは `pmset sleepnow`（権限は要らない）。起こし方は、手順 7 の「眠らせて、起こす」と同じ（LAN ケーブルが要る。まだなら、人がキーを押して起こす）。
6. 3 つのロックの状態を試し終えると、アプリは、取り込みを止めて、自分で終わる（60 分たっても終わる）。**エージェントが、アプリが終わったことを確かめて知らせてから、人がロックを外す。** パスワードを打つあいだ、画面を読むものは動いていない。
7. 報告（`lock-check-report.txt`）を読む。

答えが出る項目（どれも、はい・いいえ）：

- [ ] ロック中に、窓の絵が取り込める。絵が、窓の変化に付いてくる。
- [ ] ディスプレイがスリープしても、同じである。
- [ ] スリープから起こした直後に、取り込める。
- [ ] ロック中に、キーが、うしろのアプリに届く。
- [ ] ロック中に、ポインターの移動とクリックが、うしろのアプリに届く。
- [ ] （参考）画面より大きい窓が、はみ出た部分ごと取り込める（`--oversize`。4.5）。

「いいえ」が 1 つでもあれば、何が要るかと、その引き換え（4.6 の表）を添えて、人に知らせます。ほかの手順へ進む前にです。

この確認では分からないこと：自分の窓で試すので、ほかのアプリの窓でも同じかは、手順 1 と 4 で見る。ロックを見分けるのに使う値（セッションの状態の「画面がロックされている」）は、公開の関数で読めるが、値の名前は Apple の文書にない。

### 手順 1：取り込みを測る

ここから、画面収録の許可が要ります。6. の 1 の ADR が先です（2026-11-17 に採用）。

**初めに、取り込みの速さが、ホストの画面のリフレッシュレートで頭打ちになるかを見ます**（4.5。2026-11-17 に人が挙げた点）。道具は、手順 0b と同じ確認のプログラムで、新しい許可は要りません。準備はできています（ビルドして、Mac mini に写してある。動かしていない）。

```sh
# Mac mini で（エージェントが SSH から。計測の合図が free のときだけ）。30 秒ほどで、自分で終わる
open -W "$HOME/.cache/istesso-m4-wip/Istesso Lock Check.app" --args --rate
cat "$HOME/.cache/istesso-m4-wip/rate-check-report.txt"
```

- 自分の窓を 1 枚開く。窓は、画面が 1 枚出すたびに色を変える（`CADisplayLink`。毎秒 240 枚まで求める）。
- その窓だけ（形 A）を、続けて画面ごと（形 C）を、それぞれ 10 秒取り込む。取り込みには、毎秒 240 枚まで求める。始めの 2 秒を除いた 8 秒で、届いた枚数と、窓が描いた回数を数える。絵は残さない。
- 報告：画面のモード（大きさとリフレッシュレート）、毎秒の取り込みの枚数、毎秒の描いた回数、フレームの大きさ。
- 読み方：取り込みの枚数が、窓の描いた回数と同じで、画面のリフレッシュレート（60）を超えないなら、頭打ちである。そのときは、**4.3 の B の小さな試しを、手順 1 のすぐあとに行う**（下の「仮想ディスプレイの小さな試し」）。85 Hz の画面がないかぎり、判定の毎秒 85 枚は、B が前提になる。
- 画面ごとの取り込み（形 C）は、計測のためだけに使う（ADR 0017 の守ること 2）。画面に、個人のデータが映っていそうなら、動かさない。画面がロック中なら、ロックの画面が映る。

- テストアプリ（`istesso-flash`）を Mac mini で動かし、ScreenCaptureKit で取り込む。形は A（窓だけ）と C（画面ごと）。
- 測るもの：アプリが絵を確定してから、フレームが届くまでの時間。1秒に届く枚数。どちらも Mac mini の時計の中で閉じる。
- 設定を1つずつ変える：フレームの間隔の下限、待ち行列の深さ、絵の形式、カーソルを外す指定。
- 窓の状態を変えて、取り込めるかを表にする：ほかの窓の下、最小化、別の操作スペース、フルスクリーン、画面のスリープ、画面のロック（4.4）。
- 絵に入るものを表にする：メニュー、右クリックのメニュー、ポップアップ、保存のパネル、日本語入力の候補、2枚目の窓。
- ホストの画面のリフレッシュレートを変えて、待ちがどう変わるかを見る。リフレッシュレートを上げると、合成の待ちは縮む見込み。これを判定で使ってよいかは、ADR 0002 の「毎秒 85 枚を超えない」に照らして、M1 の流れと決める。

確かめ方：

- [ ] 取り込みの区間の中央値と 95 パーセンタイルが、3440×1440 と 1720×720 で記録にある。
- [ ] 毎秒 85 枚で届くかどうかが、分かっている。
- [ ] 取り込める窓と、絵に入るものの表がある。

### 仮想ディスプレイの小さな試し（4.3 の B。手順 1 のすぐあと）

2026-11-17 に、進め方が決まりました：A で作り、B を小さく試し、そのうえで ADR で決める。試しは、今週行ってよい。製品に入れるかどうかは、人が決める（6.2 の 2）。

取り込みの速さが画面のリフレッシュレートで頭打ちなら（手順 1 の初め）、この試しは、手順 1 のすぐあとに行います。準備はできています（ビルドして、Mac mini に写してある。動かしていない）。許可は、表の 2（画面収録）だけを使います。

```sh
# Mac mini で（エージェントが SSH から）。40 秒ほどで、自分で終わる。仮想ディスプレイは、終わるときに消える
open -W "$HOME/.cache/istesso-m4-wip/Istesso Lock Check.app" --args --virtual-display 3440x1440@85
cat "$HOME/.cache/istesso-m4-wip/virtual-display-report.txt"
```

- 非公開のクラス（`CGVirtualDisplay`）で、3440×1440、85 Hz、HiDPI なしの画面を 1 枚作る。宣言は `macos/lock-check/virtual-display.h`。Objective-C のランタイムが自分で示すクラスの中身（プロパティとメソッドの一覧）から書いた。ほかのプロジェクトのコードは、読んでいない。
- 画面の一覧に現れるまでの時間と、現れたときのモードを記録する。
- 自分の窓だけを、その画面いっぱいに置く。**ほかのアプリの窓は、動かさない。** 手順 1 の初めと同じ数え方で、窓だけ（A）と、画面ごと（C）の毎秒の枚数を数える。
- 終わったら、画面を消して、消えたかを記録する。

答えが出る項目：

- [ ] 作れるか。求めた大きさと、85 Hz になるか。
- [ ] その画面の上で、取り込みが毎秒 85 枚に届くか。フレームの大きさが 3440×1440 か。
- [ ] 消したあと、画面の並びが元に戻るか。

この試しでは分からないこと：ほかのアプリの窓を移したときの動き（アクセシビリティが要る。手順 5 で、A のあとに見る）、公証（M9）に通るか、OS の更新で止まらないか。

画面の並びが一時的に変わる（ディスプレイが 1 枚増える）ので、人がその Mac を使っているときには動かしません。

### 手順 2：圧縮を測る

[ADR 0002](adr/0002-latency-first.md) は、圧縮を H.265 の 4:4:4 と決めています（`m1-latency` ブランチで決まったもの）。Mac のエンコーダーについて、分かっていることと、分かっていないことを分けます。

分かっていること（2026-11-16 に、Air で確かめた。Apple M4、macOS 26.5.1）：

- ハードウェアのエンコーダーを必須にした圧縮のセッションに、対応しているプロパティを尋ねた（`VTSessionCopySupportedPropertyDictionary`）。H.265 のプロファイルの一覧に、`HEVC_Main444_AutoLevel` と `HEVC_Main44410_AutoLevel` があった。ほかは、Main、Main10、Main42210、MainStill と、モノクロの2つ。
- ソフトウェアのエンコーダーの一覧は、Main、Main10、MainStill、モノクロだけで、4:4:4 がなかった。
- 4:4:4 の絵（`kCVPixelFormatType_444YpCbCr8BiPlanarVideoRange`）を1枚、ハードウェアのエンコーダーに渡した。出てきたストリームの `general_profile_idc` は 4（範囲拡張）だった。
- つまり、**この Air では、4:4:4 をハードウェアで圧縮できる。** Apple の公開の文書にあるプロファイルの一覧には、4:4:4 が載っていない。文書ではなく、エンコーダーに尋ねること。

**Mac mini で測った結果（2026-11-17。[記録](measurements/2026-11-17-m4-encode-mac-mini.md)）：**

- Mac mini（Apple M4、macOS 26.7.1）のハードウェアのエンコーダーも、4:4:4 を持っている。出てきたストリームの `general_profile_idc` は 4 だった。**6.2 の 3 の問いは、要らなくなった。**
- 3440×1440、毎秒 85 枚で、1 フレームの圧縮は、中央値 8.8 ms、99 パーセンタイル 9.2 ms。Linux のホスト（4.07 ms）より、約 4.7 ms 長い。半分の大きさ（1720×720）なら 3.0 ms。
- エンコーダーの「リアルタイム」の指定を入れると、28.7 ms になった。入れないことにした。低遅延のレート制御は、70 ms になった。使わない。
- 絵は、エンコーダーに BGRA のまま渡すのが、いちばん速い。色の変換を別の段にすると、2 ms 増える。
- Mac mini のハードウェアのビデオエンコーダーは、1 つ（I/O Registry に `AppleAVE2Driver` が 1 つ。読むだけで調べた）。絵を分けて 2 つのエンコーダーで圧縮する形（6.1b の B の (b)）は、Mac mini では試さない。

**まばらな入力（2026-11-17。[記録](measurements/2026-11-17-m4-encode-sparse-mac-mini.md)。6.1b の B の 1）：**

- 止まった画面に 1 文字、の 1 フレームは、0.1〜1 秒止まったあとで中央値 13.1〜13.3 ms、3 秒止まったあとで 15.2 ms。続けて渡す毎秒 85 枚（8.8 ms）より、4.5〜6.4 ms 長い。判定の測り方（入力 1 回につき 1 フレーム、約 0.43 秒おき）も、こちらに入る。
- 時間を決めるのは、渡す頻度である。続けて渡しても、毎秒 10 枚なら 13.0 ms、20 枚なら 8.9 ms。
- 何も変わらないあいだも、最後の絵を毎秒 20 枚以上渡す（エンコーダーを起こしておく）と、変化の 1 フレームは 8.7〜9.0 ms に戻る。3 秒止まったあとでも 8.8 ms。毎秒 10 枚では戻らない。
- 作りへの見込み（提案）：Mac のホストは、セッションのあいだ、最後の絵を毎秒 20〜30 枚渡し続ける。その同じ絵のフレームを送るかは、映像の経路（ADR 0015）と合わせて決める。手順 3 の 1 本通す経路に、この形を入れて測る。

**起こしておく形の、ぶつかりと引き換え（2026-11-17。[記録](measurements/2026-11-17-m4-encode-keep-awake-mac-mini.md)）：** 人は、向きはよいとして、採る前に測るよう求めた。

- 変化を、起こしておく拍にそろわない時刻（300〜600 ms の乱数の間隔）で、条件ごとに 396 枚渡した。同じセッションで毎秒 30 枚起こしておくと、中央値 8.93 ms、95% 12.71 ms、99% 13.96 ms。起こしておかないと、14.03 ms、15.39 ms、15.95 ms。ぶつかり（変化の 2〜3 割）を入れても、どの百分位でも短い。毎秒 20 枚でも、95% と 99% はほぼ同じ（12.65 ms、13.40 ms）。
- 別の小さなセッション（64×64、640×640）を毎秒 30 枚動かしても、本物のセッションは 13.0 ms のままだった。この形は採れない。
- 引き換え：起こしておくための絵は、毎秒 30 枚で約 58 kB/s、20 枚で約 41 kB/s。計測のプログラムの CPU は、約 2 % から、20 枚で約 17 %、30 枚で約 26 % に増える。チップの電力（ワット）は、sudo がないと読めない。
- 入力のあとに控える試し（[同じ記録](measurements/2026-11-17-m4-encode-keep-awake-mac-mini.md)の「入力のあとに控える」）：変化を入力の 2〜12 ms あとに来させて、条件ごとに 396 枚。入力のあと 50 ms、起こしておくための絵を控えると、ぶつかりが 72 枚から 16 枚に減り、95% は 12.98 → 11.54 ms、99% は 14.12 → 12.92 ms。中央値は 9.2 ms のまま。入力のない変化（絵が自分で変わる）には効かない。50 ms を採って、作りに入れる（`m4-keep-awake` ブランチ。PR の前に、とりまとめ役が見る）。
- **決まった（14:58。6.1b の F）：** 同じセッションで、毎秒 20 枚起こしておく。端末がセッションを映しているあいだだけ。設定で切れる（既定は入り）。起こしておくための絵も送る。**止まった画面に 1 文字打つと、Mac mini は 9 ms かかる。Linux のホストより約 5 ms 長い。**

まだ分かっていないこと：

- **画質。** ADR 0002 の3つの条件を、この設定で満たすかどうかは、測っていない。速さを優先する設定にしてある。
- 窓の取り込みと合わせたときの値（手順 3）。
- Mac Studio など、ほかの Mac での値。

Mac mini で行う確認（この順に）：

1. **ハードウェアのエンコーダーの、プロファイルの一覧を出す。** 尋ね方は、Air のときと同じにする。`HEVC_Main444_AutoLevel` があるかを見る。あれば、4:4:4 の絵を1枚通して、`general_profile_idc` が 4 になることも見る。
2. **ADR 0002 の画質と時間の計測を、Mac のエンコーダーで行う。** 絵は、判定と同じ（3440×1440、動く文字、毎秒 85 枚）。設定は、4:4:4、キーフレームは求められたときだけ、上限 30 Mbps。画質の3つの条件と、1フレームの圧縮にかかる時間を記録する。測り方は、M1 と同じにする。
3. 低遅延の設定を1つずつ試す：リアルタイム、並べ替えなし、速さを優先。低遅延のレート制御の指定は、文書の説明が H.264 を思わせる。H.265 で効くかを見る。

1 で 4:4:4 がなかったときだけ、6. の 3 の問いを人に出します。あったときは、問いは要りません。速さが足りなかったときの扱いは、ADR 0002 の同じ版に、すでに決まりがあります（先に圧縮を縮める。それでも届かなければ、4:2:0 に戻す）。

### 手順 7：許可の案内と、誰も座っていないホスト

- `istesso doctor` が、画面収録、アクセシビリティ、音の録音の許可の状態を表示する。
- 足りない許可があるときは、何のために要るかと、設定の場所を案内する（R-12）。
- Mac mini に人がログインしたあと、画面をロックした状態と、スリープから起こした直後の状態で、Air から使えるかを確かめる（4.4）。眠らせることと、起こすことは、人に知らせてから行う。設定は変えない。

確かめ方：

- [ ] 許可を1つ外して実行すると、どれが足りないかと、設定の場所が出る。
- [ ] 案内は、開発者でない人が、説明を読まずに進められる。設定の該当の画面が開き、どの項目を入れるかが分かる。ターミナルを使わせない。
- [ ] 出力に、ペアリングコード、鍵、トークンが出ない（AGENTS.md）。
- [ ] Mac mini の画面をロックした状態で、Air から、新しい窓を開ける。開いてある窓を、操作できる。
- [ ] Mac mini をスリープから起こした直後に、Air から、新しい窓を開ける。眠る前に開いていた窓に、戻れる。
- [ ] 動かなかったものについて、理由と、インストーラーが何を入れれば動くかが、記録にある。
- [ ] 再起動のあとに1回ログインが要ることが、使う人に伝わる。導入の案内に書いてあり、ログインの前の Mac は、Air から、止まっているホストとして見える。
- [ ] 眠らせて、ネットワークから起こしたあと、眠る前の状態（ログイン済み、ロック中）に戻るかと、絵の流れが戻るまでの時間が、記録にある（下）。

#### 眠らせて、起こす（2026-11-17 に、行ってよいと決まった）

**Wi-Fi で行う（2026-11-17 20:14 の決定を受けて）。** ケーブルは要らない。Mac mini で、読むだけで確かめた（20:2x）：

- `pmset -g cap` に `womp`（マジックパケットで起きる）があり、`pmset -g` で `womp 1`。Wi-Fi の情報（`system_profiler SPAirPortDataType`）は「Wake On Wireless: Supported」。だから、Wi-Fi でも、マジックパケットで起こせる見込み（**確かめていない**）。送るのは、Air から、Mac mini の Wi-Fi の口のハードウェアアドレスへ。アドレスは、その場で読み、書かない。
- Bonjour の眠りの代理（Apple TV など）は、マジックパケットを直に送るなら要らない。SSH をつなごうとするだけで起こす形（必要なときに起こす）には要る。
- 時刻を決めて起こす（`pmset schedule wake`）は、`pmset` の説明に「設定を変えるには root が要る」とあり、使わない（sudo は人のもの）。
- 人がキーを押して起こすのは、いつでもできる。
- **いまは、人の `caffeinate` が眠りを止めている**（17:43 に `pmset sleepnow` を送ると、眠らずに DarkWake に入った）。止めるかどうかは、人が決める。それまで、眠りと起床の確認はできない。

LAN ケーブルが挿さってから（3.9 の 3）行います。起こすのは、ネットワークから（Wake-on-LAN）です。Mac mini の「ネットワークからの起床」は、すでに入っています（`womp 1`。3.9）。設定は変えません。

前に確かめること：

- 両方の計測の合図が free である。人に、始める時刻を知らせてある（6.4）。
- Mac mini の有線の口に、アドレスが付いている。Air から、有線のアドレスで SSH が通る。
- 起こすのに要る有線の口のハードウェアアドレスは、Air の ARP の表から、その場で読む。**ファイル、記録、コミットには書かない。** 送るのは、Air のスクラッチの中の、使い捨てのスクリプトから。

進め方：

1. 眠る前の状態を記録する：ログインしているか、ロック中か（`ioreg -n Root -d1` の `CGSSessionScreenIsLocked`）、ディスプレイのスリープ、`pmset -g` の眠りの設定と、眠りを止めている主張（`pmset -g assertions`）。ユーザー名は書かない（「同じユーザー」とだけ書く）。
2. Air から、`ssh <Mac mini> pmset sleepnow` で眠らせる（権限は要らない）。人が動かしている `caffeinate` が眠りを止めていて、眠らないときは、そこで止めて、人に知らせる（`caffeinate` には触らない）。
3. Air から、有線のアドレスへの ping が 30 秒続けて返らないことで、眠ったと見る。眠った時刻を記録する。
4. 60 秒待ってから、Air から、マジックパケットを有線の口へ送る。送った時刻を t0 とする。
5. t0 から、次の時刻を、Air の時計で記録する：ping が返る、SSH が通る、`ioreg` が読める、Mac mini のエンコーダーが 1 枚目を出す（`vt-bench --seconds 2`）。許可が出ていれば、確認のプログラムで、取り込みの 1 枚目が届く（`--rate`）。1 本通す経路（手順 3）ができていれば、Air に絵が戻るまで。
6. 起きたあとの状態を記録する：同じユーザーがログインしたままか、ロック中のままか、ディスプレイが点いたか。FileVault の解除を求められなかったか（眠りなので、求められない見込み）。
7. 起きなかったら：Wi-Fi のアドレスから SSH を試す。それでも届かなければ、人に、Mac mini のキーを 1 回押して起こしてもらう。そのときは「ネットワークからは起きなかった」と記録する。

記録に書くこと：眠る前と起きたあとの状態、t0 からの各時刻、つなぎ直しの回数（経路があれば）、途中で人の手が要ったか。

### 手順 8：判定

M1 の判定のあとに行います。条件と測り方は、M1 と同じです（ADR 0002、`m1-latency` ブランチの `m1-plan.md` の手順 5）。

- 2台とも有線、85 Hz、3440×1440 の動く絵、2,000 回以上。画質の条件を満たすこと。
- 当てるテスト：20 回のうち、正解が 14 回以下。
- 誰も座っていない状態の確認（手順 7）が済んでいること。
- 始める前に、人に知らせる。計測のあいだ、Air に触らない。

満たせない場合は、内訳からいちばん大きい区間を特定して、ADR に残します。

| `sink` | ほかの部品とつながる 2 つの口（下） | テストあり |

ほかのブランチのものを、インターフェースだけで使うところ：

| 相手 | 相手の場所 | こちらの口 | いまの代わり |
|---|---|---|---|
| 映像の経路（ADR 0015） | `istesso-media` クレートの `Host::send_frame`、`Host::key_frame_wanted`（`m1-dialog-windows` ブランチ） | `sink::FrameSink`。同じ形にしてある（フレーム、時刻 2 つ、キーフレームかどうか。キーフレームが要るかを聞く） | 数えて捨てる `Discard`。`istesso-media` が `main` に入ったら、数行のつなぎを書く |
| セッションの約束（ADR 0010） | エージェントがランナーに送る行（`m3-app-manager` ブランチ） | `contract`。ADR の行を、そのまま読み書きする | 行の型と、読み書きだけ。ランナーの本体は、まだない |
| 入力のイベント（ADR 0007 の「入力」） | `istesso_proto::InputEvent`（`m1-latency` の系列） | `input::Event`。同じ形にしてある（キーは、Linux の番号） | 自分の型。`main` に入ったら、相手の型に替える |

窓の取り込みを、まだクレートに書いていない理由：前提（ロックしたまま取り込める）が成り立つかどうかで、作りが変わるためです。先に、小さな道具（`macos/lock-check`）で確かめます。その道具の中には、取り込みの呼び出しが、書いてあります。

## 5c. 入力を、そのアプリだけに閉じる（設計。2026-11-17。とりまとめ役が見た。作るのは、下の確かめのあと）

**いまの形の問題。** `crates/istesso-host-macos/src/input.rs` の `post` は、作った入力を、ログインのセッションの入口（`CGEventPost` の session tap）に入れる。届き先は、そのときの OS の振り分けしだいで、確かめていない。Mac のホストでは、人自身のデスクトップが同じセッションなので、ほかの端末から来た入力が、ほかのアプリや、ロックの画面に届き得る。ADR 0017 の守ること 3（確かめた入力だけを届ける）は、「誰が送ってよいか」を確かめるが、「どこに届くか」を確かめていない。**遠くのセッションの入力を 1 つでも届ける前に、これを閉じる。** それまで、`post` は呼ばない（いまも、どこからも呼んでいない）。

**ロックは、Mac ホストのふつうの状態である**（4.4。手順 0b で、ロック中でも取り込めて、ホストの画面にはロックの画面だけが映ると分かった）。誰も座っていないホストが動くことは、各流れの受け入れ条件にある。だから「ロック中は、すべて捨てる」とはしない。それでは、人がホストのロックを外しておくことになり、守ろうとしたものより悪い。

### 閉じ方：アプリのプロセスへ直に送る

**キーもポインターも、そのアプリのプロセスへ直に送る**（`CGEventPostToPid`）。これだと、ホストの本物のポインターは動かず、イベントは window server の振り分けを通らないので、ほかのアプリにも、ロックの画面にも届きようがない。セッションの入口は、使わない。

| 入力 | 第 1 の形（これを先に確かめる） | 届かなかったときの、弱い形 |
|---|---|---|
| キー（押す、離す） | そのアプリのプロセスへ直に | — |
| ポインター（移動、ボタン、ドラッグ）、スクロール | そのアプリのプロセスへ直に | セッションの入口。ロックしていないときだけ。前面で、点のいちばん手前の窓がそのアプリのときだけ（下の「弱い形」） |

- **ロック中は、セッションの入口を、絶対に使わない。** プロセスへ直に送る形は、ロック中でも使う。ただし、ロック中に直送が本当にアプリに届くか、そしてロックの画面に何も漏れないかは、確かめてからにする（下の確かめ）。届くと分かるまで、ロック中は、直送も止める設定にできる。
- ポインターの直送が効く（確かめの 3）なら、セッションの入口は、まったく使わない。名前のとおりの隙（確かめてから届けるまでに、ほかの窓が手前に出る）も、ホストを人が使っているときにポインターを取り合うことも、なくなる。**効かないときだけ**、弱い形に落ちる。
- **前面にあること**は、送り方ごとに決める。セッションの入口を通すものには要る。直送には、前面でないアプリがキーとクリックを受け取るか（1 台のホストで 2 セッションに要る）を確かめて決める。`Confine` の入力にして、両方をテストしてある。

**人の決定（2026-11-17 の夜）：いつも、アプリのプロセスへ直に送る形を主にする。** 確かめてから届けるまでのあいだに、ほかのアプリの窓が手前に出ることは、なくせない（手順 0b の A2 で、確かめの直前に、ほかのアプリの窓が開いた）。だから、セッションの入口は、直に送れない種類の入力だけに残し、その種類ごとに理由を書く。そのため、まず直送のクリックを届くようにする。届かないと分かった種類は、試したことと、OS がしたことを添えて、とりまとめ役に知らせる（黙って試し続けない）。

| 種類 | 直送で届くか |
|---|---|
| キー（F13） | **届く**（手順 0b の A1：ロック中、A2：ロックしていないとき） |
| ポインターの移動 | 届く（A1。A2 は、人のマウスの操作と混ざったので数えない） |
| クリック | **届かなかった**（A1、A2。最初のクリックを受け取る設定と、クリックの回数の印を足して、次の場面で確かめる） |
| ドラッグ、スクロール、修飾キーの状態、文字の入力（日本語入力） | まだ試していない |

### 決める部分（`crates/istesso-host-macos/src/confine.rs`。許可なしで動く。テストあり）

決める部分を、OS を呼ばない型 `Confine` にした。入力は、ロック中か、セッションのアプリのプロセス、前面のプロセス、窓の一覧（持ち主、層、位置、透明さ。手前から順）、入力（キーか、点つきのポインターか）。出力は `ToProcess(プロセス)`、`SessionTap`、`Drop(理由)`。

- 既定（`Confine::default`）：直送する（`direct`）。前面は要らない（`direct_needs_frontmost` は偽）。直送が切れているときだけ、セッションの入口に落ち、そのときロック中なら `Drop(LockedSessionTap)`。
- テスト（`cargo test` で動く。許可は要らない）：直送はロック中でもアプリへ行く／前面を要る設定なら、前面がほかのとき落ちる／セッションのアプリがないとき落ちる／セッションの入口はロック中に使われない／セッションの入口は前面を要る／セッションの入口のポインターは、点の手前の窓がアプリのときだけ通り、ほかのプロセスの窓が手前なら落ち、点に窓がなければ落ちる／透明な窓は手前と数えない。
- 前面から外れたとき（前面が変わった、ロックされた、端末が離れた）の「押したままを全部離す」は、`Translator::release_all`（Linux のエージェントが切れたときにするのと同じ）が持つ。離すキーは直送、離すボタンも直送。そのあと前面に戻るまでの入力は、`Confine` が落とし、数える。
- 捨てた数（理由ごと）は、記録と、あとの窓に出す（6.1b の E）。

### 新しい確認のプログラム（`com.maromoco.istesso-dev.lock-check`。1 回の作り直しで、人の許可の出し直しも 1 回）

いま Mac mini にある 14:05 のビルドは、F13、ポインターの移動、クリックを、**セッションの入口に**送る。自分の窓に届くと見込むだけで、確かめていない。ロック中は、ロックの画面に届き得る。**このビルドで、入力の確認を動かさない。**

作り直しは、見える名前に「Dev」を付け、開発の証明書で署名する（証明書の名前は、この Mac の `~/.config/istesso/sign.env` の `ISTESSO_SIGN_IDENTITY`。読み込んで使い、名前はどこにも書かない）。作り直すと許可が消えるので、人に 1 回出し直してもらう。いつ作るかは、とりまとめ役と、人の署名が通ってから。

**プログラムが送るもの（これ以外は送らない）：**

| 何を | 届け先 | どの状態で | 鳴らないための配慮 |
|---|---|---|---|
| F13（何も打ち込まないキー）、押して離す | **自分のプロセスへ直に**（`CGEventPostToPid(getpid())`）。セッションの入口には、送らない | ロックしていないとき、ロック中、ディスプレイのスリープ、起こした直後 | 自分のプロセスにしか送らない。ロックの画面には届かないので、割り当てのないキーの警告音は鳴らない。だめ押しに、F13 は音に割り当てのないキー |
| ポインターの移動とクリック（左）、自分の窓の真ん中の点 | 自分のプロセスへ直に（第 1 に確かめる）。並べて、弱い形（セッションの入口）も、点の手前の窓が自分の窓のときだけ試す | 同上 | セッションの入口に送るのは、ロックしていなくて、手前が自分の窓のときだけ（`Confine`）。ロック中は、セッションの入口に送らない |

- 窓だけを、自分で開く（いまと同じ）。送った数、アプリ（自分）が受け取った数、`Confine` が落とした数を、理由ごと・状態ごとに報告する。
- ロック中に、直送が自分の窓に届くか、ロックの画面に何も漏れないかを、これで初めて確かめる。届くなら、ADR 0017 の守ること 3 を「ロック中も、直送だけで届ける」と書ける。届かないなら、ロックの扱いを人と決め直す。
- 取り込みの速さの確認（下の (b)）と、起こしておく形（6.1b の F）も、同じプログラムに入れて、許可の出し直しを 1 回で済ませる。

### (b) 取り込みの速さ：89 枚描いて 75 枚しか取れないのはなぜか（同じプログラム。許可は取り込みのぶん）

| B | Mac のエンコーダーが長くかかること（6.2 の 11） | 順番は提案のとおり：先に、窓の取り込みと合わせた値（手順 3）と、画質を測る。そのうえで (a) と (c) を採る。(a) Mac のホストは、絵の大きさごとに、測った値をそのまま書く。「合格」と書くのは、合格ラインを満たす大きさだけ。(c) Mac Studio が届いたら、同じ計測をやり直す。**(b)（絵を分けて 2 つのエンコーダーで圧縮する）は、Mac mini では試さない。** 記録では、4:2:0 でも時間が変わらず、4 分の 1 の大きさで約 3 分の 1 になった。時間は画素の数に従う。エンコーダーが 1 つなら、分けても得がない。Mac mini のエンコーダーは 1 つ（下の手順 2）。(b) は、エンコーダーを複数持つ機種で、(c) と一緒に試す。**エンコーダーの設定を探すのは、ここでやめる。** 確かめることを 3 つ足す：1. まばらな入力での圧縮の時間（手順 2）。2. 取り込みが、ホストの画面のリフレッシュレートで頭打ちになるか（手順 1 の初め。頭打ちなら、B の小さな試しを手順 1 のすぐあとへ前倒しする）。3. Mac の省エネの設定（低電力モード）を、計測の条件に書く（5. の初め） |
| C | 仮想ディスプレイ（6.2 の 2） | 提案のとおり：A で作り、B を小さく試し、そのうえで ADR で決める。試しは、今週行ってよい。製品に入れるかどうかは、人が決める。眠らせて起こす確認は、LAN ケーブルが挿さってから行ってよい。ネットワークから起こす。眠る前の状態（ログイン済み、ロック中）に戻るかと、絵の流れが戻るまでの時間を記録する（手順 7） |
| D | 署名（M9） | 人の個人の証明書（Apple Developer Program）と、公証。6.1 の 7 のとおり。証明書には加入者の名前が入り、使う人から見える。人は承知している。守ること：その名前を、コード、スクリプト、文書、コミット、CI のログに出さない。署名のスクリプトは、証明書を、環境変数か、そのハッシュで指す。署名は、人の Mac で、人の鍵で行う。鍵と証明書は、リポジトリにも CI にも入れない（変えるなら、先に尋ねる）。変わらない要件：使う人が出した許可は、更新のあとも残ること。画面の取り込みを保ち続けるための申請（6.1 の 7 の後ろ半分）を人の作業に載せるのは、手順 1 で要ると分かったときだけ |
| F | エンコーダーを起こしておく形（14:58 に決まった。手順 2） | **採る。毎秒 20 枚。** 端末がそのセッションを映しているあいだだけ動く。設定で切れる（ホストが電池で動く Mac の人のため）。既定は入り。起こしておくための絵は、**送る**。「圧縮するが送らない」形は、手元の復号器がそれに付いてくると分かるまで使わない。記録には、この言葉で書く：止まった画面に 1 文字打つと、Mac mini は 9 ms かかる。Linux のホストより約 5 ms 長い。もう 1 つ試す：入力が来た直後（50 ms ほど）は、起こしておくための絵を控えて、本物のフレームがぶつかりにくくなるか（手順 2）。手元の復号器と、Linux のホストのエンコーダーに同じ効き目があるかは、絵の流れと、とりまとめ役が見る。作りに入れる変更は、絵の経路の変更なので、PR の前にとりまとめ役が見る |
| E | つなぎ直しの回数 | いつも見えるようにする。計測の記録（あとでは窓にも）に、絵、入力、音のそれぞれが何回つなぎ直したかを出す。0 でない回があったら、その値を使う前に、人に知らせる（5. の初め） |

## 8. ライセンスの注意

- Mac のホストは内製です（[components.md](components.md)）。参照してよい実装は、`components.md` の「取り込める」にあるものだけです。
- Sunshine、Moonlight、xpra は、Mac を配信する部分を含みますが、GPL です。読みません。写しません。
- Ensemble は、ライセンスが未確認です。確認できるまで読みません。
- 非公開の API（`CGVirtualDisplay`）の使い方を、ほかのプロジェクトのコードで調べるときは、先にそのプロジェクトのライセンスを確かめて、`components.md` に載せます。小さな試し（`macos/lock-check/virtual-display.h`）の宣言は、ほかのプロジェクトのコードを読まずに、Objective-C のランタイムが示すクラスの中身から書きました（2026-11-17）。
- Apple の文書と、OS に入っているヘッダーは、読んで構いません。
- GStreamer を使う場合は、動的リンクにします。依存を足したら、`cargo deny check` を通します。
