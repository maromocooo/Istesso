# M4 の進め方：Mac をホストにする

M4 は、Mac のアプリを、別の Mac の窓として使えるようにする段階です。受け入れ条件は「Mac Studio のアプリを MacBook Air の窓として、M1 と同じ合格ラインで使える」です（[milestones.md](milestones.md)）。今週は、Mac Studio の到着を待たずに、**Mac mini（ホスト）と MacBook Air（クライアント）の2台**で進めます（2026-11-16 に決定）。

この文書は、実機の上で作業する人とコーディングエージェントのための手順書です。前半は準備の一覧、後半は手順と確かめ方です。規約は先に [AGENTS.md](../AGENTS.md) を読んでください。

読むときの注意：

- **この文書は、実機で何も動かさずに書きました。** Mac mini には、まだ触れていません。Air は、読むだけの調査（`sw_vers`、`system_profiler`、`istesso doctor`）をしました。「見込み」「未確認」と書いたところは、手順の中で確かめます。
- Apple の API について書いたことは、2026-11-16 に Apple の公開の文書で確かめた範囲です。出どころは「9. 参照した文書」にあります。
- ADR 0008 と 0009（`m1-latency` ブランチ）、ADR 0010（`m3-app-manager` ブランチ）、ADR 0011（`m2-audio` ブランチ）と、M1 の計測の記録は、まだ `main` にありません。この文書では、リンクにせずに番号で指します。

## 1. 確かめること

1. Mac mini のアプリ1つを、Air の窓1枚として出して操作できる。
2. 追加遅延と画質が、M1 と同じ合格ラインに収まる（[ADR 0002](adr/0002-latency-first.md)。数値は `m1-latency` ブランチで決まったもの）。
3. どの窓がリモートかを当てるテストで、当てられない。
4. そのアプリの音が、選んだ音の出口から鳴る（[ADR 0005](adr/0005-audio-service.md)）。
5. 足りない OS の許可を、`istesso` が案内する（R-12）。

## 2. ほかの流れとの関係

| 相手 | 関係 |
|---|---|
| M1（遅延の検証） | 関門は外さない。M4 の準備と手順 0〜2（調査、取り込み、圧縮）は、Mac だけの部分なので、M1 の判定を待たずに進められる。手順 3 から先は、M1 の受信側と経路を使う。**M4 の判定は、M1 の判定のあとに行う** |
| M1 の計測 | Air は M1 のクライアントでもある。実機で遅延を測っているあいだは、M4 のビルドと試験を止める（`m1-latency` ブランチの決まり）。計測の時間は、M1 が先 |
| M3（アプリマネージャー） | セッションの始め方は ADR 0010 に従う。ホストの側は「ランナー」というプログラムで、標準入出力に1行ずつの JSON を受ける。ADR 0010 は、Mac のアプリの起動と窓の扱いを M4 で見直すと書いている（6. の 9） |
| M2（オーディオ） | Mac の音の取り込みは、M2 の逆の向き（Mac の音をほかの PC から出す）と同じ部品になる。分担は 6. の 10 |
| M5（隔離） | Mac の専用ユーザーのセッションから配信できるかは、[ADR 0003](adr/0003-isolation.md) が M4 で確かめると書いている。今週は、ふだんのユーザーで進める（7.）。[ADR 0014](adr/0014-dedicated-user-in-practice.md)（提案）は、ホスト専用の Mac を、専用ユーザーでログインして使う形にしている |

## 3. 準備

人がやることを先に並べます。エージェントに任せられることは、そう書いてあります。

### 3.1 役と体制

| 役 | 機材 | いまの状態 |
|---|---|---|
| ホスト | Mac mini | 未確認。機種も macOS のバージョンも、まだ分からない |
| クライアント | MacBook Air（M4、macOS 26.5.1、Xcode 26.6、Rust 1.93） | M1 のクライアントとして動いている。外部ディスプレイは 3440×1440 の 85 Hz、有線 LAN のアダプターつき |

M1 と同じく、Air の上でコーディングエージェントを動かし、Mac mini へは SSH でつなぎます。

| エージェントに任せること | 人がやること |
|---|---|
| Mac mini でのビルドと実行、ログの収集（SSH が通ったあと） | Mac mini の最初の設定、ケーブルの接続 |
| 調査用の小さなプログラムと、計測 | macOS の許可のダイアログへの応答（管理者のパスワードが要る） |
| 記録、ADR と文書の更新 | 「6. コードの前に決めること」の決定 |
| 判定の計測を始める前に、人に知らせる | 当てるテスト。判定の計測のあいだ、Mac に触らない |

### 3.2 手元に用意する物と、知らせてほしいこと

用意する物：

- [ ] Mac mini 用の LAN ケーブルと、ルーターかスイッチの空いている口。
- [ ] Mac mini の最初の設定に使う、画面、キーボード、マウス。
- [ ] Mac mini の映像のケーブル（HDMI など）と、外部ディスプレイの空いている入力（3.5 の表）。
- [ ] Air の MagSafe の電源と、いま使っている有線 LAN のアダプター。

新しく買うと決まっている物は、ありません。ダミープラグが要るかどうかは、手順 0 の結果で分かります。

Mac mini について、知らせてほしいこと：

- [ ] 機種（「この Mac について」。Apple シリコンか、何年のものか）と、macOS のバージョン（`sw_vers`）。
- [ ] 映像の出力を、何につなげるか（3.5 の表の3つから）。
- [ ] その Mac mini を、ふだん誰かが使っているか。使っていなければ、ホスト専用にできる（4.2 の 1）。
- [ ] FileVault が入っているか（`fdesetup status`）。再起動のあとの扱いに関わる（6. の 5）。
- [ ] Apple Developer Program に入っているか（6. の 7）。

macOS のバージョンの目安：

| バージョン | 理由 |
|---|---|
| 14.2 以上（必須） | アプリの音を取る Core Audio のタップが、ここから（ADR 0005）。取り込みに子の窓を含める指定も、ここから |
| 15 以上 | ローカルネットワークの許可が、Mac ではここから入った。画面収録の許可を定期的に確かめ直す動きも、この版から（報道による） |
| Air と同じ系（いまは 26 系） | 片方で分かったことが、もう片方にそのまま当てはまる。違うときは、記録にバージョンを書く |

Intel の Mac mini だと、エンコーダーが別物になります。その場合は、先に知らせてください。この文書は、Apple シリコンを前提に書いています。

### 3.3 Mac mini：設定と、入れるもの

人がやること（Mac mini の前で）：

- [ ] 最初の設定を済ませる。画面、キーボード、マウスが要る。
- [ ] 有線 LAN をつなぐ（内蔵の LAN の口）。
- [ ] 「システム設定」の「共有」で、「リモートログイン」（SSH）を入れる。Air の公開鍵を登録する。あとの操作のために、「画面共有」も入れておくと、Air から画面を見て、許可のダイアログに応えられる。
- [ ] 眠らせない設定にする。配信しているあいだに眠ると、絵が止まる。画面のロックとスクリーンセーバーも切る。ロック中は、取り込みも入力もできない（4.2）。**これは安全を下げる設定なので、6. の 5 で決めてから行う。**

入れるもの。SSH が通ったあとは、エージェントに任せられます。ただし、Xcode と Homebrew のインストールは、サインインや管理者のパスワードが要るので、人がやります。ほかに権限の要るものが出たら、エージェントがコマンドを提示します。

| 入れるもの | 何のため | Air |
|---|---|---|
| Xcode。ビルドだけなら Command Line Tools（`xcode-select --install`）でも足りる見込み（未確認） | Swift と Objective-C のコード（取り込み、圧縮、入力）をビルドする。Xcode があると、役割表に `xcode_build` が付く | 済（26.6） |
| Rust（stable、1.85 以上） | `istesso` とテストアプリのビルド | 済（1.93） |
| リポジトリの複製 | ビルドのもと | 済 |
| `istesso`（`cargo install --path crates/istesso-cli --locked`） | 役割表、ペアリング、エージェント | 済 |
| テストアプリ（`istesso-flash`）と計測の道具（`m1-latency` ブランチ） | 遅延の計測 | 済 |
| GStreamer（Homebrew） | 手順 3 で、送り出しに既製の部品を使う場合だけ。LGPL なので動的リンクで使う（[components.md](components.md)） | 済 |

入れないもの：Sunshine、Moonlight、xpra。Mac を配信する実装を含みますが、GPL です。比較の対象として動かすことはあっても、コードは読みません（AGENTS.md）。

### 3.4 Air：確かめること

新しく入れるものは、ありません。

- [ ] 外部ディスプレイが、Air に直接つながっていて、85 Hz で動いている（「システム設定」の「ディスプレイ」）。
- [ ] 有線 LAN のアダプターに、LAN のアドレスが付いている（`istesso doctor` の `interfaces` に、`ethernet` がアドレスつきで出る）。
- [ ] 受信側のアプリに、ローカルネットワークの許可が出ている（M1 で済み）。
- [ ] 計測の道具を起動するターミナルに、画面収録の許可が出ている（M1 で済み。ADR 0008）。

### 3.5 つなぎ方

判定の条件は「2台とも有線、クライアントのディスプレイは 85 Hz」です（ADR 0002）。Air の USB-C の口は2つなので、使い道は決まっています。

```text
 ┌───────────────┐  映像（下の表の、どれか）
 │ Mac mini       ├──────────────────────────┐
 │ （ホスト）      │                           ▼
 │   内蔵の LAN ──┼──┐                ┌────────────────┐
 └───────────────┘  │                │ 外部ディスプレイ  │
                 ┌──┴─────┐          │ 3440×1440       │
                 │ ルーター │          └───────▲────────┘
                 │ スイッチ │                  │ USB-C その1（直接。85 Hz）
                 └──┬─────┘          ┌───────┴────────┐
                    │ 有線            │ MacBook Air     │
                    └─ LAN アダプター ─┤ （クライアント）  │
                       USB-C その2    │ 電源は MagSafe   │
                                     └────────────────┘
```

- **Air の USB-C その1：ディスプレイに直接つなぐ。** ハブを通すと、ディスプレイが 60 Hz になった（M1 の記録）。
- **Air の USB-C その2：有線 LAN のアダプター。** いまつないであるものを、そのまま使う。
- **Air の電源は MagSafe でつなぐ。** USB-C の口を使わない。これで、Air の口は埋まる。ほかの機器を Air に挿す余地はない。
- Mac mini は、内蔵の LAN の口でつなぐ。Wi-Fi は切るか、計測では有線のアドレスだけを使う（3.7）。
- 2台を Thunderbolt のケーブルで直接つなぐ形は、使わない。基準の対象は自宅の有線 LAN で、Air の口も足りない。

Mac mini の映像の出力を、何につなぐか：

| つなぎ先 | 最初の設定 | 計測での意味 |
|---|---|---|
| 外部ディスプレイの空いている入力（HDMI か DisplayPort） | できる | ホストの画面が 3440×1440、85 Hz 以上で動けば、判定と同じ絵を出せる見込み。ディスプレイが Air の入力を映しているあいだも、Mac mini から「つながっている」と見えるかは、機材しだい（未確認）。**まず、これを試す** |
| ダミープラグ（HDMI の口に挿す、画面のふりをする小さな部品） | できない（別に画面が要る） | 出せる解像度とリフレッシュレートは、部品しだい。買う前に、手順 0 の結果を見る |
| 何もつながない | できない | macOS が自分で用意する画面は 1920×1080 になる、という報告がある（未確認）。そのままでは、3440×1440 の絵は出せない。仮想ディスプレイを作る形（4.3 の B）なら、要らない見込み |

なぜホストの画面が効くか：macOS では、アプリの絵は、その窓が載っている画面の解像度とリフレッシュレートで作られる見込みです（4.2 の 2。手順 1 で確かめます）。

### 3.6 OS の許可：何を、なぜ求めるか

「システム設定」の「プライバシーとセキュリティ」にある項目です。

| 許可 | どの Mac で | 何のために | 出し方と注意 |
|---|---|---|---|
| 画面収録とシステムオーディオ録音 | Mac mini | アプリの窓の絵を読む（ScreenCaptureKit）。これがないと、絵が1枚も取れない | 管理者の認証が要る。macOS 15 以降は、許可を定期的に確かめ直す画面が出る（2024 年の報道では、月に1回。26 系での動きは、実機で確かめる） |
| 同上 | Air | 計測の道具が、2つの窓の中央の明るさを読む（ADR 0008）。製品には入れない | 出してある |
| アクセシビリティ | Mac mini | 1. キーボードとマウスの入力を、アプリに届ける（CGEvent）。2. アプリの窓を動かす、大きさを変える、前面に出す。3. 形によっては、メニューを読む（4.3） | 管理者の認証が要る。Air には要らない |
| システムオーディオ録音のみ | Mac mini | アプリの音を取る（Core Audio のタップ。ADR 0005） | 最初に録り始めたときに、macOS が尋ねる。プログラムに説明文（`NSAudioCaptureUsageDescription`）が要るので、アプリの形（バンドル）にする必要がある見込み |
| ローカルネットワーク | 両方 | LAN の相手につなぐ。mDNS で相手を見つける | ターミナルや SSH から起動したコマンドには、macOS が自動で許す。アプリとして起動するもの（Air の受信側）と、launchd のエージェントには、人の許可が要る。ユーザーごとに別に持つ |

求めないもの：root、フルディスクアクセス、入力監視。クライアントの Air は、自分の窓に来たキーとマウスを送るだけなので、入力のための許可は要りません。

注意：

- **AGENTS.md は、権限の要る処理を増やすときに、理由を ADR に残すよう求めています。** ADR 0008 が扱うのは、計測のための画面収録だけで、「製品には入れない」と書いてあります。Mac ホストのための許可には、別の ADR が要ります（6. の 1）。上の表は、その下書きです。**ADR ができるまで、Mac mini で画面収録とアクセシビリティを使うコードは書きません。**
- 許可は、プログラムの署名に結び付きます。署名なし（その場かぎりの署名）でビルドすると、ビルドのたびに別のプログラムとみなされて、許可が消えます。開発のあいだは、起動するターミナルに許可を出す形から始めます（ADR 0008 と同じ理由）。ただし、そのターミナルから起動したものは、どれも画面を読めて、入力を送れるようになります。あとで、決まった署名の付いたアプリに移します（6. の 1 と 7）。
- 許可のダイアログは、遠くから押せないことがあります。人が、Mac mini の前か、macOS の「画面共有」で応えます。
- SSH から起動したプログラムが、画面を読めて、入力を送れるかは、分かりません（手順 0 で確かめる）。だめなら、Mac mini のターミナルで起動します。

### 3.7 ペアリング

2台とも、同じ LAN に有線でつないでから行います。

```sh
# Mac mini：コードと、Air で打つコマンドが表示される
istesso pair host

# Air：表示されたコマンドをそのまま実行する（アドレスは、Mac mini の有線のもの）
istesso pair join <Mac mini のアドレス> <コード>

# 両方で、エージェントを動かしたままにする
istesso agent

# Air から
istesso hosts
```

- [ ] `istesso hosts` に、Mac mini が「動いている」と出る。
- [ ] 相手のアドレスが、有線のものになっている。Wi-Fi のアドレスが選ばれていたら、`istesso peers address <名前> <有線のアドレス>` で指定する。
- コードとアドレスとホスト名は、記録や公開する文書に書きません。
- 新しくペアリングした端末の権限は「閲覧」と「操作」です（[ADR 0006](adr/0006-pairing.md)）。音を試す段階で、音の権限を別に与えます。

## 4. macOS で「1アプリ = 1仮想ディスプレイ = 手元の1窓」は何を意味するか

R-02 は、アプリごとに仮想ディスプレイを割り当てると決めています。Linux のホストでは、そのとおりの形で動いています。macOS では、同じ形にならないところがあります。

### 4.1 Linux との違い

| | Linux のホスト（いま動いている形。ADR 0009） | macOS のホスト |
|---|---|---|
| アプリの絵の出どころ | アプリごとに専用のコンポジターを起動する。出力の大きさとフレームレートは、クライアントの窓に合わせて決める | ログインしているセッションの画面。macOS が合成したものを、ScreenCaptureKit で読む |
| 仮想ディスプレイ | コンポジターの出力が、それにあたる | 公開の API では作れない |
| 入力 | コンポジターに直接渡す。アプリごとに、別のポインターとフォーカスを持つ | セッションに、カーソルが1つ、フォーカスが1つ。入力を注入すると、ホストの本物のカーソルが動く |
| メニュー | 窓の中にある | 画面のいちばん上のメニューバーにある（窓の外） |
| 誰もデスクトップにログインしていないとき | 動く見込み。デスクトップのセッションとは別に動く | 動かない。ログインしていて、ロックされていないセッションが要る |
| 権限 | root は要らない | 画面収録、アクセシビリティ、音の録音。どれも人の操作が要る |

### 4.2 できることと、できないこと

公開の API でできること（文書で確かめた。実機での確認は、これから）：

- アプリの窓1枚だけを取り込む。または、ある画面のうち、アプリ1つの窓だけを取り込む。ほかのアプリの窓は、絵に入らない。
- カーソルを絵から外す。クライアントが手元で描ける（R-02）。
- アプリの音だけを取る。取っているあいだ、ホストのスピーカーから鳴らさないこともできる。
- アプリの窓の位置と大きさを、外から変える（アクセシビリティの許可が要る）。

正直に言って、できないこと：

| # | できないこと | 起きること |
|---|---|---|
| 1 | アプリごとに、別のカーソルとフォーカスを持たせる | ホストの Mac を、配信中に人が直接使うと、カーソルとキー入力を取り合う。2台のクライアントが、同じ Mac の別々のアプリを同時に操作することもできない。**Mac のホストは、1人が1台を使う形になる** |
| 2 | 公開の API で、仮想ディスプレイを作る | 絵の解像度、拡大率、リフレッシュレートは、ホストの画面のものになる。クライアントの窓に合わせて変えられない |
| 3 | ログインしていない Mac、ロック中の Mac から配信する | 再起動のあとは、誰かがログインするまで使えない。自動ログインは、FileVault を入れていると使えない（Air で確かめた） |
| 4 | OS の許可のダイアログと、パスワードを尋ねる画面を、中継した窓から操作する | 人が、その Mac の前か、macOS の「画面共有」で応える。安全のための仕組みなので、回り道は作らない |
| 5 | 許可を、人の操作なしに保ち続ける | 画面収録は、定期的に確かめ直される（3.6）。ホスト専用の Mac では、気づかないうちに絵が止まるおそれがある。避けるための Apple の許可（VNC アプリ向け）は、申請が要る（6. の 7） |
| 6 | トラックパッドのジェスチャー（ピンチ、スワイプ）を注入する | 公開の方法が見当たらない。スクロールとクリックとドラッグは送れる |

分かっていないこと（手順 1 と 4 で確かめる）：ほかの窓に隠れた窓、最小化した窓、別の操作スペースにある窓を取り込めるか。メニュー、ポップアップ、保存のパネルが絵に入るか。パスワードの入力欄に、注入したキーが届くか。カーソルの形を読めるか（読むための API は、Apple の文書の上では macOS 27.0 までになっている）。

### 4.3 選べる形

| | A：窓を切り出す | B：アプリごとに仮想ディスプレイを作る |
|---|---|---|
| やり方 | アプリの窓を、ホストの画面に置いたまま、その窓だけを取り込む | クライアントの窓と同じ大きさ、同じリフレッシュレートの画面を作り、アプリの窓をそこへ動かして、画面ごと取り込む |
| API | 公開のものだけ | 仮想ディスプレイを作る部分が、**非公開の API**（`CGVirtualDisplay`）。Apple の文書にない |
| R-02 との関係 | 仮想ディスプレイはない。「1アプリ = 手元の1窓」だけを満たす | 言葉どおりに満たす |
| 絵の大きさとリフレッシュレート | ホストの画面で決まる。3440×1440 の 85 Hz で測るには、ホストの画面がそれを出せること | クライアントに合わせられる見込み（未確認） |
| メニューバー | 窓の外にあるので、絵に入らない。別に運ぶ仕組みが要る（メニューバーの帯を一緒に取り込むか、メニューを読んで手元のメニューバーに出す） | 画面ごと取り込むので、絵に入る見込み（未確認） |
| メニュー、ポップアップ、2枚目の窓 | 子の窓を含める指定がある。どこまで入るかは、確かめる | その画面に出るものは、入る |
| 壊れやすさ | OS の更新に強い | OS の更新で、予告なく動かなくなり得る。Mac App Store には出せない。公証（M9）に通るかは、未確認 |
| 権限 | 画面収録、アクセシビリティ | 同じ |

どちらでも変わらないもの：4.2 の「できないこと」の 1、3、4、5、6。

もう1つ、**C：ログインしているセッションの画面を、丸ごと1つ出す**形があります。R-02 の形ではありませんが、いちばん単純で、取り込みと圧縮の数値を取るのに使えます。macOS の「画面共有」と同じ形なので、基準として比べる相手にもなります。

**提案：手順 1〜3 は A と C で測る。その間に B を小さく試して、どちらを製品の形にするかを ADR で決める（6. の 2）。** 理由は3つあります。

1. 取り込みと圧縮の数値は、どの形でも要る。A と C は、決定を待たずに測れる。
2. B は、R-02 に合い、メニューと解像度の問題をまとめて解く見込みがある。ただし、非公開の API に製品を載せることになる。これは、このプロジェクトでまだ決めたことのない種類の危うさで、人が決める。
3. B を採っても、動かなくなったときの戻り先として A が要る。

## 5. 手順

手順ごとに、結果を `docs/measurements/` に記録します。ホスト名、アドレス、ユーザー名は書きません。

### 手順 0：準備と調査

許可の要らない範囲だけを調べます。

- 両方の Mac で `istesso doctor` を実行し、3.8 の表と比べる。
- 2台の間の往復時間の分布を、有線のアドレスで測る（[measurements/README.md](measurements/README.md) の「経路そのものの遅れ」）。
- Mac mini の画面を調べる（`system_profiler SPDisplaysDataType`）。映像の出力のつなぎ先ごとに、選べる解像度とリフレッシュレートを記録する。Air の入力に切り替えたあとも、同じかを見る。
- Mac mini で起動したプログラムの優先度を見る（`ps -M`）。SSH から、ターミナルから、`open` からの3通り。Air では、エージェントのシェルから起動したものが低い優先度で動き、時刻がずれた（M1 の記録）。

確かめ方：

- [ ] 役割表が、3.8 の表のとおりである。
- [ ] 経路の往復が、M1 の有線の値（ネットワークの区間が平均 1.0 ms）と同じ程度である。
- [ ] ホストの画面を 3440×1440、85 Hz 以上で動かせるかどうかが、分かっている。

### 手順 1：取り込みを測る

ここから、画面収録の許可が要ります。6. の 1 の ADR が先です。

- テストアプリ（`istesso-flash`）を Mac mini で動かし、ScreenCaptureKit で取り込む。形は A（窓だけ）と C（画面ごと）。
- 測るもの：アプリが絵を確定してから、フレームが届くまでの時間。1秒に届く枚数。どちらも Mac mini の時計の中で閉じる。
- 設定を1つずつ変える：フレームの間隔の下限、待ち行列の深さ、絵の形式、カーソルを外す指定。
- 窓の状態を変えて、取り込めるかを表にする：ほかの窓の下、最小化、別の操作スペース、フルスクリーン、画面のスリープ。
- 絵に入るものを表にする：メニュー、右クリックのメニュー、ポップアップ、保存のパネル、日本語入力の候補、2枚目の窓。
- ホストの画面のリフレッシュレートを変えて、待ちがどう変わるかを見る。リフレッシュレートを上げると、合成の待ちは縮む見込み。これを判定で使ってよいかは、ADR 0002 の「毎秒 85 枚を超えない」に照らして、M1 の流れと決める。

確かめ方：

- [ ] 取り込みの区間の中央値と 95 パーセンタイルが、3440×1440 と 1720×720 で記録にある。
- [ ] 毎秒 85 枚で届くかどうかが、分かっている。
- [ ] 取り込める窓と、絵に入るものの表がある。

### 手順 2：圧縮を測る

- **最初に、VideoToolbox のハードウェアエンコーダーが H.265 の 4:4:4 を出せるかを確かめる。** ADR 0002 は 4:4:4 を決めている。Apple の文書にある H.265 のプロファイルは、Main、Main 10、Main 4:2:2 10、モノクロで、4:4:4 が見当たらない。出せなければ、6. の 3 の決定が要る。
- 低遅延の設定を1つずつ試す：リアルタイム、並べ替えなし、キーフレームは求められたときだけ、ビットレートの上限 30 Mbps、速さを優先。低遅延のレート制御の指定は、文書の説明が H.264 を思わせる。H.265 で効くかを見る。
- 3440×1440、毎秒 85 枚、動く絵で、1フレームの圧縮にかかる時間を測る。
- 画質を、ADR 0002 の3つの条件で測る。測り方は M1 と同じにする。

確かめ方：

- [ ] 4:4:4 を出せるかどうかが、分かっている。
- [ ] 圧縮の時間（中央値、95 パーセンタイル）と、画質の値が、記録に並んでいる。
- [ ] Linux のホストの値（圧縮は 2.6 ms、4:4:4 では 4.1 ms。ADR 0009）と比べてある。

### 手順 3：1本通す

- 取り込み → 圧縮 → 送り出し → Air の受信側。受信側は、M1 のものをそのまま使う。
- 送り出しは、M1 の手順 3 と同じく、計測のための暗号化していない UDP から始めてよい。**製品には残さない。**
- Air の画面での計測（ADR 0008）で、手元の窓との差を測る。500 回。内訳も取る。
- 任意：macOS の「画面共有」を、成熟した実装の基準として測る。画面での計測は外から測るので、相手のコードは要らない。

確かめ方：

- [ ] 手元の窓との差（中央値、95 パーセンタイル）と内訳が、記録にある。
- [ ] 合格ライン（12 ms、24 ms、47 ms）と、Linux のホストの値（500 回で、中央値 9.75 ms）に並べてある。
- [ ] いちばん大きい区間が、どこかが分かっている。

### 手順 4：入力

アクセシビリティの許可が要ります。6. の 1 の ADR と、6. の 4 の決定が先です。

- 経路は、Linux のホストと同じにする。制御チャンネルでエージェントに届き、エージェントが「操作」の権限を確かめて、ランナーのソケットへ渡す（`m1-latency` ブランチの ADR 0007 と、ADR 0010）。ランナーが、CGEvent にして注入する。
- 座標は、窓の中の位置で受け取り、ホストの画面の位置に直す。
- クライアントの窓が前面に来たら、ホストでもそのアプリを前面に出す。

確かめ方：本物のアプリ（テキストエディット）を Air から操作して、表にする。

- [ ] 文字の入力、修飾キーつきのショートカット、選択、ドラッグ、右クリック、スクロール。
- [ ] メニューから1つ選ぶ。保存のパネルで名前を付けて保存する。
- [ ] 日本語入力（ホストの側の入力方式で変換する形になる見込み）。
- [ ] Air のキーボード配列と、Mac mini の設定が違うときの動き。
- [ ] できなかった操作が、理由つきで記録にある。
- [ ] 計測を、この経路に通してある。

### 手順 5：1つのアプリを、1枚の窓にする

6. の 2（A か B か）と 9（起動と窓の役）の決定が先です。

- ランナーを、ADR 0010 の約束どおりに作る（`start` を読み、`ready` を返し、標準入力が閉じたら止まる）。
- アプリを起動し、その窓を見つけて、取り込みを始める。
- クライアントの窓の大きさに、アプリの窓（B なら仮想ディスプレイ）を合わせる。
- アプリが終わったら、エージェントに知らせる。

確かめ方：

- [ ] `istesso open <アプリ>` で、Air に窓が1枚開く（コマンドは `m3-app-manager` ブランチのもの）。
- [ ] ほかのアプリの絵と、ホストのカーソルが、混ざらない。
- [ ] 窓の大きさを変えると、絵が追従する。追従できないアプリ（大きさが決まっているもの）では、どう見えるかが決まっている。
- [ ] メニューが使える。
- [ ] アプリを終えると、窓が閉じる。窓を閉じたときの動きが、ADR 0010 のとおりである。

### 手順 6：音

- Mac mini のアプリの音を、Core Audio のタップで取り、M2 の経路で音の出口へ送る。映像のセッションとは別に動かす（ADR 0005）。
- 取っているあいだ、Mac mini のスピーカーから鳴らさない。Mac mini が音の出口のときは、取らない（手を入れない経路。ADR 0005）。

確かめ方：

- [ ] Mac mini のアプリで鳴らした音が、Air の出力から聞こえる。Mac mini からは鳴らない。
- [ ] 中継した窓を閉じても、音が止まらない。
- [ ] 8時間の確認は、M2 の受け入れ条件として、M2 の流れが行う。

### 手順 7：許可の案内

- `istesso doctor` が、画面収録、アクセシビリティ、音の録音の許可の状態を表示する。
- 足りない許可があるときは、何のために要るかと、設定の場所を案内する（R-12）。

確かめ方：

- [ ] 許可を1つ外して実行すると、どれが足りないかと、設定の場所が出る。
- [ ] 出力に、ペアリングコード、鍵、トークンが出ない（AGENTS.md）。

### 手順 8：判定

M1 の判定のあとに行います。条件と測り方は、M1 と同じです（ADR 0002、`m1-latency` ブランチの `m1-plan.md` の手順 5）。

- 2台とも有線、85 Hz、3440×1440 の動く絵、2,000 回以上。画質の条件を満たすこと。
- 当てるテスト：20 回のうち、正解が 14 回以下。
- 始める前に、人に知らせる。計測のあいだ、Air に触らない。

満たせない場合は、内訳からいちばん大きい区間を特定して、ADR に残します。

## 7. 今週に入らないもの

見積もりは、測った値ではありません。M1 で、同じ段階（道具、基準、1本通す）が1〜2日で進んだことから置いています。

| もの | 理由 |
|---|---|
| 判定（手順 8） | M1 の判定が先。M1 の自前の受信側と、暗号化した経路ができてから測る。Air を、M1 の計測と取り合う |
| 手順 4〜7 | 6. の決定（1、2、4、9）が出てから。決定が早ければ、今週に入る見込み（見積もり：2〜3日） |
| 仮想ディスプレイ（B）を製品に入れること | 非公開の API。決定と ADR が要る。小さな試しは、今週できる |
| Apple の審査が要るもの（VNC アプリ向けの許可、公証） | 審査にかかる時間が読めない。公証は M9 |
| メニューを、手元の Mac のメニューバーに出すこと。ジェスチャー | 形 A で要るかどうかが、手順 1 と 5 で分かる。見積もりは、そのあと |
| 専用ユーザーのセッションからの配信（ADR 0003） | M5 は、今週は設計まで（[m5-plan.md](m5-plan.md)） |
| 120 Hz での確認 | 85 Hz までのディスプレイで測っている |
| Mac Studio での確認 | まだ届いていない |

今週に入る見込みのもの：準備（人の作業は1〜2時間の見積もり）、手順 0〜3、6. の 1 と 2 の ADR。

## 8. ライセンスの注意

- Mac のホストは内製です（[components.md](components.md)）。参照してよい実装は、`components.md` の「取り込める」にあるものだけです。
- Sunshine、Moonlight、xpra は、Mac を配信する部分を含みますが、GPL です。読みません。写しません。
- Ensemble は、ライセンスが未確認です。確認できるまで読みません。
- 非公開の API（`CGVirtualDisplay`）の使い方を、ほかのプロジェクトのコードで調べるときは、先にそのプロジェクトのライセンスを確かめて、`components.md` に載せます。
- Apple の文書と、OS に入っているヘッダーは、読んで構いません。
- GStreamer を使う場合は、動的リンクにします。依存を足したら、`cargo deny check` を通します。
