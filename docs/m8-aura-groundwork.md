### Jetpack XR SDK で、資料に書いてあること（2026-11-18 に読んだ）

- **版**：SceneCore は 1.0.0（安定版）。Compose for XR は 1.0.0-beta02（安定版はまだ）［資料：S23、S24］。要件の 6.2 の「ベータ段階」は、Compose for XR については、まだ正しい。
- **Home Space の窓**：既定 1024×720 dp、最小 385×595 dp、最大 2560×1800 dp。1.75 m 先に置かれる［資料：S20］。
- **複数のパネル**：Full Space で、`Subspace` の中に `SpatialPanel` をいくつも置ける。`SubspaceModifier.movable()` と `.resizable(min, max)` で、人が動かし、大きさを変えられる［資料：S25］。SceneCore には `PanelEntity` と `ActivityPanelEntity` があり、後者は、別のアクティビティを自分のパネルに入れられる［資料：S23］。
- **既知の問題**：主のパネルの大きさを変えると、アクティビティが作り直されることがある［資料：S23 の更新の記録］。作り直しのたびに、映像の接続を張り直すことにならないよう、接続はアクティビティの外（サービスか、アプリの全体）に持つ。
- **映像を出す面**：`SpatialExternalSurface` は、`android.view.Surface` をくれる。`MediaCodec` の出力を、ここへ直接出せる見込み。ただし、**この面は入力を受けない。ほかのパネルより前には描けない**［資料：S26］。入力は、上に重ねた別の部品で受けることになる。
- **パネルのあいだのフォーカスと、入力の送り先**：資料に書いていない［不明］。
- **手**：人差し指と親指でつまむと、タッチか、マウスのボタンを押したことになる。つまんだまま動かすと、スクロール、移動、大きさの変更［資料：S20］。
- **目**：Android XR は、目の動きの生の値を、アプリに渡さない。システムが、乗せたときの見た目（ホバー）を描く［資料：S20］。**アプリは、視線がどこにあるかを知らない。** AURA に目の追跡があるかも［不明］。
- **Bluetooth のキーボードとマウス**：Android XR で使える。眼鏡の機械では、よく頼る、とある［資料：S20、S22］。
- **マニフェスト**：`android.window.PROPERTY_XR_ACTIVITY_START_MODE`（Home Space か Full Space で始めるか）、`<uses-feature android:name="android.software.xr.api.spatial">`（XR 専用の配布なら必須）。SDK は minSdk 24、compileSdk 34 以上［資料：S27、S28］。
- **アプリの入れ方**：Google の Engine Hub の端末の管理で、USB-C から APK を入れられる（開発者向けの設定と USB デバッグを入れたあと）［資料：S29］。XREAL の製品ページは、USB-C に「Full ADB support」と書く［資料：S1］。
- **ふつうの 2D のアプリ**：変えずに、Home Space のパネルとして動く［資料：S20、S27］。

## 3. 共通のクレートを、Android 向けにビルドできるか（読んだだけ）

Android 向けの cargo は、走らせていない。ツールチェーンも入れていない。以下は、`Cargo.toml` と `cfg` を読んで分かったことである。**ビルドが通るかどうかは、確かめていない。**

### 3.1 クレートごと

| クレート | 依存 | 台に縛られる所 | Android では |
|---|---|---|---|
| `istesso-proto` | `serde` だけ | ない | そのまま使える見込み［読んだ］ |
| `istesso-pair` | `spake2`、`ed25519-dalek`、`chacha20poly1305`、`hkdf`、`sha2`、`rand_core`（`getrandom`） | 鍵は**ファイル**に置く（`Identity::load_or_create`。16 進の種を、持ち主だけが読める権限で書く）。OS の鍵の置き場は、使っていない | 暗号はどれも純粋な Rust。乱数は `getrandom`（Android では OS の乱数を呼ぶ）。そのまま使える見込み。鍵の置き場は、下の 3.3［読んだ］ |
| `istesso-link` | `snow`（Curve25519、ChaCha20-Poly1305、SHA-2 だけ）、`zeroize` ほか | ソケットは `std` の TCP だけ | そのまま使える見込み［読んだ］ |
| `istesso-media` | `istesso-pair`、`istesso-link`、`istesso-agent`、`libc` | 主な部分は `cfg(unix)` の中。Android は `unix` に入るので、外れない。macOS だけの所は 3 つ：計測の時計（macOS は `CLOCK_UPTIME_RAW`、ほかは `CLOCK_MONOTONIC`）、受けるスレッドの実時間の扱い（macOS だけ。ほかでは何もしない）、閉じた接続への書き込みで落ちない設定（Apple では `SO_NOSIGPIPE`。ほかでは、`std` が書き込みのたびに指定する、とコードの注にある） | 時計と書き込みは、そのまま動く見込み。**受けるスレッドの優先度は、Android では何もしない**（新しく書く。3.2）［読んだ］ |

### 3.3 鍵の置き場

- いま：端末の鍵（Ed25519 の種）は、設定のフォルダーのファイルに、持ち主だけが読める権限で置く［読んだ］。
- Android のアプリの専用フォルダーは、ほかのアプリから読めない（Android のふつうの決まり。この下調べでは、資料を開いていない）。
- Android Keystore の鍵は、外に出せない。鍵の値は、アプリのプロセスに入らず、暗号の処理はシステムのプロセスが行う［資料：S30］。通信路の手順（Noise）は、`snow` の中で、鍵の生の値を使う［読んだ］。**だから、端末の鍵そのものを Keystore に入れると、`snow` が使えない。** Keystore が扱える Curve25519 の種類があるかは、この下調べでは確かめていない。
- 向き（決めるのは ADR）：鍵の種はアプリの専用フォルダーのファイルに置き、そのファイルを、Keystore の中の鍵（AES）で包む。鍵を包むのは OS の部品で、自作の暗号ではない。ADR 0006 の「鍵の置き場」に足すことになる。

### 3.4 ライセンスの点

- Android のクライアントが新しく引くものは、Android の SDK と Jetpack（Apache-2.0）、Jetpack XR SDK（Apache-2.0 で配られている見込み。採る前に、使う版で確かめる）。
- JNI の層を Rust で書くなら、`jni` クレート（MIT か Apache-2.0。採る前に確かめ、`cargo deny check licenses` を通す）。
- NDK の `MediaCodec`（`AMediaCodec`）を Rust から直に呼ぶ道もある（`ndk` クレート。同上）。どちらの側で復号器を持つかは、ADR で決める。
- Moonlight の Android 版のコードは、読まない（AGENTS.md。GPL）。Android で低遅延の復号をする知恵は、Google の資料と、`docs/components.md` の「取り込める」に載せたものからだけ取る。
- Android 向けのビルドの道具（NDK、`cargo-ndk` など）は、配るものに入らない。入れるときは、どの PC に入れるかを、持ち主に聞く。

## 4. 2 台目のクライアントとしての AURA（いまの設計の表に写す）

3 つの表は、そのまま、それぞれの設計の文書（ADR）に写せる形にした。「Mac」の列は、いまの設計のとおりである。

### 4.1 1 つのアプリの、複数の窓

いまの案：流れは 1 つ。ホストが、絵の中に窓を重ならないように並べ、クライアントが、四角ごとに切り出して、窓にする（`m3-everyday-apps` ブランチの `docs/m3-everyday-apps.md`、10 章の (ii)）。

| 項目 | Mac のクライアント | AURA のクライアント |
|---|---|---|
| 窓 1 枚の出し先 | Mac の窓 1 枚 | 空間のパネル 1 枚（1 章の (f)）。資料では、複数のパネルは Full Space だけで、そのあいだ、ほかのアプリは隠れる（f-5）。Home Space で、窓ごとに別のタスク（アクティビティ）を開けば、ほかのアプリと並べて何枚も出せるかもしれない（利用者向けのヘルプには「同じアプリの窓を複数」とある。アプリから開けるかは［不明］。4.1.1、f-6、f-7）。**だめなら、Home Space では 1 枚の窓に全部の窓を並べる形（M3 の (iii)）、Full Space では窓ごとにパネル、の 2 通りを持つ** |
| 切り出し | 復号した 1 つの面を、窓ごとに場所を変えて見せる（コピーなしの見込み） | 復号の出力は、1 つの `Surface` に出る（`SpatialExternalSurface` は、パネル 1 枚ぶんの面をくれる［資料：S26］）。**それを、複数のパネルに切り出して見せられるか**が、いちばんの問い。できなければ、復号した面を GPU のテクスチャーにして、パネルごとに描き分ける（描く段が 1 つ増える）。(f-3) |
| 知らせの中身 | 窓の一覧（番号、題名、`app_id`、親、四角、いちばん上か、キーボードを持つか） | 同じものに加えて、**ポップアップを親のパネルの中に描くか、別のパネルにするか**を、クライアントが決められること。XR では、子の窓を別のパネルにすると、奥行きがずれうる |
| 大きさ | Mac の窓の大きさを、ホストに伝える | パネルの大きさ（メートル）と、画素の数は別もの。**ホストに伝えるのは画素の数**にする。パネルの大きさを変えたときに、画素の数を変えるか（絵の並べ直し、キーフレーム）、拡大縮小で済ませるかを、クライアントが選べること |
| フォーカス | キーの窓が変わったら、フォーカスを送る | 視線や手で選んだパネルが変わったら、フォーカスを送る。**どのパネルがキーボードを受けるか**は、Android XR の決まりしだい (f-4) |
| 入力の座標 | 絵の座標のまま | 同じ。パネルの中の位置を、そのパネルの四角に足して、絵の座標にする |

### 4.1.1 窓の置き方：Home Space で窓ごとにタスクを開く形と、Full Space の形（2026-11-18 の持ち主の追記）

Full Space では、Istesso だけが見え、AURA のふつうのアプリと並べられない（f-5）。そこで、Home Space で、窓ごとに別のタスク（別のタスクのアクティビティ。大きい画面の Android の、デスクトップのウィンドウ表示と同じ仕組み）を開けば、窓を何枚も出せるかを、資料で調べた（2026-11-18）。

資料に書いてあること：

- Home Space では、いくつものアプリが並んで動く。ふつうの電話と大きい画面のアプリは、そのまま動く。窓は、既定 1024×720 dp、最小 385×595 dp、最大 2560×1800 dp で、1.75 m 先に出る［資料：S20］。
- 利用者向けのヘルプ（Android XR Help の「Spaces & multitasking」）は、Home Space で「複数の窓とアプリを、開き、動かし、大きさを変えられる」「アプリをもっと開くことも、**同じアプリの窓を複数**開くこともでき、好きに並べられる」と書く。動かすのは窓の縁を、大きさは角を、つまんで引く。「Tidy up」は、最近使った 3 つまでのアプリを並べ直す［資料：S40］。**2 枚目の窓をどう開くか、アプリから開けるかは、書いていない。**
- 開発者向けの資料は、Home Space では、アプリは「1 枚のパネル」に入り、「大きい画面の Android の端末の、デスクトップのウィンドウ表示に似た体験」になる、と書く［資料：S41。S44 も「既定では、Home Space で 1 枚のパネル」］。これは 1 つのタスクの話で、アプリが別のタスクを開いたときのことは、書いていない（読み方は推測）。
- Android のふつうの複数の窓の資料：根のアクティビティは、それぞれ自分のタスクを持ち、自分の窓に出る。新しいインスタンスを別の窓に開くには `FLAG_ACTIVITY_NEW_TASK` で始める。同じアクティビティを複数のタスクにするには `FLAG_ACTIVITY_MULTIPLE_TASK` か `FLAG_ACTIVITY_NEW_DOCUMENT`。`FLAG_ACTIVITY_LAUNCH_ADJACENT` は「できるだけ」で、保証はない。`ActivityOptions.setLaunchBounds()` は、複数の窓のモードでなければ効かない。Android 10 からは、見えているアクティビティは全部 RESUMED のまま（multi-resume）で、いちばん上になったかは `onTopResumedActivityChanged()` で分かる。Android 15 からは `PROPERTY_SUPPORTS_MULTI_INSTANCE_SYSTEM_UI` で、窓を増やす操作をシステムの UI に出させられる。端末の会社は、これらのふるまいを変えられる［資料：S42］。デスクトップのウィンドウ表示では、新しいタスクは新しい窓に開く［資料：S43］。**どちらの資料も、XR のことは書いていない。**
- Full Space では、1 つのアプリだけが動き、ほかのアプリは全部隠れる［資料：S20］。空間の UI の API は、パネルの数を制限しない。パネルの最小はなく、最大は 2560×1800 dp［資料：S45］。`ActivityPanelEntity` は、別のアクティビティをパネルに入れる。それには `EMBED_ACTIVITY` の能力が要る。どの Space でこの能力が出るかは、書いていない［資料：S46］。
- 窓（パネル）のあいだのフォーカスと、キーボードの送り先は、XR については、どちらの形でも書いていない［不明］。
- 有線の眼鏡で、Home Space の窓の数や、複数の窓のふるまいが違う、という記述は見つからなかった。眼鏡で違うと書いてあるのは、視野、UI の自動の拡大縮小、全部を覆う表示のふるまいなど［資料：S20、S22］。

### 4.2 クライアントごとの、絵の形式

いま：ホストは、起動のときに形式を決めて、`stream` の答えで伝えるだけ（`codec`、`width`、`height`、`fps`、`chroma`、`colour`）。見る側からの申し込み（`watch`）には、何を受けられるかの項目がない（ADR 0015）［読んだ］。

いまの流れ（ホストのスクリプトの既定）：H.265、8 ビット、**4:4:4**（GStreamer の `nvcudah265enc` に `Y444` を入れる。プロファイルは Main 4:4:4。HEVC の範囲拡張、RExt）、3440×1440、毎秒 85 枚、CBR 30 Mbps、`preset=p1 tune=ultra-low-latency zero-reorder-delay=true b-frames=0`、キーフレームは最初と求められたときだけ（`gop-size=-1`）、パラメーターセットはキーフレームごと（`h265parse config-interval=-1`）、色は sRGB を BT.709 の 16〜235 で（`scripts/m1_encoder.py`、ADR 0002、ADR 0015）［読んだ］。

| 項目 | Mac のクライアント | AURA のクライアント | どこで決めるか |
|---|---|---|---|
| 色の間引き | 4:4:4 | 復号器が受けるなら 4:4:4。受けなければ、下の 2 つの案のどちらか（4.2.1） | セッションの始まり。`watch` に「受けられる形式の一覧」を足す（知らない項目は無視、の決まりがあるので、版は上げずに足せる見込み）。ホストは、その中から選んで `stream` で答える |
| 4:4:4 を復号できないとき：案 (i) 2 枚に詰める | 使わない | 4:4:4 の 1 枚を、4:2:0 の 2 枚に詰めて送り、受ける側で 1 枚に戻す（Microsoft の RDP の AVC444 の考え方）。**特許の様子が分かるまで、採らない**（4.2.1） | ADR。採るなら、`stream` の `chroma` に新しい値を足す |
| 4:4:4 を復号できないとき：案 (ii) 4:2:0 のまま | 使わない | 4:2:0 で送る（`scripts/m1_encoder.py` には、もう `420` → `NV12` がある。`wire.rs` にも `Chroma::Quarter` がある）。色の線は、AURA のために別に決める。基準は、AURA の上の、ふつうのアプリの窓（4.2.1） | ADR。足りるかは、実機で見る（b-5） |
| 解像度 | 3440×1440 級 | 片目の画素の数と、パネルの大きさで決まる。3440×1440 を送っても、見えるのは縮めた絵になりうる (b) | 同上。クライアントが、復号の上限と、欲しい大きさを言う |
| 毎秒の枚数 | 85（画面に合わせる） | AURA の画面のリフレッシュレート (b) に合わせる | 同上 |
| ビットの深さ | 8 | 8（10 ビットは、要る理由がない） | 同上 |
| 低遅延の復号 | VideoToolbox | `MediaCodec` の低遅延の指定 (a) | クライアントの中だけ |
| 画質の条件 | ADR 0002 の 3 つ。色は「色の SSIM が、悪いほうから 5% のフレームでも 0.99 以上」 | **4:2:0 は、圧縮しなくても、この色の線を割る。** 判定の絵（テストアプリの流れる色つきの文字、線の太さ 2 ピクセル、3440×1440、毎秒 85 枚）を、エンコーダーに通さずに、色の変換（8 ビット、16〜235、4:2:0）だけ往復させて測った値が、色の SSIM（青と赤の色差の SSIM の平均）の悪いほうから 5% で **0.9497**（平均 0.9786、最悪 0.9459。4:4:4 は 0.9995）。ADR 0002 の「4:2:0 は、圧縮しなくても 0.95」は、この値を丸めたもの（2026-11-16 の画質の記録、「1. 上限」の表）。中身は 4.2.1 の「0.95 の出どころ」。AURA で 4:2:0 にするなら、案 (ii) のとおり、AURA の線を別に決める | ADR |

ホストのエンコーダーの数にとって：

- **いまの決まりでは、1 つのセッションの絵は、映している 1 台にだけ送る**（ADR 0015 の「権限と、切るとき」）。Mac と AURA に、同時に同じ窓を映すことはない。**だから、クライアントごとに形式を変えても、エンコーダーは増えない。** 映す端末が変わったときに、エンコーダーを、新しい形式で開き直す（ADR 0015 の `pause` と `resume` と同じ動き。開き直す時間は、`resume` の答えの `opened_ms` で、もう測れる）。
- 形式が変わる切り替えでは、最初の絵はキーフレームになる。いまの「映す端末が変わったら、前の端末を切る」と、同じ時に起きる。
- 同時に 2 台へ映すこと（ほかの人に見せる）は、ADR 0015 で「将来の項目」になっている。そのときは、形式が違えば、エンコーダーが 2 つ要る。

### 4.2.1 AURA が HEVC 4:4:4 を復号できないとき（2026-11-18 の持ち主の追記）

AURA の復号器が HEVC Main 4:4:4 を受けるかは、まだ分からない（1 章の a-1〜a-3）。受けなかったときの案は 2 つある。

**AURA の映像の道（持ち主の決め、2026-11-18）。** この順で考える。

1. 実機で、HEVC の 4:4:4 を、機械で復号できるかを見る（1 章の a-1〜a-3）。できれば、Mac と同じ流れを使う。
2. できなければ、4:2:0 で送る。見え方は、AURA の上の、ふつうのアプリの窓を基準に判定する（下の案 (ii)）。0.9497 と 0.99 は、Mac の判定の絵での値なので、そのまま当てない。
3. 長い目では、自前の圧縮（持ち主の別の取り組み）を、AURA の GPU で復号する形を、候補として置く。その側の要件は、持ち主が、別に渡す。

**案 (i)（4:4:4 の 1 枚を、4:2:0 の 2 枚に詰める形）は、採らない**（持ち主の決め、2026-11-18）。同じ考え方の Microsoft の特許が、2034〜2035 年まで生きていると表示されているため（下の「特許」）。下の表と説明は、調べた記録として残す。

| | 案 (i) 4:4:4 の 1 枚を、4:2:0 の 2 枚に詰める | 案 (ii) 4:2:0 のまま送る |
|---|---|---|
| 色 | 圧縮しなければ、ほぼ 4:4:4 の色が戻る（主の絵の色差は、なめらかにしてあるので、受ける側で戻す処理をする［資料：S31］）。圧縮すると、2 枚目（色の残り）の誤差が、色に乗る | 色の標本は 4 画素に 1 つ。ADR 0002 の色の線（0.99）は、圧縮しなくても割る（下の「0.95 の出どころ」） |
| 復号の量 | 1 枚ごとに、同じ大きさの 4:2:0 を 2 枚。画素の数で 2 倍（3440×1440、毎秒 85 枚なら、3440×2880 を毎秒 85 枚と同じ量）。チップの資料の「8K60 decode」の、半分より下［資料：S2。計算で出した。実機の上限は a-5］ | 1 枚。いまの Mac と同じ |
| 遅延 | MS-RDPEGFX では、2 枚を 1 つのエンコーダーで 1 本の流れとして符号化し、1 つの復号器で解く［資料：S31］。だから、復号は順になり、1 枚ぶん延びる見込み。私たちの形にするなら、2 つの復号器で同時に解く道もある（a-5 の同時に開ける数しだい）。どちらでも、**戻す段（2 枚から 1 枚を組み立てる GPU の描き分け）が 1 つ増える**。復号の出力を、そのまま `SpatialExternalSurface` に出す形（4.1）は使えなくなる［不明。実機で測る］ | 増えない |
| ホストの仕事 | 新しく書く：4:4:4 の絵を 2 枚の NV12 に並べ替える段（GPU。GStreamer の既製の要素にはない見込み）、エンコーダー（MS-RDPEGFX の形なら 1 つで、毎秒 170 枚ぶんを符号化する。2 つに分けるなら、NVENC の同時のセッションの数に収まるか）、2 枚を同じ元の絵の組として送る取り決め、キーフレームの求めを 2 本に効かせること。片方が欠けたら、組み立てられない | いまの `--chroma 420` のまま。新しい部品は要らない |
| 採る前に要ること | **特許の様子**（下）。分からなければ、採らない | AURA の色の線を、別に決める（下） |

**案 (i) の仕組み**［資料：S31。仕様の文を写さず、要点だけを書いた］

- Microsoft の RDP の映像の拡張（MS-RDPEGFX）に、AVC444 と AVC444v2 がある。4:4:4 の 1 枚から、ふつうの 4:2:0 の絵を 2 枚作り、どちらも H.264（AVC）の 4:2:0 で圧縮する。
- 1 枚目（主の絵）は、ふつうの 4:2:0 である：明るさ（Y）は全部、色差（U、V）は、偶数の行と偶数の列の位置の値（なめらかにする処理を通したもの）。これだけを解いても、ふつうの 4:2:0 の絵として見られる。
- 2 枚目（補いの絵）は、1 枚目で落とした色差の標本を入れる。AVC444 では、2 枚目の「明るさ」の面に、U と V の奇数の行（16 行のまとまりの中で、8 行ずつ U と V）、2 枚目の「色差」の面に、偶数の行の奇数の列の U と V を入れる。1 枚目と 2 枚目を合わせると、色差が全部の画素ぶんそろう。AVC444v2 は、2 枚目の並べ方だけが違う。
- 2 枚は、同じ 1 つの H.264 のエンコーダーで、1 本の流れとして符号化し、1 つの復号器で解く、と仕様は決めている。
- 受ける側は、2 枚を解いてから、色差を元の位置に戻して 4:4:4 の 1 枚にする。1 つの知らせの中で、主の絵だけを送り、補いの絵をあとのフレームで送る（または補いの絵だけを送る）指定もある（`RFX_AVC444_BITMAP_STREAM` の `LC`）。絵が動いているあいだは主の絵だけ、止まったら補いの絵で色を足す、という使い方ができる。
- **HEVC で使えるか**：並べ替えは、コーデックによらない（4:2:0 の絵を 2 枚送るだけ）。だから HEVC の 4:2:0（Main）でも、形の上では同じことができる。ただし、MS-RDPEGFX が定めるのは H.264 である。HEVC で同じことをすれば、それは MS-RDPEGFX ではなく、Istesso の形式になる。**下の特許の約束が、仕様をそのとおりに実装した場合にだけ効く種類なら、HEVC の形は、その約束の外になる**（これは、法律の判断ではない）。
- FreeRDP（Apache-2.0）に、AVC444 の実装がある見込み（その API の文書が、検索の結果に出た［S32。開いていない］）。**この下調べでは、そのコードは読んでいない。** FreeRDP は、いま `docs/components.md` に載っていない。AGENTS.md の決まりでは、参照してよいのは「取り込める」に載せたものだけなので、読むなら、先にそこへ載せる（持ち主が決める）。

**案 (i) の特許の様子**（2026-11-18 に、公開のページで調べた。**法律の助言ではない。採るかどうかは、持ち主が決める。要るなら、専門家に聞く**）

- 題は「System and method for effectively encoding and decoding a wide-area network based remote presentation session」。出願人と、いまの権利者は Virtualinx Inc。出願 US 13/421,019（2012-03-15。優先日も同じ）、公開 2013-09-19［資料：S36］。

- 状態は「Expired - Fee Related」。4 年目の維持費は、遅れて追加の料金とともに払われた（2018-11-15）。その次の維持費が払われず、2023-03-27 に「維持費の不払いで失効」、2023-04-18 に、2023-02-17 からの失効が記録された。調整した満了日は 2033-06-28 と表示されるが、その前に失効している［資料：S36］。
- 家族（ほかの国の出願）は、Google Patents には米国の 2 件しか出ない［資料：S36］。

分かっていないこと：

- USPTO の公の記録では確かめていない。Patent Center のページは開けなかった（403）。Google Patents は、法的な状態は「推定で、法的な結論ではない」、権利者の表示は「不正確なことがある」と自ら書く。
- 米国では、維持費の不払いで失効した特許が、あとの申し立てで戻されることがある（一般の決まり。この特許について、戻された記録は Google Patents にない。USPTO では確かめていない）。
- 地図の 9 件のうち、US 9,749,646 のほかの 8 件の中身と状態は、見ていない。Microsoft の 2 件の、ほかの国の家族の状態も、見ていない。
- **どの請求項が、私たちの作り方（HEVC で、私たちの並べ方で）にかかるか**は、請求項を読んで比べることで、法律の判断になる。この下調べでは、していない。
- ほかの会社の特許は、探していない。
- FreeRDP が Apache-2.0 であることは、Microsoft の特許の許諾にはならない（Apache-2.0 の特許の許諾は、そのコードを寄せた人が持つ特許についてのもの）。

持ち主の決まり（はっきりしなければ、採らない）に当てはめると：**いまは、はっきりしない。だから、案 (i) は採らない。** 同じ考え方の Microsoft の特許が、Google Patents の表示では生きていて（満了は 2034〜2035 年の見込み）、仕様は無償の約束の外にある。私たちの形がそれにかからないと言うには、請求項を比べる判断が要る。案 (ii) が実機で足りなかったときに、もう一度考えるなら、そのときに、持ち主が（要るなら専門家と）決める。US 20130243076（US 8,958,474）は、表示のとおり失効しているなら、この判断を左右しない。

**案 (ii)：AURA の色の線を、別に決める**

- 基準は、**AURA の上の、ふつうのアプリの窓**（ふつうの Android XR のアプリ、たとえばブラウザーや写真を見るアプリが、同じ絵を出したもの）にする。ADR 0002 の 3 つ目の条件が「Mac の手元の窓」を基準にしているのと、同じ考え方である。AURA のふつうの窓も、光学系とパネルの拡大縮小を通るので、そこでにじむぶんは、Istesso のせいではない。
- 足りるかどうかは、実機で見る（1 章の b-5）。数字の線（たとえば、取り込んだ絵どうしの差）を置けるかは、AURA で窓を取り込めるか（`adb shell screencap` で、パネルの絵が取れるか）しだい［不明］。取れなければ、目で並べて見て、持ち主が決める。
- 決めた線は、M8 の ADR に書く。ADR 0002 の線（Mac）は、変えない。

**0.95 の出どころ**（2026-11-16 の画質の記録［読んだ：[記録](measurements/2026-11-16-quality.md) の「1. 上限：圧縮をせずに、色の変換だけを往復させる」、[ADR 0002](adr/0002-latency-first.md) の「画質の条件と、圧縮の設定」、`crates/istesso-measure/src/quality.rs`、`scripts/m1-quality.py`］）

- **線**：ADR 0002 の「色の SSIM が、悪いほうから 5% のフレームでも 0.99 以上」。
- **値**：0.9497（4:2:0。平均 0.9786、最悪 0.9459）。ADR 0002 と記録の条件の表にある「4:2:0 は、圧縮しなくても 0.95」は、この値を丸めたもの。4:4:4 は 0.9995。
- **何の値か**：元の絵と、戻した絵を、どちらも BT.709 の係数で、明るさと 2 つの色差（青の色差、赤の色差）に分ける。**色差は、全部の画素の大きさのまま比べる**（4:2:0 で落とした色が、にじみとして出る所を見るため）。SSIM は 8×8 の窓を 4 画素おきに取る。1 フレームの「色の SSIM」は、青の色差と赤の色差の SSIM の平均。「悪いほうから 5%」は、20 フレームに 1 枚がそれより下になる値。
- **絵**：判定の絵。テストアプリの色つきの文字が流れる絵（`--picture text`）、線の太さ 2 ピクセル、3440×1440、毎秒 85 枚。1,700 フレームを通し、あとの 850 フレームを集計した。
- **条件**：**圧縮していない。** ホストの GStreamer で、絵を 8 ビットの明るさと色差（16〜235。4:2:0 では NV12）に変え、GPU の変換（`cudaconvert`）で戻しただけ。だから、どれだけビットレートを上げても、この値は超えられない。
- **測ったか**：測った。計算で出した値ではない（ホストの Ubuntu、RTX 4090、GStreamer 1.24.2 で、`scripts/m1-quality.py` の、エンコーダーを通さない形）。
- 同じ記録のほかの値：線が 1 ピクセルなら 0.8921。4:2:0 を 30 Mbps で圧縮すると（キーフレームなし）0.9429。止めた絵（1600×720）を Mac の画面に出して取り込み、手元の窓と比べた値（4:2:0 で、青の色差 0.9835、赤の色差 0.9804）は、別の比べ方で、0.99 の線とは比べていない。
- **言えないこと**：この値は、元の大きさの絵どうしを比べたものである。AURA では、絵はパネルの大きさに縮められ、光学系を通る（b-2、b-3）。そこで、この差がどれだけ見えるかは［不明］。だから、案 (ii) では、線を AURA の上で決める。

### 4.3 つなぎ直し

いまの設計：切れたとみなすのは、失敗か、1 秒の沈黙。試みを重ねる（10 ms、50 ms、そのあと 0.1 秒おき、5 秒のあとは 0.5 秒おき。同時に 8 まで。1 回の試みの締め切りは 2 秒）。目標は「道がまた開いてから 1 秒以内に、つながり直す」（`reconnect-within-a-second` ブランチの ADR 0007、「つなぎ直しの試みを、重ねる」）［読んだ］。

| 項目 | Mac のクライアント | AURA のクライアント（Android） |
|---|---|---|
| 切れ方 | macOS が、アプリの登録で、ローカルネットワークの決まりを作り直す。眠る。基地局を移る | 画面を外した、眠った（Doze）、アプリが後ろに回った、Wi-Fi の基地局を移った、VPN がつなぎ直した。どれで、接続がどう切れるかは［不明］(e) |
| 後ろに回ったとき | 窓は残り、つながったまま | Android は、後ろのアプリのネットワークを絞る (e)。**絵は、見えていないなら要らない。** 後ろに回ったら、こちらから `detach` にあたることをして、ホストのエンコーダーを返すほうが、ねらいに合う（ADR 0015 の「止める、戻す、離す」）。前に戻ったら、すぐ始め直す |
| 「1 秒以内」に要るもの | 試みの間隔と締め切り | 加えて：Wi-Fi が戻ったことを、OS の知らせ（`ConnectivityManager` のネットワークの知らせ。この下調べでは、資料を開いていない）で受けて、**すぐ 1 つ試みを始める**（ADR 0007 の宿題の「向き」と同じ）。VPN の上では、VPN がつながり直すまで、道は開かない。VPN の再接続にかかる時間は、1 秒に入らないことがある［不明］ |
| 往復の長さ | 有線の LAN で 1 ms 未満 | VPN 越しの出先では、往復が数十〜数百 ms。**試みの締め切り（2 秒）で届くのは、往復 450 ms ほどまで**（ADR 0007 の値）。出先の基準は「快適に作業できること」で、有線の合格ラインの対象外（要件の 2 章） |
| 試み続けること | ホストがいないあいだ、0.5 秒おき | 電池が、Mac より効く。ADR 0007 の宿題（家の外で、試み続けるか）は、AURA では先に決める |
| 運び方 | TCP の上の通信路（ADR 0015） | 同じで始める。ただし、**出先を対象に入れると、ADR 0015 の「データグラムに移る条件」の 4 に当たる**（欠けるのがふつうの経路では、再送を待つ作りは使えない）。M8 の ADR で、もう一度比べる |
| 発見 | mDNS。手がかりとして受けるのは、直接つながっているネットワークの上のアドレスだけ（ADR 0007） | VPN 越しでは、mDNS は届かない。ペアリングのときのアドレスか、手で入れたアドレスを使う。家の中の Wi-Fi では、mDNS を受けるために、Android の決まり (e) に従う |

## 5. 持ち主への問いと、ADR で決めること

### 5.1 持ち主への問い

1. **AURA で、Istesso の窓を、ほかのアプリ（ブラウザーなど）と並べて使いたいか。** 資料のとおりなら、空間のパネルを窓ごとに出すには Full Space が要り、そのあいだ、ほかのアプリは隠れる（f-5）。**2026-11-18 の持ち主の追記**：Full Space では、AURA のふつうのアプリと並べられない。Home Space で、窓ごとに別のタスクを開く形なら並べられるかもしれない（4.1.1）。アプリから開けるかは、資料に書いていないので、実機で見る（f-6、f-7）。開けなければ、並べたいときは Home Space の 1 枚の窓（窓を中に並べる）で始めることになる。
2. **AURA で 4:4:4 が使えないとき、4:2:0 でよいか。** 4:2:0 は、ADR 0002 の色の線（悪いほうから 5% のフレームの色の SSIM が 0.99 以上）を、圧縮しなくても割る（判定の絵で 0.9497。4.2.1 の「0.95 の出どころ」）。**2026-11-18 の持ち主の追記**：案は 2 つ。(i) 4:2:0 の 2 枚に詰める（AVC444 の考え方。特許の様子が分からなければ、採らない）、(ii) 4:2:0 のまま、AURA の線を、AURA のふつうのアプリの窓を基準にして別に決める（b-5 で見る）。眼鏡の上では、光学系と拡大縮小で差が見えにくいかもしれない（b-3、b-5）。
3. **出先（VPN 越し）を、M8 の受け入れ条件に入れるか。** 入れると、ADR 0015 の「データグラムに移る条件」の 4 に当たり、運び方をもう一度比べることになる。家の中の Wi-Fi だけで始めるなら、いまの運び方のままで作れる。
4. **VPN は何を使うか。** 家の側に VPN の入り口があるか。WireGuard を勧める形にするか。Istesso が VPN を持ち込むことはしない、でよいか。
5. **AURA のアプリを、どこで配るか。** 自分で入れる（APK）だけか、Play ストアに出すか（M9）。
6. **adb を Mac に入れてよいか**（Android SDK の Platform-Tools）。1 章の多くの項目に要る。
7. **Android 向けのビルドの道具（NDK、Rust の Android の対象）を、どの PC に入れるか。** M8 の作る段で要る。
8. **AURA の画面のリフレッシュレート（たぶん 90 か 120）で、ホストを流してよいか。** いまは 85 に合わせてある。AURA に映すあいだだけ、ホストの枚数を変える形になる（4.2）。
9. **遅延の線を、AURA にも置くか。** 要件の合格ラインは、有線の Mac で決めている。AURA の家の中の Wi-Fi での目標（参考の値でよいか、線を置くか）を決める。

### 5.2 ADR で決めること（M8 の ADR の目次の案）

- 絵の形式の取り決め：`watch` に「受けられる形式」（コーデック、色の間引き、最大の大きさ、毎秒の枚数）を足す。ホストが選んで `stream` で答える。映す端末が変わったら、エンコーダーを開き直す（4.2）。**これは、AURA を作る前の、いまの設計（複数の窓、ADR 0015）に入れておくと、あとで作り直さずに済む。**
- 画質の条件：AURA で 4:2:0 にするときの線。基準は、AURA の上のふつうのアプリの窓（4.2.1 の案 (ii)）。案 (i)（2 枚に詰める）を採るかは、特許の様子が分かってから（4.2.1）。
- 窓の出し方：Home Space（1 枚のパネルに並べる）と Full Space（窓ごとのパネル）の 2 通りを持つか。パネルの大きさと、ホストに伝える画素の数の関係。
- 入力：Android のキーから Linux の番号への変換（スキャンコードを使えるか）。システムが取るキーの一覧。手のつまみを、ボタンとポインターに直す決まり。視線では「乗せる」ができないことへの対し方。
- 鍵の置き場：鍵の種をファイルに置き、Keystore の鍵で包む（3.3）。ADR 0006 の更新。
- 後ろに回ったとき、眠ったとき：`detach` にあたることを、クライアントから頼むか（4.3）。
- 発見：家の中は `NsdManager`（`ACCESS_LOCAL_NETWORK` の権限か、選ぶ画面）。VPN 越しは、覚えたアドレスか、手入力。
- 運び方：出先を対象にするなら、ADR 0015 の B、C、D をもう一度比べる。
- 配布：APK か、Play ストアか。マニフェストの宣言（`PROPERTY_XR_ACTIVITY_START_MODE`、`android.software.xr.api.spatial`）。
- Rust の側の形：`Paths` を `istesso-agent` から切り出すか。JNI の層を Rust で書くか、Kotlin から C の口を呼ぶか。復号器を Kotlin の側に持つか、NDK で Rust の側に持つか（3.4）。

### 5.3 この文書で、まだ開いていること

- 1 章の項目は、全部、実機待ちである。
- 2 章の Android の版（API レベル）は、どこにも書いていなかった。
- 3 章は読んだだけで、Android 向けにビルドしていない。
- Moonlight の Android 版など、GPL の受信側のコードは読んでいない（読まない決まり）。
- 4.2.1 の案 (i)（2 枚に詰める）の特許：USPTO の公式の記録、Microsoft の地図の 9 件のうち 8 件の中身と状態、ほかの国の家族の状態、請求項と私たちの作り方の比べ（法律の判断）、ほかの会社の特許。**持ち主の決まりで、いまは採らない。**
- 4.1.1 の Home Space の形：アプリが自分で別のタスクの窓を開けるか、何枚までか、キーボードがどの窓に届くか。資料に書いていない（f-6、f-7）。
