# ADR 0006：ペアリングの方式

- 状態：採用（公開前に外部レビューを受ける）
- 日付：2026-11-15

## 背景

端末同士のリンクは、簡単で、かつ安全でなければならない。この仕組みは入力の送信やアプリのインストールまでできるので、信頼の入口は最も慎重に作る。

## 決定

### 手順

1. ホスト側が8文字のコードを表示する（Crockford base32、40 ビット。`ABCD-EFGH` の形）。
2. 両者がそのコードで SPAKE2 を実行する。コードが同じときだけ同じ共有鍵になる。
3. 共有鍵から、方向ごとの鍵を HKDF で導く。
4. 各端末が、長期公開鍵（Ed25519）と、手順の写し（transcript）への署名を、方向ごとの鍵で暗号化して送る。
5. 受け取った側は、復号と署名の検証に成功したら、相手の公開鍵を固定して保存する。
6. 以後の接続は、固定した公開鍵で相互認証する。保存した記録を消すと失効する。

### 性質

| 脅威 | 対応 |
|---|---|
| 盗聴してコードを総当たりする | SPAKE2 は、盗聴した内容からオフラインで推測を試す手段を与えない |
| コードを知らずに割り込む | 共有鍵が一致せず、復号に失敗する |
| オンラインで何度も試す | 1つのコードで受け付けるのは1回だけ。失敗したらコードを作り直す。有効期限あり |
| 送ったメッセージを送り主に送り返す | 鍵が方向ごとに違うので復号できない。SPAKE2 のメッセージの反射も拒否する |
| 他人の公開鍵を自分のものとして登録する | 手順の写しへの署名で、秘密鍵を持っていることを証明させる |
| 別の回の署名を使い回す | 署名は、その回の手順の写しと役割に結び付いている |
| 表示名に制御文字などを入れる | 名前は長さと文字種を検査する |

### 権限

新しくペアリングした端末の権限は「閲覧」と「操作」だけ。インストール、USB、音は個別に許可する。

許可と取り消しは、許可を与える側の PC で、人が行う（`istesso peers allow <端末> <権限>`、`istesso peers deny <端末> <権限>`。`istesso peers list` で、いまの権限を見られる）。

- 書き換えるのは、その PC が保存している相手の記録だけである。相手の端末とは通信しない。ペアリングの手順（プロトコル）は変わらない。
- 相手を、指紋か名前で指定する。同じ名前の端末が複数あるときは、指紋で指定する。
- 変更は、遅くとも相手の次の接続から効く。接続が続いているあいだも記録を読み直すのは、いまは次の二つだけである。
  - 映像の送り出し（`istesso-media` のホスト）。0.25 秒ごとに「閲覧」を確かめ、なくなっていたら切る。
  - エージェントが入力を受け取る接続。1 秒ごとに「操作」を確かめ、なくなっていたら切る。
- エージェントのそのほかの問い合わせ（一覧など、「閲覧」で答えるもの）は、接続を受け付けたときに読んだ記録で答え続ける。そこでの「閲覧」の取り消しは、その端末の次の接続から効く。続いている接続のあいだにも読み直すのは、これからの課題である。
- 「閲覧」も取り消せる。取り消すと、その端末は何もできなくなる。ペアリングそのものを消す（`istesso peers remove`）のとは違い、記録は残る。
- 同じ端末をペアリングし直すと、記録は新しく作り直され、権限は初めの「閲覧」と「操作」に戻る。それまでに与えた権限や取り消した権限は引き継がない。
- 記録を書き換える処理（ペアリング、`peers allow`・`deny`・`remove`）は、記録のファイルの錠を取り、ファイルを読み直したうえで変えて書き戻す。`istesso pair host` が相手を待つあいだに `peers deny` で権限を取り消しても、ペアリングが済んだときに、その取り消しが元に戻ることはない。錠を取るのは、macOS と Linux（Unix）だけである。ほかの OS では錠がなく、書き戻す直前に読み直すだけなので、同時に書くと、あとから書いたほうが残る。

## 既知の不足（公開前に対応する）

- `spake2` クレートは第三者の監査を受けていない（作者が明記している）。外部レビューを受ける。
- 端末の秘密鍵を、所有者だけが読めるファイルに置いている。OS のキーチェーンへ移す。
- ペアリングの手順は平文の TCP の上を流れる（手順そのものが内容を守る）。ペアリング後の通信は ADR 0007 の制御チャンネルを使う。
- 最後の確認応答（`OK`）は認証していない。割り込まれると、片方だけが相手を保存した状態になり得る。相手の鍵の検証は済んでいるので安全性には影響しないが、認証つきの応答へ置き換える。
- ペアリング相手の自動発見と QR はまだない（ペアリング後のアドレスの発見は ADR 0007）。
- 出先からのペアリングは想定しない（VPN 越しの LAN 内だけ）。

## 【提案】ペアリングのときに、渡す権限を選ぶ。「シェル」を足す（2026-11-21）

状態：**【提案】**。採用されるまで、上の「権限」の節が正本である。作る前に、この節を、上の「権限」の節に入れて書き直す（上の「変更の手順」と、AGENTS.md の 4）。

【決定】（2026-11-21）**持ち主の決め（ADR 0026 の【問い 範8】の答え。言葉のまま）：** 「はい。「シェル」の許可（その端末からターミナルを開いてよいか）を 1 つ足す。渡し方は、手間を増やさない形で。ペアリングのときに、渡す許可（見る、操作する、シェル）を一緒に選べる。AURA の初めの印は「シェルは切」で、その場で入れられる。あとから入れたり切ったりするのは、Air の設定で、持ち主の確かめ（Touch ID）1 回。ホストの前に行かなくてよい形に（範6、決定 14 の見直しと合わせて）。自分は、あとから切り替える場面をあまり思いつかない。なので、ふだんは目に入らない所に置くだけでよい。作り込みは後回しで、ペアリングのときに選べることを先に。」

ADR 0021（`m5-design`）、ADR 0025 と ADR 0026（`design-workspace-stage` の系列）は、まだ `main` にないので、番号で指す。

1. 【決定】（2026-11-21）権限の一覧に「シェル」を足す（ADR 0026 の範8）。【決定】（2026-11-21。範8 の「はい」＝(a)）「シェル」には、その端末からこのホストでシェルを開く、コマンドを動かす、コーディングエージェントを範囲つきで起動する、転送を受けることを含める。マウントで見ることは、「ファイル」（ADR 0013）のまま。
2. 【決定】（2026-11-21）ペアリングのとき、持ち主がその場で、渡す権限（見る＝閲覧、操作、シェル）を選ぶ（範8）。【決定】（2026-11-21）「シェル」の初めの印は、AURA を含むどの端末でも「切」で、端末の種類で分けない。渡すときだけ、持ち主がその場で入れる（ADR 0026 の範17）。【提案】見る・操作の初めの印は、この文書と、ADR 0021 の決定 13 の (2)（Mac のホストでは「閲覧」だけ）のとおり。【決定】（2026-11-21。別の見直しで出た問いへの持ち主の答え）「見る」（閲覧）の権限を外したら、「シェル」も使えなくする。【提案】形：「見る」のない端末には、「シェル」を渡さず、続いている接続の読み直し（下の 5）でも、「見る」がなければ切る。「操作」だけあって「見る」がない機器には入力を渡さない、と同じ考えである（何が開いているかを見られない端末から、シェルを開かせない）。
3. 【決定】（2026-11-21）相手の鍵を確かめ、名前が分かったあと、記録に書く前に、ホストの側（コードを出している画面か、`istesso pair host` を打ったターミナル）で選ぶ（ADR 0026 の範18）。【決定】（2026-11-21）ペアリングの手順（上の 1〜6）とメッセージは変えず、プロトコルの版も上げない。【提案】ペアリングのときの選び（とくに「シェル」を入れること）は、ADR 0021 の同じユーザーの線の 7（ペアを足す、権限を与えるときは、持ち主がいることを確かめる）の確かめを通ったあとにだけ出す。`istesso pair host` を打ったターミナルで選ぶときも同じである。同じユーザーのほかのプログラムが、持ち主のいないところで「シェル」を入れられないようにするため。
4. 【決定】（2026-11-21）Air の設定では、持ち主のどの端末（AURA を含む）の「シェル」も、Touch ID を 1 回通せば入れたり切ったりできる（ADR 0026 の範19）。【決定】（2026-11-21）あとから切り替える口は、ふだんは目に入らない所に置き、作り込みは後回しにする。【提案】ホストの前に行かずに切り替えるには、上の「権限」の節と、ADR 0021 の決定 14（与えるのは、ホストにいる持ち主だけ）の見直しが要る。範囲を広げるときの持ち主の確かめ（ADR 0026 の範6）も踏まえて、決定 14 をどう変えるかは M5 で決める。作る前に、この文書と ADR 0007（権限を変える頼みのメッセージ）を書き直す。
5. 【提案】**続いている接続で読み直すもの**に、シェルの接続と転送の接続を足す（いまは、映像と入力だけ）。どちらの接続でも、読み直すのは「シェル」の権利と、それを使える前提の「閲覧」である（上の 2 の決定。「操作」は、シェルと転送の門ではない）。外したら、遅くとも 1 秒で切る（ADR 0025 の 2.3 と、進め方の案の W2 の 3）。
6. 【提案】ペアリングし直したときの権限（上の「権限」の節：初めの値に戻る）は、新しい形では、「ペアリングのときに、もう一度選ぶ」になる。

## 【提案】遠くから外す（2026-11-21）

状態：**【提案】**。採用されるまで、上の「権限」の節が正本である。作る前にこの ADR と ADR 0007 を書き直し、コードを `main` に入れる前に Fable のレビューを受ける（ADR 0021 の 2026-11-19 の決め）。

- 【決定】（2026-11-21）遠くから端末のペアリングを外せるようにする（ADR 0021 の問い 17。持ち主の 2026-11-19 の案を採る）。【決定】（2026-11-21）外すための権限は足さず、1 台の端末が短い間に外せる台数にだけ上限を置く。【決定】（2026-11-21）外したら、ほかの端末に知らせる。【決定】（2026-11-21）自分自身はいつでも外せる。
- 【決定】（2026-11-21）外したことはほかのホストに伝え、知らせを信じるのはペアリング済みのホストから来たときだけとする（ADR 0021 の問い 21）。【決定】（2026-11-21）眠っていたホストは、起きたらまず常時稼働のホストに聞いて確かめる。【決定】（2026-11-21）元に戻す操作はほかのホストに伝えず、その機械の前で行う。
- ADR 0021 の「ホストの中の口」の抑え方から、作る前に、この節の決まりとして写すもの（2026-11-19 の【提案】。この節は、それを前提にする）：
  1. **遠くから外すのは、`deny`（権限を外す、ペアリングを止める）で、記録は残す。** `remove`（記録を消す）は、ホストにいる持ち主だけ。だから、ホストにいる持ち主が、1 つのコマンドで戻せる（ペアリングのやり直しは要らない）。
  2. **権限を外された端末は、外す頼みを送れない。** `deny` された端末はハンドシェイクは通る（`istesso-pair` の `is_trusted` は、記録があるかだけを見る）ので、外す頼みは、権限で断る（外す頼みにも「閲覧」を要る、など）。
- 【提案】上の「相手の端末とは通信しない」と「許可と取り消しは、許可を与える側の PC で、人が行う」に、この節ではペアリングを外すときだけ例外を設ける。許可を与えるのはホストの側のままとする（ADR 0021 の決定 14。「シェル」の切り替えと合わせて見直す）。ペアリングの手順（`istesso-pair-v1`）は変えず、外したことを伝えるメッセージは ADR 0007 で扱う。
