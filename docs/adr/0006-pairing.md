# ADR 0006：ペアリングの方式

- 状態：採用（公開前に外部レビューを受ける）
- 日付：2026-11-15
- 更新：2026-11-20（鍵とペアの一覧の置き場所を、1 つの口にまとめた。置き場所を移す形は【提案】で、まだ決まっていない。ペアリングの手順とプロトコルの版は変えていない）

## 背景

端末同士のリンクは、簡単で、かつ安全でなければならない。この仕組みは入力の送信やアプリのインストールまでできるので、信頼の入口は最も慎重に作る。

## 決定

### 手順

1. ホスト側が8文字のコードを表示する（Crockford base32、40 ビット。`ABCD-EFGH` の形）。
2. 両者がそのコードで SPAKE2 を実行する。コードが同じときだけ同じ共有鍵になる。
3. 共有鍵から、方向ごとの鍵を HKDF で導く。
4. 各端末が、長期公開鍵（Ed25519）と、手順の写し（transcript）への署名を、方向ごとの鍵で暗号化して送る。
5. 受け取った側は、復号と署名の検証に成功したら、相手の公開鍵を固定して保存する。
6. 以後の接続は、固定した公開鍵で相互認証する。保存した記録を消すと失効する。

### 性質

| 脅威 | 対応 |
|---|---|
| 盗聴してコードを総当たりする | SPAKE2 は、盗聴した内容からオフラインで推測を試す手段を与えない |
| コードを知らずに割り込む | 共有鍵が一致せず、復号に失敗する |
| オンラインで何度も試す | 1つのコードで受け付けるのは1回だけ。失敗したらコードを作り直す。有効期限あり |
| 送ったメッセージを送り主に送り返す | 鍵が方向ごとに違うので復号できない。SPAKE2 のメッセージの反射も拒否する |
| 他人の公開鍵を自分のものとして登録する | 手順の写しへの署名で、秘密鍵を持っていることを証明させる |
| 別の回の署名を使い回す | 署名は、その回の手順の写しと役割に結び付いている |
| 表示名に制御文字などを入れる | 名前は長さと文字種を検査する |

### 権限

新しくペアリングした端末の権限は「閲覧」と「操作」だけ。インストール、USB、音は個別に許可する。

許可と取り消しは、許可を与える側の PC で、人が行う（`istesso peers allow <端末> <権限>`、`istesso peers deny <端末> <権限>`。`istesso peers list` で、いまの権限を見られる）。

- 書き換えるのは、その PC が保存している相手の記録だけである。相手の端末とは通信しない。ペアリングの手順（プロトコル）は変わらない。
- 相手を、指紋か名前で指定する。同じ名前の端末が複数あるときは、指紋で指定する。
- 変更は、遅くとも相手の次の接続から効く。接続が続いているあいだも記録を読み直すのは、いまは次の二つだけである。
  - 映像の送り出し（`istesso-media` のホスト）。0.25 秒ごとに「閲覧」を確かめ、なくなっていたら切る。
  - エージェントが入力を受け取る接続。1 秒ごとに「操作」を確かめ、なくなっていたら切る。
- エージェントのそのほかの問い合わせ（一覧など、「閲覧」で答えるもの）は、接続を受け付けたときに読んだ記録で答え続ける。そこでの「閲覧」の取り消しは、その端末の次の接続から効く。続いている接続のあいだにも読み直すのは、これからの課題である。
- 「閲覧」も取り消せる。取り消すと、その端末は何もできなくなる。ペアリングそのものを消す（`istesso peers remove`）のとは違い、記録は残る。
- 同じ端末をペアリングし直すと、記録は新しく作り直され、権限は初めの「閲覧」と「操作」に戻る。それまでに与えた権限や取り消した権限は引き継がない。
- 記録を書き換える処理（ペアリング、`peers allow`・`deny`・`remove`）は、記録のファイルの錠を取り、ファイルを読み直したうえで変えて書き戻す。`istesso pair host` が相手を待つあいだに `peers deny` で権限を取り消しても、ペアリングが済んだときに、その取り消しが元に戻ることはない。錠を取るのは、macOS と Linux（Unix）だけである。ほかの OS では錠がなく、書き戻す直前に読み直すだけなので、同時に書くと、あとから書いたほうが残る。

## 鍵とペアの一覧の置き場所（【提案】、2026-11-20）

端末の鍵を持つ者は、ペアの相手から見て、この端末そのものになる。ペアの一覧を書ける者は、だれがこの端末を見てよいか、操作してよいかを決められる。どちらも、同じ重さで守る（ADR 0021「隔離と、机と同じ設定を両立させる」の、同じユーザーのほかのプログラムへの守り。ブランチ `m5-design`）。場所を外から受けないこと（引数、環境変数）は、先に済んでいる。ここは、その後半である。

### 作ったもの：1 つの口

- 鍵とペアの一覧を読む・書く所を、`istesso-pair` の 1 つの口（`Keeping`）にまとめた。`istesso`、エージェント、映像のライブラリは、この口だけを通る。鍵のファイルや一覧のファイルを、口の外から直に開く所は、もうない。
- 口の形は、**組み立てるときに決まる。** 引数、環境変数、ファイルでは変えられない（許可を持つプログラムは、起動した者から何も受けない）。
- **既定は、いままでどおりのファイル**（`identity.key` と `peers.json`、持ち主だけが読める 0600、同じ錠のファイル、同じ書き方）。ふるまいは変わらない。
- ファイルの形は、**同じユーザーのほかのプログラムから、鍵も一覧も守れない**（読める。書ける）。この形の版は、`istesso doctor` と、エージェントの起動のときに、標準エラーへ 1 行でそう言う。`istesso doctor --json` の中身（ペアの相手に送る役割表と同じもの）には入れていない。入れるなら通信の項目が増えるので、ADR 0007 を先に直す。
- Linux には、同じユーザーの中で鍵を守れる置き場所がない。専用ユーザーに分けるまで、ファイルのままで、上の 1 行を出す。

### 【提案】macOS：ログインのキーチェーン（組み立ての切り替え `login-keychain`）

持ち主が決めるまで（ADR 0021 の問い 27）、既定では入らない。`--features login-keychain` で組み立てた macOS の版だけが、この形になる。

- 鍵と一覧を、ログインのキーチェーンの項目 2 つにする（一覧は、ファイルと同じ JSON を、そのまま 1 つの項目に入れる）。項目は、OS の既定の決まりで作る：**作ったプログラムは問いなしで読める。ほかのプログラムが読もうとすると、OS が持ち主に問う。**
- **ファイルからは、何も取り込まない**（見直しで直した。最初の下書きは、項目がなければ、前の版のファイルを自動で移していた）。鍵のファイルも、一覧のファイルも、同じユーザーのどのプログラムも、決まった場所に置ける。最初の起動の前に置くことも、項目を消してから置くこともできる。それを取り込むと、そのプログラムの鍵がこの端末の鍵になり、そのプログラムの一覧が、この端末の信じる相手になる。だから、
  - この形の版は、ファイルの形の場所にある鍵と一覧を、**読まない。**
  - その場所に何か（ファイル、リンク、フォルダー）があるあいだは、**鍵も一覧も渡さずに、理由を言って止まる**（最初の起動でも、あとから置かれたときでも）。持ち主が取り除いたら、進む。
  - 項目がないとき、鍵は新しく作る。一覧は空になる。つまり、**ファイルの形からこの形に替える端末は、新しい鍵になり、ペアリングをやり直す**（相手の側では、古い鍵のペアリングを解く。古い鍵のファイルの写しが、どこかに残っているかもしれないため）。
  - 鍵を持ったまま移す道は、持ち主がそこにいることを確かめられるようになってから作る（閉じる順番の 3。同じユーザーのプログラムは、コマンドも、端末の窓も、まねできるので、いまは「持ち主が頼んだ」ことを確かめられない）。
- 一覧を書き換えるときの錠は、いままでと同じ錠のファイルを使う（中身は空）。
- この形の版も、守れないことを 1 行で言う（`istesso doctor` と、エージェントの起動のとき）：読むときは OS が持ち主に問うが、ほかのプログラムが、先に項目を作る、書き換える、消すことは、止められないかもしれない（下の「この形で守れないこと」）。
- この形になるのは、**アカウントの決まった場所**の鍵と一覧だけ。テストと、開発用の版（`dev-paths`）は、いつもファイルを使う（走らせた人のキーチェーンに触らないため）。`login-keychain` と `dev-paths` を一緒に付けると、組み立てが止まる。
- macOS のほかでは、この切り替えを付けると、組み立てが止まる（黙ってファイルに戻らない）。
- 使うのは、OS の Security フレームワークだけ（プロセスの中から呼ぶ。`security` コマンドは使わない）。暗号の部品は足していない。

### この形で守れないこと（同じユーザーのほかのプログラムに対して）

ログインのキーチェーンの既定の決まりは、**読むこと**を、作ったプログラムに限る。次のことは、この形では閉じていない。

1. **先に項目を作ること。** プログラムは、項目を作ったのがだれかを見ていない（読めたものを、そのまま使う）。同じユーザーのプログラムが、この端末より先に、同じ名前の項目を、自分も読める決まりで作っておけば、その鍵と一覧が使われる。あとから書き足したものも、そのプログラムに読める。見分けるには、項目の決まり（だれが問いなしで読めるか）を読んで、自分だけであることを確かめる必要がある。古い形のキーチェーンの口でできる見込みだが（考え）、動かして確かめられないあいだは、作らない。
2. **書き換えること、消すこと。** ほかのプログラムが、項目の中身を書き換える、項目を消すときに、OS が問うかは、確かめていない。問わないなら、一覧を自分の端末入りのものに差し替えられる。消されたときは、この端末は、新しい鍵と空の一覧で始まる（ファイルは取り込まないので、置かれた鍵や一覧が信じられることはない。ペアリングは失われる）。消したあとに、1 のとおり項目を作られたら、それが使われる。
3. だから、**この形が守るのは、鍵を読まれること（持ち出されること）まで**で、一覧を書き換えられないこと（ADR 0021 の「守るもの」の 2）は、この形だけでは言えない。

| 版 | できること | できないこと |
|---|---|---|
| 自分で組み立てた版（署名なし、ad hoc の署名） | ファイル（既定）。この切り替えを付ければ、読むときの問い。ただし、組み立て直すたびに別のプログラムになり、そのたびに問いが出る見込み | 先に作られること、書き換え、削除を止めること。項目を作った者の確かめ |
| 自分の証明書で署名した版 | 読むときの問い（版を上げても、同じプログラムとして読める見込み）。項目の決まりを確かめる形を足せば、1 を見分けられる見込み（作っていない） | 同じ証明書で署名したほかのプログラムからの守り。署名の鍵を、同じユーザーのプログラムが問いなしで使えるなら、何も守れない |
| 公式に署名して配る版（チームの署名とエンタイトルメント） | データ保護のキーチェーンの、アクセスのグループ（ADR 0021 の K3）：同じグループのプログラムのほかは、読むことも、書くことも、消すことも、同じ名前で作ることもできない見込み（【調べる】Developer ID の配り方で使えるか） | — |

- 一覧を守るには、K3 か、書くときの持ち主の確かめ（閉じる順番の 3）か、一覧に、鍵から作った印を付けて読むたびに確かめる形（ADR 0021 の L2。鍵を読めない者は、印を作れない。ただし 1 のとおり鍵ごと作られたら、効かない）が要る。どれも、この版には入れていない。

### 確かめていないこと（この形を既定にする前に、確かめる）

**キーチェーンに触る部分は、一度も動かしていない。** 組み立てが通ることと、キーチェーンの代わりにメモリーの入れ物を使ったテスト（新しい鍵を作る、読み戻す、一覧を書き換える、ファイルを断る）だけを見た。動かすと、持ち主のキーチェーンに項目が増え、画面に問いが出うるので、持ち主の了解のあとで、決めた機械の上で、テスト用の名前の項目だけを使って確かめる（この端末の本物の項目には触らない。作った項目だけを消す）。

1. **書き換えと削除が、問いなしでできないか**（上の 2）。
2. **先に作られた項目を、見分けられるか**（上の 1）。
3. **署名とのかかわり。** 証明書で署名した版は、版を上げても同じプログラムとして読める見込み。ad hoc の署名の版は、組み立て直すたびに別のプログラムになり、そのたびに問いが出る見込み。`istesso` と、映像のライブラリを入れたアプリは別のプログラムなので、それぞれ 1 回ずつ問いが出る見込み。
4. 持ち主が問いに「常に許可」と答えれば、そのプログラムは読める。問いに慣れると、守りは弱まる。
5. 前の版のファイルの写し（バックアップなど）は、消えない。この形に替えるときは、新しい鍵になるので、相手の側で古いペアリングを解けば、写しは使えなくなる。
6. どの形でも、鍵は、使うあいだはプロセスの中にある。デバッガーでつなげるプログラムからは、取れる。
7. **遅延。** 入力の接続と、映像を出す側は、流れているあいだ、1 秒おきに一覧を読み直す（ADR 0007）。ファイルの形では、いままでと同じ読み方で、遅延は変わらない見込み（計っていない）。キーチェーンの形では、その読み直しが、OS のキーチェーンの係への問い合わせになる（ファイルの形の場所に何もないことの確かめも、そのたびに 1 回入る）。入力を渡すスレッドの上で、どれだけ待つかは、計っていない。既定にする前に、計る（AGENTS.md の 3）。

### 決まっていないこと

- どの配り方の版を、どの形にするか（ADR 0021 の問い 26、27）。決まるまで、既定はファイルのまま。
- ファイルの形から替えるときに、ペアリングをやり直す形のままでよいか。鍵を持ったまま移す道を作るなら、持ち主がいることの確かめ（閉じる順番の 3）と一緒に作る。
- ペアを足すとき、権限を与えるときの、持ち主がいることの確かめ（閉じる順番の 3）。同じユーザーのプログラムは、いまも `istesso pair` を自分で動かせる。置き場所を移すだけでは、これは止まらない。

## 既知の不足（公開前に対応する）

- `spake2` クレートは第三者の監査を受けていない（作者が明記している）。外部レビューを受ける。
- 端末の秘密鍵とペアの一覧を、所有者だけが読めるファイルに置いている。同じユーザーのほかのプログラムは、読めて、書ける。OS のキーチェーンへ移す形は、上の「鍵とペアの一覧の置き場所」（【提案】。組み立ての切り替えの中にあり、既定ではない）。
- ペアリングの手順は平文の TCP の上を流れる（手順そのものが内容を守る）。ペアリング後の通信は ADR 0007 の制御チャンネルを使う。
- 最後の確認応答（`OK`）は認証していない。割り込まれると、片方だけが相手を保存した状態になり得る。相手の鍵の検証は済んでいるので安全性には影響しないが、認証つきの応答へ置き換える。
- ペアリング相手の自動発見と QR はまだない（ペアリング後のアドレスの発見は ADR 0007）。
- 出先からのペアリングは想定しない（VPN 越しの LAN 内だけ）。
