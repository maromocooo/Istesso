# ADR 0013：統合ストレージは、一覧と合算から作る。中身は、人が名指ししたコピーから始める

- 状態：提案（M5 の設計の段階。案の選び方は、申し送りのねらいに合わせた。「採用」に変えるのは、人が読んだあと）
- 日付：2026-11-16
- 追記（2026-11-19）：持ち主が、プロジェクトのフォルダー（作業場）について決めたことと、この文書との食い違いは、[ADR 0025](0025-workspace-terminal-ports.md) の「1.4 ADR 0013 との突き合わせ」にある。**この文書の決定は、変えていない。**

## 背景

R-06（統合ストレージ）は、3つを求めている。

1. 各 PC に、この仕組み専用の隔離領域を用意する。
2. 隔離領域を束ね、合計容量として見せる。
3. 実体のある PC が停止中のファイルは、「取得できない」と分かる表示にする。

[architecture.md](../architecture.md) は、これを「既存のファイル共有と union マウントを束ねる」と書いている。M5 の設計のために、この形を調べ直した。

2026-11-16 に、M5 の扱いが決まった。今週は設計まで。実装は試験用のフォルダーの中だけで動かし、ふだんのファイルには触れない。ねらいは、**ファイルが消える、壊れる事故を避けること**で、ここだけは急がない（[milestones.md](../milestones.md)）。決めごとで判断がつかないときは、ねらいに合うほうを選ぶ決まりである。

同じ申し送りは、使い手が開発者に限らないことも伝えている。導入のかんたんさと、説明なしで使えることを、重く見る。

隔離領域そのもの（専用ユーザーのホーム）は [ADR 0003](0003-isolation.md) が決めている。作り方は [ADR 0014](0014-dedicated-user-in-practice.md) で扱う。この文書は、領域を束ねる部分だけを扱う。

## 調べてわかったこと

「既存のファイル共有と union マウント」の形について。実機では試していない。

| 項目 | 内容 |
|---|---|
| 信頼の仕組みが2つになる | OS のファイル共有は、相手をパスワード（SMB）、アドレス（NFS）、SSH の鍵（SFTP）で確かめる。どれも、ペアリング（R-13）とは別の仕組みである。一覧から端末を失効させても、ファイルの共有は切れない。端末ごとの権限も効かない |
| 権限 | 共有を出す設定にも、マウントにも、たいてい root か管理者が要る |
| macOS で束ねられない | Linux には、複数のフォルダーを1つに束ねる仕組みがある（カーネルの overlayfs、FUSE の mergerfs）。macOS には、ネットワークの共有を束ねるのに使える標準の仕組みが見当たらない（`mount` の `union` の指定は残っているが、この用途で使えるかは確かめていない）。FUSE を足すには、他社の部品が要る |
| 止まっている PC | ネットワークのマウントは、相手が止まると、開こうとしたアプリごと待たされることがある。「取得できない」という表示は、OS の共有からは出てこない |
| ライセンス | Linux で SMB を出す Samba は GPL-3.0、SSH の上でマウントする sshfs は GPL-2.0。別のプログラムとして動かすだけなら、取り込みにはならない。ただし、利用者が入れた GPL のソフトに機能を頼る使い方は、いまは認めない方針である（[requirements.md](../requirements.md) の 7）。カーネルの機能（NFS、overlayfs）は、OS の機能として使える |
| 事故の起きやすさ | マウントした場所は、アプリから見ると、ふつうのフォルダーと同じである。まちがって消す、上書きする、書いている途中で切れて壊れる、が起きる |

## 比べる案

- **A：既存のファイル共有と union マウント。** architecture.md の、いまの記述。
- **B：一覧と合算を制御チャンネルで作る。** 中身は、自前の受け渡しで運ぶ。マウントは最後に回す。
- **C：同期。** 各 PC が、全部の写しを持つ。

| 観点 | A：共有と union | B：一覧と合算から | C：同期 |
|---|---|---|---|
| 合計容量として見せる（R-06） | 満たす | 満たす | 満たさない。どの PC も全部を持つので、容量は足し算にならない |
| 「取得できない」の表示（R-06） | 別に作る | 一覧の仕組みから出る。アプリ一覧の「！」と同じ作り | 要らない。写しが手元にある |
| 相手の確かめ方、失効、端末ごとの権限 | 別の仕組みになる | ペアリングの鍵と権限を、そのまま使う | 部品しだい |
| 要る権限 | root か管理者 | 段階 1 と 2 では要らない | 要らない |
| アプリからの使い勝手 | ふつうのフォルダーとして開ける | 段階 2 までは、手元へ写してから開く | ふつうのフォルダーとして開ける |
| 事故 | 起きやすい | 段階 1 は読むだけ。段階 2 は、消さない、上書きしない決まりで縛れる | 消した操作が、全部の PC に広がる |
| 自前のコード | 少ない | 多い | 少ない |
| macOS | 束ねる仕組みがない | 動く | 動く |

## 提案

**B を、3つの段階に分けて進める。段階 3（マウント）の方式は、いまは決めない。**

| 段階 | できること | 触るもの |
|---|---|---|
| 1. 一覧と合算 | 全部の PC の領域にあるファイルを、1つの一覧で見る。合計の容量と空きを見る。止まっている PC のファイルに印が付く | 読むだけ |
| 2. 名指しのコピー | 人が名指ししたファイルを、ほかの PC から手元へ写す（取得）。手元のファイルを、ほかの PC へ送る（受け渡し） | 領域の中に、新しいファイルを作るだけ。消さない。上書きしない |
| 3. マウント | アプリが、ほかの PC のファイルを、ふつうのフォルダーとして開く | 方式を、別の ADR で決める |

理由：

1. **R-06 が求めている3つは、段階 1 で満たせる。** 一覧、合計容量、「取得できない」の表示は、どれも名前と大きさの話で、ファイルの中身に触らない。
2. **事故が起きるのは、中身を書くところである。** そこをいちばん後ろに回し、使ってみた結果を見てから方式を決める。A はマウントから始まり、C は、消した操作が全部の PC に広がる。**ねらい（事故を避ける。急がない）に合うのは、B である。** この選び方は、ねらいから決めた。
3. **信頼の仕組みを増やさない。** 相手の確かめ方、失効、端末ごとの権限は、ペアリングと制御チャンネル（[ADR 0006](0006-pairing.md)、[ADR 0007](0007-control-channel.md)）にすでにある。
4. **Mac と Linux で同じ作りにできる。** A は、macOS で束ねる部分が作れない。

### 何を、どこに置くか

領域の根は、専用ユーザーのホームである（ADR 0003）。試すあいだは、試験用のフォルダーを根にする（[m5-plan.md](../m5-plan.md) の「7. 試験用のフォルダーで試す」）。

| 場所（根からの相対） | 中身 | ほかの PC から |
|---|---|---|
| `.istesso-area` | 印。領域の ID、作った日時、形式の版。これがないフォルダーを、領域として扱わない | 見えない |
| `files/` | 統合ストレージに出すファイル | 権限を持つ端末から、一覧と取得ができる |
| `inbox/` | ほかの端末から届いたもの。振り分けたインストーラー（R-05）も、ここに届く | 受け渡しの行き先になる。一覧は出さない |
| 根の下の、それ以外 | アプリの設定とキャッシュ、コーディングエージェントの作業場所 | 見えない |
| Istesso 自身の設定（端末の鍵、ペアリングの一覧）とキャッシュ | OS の決まった場所。いまと同じ（`istesso id` が表示する）。`files/` の下には置かない | 見えない |

コーディングエージェントの作業場所を `files/` に入れないのは、ビルドの生成物で一覧が膨らむためである。ほかの PC から見たいものだけを、`files/` に置く。

### 段階 1：一覧と合算

- 各ホストのエージェントが、制御チャンネルで2つの問い合わせに答える。メッセージの追加なので、通信路の版は上げない（ADR 0007）。
- ホストに誰もログインしていなくても、答える（2026-11-16 の決定。ホストは、画面の前に誰も座っていない状態がふつうである）。そのために、エージェントが、ログインなしで動く形で常駐していること（ADR 0014）。ディスクの暗号化が解除されていないホストは、止まっているホストと同じに見える。
  - `storage`：領域が載っているファイルシステムの全体と空き、`files/` が使っている量。
  - `files`：`files/` の下の、フォルダー1つぶんの一覧。相対パス、種類（ファイル、フォルダー、リンク）、大きさ、更新時刻。フォルダーごとに聞くので、1回の答えが大きくなりすぎない。
- 手元のコマンドが、全部の端末の答えを合わせる。作りは、アプリ一覧（`istesso-catalog`）と同じにする。
  - 応答しない端末のぶんは、最後に見えた内容をキャッシュから出し、「取得できない」の印を付ける。キャッシュは、信頼の根拠にしない（ADR 0007）。
  - 同じ相対パスのフォルダーは、1つに重ねる。
  - 同じ相対パスのファイルが複数の PC にあるときは、1つにまとめずに、PC ごとに並べる。どれが正しいかを、仕組みが勝手に決めない。
- 合計は、「いま使える分」（応答した PC）と「止まっている分」（キャッシュ）に分けて出す。
- リンク（シンボリックリンク）は、たどらない。「リンク」という項目として一覧に出すだけにする。領域の外を指していても、中身は見せない。

### 段階 2：名指しのコピー

- 取得：ほかの PC の `files/` にあるファイル1つを、手元へ写す。
- 受け渡し：人がコマンドで名指しした手元のファイル1つを、ほかの PC の `inbox/` へ送る。
- 運び方は、映像、入力、音と同じ通信路（`istesso-link`）にする。ファイルのためだけの仕組みは作らない。暗号の部品も足さない。
- 守る決まり（どれも、破ろうとするテストを付ける）：
  - **消さない。** 削除の操作を持たない。仕組みが消すのは、その受け渡しが自分で作った一時ファイルだけである。
  - **上書きしない。** 同じ名前があれば、断る。名前を付けるときは、すでにあれば失敗する方法を使う。確かめてから付ける、の2手にすると、その間に置かれたファイルを上書きし得る。
  - **元を変えない。** 元のファイルは、読むだけで開く。写すだけで、動かさない。
  - 書くときは、一時ファイルに書き、ディスクに書き終えたことを確かめてから、最後に名前を変える。途中で切れても、壊れたファイルが残らない。
  - **空きの下限を守る。** 受け取ると、ディスクの空きが下限を割るときは、断る。領域がディスクを使い切って、ふだんの側の保存が失敗することを防ぐ。
  - 写し終えたら、ハッシュ（SHA-256）を元と比べる。違えば、捨てて知らせる。
  - 領域の外に出ない。`..`、絶対パス、制御文字を含む名前を断る。リンクをたどらない。
  - 大文字と小文字だけが違う名前、文字の正規化だけが違う名前は、行き先で同じ名前になり得る（macOS と Linux で扱いが違う）。ぶつかるときは、断る。
  - ふだんの領域からは、仕組みが自分では何も読まない。読むのは、人が名指ししたファイルだけである。

### 権限

- 容量の数字（`storage`）は、「閲覧」で答える。負荷や空きメモリと同じ扱いにする。
- 一覧（`files`）、取得、受け渡しには、**新しい権限「ファイル」**を使う。新しくペアリングした端末には与えない。インストール、USB、音と同じく、個別に許可する（ADR 0006）。
- 理由：「閲覧」だけの端末は、いまは役割表とアプリ一覧と負荷しか見られない。ファイルの名前と中身まで見せると、いまより広がる。受け渡しは、相手のディスクに書く操作でもある。慎重な側を選んだ（ねらい：事故を避ける）。
- 使う人の手間は増える。権限を与える操作を、コマンドだけにしない。最初に使うときに、与える側の PC の画面で尋ねる形にする（説明なしで使える）。

### 段階 3 の候補と、決めるときの物差し

いまは決めない。候補だけを残す。ライセンスは、採用のときに原文で確かめる。

| OS | 候補 | メモ |
|---|---|---|
| Linux | FUSE を自前で実装する（`fuser` クレート、MIT。マウントには OS の `fusermount3` を使う） | root が要らない。アプリのファイル操作を、全部、自前のコードが受ける |
| Linux | カーネルの NFS を、認証つきの通信路の中に通す | 成熟した実装に頼れる。マウントに root が要る |
| Linux | 手元の領域と束ねる部分に mergerfs（ISC）を使う | 束ねるだけ。運ぶ部分は別に要る |
| macOS | File Provider（Apple の公開の仕組み。Finder に「まだ手元にない」の表示がある） | 署名したアプリと拡張が要る（M9 と同じ条件）。ファイルは、開くときに手元へ写される |
| macOS | FSKit（Apple の新しい公開の仕組み） | この用途で使えるかは、調べていない |
| macOS | 他社の FUSE | カーネル拡張が要るものは、導入が重い。入れない方向 |

物差し：

- アプリが保存している途中で切れても、元のファイルが残る。
- 止まっている PC のファイルを開こうとしたアプリが、固まらない。
- root も、他社のカーネル拡張も要らない。
- 失効と、端末ごとの権限が、そのまま効く。

段階 1 と 2 を毎日使ってみて、「写してから開く」で足りない場面が分かってから決める。

### ねらいがぶつかるところ

「写してから開く」は、ひと手間で、説明が要る。使い手が開発者に限らないことを考えると、最後は、アプリからふつうのフォルダーとして開ける形（段階 3）が要る。一方で、M5 のねらいは、事故を避けることで、急がない。**M5 では、事故を避けるほうを先にする。** 順番は変えない。そのかわり、段階 1 と 2 の入口を、コマンドだけにしない。ランチャーの画面（M3）から、一覧を見て、取得と受け渡しができるようにする。

## A や C に移るとき

- 段階 2 までを使ってみて、「写してから開く」が毎日の作業の邪魔になり、段階 3 の候補がどれも物差しを満たさないとき。A のうち、カーネルの機能だけで作れる部分（Linux の NFS）を考え直す。
- 「どの PC が止まっていても開けるフォルダー」が要ると分かったとき。C を、`files/` の一部にだけ使うことを考える。R-06 の「合計容量」とは両立しないので、要件を先に直す。

## 既知の不足

- 段階 2 までは、アプリが、ほかの PC のファイルを直接は開けない。人が、先に手元へ写す。
- 写したファイルを直しても、元の PC のファイルは変わらない。戻すには、受け渡しで送り、行き先で人が置き換える。
- クライアントだけの PC は、領域を持たない。取得したファイルをどこに置くかは、決めていない。ふだんのフォルダーに置くなら、人が行き先を名指しする形にする。
- 領域は、ふだんのファイルと同じディスクの空きを使う。受け渡しでは、空きの下限を守る（段階 2 の決まり）。ただし、領域の中で動くアプリがディスクを使い切ることは、防げない。防ぐには、別のボリュームか、OS のクォータが要る（どちらも root か管理者）。あとで考える。
- 名指しのコピーが運ぶのは、ファイルの名前と中身だけである。アクセス権と拡張属性は、運ばない。行き先では、既定の権限になる（実行できるファイルは、実行できない状態で届く）。Mac の、フォルダーの形をした書類やアプリは、ファイル1つではないので、断って、理由を表示する。黙って一部だけ運ぶと、壊れたように見えるためである。
- `files/` が使っている量を数えるのは、ファイルが多いと遅い。エージェントが裏で数えて、覚えておく。
- 一覧には、ファイルの名前が出る。名前そのものが秘密のファイルは、`files/` に置かない。
- 大きいファイルの途中からの再開、フォルダーごとの受け渡しは、段階 2 の最初の形には入れない。
- 段階 1 と 2 の実装は、今週は始めない。設計が受け入れられてから、試験用のフォルダーの中だけで始める。
- クリップボードとセッションの状態（architecture.md の「状態面」の残り）は、この ADR では扱わない。
