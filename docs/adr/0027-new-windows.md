## 背景

持ち主の言葉（2026-11-19）：中継しているアプリが新しい窓を開いたとき（⌘N／Ctrl+N、別の窓のダイアログ、設定の窓、ファイルを選ぶ窓）、それを Air でも、新しい 1 枚の窓として出したい。毎日の使い方で、いちばん当たりそうな痛み。

いまの形：

| ホスト | いま、2 枚目の窓に起きること |
|---|---|
| Ubuntu（試用版のコンポジター、`trial-windows` の修正） | 出力は 1 つ。2 枚目の窓は、**同じ 1 枚の絵の中**に出る。親のない窓は、自分の大きさで絵のまん中。親のあるダイアログは、親のまん中。出力いっぱいの窓が 2 枚あると、下になったほうには届かない（資料：m3-compositor-windows.md の 3 章と「分かっている不足」） |
| Mac Studio（`m4-daily-host` のホスト） | 取り込みは、「そのアプリの窓の全部」を、**映している窓 1 枚の四角で切り取った**絵（`SCContentFilter(display:including:[アプリ])` と `sourceRect`。資料：`macos/daily-host/main.swift`）。⌘N の窓は、同じ仮想ディスプレイの上に出れば、最初の窓の四角の中に重なった分だけが見える（推測：コードから。実機では見ていない）。映す窓は「いままでの窓が残っていれば、それ」なので、新しい窓には移らない（資料：同じファイルの `lookAtApp`） |

すでに決まっていること：

- 要件 R-02：「1 アプリ = 1 仮想ディスプレイ = 手元の 1 窓」。`milestones.md` の「将来の項目」に、「1 つのアプリが開く複数の窓を、別々の窓として出す」がある。
- m3-everyday-apps.md の 10.3（2026-11-18）：いまは、つなぎ（1 枚のまま）。目指す形は、**(ii) 1 本の流れを切り出す形を第一の候補**にして、計測と ADR から始める。(i) 窓ごとの流れは、第二の候補。
- この文書は、その「ADR」にあたる。**第一の候補を、(i) に入れ替えることを提案する**（2 章、【問い 窓1】）。11-18 のあとで変わったのは、Mac のホストができたことと、持ち主が毎日の試用で当たったこと。

言葉：**流れ** は、圧縮した映像の 1 本。**枠** は、GPU が同時に開ける圧縮の口（エンコーダーのセッション）。**最初の窓** は、アプリを開いたときに映している窓。

## 1. 何を「新しい窓」と数えるか

### 1.1 Ubuntu（自分のコンポジター）

| アプリが出すもの | 【提案】手元での扱い | 出どころ |
|---|---|---|
| 親のない `xdg_toplevel` の 2 枚目から（Ctrl+N の窓、Blender の設定の窓、2 枚目のブラウザーの窓） | **新しい窓**。自分の出力、自分の流れ、Air の新しい窓 | Blender の設定の窓は、親のない窓だった（実機：m3-compositor-windows.md の 1 章） |
| 親のある `xdg_toplevel`（確認や設定のダイアログ、アプリの中のファイルを選ぶ窓） | 試作では、**いまのまま、親の絵の中**（親のまん中）。そのあとは【問い 窓2】 | `set_parent` は、ダイアログや道具箱など「補助の面」に付け、親より上に重ねる（資料 S1）。いま、親のまん中に置いている（資料：ADR 0009） |
| `xdg_popup`（メニュー、コンボの一覧、ツールチップ） | **いつも、親の窓の絵の中**。新しい窓にしない | ポップアップは短命の面で、親の面からの位置で置く（資料 S1） |
| 別の接続が開く窓（ポータルが出す、Chrome や Firefox のファイルを選ぶ窓） | 同じアプリの窓（ADR 0009 の「同じアプリ」の決まり）。親が伝わらなければ、親のない窓なので、新しい窓 | 同じセッションの接続は同じアプリ（資料：ADR 0009）。ポータルの窓の親が、このコンポジターに伝わるか（推測：伝わらない） |
| サブサーフェス | 面の一部。数えない | Wayland の本体の決まり（この文書のためには、読み直していない） |
| X11 のアプリの窓 | 対象外 | このコンポジターは XWayland を持たない（資料：ADR 0009 の表） |

- 親は、**最初の絵が出たとき**のもので決める。あとで付いたり外れたりしても、窓の種類は変えない（出ていない親を指すと、親なしと同じになる：資料 S1。アプリがどの順で呼ぶかは、アプリごと：推測）。
- モーダルかどうかは、`xdg-dialog-v1` の `set_modal` で分かる。ただし、親の窓への入力を止めるのは、アプリ自身の務め（資料 S1）。このコンポジターとツールキットが、この口を使っているか（推測：使っていない。なくても、親の上に出す形で足りる）。

**ホストがどう気づくか**：コンポジターは、窓を作る頼み、親、題名、閉じたことを、アプリから直に受け取る。見に行く必要がない（資料 S1）。試用版の修正は、すでに、窓に番号（`id`。コンポジターが動いているあいだ、使い回さない）を付け、数（`wayland.windows` の `count`、`attention`）を知らせている（資料：m3-compositor-windows.md の 3 章）。足すのは、窓ごとの中身（番号、親、題名、大きさ）。

### 1.2 Mac

| アプリが出すもの | 見分け方 | 【提案】手元での扱い |
|---|---|---|
| ふつうの窓（書類、⌘N、ブラウザーの新しい窓、設定の窓） | 窓の一覧で、そのプロセスのもの、層 0、40×40 より大きい、画面に出ている（いまの `lookAtApp` と同じ条件：資料）。アクセシビリティの役割が `AXWindow` | **新しい窓** |
| 独立したダイアログ、パネル（アプリのモーダルの窓を含む） | 役割 `AXWindow`、種類 `AXDialog`／`AXSystemDialog`／`AXFloatingWindow`。モーダルのパネルは層 8（資料 S4。値 8 は、実機：m4-daily-host.md の「Studio に確認の窓が出たとき」の表） | **新しい窓**。モーダルの印を付ける。Mac には、シートのほかに「親」の印がない（推測） |
| シート（「保存しますか」、書類に付いた開く・保存） | 役割 `AXSheet`（ホストが、すでに見分けている：資料：`main.swift`） | **親の窓に付いたまま**（親の流れの絵の中） |
| メニュー、ポップアップ、ポップオーバー、ツールチップ | 層が 0 でない窓、または子の窓 | 開いたときにキーを受けていた窓の、流れの絵の中 |
| 開く・保存のパネル（システムの別のプロセスの窓） | いまの決まり（そのアプリが、同じ場所と大きさの窓をアクセシビリティで持ち、前面のときだけ。資料：m4-daily-host.md） | 試作では、いまのまま（キーを受けている窓の流れに入れる）。独立した窓にするのは、あと |
| タブ（Safari、Finder） | 選ばれていないタブは、画面に出ていない窓（推測） | 数えない。**画面に出ている窓だけ**を数える |
| ほかのプロセスの窓（許可の問い、通知） | — | この文書では扱わない（アプリの許可の窓を Air に出す件は、別の設計。守りの見直しが先） |

**ホストがどう気づくか**（3 つを比べた）：

| 道 | 中身 | 出どころ |
|---|---|---|
| a. 窓の一覧を、決まった間隔で読む | いまのホストが、200 ms おきにしている（`CGWindowListCopyWindowInfo`）。気づくまで、最大 0.2 秒 | （資料：`main.swift` の `watchApp`。0.2 秒は m4-daily-host.md の「まだのこと」） |
| b. アクセシビリティの知らせ | `kAXWindowCreatedNotification`、`kAXSheetCreatedNotification`、`kAXUIElementDestroyedNotification` がある（資料 S3）。ホストは、同じ仕組み（`AXObserver`）で、キーを受ける窓の変化を、すでに受けている（資料：`main.swift` の `watchFocus`）。どのアプリも必ず出すか、何 ms で届くか（推測） | |
| c. ScreenCaptureKit | 窓の一覧を取る口はあるが、**変わったことを知らせる口は、ヘッダーに見当たらない**（資料 S2）。流れの知らせは、止まったことなどだけ（資料 S2） | |

【提案】b で早く気づき、a を残して照らし合わせる（b が来ないアプリでも、0.2 秒で気づく）。c は、見つけるためには使わず、見つけた窓を取り込みの相手として引くためにだけ使う。

**許可は、増えない**。使うのは、画面の取り込みとアクセシビリティで、どちらも ADR 0017 が、すでに理由を残している。

## 2. 流れの形：窓ごとに 1 本か、1 本にまとめるか

m3-everyday-apps.md の 10.2 の 3 つの案を、いまの材料で比べ直した。

| | (i) 窓ごとに流れ | (ii) 1 本の絵に並べて、手元で切り出す | (iii) 1 枚のまま（いま） |
|---|---|---|---|
| 最初の窓の経路 | **変わらない**。絵の大きさ、エンコーダー、接続は、いまのまま | 窓が増えるたびに、絵が大きくなる。画素が増えたぶん、圧縮と復号が延びる。並びが変わるたびに、絵の大きさが変わり、キーフレームが出る。いまの試用のビューアーは、絵の大きさが変わると、つなぎ直して復号器を作り直す（資料：trial-daily.md の「絵の大きさが変わったとき」） | 変わらない |
| Mac のホスト | 取り込みが、窓を名指しして、窓ごとの流れを作れる（資料 S2）。圧縮は、流れごとにセッションを 1 つ | 窓を、仮想ディスプレイの上で、重ならないように並べ続ける（アクセシビリティで動かす）。アプリは、自分で窓を置き直す（推測：壊れやすい） | — |
| Ubuntu のコンポジター | 窓ごとに出力（仮想のモニター）を 1 つ。いまは、出力 1 つ、出口 1 つの作り（資料：ADR 0009）。**直す深さは、まだ読んでいない**（推測：数日。3 章の U0 で、最初に見積もる） | 出力は 1 つのまま。並べ方と、四角の知らせ | 小さい |
| 枠 | 窓 1 枚に 1 つ。このホストで同時に開けたのは 12（実機：measurements/2026-11-17-session-controls.md）。資料は 5、8、12 に分かれる（資料：m3-everyday-apps.md の 10.1） | アプリ 1 つに 1 つ | アプリ 1 つに 1 つ |
| 窓が出るまで | エンコーダーを開いて最初の 1 枚が出るまで、中央値 50 ms（39〜57 ms。実機：同じ記録の `resume`）。そこに、接続と、手元の窓を作る時間（測っていない） | すぐ（流れは、もうある）。ただし、絵の大きさが変われば、上と同じ | すぐ |
| はみ出すメニュー | 親の窓の絵に入れると、小さい窓では切れる（【問い 窓6】） | 四角を足すだけ | — |

【提案】**(i) を目指す形にする。うまく行かないときの戻り先は、いつも (iii)（いまの形）にする。**

1. **最初の窓の遅延を、変えない**（ADR 0002）。(i) は、最初の窓の経路に、段も画素も足さない。(ii) は、2 枚目の窓が開いているあいだ、打っている窓の 1 枚 1 枚が大きくなる。10.4 の計測（1.5 倍、2 倍の絵）は、まだ、だれも測っていない。
2. **Mac のホストに、合う**。11-18 には、Mac のホストがなかった。
3. **戻り先がある**。枠がない、手元が古い、流れが 1 秒で開かない。どのときも、窓は、いまと同じに、最初の窓の絵の中に出る。何も失わない。
4. (ii) は、捨てない。(i) の試作で、最初の窓の値が動いたとき、または、枠が毎日足りなくなったときの、次の候補にする。

### 2.1 遅延の予算（ADR 0002 に照らして）

| 守ること | どう守るか |
|---|---|
| 窓が 1 枚のとき、いまと同じ | 新しい道は、2 枚目の窓が出たときにだけ動く。**判定で測るビルドには、入れない**（試用の修正として足す。`scripts/check-plugin.sh` の決まりのまま） |
| 2 枚目が開いていて、止まっているとき | Ubuntu：描くのも圧縮するのも、その窓が絵を変えたときだけ（render-on-commit を、出力ごとに）。Mac：見ているあいだ、止まっていても毎秒 20 枚渡す決まり（資料：m4-daily-host.md）が、流れの数だけ増える（推測：軽い。測る） |
| 2 枚とも動いているとき | GPU を分け合う（推測）。参考として測る。合否には使わない |
| 毎秒 85 枚の上限 | 窓ごとに数える（どの窓も、85 を超えない） |
| ビットレートの上限 30 Mbps | 流れごと。有線では足りる。AURA と Wi-Fi は、あとで決める |
| 新しい窓が出る・消える瞬間 | 最初の流れに、キーフレームも、つなぎ直しも、起こさない。3 章の受け入れの確かめに入れる |

線の案：2 枚目の窓を開いて止めたままの回と、開かない回で、最初の窓の値の中央値の差が **0.5 ms 以内**（ADR 0002 が「遅延に効く変更」と数える幅と同じ）。

### 2.2 枠と GPU

- 【提案】アプリ 1 つが持てる流れは、**4 本まで**（最初の窓と、あと 3 枚）。ホスト全体では、枠の予算（ADR 0010 の初めの値 8）の中。足りないときは、【問い 窓5】。
- 手元で見えていない窓（最小化、しまった窓）は、枠を手放す（いまの `pause` と同じ。資料：ADR 0015 の「止める、戻す、離す」）。
- 窓をいくつでも開くアプリが、ほかのアプリの枠を食いつぶさないための上限でもある。
- Mac：VideoToolbox が同時に開けるセッションの数は、資料を見つけていない（推測：数本は開く）。流れを増やしたときの、取り込みの枚数と圧縮の時間を、試作で測る。

## 3. 知らせと頼み（言葉の案）

中身だけを決める。並びと番号は、採用のあと、ADR 0007 と ADR 0015 を先に直してから、実装で決める。

| 向き | 言葉 | 中身 |
|---|---|---|
| ホスト → 手元 | 窓の一覧 | 窓ごとに：番号、親の番号（なければ、なし）、題名、大きさ、モーダルか、キーボードを持つか、「見てほしい」の印、流れがあるか。変わるたびに、**全部**を、通し番号を付けて送る（抜けても、次の 1 つで直る） |
| 手元 → ホスト | 窓を映してほしい（番号） | ホストは、その窓に出力と流れを作る。手元が言わなければ、作らない（古い手元、AURA の試作、計測のクライアントは、いまのまま動く） |
| 手元 → ホスト | 前に出した（番号） | いまの `focus` に、番号を足す。なければ、最初の窓 |
| 手元 → ホスト | 閉じてほしい（番号） | その窓だけに、閉じる頼み |
| 手元 → ホスト | 大きさ（番号、幅、高さ） | いまの `resize` に、番号を足す。試作では、作らない |
| 手元 → ホスト | ポインターの位置に、番号 | その窓の絵の座標。なければ、最初の窓 |

- 題名は、画面の文字と同じ扱い。どこにも記録しない（m4-daily-host.md の、メニューの名前と同じ決め）。
- 番号は、ホストが一覧で知らせたものだけが通る。知らない番号の頼みは、捨てる。
- 通り道は【問い 窓9】（決め：流れは (c)。知らせは、試作は (a)、製品は (b)）。

**最初のやり取り（【提案】、窓9 の (c)）**：

- 映像のポートは、窓が何枚あっても 1 つ。ほかの窓の絵は、最初の窓と同じポートに、最初のやり取りで窓の番号を言ってつなぐ（`{"type":"watch","version":1,"window":N}`）。最初の窓は、番号を言わない（いまのまま）。
- 番号を言ったときは、ホストは答えに同じ番号を返す（`"window":N`）。番号を返さない古いホストは、番号を読まずに最初の窓の絵を送るので、手元はその答えを断る。一覧の項目に `port` があれば（窓ごとにポートを分けていた古いホスト）、手元はその窓を頼まない。
- 番号が通るのは、ホストがその窓の流れを開いていて、その窓が最新の一覧に載っているときだけ。ほかは `no_window` で断る。閉じた窓の番号は、二度と使わない（ほかの窓に、前の窓あての接続や頼みが届かないため）。大きさが変わって流れを作り直す窓も、新しい番号にする。
- 見てよい相手は、その窓の流れと、最初の窓の流れの、両方が許す端末だけ。最初の窓を止める・相手を変える・閉じると、ほかの窓の絵も止まる。
- 断る順は、ペアリング → 見る権利 → 最初の窓の見てよい相手 → 窓の番号 → その窓の流れの見てよい相手。見てよい相手でない端末には、どの番号の窓があるかも分からない。
- ポートの予約は増えない（Ubuntu でも）。
- 試作のあいだ、ホストと手元は同じ版で入れ替える。

**窓が出るときの順（【提案】）**：

1. アプリが窓を出す。手元が「窓ごとに映せる」と言っていなければ、いまと同じ（最初の窓の絵の中）。ここで終わり。
2. 言っていれば、ホストは、1 章で「新しい窓」と数えた窓を、最初の絵には入れず、一覧で知らせる（親の絵の中に出す窓は、いまのまま）。
3. 手元が「映してほしい」と言う。ホストは、出力と流れを作る。
4. 最初の 1 枚が届いたら、手元は、新しい窓を出す。
5. **1 秒たっても 4 まで来なければ、ホストは、その窓を、いまと同じに最初の絵の中へ出し、「見てほしい」の印を付ける。** 枠がないときも、同じ。

## 4. Air の側

【提案】**アプリ 1 つに、ビューアーのプロセス 1 つ。そのプロセスが、窓を何枚も持つ。**

| こと | 形 | 出どころ |
|---|---|---|
| Dock と ⌘Tab | アプリごとに 1 つ（機械の印の付いた、そのアプリの絵）。同じプロセスの窓なので、macOS が自分でまとめる。⌘\` で、そのアプリの窓を回る。Mission Control でも、同じアプリの窓として並ぶ | いま、アプリごとのプロセスに、アプリの絵を付けている（資料：trial-daily.md の「Spotlight、Alfred、Dock から開く」）。まとまり方は macOS のふつうの決まり（推測：確かめる）。Studio の窓に絵が出ない欠けは、そのまま（同じ文書） |
| 題名 | 窓ごとに、ホストの窓の題名。「ウインドウ」メニューにも並ぶ | |
| 大きさと場所 | 最初は、ホストの窓の大きさ（絵 1 画素を、いまと同じ点の数で）。場所は、親のない窓は、最初の窓から少しずらす。親のある窓は、親のまん中。Air の画面からはみ出さない | |
| Air → ホストの前面 | Air の窓が、打ち込む窓になったら、「前に出した（番号）」。ホストは、その窓にキーボードを渡す（Ubuntu）、その窓を前に出す（Mac。いまと同じ、アクセシビリティで） | いまの `focus`（資料：m4-daily-host.md） |
| ホスト → Air の前面 | アプリが自分で、別の窓にキーボードを移したとき（窓を閉じて親に戻った、など）。【問い 窓7】。おすすめ：**そのアプリが Air で前面のときだけ、従う。** ほかのアプリを使っているときは、動かさず、印だけ | ホストの側の決め（どのアプリも、人が何かをしないかぎり、キーボードを取らない。資料：m3-compositor-windows.md）と、同じ考え |
| 重なりの順 | **Air の順が、正しい順。** ホストの順は、合わせない。Ubuntu は、窓ごとに出力が別なので、重なりがない。Mac は、同じ仮想ディスプレイの上で重なるので、押す前に、その窓を前に出す（いまも、している。資料：m4-daily-host.md の「入力が届く範囲」） | |
| 閉じる（Air から） | 【問い 窓3】。おすすめ：足された窓の赤いボタンは、**その窓を本当に閉じる頼み**。アプリが「保存しますか」と聞けば、それが出る。Air の窓は、ホストが「なくなった」と言ってから消す。**最後の 1 枚の赤いボタンは、いまのまま**（しまうだけ。アプリと窓は、ホストに残る） | いまの赤いボタン（実機：trial-daily.md の最初の節。持ち主が 11-18 に確かめた） |
| 閉じる（ホストから） | 一覧からなくなったら、Air の窓を、すぐ消す。聞かない | |
| モーダルのダイアログ | 親の**子の窓**として出す（親の上にあり、親といっしょに動く：資料 S4）。出たとき、そのアプリが Air で前面なら、打ち込む窓にする。開いているあいだ、親の窓を押しても、押したことは送らず、ダイアログを前に出す。親への入力を止めるのは、もともとアプリの務めなので（資料 S1）、これは、見た目をそろえるだけ | Ubuntu の親のあるダイアログは、試作では親の絵の中なので、ここは、Mac のモーダルの窓と、【問い 窓2】のあとの形 |
| ファイルを選ぶ窓 | アプリの中のもの（親のあるダイアログ、シート）：親の絵の中。ポータルや、独立したパネル：新しい窓。打ち込む欄があるので、5 章の決まりが、そのまま効く | |
| ビューアーが落ちた、つなぎ直した | ホストの窓は、全部残る。つなぎ直したら、一覧をもらい直し、窓を出し直す | 要件「窓はホスト側で生き続ける」 |

## 5. 入力、文字、クリップボード

- 【提案】**入力の接続は、アプリごとに 1 本のまま。** 窓ごとに分けない。順番が守られる：「前に出した（B）」のあとに打ったキーは、必ず、そのあとに着く。修飾キーの状態も、1 つで済む。
- キーと確定した文字には、番号を付けない。ホストで、キーボードを持つ窓へ行く。キーボードを動かすのは、「前に出した」と、押したときだけ。
- ポインター、ボタン、スクロールは、その窓の絵の座標で、番号を付ける。Ubuntu は、その窓の出力の中の位置。Mac は、その窓の四角の中の位置。
- **文字の欄の知らせ**（欄があるか、パスワードの欄か、文字の場所）：いまはアプリごとに 1 つ。これに、窓の番号を足す。Air では、窓ごとに、文字を受ける口を持つ（変換の候補の窓が、その窓の文字の場所に出る）。
- **変換の途中で、別の窓へ移ったとき**：変換中の文字を、元の欄に 1 度だけ確定してから、「前に出した」を送る（変換中の ⌘V と同じ決まり。資料：trial-daily.md の「文字のコピーと貼り付け」）。同じ接続なので、確定が先に着く。
- **クリップボード**：通り道は、アプリごとのまま（ADR 0022）。変わるのは 1 つだけ：パスワードの欄で ⌘C と ⌘X を断る決まりは、**キーボードを持つ窓の欄**で見る。
- 守り：ほかのアプリの窓は、この道では、決して Air の窓にならない（Ubuntu：ADR 0009 の「同じアプリ」。Mac：同じプロセスと、いまの決まりのパネルだけ）。Mac で窓を前に出すときは、手元の入力を先にする守り（Studio の前で人が打っているときは、前に出さない。ブランチ `m4-local-input-first`）に従う。

## 6. AURA（あとで）

- ホストの側は、手元の種類を知らない。「窓ごとに映せる」と言わない手元（いまの AURA の試作）には、いまと同じ 1 枚の絵を出す。**AURA は、この文書で、何も変わらない。**
- AURA で窓ごとのパネルにするには：ふつうの 2D のアプリは、パネル 1 枚（資料：m8-aura-groundwork.md）。何枚も出すには Full Space と XR の SDK が要る見込みで、有線の眼鏡でのふるまいは、まだ分かっていない（同じ文書の f-1、f-5）。映像の面は入力を受けない（同じ文書）。
- 復号器は、同時に 16、4:2:0 だけ（実機：m8-aura-groundwork.md の表）。数は足りる。
- Air と AURA が、同じ窓を同時に見ると、枠が 2 つ要る（色の形が違うので、流れが別）。枠の配り方（【問い 窓5】）は、そのときに見直す。

## 7. いちばん小さい試作

共通の決まり：試用の修正としてだけ入れる。計測の合図（AGENTS.md）に従う。Studio で流れが開いてよいのは、TextEdit の試用の書類と、数える窓だけ（持ち主の決め。資料：m4-daily-host.md）。採用のあと、ADR 0007 と ADR 0015 を先に直す。

### M：Mac（TextEdit の 2 枚目の書類）

1. ホスト：2 枚目の窓に気づく（1.2 の a と b）。取り込みを、窓を名指しする形に変える（最初の流れは、最初の窓とそのシートとメニューだけ。パネルのときの名指しの道が、もうある：資料 `main.swift`）。2 枚目の窓に、2 つ目の取り込みと、2 つ目の圧縮のセッション。窓は、同じ仮想ディスプレイに置いたまま（【問い 窓10】）。
2. ビューアー：一覧を受け、2 枚目の窓を出し、2 本目の流れをつなぐ。「前に出した」「閉じてほしい」とポインターに、番号。
3. しないこと：大きさの変更、独立したパネル、3 枚目より先、AURA。

### U：Ubuntu（Text Editor の Ctrl+N）

1. **U0（ホストだけ。Air は使わない）**：最初に、コンポジターに 2 つ目の出力と 2 つ目の出口を足す深さを読み、半日で見積もる。**1 週間を超えるなら、作らずに、【問い 窓1】に戻る。** 作るなら：切り替え（既定は切）が入のときだけ、親のない 2 枚目の窓に、自分の出力と流れ。ポップアップは、その出力の中に収める。圧縮した絵は、数えるだけで捨てる。
2. **U1**：M で作ったビューアーと、同じ言葉でつなぐ。
3. しないこと：親のあるダイアログ（いまのまま）、大きさの変更、全画面。

## 8. 採用されたら、いっしょに直すもの
