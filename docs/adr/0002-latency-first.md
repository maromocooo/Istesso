# ADR 0002：遅延を最優先する（手元優先の構成）

- 状態：採用
- 日付：2026-11-15
- 更新：2026-11-16（合格ラインを数値で決めた。同じ日に、判定の条件と測り方の決まり、画質の条件と圧縮の設定を決めた）

## 背景

成功の基準は「リモートだと感じないこと」。映像の中継は、どれだけ速くしても取り込み・圧縮・転送・復号の分だけ遅れる。

## 決定

遅延の小さい順に、次の3つを使い分ける。

1. **手元で動くものは手元で動かす。** 同期するのは状態（ファイル、セッション、クリップボード）だけ。
2. **文字はターミナルで直接つなぐ。** herdr のセッションをホスト側に置き、手元の端末から入る。
3. **残りだけを映像で中継する。** 有線、120 Hz、ハードウェアエンコード。カーソルと窓の移動は手元で描く。

あわせて次を決める。

- 合格ラインは追加遅延の数値で定義し、常時計測する。数値は下の「合格ライン」のとおり。
- 基準の対象は自宅の有線 LAN とする。出先は対象外。
- メインの端末は Mac とする。Mac アプリが手元でそのまま動き、中継が要るのは Linux のアプリだけで済むため。

## 合格ライン（2026-11-16 に決定）

**追加遅延**は、往復時間（入力を送り出してから、その入力に反応したフレームが画面に出るまで）から、アプリ自身の応答時間を引いた値とする。

手元で動かしたテストアプリの窓と、中継したテストアプリの窓を同じディスプレイに並べ、同じ入力を同時に与えて、それぞれの追加遅延を測る（[measurements/README.md](../measurements/README.md) の「画面での計測」）。合格ラインは、**中継した窓の値から手元の窓の値を、同じ分位どうしで引いた差**で決める。単位は ms。

| 分位 | 差（中継した窓 − 手元の窓） |
|---|---|
| 中央値 | 12 ms 以下 |
| 95 パーセンタイル | 24 ms 以下 |
| 99 パーセンタイル | 47 ms 以下 |

- 3 つとも満たして合格とする。
- 入力ごとの差を画面更新の回数に丸めた値の中央値は、使わない。画面更新の刻みに乗るので、1 回ぶんと 2 回ぶんの間の違いが見えないため。「更新 N 回ぶん以内に収まった割合」は、参考として記録する。

判定の条件：

- 2台とも有線。クライアントのディスプレイは 85 Hz。
- 中継する絵は 3440×1440。テストアプリは、文字がスクロールする動く絵を出す（`istesso-flash` の既定）。ふだんの画面に近い絵で、どのフレームも前のフレームと違う。
- 小さい窓や、一面の灰色の絵で測った値は、いちばん良い場合の参考として記録する。Wi-Fi や、ほかのリフレッシュレートで測った値も参考とする。
- 計測は 2,000 回以上。手元の窓と中継した窓を前面に出して測り、そのあいだ Mac には触らない。始める前に、測る人に知らせる。
- **入力は、人が打ったキーと同じ経路を通す**（制御チャンネル → コンポジター → アプリ。2026-11-16 に決めた）。テストアプリへ直接送る形の値は、参考とする。
- **結果の扱いは、測る前に決めておく**（2026-11-16 に決めた。あとから都合よく読まないため）。
  - 測るのは 1 回。やり直すのは、前から決めてある条件（手元の窓の中央値が、いつもの値から 2 ms 以上ずれた）に当たったときだけ。
  - 中央値の差が 11.6〜12.4 ms に入ったら、合格とも不合格とも書かず、「境界」と記録する。2,000 回でも、±0.4 ms ほどの誤差があるため。`istesso measure compare` は、この幅を `border` と表示する。
  - 95 パーセンタイルと 99 パーセンタイルは、合格ラインのとおりに判定する。
  - 判定のあいだ、どの流れも、2 台の上で、ビルド、試験、音の再生をしない。始める前に、止まっていることを確かめる。
  - 手元の窓と中継した窓は、同じ入力で、同時に測る（プローブは、1 つの入力を両方のテストアプリへ同じ瞬間に送り、両方の窓を同じ画面の取り込みで見ている）。時間とともに何かがずれても、2 つの窓に同じように効く。そのうえで、計測を 4 つに区切った値も記録する（`--parts 4`）。
  - Wi-Fi は入れたままにする（予備の計測と条件をそろえるため）。記録には「Wi-Fi は入っていたが、経路には使っていない」と書く。
  - **確定の判定の前に、まだ決めていないこと**：仮の判定（[記録](../measurements/2026-11-16-m1-provisional-verdict.md)）で、合格ラインの指標（2 つの窓の中央値どうしの差）は 11.30 ms、入力 1 回ごとの差の中央値は 12.30 ms と出た。入力の 85% が、手元の窓より、ちょうど画面の更新 1 回ぶん遅れて見えるためである。合格ライン（12 ms）は更新 1 回ぶん（11.76 ms）のすぐ上にあるので、どちらの値で問うかによって、内側にも外側にも出る。確定の判定で使う値は、測る前に決める。
- **判定は 2 回に分ける**（2026-11-16 に決めた）。いまの部品（計測用の暗号化していない映像の経路、試作のビューアー、絵の中のカーソル）で測る 2,000 回は「仮の判定」として記録する。映像の暗号化、自前のクライアント、手元で描くカーソルが入ったあとに測り直し、当てるテストと合わせて確定する。
- 中継する側は、毎秒 85 枚（ディスプレイのリフレッシュレート）を超えるフレームを出さない。フレームを余分に出せば待ちは減らせるが、それは使わない。数えるのは、コンポジターが描き始める回数で、どの 1 秒を取っても 85 回まで。描くのにかかる時間は毎回少し違うので、出てきたフレームで数えると、1 秒に 86 枚入ることがある。
- 中継の窓は画面いっぱいに等倍で出し、600×400 の手元の窓をその隅に重ねる。手元の窓の値は、窓の大きさでほとんど変わらない（[記録](../measurements/2026-11-16-local-window-size.md)）。
- テストアプリは、ホストの側では GPU で描き、手元では CPU で描く。ふつうのアプリは GPU で描くので、ホストの側をそれに合わせる。手元の窓の描き方は、比べる相手の値を動かさないために変えない。CPU で描く形の値も、参考として記録する。
- 画質は、下の「画質の条件と、圧縮の設定」を満たすこと。遅延の値には、画質の値を並べて記録する。
- 受信側が、自分でキーフレームを求められる状態で測る（Mac では、アプリにローカルネットワークの許可が要る）。途中でキーフレームを求めた回数と、そのたびに絵が止まっていた時間を記録する。

ふだんの計測の決まり：

- 500 回以上でよい。中央値と 95 パーセンタイルで見る。99 パーセンタイルは、2,000 回以上の計測でだけ判断に使う。500 回の 99 パーセンタイルは、遅いほうの 5 回で決まるため。
- 手元の窓と中継した窓は、同じ状態で測る。どちらも前面に出さずに起動する。前面に出すと、Mac を使っている人のキー入力をテストアプリが受け取ってしまう。
- 手元の窓の追加遅延の中央値が、いつもの値から 2 ms 以上ずれた回は、やり直す。この指標は、手元の窓が遅くなった分だけ小さく出るため。

決めた経緯：

- はじめの暫定の目標は「追加遅延の 95 パーセンタイルで 16 ms 以下」だった。計測してみると、手元の窓でも、追加遅延は中央値で 18 ms あった（アプリがフレームを確定してから、macOS が画面に出すまでの時間）。中継の時間が 0 でも満たせない定義だったので、手元の窓との差に改めた（[記録](../measurements/2026-11-16-step2-baseline-sunshine-moonlight.md)）。
- 85 Hz の画面更新は 1 回 11.8 ms で、12 ms、24 ms、47 ms は、その 1 回、2 回、4 回ぶんにあたる。
- 決めた日の値は、成熟した実装（Sunshine と Moonlight）が 18.0 ms、41.7 ms、42.4 ms、既製の部品でつないだ 1 本が 19.5 ms、23.6 ms、25.1 ms だった。どちらも Mac が Wi-Fi で、500 回の値（[記録](../measurements/2026-11-16-step3-first-path.md)）。

## 画質の条件と、圧縮の設定（2026-11-16 に決定）

遅延は、画質と引き換えに小さくできる。そこで、判定には画質の条件を付ける。判定の計測と同じ設定のエンコーダーに、判定と同じ絵（3440×1440、動く文字、毎秒 85 枚）を通して測る（[measurements/README.md](../measurements/README.md) の「画質の計測」）。値と、その出どころは、[記録](../measurements/2026-11-16-quality.md)にある。

| 条件 | 値 | 何を防ぐか |
|---|---|---|
| 明るさの SSIM が、いちばん悪いフレームでも | 0.99 以上 | 決まった間隔で絵が崩れること。2 秒ごとにキーフレームを出すと、そのたびに 0.76〜0.81 まで落ちる |
| 色の SSIM が、悪いほうから 5% のフレームでも | 0.99 以上 | 色つきの文字がにじむこと。色を 4 分の 1 に間引く 4:2:0 は、圧縮しなくても 0.95 |
| 止めた絵を Mac の画面に出したとき、手元の窓との差が、どの色でも | 1 チャンネルあたり平均 5 レベル以内 | 色で、中継の窓だと分かること |

- 最初のキーフレームからの回復（エンコーダーが絵を直し終えるまでの 6〜7 秒）は、条件に入れない。計測は、それが済んでから始める。
- 途中でキーフレームを出し直したあとの落ち込みも、条件に入れない。求めた回数と、戻るまでの時間を記録する。

圧縮の設定：

- H.265 の 4:4:4。4:2:0 は、選べる形で残す。
- キーフレームは、求められたときだけ出す。受信側は、始めと、パケットが欠けたときに求める。
- ビットレートの上限は 30 Mbps。写真や動画に近い、難しい絵で測った結果を見て、見直す。
  - **見直した結果、30 Mbps のままにする**（2026-11-16）。難しい絵では、上限を上げても画質の伸びが小さく（30 Mbps で 39.8 dB、150 Mbps で 41.7 dB）、フレームだけが大きくなる（[記録](../measurements/2026-11-16-hard-picture.md)）。
- 絵は sRGB と伝え、受信側はそのとおりに出す。
- 4:4:4 は、4:2:0 に比べて、圧縮と復号が合わせて 2.3 ms 延びる。**有線で測って、中央値が合格ラインに届かなければ、先に圧縮を縮める。それでも届かなければ、4:2:0 に戻す。**

## 根拠

- 間接操作（トラックパッド）で人が遅延の差に気づき始めるのは約 55 ms という研究がある（Deber ほか、CHI 2015）。有線 LAN の配信で加わる遅延はこれより十分小さくできる。
- 反応の速さが要るゲームは遅延に最も敏感なので、同じ基準では扱わない（配信の種類を分ける）。

## 結果

- 「同じ画面」は「同じ画素を飛ばす」ことではなく、「同じ作業状態に戻れる」ことと定義する。
- 出先でも続きをやりたいアプリは、常時稼働のホストに置く必要がある。
- 最初のマイルストーン（M1）で遅延を実機で確かめ、満たせなければ構成を見直す。
