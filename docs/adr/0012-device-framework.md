# ADR 0012：機器の対応は、フレームワークの上に、アダプターとして足す

- 状態：方針は採用（2026-11-16）。細目は提案（採用するかどうかは、人が決める。下の「決めてほしいこと」）
- 日付：2026-11-16

## 背景

[ADR 0004](0004-usb-devices.md) は、Stream Deck を「このプロダクトが直接制御する」と決めた。直接制御とは、このプロダクトが自分で機器と話すことである。話し方は機器ごとに違うので、機器の数だけ対応を書くことになる。

ねらい：作者が持っていない機器まで、1 人で対応し続けることはできない。機器ごとの対応を、本体を変えずに、あとから足せる作りにする。ほかの人が、自分のエージェントに自分の機器の対応を書かせて、プルリクエストで送れるようにする。

- 実機が要る作業は、実機の上で動かして確かめる決まりである（AGENTS.md）。作者が持っていない機器の対応は、作者には動かせない。
- 使う人は、開発者に限らない。対応が増えても、使う人の手間が増えない形にする。

USB/IP で付け替える機器（ADR 0004 の「その他」）は、機器を丸ごと運ぶ。受け側の PC のドライバーとアプリが扱うので、このプロダクトが機器と話すことはない。

## 用語

| 語 | 意味 |
|---|---|
| フレームワーク | 機器対応のための共通の口と、その口の手前でこのプロダクトが受け持つ部分 |
| 口 | フレームワークがアダプターに渡す、インターフェース。Istesso の中に 1 つだけ決める |
| アダプター | 機器 1 種類につき 1 つ書く、口を実装した部品 |
| 本体 | アダプター以外の、このリポジトリのコード |
| 通知 | アダプターとフレームワークのあいだでやり取りする、決まった形の知らせ |
| 記録 | 口を通ったものを、順に書き取ったファイル |
| 作者、投稿者 | このリポジトリの持ち主、プルリクエストを送る人 |

## 決定（採用）

フレームワークとは：

- 機器対応のための共通の口を、Istesso の中に 1 つ決める。
- 機器 1 種類につき、その口を実装したアダプターを 1 つ書く。本体のコードを変えずに足せること。
- 受け持ちを、次のように分ける。

| 受け持つ側 | 受け持つこと |
|---|---|
| フレームワーク | 機器の一覧への表示、どの PC に挿してあるかの把握、端末間の転送、権限、切り替えの操作 |
| アダプター | その機器との会話だけ。Stream Deck なら、ボタンが押された知らせを受け取り、ボタンの絵を送る |

決めたこと：

1. 個別の対応は、まず、作者が持っている機器だけにする。
2. ほかの機器は、使う人が自分のエージェントに作らせたプルリクエストを受け付ける。
3. Stream Deck は、最初のアダプターとして、このフレームワークの上で作る。
4. Stream Deck のための特別なコードを、本体に書かない。書かないと作れないなら、口の設計が足りないということなので、口のほうを直す。

想定する投稿の流れ：

1. 使う人が、自分のエージェントに「この機器のアダプターを作って」と頼む。
2. エージェントは、手順書とひな形に従って作り、機器とのやり取りの記録と試験を付けて、プルリクエストを送る。
3. 作者は、記録を再生する試験と、決まり（ライセンス、口の外に出ていないか）を見て、受け入れる。

名前と作りは、任されている。物差しは 1 つで、**機器を足すときに、本体を触らずに済むこと**である。

## 決定に照らした作り（任された部分）

### 物差しを、検査できる形にする

- アダプター 1 つは、1 つのディレクトリに収まる。
- アダプターを足すプルリクエストが触るのは、そのディレクトリだけである。CI が、それを検査する。
- アダプターの一覧は、ビルドのときに、ディレクトリを見て作る。本体に、アダプターの名前を書く場所を持たない。
- アダプターは、依存クレートを足せない（足すと、共有のファイルを触ることになる）。要る機能は、口が渡す。
- Stream Deck のアダプターのディレクトリを消しても、本体のビルドとテストが通る。これを、決定の 4 の検査にする。

### Stream Deck に要ることを、どちらが受け持つか

| 要ること | 受け持つ側 |
|---|---|
| 機器を見つけて、アダプターに割り当てる | フレームワーク。アダプターの説明にある ID を見る |
| ボタン、つまみ、タッチの知らせを読む | アダプター |
| 絵を、機器が求める順に小分けにして送る | アダプター |
| 絵を、機器が求める大きさと形式に変える | フレームワーク。アダプターは、求める大きさと形式を名乗るだけ。絵を出す機器に共通の機能で、Stream Deck だけのものではない |
| 一覧に出す。どの PC に挿してあるかを知る | フレームワーク |
| ボタンの知らせと絵を、ほかの端末とのあいだで運ぶ | フレームワーク。制御チャンネル（[ADR 0007](0007-control-channel.md)）の上で運ぶ。アダプターは、相手がどの端末かを知らない |
| ほかの端末に使わせてよいかを決める | フレームワーク。端末ごとの USB の権限（R-13） |
| 公式ソフトとの切り替え | フレームワーク。どのソフトが公式ソフトかは、アダプターの説明に書く |
| Linux で機器を開けるようにする（udev の決まり） | フレームワーク。アダプターの説明から作る |
| ボタンに割り当てる動作（アプリを開く、など） | フレームワークの上の層。アダプターは、それを知らない |

作っていて、本体の中に Stream Deck のためのコードが要ると分かったら、この表に行を足して、口を直す。

### アダプターの形（比べる案）

- **A：Rust のコードを、このリポジトリに入れて、一緒にビルドする。**
- **B：実行時に読み込む。** アダプターを WebAssembly にして、エージェントが読み込む。
- **C：別のプロセスにする。** アダプターごとに実行ファイルを持ち、標準入出力でやり取りする。

| 観点 | A：一緒にビルドする | B：実行時に読み込む | C：別のプロセスにする |
|---|---|---|---|
| 本体を触らずに足せるか | 足せる（上の「物差し」の作りにすれば） | 足せる | 足せる |
| 想定する投稿の流れとの合い方 | そのまま合う。入るものは全部、作者の確認と CI を通る | 合う。リポジトリの外から足す道も開く | B と同じ |
| ネットワークやファイルに触れられないこと | 確認と CI の検査で守る。動いているときに止める仕組みではない | 動いているときに止まる。渡した関数しか呼べない | OS の権限で止める。その仕組みを、OS ごとに作る |
| 使う人が、新しい機器を使えるまで | 次の更新に入ってくる。使う人は、何もしない | アダプターのファイルを、自分で置く | 実行ファイルを、自分で置く |
| 投稿者が、自分の機器を使えるまで | 取り込まれるのを待つか、自分でビルドする | ファイルを置くだけ | 実行ファイルを置くだけ |
| 足す依存 | なし | WebAssembly の実行系。大きい | なし |
| 配布（R-12） | 本体に入る | アダプターを配る仕組みが要る | 実行ファイルを、機器の数だけ配る |
| 再生の試験 | `cargo test` で、CI がそのまま動かす | 実行系を CI に入れれば動く | プロセスを起動する試験になる |

**A を選んだ。**

- 使う人の手間が、いちばん少ない。対応が増えても、入れるものは増えない。
- 想定する流れの 3（作者が、口の外に出ていないかを見る）と、同じ形で守れる。
- 口が固まる前は、口と通知の形が変わる。変えやすいのは A である。
- 口を狭くしておけば、あとで B に移っても、アダプターの中身はほぼそのまま使える。移るのは、動いているときに止める仕組みが要ると分かったとき、または、取り込みを待たずに足したいという声が増えたときである。

A での守らせ方：

- アダプターは、口の型だけを持つ小さなクレートにしか依存しない。
- `unsafe` を禁じる。
- 標準ライブラリの、ファイル、ネットワーク、プロセスの関数を使っていないことを、CI が検査する。
- これは、悪意のあるコードを止める仕組みではない。確認で見る範囲を狭める仕組みである。

## 提案（細目）

ここから下は、提案である。決まったものではない。

### 1. フレームワークが渡す機能は、狭くする

渡すもの：

- **機器とやり取りする関数。** 相手は、そのアダプターに割り当てた機器 1 台だけ。最初は HID の 4 つ：入力レポートを読む、出力レポートを書く、フィーチャーレポートを読む、フィーチャーレポートを書く。
- **決まった形の通知。** 出す関数と、受け取る関数。形は下の表。
- **経った時間。** 時刻そのものは渡さない。再生の試験（6）で、いつも同じ結果になるようにするためである。

渡さないもの：ネットワーク、ファイル、プロセスの起動、ほかの機器、環境変数、ペアリングの鍵と一覧。

通知の形（最初の語彙。Stream Deck Plus に要るものから始める）：

| 向き | 通知 | 中身 |
|---|---|---|
| アダプター → フレームワーク | 機器の形 | ボタンの数と並び、つまみの数、絵を出せる場所と、求める大きさと形式 |
| | ボタン | 番号、押した／離した |
| | つまみ | 番号、回した量、押した／離した |
| | タッチ | 位置、種類 |
| フレームワーク → アダプター | 絵を出す | 場所、絵（求めた大きさと形式に、もう変えてある） |
| | 明るさ | 0〜100 |
| | 元に戻す | 絵を消して、機器をつないだときの状態に戻す |

- 通知は、そのまま端末のあいだを運べる形にする。版の番号を持たせ、知らない通知は読み飛ばす（ADR 0007 のメッセージと同じ考え方）。

狭くする理由：

1. 作者は、持っていない機器のコードを動かせない。読むだけで受け入れるには、コードにできることが少ないほうがよい。
2. アダプターは、エージェントのプロセスの中で動く。そこには、ペアリングの鍵がある。
3. 機器とのやり取りが 1 か所を通るので、記録と再生がそこでできる。

### 2. アダプターは、機器の説明を持つ

アダプターは、会話の部分のほかに、機器の説明を持つ。フレームワークは、説明だけを見て、自分の受け持ちを果たす。

| 説明に書くこと | フレームワークが、それで行うこと |
|---|---|
| 機器の名前と ID | 一覧への表示。アダプターへの割り当て。Linux の udev の決まり |
| この機器を使う、ほかのソフト（公式ソフトなど） | 切り替えの操作。そのソフトが動いているあいだは、機器に触らない |
| この機器を使うアプリ | 起動先の選び方（ADR 0004 の「ねらいに照らして選んだこと」の 1） |
| 確認した人、OS、日 | 対応表（5） |

- 会話の部分を持たない、説明だけのものも置ける。付け替える機器（「その他」）について、「この機器を使うアプリ」だけを書くためである。

### 3. 単純な機器は、設定ファイルで書ける

- 対象は、レポートの形が決まっている機器。「何バイト目の何ビット目が、どのボタンか」「このバイト列を書くと、ランプが点く」と書けるもの。
- 形式は TOML。フレームワークが読んで、コードのアダプターと同じ通知に変える。
- コードを含まないので、口の外には出られない。記録と再生の試験は、同じように付ける。
- 設定で書けないものは、コードで書く。Stream Deck は、絵を小分けにして送る手順があるので、コードになる。

形の例（決めたものではない）：

```toml
[device]
name = "Example Pad"
transport = "hid"
vendor_id = 0x1234
product_id = 0x5678

[[button]]
index = 0
report_id = 1
byte = 1
bit = 0
```

### 4. 口を固める前に、種類の違う機器をもう 1 つ通す

- 1 つだけで作ると、口も通知も、その機器の形に寄る。
- 種類の違う機器をもう 1 つ通して、口と通知が持ちこたえるかを見る。それから固める。
- **どの機器にするかは、決まっていない。** シリアルでつながる機器が、候補に挙がっている。この文書では選ばない。
- 固めるまでは、口と通知の版を 0 とする。固めたあとは、変えるたびに、すべての記録を再生して確かめる。
- 2 つ目が HID でない場合に備えて、機器とやり取りする関数は、つなぎ方ごとに分けておく（最初は HID だけ）。シリアルの機器になった場合、Rust でよく使われるクレート（`serialport`）は MPL-2.0 なので、採るなら条件つきの扱いになる（[ADR 0001](0001-license-and-components.md)）。

### 5. 対応表は、「作者が確認済み」と「投稿者が確認」に分ける

- **作者が確認済み：** 作者が、実機で動かして確かめた。
- **投稿者が確認：** 投稿者が、自分の実機で動かして確かめ、記録を添えた。作者が見たのは、再生の試験と、決まりである。
- 表は、アダプターの説明（2）から作って出す。手で書く表は持たない。アダプターを足すプルリクエストが、共有のファイルを触らずに済む。
- この区別は、使う人に見える場所（機器の一覧）にも出す。
- 投稿者が確認した機器が動かなくなったとき、実機で直せるのは、その機器を持っている人だけである。表に、そう書く。
- 作者の Mac につながっているのは、Stream Deck Plus である（2026-11-16 に確認）。Stream Deck のほかの型は、作者が持っていなければ、「投稿者が確認」として入ることになる。

### 6. 持っていない機器のプルリクエストには、やり取りの記録と、それを再生する試験を求める

- **記録**に書き取るもの：アダプターが機器に書いたもの、機器が返したもの、出入りした通知、そのあいだに経った時間。
- 記録は、フレームワークの道具で取る（`istesso devices record` のようなコマンド）。口が 1 か所なので、そこで書き取れる。root は要らない。
- **再生の試験**は、記録の中の「機器が返したもの」を、偽の機器から返す。アダプターが、記録と同じものを書き、同じ通知を出すことを確かめる。作者は、実機なしで確かめられる。
- 記録に入れる場面（最低限）：つなぐ、ボタンやつまみを 1 つずつ全部動かす、出せるものを 1 回ずつ出す、抜く。
- 記録に入れないもの：機器の製造番号（道具が、決まった値に置き換える）、使う人の絵（道具が、試験用の絵を使う）。
- 作者が持っている機器にも、同じ記録と試験を付ける。Stream Deck が最初の例になる。

これで分かること：フレームワークやアダプターを直したときに、その機器とのやり取りが変わっていないこと。

これで分からないこと：記録が本物かどうか。記録にない操作が正しいかどうか。

### 7. 投稿者のエージェントのために、ひな形と手順書を用意する

- 読むのは、投稿者のエージェントである。人に向けた説明ではなく、エージェントがそのまま従える手順にする。
- ひな形は、アダプター 1 つぶんのディレクトリ。機器の説明、会話の部分の骨組み（または設定ファイルの例）、再生の試験。
- 手順書の中身（順に）：
  1. 守ること（ライセンス。下の 8）。
  2. 機器を見つける（`istesso devices list`）。
  3. コードで書くか、設定ファイルで書くかを選ぶ。
  4. 書く。口の外に出ない。自分のディレクトリの外を触らない。
  5. 実機で動かして、記録を取る。
  6. 再生の試験を通す。`cargo fmt`、`cargo clippy`、`cargo test` を通す。
  7. プルリクエストに書く：機器の名前、確認した OS、参照したものとそのライセンス、記録に個人の情報が入っていないこと。
- AGENTS.md には、入口だけを書く（R-10 と同じ考え方）。
- プルリクエストのひな形に、同じ確認の一覧を入れる。

### 8. GPL のコードを写さない決まりは、アダプターにも適用する

- GPL・AGPL のコードを入れない、読みながら同じものを書かない、という決まり（ADR 0001、AGENTS.md）は、リポジトリの全部に掛かっている。アダプターだけが外れることは、もともとない。ここで提案するのは、それを投稿でどう守ってもらうかである。
- 機器の話し方を書いたコードには、GPL のものが多い（Linux カーネルのドライバーなど）。エージェントは、頼まれなくても、それを探して読みにいく。だから、手順書のいちばん上に書く。
- 使ってよい情報源：
  - 自分の機器とのやり取りを、自分で観察したもの
  - メーカーが公開している資料
  - [components.md](../components.md) の「取り込める」に載っている実装
- それ以外の実装を参照したいときは、先に、components.md に足すプルリクエストを出す。
- プルリクエストには、参照したものを書く。

## 結果

- 対応する機器は、作者が持っているものから始まり、あとは投稿で増える。
- 使う人は、機器の対応のために、何も入れない。対応は、ふだんの更新に入ってくる。Linux で機器を開くための決まりも、インストーラー（M9）が一緒に入れる。
- 投稿者には、エージェントと、ソースからのビルドが要る。取り込まれるまでは、自分でビルドしたものを使う。
- 作者は、動かせないコードを受け入れることになる。支えは、狭い口、再生の試験、対応表の区別の 3 つである。
- 口と通知を固めたあとは、変えるのが高くつく。実機で確かめ直せるのは、機器を持っている人だけだからである。だから、固める前に 2 つ目を通す。
- 映像・入力・音の経路には、手を入れない。

## 既知の不足

- 記録が本物かどうかは、確かめられない。
- 参照したものの申告も、確かめられない。作者は、書かれたことを信じるしかない。
- 機器を壊しうる命令（ファームウェアの書き換えなど）を、フレームワークは見分けられない。確認で見るしかない。
- A の形では、アダプターがネットワークやファイルに触れないことを、動いているときには止めない。

## 採用されたら直すもの

- AGENTS.md：手順書への入口。「どこで何を動かすか」に、アダプターの行（その機器が挿してある実機）。
- [architecture.md](../architecture.md)：クレートの表に、フレームワークのクレート。
- [components.md](../components.md)：HID と話すための部品。採るときに、ライセンスを原文で確かめる。
- [milestones.md](../milestones.md)：M7 に、2 つ目の機器と、口を固めること。
- ADR 0007：通知を端末のあいだで運ぶメッセージ。
- `.github/`：プルリクエストのひな形と、CI の検査。

## まだ決まっていないこと（この文書では触らない）

- フレームワークを確かめる、2 つ目の機器。
- Windows をこのリリースに含めるか。含めるなら、機器とやり取りする関数を Windows でも用意する。
