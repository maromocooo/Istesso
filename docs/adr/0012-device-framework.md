# ADR 0012：機器の対応は、枠組みの上に、プルリクエストで足す

- 状態：方針は採用（2026-11-16）。細部は提案（採用するかどうかは、人が決める。下の「決めてほしいこと」）
- 日付：2026-11-16

## 背景

[ADR 0004](0004-usb-devices.md) は、Stream Deck を「このプロダクトが直接制御する」と決めた。直接制御とは、このプロダクトが自分で機器と話すことである。話し方は機器ごとに違うので、機器の数だけ対応を書くことになる。

- 実機が要る作業は、実機の上で動かして確かめる決まりである（AGENTS.md）。作者が持っていない機器の対応は、作者には確かめられない。
- 利用者は、自分の機器を持っている。コーディングエージェントも使える。自分の機器の対応を、自分のエージェントに書かせることができる。
- そのとき、作者は、動かせないコードを受け入れることになる。受け入れられる形を、先に決めておく。

USB/IP で付け替える機器（ADR 0004 の「その他」）には、個別の対応は要らない。機器を丸ごと運び、受け側の PC のドライバーとアプリが扱うからである。この文書が扱うのは、直接制御する機器だけである。

## 用語

| 語 | 意味 |
|---|---|
| プラグイン | 機器 1 種類ぶんの対応。コードか、設定ファイル |
| 口 | 枠組みがプラグインに渡す、機器と話すための関数の組 |
| 通知 | プラグインと枠組みのあいだでやり取りする、決まった形の知らせ |
| 記録 | 口を通ったものを、順に書き取ったファイル |
| 作者、投稿者 | このリポジトリの持ち主、プルリクエストを出す利用者 |

## 決定（採用）

1. 個別に対応するのは、作者が持っている機器だけにする。
2. ほかの機器は、利用者が自分のエージェントに書かせたプルリクエストで足す。
3. そのための枠組みを用意する。
4. Stream Deck の対応も、同じ枠組みの上に作る。

## 提案（細部）

ここから下は、提案である。決まったものではない。

### 1. プラグインに渡すのは、狭い口だけにする

渡すもの：

- **機器と話す関数。** 相手は、そのプラグインに割り当てた機器 1 台だけ。最初は HID の 4 つ：入力レポートを読む、出力レポートを書く、フィーチャーレポートを読む、フィーチャーレポートを書く。
- **通知を出す関数と、受け取る関数。** 形は下の表。
- **経った時間。** 時刻そのものは渡さない。再生のテスト（6）で、いつも同じ結果になるようにするためである。

渡さないもの：ファイル、ネットワーク、プロセスの起動、ほかの機器、環境変数、ペアリングの鍵と一覧。

通知の形（最初の語彙。Stream Deck Plus に要るものから始める）：

| 向き | 通知 | 中身 |
|---|---|---|
| プラグイン → 枠組み | 機器の形 | ボタンの数と並び、つまみの数、絵を出せる場所と大きさ |
| | ボタン | 番号、押した／離した |
| | つまみ | 番号、回した量、押した／離した |
| | タッチ | 位置、種類 |
| 枠組み → プラグイン | 絵を出す | 場所、絵 |
| | 明るさ | 0〜100 |
| | 元に戻す | 絵を消して、機器をつないだときの状態に戻す |

- 通知には版の番号を持たせ、知らない通知は読み飛ばす（[ADR 0007](0007-control-channel.md) のメッセージと同じ考え方）。
- ボタンに何を割り当てるか（アプリを開く、など）は、枠組みの上の層が決める。プラグインは、それを知らない。

狭くする理由：

1. 作者は、持っていない機器のコードを動かせない。読むだけで受け入れるには、コードにできることが少ないほうがよい。
2. プラグインは、エージェントのプロセスの中で動く。そこには、ペアリングの鍵がある。
3. 機器とのやり取りが 1 か所を通るので、記録と再生がそこでできる。

### 2. プラグインの形（比べる案）

- **A：Rust のコードを、このリポジトリに入れて、一緒にビルドする。**
- **B：実行時に読み込む。** プラグインを WebAssembly にして、エージェントが読み込む。
- **C：別のプロセスにする。** プラグインごとに実行ファイルを持ち、標準入出力でやり取りする。

| 観点 | A：一緒にビルドする | B：実行時に読み込む | C：別のプロセスにする |
|---|---|---|---|
| 方針（プルリクエストで足す）との合い方 | そのまま合う。レビューと CI を通ったものだけが入る | 合う。リポジトリの外から足す道も開く | B と同じ |
| 狭い口の守らせ方 | 型と、CI の検査で守らせる。柵であって、砂場ではない | 実行時に守られる。渡した関数しか呼べない | OS の権限で守る。プロセスごとの制限を、OS ごとに作る |
| 足す依存 | なし | WebAssembly の実行系。大きい | なし |
| 配布（R-12） | 本体に入る | プラグインのファイルを配る仕組みが要る | 実行ファイルを、機器の数だけ配る |
| 書く言語 | Rust | WebAssembly にできる言語 | 何でも |
| 再生のテスト | `cargo test` で、CI がそのまま動かす | 実行系を CI に入れれば動く | プロセスを起動するテストになる |
| 利用者が、自分の機器を使えるまで | プルリクエストが入るのを待つか、自分でビルドする | ファイルを置くだけ | 実行ファイルを置くだけ |

**A から始める。**

- 方針が、プルリクエストで足す形である。入るコードは、全部レビューを通る。
- 凍結（4）の前は、口と通知の形が変わる。変えやすいのは A である。
- 口を狭くしておけば、あとで B に移っても、プラグインの中身はほぼそのまま使える。移るのは、プルリクエストを待たずに足したいという声が増えたとき、または、レビューで見きれない数になったときである。

A での守らせ方：

- プラグインは、口の型だけを持つ小さなクレートにしか依存しない。
- `unsafe` を禁じる。
- 標準ライブラリの、ファイル、ネットワーク、プロセスの関数を使っていないことを、CI が検査する。
- これは、悪意のあるコードを止める仕組みではない。レビューで見る範囲を狭める仕組みである。

### 3. 簡単な機器は、設定ファイルで書ける

- 対象は、レポートの形が決まっている機器。「何バイト目の何ビット目が、どのボタンか」「このバイト列を書くと、ランプが点く」と書けるもの。
- 形式は TOML。枠組みが読んで、コードのプラグインと同じ通知に変える。
- コードを含まないので、口の狭さは最初から守られる。記録と再生のテストは、同じように付ける。
- 設定で書けないものは、コードで書く。Stream Deck は、絵を小分けにして送る手順があるので、コードになる。

形の例（決めたものではない）：

```toml
[device]
name = "Example Pad"
transport = "hid"
vendor_id = 0x1234
product_id = 0x5678

[[button]]
index = 0
report_id = 1
byte = 1
bit = 0
```

### 4. 凍結の前に、種類の違う機器をもう 1 つ通す

- Stream Deck だけで形を決めると、口も通知も Stream Deck の形になる。
- 種類の違う機器をもう 1 つ通して、口と通知が持ちこたえるかを見る。それから凍結する。
- **どの機器にするかは、決まっていない。** シリアルの機器が候補に挙がっている。この文書では選ばない。
- 凍結までは、口と通知の版を 0 とし、断りなく変える。凍結のあとは、変えるたびに、すべての記録を再生して確かめる。
- 2 台目が HID でない場合に備えて、機器と話す関数は、つなぎ方ごとに分けておく（最初は HID だけ）。シリアルの機器になった場合、Rust でよく使われるクレート（`serialport`）は MPL-2.0 なので、採るなら条件つきの扱いになる（[ADR 0001](0001-license-and-components.md)）。

### 5. 対応表は、「作者が確認」と「投稿者が確認」を分ける

- 置き場所は `docs/devices.md`。最初の機器が入るときに作る。
- 列：機器、形（コード／設定ファイル）、できること、確認した人、確認した OS、確認した日。
- 「確認した人」は 2 つに分ける。
  - **作者が確認：** 作者が、実機で動かして確かめた。
  - **投稿者が確認：** 投稿者が、自分の実機で動かして確かめ、記録を添えた。作者が見たのは、コードと、再生のテストが通ることだけである。
- この区別は、利用者に見える場所（機器の一覧）にも出す。
- 投稿者が確認した機器が動かなくなったとき、直せるのは、その機器を持っている人だけである。表に、そう書く。
- 作者の Mac につながっているのは、Stream Deck Plus である（2026-11-16 に確認）。Stream Deck のほかの型は、作者が持っていなければ、「投稿者が確認」として入ることになる。

### 6. 作者が持っていない機器のプルリクエストには、記録と、それを再生するテストを付ける

- **記録**に書き取るもの：プラグインが機器に書いたもの、機器が返したもの、出入りした通知、そのあいだに経った時間。
- 記録は、枠組みの道具で取る（`istesso devices record` のようなコマンド）。口が 1 か所なので、そこで書き取れる。OS の USB の通信をのぞく道具（root が要る）は使わない。
- **再生のテスト**は、記録の中の「機器が返したもの」を、偽の機器から返す。プラグインが、記録と同じものを書き、同じ通知を出すことを確かめる。機器がなくても、CI で動く。
- 記録に入れる場面（最低限）：つなぐ、ボタンやつまみを 1 つずつ全部動かす、出せるものを 1 回ずつ出す、抜く。
- 記録に入れないもの：機器の製造番号（道具が、決まった値に置き換える）、利用者の絵（道具が、試験用の絵を使う）。
- 作者が持っている機器にも、同じ記録とテストを付ける。Stream Deck が最初の例になる。

これで分かること：枠組みやプラグインを直したときに、その機器とのやり取りが変わっていないこと。

これで分からないこと：記録が本物かどうか。記録にない操作が正しいかどうか。

### 7. 投稿者のエージェントのための、ひな形と手順書を置く

- 読むのは、投稿者のエージェントである。人に向けた説明ではなく、エージェントがそのまま従える手順にする。
- ひな形は、機器 1 つぶんのディレクトリ。プラグインの骨組み（または設定ファイルの例）、再生のテスト、対応表の 1 行。
- 手順書の中身（順に）：
  1. 守ること（ライセンス。下の 8）。
  2. 機器を見つける（`istesso devices list`）。
  3. コードで書くか、設定ファイルで書くかを選ぶ。
  4. 書く。口の外に出ない。
  5. 実機で動かして、記録を取る。
  6. 再生のテストを通す。`cargo fmt`、`cargo clippy`、`cargo test` を通す。
  7. 対応表に 1 行足す（「投稿者が確認」）。
  8. プルリクエストに書く：機器の名前、確認した OS、参照したものとそのライセンス、記録に個人の情報が入っていないこと。
- AGENTS.md には、入口だけを書く（R-10 と同じ考え方）。
- プルリクエストのひな形に、同じ確認の一覧を入れる。
- Linux で機器を開くための udev の決まり（ADR 0004 の「権限」）は、プラグインが名乗る機器の ID から、枠組みが作る。投稿者には書かせない。

### 8. GPL のコードを写さない決まりは、機器の対応にも当てはまる

- GPL・AGPL のコードを入れない、読みながら同じものを書かない、という決まり（ADR 0001、AGENTS.md）は、リポジトリの全部に掛かっている。機器の対応だけが外れることは、もともとない。ここで提案するのは、それを投稿でどう守ってもらうかである。
- 機器の話し方を書いたコードには、GPL のものが多い（Linux カーネルのドライバーなど）。エージェントは、頼まれなくても、それを探して読みにいく。だから、手順書のいちばん上に書く。
- 使ってよい情報源：
  - 自分の機器とのやり取りを、自分で観察したもの
  - メーカーが公開している資料
  - [components.md](../components.md) の「取り込める」に載っている実装
- それ以外の実装を参照したいときは、先に、components.md に足すプルリクエストを出す。
- プルリクエストには、参照したものを書く。

## 結果

- 対応する機器は、作者が持っているものから始まり、あとは投稿で増える。作者は、持っていない機器の対応を頼まれても、書かない。
- 作者は、動かせないコードを受け入れることになる。支えは、狭い口、再生のテスト、対応表の区別の 3 つである。
- 口と通知を凍結したあとは、変えるのが高くつく。記録を取り直せるのは、機器を持っている人だけだからである。だから、凍結の前に 2 台目を通す。
- Linux では、対応する機器が増えるたびに、udev の決まりが 1 行増える。
- 映像・入力・音の経路には、手を入れない。

## 既知の不足

- 記録が本物かどうかは、確かめられない。
- 参照したものの申告も、確かめられない。作者は、書かれたことを信じるしかない。
- 機器を壊しうる命令（ファームウェアの書き換えなど）を、枠組みは見分けられない。レビューで見るしかない。
- A の形では、狭い口は柵であって、砂場ではない。

## 採用されたら直すもの

- AGENTS.md：手順書への入口。「どこで何を動かすか」に、機器の対応の行（その機器が挿してある実機）。
- [architecture.md](../architecture.md)：クレートの表に、枠組みのクレート。
- [components.md](../components.md)：HID と話すための部品。採るときに、ライセンスを原文で確かめる。
- [milestones.md](../milestones.md)：M7 に、2 台目の機器と凍結。
- `.github/`：プルリクエストのひな形と、CI の検査。
