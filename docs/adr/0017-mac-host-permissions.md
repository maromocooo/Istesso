# ADR 0017：Mac のホストが求める OS の許可

- 状態：採用（2026-11-17、人が決めた。条件が 2 つある。下の「採用の条件」）
- 日付：2026-11-17（提案も採用も）

## 背景

M4 は、Mac のアプリを、ほかの端末の窓として使えるようにする（[m4-plan.md](../m4-plan.md)）。そのために、Mac のホストは、macOS が人の許可を求める操作を 2 つ行う。アプリの窓の絵を読むことと、アプリに入力を届けることである。

[AGENTS.md](../../AGENTS.md) は、権限の要る処理（root、画面収録、アクセシビリティ）を増やすときに、理由を ADR に残すよう求めている。ADR 0008（`m1-latency` ブランチ）は、計測のための画面収録だけを扱っていて、「製品には入れない」と書いている。製品のホストが使う許可は、この文書で扱う。

2026-11-16 と 17 に決まっていること：

- Mac のホストは、今回は、人がログインしておく形にする。FileVault は切らない（m4-plan.md の 4.4）。
- 映像を受け取れるのは、そのセッションを映している端末だけ。入力を送れるのも、その端末だけ。入力を開くときの権限は、頼まれたときに読み直す。
- 映像は、制御チャンネルと同じ通信路（暗号化と認証つき）で運ぶ（ADR 0015、`m1-dialog-windows` ブランチ）。

## 決定

Mac のホストは、次の許可を求める。これ以外は、求めない。

| 許可（「プライバシーとセキュリティ」の項目） | 何に使うか | 使わないこと |
|---|---|---|
| 画面収録とシステムオーディオ録音 | **配信しているアプリの窓の絵を読む**（ScreenCaptureKit）。読むのは、セッションで開いたアプリの窓だけ。カーソルは絵に入れない | 画面全体を読まない。ほかのアプリの窓を読まない。絵を保存しない。セッションを映している端末のほかには、送らない |
| アクセシビリティ | 1. **配信しているアプリに、キーボードとマウスの入力を届ける**（CGEvent）。届けるのは、セッションを映している端末から、制御チャンネルを通って来た入力だけ。2. そのアプリの窓を、前面に出す、動かす、大きさを変える | ほかのアプリを操作しない。キーの入力を読まない（入力監視は求めない）。OS の許可のダイアログを押さない |
| システムオーディオ録音のみ | 配信しているホストの音を取る（Core Audio のタップ。[ADR 0005](0005-audio-service.md)）。作るのは、音の流れ（M2） | マイクを読まない |
| ローカルネットワーク | ペアリングした端末につなぐ。LAN の中で相手を見つける（[ADR 0007](0007-control-channel.md)） | — |

求めないもの：root、フルディスクアクセス、入力監視、マイク、カメラ。

### 守ること

1. **許可を使うのは、セッションがあるあいだだけ。** セッションが始まったら読み始め、端末が離れたら（`detach`）、0.1 秒以内に、読むのも届けるのもやめる（ADR 0010、`m3-app-manager` ブランチ）。セッションがないときは、何も読まない。
2. **読む範囲は、アプリの窓まで。** 取り込みのフィルターで、そのアプリの窓だけを選ぶ。画面全体を取り込む形は、計測のときだけ使い、製品には入れない（m4-plan.md の 4.3 の C）。
3. **入力は、権限を確かめてから届ける。** 相手が「操作」を持っていること、そのセッションを映している端末であることを、エージェントが確かめる。確かめたあとの入力だけが、注入する部分に届く。
4. **絵も入力も、ログに書かない。** 記録するのは、時刻と件数までにする。
5. **許可がないときは、何もせずに、理由と、設定の場所を伝える**（R-12）。許可を得るために、回り道をしない。
6. **許可を出す相手は、製品では、署名したアプリにする。** 使う人に、ターミナルを使わせない。

### 開発のあいだ

- 開発のあいだは、プログラムを起動するターミナル（または、SSH の入口）に、許可を出してもらう。ADR 0008 と同じ理由である。署名のないプログラムは、ビルドのたびに別のものとみなされて、許可が消える。
- 最初の確認（m4-plan.md の手順 0b、取り込みの速さ、仮想ディスプレイの小さな試し）は、確認のプログラム（`macos/lock-check` の「Istesso Lock Check」）1 つに許可を出して行う。ターミナルに出すより、許可を持つものが狭い。許可を出したあとで、このプログラムを作り直すと、許可が消える。作り直すときは、人に知らせて、出し直してもらう。
- 開発の形は、上の「採用の条件」の条件 1 のとおり、個人のデータを持たないユーザーの下でだけ使う。
- この形では、そのターミナルから起動したものは、どれも画面を読めて、入力を送れる。開発に使う Mac（Mac mini）だけの、一時の形にする。判定（m4-plan.md の手順 8）の前に、決まった署名の付いたアプリに移す。
- 許可のダイアログは、わざと出さない。許可を出すのは、人である。出してもらうまで、この文書の許可を使うコードは、動かさない。

## 採用の条件（2026-11-17）

求める許可と、上の「守ること」の 6 つは、提案のとおりに決まった。そのうえで、次の 2 つが条件として付いた。

### 条件 1：開発の形を使うのは、個人のデータを持たないユーザーの下だけ

開発の形（許可を、ターミナル、SSH の入口、または確認のための小さなプログラムに出す形）は、個人のデータを持たないユーザーの下でだけ使う。

- 人が確かめた。Mac mini のいまのユーザーは、キーチェーンを除いて、個人のデータを持たない見込みである。このユーザーのまま進める。
- 許可の出し方は、人に、1 つの表で渡す（[m4-plan.md](../m4-plan.md) の 3.9）。**人が「許可を出した」と言うまで、許可を使うコードは、1 行も動かさない。**
- キーチェーン、パスワードのアプリ、ブラウザーに保存したログインには、触らない。開かない。
- 人がその Mac でパスワードを打っているあいだは、画面を読むコードを動かさない。確認のプログラムは、確かめ終わったら、自分で取り込みを止めて終わる。人がロックを外すのは、終わったのを確かめてからにする。
- 作業の途中で個人のデータ（メール、メッセージ、写真、iCloud の中身）が見えたら、読まずに止めて、知らせる。

### 条件 2：定期的な確かめ直しの画面と、「誰も座っていないホスト」

macOS は、画面収録の許可を、定期的に確かめ直す画面を出すことがある（m4-plan.md の 3.6）。これは、「ふつう、ホストの前には誰もいない」（m4-plan.md の 4.4）とぶつかる。確かめ直しの画面が出ているあいだは、絵が止まるおそれがあり、応えられるのは、その Mac の前にいる人だけである。

手順 1 で、この画面が出ると分かったら、使う人向けの文書に、既知の制約として書く。避けるための Apple の許可（VNC アプリ向け。申請が要る）を人の作業の一覧に載せるのも、そのときだけにする（m4-plan.md の 6.1 の 7）。

### 入力を確かめる場所は、PR の前に見てもらう

「守ること」の 3（相手が「操作」を持っていること、そのセッションを映している端末であることを確かめてから、入力を届ける）を実装する場所は、PR に入れる前に、とりまとめ役が見る。そこまで来たら、押し上げずに、止めて知らせる。

## 検討したほかの形

| 形 | 採らなかった理由 |
|---|---|
| macOS の、窓を選ぶ画面（人が、取り込む窓をその場で選ぶ） | 画面収録の許可を先に出さなくて済む。しかし、ホストの前には、ふつう誰もいない。セッションのたびに、ホストの画面で人が選ぶことになる |
| 画面全体を取り込んで、クライアントで切り出す | 読む範囲が、要る分より広い。ほかのアプリの絵が、ホストの外へ出る |
| アクセシビリティを使わず、アプリごとの口（AppleScript など）で操作する | アプリごとに作ることになる。ふつうのキーとマウスを届けられない |
| root で動く部品 | 要らない。ログイン画面の中継（将来の項目）を採るときに、別の ADR で扱う |

## 結果

- Mac のホストを入れる人は、2 つの許可（画面収録、アクセシビリティ）を、自分の操作で出す。管理者のパスワードが要る。音を使うなら、もう 1 つ出す。
- 許可を持つプログラムは、その Mac の画面を読めて、入力を送れる。だから、読む範囲と、届ける入力を、上の「守ること」で絞る。
- macOS は、画面収録の許可を、定期的に確かめ直すことがある（m4-plan.md の 3.6）。確かめ直しの画面が出ているあいだ、絵が止まるおそれがある。避けるための Apple の許可（VNC アプリ向け）は、申請が要る。
- **（条件 2）** この確かめ直しの画面は、「ふつう、ホストの前には誰もいない」とぶつかる。手順 1 で出ると分かったら、使う人向けの文書に、既知の制約として書く。
- 許可は、更新のあとも残らなければならない（R-12）。製品では、決まった署名の付いたアプリに許可を出す。署名は、人の個人の証明書（Apple Developer Program）で、人の Mac で、人の鍵を使って行う（m4-plan.md の 6.1 の 7）。
- アプリが開く、OS の許可のダイアログと、パスワードの画面には、中継した窓からは応えられない。人が、その Mac で応える。

## 既知の不足

- **この文書の許可を使うコードは、まだ 1 回も動かしていない。** 取り込みと入力の部分は、書いてあるが、許可が出ていないので、動かしていない（m4-plan.md の「作り」）。採用のあとも、人が「許可を出した」と言うまでは、動かさない。
- 画面がロックされているあいだ、取り込みと入力がどうなるかは、分かっていない（m4-plan.md の 4.4）。
- 子の窓（メニュー、ポップアップ）と、メニューバーの扱いは、決まっていない。読む範囲が「アプリの窓」より広がるなら、この文書を先に直す。
- 仮想ディスプレイを作る非公開の API を使うかどうかは、別の ADR で扱う（m4-plan.md の 6.2 の 2）。
