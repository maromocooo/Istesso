# ADR 0004：USB 機器は種類ごとに扱いを分ける

- 状態：採用（2026-11-15）。2026-11-16 に決定を 5 つ足した。細部には、まだ決まっていないものがある（下の「決めてほしいこと」）
- 日付：2026-11-15
- 更新：2026-11-16（挿す場所の勧め、起動先の決まり、会議アプリの扱い、Mac で作らないもの、確認項目を足した。2 台の実機を調べて「権限」の節を足し、「制約」と「部品」を直した）

## 背景

Stream Deck、キーボード、マウス、オーディオ機器など、普段使っている機器をこの仕組みの中でも使いたい。全 PC の機器を一覧し、切り替えられるようにする。

USB をそのまま別の PC に付け替える方式（USB/IP）は汎用だが、次の問題がある。

- 受け側が Mac の場合、仮想 USB コントローラーの作成に Apple の個別許可が要る。各自がビルドする OSS では現実的でない。
- タイミングに厳しいオーディオ機器では、ネットワークの遅延でノイズが出やすい。
- 入力機器を付け替えると、挿してある PC では使えなくなる。

2026-11-16 に、付け替えに頼る場面そのものを減らす向きで、決定を足した。機器を動かすより先に、**機器を使える PC でアプリを開く**。

## 決定

一覧と切り替えの画面は共通にし、裏の方式を種類で分ける。

| 種類 | 方式 |
|---|---|
| キーボード、マウス | 入力の転送。USB の付け替えはしない |
| Stream Deck | このプロダクトが直接制御するモードを持つ。公式ソフトとどちらが使うかを切り替える。機器の枠組み（[ADR 0012](0012-device-framework.md)）の上に作る |
| オーディオ機器 | 音だけを運ぶ（[ADR 0005](0005-audio-service.md)） |
| その他 | USB/IP で付け替える |

2026-11-16 に足した決定：

1. **USB 機器は、Linux か Windows の PC に挿すことを勧める。** オーディオ機器は例外で、機器は動かさず、音を音として運ぶ（ADR 0005）。
2. **アプリマネージャーの起動先の決まりに、1 つ足す。** USB 機器を使うアプリは、その機器を受けられるホストを優先する。
3. **会議アプリは、マイクとカメラがつながっている PC で開く。**
4. **Mac の上に、仮想のマイク、カメラ、USB 機器を作ることは、範囲に入れない。**
5. **確認項目を足す。** スピーカーで聞く会議で、声が回り込まないか（下の「確認項目」）。

Windows をこのリリースに含めるかどうかは、まだ決まっていない。この文書の Windows についての記述は、含めると決まったときのものである。

## 理由

- **1 について。** 付け替えを受けられるのは、Linux と Windows だけである。機器が Linux か Windows に挿してあれば、その PC のアプリはそのまま使える。Mac に挿した機器をほかの PC へ出すには、root が要る。
- **2 について。** アプリのほうを、機器を使える PC で開けば、機器を Mac へ運ぶ必要がなくなる。Mac は受けられないので、これしか方法がない場面がある。
- **3 と 4 について。** Mac のアプリに、ほかの PC のマイクやカメラを見せるには、Mac の上に仮想の機器を作るしかない。仮想のカメラはシステム拡張、仮想のマイクはシステムに入れるオーディオドライバーで、どちらも利用者の承認や管理者権限での導入が要る。GPL の仮想オーディオドライバーは使わない（[components.md](../components.md)）。導入のしやすさ（R-12）に合わないので、作らない。その代わりに、会議アプリを、マイクとカメラのある PC で開く。

## 挿す場所と、使えるアプリ

| 機器を挿した PC | その PC のアプリ | ほかの Linux のアプリ | ほかの Windows のアプリ | ほかの Mac のアプリ |
|---|---|---|---|---|
| Linux | そのまま使える | 付け替えで使える | 付け替えで使える | 使えない |
| Windows | そのまま使える | まだ使えない（出す側の実装がない。下の「制約」） | 同左 | 使えない |
| Mac | そのまま使える | 付け替えで使える。出す側に root が要る | 同左 | 使えない |

この表から言えること：

- 決定の 2 の「機器を受けられるホスト」は、その機器が挿してあるホストか、付け替えを受けられるホスト（Linux、Windows）のことと読んだ。挿してあるホストが先で、付け替えずに済む。
- 勧めの中でも、Linux が先になる。Windows に挿した機器は、いまはその Windows のアプリからしか使えない。
- Mac でしか動かないアプリが使う機器は、勧めの例外で、その Mac に挿す。
- 勧めのとおりに挿してあれば、付け替えが要るのは、Linux か Windows のホストが 2 台以上あるときだけになる。いまの機材（Linux は 1 台。Windows は未決）で付け替えが要るのは、Mac に挿した機器を Linux のアプリで使うときだけである。
- 勧めが効くのは、付け替える機器（「決定」の表の「その他」）である。キーボードとマウスは、操作する端末に挿したまま、入力を転送する。Stream Deck は、挿した PC のエージェントが直接制御する。どちらも付け替えないので、Mac の制約に当たらない。この 2 つを勧めの対象に入れるかどうかは、まだ確かめていない（「決めてほしいこと」の 1）。

## 制約

- 受け側が Mac の付け替えはしない。Mac のアプリで使う機器は、その Mac に直接挿す。
- Linux や Windows のアプリで使う機器は、Linux か Mac に挿してあれば、付け替えて使える。2026-11-15 の版は「どの PC に挿してあってもよい」と書いていたが、Windows に挿した機器は出せないので、こう直した。
- Mac から出す側は root 権限が前提。
- Windows から出す側の既存実装（usbipd-win）は GPL-3.0 なので使わない。必要になれば内製する。
- USB/IP の手順そのものには、認証も暗号化もない。R-13（相互認証、端末ごとの USB の権限）を満たす運び方は、まだ決めていない。付け替えを作る前に、この文書に足す。

## 権限

権限の要る処理を増やすときは、理由を ADR に残す決まりである（AGENTS.md）。2026-11-16 に、Ubuntu 24.04 のホストと、macOS 26 の Mac を、何も変えずに調べた。

| 場面 | 要る権限 | 理由 | 実機で分かったこと |
|---|---|---|---|
| 機器の一覧（Linux） | なし | sysfs は誰でも読める | つながっている 23 台（ハブを含む）の ID と種類を、権限なしで読めた |
| 機器の一覧（Mac） | なし | OS が持っている機器の情報は、誰でも読める | `system_profiler` と `ioreg` から読めた |
| Stream Deck の直接制御（Linux） | 導入のときに 1 回、udev の決まりを入れる（root）。動かすときは要らない | HID の機器と直接話す口（hidraw）は、既定では root しか開けない | 口は 18 個すべて root だけだった。Elgato の機器のための決まりは、入っていなかった |
| Stream Deck の直接制御（Mac） | 未確認 | macOS が「入力監視」の許可を求めるかもしれない | 試していない。公式ソフトが動いている |
| 付け替えの受け側（Linux） | root。仮想 USB コントローラー（`vhci-hcd`）の読み込みと、付け替えのたびの操作 | カーネルの仮想コントローラーに機器をつなぐ操作は、root だけに許されている | モジュールはあるが、読み込まれていない。Secure Boot は有効で、モジュールにはカーネルの署名がある |
| 付け替えの出す側（Mac） | root | OS のドライバーから、機器を取り上げるため | 試していない |
| 付け替えの出す側（Linux） | udev の決まりで足りる見込み | 機器のデバイスノードを開ければ足りる見込み | 試していない |

- udev の決まりは、対応する機器が増えるたびに 1 行増える。入れるのは、インストーラー（M9）である。
- 専用ユーザー（[ADR 0003](0003-isolation.md)）で動かすときは、その PC の前でログインしている人に与える形（`uaccess`）では届かない。グループで与える形にする。M5 と合わせて決める。
- root の要る部分（Linux の受け側、Mac の出す側）を、製品でどういう形で持つかは、まだ決めていない。付け替えを作る前に、この文書に足す。

## 部品

- 出す側：jiegec/usbip（MIT）。0.9.0 は、`rusb` クレートを通じて libusb（LGPL-2.1）を使う。libusb は動的リンクで使い、依存を足すときに components.md の「条件つきで使える」に書く（[ADR 0001](0001-license-and-components.md)）。クレートの表示は MIT なので、`cargo deny` はこれに気づかない
- Linux の受け側：カーネル標準
- Windows の受け側：usbip-win2（BSD-2-Clause）
- Stream Deck：公開されている MIT の実装を参考に内製。機器の枠組み（ADR 0012）の上に作る

## 確認項目

### スピーカーで聞く会議で、声が回り込まないか

- **確かめること：** 会議の相手に、相手自身の声が返って聞こえないこと。
- **なぜ起きうるか：** 会議アプリは、自分が鳴らした音を手がかりにして、マイクに入った相手の声を消す。音をほかの PC のスピーカーから出すと、鳴る時刻が遅れ、時計も別になる（ADR 0005 の配信経路）。アプリの消し方がそれに追いつくかどうかは、試すまで分からない。
- **3 つの形で確かめる：**
  1. 会議アプリのある PC のスピーカーで聞く。この仕組みは音に関わらない。比べるための基準である。
  2. 会議アプリのある PC の音を、ほかの PC の「音の出口」から聞く。
  3. 2 に加えて、会議アプリの窓を、ほかの端末に映す。
- ヘッドホンで聞くときは、対象にしない。
- 回り込んだときの手当ては、決めていない。確かめた結果を見て、この文書に足す。

## 結果

- 起動先の決まり（R-04）は、「手元 → 起きているホスト → 負荷の低いホスト」の前に、機器の条件を見る形になる。同じアプリが手元にあっても、機器がほかの PC にあれば、そちらで開いて映像で中継する。手元で動かすより、遅延は増える。機器が要るアプリを「手元では動かないもの」として扱う、ということである（[ADR 0002](0002-latency-first.md) の順は変えない）。
- Mac の会議アプリは、ほかの PC のマイクとカメラを使えない。Mac で会議をするなら、マイクとカメラをその Mac につなぐ。
- 付け替えの出番が減る（上の「挿す場所と、使えるアプリ」）。
- アプリマネージャー（M3）は、起動先を選ぶときに、機器の一覧を見ることになる。
- 個別に対応する機器と、その足し方は、ADR 0012 で決める。

## 決めてほしいこと

| # | 項目 | 提案 |
|---|---|---|
| 1 | 「Linux か Windows に挿す」の勧めを、キーボード、マウス、Stream Deck にも当てはめるか | 当てはめない。対象は、付け替える機器（「その他」）だけにする。キーボードとマウスは操作する端末に挿すもので、メインの端末は Mac である（ADR 0002）。Stream Deck は付け替えないので、どこに挿しても動く |
| 2 | アプリが USB 機器を使うことを、どう知るか | 利用者が、ランチャーでアプリに印を付ける（どの機器を使うか）。自動では分からない |
| 3 | 会議アプリを、どう見分けるか。ブラウザーで開く会議は、アプリの種類からは分からない | 2 と同じ印（「マイクとカメラを使う」）にする。種類で分かるアプリには、最初から付けておく |
| 4 | 優先するホストが止まっているとき、機器を使えないホストで開くか | 開かない。「！」と、起こす操作を出す（R-04 の停止中の扱いと同じ） |
| 5 | マイクとカメラが、別々の PC にあるとき | カメラのある PC で開く。マイクの音をそこへ運ぶかどうかは、ADR 0005 にまだない（ADR 0005 は、出る音だけを扱っている） |
| 6 | USB/IP の付け替えを、このリリースで作るか | 一覧、Stream Deck、起動先の決まりを先にする。付け替えは、手動で試すところまでにして、作るかどうかは、Windows の扱いと合わせて決める。いまの機材では、向きが 1 つ（Mac から Ubuntu）しかなく、両側に root が要る |
