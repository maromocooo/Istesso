# ADR 0004：USB 機器は種類ごとに扱いを分ける

- 状態：採用（2026-11-15）。2026-11-16 に決定を足した。まだ決まっていないのは、「自分で分かる範囲」を今週どこまで作るかだけである（下の「決めてほしいこと」）
- 日付：2026-11-15
- 更新：2026-11-16（挿す場所、アプリを開く場所、確かめることの決定を足した。USB/IP の付け替えと Windows は、今回の公開に入れないと決まった。2 台の実機を調べて「権限と、使う人の手間」「ホストの前に誰もいない状態」の節を足し、「制約」と「部品」を直した）

## 背景

Stream Deck、キーボード、マウス、オーディオ機器など、普段使っている機器をこの仕組みの中でも使いたい。全 PC の機器を一覧し、切り替えられるようにする。

USB をそのまま別の PC に付け替える方式（USB/IP）は汎用だが、次の問題がある。

- 受け側が Mac の場合、仮想 USB コントローラーの作成に Apple の個別許可が要る。各自がビルドする OSS では現実的でない。
- タイミングに厳しいオーディオ機器では、ネットワークの遅延でノイズが出やすい。
- 入力機器を付け替えると、挿してある PC では使えなくなる。

2026-11-16 の決定のねらい：

- Mac は、ほかの PC に挿した機器を、USB 機器として受け取れない。それでも使う人が困らないように、**機器を挿す場所と、アプリを開く場所**で解く。使う人に守ってもらうのは「どこに挿すか」だけにする。あとは、Istesso が正しい側でアプリを開く。
- 使う人は、開発者に限らない。導入がかんたんで、説明なしで使えることが要る。
- ホストの画面の前には、誰もいないのがふつうである。起こしたばかりで、ログイン画面のままのこともある。その状態で動かないものがあると、使う人から見て「ときどき動かない」になる。

## 決定

一覧と切り替えの画面は共通にし、裏の方式を種類で分ける。

| 種類 | 方式 |
|---|---|
| キーボード、マウス | 入力の転送。USB の付け替えはしない |
| Stream Deck | このプロダクトが直接制御するモードを持つ。公式ソフトとどちらが使うかを切り替える。機器対応のフレームワーク（[ADR 0012](0012-device-framework.md)）の上に、最初のアダプターとして作る |
| オーディオ機器 | 音だけを運ぶ（[ADR 0005](0005-audio-service.md)） |
| その他 | USB/IP で付け替える。今回の公開では作らない（下の 5） |

### 挿す場所（2026-11-16）

1. **USB 機器は、Linux か Windows の PC に挿すことを勧める。** オーディオ機器は例外で、機器は動かさず、音として運ぶ（ADR 0005）。
2. **キーボードとマウスは、この方針の対象外である。** 上の表のとおり、入力の転送で扱う。
3. **Stream Deck は、この勧めに入れない。** 付け替えず、挿した PC のエージェントが直接制御するためである。
4. **Mac の上に、仮想のマイク、カメラ、USB 機器を作ることは、対象外とする。**
5. **USB/IP の付け替えは、今回の公開では作らない。Windows は、今回の公開に含めない。** Windows は、次の大きな目標とする。

### アプリを開く場所（2026-11-16）

6. **アプリマネージャーの起動先の選び方に、1 つ足す。** USB 機器を使うアプリは、その機器を受け取れるホストを優先する。同じアプリが Mac と Linux の両方にあるとき、機器を使うなら Linux の側で開く。
7. **会議アプリは、マイクとカメラがつながっている PC で開く。**
8. **Istesso が、自分で分かる範囲を先に探す。** 使う人が印を付けることを、前提にしない。そのうえで、次を守る。
   1. 自動で決めたことは、使う人に見えて、直せる。ランチャーの項目ごとに、どの PC で開くかと、その理由（例：カメラを使うため）が分かる。直す手段として、使う人の指定を残す。
   2. 分からないときは、今までどおり手元で開く。推測で、ほかの PC に寄せない。
   3. ブラウザーそのものを、カメラのある PC に寄せない。ふだんの閲覧まで、ほかの PC で開くことになるためである。会議のページを、1 つの項目としてランチャーに登録できるようにする。その項目を開くと、カメラのある PC のブラウザーで、会議のページが開く。ふだんのブラウザーは、今までどおり手元で開く。会議のリンクを開いたときに自動で振り分ける機能は、今回は作らない。
   4. マイクとカメラのある PC が 2 台以上あるとき：家（同じ LAN）では、外付けを内蔵より優先する。使う人が選び直せる。出先（VPN 経由）では、手元の端末のマイクとカメラを使う。家のカメラは、その場にいないと意味がないためである。
   5. 選ばれた PC が止まっているとき、自動では、ほかの PC で開かない。「！」と、起こす操作を出す。条件を満たす PC がほかにあれば、「この PC で開く」も選べるようにする。
   6. マイクとカメラが別々の PC にあるときは、カメラのある PC で開く。マイクの音は、今回は運ばない。その PC にマイクがなければ、そう知らせる。

### 確かめること（2026-11-16）

9. **スピーカーで聞く会議で、声が回り込まないか**（下の「確認項目」）。
10. **ホストを起動した直後（ログイン画面のまま、SSH だけ）の状態で動くこと。** 動かないものは、理由と、インストーラー（M9）で何を入れれば動くかを書く（下の「ホストの前に誰もいない状態」）。

例：

- マイクとカメラを Ubuntu に挿してある。会議を始めると、会議アプリは Ubuntu で開き、Mac には窓として出る。マイクもカメラも Ubuntu の中で済むので、何も運ばない。
- MacBook Air の内蔵のマイクとカメラを使うときは、会議アプリを Air でそのまま開く。

## 理由

- **1 について。** 付け替えを受けられるのは、Linux と Windows だけである。機器が Linux に挿してあれば、その PC のアプリはそのまま使え、その窓は、どの端末にも出せる。
- **4 と 7 について。** Mac のアプリに、ほかの PC のマイクやカメラを見せるには、Mac の上に仮想の機器を作るしかない。仮想のカメラはシステム拡張、仮想のマイクはシステムに入れるオーディオドライバーで、どちらも使う人の承認や管理者権限での導入が要る。GPL の仮想オーディオドライバーは使わない（[components.md](../components.md)）。導入のしやすさ（R-12）に合わないので、作らない。その代わりに、会議アプリを、マイクとカメラのある PC で開く。
- **5 について。** Windows を今回の公開に含めないと決まった。Linux のホストは 1 台なので、付け替えの出番は、Mac に挿した機器を Linux のアプリで使うときだけになる。それは、勧めが避けようとしている形である。
- **6 について。** アプリのほうを、機器を使える PC で開けば、機器を運ぶ必要がなくなる。

## 挿す場所と、使えるアプリ

今回の公開では、付け替えを作らない。機器は、挿した PC のアプリから使う。そのアプリの窓は、どの端末にも出せる。

- アプリが Linux にあるなら、機器も Linux に挿す。決定の 6 のとおり、Linux の側で開く。
- 機器が Mac に挿してあって、そのアプリが同じ Mac にあるときは、その Mac で開く。機器が、そこでそのまま使えるからである。2 つ目の例（Air の内蔵のマイクとカメラ）と同じ考え方で、こう読んだ。
- Mac でしか動かないアプリが使う機器は、勧めの例外で、その Mac に挿す。

付け替えを作ったあとは、次の表のようになる（Windows の行と列は、Windows を含めたあとの話である）。

| 機器を挿した PC | その PC のアプリ | ほかの Linux のアプリ | ほかの Windows のアプリ | ほかの Mac のアプリ |
|---|---|---|---|---|
| Linux | そのまま使える | 付け替えで使える | 付け替えで使える | 使えない |
| Windows | そのまま使える | 使えない（出す側の実装がない。下の「制約」） | 同左 | 使えない |
| Mac | そのまま使える | 付け替えで使える。出す側に root が要る | 同左 | 使えない |

- 勧めの中でも、Linux が先になる。Linux か Mac に挿してあれば、付け替えて使える。Windows に挿した機器は、その Windows のアプリからしか使えない。この読み方は、2026-11-16 に確かめた。

## 自分で分かる範囲（提案。今週どこまで作るかは、人が決める）

決定の 8 を、手がかりごとに当てはめた。寄せる根拠にするのは、**分かっていること**だけである。見当にすぎないものでは、寄せない。

| 手がかり | 寄せる根拠にするか | 弱み |
|---|---|---|
| 使う人の指定 | する。いちばん強い | 手間がかかる。だから、直すときにだけ使う |
| 実際に使ったのを見た。アプリが機器を開いているのをエージェントが見て、次から反映する | する | 最初の 1 回には間に合わない。OS のサービスごしに使う機器（ストレージ、プリンターなど）は見えない |
| 書いてある。機器の説明（ADR 0012）に「この機器を使うアプリ」として、または、本体に持つ会議アプリの表に | する | 誰かが書く必要がある |
| アプリの種類が、ちょうどそれを指している（会議のための種類） | する | その種類を持つアプリが少ない |
| アプリの種類が大まか（通話、ゲームなど） | しない。推測になる | — |
| アプリが名乗っている権限（Mac の Info.plist、snap の接続、Flatpak の権限） | しない。絞り込みにだけ使う | 使えることと、使うことは違う |

実機で見たこと（2026-11-16）：

- Mac では、機器を開いているプロセスの名前を、権限なしで読めた（Stream Deck の公式ソフトが、そう見えた）。Linux では、同じユーザーのプロセスについて読める見込みだが、調べたときには、機器を開いているプロセスがなかった。
- アプリの種類は粗い。ホストのアプリ 122 個のうち、通話らしい種類を持つものは 2 個で、会議のための種類を持つものはなかった。ブラウザーは 3 個だった。
- 名乗っている権限は広すぎる。Mac のアプリ 53 個のうち 25 個が、カメラとマイクの両方を使うと名乗っていた。これで寄せると、半分のアプリが動く。

今週の案：

| 順 | 作るもの | 理由 |
|---|---|---|
| 今週 | ランチャーの項目ごとの、開く PC と理由の表示。使う人の指定 | 決定の 8 の 1。ほかの手がかりが外れたときの直し方でもある |
| 今週 | 会議のページを、項目として登録する | 決定の 8 の 3。会議アプリを持たない人でも、これだけで例のとおりになる |
| 今週 | 書いてあるもの（機器の説明、会議アプリの表）と、会議のための種類 | 見るだけで決まる。試験が書きやすい |
| 次 | 実際に使ったのを見て、次から反映する | Linux で読めることを、まだ確かめていない。覚えた中身の見せ方と消し方も要る |

- 寄せるのは、その機器が、どこかの PC に挿してあるときだけである。
- 仮想のカメラは、数えない。Mac には、カメラのソフトが作った仮想のカメラが見えていた。
- 家か出先かは、相手の PC を LAN の中で見つけたか、VPN ごしに到達先を指定してつないでいるかで分ける（R-13）。
- 覚えた中身は、ペアリングした端末の外へ出さない。

## 制約

- 受け側が Mac の付け替えはしない。Mac のアプリで使う機器は、その Mac に直接挿す。
- 2026-11-15 の版は「Linux や Windows のアプリで使う機器は、どの PC に挿してあってもよい」と書いていた。Windows に挿した機器は出せないので、「Linux か Mac に挿してあれば、付け替えて使える」に直した。
- Mac から出す側は root 権限が前提。
- Windows から出す側の既存実装（usbipd-win）は GPL-3.0 なので使わない。必要になれば内製する。
- USB/IP の手順そのものには、認証も暗号化もない。R-13（相互認証、端末ごとの USB の権限）を満たす運び方は、まだ決めていない。付け替えを作るときに、この文書に足す。

## 権限と、使う人の手間

権限の要る処理を増やすときは、理由を ADR に残す決まりである（AGENTS.md）。2026-11-16 に、Ubuntu 24.04 のホストと、macOS 26 の Mac を、何も変えずに調べた。

| 場面 | 要る権限 | 理由 | 実機で分かったこと | 使う人の手間 |
|---|---|---|---|---|
| 機器の一覧（Linux） | なし | sysfs は誰でも読める | つながっている 23 台（ハブを含む）の ID と種類を、権限なしで読めた | ない |
| 機器の一覧（Mac） | なし | OS が持っている機器の情報は、誰でも読める | `system_profiler` と `ioreg` から読めた | ない |
| Stream Deck の直接制御（Linux） | 導入のときに 1 回、udev の決まりを入れる（root）。動かすときは要らない。権限は、グループに与える。`uaccess` だけには頼らない | HID の機器と直接話す口（hidraw）は、既定では root しか開けない | 口は 18 個すべて root だけだった。Elgato の機器のための決まりは、入っていなかった | インストーラー（M9）ができれば、ない。.deb が決まりを一緒に入れる。それまでは、`sudo` のコマンド 3 行を 1 回 |
| Stream Deck の直接制御（Mac） | 未確認 | macOS が「入力監視」の許可を求めるかもしれない | 試していない。公式ソフトが動いている | 許可が要るなら、最初に 1 回、ダイアログに応える（R-12 の案内に入れる） |
| 会議アプリが使う、カメラとマイク（Linux のホスト） | グループに与える決まりが要る見込み | カメラと音のデバイスノードは、いまは `uaccess` で開けている | 下の「ホストの前に誰もいない状態」 | インストーラーができれば、ない |

付け替えは、今回の公開では作らない。作るときのために、分かったことを残す。

| 場面 | 要る権限 | 理由 | 実機で分かったこと |
|---|---|---|---|
| 付け替えの受け側（Linux） | root。仮想 USB コントローラー（`vhci-hcd`）の読み込みと、付け替えのたびの操作 | カーネルの仮想コントローラーに機器をつなぐ操作は、root だけに許されている | モジュールはあるが、読み込まれていない。Secure Boot は有効で、モジュールにはカーネルの署名がある。`usbip` コマンドは、いまのカーネル用が入っていない |
| 付け替えの出す側（Mac） | root | OS のドライバーから、機器を取り上げるため | 試していない |
| 付け替えの出す側（Linux） | udev の決まりで足りる見込み | 機器のデバイスノードを開ければ足りる見込み | 試していない |

- udev の決まりは、対応する機器が増えるたびに 1 行増える。フレームワークが、アダプターの説明から作る（ADR 0012）。
- 専用ユーザー（[ADR 0003](0003-isolation.md)）で動かすときも、グループで与える形なら届く。どのグループにするかは、M5 と合わせて決める。今週の確認では、ホストのユーザーがもう入っている `plugdev` を使う。

## ホストの前に誰もいない状態

決定の 10 を、M7 の範囲に当てはめた。ログイン画面のままの状態には、まだしていない。下の「動くか」は、仕組みと、いまの設定から見た見込みである。

| 何が | 動くか | 理由 | インストーラー（M9）が入れるもの |
|---|---|---|---|
| 機器の一覧 | 動く見込み | sysfs は、誰がログインしているかに関わらず読める | エージェントを、常駐のサービスにする。ホストでは、ログインしていなくてもユーザーのサービスが動く設定が、もう入っていた |
| Stream Deck のアダプター（Linux） | `uaccess` だけでは、動かない | `uaccess` は、その PC の前でログインしている人にしか効かない | グループに与える udev の決まり。エージェントのユーザーを、そのグループに入れる |
| 会議アプリが使う、カメラとマイク | 動かない見込み | カメラと音のデバイスノードは、グループ `video` と `audio` のもので、ホストのユーザーはどちらにも入っていない。いま開けているのは、持ち主がデスクトップにログインしていて、`uaccess` が効いているからである | カメラ：グループに与える決まり。音：音の流れ（M2）で決める |

- Stream Deck の確認（m7-plan.md の手順 5）で、ログイン画面のままの状態を作って、実際に確かめる。
- カメラは、会議アプリの窓が出るようになってから確かめる（映像の経路とアプリマネージャーが `main` に入ってから）。それまで、ホストの設定は変えない。
- Mac をホストにしたときの同じ確認は、M4 の機材で行う。

## 部品

- Stream Deck：第一の情報源は、Elgato が公開している HID の仕様（<https://docs.elgato.com/streamdeck/hid/>）。Stream Deck + のページがある。足りないところだけ、公開されている実装（components.md）を参考にする。フレームワーク（ADR 0012）の上のアダプターとして、内製する
- 付け替えの出す側：jiegec/usbip（MIT）。0.9.0 は、`rusb` クレートを通じて libusb（LGPL-2.1）を使う。採るときは、libusb を動的リンクで使い、components.md の「条件つきで使える」に書く（[ADR 0001](0001-license-and-components.md)）。クレートの表示は MIT なので、`cargo deny` はこれに気づかない
- 付け替えの受け側（Linux）：カーネル標準
- 付け替えの受け側（Windows）：usbip-win2（BSD-2-Clause）

## 確認項目

### スピーカーで聞く会議で、声が回り込まないか

- **確かめること：** 会議の相手に、相手自身の声が返って聞こえないこと。
- **なぜ起きうるか：** 会議アプリは、自分が鳴らした音を手がかりにして、マイクに入った相手の声を消す。音をほかの PC のスピーカーから出すと、鳴る時刻が遅れ、時計も別になる（ADR 0005 の配信経路）。アプリの消し方がそれに追いつくかどうかは、試すまで分からない。
- **3 つの形で確かめる：**
  1. 会議アプリのある PC のスピーカーで聞く。この仕組みは音に関わらない。比べるための基準である。
  2. 会議アプリのある PC の音を、ほかの PC の「音の出口」から聞く。
  3. 2 に加えて、会議アプリの窓を、ほかの端末に映す。1 つ目の例の形で、ふだんはこの形になる。
- ヘッドホンで聞くときは、対象にしない。
- 回り込んだときの手当ては、決めていない。確かめた結果を見て、この文書に足す。

## 結果

- 起動先の選び方（R-04）は、「手元 → 起きているホスト → 負荷の低いホスト」の前に、機器の条件を見る形になる。同じアプリが手元にあっても、機器がほかの PC にあると分かっていれば、そちらで開いて映像で中継する。手元で動かすより、遅延は増える（[ADR 0002](0002-latency-first.md) の順は変えない）。
- 「その他」の機器は、今回の公開では、挿した PC のアプリからしか使えない。一覧には、そう出す。Mac に挿さっているときは、「Linux の PC に挿すと、Linux のアプリから使えます」と出す。文書を読まなくても、挿す場所が分かるようにするためである。
- Mac の会議アプリは、ほかの PC のマイクとカメラを使えない。Mac で会議をするなら、その Mac のマイクとカメラを使う。
- マイクの音は運ばない。ADR 0005 に、入る音は今回の範囲に入れない、と書き足す（音の流れで行う）。
- アプリマネージャー（M3）は、起動先を選ぶときに、機器の一覧を見ることになる。会議の決まりのために、一覧には、USB でない内蔵のマイクとカメラも入れる。
