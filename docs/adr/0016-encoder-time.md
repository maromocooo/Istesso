# ADR 0016：圧縮にかかる時間を縮めるか。縮めるなら、どの作りにするか

- 状態：一部を採用（2026-11-17）。**B（効果だけを測る試験プログラム）は、やってよい、と決まった。** その先（C、D）へ進むかどうかは、B の数字と、別に進んでいる自前の圧縮の実験の結果を見て、人が決める。LGPL のコードへの差分は、このリポジトリに置かない、と決まった
- 日付：2026-11-17

## 背景

仮の判定（[記録](../measurements/2026-11-16-m1-provisional-verdict.md)）で、手元の窓との差は中央値 11.30 ms、合格ラインまでの余裕は 0.7 ms だった。足される区間のうち、いちばん大きいのが「色の変換と圧縮」の 4.0 ms で、分けて測ると、色の変換は 0.16 ms、エンコーダーが 3.92 ms だった（[記録](../measurements/2026-11-16-encode-split.md)）。

- 圧縮の時間は、ばらつきが小さい（中央値 3.91 ms、99% 4.20 ms）。待ち行列ではなく、エンコーダーが 3440×1440、4:4:4 の 1 フレームにかける時間そのもの、と見ている。
- いまは、GStreamer 1.24.2 の `nvcudah265enc` を、いちばん速い設定（`preset=p1 tune=ultra-low-latency`）で使っている。設定で縮める余地は、もう残っていない（[画質の記録](../measurements/2026-11-16-quality.md)）。

## 調べてわかったこと

- **NVENC には、1 フレームを横に分けて、複数のエンコーダーに同時に圧縮させる機能がある**（split frame encoding）。エンコーダーを 2 つ積んだ GPU で使える。ホストの RTX 4090 は 2 つ積んでいる。H.265 と AV1 で使える。
- 指定は、エンコーダーを開くときの `splitEncodeMode`。自動（解像度と設定から決まる）、2 つに分けることを強制、3 つに分けることを強制、分けない、がある。強制の指定は、Video Codec SDK 12.1 から。
- NVIDIA の資料にある効果は、8K の変換での値：2 つに分けて、処理できる量が平均 1.8 倍。画質の代償は、同じ画質に要るビットレートで 2% 未満。**3440×1440、4:4:4、いちばん速い設定での効果は、資料にない。** 分けるための手間のぶん、小さい絵では効きにくいはずで、測らないと分からない。
- **GStreamer 1.24.2 の `nvcudah265enc` には、この指定がない**（ホストで `gst-inspect-1.0` で確かめた）。新しい版にあるかは、確かめられていない。
- 分けて圧縮するとき、「同時に圧縮できる数」（GeForce は PC 1 台で 8 本）を何本ぶん使うかは、資料から読み取れていない。アプリマネージャーの上限の設計に関わるので、試すときに数える。
- ライセンス：
  - NVENC を呼ぶためのヘッダー（`nvEncodeAPI.h`）は、MIT の許諾文が先頭に付いた形で配られている（FFmpeg の nv-codec-headers）。`docs/components.md` も「ヘッダーは MIT、本体はドライバー」としている。採用する前に、使う版のファイルの先頭で確かめる。
  - エンコーダーの本体（`libnvidia-encode`）は、NVIDIA のドライバーに入っていて、こちらからは配らない。SDK の本体（サンプルや文書）は、リポジトリに入れない。
  - GStreamer の NVIDIA 向けのプラグインは LGPL。直して使うなら、直した分を LGPL で公開することになる。このリポジトリ（MIT OR Apache-2.0）に、LGPL のコードを直す差分のファイルを置くことになる点は、決めが要る。

## 比べる案

| 案 | やること | 見込み | 手間 | 配るもの、ライセンス | 弱み |
|---|---|---|---|---|---|
| A. 何もしない | — | 0 | 0 | 変わらない | 余裕は 0.7 ms のまま。映像の暗号化と、自前のクライアントでの増減しだい |
| B. 先に、効果だけを測る | NVENC を直接呼ぶ小さな試験プログラムを書く。判定と同じ大きさと設定の絵を、分ける指定のあり・なしで圧縮して、時間と画質を比べる。経路には入れない | 効果が分かる（値そのものは縮まらない） | 1〜2 日 | ヘッダー（MIT）だけ。リポジトリには、試験プログラムと、ヘッダーの入手のしかたを置く | 経路に入れたときの値は、別に測る必要がある |
| C. GStreamer のプラグインを直す | `nvcudah265enc` に、分ける指定を足す（数行）。直したプラグインを、ホストでビルドして使う | B で分かった効果が、そのまま経路に出る | 2〜3 日（ビルドの用意を含む） | 直したプラグイン（LGPL）。差分を公開する。元のプロジェクトへの提案もできる | LGPL の差分を、このリポジトリに置くかどうか。GStreamer の版に結び付く |
| D. NVENC を自前で呼ぶ | 色の変換のあとのフレーム（GPU の上）を受け取り、自前のコードで NVENC に渡す。GStreamer のエンコーダーは使わない | B の効果に加えて、設定を細かく選べる（参照フレームの持ち方、スライス、欠けたときの立て直し） | 1〜2 週間 | ヘッダー（MIT）と自前のコード | GPU の上のフレームを GStreamer から受け取る部分が、安定していない API に頼る。作る量が多い |
| E. GStreamer を外す | コンポジターから圧縮までを、すべて自前にする | D に加えて、色の変換（0.16 ms）と受け渡しが縮む | 数週間 | 自前のコード | いちばん大きい作り直し。得られる時間は、D とほとんど変わらない |

## 提案

**B を先にやる。その値を見て、C か D を選ぶ。E は、いまはやらない。**

- 理由：効くかどうかが、まだ分からない。3440×1440 で 2 つに分けても、縮むのは 0.5 ms かもしれないし、1.5 ms かもしれない。B は 1〜2 日で、経路に何も足さずに、その答えが出る。
- B で、圧縮が 1 ms 以上縮むと分かったら：
  - 今週の公開に間に合わせるなら C（小さい直しで、効果がそのまま出る）。LGPL の差分の置き場所を、先に決める。
  - 欠けたときの立て直しや、窓ごとの設定まで見込むなら D。
- B で、縮むのが 0.5 ms に満たなければ：この道は閉じる。余裕は、合成を省くこと（[M1 の計画](../m1-plan.md) の候補）と、入力の受け渡しで取り戻す。
- 順番：追記で決まった順（内訳を測る → 自前のクライアントとホスト → 映像の暗号化 → 余裕が 0.5 ms を切ったら合成を省く）は変えない。B は、ホストだけでできて、ほかの作業と重ならないので、その合間に入れられる。

## 決まったこと（2026-11-17）

1. **B（効果だけを測る試験プログラム）は、やってよい。** ヘッダーは、FFmpeg の nv-codec-headers（MIT）から、作業用のフォルダーに取ってくる。パッケージは入れない。
2. **その先へ進むかどうかは、まだ決めない。** B の数字と、別に進んでいる実験の結果を見て決める。その実験は、ハードウェアのエンコーダーを使わない自前の圧縮で、文字入力やスクロールのような絵の圧縮と復元の時間を縮めることをねらう（このリポジトリの外で、持ち主が進めている）。うまくいけば、あとで、切り替えできる形で組み込む。
3. **LGPL のコードへの差分は、このリポジトリに置かない。** 置くなら、元のプロジェクトの fork（別のリポジトリ。元のライセンスのまま）に置く。このリポジトリのライセンスを、MIT と Apache-2.0 だけに保つためである。C に進む場合も、この決まりに従う。
