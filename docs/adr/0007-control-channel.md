## 背景

ペアリング（ADR 0006）を終えた端末は、互いの公開鍵を固定して持っている。これを土台に、役割表・アプリ一覧・負荷をやり取りする通信路が要る。将来はアプリの起動や入力の制御もここを通るので、「相手が誰か」の確認は最初から厳密に作る。

あわせて、IP アドレスが変わっても相手を見つけられる仕組みが要る。リンクのしやすさは必須要件（R-13）である。

## 決定

### 通信路

- TCP（既定のポート 47801）の上で Noise XX（`Noise_XX_25519_ChaChaPoly_SHA256`）を実行する。実装は `snow` を使い、暗号の手順は自作しない。
- 端末の身元は Ed25519 の鍵で、**署名にしか使わない**。鍵交換用の X25519 鍵はプロセスごとに作ってメモリにだけ置き、その公開鍵に身元の鍵で署名したもの（以下「証明」）をハンドシェイクの中で送る。libp2p の Noise ハンドシェイクと同じ考え方である。
  - 身元の鍵を鍵交換に流用する案（Ed25519 から X25519 への変換）は採らない。`ed25519-dalek` の文書が勧めておらず、鍵を分けても実装は増えない。

| 順 | 向き | 内容 |
|---|---|---|
| 1 | 接続側 → 受け側、受け側 → 接続側 | `ISC1`（プロトコル名と版）。違えば、その旨を表示して切る |
| 2 | 接続側 → 受け側 | Noise メッセージ 1（`e`） |
| 3 | 受け側 → 接続側 | Noise メッセージ 2（`e, ee, s, es`）＋受け側の証明 |
| 4 | 接続側 | 証明を検証し、ペアリング済みの相手かを確かめる。違えばここで切る |
| 5 | 接続側 → 受け側 | Noise メッセージ 3（`s, se`）＋接続側の証明 |
| 6 | 受け側 → 接続側 | 判定（受け入れる／信頼していない）。ここから暗号化済み |
| 7 | 双方向 | メッセージ |

性質：

| 脅威 | 対応 |
|---|---|
| 記憶したアドレスや発見したアドレスに別の端末がいる | ハンドシェイクで弾く。相手を指定して接続した場合は、ペアリング済みの別の端末でも弾く |
| 他人の身元を名乗る | 証明は鍵交換用の鍵に結び付いており、その秘密鍵がなければハンドシェイクが完了しない。他人の証明を写しても通らない |
| ペアリングを解除した端末がつなぎ続ける | 受け側は接続のたびにペアリング一覧を読み直す。解除は次の接続から効く |
| 知らない相手に身元を明かす | 接続側は、相手を確かめてから自分の身元を送る |
| 認証前に資源を使わせる | 認証前に受け付けるのは 512 バイトまでのハンドシェイクだけ。**ハンドシェイクの全体に期限がある**（待ち受ける側。既定 5 秒）。1 バイトずつ、待ち時間が切れる直前に送ってくる相手も、期限で切る。同時接続数に上限がある |
| 途中で書き換える、順序を変える | Noise の認証つき暗号と連番で検出し、その接続を捨てる |
| ハンドシェイクだけを終えた接続で、流れている会話を止める、番号を進める（2026-11-17） | ホストは、最初の申し込みが来た接続だけを採る。申し込みは、暗号化された通信路の中を通るので、ペアリングの鍵を持たない相手には送れない。下の「つなぎ直しの試みを、重ねる」 |

### メッセージ

- JSON。`type` で種類を表す。いまは `ping`、`manifest`（役割表）、`apps`（アプリ一覧）、`status`（負荷と空きメモリ）。どれも「閲覧」の権限が要る。
- 端末は1台ずつ更新されるので、版のずれに寛容にする。
  - 知らないリクエストには `unsupported` を返し、接続は続ける。
  - 読む側は知らない項目を無視する。知らない列挙値は「不明」に落とすか、その要素だけ読み飛ばす（`istesso_proto::known_only`）。
  - 互換性のない変更をするときは、先頭の `ISC1` の版を上げる。
- 1メッセージは最大 16 MiB。Noise の上限（65535 バイト）を超える分は分割して送る。
- 待ち時間は2種類に分ける。相手が現れるまで（接続とハンドシェイク）は短く（既定 0.8 秒）、眠っている端末1台のために待つのはこれだけ。現れた相手の答えは長く待つ（既定 5 秒）。答えが遅いことと、いないことは別である。
- エージェントは役割表をメモリから答える。PC の調査（macOS では 1 秒以上かかる）は裏で定期的に行い、問い合わせを待たせない。
- いまは短い接続（つないで、聞いて、切る）。入力と映像は例外で、流れているあいだ開いたままになる（下の「入力」と「映像」）。

### 入力（2026-11-16 に追加）

キーボードとポインターの入力は、この制御チャンネルで運ぶ。打ったキーが、暗号化されずに LAN を流れることがないようにするためである。新しい暗号の部品は足していない。

- `input_open`：「入力を送ってよいか」。「操作」の権限が要る。受け側は、入力を受け取るアプリを映しているときに `input_open` と答える。権限がなければ `forbidden`、受け取る相手がいなければ `internal`。
- `input`：入力のイベントの並び（`events`）。`input_open` が通った接続でだけ受け付ける。**答えは返さない。** 打ったキーを、往復のぶん待たせないため。空の並びは「まだここにいる」の合図で、送る側が 2 秒おきに送る（受け側は、5 秒黙った相手を切る）。
- イベントは `istesso_proto::InputEvent`：`key`（キーが下がった、上がった）、`pointer_at`（ポインターの位置。絵の画素で、左上から）、`button`、`scroll`。キーとボタンは、Linux の番号（`input-event-codes.h`）で表す。文字ではなく、キーボードの上の場所である。その場所に何の字があるかは、アプリを動かしている側が決める。知らないイベントは、その 1 つだけ読み飛ばす。
- 受け側のエージェントは、イベントを、アプリを映しているプログラムへ、手元のソケットで渡す（Linux では `$XDG_RUNTIME_DIR/istesso/input.sock`。本人しか開けない場所）。
- この接続は、入力が続くあいだ開いたままになる。短い接続、という上の説明の例外である。
- 送る側は、相手を覚えているアドレスのうち、どれでつなぐかを指定できる（`istesso input relay --address`）。ホストが有線と Wi-Fi の両方でつながっているとき、入力を有線に通すためである。つながる相手がペアリング済みの端末であることの確認は、変わらない。
- Mac の Command キーは、既定では Control として送る（Mac で Command を使う操作は、Linux のアプリでは Control を使うため）。Super として送る設定も残す。これは送る側（クライアント）の決まりで、メッセージの形は変わらない。
- 修飾キーは、押した知らせが来なくても、キーに付いた印から補う。キーを送るプログラム（ボタンにホットキーを割り当てる道具など）は、修飾キーを押した知らせを出さず、キーに「Command つき」の印だけを付けて送ることがある。印にあって、押されていない修飾キーは、そのキーの前に押し、あとで離して送る（2026-11-16。Command-A が「a」として届いた不具合の直し）。これも送る側の決まりで、メッセージの形は変わらない。
- 修飾キーの状態は、送る側が、決まったときに、Mac の印と合わせ直す（2026-11-18 に決定。Blender で、Shift-A、Option でのドラッグ、修飾キーつきのスクロールが、修飾キーなしとして働いた試用のあと。原因は分かっていない）。合わせ直すのは、キー、修飾キーの知らせ、ボタン、スクロール、ポインターの動き、窓がキーを受けるかどうかが変わったとき、である。それ以外のとき（たとえばドラッグの途中）は、合わせない。メッセージの形は変わらない。
  - 修飾キーの知らせに、その修飾キーの印があり、左右どちらのキーかを示す印がないときは、左のキーとして送る（これまでは、送らなかった）。
  - 比べるのは、イベントの印と、ホストへ「押した」と送ってある修飾キーである。押したと送ってあるのに印にないものは、離したと送る。離したと送るのは、押したと送ってあるものだけである。
  - 印にあるのに押したと送っていないものは、イベントによって扱いが違う。キーでは、上の「補う」のとおり、前に押してあとで離す。修飾キーの知らせでは、ほかの修飾キーも合わせ、左のキーで押したと送る。ボタンとスクロールでは、窓がキーを受けているとき（作業中のアプリのキーの窓のとき）は、左のキーで押したと送り、押したままにする。受けていないとき（macOS は、スクロールや、アプリを前に出すクリックを、ポインターの下の窓へ送る）は、前に押してあとで離す。離した知らせは、別のアプリへ行き、ホストで押されたままになるからである。ポインターの動き（窓に入ったときも）では、離すだけで、押さない。合っていれば、何も送らない。
  - 窓がキーを受けなくなったら（別の窓、別のアプリ、Command-Tab、そして、たぶん画面を撮るキー。撮る画面が窓からキーを取るかどうかは、実機で確かめていない）、押したと送ってあるキーをすべて離したと送り、覚えを消す。窓がまたキーを受けるようになったら、そのときの修飾キーを読み、押されているものを押したと送る（絵がつなぎ直しの最中なら送らない。つながったときに、窓がキーを受けていれば、合わせ直す）。キーを取ったことを窓に知らせないもの（Spotlight、入力方式のパレット、メニューなど）のあとは、次のポインターの動きか、キーか、ボタンか、スクロールで、離すほうだけ合う。
  - 分かっていて、残したこと。
    - プログラムのホットキーが、Command の印だけを付けてくると、人が手で押している Shift を、離したと送る。そのあとの Shift つきのキーは、Shift を借りて送る。クリックかスクロールで、押したままに戻る。
    - 押した知らせが失われたのか、プログラムのホットキーなのかは、イベントの印からは分からない。だから、キーでは借りる（押したままにはしない）。手元のキーボードの本当の状態（`CGEventSourceFlagsState`）を読めば分かるが、キーの経路に呼び出しが 1 つ増える。計測なしには入れない。
    - Command を Control として送るとき、Command と手の Control は、ホストでは同じキーになる。左右が違って届くことがある。押されたままには、ならない。
- 計測のために、入力が通った時刻を書き出せる（`istesso input relay --timings`、`istesso agent --input-timings`）。書くのは、メッセージを受け取った時刻、渡し終えるまでの時間、イベントの数だけで、何が入力されたかは書かない。時刻だけでも、いつ打ったかが分かるので、指定したときにだけ書き、ファイルは持ち主だけが読める。ふだんは使わない。
- セッション（どのアプリへの入力か）の区別は、まだない。1 台のホストが映すアプリは 1 つ、という前提で動く。アプリマネージャー（M3）がセッションを決めたら、それに合わせる。

### 切れたあとの、つなぎ直し（入力）（2026-11-17）

送る側（`istesso input relay`。中身は `istesso-agent` の `relay`）と、受け側（`istesso agent`）に入れた。セッション（どのアプリへの入力か）とは、関係なく作ってある。2 台でも確かめた（[記録](../measurements/2026-11-17-reconnection-check.md)）。

送る側は、接続が切れた回数を、いつも言う（標準出力、時間の記録、ソケットの隣の小さいファイル。0 回のときも言う）。2026-11-17 に決まった。

入力の接続は、流れているあいだ開いたままなので、切れることがある。両端が生きていても、切れる（Mac で、アプリが新しく登録されたときに、macOS が、つながっている接続に届くパケットを黙って捨て始めることがある。[ADR 0015](0015-media-transport.md) の「切れたあとの、つなぎ直し」）。切れたら、**送る側（`istesso input relay`。あとでは、クライアント）が、すぐにつなぎ直す。** 映像、音と、同じ決まり、同じ数にする。

**通信路の手順（`istesso-link`。ハンドシェイク、封のしかた）は、変えない。** つなぎ直しは、新しい接続を、いつもの手順で開いて、`input_open` をやり直すだけである。足すのは、ハンドシェイクのあとのメッセージ 1 つ（`input_alive`）と、`input_open` の項目 1 つである。先頭の版（`ISC1`）も、プロローグも、上げない（下の「変更の手順」の「メッセージの追加は版を上げずに行える」にあたる）。

直す前の動き：

- 送る側は、受け側から何も読まない（`input` に、答えは返らない）。そのため、**黙って切られたことに、気づけない。** 書き込みが失敗するのは、OS が再送をあきらめたあとで、何分もかかる。
- 書き込みが失敗すると、送る側のプログラムは、終わる。つなぎ直さない。
- 受け側は、接続が終わっても、押されたままのキーやボタンを離さない。

#### 何を「切れた」とみなすか

- 書き込みか読み込みが、失敗した。
- **1 秒のあいだ、受け側から何も届かない。** 数え方は、「まだここにいる」と言ってから 0.5 秒、答えが来ないこと（0.5 秒おきに言うので、前の答えから数えて 1 秒になる）。自分が言った時刻から数えるので、送る側のプログラムがしばらく動けなかったとき（Mac が忙しかった、一瞬眠った）に、それを相手の沈黙と取り違えない。そのために、受け側が「ここにいる」と答えるようにする：
  - 送る側は、`input_open` に `"alive": true` を付けて、「空の `input` には答えてほしい」と言う。受け側は、それを知っていれば、答えの `input_open` に `"alive": true` を付ける。
  - そう決まった接続では、送る側は、打っているあいだも、0.5 秒おきに空の `input`（「まだここにいる」）を送る。受け側は、**空の `input` にだけ**、`{"type":"input_alive"}` と答える。
  - **キーやポインターを運ぶ `input` には、これまでどおり答えない。** 打ったキーを、往復のぶん待たせない、という決まりは変わらない。送る側は、答えを、送るのとは別に読む（送るのを、読むことで待たせない）。
  - 古い受け側は、知らない項目を無視するので、答えに `alive` が付かない。そのときは、沈黙では見分けない（空の `input` は、これまでどおり 2 秒おき）。書き込みの失敗でだけ、つなぎ直す。古い送る側は、頼まないので、新しい受け側も答えない（読まれない答えを、ためない）。
- 受け側は、`alive` と決まった接続では、**2 秒**黙った相手を切る（これまでは 5 秒）。切るとき、その接続が押したままにしていたキーとボタンを、離す（下）。

#### どれだけ速く、つなぎ直すか

- 切れたと分かったら、待たずに 1 回め。その 10 ms あとに 2 回め、50 ms あとに 3 回め（2026-11-17 の夜に足した。下の「はじめの 2 つ」）。そのあとは、前の試みを待たずに、0.5 秒おきに次の試みを始める（切れてから 5 秒のあいだは、走っている試みが 4 つより少なければ 0.1 秒おき）。試みの 1 回（名前を引くこと、接続、ハンドシェイク）には、合わせて 2 秒。`input_open` は、最初にハンドシェイクを終えた接続でだけ送り、その答えには 1 秒。下の「つなぎ直しの試みを、重ねる」（2026-11-17 に、この形に直した）。
  - それまでは「0.25 秒おき、10 秒たったら 1 秒おき、1 回には合わせて 1 秒」と書いていた。コードは、待ちの 1 回ごとに 1 秒を与えていて、文書と合っていなかった。いまは、文書もコードも、「合わせて」である。
- 相手は、はじめに指定した端末だけ（`--to`）。アドレスの選び方（`--address`）も、はじめと同じ。
- 目安：失敗が見えた切れ方では 0.25 秒以内、黙って切られたときは、最後に答えが届いてから 1.25 秒以内に、入力がまた通る。Mac の中だけ（ループバック）で試すと、黙って止めてから 0.6 秒で切れたと分かり、0.01 秒後に、また通った。

#### つなぎ直したあと

- `input_open` は、**やり直すたびに、そのときの権限で確かめられる。** 受け側は、頼まれたときにペアリング一覧を読み直した値を使い、入力を受け取るのは、そのセッションを映している端末からだけである（どちらも、2026-11-17 に決まった。書き込みは、アプリマネージャーの流れが、この文書の「入力」に行う）。つなぎ直しは、解除や、権限の取り消しを、すり抜けない。
- **受け側は、入力の接続が終わったら（切れた、黙った、同じ端末の新しい接続に替わった）、その接続で押されたままのキーとボタンを、離す。** キーが押されたままになって、字が打たれ続けることがないようにする。
- **同じ端末が `input_open` をやり直したら、受け側は、その端末の古い入力の接続を、その場で終える。** 死んだ接続が、2 秒のあいだ残らないように。
- **送る側は、切れているあいだに打たれたキーと、押されたボタンを、あとから送らない。** 1 秒遅れて届くキーは、もう変わってしまった画面に打たれる。また、黙って切られたときは、こちらからのパケットが、相手に届いていたかどうかが分からない。送り直すと、同じキーが 2 度打たれうる。
- つながったら、送る側は、**修飾キーとボタンの状態を、合わせ直す**（2026-11-17 に決定）。**いま押されている修飾キー**（Shift、Control、Alt、Super）は、押し直す（Shift を押したまま、切れ目をまたいで打った字が、小文字にならないように）。ボタンは、ホストの側を、すべて離れた状態にそろえる（受け側が、接続の終わりで離している。「合わせ直す」をこう読むことは、ADR 0015 で、人の確認を待っている）。押されたままのボタンを押し直すことは、しない（ドラッグが、別の場所で始まる）。ふつうのキーも、押し直さない（字が 1 つ余分に打たれる）。ポインターの位置は、最新の 1 つを送る。
- 将来の候補（いまは作らない）：ごく短い切れ目（0.5 秒未満）で、同じ窓が前に出たままなら、打った文字を送り直す。

#### つなぎ直さないとき

| 起きたこと | 送る側に、どう見えるか | すること |
|---|---|---|
| ペアリングを解除された | つなぎ直すと、ハンドシェイクで「信頼していない」 | やめる |
| 「操作」を外された。セッションを映している端末ではなくなった | 切られる。`input_open` に `forbidden` | やめる。取り返しには行かない |
| 入力を受け取る相手がいない（アプリを映すプログラムが、動いていない） | `input_open` に `internal` | 1 秒おきに、やり直す。映すプログラムが起動し直されるあいだを、またぐため |
| 版が合わない | `unsupported` | やめる |
| 受け側が落ちた、眠った | 何も言われずに切れる。つながらない | やり直し続ける |
| 起動した側が、止めた | — | やめる |

やめるとき、送る側は、わけを 1 行で言って終わる（鍵、打たれた内容、アドレスは、言わない）。

#### セッションの話と合わせるとき

この節のものは、セッションを知らない。アプリマネージャー（M3）の入力（`input_open` がセッションを名乗る、映している端末だけが送れる）と合わせるときに、決めること：

- 受け側が「同じ端末の古い接続を終える」ときの「同じ」は、いまは端末ごとである。セッションごとの入力になったら、端末とセッションの組ごとにする（1 台が、2 つのセッションに、別々の接続で入力を送れるように）。
- 送る側がつなぎ直すときの `input_open` に、セッションを付ける。

#### 映像との関係

- 映像と入力は、別々の接続で、別々に切れ、別々につなぎ直す。
- 絵が古いと分かっているあいだ、キーとボタンの「押した」を渡さない、という決まりは、窓を持つ側（見る側のプログラム）のものである（ADR 0015 の「そのあいだのキーとボタン」。2026-11-17 に決定。計測の道具のビューアーには、入れてある）。打った文字が落ちていることを人に知らせるのも、窓を持つ側である。入力の接続は、それとは関係なく、つないだままにする。

### 映像（2026-11-17 に追加。[ADR 0015](0015-media-transport.md)）

映像は、この文書の通信路を、映像のための TCP の接続（既定のポート 47803）でそのまま使って運ぶ。`istesso-link` の `Channel` を呼ぶだけで、ハンドシェイクにも暗号にも、何も足していない。`istesso-link` のコードも、変えていない。

- 違うのは、ハンドシェイクのあとに流れるメッセージの中身（最初のやり取りと、フレーム）と、接続が長く続くことである。求める権限は「閲覧」。
- 接続が長く続くので、「解除は次の接続から効く」では足りない。映像を出す側は、流しているあいだ、1 秒より長くは空けずにペアリング一覧を読み直し、解除されたか、権限を外された相手の接続を切る。一覧が読めないときは、何も送らない。入力の接続が、同じことをしている（上の「入力」）。
- 待ち受ける側は、ハンドシェイクと最初のメッセージを合わせて 3 秒で締め切る。待ち時間を、読み書きのたびに数え直さないことは、制御チャンネルと同じである。
- キーフレームの求めは、同じ接続を逆向きに流れる。
- 1 メッセージが Noise の上限を超えるときに分けて送る決まり（上の「メッセージ」）を、大きなフレームが使う。
- 映像の接続が切れたあとのつなぎ直しも、新しい接続を、この文書の手順で開くだけである。手順は、変えない（ADR 0015 の「切れたあとの、つなぎ直し」）。
- 通信路の手順を変えるときは、映像も同じ変更を受ける。映像をデータグラム（UDP）に移すときは、手順の変更になるので、先にこの文書を更新する（ADR 0015 の「データグラムに移る条件」）。

### つなぎ直しの試みを、重ねる（2026-11-17。入力と映像に入れた。音は、これから）

**仕組み（`istesso-link`）と、入力、映像に入れた。** 試験は、この Mac の中だけで行っている（にせの時計と、ループバック）。**2 台では、まだ確かめていない**（下の「測ること」）。音（ADR 0011。`m2-audio` ブランチ）は、main に入っていないので、あとで入れる（下の「3 つの会話で、どう分けるか」）。

目標は、持ち主の読み方（2026-11-17）のとおりである：**切れたあと、道がまた開いてから 1 秒以内に、つながり直す。いつも。ホストが 1 時間いなかったあとでも。**

#### 困っていたこと（直す前）

- つなぎ直しの 1 回（接続、ハンドシェイク、最初の返事）には、締め切りがある（音は合わせて 2 秒、映像は合わせて 1 秒。入力は、待ちの 1 回ごとに 1 秒で、ホストが黙っていれば、接続の 1 秒で終わる）。直す前は、1 回が終わってから、次を始めていた。
- 自分の PC が接続を断るとき（Mac が、ローカルネットワークの決まりを作り直しているあいだ）は、1 回がすぐ失敗するので、次までは 0.1〜0.25 秒である。道が開いてから 0.23〜0.37 秒でつながった（音の計測。`m2-audio` ブランチの記録）。
- **ホストが何も答えないとき（電源が切れている、ケーブルが抜けている、眠っている）は、1 回ごとに、締め切りまで待つ。** 次の試みまでが、最長で 2.25 秒になる。道が開いた直後に始まった試みがなければ、1 秒を超える。
- **締め切りを短くするのは、直し方ではない。** つなぐまでには、往復が 5 回ある（接続 1、`ISC1` 1、Noise 2、最初の返事 1）。往復に 400 ms かかる道（VPN、遠い Wi-Fi）では、ハンドシェイクが終わるのが 1.6 秒、返事が届くのが 2.0 秒である。締め切りが短いと、そのホストには、いつまでもつながらない。
  - 読んでいて分かったこと 1：**映像の、つなぎ直しの締め切りは、合わせて 1 秒だった。往復 400 ms の道では、はじめの 1 回（3 秒）はつながるが、切れたあとは、二度とつながらなかった。** 音（合わせて 2 秒）も、往復 400 ms では、ちょうど足りない。映像は、この節で直した。
  - 読んでいて分かったこと 2：**入力は、文書とコードが食い違っていた。** 上の「どれだけ速く、つなぎ直すか」は「合わせて 1 秒」と書いていたが、コード（`Client::connect`）は、待ちの 1 回ごとに 1 秒を与えていて、全体は 3 秒まで続きえた。そのため、往復 400 ms の道でも、入力はつながり直していた。試みの締め切りを、3 つとも「合わせて」にそろえ、文書も直した。

#### 決まっていること（持ち主、2026-11-17）

1. 試みを、重ねる。新しい試みは、前の試みを待たずに、長くても 0.5 秒おきに始める（切れてから 5 秒のあいだは、いまの音と同じ 0.1 秒おき）。それぞれの試みが、自分の締め切りを持つ。最初にハンドシェイクを終えた試みを使い、ほかは捨てる。同時に走る数には、上限がある。
2. ホストは、ハンドシェイクを終えただけの接続のために、前の接続を手放さない。どの番号も進めない。クライアントが「これを使う」と言った接続だけを、採る。言われないままの接続は、数秒で閉じる。
3. 試みは、それぞれ、自分の鍵と、自分の番号の状態を持つ。試みのあいだで、共有するものはない。
4. つなぎ直しの 1 回は、試みが何回あっても、1 回と数える。
5. 公開の前の宿題（いまは作らない）：下の「宿題」。

設計を見たうえでの、持ち主の答え（同じ日）：

7. 試みの締め切りは、3 つの会話とも **2 秒**。届く範囲（往復 450 ms ほどまで）を書いておき、公開の前に、Wi-Fi と VPN で測る（下の「測ること」）。

9. 遅れて届いた申し込みのこと（下の「既知の不足」）は、いまは直さない。

同じ日の夜の、持ち主の決定：

#### 「これを使う」は、いまある最初の申し込みである。新しいメッセージは、足さない

「これを使う」には、どの会話にも、もうある最初のメッセージを使う：映像の `watch`、音の `subscribe`、入力の `input_open`。以下、「申し込み」と書く。

そうできるのは、3 つのホストが、いまも、申し込みが来るまでは何もしないからである（コードを読んで確かめた。音は、`m2-audio` ブランチのコード）。

| 会話 | ハンドシェイクを終えただけの接続に、ホストがすること | 申し込みが来たときに、ホストがすること |
|---|---|---|
| 映像 | 「まだ誰とも分かっていない相手」の枠を 1 つ使う（8 まで）。ほかには、何もしない | 「閲覧」と、映す相手かどうかを確かめる。同じ端末の古い接続を切る。映像の枠を取る。`stream` と答える。キーフレームを 1 枚求める |
| 音 | 同じ枠を 1 つ使う（16 まで）。ほかには、何もしない | 「音」の権限を確かめる。聞き手を、この接続に替える（聞き手の番号が 1 進む。前の送り手は、連番から番号を取らずに止まる）。`stream` と答える |
| 入力 | 同時接続の枠を 1 つ使う（64 まで）。つないできたアドレスを、手がかりとして覚える（相手は、ペアリング済みと確かめたあと。番号は、何も進まない） | 「操作」の権限を確かめる。同じ端末の古い入力の接続を終え、押されたままのキーとボタンを離す。`input_open` と答える |

変わるのは、つなぎに行く側である：**申し込みを、選んだ 1 本にだけ送る。** ホストの側は、いまの動きを、守る決まりとして書いておく（あとの変更で、崩さないため）。

1. ハンドシェイクを終えただけの接続のために、ホストは、流れている会話を終えない。キーフレームを求めない。聞き手の番号も、連番も進めない。押されたままのキーを離さない。
2. 採るのは、申し込みが来た接続だけである。採るときにすることは、いまと同じ（上の表の右の列）。
3. 申し込みが来ない接続は、閉じる。期限は 3 秒（下の「ホストの側」）。
4. 申し込みを待つ接続の数に、端末ごとと、全体の上限を置く（下の「ホストの側」）。

この形のよいところ：

- **通信路の手順（上の表の順 1〜7）は、変わらない。** 申し込みは、順 7 の最初のメッセージである。`ISC1` もプロローグも、上げない。メッセージも、項目も、足さない。**Noise の層に、新しく求めるものはない**（`Channel::initiate` と `Channel::respond` を、いまのまま呼ぶ）。
- **版が違っても動く。** 古いホストは、もう決まり 1 と 2 のとおりに動いている（足りないのは、決まり 4 の上限と、エージェントの 3 秒だけ）。古いクライアントは、試みを重ねないので、どの接続でも申し込みを送る。新しいホストには、いままでどおりに見える。

比べた案：試みのそれぞれが、最初の返事まで進み、そのあと、選んだ 1 本で新しいメッセージ（「これを使う」）を送る。ホストは、答えたが採っていない、という状態を、会話ごとに持つことになる（映像なら、`stream` と答えたのに、古い接続を切らず、キーフレームも出さない状態）。新しいメッセージを知らないホストでは、使えない。得るものは、選んだあとの往復が 1 回減ることだけなので、採らない。

#### つなぎに行く側の動き

言葉：**試み**は、接続とハンドシェイクまで（往復 4 回）。申し込みと、その返事は、試みには入れない。

| 項目 | 値 | わけ |
|---|---|---|
| 試みの締め切り（名前を引くこと、接続、ハンドシェイクを合わせて） | 2 秒。3 つの会話で同じ | それまでの音の値。往復 400 ms の道で、ハンドシェイクは 1.6 秒で終わる。**届くのは、往復 450 ms ほどの道まで**（往復 500 ms で、ハンドシェイクがちょうど 2 秒かかる。それより長い道のホストには、切れたあと、つながらない） |
| 新しい試みを始める間隔 | 前の試みを始めてから 0.5 秒。切れてから 5 秒のあいだは、**走っている試みが 4 つより少なければ**、0.1 秒 | 0.1 秒おきは、試みがすぐ失敗するとき（自分の PC が断るとき）のためのものである。そのときは、次を始めるときに、走っている試みがない。ホストが黙っているときは、試みが残るので、4 つ走った所で、0.5 秒おきになる |
| はじめの 2 つ（2026-11-17 の夜に足した） | 切れのあとの最初の試みから **10 ms あと**と **50 ms あと**に、1 つずつ。上の間隔の試みとは別に数える（上の間隔は、最初の試みから数えるので、4 つめは 0.1 秒あと）。**走っている試みが 4 つより少ないあいだだけ** | Mac は、アプリを作り直した（更新した）すぐあと、そのアプリの最初の接続を、短いあいだ落とす。見た値は 2 ms ほど、悪いときで 13 ms ほど。これがないと、次の機会は 0.1 秒あとになる。下の「はじめの 2 つ」 |
| 同時に走る試みの上限 | 8。1 つの会話（映像、音、入力のそれぞれ）ごとに | 0.5 秒より短い間隔で始めた 4 つ（はじめの 2 つを入れて。どれも、走っている試みが 4 つより少ないときにしか始めない）と、0.5 秒おきに始めた 4 つ（締め切りが 2 秒なので、0.5 秒おきの試みは、同時に 4 つまでしか残らない）。上の間隔の決まりだけで、8 を超えない。上限は、それでも超えそうなときの歯止めで、8 に達したら、新しい試みを始めない |
| 申し込みの返事を待つ時間 | 1 秒。返事の全体に、合わせて（入力も、映像も） | それまでの入力の値（入力は、それまで、読み込みの 1 回ごとに 1 秒だった。レビューを受けて、合わせて 1 秒にした）。往復 400 ms の道で、返事は 0.4 秒で届く。試みの締め切りとは別に数える（合わせて数えると、締め切りの間際にハンドシェイクを終えた試みは、返事を待てない） |
| 試みの 1 回が開く接続 | 1 本。入力で、相手のアドレスをいくつか覚えているときだけ、4 回に 1 回、2 本（下） | ホストが数えるのは、試みではなく、届いた接続である。上の数が、接続の数としても、ほぼそのまま言えるようにする |

- **始めるのは、切れたと分かった時点で、すぐ**（いまと同じ。つないだばかりの接続が切れたときだけ、0.25 秒待つ。これも、いまと同じ）。間隔の決まりは、前の切れのときに始めた試みにも当てはめる（切れが続いても、上限の 8 を超えないように）。
- **はじめの 2 つ（2026-11-17 の夜。持ち主の決定 11）。** 1 回の切れの試みが始まる時刻は、最初の試みから数えて、**0、10 ms、50 ms、0.1 秒、0.2 秒、…** になる（試みがすぐ失敗するとき）。ホストが黙っているときは、0、10 ms、50 ms、0.1 秒で 4 つが走るので、そこから 0.5 秒おき（0.6 秒、1.1 秒、…）。
  - **わけ。** Mac は、アプリを作り直した（更新した）すぐあと、そのアプリが始めた最初の接続を、短いあいだ落とす。見た値は 2 ms ほど、悪いときで 13 ms ほどである（持ち主が挙げた値。この文書のための計測では、ない）。10 ms あとの試みで、ふつうは通る。
  - **50 ms の段が要るわけ。** 悪いときの 13 ms は、10 ms を超えている。10 ms あとの試みも、落とされうる。50 ms の段がなければ、その次は 0.1 秒あとで、最初の機会が 0.1 秒まで遅れる。50 ms は、見た最悪の値の 4 倍ほどで、0.1 秒の半分である。
  - **変えていないもの。** はじめの 2 つも、試みの 1 つである：自分の締め切り（2 秒）、自分の鍵を持ち、走っている数に入る。始めるのは、**切れてから 5 秒のうちで、走っている試みが 4 つより少ないあいだだけ**（0.1 秒おきの試みと同じ決まり）。前の切れで捨てた試みが残っていて、合わせて 4 つ走っていれば、始めない。全体の上限の 8 も、同じに効く。切れた回数は、1 のまま。やり取りするものは、変わらない（接続が、多くて 2 本、早く開くだけである）。
  - **数えるのは、最初の試みから。** つないだばかりの接続が切れて 0.25 秒待ったとき、「ゆっくり」で 1 秒待ったときも、その待ちのあとの最初の試みから、10 ms と 50 ms である。0.1 秒の拍までに始められなかったぶん（「ゆっくり」の答えで待った、申し込みの返事を待っていた、プログラムが起こされるのが遅れた）は、あとから始めない。1 回の切れに、多くて 2 つである。
  - **値段。** 最初の試みが 10 ms で終わらない道では、切れのたびに、接続が 1 本（50 ms でも終わらなければ 2 本）、余分に開かれて、採られずに閉じられる。往復 4 回が 10 ms に入らないのは、往復 2.5 ms より長い道である。試みは、鍵を作ることと、ファイルを読むことにも時間を使うので、有線の LAN でも、そうなりうる（ループバックで、つなぎ直しの全体に 0.01 秒かかっている。上の「どれだけ速く、つなぎ直すか」）。足す前は、0.1 秒で終わらない道（往復 25 ms より長い道）でだけ、そうなっていた。ホストにとっては、ハンドシェイク 1 回ぶんの仕事と、閉じられる接続 1 本で、ほかには何も起きない（上の決まり 1。流れている会話は、止まらない）。
  - **入力のアドレスの数え方。** 入力が、ほかのアドレスへも行き始めるのは、切れてから 9 回めの試みのままである（下の「どのアドレスへ試みるか」）。はじめの 2 つも数に入るので、ホストが黙っているときの 9 回めは、2.8 秒あとから 2.6 秒あとに、早まる。
  - **起動のとき。** 持ち主の決定は「起動して最初の試みが失敗したあと」も含む。決定のもとは、こちらである（作り直したばかりのアプリが、起動して最初につなぐとき）。起動のときの最初の接続は、この仕組み（`Tries`）を通らない。
    - **映像には、入れた**（`istesso-media` の `rejoin` の `First`。ADR 0015 の「どれだけ速く、つなぎ直すか」）。1 回ずつで、重ねないことは、変えていない。失敗したあとの次の試みを、最初の試みを始めた時刻から数えて 10 ms、50 ms、そのあと 0.1 秒おきの、次に来る時刻に始める。失敗が 10 秒続いたあとの 1 秒おきは、そのまま。**効くのは、試みがすぐ失敗するときだけ**である：試みが黙って待たされるときは、1 回が 3 秒かかり、段は意味を持たない。そこにも効かせるには、起動のときにも試みを重ねる（この仕組みに通す）ことになる。作り直しになるので、今夜は入れていない。
    - **入力には、このブランチでは入れていない。** 入力の起動の道は、自前のクライアントのブランチにある。このブランチの `istesso input` は、`--keep-trying` を付けたときだけ、失敗のたびに 0.5 秒あとで、1 回ずつ（付けなければ、最初の失敗で終わる）。**合流のときにすること（宿題）**：入力の起動にも、映像と同じ段を入れる（最初の試みを始めた時刻から 10 ms、50 ms、そのあと 0.1 秒おき。数は、`Pace` の `early` と `quick` から取る。映像の `First` と同じ形にするか、起動を `Tries` に通す）。
- **最初にハンドシェイクを終えた試みを、採る。** そのとき走っているほかの試みは、捨てる：結果を受け取らず、接続を閉じる。接続の途中の試みは、途中では止められないので、自分の締め切りまでに終わり、終わった所で、そのスレッドが自分で閉じる。捨てた試みも、そのスレッドが終わるまでは、「走っている」に数える（つなぎ直しが続けて起きても、スレッドが増え続けないように）。**捨てた試みは、あとで何を持ってきても、使わない**（そのあとに次の切れが始まっていても）。
- **名前を引くことも、試みの締め切りのうちである。** アドレスを名前で指定した試みは、名前が引けなくても、締め切りで終わって、場所を空ける。名前を引くことそのものは、途中で止められないので、別のスレッドで行い、試みは、締め切りまでしか待たない。同じ名前を引いているあいだは、新しく引き始めない（あとから来た試みは、同じ答えを、自分の締め切りまで待つ）。引けない名前のために残るスレッドは、1 つである。数字のアドレスは、引かない。
- **採った接続で、申し込みを送り、返事を待つ。** 待つあいだは、新しい試みを始めない。

| 申し込みのあと | すること |
|---|---|
| 受け入れられた（`stream`、`input_open`） | つながった。ここから先は、いまと同じ（映像はキーフレームを待つ、入力は修飾キーを合わせ直す） |
| わけを言って、断られた | いまの表のとおり（上の「つなぎ直さないとき」、ADR 0015 の同じ名前の表）。やめるか、1 秒おきにやり直す |
| 1 秒、返事がない。または、接続が切れた | その接続を捨てて、試みを続ける。**同じ 1 回の切れの続きである**（数は増えない。「切れてから」の時計も、戻さない） |

- 試みが、やり直しても変わらない答えで終わったとき（ハンドシェイクで「信頼していない」、ペアリングしていない相手、指定と違う端末、版が合わない）は、いまと同じく、やめる。ほかの試みは、捨てる。
- 流れていた会話が、「ゆっくり」を求める誤りで終わったときは、最初の試みも、1 秒待ってから始める（試みを重ねる前と同じ）。映像では、いま、流れている接続がそういう誤りで終わることはない（ホストがいっぱいのときの `busy` は、申し込みの返事でしか来ない。ペアリング一覧が読めない、は、つなぐときにしか起きない）。起きるようになったときのために、待ちは残してある。
- **鍵と番号。** 試みは、それぞれ、自分の鍵交換用の鍵（`LocalKeys`。入力も、映像の C の口も、試みのたびに作る）、自分のハンドシェイクの状態（Noise の、その回かぎりの鍵）、自分の通信路の状態（封の鍵と、その連番）を持つ。試みのあいだで共有するのは、署名にしか使わない身元の鍵と、読むだけのペアリング一覧だけである。捨てた試みの状態は、何にも使わない。
- **数え方。** 切れた回数は、切れたと分かったときに、1 つ増える。試みの数も、返事のなかった申し込みの数も、足さない。
- **どのアドレスへ試みるか（レビューを受けて決めた）。** 映像は、起動のときのアドレス 1 つである。入力は、`--address` を付けなければ、相手を覚えているアドレス（8 つまで）を使う。はじめてつなぐときは、これまでどおり、全部を同時に試す。**つなぎ直しの試みは、会話が最後に通じたアドレスへ、1 本だけ。** 切れてから 8 回の試みは、そこへだけ行く。9 回めからは、4 回に 1 回、その試みが、もう 1 本、ほかのアドレスの 1 つへも行く（ほかのアドレスを、順に回す）。最後に通じたアドレスへは、毎回行くので、0.5 秒おきの線は、変わらない。アドレスが変わった端末は、9 回めから（ホストが黙っているなら、切れてから 2.6 秒あとから。はじめの 2 つを足す前は、2.8 秒あとから）、2 秒に 1 つずつ、ほかのアドレスで探される。
  - 接続の数で言うと：試みの 1 回は、多くて 2 本。続く 8 回の試みで、多くて 10 本。**同時に開いている接続は、1 つの会話で、多くて 10 本**（アドレスが 1 つなら 8 本）。ホストに届く接続は、はじめの 5 秒を過ぎたら、1 秒に 2.5 本まで（アドレスが 1 つなら 2 本）。
  - それまで（この節をはじめに作ったとき）は、試みの 1 回が、覚えている全部のアドレスへ同時につないでいた。「8 つまで」「1 秒に 2 回」は、アドレスの数だけ、ずれていた。
- **ホストが、ハンドシェイクのあとで閉じた接続は、「開いた」とは言わない。** ホストは、1 台の端末の、申し込みを待つ接続が上限に達していると、次の接続を、ハンドシェイクを終えた所で閉じる（下の「ホストの側」）。つなぎに行く側は、ハンドシェイクを終えたときと、その接続を採ろうとするときに、もう閉じられていないかを見る。閉じられていれば、失敗した試みとして数え、申し込みを送らない。見るのは、待たずに分かる範囲である（閉じたことが、まだ届いていなければ、分からない。そのときは、申し込みがすぐ失敗して、試みが続く）。
- **試みが読むファイル。** 試みは、それぞれ、身元の鍵とペアリング一覧を、自分で読む（8 つまで同時に）。ペアリング一覧は、書く側が、別のファイルに書いてから置き換えるので、読む側が、書きかけを読むことはない。身元の鍵は、作るときにだけ書かれる。つなぎ直しの試みは、身元の鍵がなくても、作らない（会話があったのだから、鍵はあった。なければ、やめる）。エージェントが、つないできた端末のアドレスを覚えるファイルは、同じ端末の接続がいくつか同時に来ると、同じ一時ファイルに書いていた。書くたびに別の名前にした。
- 相手の指定（はじめにつながった端末だけ）は、いまと同じである。

**言えること。** ホストが黙っているあいだ、0.5 秒より長く、試みを始めない時間はない。道が開いたあと、最初に始まる試みは、長くても 0.5 秒あとで、その試みは、往復 4 回でハンドシェイクを終え、往復 1 回で返事を受ける。

| 道 | 道が開いてから、つながるまで（長くても） |
|---|---|
| 有線の LAN（往復 1 ms） | 0.5 秒あまり |
| 往復が 100 ms 足らずの道 | 1 秒以内（0.5 秒＋往復 5 回） |
| 往復 400 ms の道 | 1 秒は、言えない（往復 5 回だけで 2.0 秒）。つながりは、する：0.5 秒＋2.0 秒以内 |
| 往復が 450 ms ほどを超える道 | つながらない（ハンドシェイクが、試みの 2 秒に入らない） |

この表は、にせの時計の試験で確かめた値である（往復 1 ms で、道が開いてから長くて 0.495 秒。往復 400 ms で、切れてから 2.0 秒）。**実機の値では、ない。**

1 秒を超えうるのは、次の 2 つのときである。

- **申し込みの返事を待っているあいだ（長くて 1 秒）に、道がもう一度閉じて、開いたとき。** 待ち終わるまで、新しい試みを始めないためである。にせの時計の試験では、このとき、試みと試みのあいだが 1.004 秒あいた。
- **OS が、いないホストへの送信を、しばらくやめているとき。** 確かめていない。下の「測ること」。

試みが締め切りを過ぎても終わらないことは、名前を引くことに期限を付けたので、ネットワークのためには起きない。それでも終わらない試みがたまったときの歯止めが、上限の 8 である（8 に達したら、新しい試みを始めない）。

#### ホストの側

- **申し込みを待つ接続**（ハンドシェイクを終えて、最初のメッセージがまだ来ていない接続）は、**端末ごとに、映像と音は 4 本まで、エージェントは 6 本まで**。それを超える接続は、ハンドシェイクを終えた所で、すぐ閉じる。閉じるのは、新しいほうである：往復の長い道では、クライアントが採るのは、先に終えた古いほうなので、古いほうを閉じると、採られる直前の接続を切ってしまう。4 は、クライアントが 0.5 秒より短い間隔で始める試みの数（はじめの 2 つを入れて、4 つまで）と、同じにしてある。
  - **はじめの 2 つを足しても、行儀のよいクライアントは、この数を超えない（2026-11-17 の夜に確かめた）。** ホストで待つのは、ハンドシェイクを終えてから、申し込みか、閉じたことが届くまでの、往復 1 回ぶんである。同時に 5 本が待つには、5 つの試みが、往復 1 回（届く範囲で、長くて 0.5 秒）のうちに始まっていなければならない。0.5 秒より短い間隔で始まる試みは、はじめの 2 つも、走っている試みが 4 つより少ないときにしか始まらないので、4 つまで。5 つめは、4 つめの拍から 0.5 秒あとである（0、10 ms、50 ms、0.1 秒の次は、0.6 秒）。確かめ方：にせの時計の試験で、往復 1 ms から 500 ms までの 15 通りの道のそれぞれに、切れを続けて 6 回起こし、ハンドシェイクを終えた試みを、ホストが数えるとおりに、ホストの枠（`Waiting`。端末ごとに 4）に入れた。どの道でも、断られた接続はなく、同時に待ったのは、往復 10 ms までで 1 本、13〜50 ms で 2 本、100 ms で 3 本、125〜500 ms で 4 本。往復 400 ms の道の試験（下の 3）も、足す前と同じ 4 本のままである。エージェントの 6 にも、入る。**2 台では、確かめていない。**
  - **エージェントの 6 は、4 に 2 を足したものである（レビューを受けて決めた）。** 映像と音の待ち受けには、その会話の接続しか来ない。エージェントには、その端末の会話が、どれも来る（入力、`istesso hosts` の問い合わせ、はじめての接続）。4 のままだと、往復の長い道で入力がつなぎ直しているあいだ、同じ端末の `istesso hosts` が、ハンドシェイクのあとで閉じられる。2 つは、いつも残す。
- **全体では**、映像は 8、音は 16（どちらも、いまある「まだ誰とも分かっていない相手」の枠。この枠は、いまも、申し込みが来るまで持たれている）。エージェント（入力）は、同時接続 64 のうち、申し込みを待つ接続を 16 までにする（新しく置く）。
- **期限は 3 秒。** 映像と音は、前から、つないできてから申し込みまでを、合わせて 3 秒で締め切っている。エージェントは、ハンドシェイクの期限（5 秒）はそのままで、そのあとの最初のメッセージを 3 秒で締め切る（それまでは 5 秒）。**この 3 秒は、ハンドシェイクが終わってからの、合わせての時間である**：1 バイトずつ送ってくる相手も、この版の知らない頼みごとを送り続ける相手も（そのたびに `unsupported` と答えるが、時間は延びない）、3 秒で切る。はじめに作ったときは、読み込みの 1 回ごとの 3 秒で、そういう相手は、枠を持ち続けられた（レビューで見つかった）。**`unsupported` の答えを書くことも、この 3 秒のうちである**：答えを読まずに頼みごとを送り続けて、接続がそれ以上受け取らなくなった相手も、3 秒で切る（それまでは、答えを書く待ちだけが、ふつうの待ち時間（5 秒）で、枠を 3 秒＋5 秒まで持てた。これも、レビューで見つかった）。最初のメッセージが来たあとは、これまでどおりの待ち時間（5 秒。入力は 2 秒）に戻る。ふつうの短い会話（`ping`、`manifest`）は、つないですぐ頼むので、変わらない。
- 捨てられた試みの接続は、クライアントが閉じるので、ふつうは、すぐに終わる。3 秒は、閉じたことが届かないときのためである。
- ホストにかかるもの：ホストに届く接続は、1 台の 1 つの会話あたり、**切れてからの最初の 1 秒は 12 本まで**（0、10 ms、50 ms と、0.1 秒から 0.9 秒までの 9 本。はじめの 2 つを足す前は、10 本）、そのあと 5 秒までは 1 秒に 10 本まで、そのあとは 1 秒に 2 本まで（入力で、相手のアドレスをいくつか覚えているときは、2.5 本まで）。12 本は、試みがすぐ失敗するときの数である。ホストが黙っているときは、最初の 1 秒に 5 本（0、10 ms、50 ms、0.1 秒、0.6 秒）で、足す前（0、0.1、0.2、0.3、0.8 秒）と同じ数である。同時に走る試みは、足す前と同じく、0.5 秒より短い間隔のうちは 4 つまで、全体で 8 つまで。ホストが答えられるなら、最初の 1 本でつながるので、続くのは、ホストが断っているあいだだけである。

#### ペアリングの鍵を持たない相手に、できること、できないこと

| その相手に | 中身 |
|---|---|
| できない | ペアリング済みの端末として、ハンドシェイクを終えること。自分の身元でつなげば、ペアリング一覧にないので、断られて、切られる。ペアリング済みの端末の身元を名乗れば、その鍵の署名がないので、証明が通らない。だから、「申し込みを待つ接続」の枠（端末ごとの 4）には、入れない |
| できない | 申し込みを送ること。申し込みは、暗号化された通信路の中を通る。流れている映像、音、入力を止めること、キーフレームを出させること、聞き手の番号を進めること、押されたキーを離させることは、できない |
| できない | 録っておいたハンドシェイクや申し込みを、送り直して通すこと。ホストの、その回かぎりの鍵が毎回違うので、3 つめのメッセージが合わない。申し込みは、別の回の鍵で封がしてある |
| できる（いまと同じ） | 接続を開いて、ハンドシェイクを途中で止めること。「まだ誰とも分かっていない相手」の枠を、期限（3 秒、エージェントは 5 秒）まで使う。枠を埋め続けているあいだ、ペアリング済みの端末がつなぐのを、妨げられる。下の「既知の不足」のとおりで、この設計で、悪くも、よくもならない。すでに流れている会話は、止まらない |
| できる（道の途中にいる相手） | パケットを捨てて、試みを失敗させること、どの試みが先に終わるかを選ぶこと。試みは、どれも同じ相手との、同じ確かめを通った接続なので、選べても、得るものはない。接続を切り続けて、つなぎ直しを繰り返させることは、できる（いまと同じ） |

ペアリング済みの端末（鍵を持つ相手）が、おかしな動きをするとき：申し込みを待つ接続を、4 本まで（エージェントでは 6 本まで）、それぞれ 3 秒まで持てる。それより多くも、長くも、持てない（3 秒は、どの待ち受けでも、合わせての時間である）。エージェントの全体の枠（16）は、そういう端末が 3 台あれば、埋まる。埋まっているあいだ（長くて 3 秒ずつ）、ほかの端末の新しい接続は、ハンドシェイクのあとで閉じられる。

#### 3 つの会話で、どう分けるか

**仕組みは 1 つで、`istesso-link` に置く。** 暗号には、触れない。依存も、足さない。

| 置くもの | 中身 |
|---|---|
| つなぎに行く側（`istesso_link::again`） | `Tries`：いつ試みを始めるか、どれを採るか、いつやめるかを決める、状態の機械。**時計も、スレッドも、ソケットも持たない**（時刻は、呼ぶ側が渡す。試験で、にせの時計を使うため）。`Racer`：その外側の、試みをスレッドで走らせる薄い部分。試みの中身（どこへ、どの鍵でつなぐか）は、会話ごとに渡す。数は `Pace`。`Again`（すぐ、ゆっくり、やめる）は、`istesso-agent` と `istesso-media` に 1 つずつあったものを、ここに寄せた |
| ホストの側（`istesso_link::waiting`） | `Waiting`：申し込みを待つ接続を数える部分（端末ごと、全体）。枠を取り、申し込みが来たときか、閉じたときに返す。時計は持たない |

会話ごとに変えた所：

| 会話 | つなぎに行く側 | ホストの側 |
|---|---|---|
| 入力（`istesso-agent`）。**入れた** | `relay` の `InputLine`：つなぐこと（試み）と、`input_open`（申し込み）は、前から分かれていた。試みを、上の仕組みで重ねる。数（0.25 秒、10 秒たったら 1 秒）を、上の表の数に替えた。試みの締め切りは、合わせて 2 秒（それまでは、待ちの 1 回ごとに 1 秒）。試みは `survey` の `Reaching::open` で、どのアドレスへ行くかも、ここが決める（上の「どのアドレスへ試みるか」）。そのために、`istesso-link` の `Client` に、全体の締め切りでつなぐ口（`connect_by`、`Channel::initiate_by`）を足した。待ち受ける側の `respond_within` と同じ作りで、読み書きの待ち方だけの話である。ハンドシェイクの中身は、変わらない | `serve`：ハンドシェイクのあとで枠を取り、最初のメッセージで返す。最初のメッセージを 3 秒で締め切る。ほかは、変えていない |
| 映像（`istesso-media`）。**入れた** | `Viewer::connect` を、つなぐ所（`Viewer::open`。試み）と、`watch` を送って `stream` を受ける所（`Opened::watch`。申し込み）に分けた。`Viewer::connect` は、その 2 つを続けて呼ぶ。`rejoin` の `Lasting` が、試みを重ねる。数は、入力と同じ。C の口（`istesso_media_watch_*`）は、変えていない | `host`：ハンドシェイクのあとで、端末ごとの枠を取る。ほかは、変えていない（決まり 1〜3 は、前からの動きである） |
| 音（`istesso-audio`。`m2-audio` ブランチ）。**これから** | `session` の `subscribe` を、同じように分ける（つなぐ所は、もう `open` として分かれている）。出口のやり直しの輪を、上の仕組みに替える | `serve`：端末ごとの枠を取る。ほかは、変えない。聞き手を替えたときに連番を飛ばさない直し（`m2-audio` の 9d3fe6a）は、そのまま要る |

- 音は main にないので、このブランチ（`reconnect-within-a-second`）には、`istesso-link` の仕組みと、入力と映像までが入っている。音には、`m2-audio` から切ったブランチに、このブランチを取り込んで入れる。**いつ始めるかは、調整役が言う**（夜の計測と、持ち主が聞いているあいだは、音のプログラムを作り直さない）。
- はじめてつなぐとき（3 秒、1 回ずつ）は、試みを重ねる仕組みには、通していない。この節は、切れたあとの話である。持ち主の決定 11 のうち、起動して最初の試みが失敗したあとのぶんは、映像にだけ、1 回ずつのままで入れた。入力は、合流のときの宿題である（上の「はじめの 2 つ」の「起動のとき」）。
- セッション（M3）が入っても、申し込みは `input_open` と `watch` のままである（セッションの名前が、項目として付くだけ）。

#### 試験

下の 16 個を、書いた（音のぶんを除く）。この Mac で、`cargo test --workspace` として通している。どれも、ループバックと、にせの時計の上の話で、**2 台のあいだの道で確かめたものは、まだない。**

にせの時計で行うもの（`istesso-link` の `again` と `waiting`。状態の機械に、にせの時計と、にせの道を渡す。にせの道は、試みがいつ、どう終わるかを決める：黙っている、すぐ断る、往復に決まった時間がかかる。道が閉じているあいだに始まった試みは、道が開いても終わらない、と厳しいほうに置く）：

1. **ホストが 1 時間黙っていて、そのあと答える → 1 秒以内につながる。** 道が開く時刻を、10 ms ずつずらして、1 秒ぶん試す。どの時刻でも、道が開いてから 0.5 秒＋往復 5 回（往復 1 ms）以内。
2. 同じ 1 時間のあいだ、試みを始める間隔が、0.5 秒を超えない。同時に走る数が、8 を超えない。始めた数を、記録に出す（宿題の材料）。
3. **往復 400 ms の道 → つながる。** 1.6 秒でハンドシェイクが終わった試みを採り、2.0 秒でつながる。締め切りの前に捨てられた試みがない。そのあいだ、ホストの側で申し込みを待つ接続が、4 本を超えない。試みが始まる時刻は、0、10 ms、50 ms、0.1 秒、0.6 秒、1.1 秒（はじめの 2 つを足す前は、0、0.1、0.2、0.3、0.8、1.3 秒。試験の数を、ここだけ替えた）。
4. 試みがすぐ失敗するあいだ（自分の PC が断る）、はじめの 2 つ（10 ms、50 ms）のあと、切れてから 5 秒までは 0.1 秒おき、そのあとは 0.5 秒おき。道が開いたら、次の試みでつながる。
5. **数は 1。** 18 秒黙っていたホストに、何十回も試みて、つながる。そのあいだに、返事のない申し込みが 1 回ある。切れた回数は、1。
6. 2 つの試みが、同じ時刻にハンドシェイクを終える → 採るのは 1 つ。もう 1 つは、捨てる。
7. やり直しても変わらない答えが 1 つ来たら、やめる。走っている試みは、捨てる。「ゆっくり」の答え（`busy`、`internal`）のあとは、次の試みまで 1 秒。
8. つないだばかり（0.25 秒以内）の接続が切れたときは、すぐには始めない（いまの決まりが残っている）。
9. 捨てた試みは、スレッドが終わるまで、走っている数に入る。つなぎ直しを続けて 10 回起こしても、8 を超えない。
10. ホストの枠（時計を持たない部分）：同じ端末の 5 本めは、断る。ほかの端末は、入れる。全体の上限。枠は、申し込みが来たとき、閉じたときに、返る。

ソケットで行うもの（この Mac の中だけ。期限は、試験のために短くする。入力は `istesso-agent` の `relay` と `serve`、映像は `istesso-media` の `session_tests`、12 は `istesso-link` の `channel`）：

11. **2 つの試みが、続けてハンドシェイクを終える。** ホストの側の試験では、ハンドシェイクだけを終えた接続を 2 本、手で作る。つなぎに行く側の試験では、試みを、ハンドシェイクのあと 0.4 秒遅らせて、3〜4 つが走っているようにする。会話ごとに：
    - ホストは、申し込みを 1 つだけ受け取り、その接続を採る。もう 1 つの接続は、何も言われずに閉じられ、ホストは、記録に何も書かず、何も進めない。
    - 古い接続は、ハンドシェイクが 2 つ終わった時点では、まだ流れている。切られるのは、申し込みが届いたときである。
    - 映像：求められたキーフレームは 1 枚。採った接続のフレームの連番に、飛びがない。入力：押されたままのキーが離されるのは、1 回。音（`m2-audio` の側で。**まだ書いていない**）：聞き手の番号は 1 だけ進み、採った接続の連番に、飛びがない。
12. **鍵と番号を、共有していない。** 2 つの試みの通信路で、同じ中身を最初のメッセージとして送ると、線の上のバイトが違う。片方の通信路の封を、もう片方で開けようとすると、失敗する。両方の通信路で、交互に送っても、どちらも順に届く。
13. **申し込みの来ない接続は、期限で閉じられる。** ハンドシェイクを終えて黙っている接続が、期限（試験では 0.3 秒）で閉じられ、枠が返る。そのあいだ、流れている会話は、止まらない。
14. ペアリングしていない相手は、いくつつないでも、申し込みを待つ枠に入らない。流れている会話は、止まらない。
15. 黙って何も通さなくなる中継（前からある試験の道具に、「ホストがいない」を足した：来た接続を受けるだけで、何も返さない）で、切ってから 2.5 秒黙らせ（試みの締め切りを 1 秒、間隔を 0.25 秒にして、試みが重なるようにする）、通したら、次の試みでつながる。切れた回数は、1。
16. 古い相手との組み合わせ：試みを重ねないクライアント（前の版の動き）が、新しいホストにつながる（入力、映像）。枠のないホスト（前の版の動き）に、新しいクライアントがつながる（入力。前の版のホストの代役を立てた。映像のホストは、端末ごとの枠のほかは変えていないので、代役は立てていない）。

設計のあとで足した試験：名前を引くことが、試みの締め切りで終わり、そのあいだ、引き直しが始まらない。つなぎに行く側のハンドシェイクが、1 バイトずつ答える相手にも、1 つの締め切りで終わる。1 台の端末が、申し込みを待つ接続を、映像では 4 本、エージェントでは 6 本までしか持てず、そのあいだも、ほかの端末は入れる。届く範囲（往復 450 ms と 500 ms はつながり、510 ms はつながらない）。試みのスレッドが落ちても、場所が空く。

#### 測ること（まだ測っていない）

- **持ち主のいる所で、2 台で測る：OS が、いなかったホストへの送信を、どれだけ速く始め直すか。** 同じ LAN の上でホストがいなくなると、Mac は、ホストの機械のアドレスを引けなくなる。引けないあいだ、接続がすぐ失敗するのか、ホストが戻ったあと、どれだけたってから引き直すのかは、OS の中の話で、コードからは分からない。引き直しが遅ければ、試みを 0.5 秒おきに始めていても、1 秒を超える。測るのは：ケーブルを抜いて 1 分、ケーブルを抜いて 1 時間、ホストを眠らせて起こす。それぞれ、道が開いてから、つながるまで。**これを測るまで、「いつも」とは言えない。** 持ち主の一覧に、載っている。
- **ケーブルを抜かずに測る案（2026-11-17。案だけで、何も実行していない）：** ホストの上で、Istesso のポートだけを、決めた時間、捨てる。[reconnect-away-measurement.md](../reconnect-away-measurement.md)。この形で測れるのは、こちらの試みの間隔と締め切りの働きで、上の OS の問いは、測れない（そのあいだも、ホストは LAN の上にいて、Mac の問い合わせに答える）。OS の問いは、ケーブルを抜ける日に残す。
- 同じ機会に：ホストのプログラムだけを止めて、始め直す。
- **はじめの 2 つ（10 ms、50 ms）は、2 台では、何も測っていない。** にせの時計の試験で、時刻と上限を確かめただけである。測るのは：Mac のアプリを作り直した（更新した）すぐあとに切れを起こして、何回めの試みでつながるか、切れてから何 ms か。Mac が最初の接続を落とす長さ（2 ms ほど、悪いときで 13 ms ほど）も、持ち主が挙げた値で、この文書のために測り直してはいない。50 ms で足りるかどうかは、その計測で決まる。**起動のとき（映像）の段も、測っていない。** Mac が落とした接続が、すぐ失敗として返るのか、黙って待たされるのかも、確かめていない（待たされるなら、1 回ずつの起動では、段は効かない）。**プログラムが、10 ms あとに、時間どおりに起こされるかどうかも、測っていない**：この Mac で、優先度の低いシェルから走らせた映像の試験（ループバック）では、50 ms 待つ呼び出しの 1 回が 120 ms ほどかかり、試みは、0.9 秒のあいだに 9〜10 しか始まらなかった（時間どおりなら 12）。起こされるのが遅れて、はじめの 2 つが、1 つにまとまるか、0.1 秒の拍に追い越された、と見ている（その分は、あとから始めない決まりである）。ふつうの優先度で動くアプリでの値は、測っていない。
- **公開の前に、Wi-Fi と VPN で測る：届く範囲。** 試みの締め切り（2 秒）で届くのは、往復 450 ms ほどまで、という値は、往復の回数から数えたもので、測った値ではない。[milestones.md](../milestones.md) の M9。

#### コードからは分からなかったこと

- 上の「測ること」の 1 つめ。
- 音の締め切り（2 秒）を、どこで渡しているか。`session` は、呼ぶ側から受け取っている。呼ぶ側（出口のプログラム）は、読んでいない。音に入れるときに、読む。
- 脅威をまとめた文書は、main にも、ほかのブランチにも、見つからなかった。宿題の 1 行は、この文書の「既知の不足」に書いた。

#### 既知の不足（残っているもの）

- **遅れて届いた申し込みが、あとから採った接続を切ることがある。** 申し込みを送った接続で、1 秒、返事がなく、その接続を捨てて、次の接続で申し込んだあとに、前の申し込みが、遅れてホストに届いたとき。ホストは、前の接続を採り、あとの接続を切る。前の接続は、もう閉じられているので、すぐ終わる。**値段は、切れが 1 回増えること**である（クライアントは、もう 1 度つなぎ直す。切れた回数は、2 になる。映像なら、キーフレームがもう 1 枚出る）。直す前の、1 回ずつの試みでも、同じことは起きた。**直すには、申し込みに、何回めの試みかの番号を付ける。** メッセージを変えることになるので、いまは、しない（持ち主の答えの 9）。
- 上の「言えること」の、1 秒を超えうる 2 つ。
- **閉じたことが届かなかった接続が、枠をふさぐことがある。** 1 台の端末の、申し込みを待つ接続が上限（映像は 4 本、エージェントは 6 本）まであるときに道が閉じ、クライアントが閉じたことがホストに届かないまま、3 秒より前に道が開き直したとき。その端末の新しい接続は、古いものが期限で閉じられるまで（長くて 3 秒）、ハンドシェイクのあとで閉じられる（つなぎに行く側は、それを、失敗した試みとして数える）。それだけの数が同時に待つのは、往復の長い道でだけで（有線の LAN では、待つのは 1 本。はじめの 2 つが重なっても、3 本まで）、その道では、もともと 1 秒は言えない。新しいほうではなく、古いほうを閉じれば、これは起きないが、往復の長い道で、採られる直前の接続を切ってしまう（上の「ホストの側」）。
- 1 台のクライアントが、往復の長い道でつなぎ直すとき、ホストの「まだ誰とも分かっていない相手」の枠を、2 秒ほど、6 つまで使う（映像は、8 のうち）。そのあいだ、ほかの端末の新しい接続が、断られることがある。断られた端末は、次の試みでつなぐ。
- 試験は、ソケットを使うものが、時間に寄りかかっている（中継を黙らせてから 2.5 秒、など）。この Mac が、ほかの仕事でひどく忙しいと、数（始まった試みの数）が、書いた幅から外れうる。幅は、広めに取ってある。

#### 宿題（公開の前に決める。いまは作らない）

**家のネットワークの外にいるとき、ホストが長くいないときにも、0.25〜0.5 秒おきに試み続けるかどうか。**

- わけ 1：電池。1 つの会話が、1 秒に 2 回、1 時間に 7,200 回、接続を始める。映像、音、入力で、その 3 倍。
- わけ 2：出先のネットワークで、家のホストと同じアドレスを持つ、別の機械に、ハンドシェイクの最初のメッセージを送り続けることになる。身元は明かさない（相手を確かめてから、送る決まり）。それでも、「この端末は Istesso を使っていて、このアドレスを探している」ことは、その機械と、道の途中から見える。
- 向き：経路が変わった、という OS の知らせを受けたら、すぐに試みを 1 つ始める。そうすれば、ふだんの間隔を長くしても、道が開いてから 1 秒の線は、守れる。

**合流のときの宿題（2026-11-17 の夜）：入力の起動に、はじめの 2 つの段を入れる。** 入力の起動の道は、自前のクライアントのブランチにあり、このブランチでは変えていない。することは、上の「はじめの 2 つ」の「起動のとき」。起動のときにも試みを重ねるかどうか（黙って待たされる試みにも、段を効かせるかどうか）も、そのときに決める。

### 発見とアドレスの記憶

- 各エージェントが mDNS（DNS-SD）で `_istesso._tcp` を広告し、他の広告を聞く。実装は `mdns-sd`。
- 広告は**アドレスの手がかり**としてだけ使う。広告は誰でも出せるので、何の証明にもならない。接続先が本物かどうかは、通信路のハンドシェイクだけが決める。
- 手がかりとして受け入れるのは、ペアリング済みの端末の指紋を名乗り、かつ自分が直接つながっているネットワーク上のアドレスだけ。
- 手がかりは他に、ペアリングのときに使ったアドレス、相手から接続が来たときの送信元、相手が役割表で申告したアドレス、`istesso peers address` での手動指定がある。最後に通じたアドレスを先頭に置き、複数あれば同時に試す。
- 応答しない端末は、最後に応答したときの役割表とアプリ一覧をキャッシュから表示する。エージェントは定期的に相手へ問い合わせて、この記憶を更新する。キャッシュは信頼の根拠にしない。

## 既知の不足（公開前に対応する）

- `snow` は第三者の監査を受けていない。ペアリング（ADR 0006）と合わせて外部レビューを受ける。
- 受け側の身元（公開鍵）は、接続してきた誰にでも見える。Noise XX の性質である。
- mDNS の広告に含まれる指紋は、同じネットワークの誰にでも見える固定の識別子になる。信頼できないネットワークでは `istesso agent --no-discovery` を使う。識別子を回す方式は未検討。
- IPv4 のみ。
- 同じネットワークからの大量接続への対策は、同時接続数の上限と、ハンドシェイク全体の期限だけ。期限は、読み書きのたびに数え直さない（2026-11-16 に直した。それまでは、待ち時間が読み込み 1 回ごとだったので、1 バイトずつ送る相手が、接続の枠を何十分も占められた）。接続を開き続ける相手は、そのあいだ、ほかの端末がつなぐのを妨げられる。これは受け入れている。
- 相手の待ち受けポートは、発見できたとき以外は既定値を仮定している。
- エージェントはまだ常駐サービスではない（手で `istesso agent` を起動する）。launchd / systemd への登録は M9。
- ペアリングは別のポート（47800）で、エージェントとは別に動く。エージェントへの統合と、ペアリング相手の自動発見・QR はこれから。
- 出先（VPN 越し）では発見が届かない。`istesso peers address` で指定する。
- **つなぎ直しの試みは、ホストがいないあいだ、止まらない**（2026-11-17。公開の前に決める宿題）。家のネットワークの外では、家のホストと同じアドレスを持つ別の機械に、ハンドシェイクの最初のメッセージを送り続ける。身元は明かさないが、Istesso を使っていることと、探しているアドレスは、その機械と、道の途中から見える。電池も使う。上の「つなぎ直しの試みを、重ねる」の「宿題」。
