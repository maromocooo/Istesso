## 背景

関門の判定は、計測用のスクリプト（`scripts/m1-step3-host.py`）で通った。確定の判定は、自前のホストで測り直す。自前のホストは、スクリプトがしていることを、エージェントがランナーとして起動する **1 つのプログラム**で行い、次を足す：エンコーダーを断られたときの動き、止めるときにエンコーダーを 0.3 秒以内に手放すこと、試して測る切り替え（変わらない絵を送り続ける、「起きる時間」）。

関門の数値の回で、ホストの受け持ちは、平均で次のとおりだった（[記録](../measurements/2026-11-17-m1-gate.md)）。

| 区間 | 値 | このプログラムの中身 |
|---|---|---|
| 入力がホストに届いてから、アプリに届くまで | 0.31 ms | エージェント → ソケット → スクリプトのメインループ → コンポジターのスレッド → アプリ |
| コンポジター（確定からフレームが出るまで） | 0.98 ms（負荷つきの回は 0.63） | コンポジターの修正版のプラグインの中 |
| 色の変換と圧縮 | 4.03 ms（うち、圧縮 3.92） | GStreamer の要素と、NVENC の中 |
| 暗号化して、通信路に書く | 0.17 ms（負荷つきの回は 0.07） | スクリプトのコールバックと、`istesso-media` |

**作り直して縮められるのは、合わせて 0.1〜0.2 ms ほどの見込みである**（測っていない）。圧縮の 3.9 ms は、作り直しでは動かない（ADR 0016）。この束でのねらいは、速くすることより、**製品に残せる形にして、遅くしないこと**と、切り替えを 1 つずつ測れるようにすることである。

## 比べる案

| 観点 | A：Python のまま、入力だけ中へ | B：Rust のプログラムが、GStreamer を Rust の束縛で動かす | C：Rust のプログラムが、コンポジターの本体（`wayland-display-core`）を直接呼ぶ |
|---|---|---|---|
| フレームの通り道 | 関門で測ったものと同じ。フレームごとに、Python のコールバックが 4 つ残る | **要素も設定も、関門で測ったものと同じ。** コールバックが Rust になる。ライブラリーは、C の口を通さずに呼ぶ | コンポジターの要素（描く拍、フレームの受け渡し）を、作り直すことになる |
| 遅延 | 変わらない | 同じか、0.1 ms ほど短い見込み。入力が、メインループのほかの仕事（4 ms ごとの見回り、1 秒ごとの記録の書き出し）のうしろに並ばなくなる | B より、入力 1 回あたり数 µs 短い見込み |
| 危うさ | いちばん小さい（いま）。あとで大きい：変わらない絵の送り直しは、コンポジターのスレッドと順番をそろえる必要があり、プローブでは書きにくい。インタープリターの止まり（メモリーの掃除、ロック）が、通り道に残る | 通り道に、新しいコードが入る。**スクリプトと並ぶことを、測って確かめるまで、置き換えない** | いちばん大きい。4 つの修正を当てた版を、依存として抱える。関門で測った形と、比べられなくなる |
| 依存 | Python、GObject の束縛（入っている） | `gstreamer` のクレート（MIT OR Apache-2.0 の見込み。`cargo deny` で確かめる）。GStreamer そのものは、入っているライブラリーに動的にリンクする（[components.md](../components.md)）。ビルドに、GStreamer の開発用のパッケージが要る | B のものに加えて、Smithay と、修正を当てたコンポジターの git の依存（`deny.toml` は、知らない git を断る） |
| ランナーの約束、配布（M9） | Python で書ける。配布物に、Python と束縛が要る | 実行ファイル 1 つ | 同じ |

ほかの形：

- **エージェントの中に入れる**（ADR 0010 の B）。入力は、関数の呼び出しで渡せる。ADR 0010 が退けた形で、わけは変わっていない（エージェントが GStreamer を抱える。落ちたときに、全部のセッションを巻き込む）。
- **パイプラインを 2 つに分けて、あいだを待ち行列でつなぐ**（`appsink` → `appsrc`）。送り直しや止める処理は書きやすいが、フレームの通り道に、スレッドの受け渡しが 1 回増える。採らない。

## 入力の受け渡し：減らせるのか

いまの受け渡しは、エージェント →（ソケット）→ スクリプトのメインループ →（要素のイベント）→ コンポジターのスレッド → アプリ。ランナーの約束の決まり 4 は、「入力は、`input_socket` からだけ受け取る」である。この決まりの下では、**エージェントとランナーのあいだのソケットは、なくせない。**

| 形 | ホストの中で、起こされるスレッド | 要るもの |
|---|---|---|
| I-0：ソケットのまま。受けるのは、それだけを待つ Rust のスレッド | エージェント、入力のスレッド、コンポジター（いまと同じ数。1 回ずつが軽い） | なし。約束のとおり |
| I-1：ランナーが、入力の接続を自分で受ける（エージェントの入力の関数を、ランナーのプロセスで動かす。ポートは `answer` で知らせる） | 入力のスレッド、コンポジター（**1 つ減る**） | 決まり 4 と ADR 0007 の書き換え。クライアントが、入力をランナーのポートへつなぐ。「入力を送れるのは、映している端末だけ」（ADR 0010 の 13）を確かめる場所が、エージェントからランナーへ移る |
| I-2：コンポジターのスレッドが、ソケットを自分で読む | エージェント、コンポジター（**1 つ減る**） | コンポジターへの 5 つ目の修正（入力の通り道）。Istesso のイベントの形を、プラグインが知ることになる |

1 つ減らして縮むのは、静かなときで 0.05〜0.15 ms の見込みである（測っていない）。

## 決定（提案）

**B を採る。入力は、I-0 で作る。** 入力の出どころは、1 つの口のうしろに置く。I-1 は、この束では、何も作らない。I-1 にするかどうかは、I-0 で「エージェントが手にしてから、コンポジターに渡すまで」を測ってから（下の計測の 4）、持ち主が決める。**この束では、ホストの側の入力の受け渡しは、減らない**（数は同じで、1 回が軽くなる）。

わけ：

1. 通り道の要素と設定が、関門で測ったものと同じなので、「並んだ」と言うための比べが、作り直しの違いに埋もれない。
2. エンコーダーを断られたとき、止めるとき、送り直すとき、のどれも、「コンポジターと、エンコーダーのあいだ」に自分のコードが要る。それを、Rust で 1 か所に置ける（下の「関」）。
3. I-1 は、アプリマネージャーとつなぐ作業（束の 5）の形を変える。だれが入力を送ってよいかは、いまある関数（エージェントの入力の確かめ）のうしろに置いたままにする。

### 作り

- 新しいクレート `crates/istesso-host-linux`。GStreamer を使う部分は、**既定では切ってある feature** に入れる。ワークスペースのビルドと試験は、これまでどおり、GStreamer のない PC でも通る（ADR 0010 が境界を決めたわけの 1 つ）。feature を入れたビルドと試験は、ホストで行う。
- 状態の動き（ランナーの行、止める・戻す、断られたとき、送り直しの時刻、入力の変換、カーソルの突き合わせ）は、GStreamer に触らない部分に置き、どの PC でも試験する。
- 起動の形は 2 つ。中身は 1 つ。
  - **ランナーの形**（引数なし）：ADR 0010 の行を、標準入力と標準出力で話す。切り替えは、環境変数で渡す。
  - **計測の形**（`measure`）：スクリプトと同じ引数、同じ語（`pause`、`resume`、`detach`、`admit`、`close`）、同じ答え、同じフレームの記録。計測の道具と `scripts/m1-step3-breakdown.py` が、そのまま使える。暗号化していない UDP の経路（`--to`）は、移さない。その比べには、スクリプトを使い続ける。
- パイプラインは、スクリプトと同じ文字列から作る（`waylanddisplaysrc` → CUDA のフレーム → `cudaconvert` → `nvcudah265enc` → `h265parse` → 取り出し口）。同じ文字列になることを、試験で確かめる。
- **関**：コンポジターの要素と、色の変換のあいだに、このプログラムの小さな通り抜けの要素を 1 つ置く。フレームは、コンポジターのスレッドのまま、関数の呼び出しで通る（スレッドの受け渡しは、増えない）。関は、次を受け持つ。
  - 最後のフレームを持っておく（送り直しと、戻すときの最初の 1 枚のため）。
  - 止めているあいだ、フレームを先へ通さない。コンポジターへの見え方は、いまと同じにする（確定のたびに描く形では、描かせない）。
  - **エンコーダーの側の失敗を、コンポジターへ返さない。** コンポジターが失敗を知ると、パイプラインごと終わって、アプリが表示先を失う。
  - 送り直しのフレームと、コンポジターのフレームを、1 本の順番にそろえる。
- 関のうしろ（色の変換、エンコーダー、取り出し口）は、「エンコーダーの側」として、まとめて足し、まとめて外す。

### スレッドと優先度

既定は、**関門で測った形と同じ**（どのスレッドも、ふつうの優先度）。はじめの比べが、「Rust にした」ことだけの違いになるように。

| スレッド | 仕事 | 通り道か | 切り替え `sched` を入れたとき |
|---|---|---|---|
| 制御 | 標準入力の行を読む。標準出力に書く。止める・戻す。4 ms ごとに、キーフレームが要るかを見る（いまと同じ） | いいえ | そのまま |
| 入力 | `input_socket` を待つ → イベントにして、コンポジターの要素へ渡す（その場で、コンポジターのスレッドへ送られる） | 入力 | 上げる |
| コンポジター（プラグインの中） | アプリの確定を受けて、描く | 入力と絵 | 上げる（外から、スレッドの番号で） |
| フレームを運ぶ（コンポジターの要素の流れのスレッド） | 関 → 色の変換 → エンコーダーへ渡す | 絵 | 上げる |
| エンコーダーの出口（NVENC の要素の中） | 圧縮の済んだフレーム → `istesso-media` で封をして書く（いまと同じく、このスレッドの上で） | 絵 | 上げる |
| 送り直し | 最後のフレームから 50 ms たったら、関に 1 枚渡す | いいえ（順番は、関がそろえる） | そのまま |
| 知らせ | GStreamer のバス：カーソル、窓の数、失敗 | いいえ | そのまま |
| 記録 | フレームの記録を、ファイルに書く | いいえ | そのまま |
| `istesso-media` の中 | 受け付け、ペアリングの見回り、見る側ごとのスレッド | 変えない | そのまま |

- 通り道のスレッドは、ファイルに書かない、標準出力に書かない、通り道でないスレッドが長く持つロックを取らない。記録の行は、メモリーの中の待ち行列に入れ、記録のスレッドが書く（スクリプトは、1 秒ごとの書き出しのあいだ、通り道も待たせうる）。
- 「上げる」は、実時間の優先度の低い値（10。音より下、ふつうのプログラムより上）。権限がなくて上げられなかったときは、そのまま動き、**上げられなかったことを、フレームの記録の先頭に書く**（切り替えが効いていない回を、効いた回として読まないため）。上げたスレッドは、1 つずつ、記録の行になる（`sched`）。
- **作ったもの（2026-11-17、ホストで動かした）**：入力のスレッド、フレームを運ぶスレッド、エンコーダーの出口のスレッドは、自分で上げる。コンポジターのスレッドは、プラグインが名前を付けていないので、「パイプラインを始めたあとに増えた、名前のないスレッド」を上げる（ホストでは 3 つ。いちばん働いているのが、コンポジター）。
- **歯止め（`RLIMIT_RTTIME`）は、付けない**（2026-11-17、本線と決めた）。超えたときに、プロセスごと終わらされる決まりで、守るものより、落とすセッションのほうが痛い。代わりに、次の 3 つを守る。
  - **眠らずに待つ所は、どれも、コードの中の定数で長さを限る。** いま、眠らずに待つのは、入力のスレッドだけである（`spin-after-input`）。入力 1 つのあとに待つ長さは、20 ms まで（それより長い値は、起動のときに断る）。入力が途切れずに来ても、0.2 秒に 1 度は、眠って待つ形に戻る。どちらも定数で、試験がある。
  - **優先度は、音のスレッドより、ずっと下に置く。** このホストの音（PipeWire）は、88 と 83 で動いている。こちらは 10。
  - **最後の歯止めは、OS のものだけ**である（実時間のスレッドは、1 秒のうち 0.95 秒まで）。
- **ドライバーのスレッドは、別の値にした**：NVIDIA のドライバーが、このプロセスの中に作るスレッド（`cuda-EvtHandlr`。フレームごとに 2 回ほど起きている）は、`sched rt` では上げない。`sched rt+driver` で、それも上げる。`rt` だけを測ったあとで、分けて測る。

### エンコーダーを断られたとき、止めるとき（計画の行 4）

- **起動のとき**：コンポジターの側を先に動かして、`ready` と言う。そのあとで、エンコーダーの側を足す。開けなければ、足したものを外して、`no_encoder` と言う。終了しない。
- **`resume`、`attach` のとき**：同じ。開けなければ `no_encoder`。次の `resume` で、もう一度試す。
- **動いている最中**：エンコーダーの側が失敗を返したら、関がそれを受け止めて、エンコーダーの側を外し、`no_encoder` と言う。コンポジターとアプリは、気づかない。見る側は、つないだままで、「いま出す絵がない」（0.5 秒おき）を受ける。
- 失敗の出どころが、エンコーダーの側の要素なら `no_encoder`、コンポジターなら `error`（このあと終了）。スクリプトは、「断られてから 2 秒以内の失敗」という時間で見分けていた。
- **`pause`**：語を読んでから 0.3 秒以内に、エンコーダーの要素を閉じ終える。絵が止まっていても、すぐ閉じる（スクリプトは、次のフレームが来てから閉じる。確定のたびに描く形で、絵が止まっていると、閉じないままになる）。かかった時間を答えに書き、試験で確かめる。
- **`detach`**：先に、見る側を切る（0.1 秒以内）。そのあとで、エンコーダーを閉じる。
- 試験：断られることは、エンコーダーの名前を差し替える切り替えで作る（まねるだけ）。**本物の枠を使い切る試しは、持ち主の動いているセッションを止めうるので、この流れでは行わない。** 本線が、持ち主と時間を決めて行う。

### 切り替え（どれも、既定は「切」。入っているものは、フレームの記録の先頭に書く）

| 切り替え | すること | 前と後で比べるもの |
|---|---|---|
| `keep-awake <毎秒の回数>`（案：20）と `keep-awake-hold <ms>`（案：50） | 映している端末がつないでいて、絵を作っているあいだ、最後のフレームからも、最後の入力からも 50 ms たったら、最後のフレームを、もう一度エンコーダーに通して送る。描き直しはしない（GPU の上の同じ絵を、時刻だけ替えて渡す） | 止まっている画面の回の、圧縮の 95% と 99%（流れている絵：4.04 / 4.14 ms、止まっている絵：5.66 / 6.69 ms）。差の 3 つの値 |
| `sched off\|rt\|rt+driver` | 上の表の「上げる」。`rt+driver` は、ドライバーのスレッドも | 差の 3 つの値、「2 回以上遅れ」、区間ごとの値。負荷つきでも 1 回 |
| `spin-after-input <ms>` | 入力のスレッドが、入力のあと、この長さだけ、眠らずに次の入力を見る。**効くのは、続けて来る入力（ポインターの動き、押しっぱなし）だけ。** 間のあいた 1 回のキーには、効かない（そのあと待つのは、プラグインとドライバーの中のスレッドで、このプログラムのものではない） | 入力の区間。ポインターを動かす回が要る |
| `cpu-latency shown:<µs>` | `/dev/cpu_dma_latency` を、映している端末がつないでいるあいだだけ開いて、値を書く。深い眠りを、PC 全体で止める | 静かなときの、差の 3 つの値と区間ごとの値。**消費電力**（値 0 は、全部のコアが眠らない） |
| `cpu-latency input:<µs>:<ms>` | 同じ口を、入力のあとの短いあいだだけ使う。「入力の直後だけ眠らない」を、このプログラムのものでないスレッド（コンポジター、アプリ、ドライバー）にも効かせる形 | 同じ。止まっている画面の回で |

- 毎秒 85 枚の決まり（ADR 0002）：数えるのは、コンポジターが描き始める回数で、送り直しは、描かない。送り直しは、50 ms のあいだ何も出なかったときだけ出るので、流れている絵の回には、1 枚も入らない。
- **送り直しを待たせる入力は、絵で答えが返りそうなものだけ**：キーとボタンの「押した」、スクロール。ポインターの動きと、「離した」は、待たせない。動かない窓の上でポインターを動かすと、入力は毎秒 60 回以上来る。それで待たせると、送り直しが 1 枚も出なくなり、そのあとのクリックが、眠ったエンコーダーに当たる。
- **待たせる長さには、上限がある**：送り直しは、入力がなければ出ていた時刻から、`keep-awake-hold` より長くは遅れない。キーを打ち続けても、送り直しは、少なくとも「間隔 ＋ 待ち」（既定で 0.1 秒）に 1 枚は出る。Mac のホスト（`istesso-host-macos` の keep-awake）と、同じ決まりにした。
- **ぶつかりは、記録に出る**：新しいフレームが、関の順番待ちで 0.1 ms より長く待ったら、待った長さをフレームの記録に書く（`gate_wait`）。送り直しを入れた回で、入力に答えるフレームが、送り直しのうしろで、何回、どれだけ待ったかを、推し量らずに読める。
- 送り直しの 1 枚がエンコーダーの中にあるあいだに、アプリのフレームが来ると、そのフレームは、最大で 1 枚ぶん（4 ms 弱）待つ。入力のあと 50 ms は送り直さないので、入力に答えるフレームは、待たない。入力によらないフレーム（点滅、動画）は、8% ほどが待ちうる（毎秒 20 回 × 4 ms）。測って、記録に書く。

### 関が持つ最後のフレームと、時刻の印

**時刻の印（pts）は、エンコーダーへ、後戻りしない。**

- 印は、何に使われているか（コードを読んで確かめた）：フレームのヘッダーに載って、見る側へ行く（ADR 0015）。試作のビューアーは、復号器に渡すフレームの名札にして、自分の記録の行に書く。**表示の時刻を決めるのには、使っていない**（届いたら、すぐ出す）。計測の道具（`scripts/m1-step3-breakdown.py`）は、**1 枚のフレームの行を、印で突き合わせ**（コンポジターを出た、変換を出た、圧縮を出た、渡した、見る側の行）、見る側の行を、印の順に読む。だから、印は、フレームごとに違い、増え続けなければならない。
- 送り直しのフレームは、パイプラインのいまの時刻（と、前の印 ＋ 1 の、遅いほう）を印にする。そのあとに来るコンポジターのフレームが、それより前の印を持っていたら（描き始めた時刻を印にしている場合など）、**前の印 ＋ 1 に付け替える**。付け替えは数えて、1 枚ごとにフレームの記録に書き（`restamped`。もとの印も）、回の終わりに数を書く（`restamps`）。「コンポジターを出た」の行は、付け替えたあとの印で書くので、突き合わせは切れない。
- 付け替えが計測をゆがめるのは、道具が印そのものを時間として使うときだけで、いまの道具は、そうしていない（時間は、各行の `t_ns`）。それでも、**切り替えを全部切った回では、付け替えは 0 のはず**である（送り直しがなければ、印はコンポジターのものだけ）。0 でなければ、その回は、わけが分かるまで使わない。
- コンポジターが印をどう付けているかは、ホストで確かめる（下の「確かめていないこと」）。

**関は、最後のフレームへの参照を 1 つ持ち続ける。** 本物のパイプラインでは、次の 2 つを意味する。どちらも、計測の 1 で確かめる。

- コンポジターのフレームの置き場（プール）から、**いつも 1 枚が出たまま**になる。プールの枚数が少ないと、コンポジターが次のフレームを取れずに待つ。枚数は、ホストで確かめる。スクリプトも、止めているあいだは、1 枚を持っていた。
- 色の変換に入るフレームが、**書き換えられない形**（参照が 2 つ）になる。変換は、別のフレームに書き出すので、写しは増えない見込みだが、確かめていない。「コンポジターを出てから、変換を出るまで」（関門の数値の回で 0.11 ms）を、スクリプトと比べる。
- 測って分かる差が出たら、隠さずに書いて、持ち方を変える（送り直しを切っているあいだは、持たない、など）。

### 変えないもの

コンポジターのプラグイン（同じコミット、同じ 4 つの修正、同じビルド）とその設定。色の変換とエンコーダーの設定（`scripts/m1_encoder.py` と同じ文字列）。`istesso-media` のライブラリー（1 フレームを、エンコーダーの出口のスレッドの上で、1 回の呼び出しで渡す）。キーフレームの求め方（4 ms ごとに見る。50 ms に 1 枚まで）。コンポジターへ渡す入力のイベントの形。カーソルと窓の数の知らせの受け方。**フレームの記録の形**と、計測の形の語と答え。

### クライアントの流れとの境目

**セッションのメッセージ**（エージェントとランナーのあいだは、ADR 0010 の行。標準入力と標準出力、1 行に 1 つの JSON）

| 用件 | クライアント → エージェント（制御チャンネル。ADR 0010 の 4。束の 5） | エージェント → ランナー | ランナーがすること | ランナー → エージェント | 見る側の接続に見えること（ADR 0015） |
|---|---|---|---|---|---|
| 閉じるよう頼む。**アプリを終える（Command-Q）も、これ** | `session_stop`（`force` なし） | `{"v":1,"cmd":"close"}` | コンポジターが、**そのアプリの全部の窓に**「閉じてほしい」と伝える。力ずくでは閉じない | `{"v":1,"event":"close_asked","asked":true,"windows":N}`（足す提案。下の「アプリを終える」） | 何も変わらない。アプリが尋ねたら、その窓が映る |
| 窓をしまった | `session_show`（見えていない） | `{"v":1,"cmd":"pause"}` | 0.3 秒以内に、エンコーダーを閉じる | `{"v":1,"event":"paused","took_ms":T}`（足す提案） | つないだまま。0.5 秒おきに「いま出す絵がない」 |
| 窓を出した | `session_show`（見えている） | `{"v":1,"cmd":"resume"}` | エンコーダーを開き直す。最初は、キーフレーム | `{"v":1,"event":"resumed","opened_ms":T,"encoded_ms":T,"written_ms":T}`（足す提案）。開けなければ `{"v":1,"event":"no_encoder","message":…}` | キーフレームが、ふつうのフレームとして届く。断られたときは、「いま出す絵がない」が続く |
| 最後の窓が閉じた | （`session_wait` の答えで知る） | — | 窓の数が 0 になったと、コンポジターが知らせる。ランナーは、数をすぐに言い、**窓が 1 枚もないまま 5 秒たってから** `empty` と言う（閉じるよう頼んだ答えなら、待たない。下の「窓がなくなっても、プロセスが残るアプリ」） | 数が変わるたびに `{"v":1,"event":"windows","count":N}`（足す提案）。そのあとで `{"v":1,"event":"empty"}` | エージェントがセッションを終え、ランナーの標準入力が閉じる。ランナーは「終わり」（わけ 0）を送って切る |
| 窓だけ閉じる（離れる） | `session_detach` | `{"v":1,"cmd":"detach"}` | 0.1 秒以内に見る側を切り、エンコーダーを閉じる | `{"v":1,"event":"paused","took_ms":T}`（足す提案） | 「終わり」（わけ 2） |
| つなぐ | `session_attach` | `{"v":1,"cmd":"attach","peer":{…}}` | その端末だけを名指して、絵を作り直す | `{"v":1,"event":"attached","display":{…},"answer":{"transport":"channel","channel_port":N}}`。開けなければ、続けて `no_encoder` | `watch` に `stream` と答える。最初は、キーフレーム |

**アプリを終える**（2026-11-17、持ち主の決定）：中継の窓での Command-Q は、クライアントが、キーとしてではなく、「このアプリを終える」という**意味**として送る。ホストは、それを、その OS のふつうの終わり方にする。Linux では、アプリの窓への「閉じてほしい」の頼みで、上の表の `close` と**同じ行**である（別の行は、作らない。1 つのセッションのコンポジターには、そのアプリの窓しかなく、`close` は、その全部に頼む）。

- **力ずくでは、終わらせない。** アプリが保存を尋ねたら、その窓が映り、セッションは続く。
- **切れているあいだは、届かない。あとから送り直しもしない**（クライアントの側の決まり。ADR 0015 の「切れているあいだに打たれたものは、あとから送り直さない」と同じ）。
- ランナーの答え（どれも、足す提案の行。古いエージェントは、読み飛ばす）：

| 起きたこと | ランナー → エージェント |
|---|---|
| 頼みを、N 枚の窓に伝えた | `{"v":1,"event":"close_asked","asked":true,"windows":N}` |
| 終えるものがない（窓が 1 枚もない） | `{"v":1,"event":"close_asked","asked":true,"windows":0}` |
| このホストでは頼めない（コンポジターに、3 つ目の修正がない） | `{"v":1,"event":"close_asked","asked":false,"windows":N}` |
| 窓が閉じていく | これまでどおり `{"v":1,"event":"windows","count":M}`。最後の 1 枚が閉じたら、続けて `{"v":1,"event":"empty"}` |
| 頼んでから 5 秒たっても、窓が残っている（アプリが何か尋ねている。または、閉じないと決めた） | `{"v":1,"event":"still_open","windows":M,"after_s":5}`。1 度だけ言う。セッションは続く。どちらなのかは、ランナーには分からない（尋ねる窓は、ふつうの窓として映っている） |

- 5 秒は、コードの中の定数である。そのあとで窓が全部閉じれば、`empty` が出る。もう 1 度 `close` を送れば、もう 1 度、頼む。

**窓がなくなっても、プロセスが残るアプリ**（2026-11-17、持ち主の決定）：最後の窓を閉じたあとも、裏で動き続けるアプリがある。窓がなければ、映すものも、人が触れるものもないので、セッションは終える。受け持ちは、**知っている側**で分ける：窓のことは、ランナー（コンポジター）が知っている。プロセスのことは、アプリを起動したエージェントが知っている（アプリは、エージェントの子で、エージェントが作ったプロセスグループにいる。終わったかどうかを確かに知れるのも、グループの番号がほかのプロセスに渡ったあとで送らないようにできるのも、親だけである）。**プロセスに合図を送るのは、その持ち主（エージェント）で、ランナーは送らない。**

ランナーの側（作った。`istesso-host-linux` の `session`）：

| 起きたこと | ランナー → エージェント |
|---|---|
| 最後の窓が閉じた（アプリが、自分で閉じた） | すぐに `{"v":1,"event":"windows","count":0}`。**窓が 1 枚もないまま `LAST_WINDOW_WAIT_S`（5 秒）たったら** `{"v":1,"event":"empty"}` |
| 待っているあいだに、窓が出た | `{"v":1,"event":"windows","count":1}`。`empty` は言わない。セッションは続く。その窓があとで閉じたら、もう一度、はじめから待つ |
| 最後の窓が、`close` を伝えてから `CLOSE_ANSWERED_WITHIN_S`（5 秒）以内に閉じた | `windows` の 0 に続けて、**待たずに** `empty`。人が終わりを頼んだ答えなので、クライアントの窓に、空の絵を 5 秒見せない |
| 待っているあいだに、`close` が来た | `close_asked`（窓は 0）に続けて、待たずに `empty`。頼む窓はもうなく、終わりを頼まれているため |

- **スプラッシュ（最初の窓が閉じてから、本当の窓が開くまで、窓がないアプリ）との見分け**：コンポジターから見ると、「窓の数が 0」は、どちらも同じである。見分ける材料は、ない。セッションを守るのは、**待つ長さだけ**である。5 秒より長く、窓を 1 枚も出さないアプリは、終わったものとして扱われる（分かっている不足。値は定数で、使ってみて直す）。
- 待ちは、ふつうのアプリ（窓と一緒にプロセスも終わる）を、遅くしない。プロセスが終われば、エージェントが自分で気づいて、すぐにセッションを終える（ADR 0010）。待ちが効くのは、プロセスが残るときだけである。
- 計測の形は、変えていない（スクリプトと同じく、0 になったら、すぐ `empty` と言う）。
- 試験：どの PC でも動く試験（まねたコンポジター）が 4 本。本物のコンポジターでは、この流れの試験用のアプリ（`istesso-stay`。計測のテストアプリ `istesso-flash` は、変えていない）で動かした（下の「ホストで確かめたこと（夜）」）。

**最初の窓が出るまで**（持ち主の決定の 1。ランナーの側は、作った）：始まってから最初の窓が出るまでは、5 秒の決まりは、当てはまらない。起動の遅いアプリ（snap のアプリの、初めての起動など）を、終わったものと取り違えないためである。

| 起きたこと | ランナー → エージェント | 受け持ち |
|---|---|---|
| エージェントが、アプリを起動したと伝えた（`application`）。窓は、まだない | `{"v":1,"event":"opening"}`（足す行）。1 度だけ | ランナー（作った）。クライアントの窓に「開いています」と出すのは、クライアントの流れ。運ぶのは、エージェント（つなぐとき） |
| 最初の窓が出た | これまでどおり `{"v":1,"event":"windows","count":1}` | ランナー（作った） |
| `opening` から `FIRST_WINDOW_WAIT_S`（60 秒）たっても、窓がない | `{"v":1,"event":"no_window_yet","after_s":60}`（足す行）。1 度だけ。**ランナーは、何も決めない**（`empty` も言わない。セッションは続く） | 言うのは、ランナー（作った）。どうするかを決めるのは、アプリのプロセスが生きているかを知っている、エージェント（つなぐとき） |
| `application` が来たときに、もう窓がある | `opening` は言わない | ランナー（作った） |

**アプリが、自分で終わったとき**（持ち主の決定の 2）：アプリのプロセスが自分で終わったら（自分の閉じるボタン、自分の「終了」）、5 秒を待たずに、すぐにセッションを閉じる。Mac に、空の窓を残さない。

- エージェントの側：いまのコードは、`empty` を待たずに、アプリのグループがなくなったことに自分で気づいて、セッションを終える（`origin/m3-app-manager` の `session/mod.rs`。読んだだけ）。つなぐときにも、この形を保つ（アプリマネージャーの流れ）。
- ランナーの側：`empty` を待っているあいだでも、標準入力が閉じたら、すぐに終わる。ホストで見た：窓が閉じて、プロセスが終わり、エージェントの役の試験が標準入力を閉じてから、0.26 秒でランナーが終了した（`empty` は、出ていない）。

**残ったプロセスを、見えるようにする**（持ち主の決定の 3。**ランチャーとエージェントの仕事。作っていない**）：頼む合図のあとも残っているプロセスは、それが起動したものも含めて、ランチャーに出す。人は、そこで、力ずくで終わらせることを選べる。黙って残さない。知らせるのは、エージェント。見せるのは、ランチャー。

**試験**（持ち主の決定の 4。**アプリマネージャーの流れ**）：エージェントの変更には、「どの道も、力ずくの終わり（SIGKILL）を送らない」ことを確かめる試験を付ける（人が、力ずくで終わらせると選んだ道を除く）。

**記録のための 1 行**（持ち主の決定の 5）：「最後の窓を閉じたら、アプリを終える」は、最初の版の割り切りである。Mac では、窓を閉じても、アプリは、ふつう動き続ける。裏で動くアプリを残すかどうかは、その知らせ（通知）を運ぶことと合わせて、あとで決める。

エージェントの側（**アプリマネージャーの流れが、つなぐときに作る。作っていない**）：

| `empty` を受けたとき | エージェントがすること | セッションの終わりに言うこと |
|---|---|---|
| アプリのグループが、もうない | 何も送らない。セッションを閉じる | 自分で終わった |
| グループが、まだある | グループに、終わるよう頼む合図（SIGTERM）を送り、数秒待つ（値は、その流れが決める）。終わったら、セッションを閉じる | 合図のあとで終わった |
| 待っても、まだある | **力ずくでは、終わらせない（この道から、SIGKILL は送らない）。** セッションは閉じる | プロセスが残った。何が残ったか（グループの番号）と、終わらせ方（ホストの持ち主が、力ずくで終わらせるコマンドを使う。形は、その流れが決める） |

- **いまのエージェントは、これと違う**（`origin/m3-app-manager` のコードを読んだ。動かしてはいない）：`empty` を受けると、**すぐに**セッションを終え、アプリのグループに SIGTERM を送り、3 秒後に SIGKILL を送る（`session/mod.rs` の `Empty` の枝と、そのあとの `app.stop(rules.app_stop_grace)`。`session/process.rs` の `stop`）。持ち主の決定（この道では、力ずくで終わらせない）と合わないので、つなぐときに変える。ランナーの待ちは、この変更がなくても効く（`empty` が遅く出るだけで、行は増えていない）。
- ランナーの行は、足していない。何が起きたかは、プロセスを知っているエージェントが、セッションの終わり（`end`）に書く。

- 「足す提案」と書いた行と項目は、知らない行と項目を読み飛ばすエージェント（ADR 0010 の約束）には、害がない形で作る。下の表にまとめる。
- **ランナーは、`ready` より前には、何も言わない。** その前に起きたこと（コンポジターが始まったときの「窓の数は 0」など）は、取っておいて、`ready` を言ったあとに、起きた順に言う。フレームの記録には、起きたときに書く。計測の形は、取っておかない（道具が、行を、来た順に読む）。
- 束の 5 が入るまで：クライアントからは、届かない（ADR 0018 のとおり）。計測の形では、スクリプトと同じ語を、標準入力で受ける。

**アプリマネージャーの流れと、つなぐとき（束の 5）に合わせるもの**

| 足すもの | 向き | 形 | 古いエージェントでは |
|---|---|---|---|

| `windows` | ランナー → エージェント | `{"v":1,"event":"windows","count":N}`。窓の数が変わるたび。0 になったときは、続けて `empty`（約束にある行） | 読み飛ばされる |

| `no_window_yet` | ランナー → エージェント | `{"v":1,"event":"no_window_yet","after_s":60}`。`opening` から 60 秒たっても、窓がないとき、1 度 | 読み飛ばされる |

送るときの文面（英語。案）：

```text
A toplevel whose first commit arrives before the output exists is never configured

With gst-wayland-display at 1301f86, a client that connects and commits its new xdg_toplevel
before the compositor has created its output never receives the initial configure, and waits
for it forever. Nothing is logged.

Seen with a small winit 0.30 client started about 4 ms after the element posted `wayland.src`
(2 of 3 starts; GStreamer 1.24, Ubuntu 24.04). With WAYLAND_DEBUG=1 the client shows
get_toplevel, set_title, wl_surface.commit and a sync; the answers are wl_keyboard.keymap,
repeat_info and the sync's done, and no xdg_toplevel.configure / xdg_surface.configure. The
wl_output global was announced 1.3 ms after that commit. A client that starts more slowly
(a GTK 4 application, about 0.2 s) is configured normally.

Cause, from reading wayland-display-core/src/wayland/handlers/compositor.rs: `commit` takes the
window out of `pending_windows` (`swap_remove`) and then returns when `self.output.is_none()`,
without putting it back. The output is created later, by the first `Command::VideoInfo`
(`apply_video_info`), which does not look at windows that committed before it. The client does
not commit again until it has been configured.

A possible fix (not written): keep the window in `pending_windows` when there is no output, and
send the initial configure to the pending windows that have committed when the output is first
created.

What we do meanwhile: we let clients in only after the element has pushed its first buffer.
```
