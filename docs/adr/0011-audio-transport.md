# ADR 0011：音の配信は自前で作り、認証つきの通信路に乗せる

- 状態：採用（2026-11-16。条件つき。下の「採用の条件」）
- 日付：2026-11-16

## 背景

[ADR 0005](0005-audio-service.md) は、音を映像から独立した常駐サービスにすると決め、配信の部品に Roc Toolkit を挙げた。この決定のうち、次の 2 つはまだ決まっていない。

- **音の経路の認証と暗号化。** 端末どうしは、ペアリングで固定した鍵で相互に認証する（R-13）。音にも、端末ごとの権限がある。暗号の部品は自作しない（AGENTS.md）。
- **Roc の動かし方。** PipeWire のモジュールとして使うのか、ライブラリとして自分のプロセスに組み込むのか。

最初の向き（Ubuntu で鳴らした音を、Mac から出す）を設計するために、2 台の実機と Roc の現状を調べた（[記録](../measurements/2026-11-16-m2-step0-survey.md)）。その結果、上の 2 つを決めるだけでは足りず、**配信の部品そのものを替えたほうがよい**と考えるに至った。この文書は、その提案として書かれ、2026-11-16 に、条件つきで採用された。

ADR 0005 のほかの決定（独立した常駐サービス、音の出口を 1 つ選ぶ、非圧縮で送る、時計のずれを補正する、再生中は眠らせない、手を入れない経路）は変えない。

## 採用の条件

- **音は、映像と入力の経路と同じ仕組みで運ぶ。音のためだけの仕組みは、作らない。**
- いま、その仕組みは `istesso-link` の通信路である（入力は、`m1-latency` ブランチで、すでにこの上を流れている）。音は、`istesso_link::Channel` をそのまま使う。ハンドシェイクにも暗号にも、音の側からは何も足さない。
- 映像の運び方は、まだ決まっていない。決まったら、音は、映像と入力といっしょにそこへ移る。音だけが別の仕組みに残ることも、音が先に別の仕組みを作ることも、しない。

## 調べてわかったこと

| 項目 | 内容 |
|---|---|
| 認証と暗号化 | Roc にはない。計画表に SRTP と DTLS があるが、未着手。受信側は、ポートに届いた RTP を、送り主を確かめずに再生する |
| ホスト（Ubuntu 24.04） | `libroc` 0.3.0 と、PipeWire の Roc 用モジュールが、最初から入っている。ただし Ubuntu の `libroc` は OpenFEC を外してビルドされていて、**失われたパケットを復元する機能（FEC）が使えない** |
| Mac | Roc を入れる手段が、ソースからのビルドしかない（Homebrew に formula がない）。ビルドには scons、ragel、gengetopt などを入れる必要がある |
| 音の形式 | Roc が最初から持っている形式は、16 ビット・44.1 kHz。ホストの PipeWire は 48 kHz で動いているので、送る前と受けたあとの 2 回、サンプルレートの変換が入る。PipeWire のモジュールには、形式を変える設定がない |
| 欠落の補完 | Roc にあるのは、FEC による復元だけ。復元できなかった分を聞こえにくくつなぐ補完（PLC）は、計画表で未着手 |
| Rust から使う手段 | 公式のバインディングは C、Go、Java。Rust は計画表で未着手で、crates.io にもない。使うなら、C の API を自分でつなぐ |
| Windows | 未対応（計画表で未着手）。R-14 は、Windows をあとから足せる構成を求めている |
| リリース | 最新は 0.4.0（2024-06-14）。それより新しいものはない |
| OpenFEC のライセンス | 大半は CeCILL-C（LGPL に近い）。LDPC-Staircase の部分は CeCILL（GPL に近い）。FEC を使うなら、この部分を外してビルドする必要がある |

## 比べる案

- **A：Roc をそのまま使う。** ADR 0005 の表のとおり。ホストは PipeWire の `roc-sink` モジュール、Mac は Roc の受信側を Core Audio につなぐ。経路は、暗号化していない RTP（UDP）。
- **B：Roc を、認証つきの通信路の中に通す。** Roc には、ネットワークを自分では持たず、パケットの出し入れだけをする API がある（0.3.0 以降）。そのパケットを、`istesso-link` の通信路（[ADR 0007](0007-control-channel.md)）で運ぶ。
- **C：自前で作る。** PipeWire から取り込んだ PCM を、そのまま `istesso-link` の通信路で運ぶ。時計のずれ補正は、出口の側で、既製のリサンプラー（rubato、MIT OR Apache-2.0）を使って行う。

| 観点 | A：Roc をそのまま | B：Roc を通信路の中に | C：自前で作る |
|---|---|---|---|
| 認証と暗号化 | ない。同じ LAN の誰でも聞け、誰でも Mac に音を送り込める | `istesso-link` で守れる | B と同じ |
| ホストに入れるもの | なし（モジュールは入っている） | `libroc-dev`。自分で取り込むなら、C と同じものも要る | `libpipewire-0.3-dev`、`libclang-dev`（PipeWire のクライアントをビルドするため） |
| Mac に入れるもの | Roc をソースからビルドする。そのために scons、ragel、gengetopt、cmake などを入れる | A と同じ | なし |
| 配布（R-12） | pkg に `libroc` と、その依存を同梱する。.deb は、配布元の `libroc` の版に縛られる | A と同じ | Rust のクレートだけ。同梱するライブラリはない |
| 版のずれ | ホストは 0.3.0、Mac は自分でビルドした版。API が版で違う | A と同じ | ない |
| 音の形式 | 16 ビット・44.1 kHz。変換が 2 回入る | 形式を登録すれば 48 kHz にできる。16 ビットは同じ | 32 ビット浮動小数・48 kHz（PipeWire の中の形式のまま）。変換は、ずれ補正の 1 回だけ |
| 時計のずれ補正 | Roc が行う。実績がある | A と同じ | 自分たちで作る。測って確かめる必要がある |
| 欠落 | Ubuntu の版では FEC が使えない。失われた分は無音になる | TCP の上なので、失われない（遅れて届く） | B と同じ |
| テスト | 実機が要る | 実機が要る | 中心の部分（受信バッファーと、ずれ補正）は、時計を模擬して CI で確かめられる |
| Windows（R-14） | Roc が対応するまで、足せない | A と同じ | 入出力を書けば足せる |
| ライセンス | MPL-2.0（ADR 0001 の条件つき）。FEC を使うなら CeCILL-C も | A と同じ | MIT、Apache-2.0 など。`deny.toml` に例外を足さない |

## 決定

**C を採る。届かなければ B に移る。**

理由：

1. **A は、製品に残せない。** 認証も暗号化もない。計測のためだけに使うことはできる（M1 の手順 3 で、暗号化していない UDP をそう扱ったのと同じ）。ただ、そのために Mac で Roc をビルドしても、その手間は製品に残らない。
2. **B で Roc に残る役目は、受信側のずれ補正だけになる。** 認証つきの通信路は TCP の上にあるので、パケットは失われず、FEC は要らなくなる（Ubuntu の版では、そもそも使えない）。その 1 つの役目のために、C++ のライブラリを 2 つの OS で用意し、Rust からつなぎ、配布物に同梱することになる。
3. **C は、入れるものと配るものが少ない。** Mac には何も入れない。配布物に同梱するライブラリがない。Windows を足すときも、入出力を書けば済む。
4. **C は、音がそのまま届く。** PipeWire の中の形式のまま運ぶので、変換は、ずれ補正の 1 回だけになる。
5. **C の弱みは、ずれ補正を自分たちで作ること。** ここは Roc に実績があり、こちらにはない。ただ、作るのは「受信バッファーにたまっている量を見て、リサンプラーの比をゆっくり動かす」という制御で、時計を模擬すれば、実機がなくても長い時間ぶんを確かめられる。実機では、短いテストから始めて、8 時間の受け入れ条件（ADR 0005）まで段階を踏む（[m2-plan.md](../m2-plan.md)）。

   この弱みについては、提案のあとで材料がそろった。時計を模擬した試験では、時計の差が ±100 ppm（合わせて 200 ppm まで）でも、44.1 kHz の機器でも、8 時間のあいだ途切れも飛ばしもなく、音程のずれは 50 ppm（0.09 セント）以内だった（[記録](../measurements/2026-11-16-m2-step1-simulated-clocks.md)）。Mac の実機の時計でも、無音を渡しながら 90 秒動かして、途切れなく動いた（[記録](../measurements/2026-11-16-m2-step2-mac-playback.md)）。2 台のあいだでも、テスト用の正弦波を有線で 90 秒通して、受け取ったパケットは送ったものとすべて同じで、取り込みから機器に渡すまでは中央値 46.5 ms だった。ただし、実機の短い計測では、音程が ±69 ppm（0.12 セント）動き、模擬で検査している上限を超えた。聞こえる大きさではないが、実機での上限は、まだ示せていない（[記録](../measurements/2026-11-16-m2-step3-cable-test-sources.md)）。本物の取り込みでの計測と、8 時間の実機での確認は、まだである。

## 決定の中身

### 経路

- 音源のホストが、音のための TCP ポート（既定 47802）で待ち受ける。出口の端末が、つなぎに行く。小さなパケットをすぐ出すために、どちらの側も no-delay にする。
- つないだら、制御チャンネルと同じ手順（ADR 0007：Noise XX、固定した鍵での相互認証）を、`istesso-link` の `Channel` をそのまま使って行う。**暗号の手順は、何も足さない。**
- 音源の側は、相手がペアリング済みで、かつ音の権限（`Permission::Audio`）を持つときだけ送る。この権限は、新しくペアリングした端末には付いていない（[ADR 0006](0006-pairing.md)）。
- 音源の側は、流しているあいだも、1 秒より長くは空けずにペアリング一覧を読み直す。ペアリングを解除されたか、音の権限を外された相手への送信は、そこで止める。制御チャンネルは短い接続なので「解除は次の接続から効く」で足りたが、音の接続は長く続くためである。
- つないできた相手には、ハンドシェイクと最初のメッセージを**合わせて** 3 秒しか与えない。待ち時間を読み取りのたびに数え直すと、1 バイトずつ送る相手が、接続を何分も開いたままにできる。そこで、読み書きのたびに、締め切りまでの残りだけを渡す。出口の側も、つなぐとき（接続、ハンドシェイク、最初の返事）に同じことをする。
- 同時に相手をする数は、2 つに分けて数える。まだ誰とも分かっていない相手は 16 まで、ペアリング済みで音の権限を持つと分かった相手は 8 まで。前者がいくら増えても、後者の枠は減らない。すでに流れている音は、止まらない。
- 出口の側がつなぎに行く理由：出口（ノート PC など）は、眠ったり、アドレスが変わったりする。音源は動き続けている。つなぎ直すのを、いなくなった側の役目にしておくのが単純である。Mac の側で、着信の許可を求められることもない。

### 形式

- 非圧縮の PCM。32 ビット浮動小数、48 kHz、2 チャンネル。約 3.1 Mbps。
- 1 パケットは、PipeWire の 1 回の処理ぶん（256 フレーム、5.3 ms を求める）。先頭に、並びの版、連番、ストリームの先頭からのフレームの位置、取り込んだ時刻（音源の時計）を付ける。
- 並びの詳細は [m2-plan.md](../m2-plan.md) に書く。版の番号を持たせ、知らない項目は読み飛ばす（ADR 0007 のメッセージと同じ考え方）。

### 時計のずれ補正

- 出口の側で行う。音源の時計（ホストのシステムの時計）と、出口の機器の時計は、少しずつずれる。ずれが 50 ppm なら、8 時間で 1.4 秒ぶんになる。
- 出口は、受け取った音を受信バッファーにため、機器が引き取る速さに合わせて、リサンプラーの比を少しずつ動かす。たまっている量を、目標から離さないための制御である。
- 配信経路がビットパーフェクトにならないことは、ADR 0005 のとおりで、変わらない。

### 欠落と途切れ

- TCP なので、音が欠けることはない。遅れて届くだけである。遅れは、受信バッファーが吸収する。
- 受信バッファーが空になったら、短くフェードして無音にし、回数と長さを数える。たまり直したら、フェードして再開する。
- **遅延は、経路が止まったあとも、目標のまわりに保つ。** 止まっていたあいだの分がまとめて届いたら、あいだの音を捨てて先へ進み、短いクロスフェードでつなぐ（届いたパケットの待ち時間が、目標より 20 ms を超えて長いとき）。遅れた分を、リサンプラーで少しずつ取り戻すことはしない。捨てた回数とフレーム数は、数える。
- 音源の側では、取り込みのスレッドを待たせない。取り込みのスレッドはリングバッファーに書くだけで、送るのは別のスレッドである。送るのが遅れたら、古い音から捨て、位置を飛ばして、音が抜けたことを出口に知らせる。
- 数えた値は、いつでも見られるようにする。受け入れ条件（8 時間、途切れない）は、この値が 0 であることで確かめる。

### UDP にしない理由

- 有線 LAN では、パケットはほとんど失われない。失われたときの再送は、たいてい十数 ms 以内で済み、受信バッファー（数十 ms）の中に収まる見込みである。短いテストで、届く間隔の分布を測って確かめる。
- Wi-Fi で起きるのは、欠落よりも「まとめて遅れる」ことである。M1 の計測では、Mac の Wi-Fi が別のチャンネルへ移るあいだ通信が待たされ、経路の 95 パーセンタイルが約 95 ms になっていた（記録は `m1-latency` ブランチにある）。これは UDP にしても FEC を足しても救えず、受信バッファーの大きさで受けるしかない。
- UDP の上で認証と暗号化を行うには、通信路の手順を新しく決める必要がある。映像と入力の経路の方式は、M1 の手順 4 で決める予定で、まだ決まっていない（[m1-plan.md](../m1-plan.md)）。音が先に、独自の方式を作ることはしない。
- その方式が決まったら、音も、映像と入力といっしょにそこへ移る（採用の条件）。認証つきのデータグラムになっても載せ替えられるように、パケットには最初から連番と位置を入れておく。

### 部品（ADR 0005 の表を、こう替えた）

| 役割 | これまでの ADR 0005 | この文書 |
|---|---|---|
| 配信 | Roc Toolkit | `istesso-audio`（自前）と、`istesso-link` の通信路 |
| 時計のずれ補正 | Roc Toolkit | rubato のリサンプラー（MIT OR Apache-2.0）と、自前の制御 |
| 欠落の補完 | Roc Toolkit（FEC） | TCP の再送と、受信バッファー。途切れたときは、フェードして数える |
| Linux の取り込み | PipeWire（Roc 用のモジュール） | PipeWire のクライアントとして、仮想の出力先を作る（`pipewire` クレート、MIT）。Roc 用のモジュールは使わない |
| Mac の再生 | Core Audio | Core Audio（`coreaudio-rs`、MIT OR Apache-2.0）。変えない |
| Mac の取り込み | Core Audio のタップ | 変えない（この文書の範囲の外） |

## B に移るとき

次のどれかが起きたら、Roc を通信路の中に通す案（B）を考え直す。

- 自前のずれ補正が、8 時間の受け入れ条件を満たせない。または、補正による音の揺れが聞き取れる。
- 欠落の多い経路（出先など）で使うことになり、再送では間に合わない。このときは、映像の経路で決まった方式の上で、FEC を使う。

B に移っても、取り込み、通信路、権限の確かめ方、再生、計測は、そのまま使える。替わるのは、受信バッファーとずれ補正の部分だけである。

## 既知の不足

- **経路が、受信バッファーより長く止まれば、途切れになる。** 再送を待つあいだ、あとの音も届かないからである。たまった分は捨てるので、遅延は元に戻る。待ち時間の目標 40 ms のうち、遅れたパケットのために使えるのは約 12 ms で、Wi-Fi の Mac では目標を大きくする必要がある。目標を自動で決める仕組みは、まだ設計していない。
- **同じネットワークから接続を開き続ける相手は、開き続けているあいだ、ほかの端末が新しくつなぐのを妨げられる。** 誰とも分かっていない相手の枠（16）を、3 秒ごとに埋め直せばよいからである。すでに流れている音は止まらないが、切れたあとのつなぎ直しは待たされる。制御チャンネルについて ADR 0007 が受け入れているのと同じ不足で、対策は、同時に相手をする数の上限と短い締め切りだけである。
- 1 つの音源の音を同時に受け取れる出口は、1 つだけにする。あとから申し込んだ出口に切り替わる。
- 音の接続は、制御チャンネルとは別のポートで受ける。エージェントを常駐サービスにするとき（M9）に、1 つのポートに寄せるかどうかを決める。
- 出先（インターネット越し）は、この文書の対象の外である。非圧縮の 3.1 Mbps を、そのまま出先へ送ることは考えていない。
- `snow` が第三者の監査を受けていないことは、ADR 0007 と同じである。
