# ADR 0014：ホストの役は、丸ごと専用ユーザーで動かす

- 状態：提案（M5 の設計の段階。案の選び方は、申し送りのねらいに合わせた。「採用」に変えるのは、人が読んだあと）
- 日付：2026-11-16

## 背景

[ADR 0003](0003-isolation.md) は、隔離を専用ユーザーで行うと決めた。アプリと、herdr・コーディングエージェントを、専用ユーザーで動かす。決まっていないことが、3つ残っている。

1. **Istesso 自身のプロセスを、どのユーザーで動かすか。** エージェント（`istesso agent`）、セッションのランナー、音の取り込みである。
2. **専用ユーザーを、OS ごとにどう作るか。** 何に権限が要るか。[AGENTS.md](../../AGENTS.md) は、権限の要る処理を増やすときに、理由を ADR に残すよう求めている。
3. **Mac で、GUI のアプリを専用ユーザーのセッションから配信する方法。** ADR 0003 は、M4 で検証すると書いている。

いまは、どの PC でも、すべてがふだんのユーザーで動いている。この状態には、見落としやすい穴がある。**ふだんのユーザーで動くエージェントが、アプリの起動と入力を受け付けると、ペアリングした端末は、ふだんのユーザーとしてアプリを操作できる。** ファイルを開く窓から、ふだんのファイルに届く。隔離は、ホストの役がどのユーザーで動くかで決まる。

2026-11-16 の決定で、M5 は今週、設計までである。実装するときも、ふだんのファイルには触れない。ねらいは、ファイルが消える、壊れる事故を避けることで、ここだけは急がない。決めごとで判断がつかないときは、ねらいに合うほうを選ぶ決まりである。同じ申し送りは、使い手が開発者に限らないので、導入のかんたんさと、説明なしで使えることを重く見る、とも伝えている。

この文書の中身は、今週は何も実行しない。

ADR 0009（`m1-latency` ブランチ）と ADR 0010（`m3-app-manager` ブランチ）は、まだ `main` にない。この文書では、リンクにせずに番号で指す。

## 比べる案

- **A：ホストの役を、丸ごと専用ユーザーで動かす。** エージェント、ランナー、アプリ、音の取り込み、herdr とコーディングエージェント。ふだんのユーザーで動かすのは、クライアントの役だけ。
- **B：エージェントはふだんのユーザーで動かし、アプリだけを専用ユーザーで起動する。**
- **C：ユーザーを2つ作る。** 鍵を持つ側（エージェント）と、アプリの側。

| 観点 | A：丸ごと専用ユーザー | B：アプリだけ専用ユーザー | C：ユーザーを2つ |
|---|---|---|---|
| 動いているあいだに要る特権 | ない | ある。ユーザーを切り替える仕組み（sudo の規則か、root で動く小さなプログラム）が、アプリを起動するたびに働く | ある（B と同じ） |
| 端末の鍵と、ペアリングの一覧 | 専用ユーザーの中にある。アプリとコーディングエージェントから、手が届く | ふだんのユーザーの中にある。アプリからは届かない | 鍵を持つ側の中にある。アプリからは届かない |
| ふだんのファイル | OS の権限で届かない | アプリからは届かない。エージェントからは届く。エージェントに不具合があると、ペアリングした端末がふだんの領域に届く | OS の権限で届かない |
| 作りの単純さ | 単純。「アプリは、エージェントと同じユーザーで動く」（ADR 0010）が、そのまま成り立つ | ランナーの画面と入力のソケット、音を、ユーザーの間で渡す細工が要る | B と同じ |
| Mac | 専用ユーザーの GUI のセッションが要る | 別のユーザーの GUI のセッションでアプリを起動する、公開の方法が限られる | B と同じ |

## 提案

**A にする。**

1. **ホストの役は、専用ユーザーでだけ動かす。** ホストの役とは、アプリの起動と入力を受け付けるエージェント、ランナー、起動されたアプリ、音の取り込み、herdr とコーディングエージェントである。
2. **ふだんのユーザーで動かすのは、クライアントの役だけにする。** 窓を出す、入力を送る、音を鳴らす（音の出口）、一覧を見る。ふだんのユーザーで動くエージェントには、ランナーを設定しない。ADR 0010 の決まりで、設定のないエージェントは、起動の頼みを断る。
3. **端末の身元は、ユーザーごとに持つ。** 専用ユーザーのエージェントは、自分の鍵とペアリングの一覧を持つ。1台の PC が両方の役を持つときは、端末が2つに見える。
4. **専用ユーザーに、管理者の権限を与えない。** `sudo` を使えるグループ、管理者のグループ、Docker のグループに入れない。インストールのように root が要る作業は、その PC の管理者が、内容を見てから行う（R-05）。
5. **どちらの向きにも、OS の権限では読めないようにする。** 専用ユーザーは、ふだんのホームを読めない。ふだんのユーザーも、領域を直接は読まない。行き来は、人が Istesso の操作（[ADR 0013](0013-unified-storage.md) の取得と受け渡し）で行う。
6. **ふだんの側を、変えない。** 隔てるために、ふだんのユーザーのファイルや権限を変えることを、仕組みはしない。変えるしかないと分かったときは、人に尋ねる。
7. **導入は、インストーラーが行う。** 使う人がするのは、管理者のパスワードを1回入れることだけにする。同じ名前のユーザーがすでにあれば、止まる。使い回さない。
8. **取り除くときに、専用ユーザーとそのホームを消さない。** 消すのは、人が自分で行う。

理由：

- **Istesso 自身がまちがえても、ふだんのファイルに届かない。** ホストの役が丸ごと専用ユーザーで動くので、壊れる範囲が、専用ユーザーの中で止まる。B では、エージェントがふだんのユーザーで動くので、そうならない。ねらい（事故を避ける）に合うのは、A である。この選び方は、ねらいから決めた。
- **動いているあいだに、特権が要らない。** root で動くプログラムも、sudo の規則も置かない。導入が軽くなる（導入のかんたんさ）。
- **境目が1つで、説明しやすい。** 「専用ユーザーの中で起きたことは、専用ユーザーの中で終わる」。
- 鍵に手が届くことは、ADR 0003 がすでに「結果」として認めている。下の「鍵に手が届くことへの備え」で、広がりを抑える。

### Linux での作り方

| 項目 | 内容 |
|---|---|
| ユーザー | 専用ユーザーを1つ作る。ログインの画面には出さない。パスワードでのログインはさせない。ホームが、隔離領域になる |
| ふだんのホーム | Ubuntu の新しい版（21.04 以降という理解）では、ホームは作られたときから、ほかのユーザーが読めない（750）。古い版から上げてきた PC では、読めることがある。実機で確かめる |
| 動かし方 | 専用ユーザーの常駐サービスとして動かす。誰もデスクトップにログインしていなくても動く。アプリの絵は、専用ユーザーのランナーの中の仮想コンポジターに出るので、デスクトップの画面とは関わらない（ADR 0009） |
| GPU | 専用ユーザーが、GPU のレンダーノードを開けること。Ubuntu では、そのためのグループ（`render`、`video`）に入れる。どれが要るかは、実機で確かめる |
| 音 | アプリの音は、専用ユーザーのサウンドサーバー（PipeWire）に出て、そこから取り込む。スピーカーや DAC は、デスクトップにログインしている人のものなので、音の出口の役は、ふだんのユーザーの側で動かす |

### macOS での作り方

| 項目 | 内容 |
|---|---|
| ユーザー | 管理者でない、標準のユーザーを1つ作る。ホームが、隔離領域になる |
| ふだんのホーム | Air（macOS 26.5.1）で見ると、ホームは 750 で、グループは `staff` だった。ふつうに作ったユーザーは `staff` に入るはずなので、**専用ユーザーは、ふだんのホームの直下を一覧できる。** 直下に置いたファイルのうち、誰でも読める権限のもの（シェルや Git の設定など）は、中身も読める。書類、デスクトップ、ダウンロード、ライブラリは 700 で、読めない。塞ぎ方は2つある。**専用ユーザーを、`staff` でないグループで作る**（ふだんの側を変えない。ユーザーを作る道具に、グループを指定する口がある）。または、ふだんのホームを 700 にする（ふだんの側を変える）。上の 6 に従って、前のほうを先に試す |
| 動かし方 | GUI のアプリは、そのユーザーがログインしているセッションの中でしか動かない。**ホスト専用の Mac（Mac mini、Mac Studio）は、専用ユーザーでログインして使う。** 取り込み、入力、音の許可も、そのセッションのプログラムに出す |
| 人がふだん使う Mac | **ホストにしない（クライアントだけ）。** ふだんのユーザーがログインしている裏で、専用ユーザーのセッションから配信できるかが、分かっていない。Mac のセッションには、カーソルとフォーカスが1つしかない（[m4-plan.md](../m4-plan.md) の 4.2）。M4 で確かめられたら、見直す |
| 再起動のあと | ホスト専用の Mac は、誰かが専用ユーザーでログインするまで、ホストとして動かない。自動ログインは、FileVault を入れていると使えない（Air で確かめた）。どうするかは、人が決める（m4-plan.md の 6. の 5） |
| アプリ | `/Applications` に入れたアプリは、専用ユーザーからも起動できる。設定、ログインの状態、ライセンスの認証は、ユーザーごとなので、専用ユーザーの中でやり直すことになる |

### 権限の要るものと、その理由

どれも、導入のときに1回だけである。動いているあいだには、要らない。今週は、どれも実行しない。

| OS | 何を | 要る権限 | 理由 |
|---|---|---|---|
| Linux | 専用ユーザーを作る | root | 隔離の土台（ADR 0003）。OS の権限で区切るには、別のユーザーが要る |
| Linux | 専用ユーザーを、GPU を使えるグループに入れる | root | アプリの絵を GPU で描き、GPU で圧縮する（R-02 のハードウェアエンコード）。デスクトップにログインしていないユーザーには、GPU を開く権限が自動では付かない |
| Linux | 専用ユーザーのサービスを、ログインなしで動かす設定（linger） | root | 窓は、ホストの側で生き続ける（R-03）。誰もログインしていなくても、ホストとして動かす |
| Linux | サービスの登録 | 専用ユーザーの中に置くなら、要らない | 常駐（M9 のインストーラーと合わせる） |
| Linux | ふだんのホームが、ほかのユーザーから読める権限だったとき | 仕組みは、変えない。人に尋ねる（直すなら、本人。root は要らない） | ADR 0003 の「他のユーザーから読めない権限にしておく」。すでに読めないなら、何もしない |
| macOS | 専用ユーザーを、`staff` でないグループで作る | 管理者 | Linux と同じ。グループを分けるのは、ふだんのホームの直下を、ふだんの側を変えずに読めなくするため |
| macOS | 上で足りなかったときだけ：ふだんのホームを 700 にする | 本人（管理者は要らない）。人に尋ねてから | いまの権限（750）では、`staff` のユーザーが直下を一覧できる |
| macOS | 画面収録、アクセシビリティ、音の録音の許可 | 管理者の認証と、専用ユーザーのセッションでの操作 | Mac ホストの取り込み、入力、音。理由は、M4 の ADR に書く（m4-plan.md の 6. の 1） |
| macOS | 自動ログイン（採るなら） | 管理者。FileVault を切ることになる | 再起動のあと、人がいなくてもホストに戻る（R-03）。安全を下げるので、人が決める |
| macOS | サービスの登録 | 専用ユーザーの中に置くなら、要らない | 常駐（M9） |

置かないもの：root で動き続けるプログラム、パスワードなしの `sudo` の規則、ユーザーを切り替えるための特権つきのプログラム。

### 二重の柵

R-07 は、ツールの側のサンドボックスを、二重の柵として使うと決めている。土台は OS の権限に置く（ADR 0003）。

- コーディングエージェントの設定のひな形を、専用ユーザーのホームに置く。読める範囲を、領域の中に絞る。
- ひな形では、Istesso 自身の設定の場所（端末の鍵、ペアリングの一覧）を読めなくする。
- ひな形は、試験用のフォルダーの中で、権限なしで試せる（[m5-plan.md](../m5-plan.md) の手順 2）。

### 鍵に手が届くことへの備え

A では、専用ユーザーで動くアプリとコーディングエージェントが、その端末の鍵を読める。鍵を読まれると、その端末のふりをして、ペアリングした相手につなげる。広がりを、次のように抑える。

- 相手の PC でも、ホストの役は専用ユーザーで動く。つながれて届くのは、相手の専用ユーザーの中までである。
- ふだんのユーザーで動くエージェントは、起動も入力も受け付けない（上の 2）。つながれても、役割表とアプリ一覧と負荷しか見せない。
- インストール、USB、音、ファイルの権限は、ホストどうしでは、要るものだけを与える。
- 二重の柵で、鍵の場所を読めなくする。

**C に移るとき：** ホストどうしで、インストールや USB の権限を与え合う使い方が要ると分かったとき。または、ほかの人の端末とペアリングするようになったとき。そのときは、鍵を持つ側を別のユーザーに分ける。

## 専用ユーザーでも、隔てられないもの

専用ユーザーは、サンドボックスではない。次のものは、隔てない。

| もの | 内容 |
|---|---|
| 同じ PC のネットワーク | 同じ PC の中で待ち受けているもの（開発用のサーバー、データベース、管理画面）には、どのユーザーからもつなげる。LAN のほかの機器にも、つなげる |
| 誰でも読める場所 | Linux の `/tmp`、macOS の `/Users/Shared`、権限をゆるく付けた外付けのディスク。ふだんのユーザーがそこに置いたファイルは、読める |
| プロセスの一覧 | ほかのユーザーのプロセスの名前と引数は、見える。引数に書いた秘密は、漏れる |
| 資源の使い切り | CPU、メモリ、ディスクを使い切ることは、防がない |
| OS の不具合を突く攻撃 | 防がない |

## 採用されたら直すもの

- [ADR 0003](0003-isolation.md) の「結果」の最後の行（Mac の GUI アプリの配信は M4 で検証する）に、この文書への参照を足す。
- [requirements.md](../requirements.md) の R-07 に、「ホストの役は専用ユーザーで動かす」を足す。「3. 想定する環境」の MacBook Air の行（ホストにしない）は、M4 で裏のセッションを確かめたあと、人に尋ねてから直す。
- ADR 0010（`m3-app-manager` ブランチ）の「専用ユーザーでの起動」の行。プロセスの境目に足すものは、ない（エージェントごと、専用ユーザーで動くため）。
- `istesso doctor` に、隔離の状態（専用ユーザーで動いているか、ふだんのホームが読めないか、管理者の権限を持っていないか）を出す。

## 既知の不足

- **この文書は、実機で確かめていない。** Air で読むだけの調査をした以外は、文書と、いまのコードから書いた。Ubuntu のホストは、見ていない。
- Mac で、ふつうに作ったユーザーが `staff` に入るかどうかと、`staff` に入っていないユーザーでアプリがふつうに動くかどうかは、作ってみて確かめる。
- ホストで、ふだんのユーザーが使っていたアプリの設定とデータは、専用ユーザーからは見えない。Istesso から開いたアプリは、まっさらな状態で始まる。使う人には、消えたように見える。移す道具は作らない（ふだんのファイルに、仕組みが触れることになる）。画面で、理由を伝える。移したいものは、人が、名指しのコピーで移す。
- 1台の PC が両方の役を持つとき、エージェントが2つ動く。待ち受けるポート（いまは、どちらも 47801）と、一覧での見え方を、実装の前に決める。
- 専用ユーザーの中のアプリどうしは、隔てない。あるアプリが、別のアプリのファイルを読める。
- 人が、専用ユーザーの中のファイルを、ふだんのアプリで直接開くことはできない。取得して、写しを開く。
- Mac で、人がふだん使う Mac をホストにできない。要件の「任意参加」の MacBook Air は、クライアントとして参加する形になる。
- Windows は、扱っていない。
