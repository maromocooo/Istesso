# ADR 0008：遅延の計測に、Mac の画面収録を使う

- 状態：採用
- 日付：2026-11-16
- 更新：2026-11-16（色を確かめるために、テスト用の窓 2 枚を取り込む使い方を足した）

## 背景

M1 は、追加遅延の数値と「当てるテスト」で合否が決まる（[ADR 0002](0002-latency-first.md)、[m1-plan.md](../m1-plan.md)）。どちらも、手元で動く窓と中継した窓の**差**を見ている。

この差を測る手段として、計画にはカメラしかなかった。240 fps で撮り、人がコマを数える方法で、1回の計測は 20 回程度にとどまる。手元にあるカメラは最高 60 fps（1コマ 16.7 ms）で、測りたい差（10〜20 ms）には粗い。

比較対象の配信ソフト（Sunshine と Moonlight）は、コードを読まない決まりなので、中で表示の時刻を記録させることもできない。外から、同じ方法で何度でも測れる手段が要る。

画面収録は強い許可で、[AGENTS.md](../../AGENTS.md) は、これを使う処理を増やすときに理由を残すよう求めている。

## 決定

計測の道具 `istesso-screen-probe`（`macos/screen-probe`）が、ScreenCaptureKit で Mac の画面を読む。

- **読むのは、2つの窓の中央の明るさだけ。** 手元のテストアプリの窓と、中継したテストアプリを映している窓について、灰色が切り替わった最初の画面更新の時刻を記録する。画面は 4 分の 1 に縮めて受け取り、その 2 点を見たら捨てる。画像を保存しないし、どこにも送らない。
- **計測のときだけ動かす。** 人かエージェントが計測のために起動し、決めた回数の入力を送り終えたら終わる。常駐しない。
- **製品には入れない。** クライアントにもホストにも組み込まない。配布物にも含めない。
- **許可は、道具を起動したアプリ（ターミナル）のものを使う。** 道具だけに許可を出す形にするには、署名した `.app` にする必要がある。ビルドのたびに許可を取り直すことになるので、そうしない。許可がないときは、道具は何も読まずに、許可の場所を案内して終わる。

入力は、手元とホストの両方のテストアプリへ、同じ瞬間に合成の入力（UDP）を送る（[measurements/README.md](../measurements/README.md)）。実際のキー入力を注入する方法は採らない。アクセシビリティの許可がもう1つ要るためである。

## 追加：色を確かめるための、窓の取り込み（2026-11-16）

中継した絵が、Mac の画面で手元の窓と同じ色に出ているかは、ホストでは分からない（[記録](../measurements/2026-11-16-quality.md)）。そこで、同じ許可を使って、もう 1 つの読み方をする。

- **取り込むのは、テストアプリの窓と、それを中継している窓の 2 枚だけ。** macOS の `screencapture` に窓の番号を渡して、その窓の中身だけを取り込む（`screencapture -l`）。画面全体や、ほかの窓は取り込まない。
- **映っているのは、テストアプリの絵だけ。** どの PC でも同じ、作りものの文字である。
- **画像は、計測の作業用の置き場所に保存する。** 記録に載せるのは、その一部（文字が数行ぶん）だけで、どこにも送らない。
- **計測のときだけ行う。** 文字を止めた絵を 10 秒ほど出し、1 回ずつ取り込んで終わる。製品には入れない。

## 測れるものと、測れないもの

| | 内容 |
|---|---|
| 測れる | 入力を送り出してから、それぞれの窓が画面に出るまでの時間。中継した窓が、手元の窓より画面更新の何回ぶん遅れるか |
| 測れない | ディスプレイのパネルの遅れと、入力機器の遅れ。どちらの窓にも同じだけかかるので、差には現れない |
| 測れない | 配信ソフト自身の入力の経路。合成の入力は、その経路を通らない |

時刻の刻みは、画面更新 1 回ぶん（85 Hz で 11.8 ms）である。1回ごとの値はこの刻みに丸まるが、入力の間隔をばらつかせて数百回測るので、分布は読める。

道具の検査として、手元のテストアプリを 2 つ並べて測ると、120 回すべてが同じ画面更新で切り替わり、差は 0 だった。記録された時刻は、ディスプレイの更新（84.96 Hz）にそろっていた。

## 検討したほかの方法

| 方法 | 採らなかった理由 |
|---|---|
| カメラだけで測る（計画どおり） | 人手がかかり、回数が少ない。節目の確認としては残す |
| ホストにつないだ Web カメラで録画し、自動で数える | 60 fps しか出ない。カメラを画面に向ける作業も人に残る |
| 実際のキー入力を注入する | アクセシビリティの許可が増える。差を測るには、合成の入力で足りる |
| クライアントの中で表示の時刻を記録する | 比較対象の配信ソフトには使えない。自前の受信側（手順 3 以降）では、これも行う |

## 結果

- 手元の窓との差を、500 回単位で、人手なしに測れる。カメラでの確認は、節目に 1 回、240 fps で行う。
- Swift のコードがリポジトリに入る（`macos/`）。使うのは OS の機能だけで、依存は増えない。
- 画面収録の許可を持つターミナルからは、ほかのプログラムも画面を読める。これは道具を入れる前からの状態で、道具が広げるものではない。
