# ADR 0009：ホストのコンポジターは、既製のもの（MIT）を直して使うところから始める

- 状態：採用（2026-11-16。下の「提案」を採った。あわせて、直した分は小さく保ち、元のプロジェクトに提案できる形にする、と決めた）
- 日付：2026-11-16

## 背景

Linux のアプリを中継するには、そのアプリの絵を受け取る専用のコンポジター（Wayland）が要る。手順 3 では、既製の gst-wayland-display（MIT）を、コードを変えずに使うところから始めた（[m1-plan.md](../m1-plan.md)）。測ってみると、遅延のいちばん大きい部分は、このコンポジターの**フレームの出し方**にあった。

- 既製のものは、決まった間隔（85 fps なら 11.8 ms）でしか描かない。アプリが絵を確定してから、平均 5.9 ms 待つ（[記録](../measurements/2026-11-16-step3-breakdown.md)）。
- 「アプリが確定したら描く。ただし、どの 1 秒にも 85 枚まで」という形に、199 行の修正ファイルで直した。3440×1440 の動く絵で、コンポジターの区間は 14.8 ms から 8.7 ms になり、テストアプリを GPU で描く形にすると 1.9 ms になった（[記録](../measurements/2026-11-16-step3-moving-picture.md)、[記録](../measurements/2026-11-16-step3-85fps-gpu-app.md)）。
- フレームを GPU の外に出さない経路（CUDA）は、既製のものにあった。ビルドのときに有効にするだけで動いた（[記録](../measurements/2026-11-16-step3-gpu-frames.md)）。

つまり、遅延を決める部分はコンポジターの中にあり、そこを自分たちで決められることが要る。手順 4（自前の実装への置き換え）で、コンポジターを一から作るか、既製のものを取り込んで（fork して）直すかを、ここで比べる。

## 既製のものの中身（2026-11-16 に調べた）

固定しているコミット（`1301f86`、2026-05-01）について。

| 項目 | 内容 |
|---|---|
| ライセンス | MIT。土台の Smithay（Wayland コンポジターを作るためのライブラリ）も MIT |
| 大きさ | Rust で約 8,400 行。コンポジターの本体（`wayland-display-core`）が約 6,800 行（うちテストが約 1,350 行、CUDA との受け渡しが約 1,080 行）、GStreamer のプラグインが約 1,300 行 |
| 土台 | Smithay 0.7.0 を、games-on-whales の複製から、コミットを指定して取り込んでいる（crates.io からではない） |
| 対応しているもの | xdg-shell、linux-dmabuf、wl_shm、wl_drm、viewporter、presentation-time、ポインターの相対移動と拘束、クリップボード（data_device）、出力の大きさの変更 |
| 入力 | コンポジターに直接渡せる（キー、ポインターの移動とボタンとホイール、タッチ）。実機の入力デバイス（libinput）も使える |
| フレームの出力 | GStreamer のバッファー。メインメモリー、DMABuf、CUDA のメモリー |
| 窓の扱い | 出力は 1 つ。中のアプリの窓を、その 1 枚の絵に合成する。要件（R-02）の「1 アプリ = 1 仮想ディスプレイ = 手元の 1 窓」と同じ形 |
| ないもの | X11 のアプリ（XWayland）、日本語入力（text-input）、小数の拡大率、アプリの窓を 1 枚ずつ別の絵にして出すこと |
| 依存のライセンス | このリポジトリの `deny.toml` で検査して、すべて通る（`cargo deny check licenses`）。取得元の検査は、Smithay が git から来るので、許可を 1 行足す必要がある |

上流のいま（2026-11-11 まで）：

- 固定したコミットのあとに、205 のコミットがある。中心は、Vulkan で圧縮する経路（NVIDIA 以外の GPU でも動く）と、新しい Smithay への移行。
- いまの版は、GStreamer 1.28 以上と libwayland 1.23 以上を求める。Ubuntu 24.04 に入るのは 1.24 と 1.22 なので、**上流の最新は、この OS ではそのまま動かない**（[m1-plan.md](../m1-plan.md) の手順 3）。

## 要るもの

「関門」は M1 の判定（合格ラインと、当てるテスト）のこと。

| 要るもの | 関門までに要るか | 既製のもの（`1301f86`）では |
|---|---|---|
| アプリが確定したら描く。毎秒 85 枚まで | 要る（数値の中心） | ない。199 行の修正で動かしてある（`scripts/patches/`） |
| フレームを GPU の外に出さずにエンコーダーへ渡す | 要る | ある（`cuda` を有効にしてビルド） |
| 入力を、コンポジターからアプリへ渡す | 要る。いまの計測は、入力を UDP でテストアプリに直接渡していて、この経路を通っていない | 受け口はある。ネットワークから来た入力をつなぐ部分を書く |
| カーソルを絵に入れず、形と位置を別に伝える（クライアントが手元で描く。R-02） | 当てるテストでマウスを使うなら要る | ない。いまは絵に描き込む。**2 つ目の修正で入れた（2026-11-17）**：要素のプロパティ `cursor-messages`（既定は切）。入れると、カーソルを絵に描かず、形（画像、ホットスポット、拡大率、隠れているか）を、変わるたびにアプリケーションメッセージ（`wayland.cursor`）で伝える。位置は伝えない（クライアントが、自分のポインターの位置を使う） |
| アプリの窓 1 枚を、出力いっぱいに出す。クライアントの窓の大きさに合わせて変える | 要る | ある |
| フレームコールバックを、次に描く直前に送る | 要らない。あとで効く（下の「あとで」） | ない |
| 窓が 1 枚で出力を覆うとき、合成せずにそのまま渡す | 要らない | ない |
| アプリが開いた窓を、1 枚ずつ別の絵にして出す | 要らない。要件にもない（R-02 は、1 アプリを 1 つの仮想ディスプレイにして、手元の窓 1 枚に出す） | ない。作りが違う |
| X11 のアプリ、日本語入力、小数の拡大率、HDR | 要らない | ない |

エンコーダーと経路の側で要るもの（キーフレームを求められたときだけ出す、4:4:4、色の伝え方、暗号化と認証）は、コンポジターの選び方とは別に決まる（[画質の記録](../measurements/2026-11-16-quality.md)）。

## 比べる案

- **A：一から作る。** Smithay の上に、自分たちのコンポジターを書く。Wayland のプロトコルそのものまで自分で書く案は、得るものがないので考えない。
- **B：取り込んで直す。** `wayland-display-core` を `1301f86` から取り込み（fork）、要るところを直す。上流には追従しない。
- **C：いまのまま、修正のファイルを当て続ける。** 比べるための基準。

| 観点 | A：一から作る | B：取り込んで直す | C：修正を当て続ける |
|---|---|---|---|
| 関門までの作業（見積もり。測った値ではない） | 3〜5 週。同じところまで来るのに、EGL の初期化、DMABuf、CUDA との受け渡し、フォーカス、ポインターの拘束を書き直す | 約 1 週。入力をつなぐ、カーソルを外に出す、いまの修正にテストを付ける | 数日。ただし入力とカーソルは、修正のファイルでは大きくなりすぎる |
| 遅延 | B と同じにできる。フレームの出し方は、どちらでも自分で決める | 測ってある（コンポジターの区間 1.9 ms） | B と同じ |
| 関門を危うくするもの | NVIDIA の EGL と CUDA まわりで詰まること。既製のものが解いた問題を、もう 1 度解く | 取り込んだコードの不具合を、自分たちで直すことになる | 上流が進むと、修正が当たらなくなる（もう当たらない：上流の最新は、この OS で動かない） |
| GStreamer への依存 | なくせる | 残る（出力が GStreamer のバッファー）。外すには、出力の型を替える | 残る |
| 要件にない形（アプリの窓を 1 枚ずつ別の絵に）が、あとで欲しくなったとき | 最初からその形に作れる。ただし、要るかどうか分からないうちに形を決めることになる | 作り替えが要る。そのときに A へ移ってもよい | 作り替えが要る |
| 保守 | 全部が自分たちのコード | 全部が自分たちのコードになる。上流の修正は、要るものだけ手で移す | 上流に頼る |
| ライセンス | MIT の Smithay に依存 | MIT。著作権の表示を残す | 変えない |
| 権限 | root は要らない。GPU のレンダーノードを開けること | 同じ | 同じ |

## 提案

**B で関門まで進む。A に移るのは、B の作りでは入らないものが要ると分かったときにする。**

理由：

1. **関門が問うのは遅延で、コンポジターの作りではない。** 遅延を決める部分（フレームの出し方）は、B でもう自分たちで決めていて、測ってある。A は、関門までの数値を良くしない。
2. **関門は落ちるかもしれない。** 落ちたら構成を見直す決まりである（[ADR 0002](0002-latency-first.md)）。その前に、数週間ぶんのコンポジターを書くのは順番が逆になる。
3. **A でしか得られないものが、いまの要件にない。** 要件（R-02）は「1 アプリ = 1 仮想ディスプレイ = 手元の 1 窓」で、既製のものの作り（出力 1 つに、アプリの窓を合成する）と同じである。アプリの窓を 1 枚ずつ別の絵にする形は、A なら最初から作れるが、要るかどうかを決める材料（複数の窓やポップアップを使ってみた結果）が、まだない。
4. **B で書くものは、A に移っても残る。** フレームの出し方の決まり、入力のつなぎ方、カーソルの伝え方、計測は、コンポジターを替えてもそのまま使う。B のコンポジターは、A が下回ってはいけない基準にもなる。

B の進め方（採用のときに決めた形）：

- **直した分は小さく保ち、元のプロジェクトに提案できる形にする。** 元のコミット（`1301f86`）に、修正を 1 つずつ重ねる。1 つの修正は 1 つのことだけをし、既定では元の動きのままにして、設定で切り替える。元のプロジェクトにテストがあるところには、テストを付ける。作りを変えたり、書き直したりはしない。
- 修正は、差分のファイルとしてこのリポジトリに置く（`scripts/patches/`）。元のコードを丸ごと写して持つことはしない。元のプロジェクトの複製（fork）を公開の場所に作って、そこから提案するかどうかは、人が決める。
- 元のプロジェクトのいまの版は、新しい GStreamer を求める（上の表）。提案するときは、修正をその版に移す必要がある。こちらで動かすのは、`1301f86` に重ねたものである。
- 本体（`wayland-display-core`）を、ホストのエージェント（`istesso-media-linux`）から使う。圧縮は、関門までは GStreamer の要素（`nvcudah265enc`）を使い続ける。測ってある経路を変えないため。
- 入力は、コンポジターに直接渡す。仮想の入力デバイス（uinput）は使わない。権限が 1 つ減る。ゲームパッドが要るようになったら、そのときに考える。
- 依存を足すので、`deny.toml` に Smithay の取得元を登録し、`components.md` に理由を書く（AGENTS.md）。

関門までに要る分を、先にする順（コンポジターに関わるもの。手順 4 の全体の順は [m1-plan.md](../m1-plan.md)）：

1. いまの修正（確定したら描く、毎秒 85 枚まで）を、提案できる形に直す。既定では元の動きのままにして、設定で切り替える。描き始めた回数を数えて、記録に出せるようにする（判定の決まりは、描き始めが毎秒 85 回まで）。テストを付ける。直す前と同じ数値が出ることを測る。
   - **済み（2026-11-16、[記録](../measurements/2026-11-16-step3-pacing.md)）。** 要素のプロパティ `render-on-commit` で入れる（既定は切）。決まりは 1 つのファイル（`comp/pacing.rs`）にまとめ、テストを 16 本付けた。描き始めた回数と、どの 1 秒にも何回までだったかを、配信の終わりにログへ出す。
   - 作り直しの途中で、**それまでの修正が、フレームコールバックで描くアプリでは壊れる**ことが分かった（フレームが固まって出たあと、最長 0.6 秒止まる）。描くたびに「描いてよい」と知らせていたためである。直した形では、知らせをフレームとは別の拍で出す（確定したときに、フレームの間隔に 1 回まで）。
   - 数値：85 Hz・有線・3440×1440 で、差の中央値は 9.75 ms（それまでの修正は 10.43 ms。違いは、ほぼ手元の窓の値）。コンポジターの区間は、平均 1.68 ms から 1.32 ms。コールバックで描くアプリの絵は、確定の 1.9 ms あとに出る（元の動きでは 11.6 ms）。
2. 入力を、コンポジターからアプリへ渡す。テストアプリが、キーとして受け取る。計測も、この経路を通す。
3. カーソルを絵から外し、クライアントで描く。当てるテストの前に。
   - **コンポジターの側は、済み（2026-11-17）。** 1 つ目の修正の上に重ねる、2 つ目の修正のファイル（`scripts/patches/gst-wayland-display-cursor-messages.patch`）。決まりは 1 つのファイル（`comp/cursor.rs`）にまとめ、テストを 14 本付けた（うち 7 本は、本物の Wayland クライアントがカーソルを設定する）。1 つ目の修正のファイルは、変えていない。
   - アプリが渡すカーソルの画像は、信頼しない。共有メモリーのバッファー（ARGB8888 か XRGB8888）で、位置と行の長さと大きさがバッファーの実際の長さに収まり、辺が 256 ピクセルまでで、ホットスポットが画像の中にあるときだけ読む。それ以外は、「画像のないカーソル」として伝える。
   - カーソルを絵から外すと、ポインターが動いても絵は変わらない。「確定したら描く」の決まりでは、ポインターの動きでフレームを出さなくなる。
   - クライアントへの運び方は [ADR 0015](0015-media-transport.md) の「カーソル」。

4. アプリの窓に、閉じるよう頼む。窓がいくつあるかを知らせる（アプリマネージャーの `close` と `empty`。ADR 0010、`m3-app-manager` ブランチ）。
   - **コンポジターの側は、済み（2026-11-17）。** 3 つ目の修正のファイル（`scripts/patches/gst-wayland-display-windows.patch`。前の 2 つの上に重ねる。前の 2 つは、変えていない）。決まりは 1 つのファイル（`comp/windows.rs`）にまとめ、テストを 5 本付けた（うち 4 本は、本物の Wayland クライアント）。
   - **閉じるよう頼む**：要素が、入力のイベントと同じ形（上流へのカスタムイベント）で、`CloseWindows` という名前のイベントを受け取る。コンポジターは、すべてのトップレベルに `xdg_toplevel.close` を送る。ウィンドウマネージャーの「閉じる」ボタンと同じである。**力ずくでは、何も閉じない。** 保存していないものがあるアプリは、尋ねて、残る。
   - **窓の数を知らせる**：要素のプロパティ `window-messages`（既定は切）を入れると、トップレベルの数が変わるたびに、アプリケーションメッセージ `wayland.windows`（`count`）を出す。0 は、最後の窓が閉じたことを表す。ポップアップとカーソルは、数えない。
   - パイプライン（`scripts/m1-step3-host.py`）は、標準入力の `close` で頼み、標準出力に `{"istesso":"close","asked":true}` と答える。窓の数は、頼まれなくても `{"istesso":"windows","count":N}` で知らせ、最後の窓が閉じたら `{"istesso":"empty"}` と言う（語と行の全体は [ADR 0015](0015-media-transport.md) の「止める、戻す、離す」）。
   - 見つかった不足「アプリが尋ねる窓（「保存しますか」）が、絵に出ない」は、次の 5 で直した。
5. アプリがあとから開く窓（尋ねる窓、ファイルを選ぶ窓、2 枚目の窓）を、絵に出す。
   - **済み（2026-11-17、[記録](../measurements/2026-11-17-dialog-windows.md)）。** 4 つ目の修正のファイル（`scripts/patches/gst-wayland-display-dialogs.patch`。前の 3 つの上に重ねる。前の 3 つは、変えていない）。置く場所の決まりは、`comp/windows.rs` の関数 1 つ（`place`）。テストを 8 本付けた（うち 6 本は、本物の Wayland クライアントが、1 回だけ描く 2 枚目の窓を開く）。
   - **原因**：コンポジターは、新しい窓を、最初の絵が届いた確定の処理の中で絵に入れるが、窓の大きさを調べ直すのは、その処理の始めにすでに絵に入っていた窓だけだった。窓は、大きさが 0×0 のまま絵に入り、次の確定で初めて大きさが分かる。1 回描いて人の答えを待つ窓は、描かれず、ポインターも届かない。それでも、キーボードは持っていた。
   - **決めたこと**：
     - 大きさは、最初の絵が届いた確定で調べる。
     - 親のあるトップレベル（`xdg_toplevel.set_parent`）は、全画面にしない。使える広さだけを伝え、望む大きさのまま、親の中央に、出力の中に収めて置く。出力より大きければ、左上の隅から置く（収まらないぶんは、見えない）。
     - 親のないトップレベルは、これまでどおり（出力と同じ大きさで全画面と伝え、左上の隅に、いちばん上に置く）。
     - 窓が閉じたら、すぐに絵から外し、キーボードを、いちばん上に残った窓へ渡す。
     - ポインターのイベントは、ポインターがいまあるところの窓へ送る（これまでは、動く前にあったところの窓へ送っていた）。窓が、ほかの窓の上に開いたとき、閉じたときは、ポインターが動いていなくても、調べ直す。
     - 窓をクリックしても、その窓を親とする窓は、前に残す。
   - **プロパティは付けず、いつも入れる。** 直しているのは不具合で、窓が 1 枚のアプリでは、何も変わらない。ほかの 3 つの修正（頼まなければ何も起きない）とは、ここが違う。
   - **ふつうの窓を 2 枚開くアプリ**では、2 枚とも出力と同じ大きさで、1 枚の絵に重なる（あとの窓が上）。これは、前と同じである。「1 つのアプリの複数の窓を、クライアントの別々の窓にする」（下の「あとで」）への道は、ふさいでいない：絵の作り方には触れておらず、窓の数の知らせ（`wayland.windows`）に、窓ごとの場所・大きさ・親を載せれば、分けて出す材料になる。
   - **分かっている不足**：窓を置くのは、1 回だけ（あとで大きさが変わっても、置き直さない）。尋ねる窓が出ているあいだに親をクリックすると、キーボードは親へ移る（窓は、前に残る）。サンドボックスに入ったアプリが、デスクトップのポータルに頼んで開くファイルの窓は、このコンポジターの外のプロセスが出すので、絵には入らない（確かめていない）。
6. アプリが、カーソルの形を名前で言えるようにする（cursor-shape の口、`wp_cursor_shape_manager_v1`。[ADR 0019](0019-own-host.md) の「カーソルの名前」）。
   - **コンポジターの側は、済み（2026-11-17）。** 5 つ目の修正のファイル（`scripts/patches/gst-wayland-display-cursor-shape.patch`。前の 4 つの上に重ねる。前の 4 つは、変えていない）。テストを 4 本付けた（どれも、本物の Wayland クライアントが、形を名前で言う）。
   - **口は、カーソルを絵から外しているあいだだけ開ける。** コンポジターの状態に、Smithay の cursor-shape の管理役を、「ないこともある」項目として足した。作って、口を知らせるのは、カーソルの知らせ先が、初めて付けられたとき（プロパティ `cursor-messages` を入れたとき）だけである。入れなければ、口はなく、何も変わらない。カーソルを絵の中に描くコンポジターは、名前の形を描き分けられない（どの名前にも、同じ画像しか持っていない）ので、そこで口を開けると、どのカーソルも矢印になる。
   - 一度開けた口は、`cursor-messages` を切っても、残す（クライアントは、つかんだ口を持ち続ける）。そのとき、名前の形は、これまでの名前つきのカーソルと同じく、内蔵の画像で絵に描かれる。
   - 名前は、2 つ目の修正の知らせ（`wayland.cursor` の `named` と `name`）に、そのまま載る。名前は、口と同じ（CSS の名前）。
   - **触っていないもの**：描く拍、描くこと、フレームの受け渡し、入力、要素。足したのは、状態の項目 1 つ、知らせ先を付ける関数の 3 行、口の受け口のファイル 1 つ（`wayland/handlers/cursor_shape.rs`）、テスト。
   - プロパティは付けていない（`cursor-messages` に従う）。もとのプロジェクトは、MIT ライセンス。

エンコーダーと経路の側（キーフレームを求められたときだけ出す、色を間引かずに送る、暗号化と認証）は、これと並べて進める。コンポジターを替えずに済む。

あとで（関門を通ってから、効果を測って決める）：

- **コールバックで描くアプリを、Mac まで通して測る。** 作り直した修正では、「描いてよい」の知らせを別の拍で出すので、こういうアプリの絵も、確定したらすぐ出る（上の 1）。残っているのは、アプリの側の待ちである。描いてから、知らされるのを待って渡すアプリ（垂直同期つきの OpenGL）は、入力から確定までに、フレーム 2.5 枚ぶん（約 29 ms）かかっていた。手元で動かしても同じ種類の待ちがあるが、体感には入る。テストアプリに、この描き方（`--when-told`）を足したので、判定のあとに参考値を取る。判定に使うテストアプリは、自分のタイマーで描く。
- 窓が 1 枚で出力を覆うとき、合成せずにそのまま渡す（3440×1440 で 1.9 ms かかっている合成を省く）。
- アプリが複数の窓を開いたときの見せ方。使ってみて、いまの形（1 枚の絵に合成）で足りなければ、ここで A に移るかを決める。
- GStreamer を外して、NVENC を直接使う。欠けたときに、キーフレームなしで戻す仕組みが使える。また、1 フレームを GPU の 2 つのエンコーダーに分けて圧縮する機能（split frame encoding。[NVIDIA の説明](https://docs.nvidia.com/video-technologies/video-codec-sdk/12.1/nvenc-application-note/index.html)）を指定できる。GStreamer 1.24 の要素からは指定できない。4:4:4 にすると圧縮が 2.6 ms から 4.1 ms に延びるので（[画質の記録](../measurements/2026-11-16-quality.md)）、これが関門の前に要るかもしれない。3440×1440 で効くかどうかは、確かめていない。

## A を選ぶべきとき

次のどれかが起きたら、関門の前でも A を考え直す。

- 取り込んだコードの不具合で、数値が安定しない。
- 関門までに要るものが、取り込んだコードの作りでは入らないと分かった。
- Ubuntu 24.04 以外のホスト（新しい libwayland）で、取り込んだコードが動かない。

## 結果

- このリポジトリに入るのは、修正の差分だけである。元のコード（MIT、約 6,800 行）は、ビルドのときに元のコミットから取ってくる。
- Linux のホストのビルドに、libwayland、EGL、GBM、GStreamer の開発用のパッケージが要る。CI では、Linux のときだけビルドする。
- [architecture.md](../architecture.md) の「入力」の欄（Linux は uinput）と、[components.md](../components.md) の Wolf の行を、決定に合わせて直した。
- m1-plan.md の手順 3 にあった宿題（古いコミットを使い続けるか、新しい GStreamer を別に用意するか）は、「`1301f86` に小さな修正を重ねて使う。新しい版には、提案するときに移す」で決着する。
