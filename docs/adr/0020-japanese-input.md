# ADR 0020：日本語入力の経路（4 つの案を比べる）

- 状態：提案（決めていない。持ち主への質問は、末尾にある）
- 日付：2026-11-18

## 背景

試用版で、持ち主が Mac を日本語入力にして打ったところ、ホストのアプリには**ローマ字**が届いた。

- クライアントは、キーの**位置**（キーの番号）だけをホストへ送る（[ADR 0007](0007-control-channel.md)）。変換は、Mac の側では起きない。
- ホストのアプリは、アプリごとに、隠れたコンポジター（Wayland）のセッションの中で動く。そのセッションには、入力方式（IME）がない。
- ホストの机のログインには、IBus と Mozc（日本語）が入っている。しかし、アプリのセッションからは使えない。
- コンポジター（gst-wayland-display を元にした、Smithay 製）は、text-input と input-method の口を出していない（[ADR 0009](0009-host-compositor.md) の「ないもの」）。

M3 の受け入れ条件は、「日本語が打てる」こと（[milestones.md](../milestones.md)）。持ち主は、2026-11-18 に、次のように決めている：**M3 では、ホストの側の変換を、セッションの中で使う。Mac の変換で打つ形は、M3 のあとの宿題で、先に設計する。** つまり、案 b と c は、この決定の内側（M3）。案 d は、M3 のあとの形。ここでは、そのための 4 つの案を比べる。

この文書は、すべて「考え」で、実機で動かして確かめた案はまだない。試すまでは、確かではない。

## 案

### a. 机のログインの IBus を使う

アプリのセッションから、ホストの机のログインで動いている IBus に話しかける。

- **見えるもの**：変換の候補の窓は、ホストの**机の画面**に出る。中継している窓の絵には出ない。Mac の前の人からは、候補が見えない。打っているところの下線つきの文字（変換前）も、アプリの側の描き方しだいで、絵に出たり出なかったりする。
- 候補を選ぶには、ホストの机の画面が見えなければならない。ホストの前にだれもいない使い方（遠隔だけの使い方）では、変換が成り立たない。
- 切り替え（英数とかな）：机のログインの設定に従う。持ち主の机の設定に、触れる可能性がある。
- **X11 と Wayland**：アプリが IBus に話しかける道があれば、どちらでも使える。ただし、コンポジターは XWayland をまだ持たない。
- **ホストに要るもの**：机のログインの D-Bus への道。セッションをまたぐので、隔離（[ADR 0003](0003-isolation.md)）と食い違う。
- **遅延**：キーの 1 つごとに、別のプログラムへ往復が入る。ただし、IBus の変換は、どの案でも同じ種類の往復で、差は小さいと考える（測っていない）。
- **安全**：アプリのセッションが、机のログインの入力方式に話しかけられる。入力方式は、打った文字をすべて見る。机のログインとアプリのセッションが、打った文字を互いに見られる形になる。入力の権限を増やすので、理由を残す必要がある（AGENTS.md の 4）。
- **ライセンス**：IBus は LGPL。別のプログラムとして動かすだけで、このリポジトリには入れない。直さない。Mozc は BSD。

### b. コンポジターに text-input-v3 と input-method-v2 を入れ、セッションごとに入力方式のプログラムを動かす

コンポジターが、アプリには text-input-v3 を、入力方式のプログラムには input-method-v2 を出す。入力方式のプログラム（IBus の Wayland 版、または別のもの）を、セッションごとに 1 つ動かす。

- **見えるもの**：候補の窓は、input-method-v2 の「ポップアップ」の面で、コンポジターが絵の中に描く。**中継する絵に出る**。変換中の文字は、アプリが text-input-v3 の preedit で描く。
- **X11 と Wayland**：text-input-v3 に対応する Wayland のアプリ（GTK、Qt の多く）は動く。X11 のアプリ（XWayland）は、この道を通らない。XWayland がまだないので、いまは関係しないが、入れたときは別の道（XIM など）が要る。Firefox が Wayland で動くなら、対象になる。
- **切り替え**：入力方式のプログラムに届くキーで決まる。Mac の「英数」「かな」が、どのキーとして届くかを、決める必要がある。
- **ホストに要るもの**：コンポジターの修正（Smithay にこの部品がある。使い方は、確かめる）。セッションごとの入力方式のプログラムと、設定と学習の置き場所（専用のフォルダー）。
- **遅延**：キーがコンポジターの中で、入力方式へ渡り、結果が戻る。同じホストの中で、手元の通信だけ。ふつうの打鍵の速さでは、気にならないと考える（測っていない）。映像の経路には、手を入れない。
- **安全**：入力方式のプログラムは、打った文字を見る（変換するのだから、必要なこと）。見られる範囲は、そのセッションだけ。コンポジターが渡す相手を、そのセッションの 1 つだけにする。ほかのセッションと机のログインには、見えない。
- **ライセンス**：Smithay は MIT。wayland-protocols は MIT 系（読んで確かめた、ではなく、考え。入れる前に確かめる）。IBus は LGPL で、別のプログラムとして動かすだけ。Mozc は BSD。辞書のデータには別の条件があるものがある（IPAdic 由来など）。どの辞書を入れるかで、確かめる。

### c. セッションごとの IBus（アプリのセッションの中に、自前のバス）

アプリのセッションごとに、IBus のデーモンと Mozc を、そのセッション専用のバスの上で動かす。アプリは、ツールキットの口（GTK の IBus の入力方式モジュールなど）で、そのバスに話しかける。

- **見えるもの**：候補の窓は、そのセッションの中に出る。**中継する絵に出る**。変換中の文字と切り替えは、ふつうの IBus と同じ。
- **X11 と Wayland**：ツールキットの IBus の口を使うので、X11 のアプリも Wayland のアプリも、同じ道で動く（GTK、Qt、そうでないものは別）。コンポジターは直さなくて済むが、候補の窓をどう出すか（IBus の候補の窓は、自分でウィンドウを作る）は、確かめる。Wayland で、入力方式の窓の置き場所を決められるかは、確かめる。
- **確かめること（候補の窓）**：IBus の候補の窓（パネル）は、セッションの中の、別のクライアントの窓になる。試用のコンポジターの窓の決まり（2 枚目の窓は中央に置く、前に出し続ける、親のない窓は積み直す）で、候補の窓が、違う場所に出るか、アプリからキーを取ってしまうかもしれない。実機で見る。
- **ホストに要るもの**：セッションごとに、D-Bus のバス、IBus のデーモン、Mozc を起動するランナー。環境変数（`GTK_IM_MODULE` など）をアプリに渡す。設定と学習の置き場所（専用のフォルダー）。ホストの前にだれもいなくても動く。
- **遅延**：案 b と同じ種類（ホストの中だけ）。プロセスが増えるぶん、起動が重い。測っていない。
- **安全**：バスが、そのセッションの中だけにある。机のログインとは、つながらない。IBus は打った文字を見るが、見られるのはそのセッションだけ。ソケットは、本人だけが開ける場所に置く。
- **ライセンス**：IBus は LGPL。別のプログラムとして動かすだけ。直さない。Mozc は BSD。辞書は案 b と同じ。

### d. Mac で、Mac の入力方式を使って変換し、確定した文字（と変換中の文字）をホストへ送る

Mac の側で、Mac 自身の日本語入力で変換する。確定した文字と、変換中の文字を、ホストへ送る。ホストは、text-input-v3 で、アプリに渡す。

- **見えるもの**：候補の窓は、**Mac の画面**に、Mac の入力方式の見た目で出る。持ち主がふだん使っている変換と、同じ変換結果と、同じ学習。切り替えも、Mac の「英数」「かな」のまま。いちばん自然な形。
- **X11 と Wayland**：ホストの側は、アプリに text-input-v3 で渡す。Wayland のアプリだけ。X11 のアプリ（XWayland）には、別の渡し方（キーの合成、XIM など）が要る。
- **ホストに要るもの**：コンポジターの text-input-v3（アプリの側だけ。input-method は要らない）。入力方式は、ホストに要らない。
- **クライアントに要るもの**：Mac の文字入力の受け口（NSTextInputClient）。窓が、変換中の文字を持てるようにする。
- **新しいメッセージが要る**。確定した文字と、変換中の文字（位置つき）を運ぶ。そのため、**先に ADR 0007（制御チャンネル）を直す**。直すまで、実装しない。
- **遅延**：変換は Mac の中で終わる。ホストへは、確定のときと、変換中の変化のときだけ送る。キー 1 つごとの往復がない。
- **安全**：打った文字そのものを、制御チャンネルで運ぶ。これは新しい種類の情報で、ログと診断に出さない（AGENTS.md の 4）。Mac の入力方式は、Mac の側だけで動く。ホストのセッションは、確定した文字だけを受ける。
- **ライセンス**：Mac の OS の部品を使うだけ。ホストの側は、Smithay（MIT）。
- 弱いところ：ホストのアプリが、カーソルの周りの文字（前後の文）を見て変換するもの（再変換など）は、Mac が前後の文を知らないので、効かない。

## つなぎと、本来の形（提案。持ち主が決める）

日本語入力は、毎日の使い方に要る。そこで、いちばん早く打てるようにする「つなぎ」と、本来の形を分けて考える。大きさは、すべて見込みで、測っていない。つなぎ（b か c）は、持ち主の決定（M3 では、ホストの側の変換を使う。上の「背景」）の内側にある。

### 1. つなぎ：2 つの道がある

**道 1：まず c（GTK のアプリ）、そのあと b（Blender）。**

- **大きさ**：c は小さい〜中ぐらい。b はそのあと、中〜大きい。
- **作るもの**：
  - c：アプリのセッションごとに、専用のバス（D-Bus）、IBus のデーモン、Mozc を起動する手順。アプリへ渡す環境変数。設定と学習の置き場所（専用のフォルダー）。セッションを終えるとき、起動したものを、プロセスの番号で止めること。
  - b：コンポジターに text-input-v3 と input-method-v2 を入れる。セッションごとに、入力方式のプログラムを動かす。
- **動かす場所**：ホスト（GPU を積んだ Ubuntu の実機）。持ち主の机のログインとは別のフォルダーで確かめる。コードは、どの PC でも書ける。
- **順**：
  1. ホストで、手で、専用のバスと IBus と Mozc を起動し、GTK のエディターで打てるかを見る。**候補の窓が、どこに出るか、アプリからキーを取らないか**も見る（試用のコンポジターの窓の決まりが、パネルの窓に当たる）。
  2. Firefox（Wayland）で同じことを見る。Chrome も見る。
  3. 切り替えのキー（Mac の「英数」「かな」が、ホストでどのキーになるか）を決める。
  4. ランナーに、手順を組み込む。セッションの終わりで止める。
  5. Blender で見る。届かなければ、b に進む（コンポジターの修正）。
- 良いところ：GTK のアプリは、コンポジターを直さずに、早く打てる。
- 悪いところ：Blender が最後になる。c で作った手順の一部（環境変数、IBus のデーモンの起動）は、b に移ると、いらなくなる。

**道 2：最初から b。**

- **大きさ**：中〜大きい。コンポジターの修正が中心。
- **作るもの**：text-input-v3 と input-method-v2 の口。セッションごとの入力方式のプログラムと、専用のフォルダー。候補の窓を、コンポジターが絵に描く。
- **動かす場所**：ホスト。
- **順**：
  1. text-input-v3 を入れ、GTK のエディターで、文字が渡るのを見る。
  2. input-method-v2 を入れ、入力方式のプログラムをつなぐ。候補の窓が絵に出るのを見る。
  3. 切り替えのキーを決める。
  4. Firefox、Blender で見る。
  5. ランナーに組み込む。
- 良いところ：Blender と GTK のアプリが、同じ道で動く見込み。本来の形の d の、ホストの側（text-input-v3）と、コンポジターの仕事を共有できる。
- 悪いところ：最初の 1 つ目が打てるまでが、c より遅い。

**提案**：Blender と Firefox の 2 つが M3 の名指しなので、**道 2（最初から b）を提案する**。c は Blender に届かない可能性が高く、c で作った分の一部は、b に移ると捨てることになる。ただし、「いちばん早く、何か 1 つ打てる」ことを優先するなら、c の手順 1 だけ（手で動かして、GTK のエディターで見る）は、短い時間で済むので、b の作業と並べて試せる。この 1 つ目の確かめで、候補の窓の置き場所の問題（上の c の「確かめること」）も分かる。

- **つなぎが残すもの（あとで外すか、置き換えるもの）**：
  - 変換は、ホストの Mozc で行う。Mac の変換と、結果と学習が違う。
  - 設定と学習の専用のフォルダーは、d に移るとき、不要になる（捨てるか、移す）。
  - c を使った場合は、環境変数と IBus のデーモンの起動の手順も、b に移ると不要になる。
  - b のコンポジターの修正は、d でも使うので、残る。

### 2. 本来の形（M3 のあとの宿題）：案 d（Mac の入力方式で変換し、確定した文字と変換中の文字を送る）を提案する

選ぶ理由：変換が、持ち主のふだんの変換と同じ。候補の窓は、手元の Mac に出る。キー 1 つごとの往復がない。ホストに入力方式が要らない。

- **大きさ**：大きい。クライアント、プロトコル、ホストのコンポジターの 3 か所に手が入る。
- **作るもの**：
  - 先に、ADR 0007 を直す（確定した文字と、変換中の文字を運ぶメッセージ。ログには出さない）。
  - クライアント：窓に、Mac の文字入力の受け口（NSTextInputClient）を付ける。変換中の文字の印と位置を出す。キーの番号を送る道は、英字のあいだは今のまま。
  - ホストのコンポジター：text-input-v3 をアプリに出し、受けた文字を、アプリに渡す（preedit と commit）。input-method は要らない。
  - 再変換など、前後の文を使うものは、効かない。どこまで足すかを決める。
- **動かす場所**：クライアントは Mac の実機（Xcode の入った Mac）。ホストの修正は、ホストの実機。ADR とプロトコルの試験は、どの PC でも。
- **順**：
  1. ADR 0007 を更新する（提案から決定へ。持ち主が決める）。
  2. メッセージの定義と、そのテスト（どの PC でも）。
  3. コンポジターに text-input-v3 を入れる（ホスト。先に、つなぎで使う Wayland アプリで、文字が渡るのを見る）。
  4. クライアントの受け口を作る（Mac）。
  5. 2 台を有線でつなぎ、打ってみる。遅延に影響しないかを見る（キー、映像の経路には、手を入れない）。
  6. つなぎを外す。残したものの片づけをする（上の「残すもの」）。
- d のホストの側（text-input-v3）は、b と同じコンポジターの仕事を使う。b を先にやれば、共有できる。変換をホストで行う形でよいなら（質問 1）、b を本来の形にして、d を取らない選び方もある。

### 3. 試す順

1. つなぎは、道 2（最初から b）を提案する。c の手順 1（手で動かす確かめ）だけを、並べて試してよい。
2. Blender で c が届かなければ、b が必要になる。
3. a は使わない（候補が机にしか出ない）。最初の確かめに使うかどうかは、持ち主が決める。
4. 本来の形（d）は、ADR 0007 を直すところから始める。c と同時には進めない。d の手順 3（ホストの text-input-v3）は、b と同じコンポジターの仕事なので、共有できる。

## 持ち主への質問

1. M3 では、ホストの側の変換を使うと、すでに決めてある（2026-11-18）。残る問いは、M3 のあとに、Mac の変換（案 d）を作りたいか。作らないなら、b を本来の形にできる。
2. 候補の窓は、中継する窓の中に出てよいか。
