# 進め方

危険度の高い前提（遅延）を早く確かめ、毎日使える部分から順にドッグフーディングへ入れていきます。
各マイルストーンは、受け入れ条件を満たして初めて完了です。

「場所」は作業と検証に必要な環境です。実機が要るものは、実機の上で動かして確かめます。

## M0 共通の土台

| 項目 | 状況 | 場所 |
|---|---|---|
| データ型（`istesso-proto`） | 済 | どこでも |
| 役割表（`istesso doctor`） | 済。実機2台で確認 | 各実機 |
| アプリ一覧の収集と統合（`istesso apps`） | 済。実機2台で確認 | 各実機 |
| ペアリング（`istesso pair`、`istesso peers`） | 済。実機2台で確認 | 2台の実機 |
| 固定した鍵で相互認証する制御チャンネル（`istesso-link`） | 済（ADR 0007）。実機2台で、両方向とも確認 | どこでも |
| エージェント（`istesso agent`）と LAN 内の自動発見 | 済。自動発見は1台の中で2台分を動かして確認した。実機では、アドレスが変わったあとに追従するかをまだ見ていない | 2台の実機 |
| 役割表とアプリ一覧をチャンネル越しに交換（`istesso hosts`、`istesso apps list --all`） | 済。実機2台で確認 | 2台の実機 |
| ペアリングをエージェントに統合し、相手を自動で見つける。QR | 未 | どこでも |
| エージェントの常駐サービス化（launchd / systemd） | 未（M9 のインストーラーと合わせる） | 各実機 |

受け入れ条件：2台の実機でペアリングし、片方から `istesso apps list --all` を実行すると両方のアプリが1つの一覧で見える。片方を止めると、その端末にしかないアプリに `!` が付く。

**2026-11-16 に達成。** MacBook Air（macOS 26、M4）と Ubuntu 24.04（RTX 4090）を Wi-Fi でつないで確認しました。

## M1 遅延の検証（最重要）

進め方と体制は [m1-plan.md](m1-plan.md)、計測の方法は [measurements/README.md](measurements/README.md) にあります。

**状態（2026-11-17）：M1 は、関門を通過。受け入れは、確定の判定のあと。** 関門の判定（[記録](measurements/2026-11-17-m1-gate.md)）は、いまの形（試作のビューアーと、計測用のホストのスクリプト）で測った。確定の判定は、自前のクライアントとホストが入ったあとに測る（[計画](m1-final-verdict-plan.md)、[ADR 0002](adr/0002-latency-first.md)）。

1. **基準を取る。** 既存の配信ソフトを比較対象として動かし、遅延の体感と数値を記録する（`docs/measurements/`）。ここで合格ラインを数値で決める。
2. **縦に1本通す。** Ubuntu のアプリ1つを、Mac の窓1枚として出す。
   - Linux ホスト：仮想コンポジター → NVENC → 送信
   - Mac クライアント：受信 → VideoToolbox → 窓、カーソルは手元で描画、入力を返送
   - 遅延の常時表示

受け入れ条件：決めた合格ラインを満たす。どの窓がリモートかを当てるテストで、当てられない。

場所：Ubuntu の実機（GPU）と Mac の実機。基準の対象は有線 LAN で、Wi-Fi から測り始めるときの扱いは [m1-plan.md](m1-plan.md) に書いてあります。

**ここで基準を満たせない場合は、先へ進む前に構成を見直します。**

### 判定を待たずに始めるもの（2026-11-16 に決定）

M1 の関門は、ほぼ通る見込みになった（Wi-Fi で、手元の窓との差の中央値が 15.5 ms。有線にしたときの見込みが約 11 ms。[記録](measurements/2026-11-16-quality.md)）。そこで、映像の方式に依存しない 2 つを、判定を待たずに始める。関門を通らなかったときに作り直しになるものは、始めない。

| 流れ | 最初にやること | ブランチ |
|---|---|---|
| 音（M2） | Ubuntu で鳴った音を Mac で出す向きから。ADR 0005 に沿って設計し、短い試験まで | `m2-audio` |
| アプリマネージャー（M3） | アプリの起動と終了を頼む制御チャンネルのメッセージと、コマンド 1 つで窓が開くところまで。本線との境目（セッションの始め方）は、先に ADR で決める | `m3-app-manager` |

並行して進めるときの決まり：

- 流れごとに、`main` から切ったブランチと、別の作業ツリーで進める。ドラフトの PR を作って、CI を通す。
- 共通のクレート（`istesso-proto`、`istesso-link`）を変えるときは、先に本線（M1）と合わせる。
- 実機で遅延を測っているあいだは、ほかの流れのビルドと試験を止める。計測を最優先にする。
- 8 時間の試験のような長いものは、夜に回す。始める前に、人に知らせる。
- 人への質問と、人の手が要る作業は、流れをまたいで 1 つの一覧にまとめる。

## M6 エージェント連携

- `istesso run` / `istesso build` / `istesso deploy`（必要条件から行き先を決める）
- エージェント向けスキルと、Gate に載せる確認項目
- herdr を専用ユーザーで動かす手順

進め方は [m6-plan.md](m6-plan.md) にあります。

受け入れ条件（2026-11-17 に決定。2 段に分ける。記号は m6-plan.md の「2.」と同じ）：

1 段目（今週通す）

- A：AGENTS.md の「どこで何を動かすか」の表の行のうち、必要条件として書ける行は、すべて、表と同じ行き先になる。理由が一緒に出る。書けない行は、理由とともに一覧にする。試験用の役割表のほかに、実機の `istesso hosts --json` の出力でも 1 回確かめる。PC の台数は決めない（そのときペアリングしてある全部）。記録に、PC の名前とアドレスを残さない。
- B：必要条件を満たす PC がないとき、満たす PC が答えないときは、ほかの PC で黙って動かさない。理由を出す。起こせる PC なら、そのことを出す。
- C：デプロイは、行き先がただ 1 つに決まり、その行き先が答えるまで、進まない。確かめたかどうかを、コマンド 1 つで問い合わせられる。
- D：軽いモデル 1 つが、入口の 1 行とスキルだけで、PC の名前を知らないまま、書ける行のすべてについて正しい行き先を答え、終了コード 70〜75 のそれぞれでスキルのとおりに振る舞う（72 で自分から選ばない。75 で人に伝える）。ほかのコーディングエージェントでの確かめは、あとの項目。
- H（A と B の部分）：ホストを起動した直後（ログイン画面のまま、SSH だけ）の状態で、A と B が動く。動かないものは、理由と、インストーラー（M9）が何を入れれば動くかを書く。

2 段目（M5 と、ほかの PC で動かす方式の ADR のあと。いまは案。ADR を書くときに確定する）

- E（案）：`istesso build`、`istesso run`、`istesso deploy` が、決まった行き先の PC で、実際に動く。動くのは専用ユーザーで、作業の場所は隔離領域の中である。
- F（案）：権限のない端末からの頼みは、断られる。権限を外すと、すぐ効く。
- G（案）：herdr が専用ユーザーで動いている。その上のコーディングエージェントから、ふだんのホームに置いた目印のファイルが読めない。
- H（E の部分、案）：ホストを起動した直後の状態で、E が動く。
- 確定するときに足す候補：送られてきても、タスクの名前のほかは受け取らない（コマンドライン、引数、環境変数を受け取らない）。隔離されていないホストは断る。権限を外すと、1 秒以内に効く。

場所：A は、試験用の役割表ならどの PC でも。実機の役割表での確かめは、ペアリングしてある PC から。D は、どの PC でも。

## M7 USB と Stream Deck

進め方と、今週（2026-11-16 の週）に通せるもの・通せないものは [m7-plan.md](m7-plan.md) にあります。決定は [ADR 0004](adr/0004-usb-devices.md) と [ADR 0012](adr/0012-device-framework.md)（機器対応のフレームワーク）です。

- 全ホストの機器の一覧。どの PC に挿してあるかが分かる
- 機器対応のフレームワークと、最初のアダプターとしての Stream Deck の直接制御モード
- 起動先の選び方：USB 機器を使うアプリは、その機器を受け取れるホストを優先する。会議アプリは、マイクとカメラがつながっている PC で開く。会議のページを、ランチャーの項目として登録できる

受け入れ条件（2026-11-16 に採用）は、m7-plan.md の「6. 受け入れの確認」にあります。ホストを起動した直後（ログイン画面のまま、SSH だけ）の状態で動くことを含みます。

あとに回すもの（今回の公開では作らない）：

- USB/IP による付け替え（受け側は Linux）
- 会議のリンクを開いたときに、マイクとカメラのある PC へ自動で振り分ける
- アプリが機器を実際に使ったのを見つけて、次から起動先に反映する
- 外からのアダプターの受け付け。種類の違う 2 つ目の機器を通して、口を固めてから

場所：機器が挿してある実機。

## 今週の進め方（2026-11-16 に決定）

2026-11-16 の申し送りで決まったことの記録です。上の各マイルストーンの内容と受け入れ条件は、変えていません。

決めごとには、ねらいが付いています。**書いてある決めごとで判断がつかないときは、ねらいに合うほうを選びます。**

背景：

- 使い手は、開発者に限らない。複数の端末を持て余している人である。導入のかんたんさと、説明なしで使えることを、開発者向けの道具より重く見る。
- 公開の場では、ほかの製品の名前を出して比べない。比べるのは、困りごと（リモートだと感じる、切り替えが面倒、OS をまたいでアプリを使えない）。

### 目標

ねらい：早く使い始め、早く公開して、使う人を集め始める。そのために、流れを分けて、並行で進める。

- AURA 対応（M8）を除く範囲を、今週（2026-11-16 の週）のうちに形にすることを目指す。
- **「形にする」とは、受け入れ条件を通ること。** 通らなかったものは、公開するものと、公開のときに見せるページ（LP）に書かないだけで、ほかの流れは止めない。
- M1 の関門だけは外さない。ここが通らないと、残りを作っても、「リモートだと感じる」土台の上に載るため。

### 受け入れ条件に足すもの

**ホストは、画面の前に誰も座っていない状態がふつうである。** 起こしたばかりで、ログイン画面のままのこともある。その状態で動かないものがあると、使う人から見て「ときどき動かない」になる。

- 各流れの受け入れ条件に、「ホストを起動した直後（ログイン画面のまま、SSH だけ）の状態で動く」を足す。
- 動かないものは、理由と、インストーラー（M9）が何を入れれば動くかを書く。
- **Mac のホストは、今回は、「人がログインしておく」形にする。** ねらいは、導入した人に、ディスクの暗号化を切らせる作りを、既定にしないこと。Mac mini の FileVault は切らない。Mac のホストでは、上の条件を、「ログイン済みで画面をロックした状態と、スリープから起こした直後の状態で、動くこと」と読み替える。
- 制約：Mac のホストは、再起動のあとに、人が1回ログインするまで使えない。自動ログインは、使う人が自分で選べる設定として、説明だけを書く。今回は試さない。
- M4 のぶんは [m4-plan.md](m4-plan.md) の 4.4、M5 のぶんは [m5-plan.md](m5-plan.md) の 4.4 に書いた。

### インストーラー（M9）と、ホストの準備で気を付けること

**カーネルを更新したあとに、GPU が使えなくなる落とし穴がある。** NVIDIA のドライバーのカーネルモジュールは、カーネルの版ごとに要る。自動で作り直す仕組み（DKMS）が入っていない PC では、新しいカーネルで起動すると、モジュールがなくて、GPU が使えない。

- M1 のホストが、この状態だった（2026-11-16 に、読むだけで調べた）。動いているカーネルは 6.17.0-19。入っている中でいちばん新しいのは 7.0.0-43。ドライバーのモジュールは、6.17.0-19 のぶんしかなく、DKMS は入っていない。起動の設定は、6.17.0-19 を名指ししている。
- インストーラーは、GPU に頼る前に、**次に起動するカーネルのぶんのモジュールがあるか**を確かめる。なければ、何が起きるかを、ふつうの言葉で伝える（例：「次に再起動すると、この PC のアプリを映せなくなります」）。黙って進めない。
- 導入の文書に、「カーネルを更新したあとは、再起動の前に確かめる」と書く。`istesso doctor` で確かめられるようにする。
- 再起動のあとに確かめ直す項目の一覧は、`m1-latency` ブランチの `docs/m1-plan.md` の「ホストを再起動したあとに、確かめ直すこと」にある。ここには写さない。

### この決定を当てはめると

- **M5、M6、M7、M9 には、受け入れ条件がまだ書かれていません。** 条件がないと、形になったかどうかを言えません。それぞれの流れが、先に条件を書きます。M5 の条件の案は [m5-plan.md](m5-plan.md) の「1. 確かめること」にあります。M7 の条件の案は、M7 の流れの計画（`m7-usb-devices` ブランチ）にあります。
- **M5 は、今週は設計までなので、今週のうちに受け入れ条件を通ることはありません。** 今週の公開と LP には、書きません。ほかの流れは、止めません。
- M4 の受け入れ条件は「Mac Studio のアプリ」と書いてあります。ねらいは、Mac Studio の到着を待たずに確かめることなので、**Mac mini での確認を、M4 の確認とします。** 記録には機種を書き、Mac Studio が届いたら、同じ計測をやり直します。

| 圧縮の枠が足りなくなったとき。GeForce は、PC 1台で、同時に 8 本までしか映像を圧縮できない。モニターを増やすと、同時に見える窓が増えて、8 本に当たりやすくなる。上の、マルチモニターの対応と一緒に設計する。手は3つ：(1) 枠を、窓ではなく「いま絵が変わっている窓」に配る。止まっている窓は、最後の絵を出したまま枠を手放し、動き出したら取り直す。(2) 何枚かの窓を 1 本の映像にまとめて送り、クライアントで切り分ける。操作中の窓には、1 本を独占させる。(3) 別の圧縮の口（内蔵グラフィックス、CPU）も使う | セッション1つに、ランナーが1つ、圧縮が1本（`m3-app-manager` ブランチの ADR 0010）。窓と圧縮の枠が、1 対 1 で結び付いている。この3つの手を入れるときは、ここを先に見直す |
| Mac のホストで、ログイン画面を中継して、手元の窓からログインする | 再起動のあとは、人が、その Mac で1回ログインする。それまで、ホストとして使えない（[m4-plan.md](m4-plan.md) の 4.4） |

取りかかるときは、先に R-02 と、関係する ADR を直します。ログイン画面の中継は、root で動く部品が要るので、先に ADR を書きます。
