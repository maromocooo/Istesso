# 進め方

危険度の高い前提（遅延）を早く確かめ、毎日使える部分から順にドッグフーディングへ入れていきます。
各マイルストーンは、受け入れ条件を満たして初めて完了です。

「場所」は作業と検証に必要な環境です。実機が要るものは、実機の上で動かして確かめます。

## M0 共通の土台

| 項目 | 状況 | 場所 |
|---|---|---|
| データ型（`istesso-proto`） | 済 | どこでも |
| 役割表（`istesso doctor`） | 済。実機2台で確認 | 各実機 |
| アプリ一覧の収集と統合（`istesso apps`） | 済。実機2台で確認 | 各実機 |
| ペアリング（`istesso pair`、`istesso peers`） | 済。実機2台で確認 | 2台の実機 |
| 固定した鍵で相互認証する制御チャンネル（`istesso-link`） | 済（ADR 0007）。実機2台で、両方向とも確認 | どこでも |
| エージェント（`istesso agent`）と LAN 内の自動発見 | 済。自動発見は1台の中で2台分を動かして確認した。実機では、アドレスが変わったあとに追従するかをまだ見ていない | 2台の実機 |
| 役割表とアプリ一覧をチャンネル越しに交換（`istesso hosts`、`istesso apps list --all`） | 済。実機2台で確認 | 2台の実機 |
| ペアリングをエージェントに統合し、相手を自動で見つける。QR | 未 | どこでも |
| エージェントの常駐サービス化（launchd / systemd） | 未（M9 のインストーラーと合わせる） | 各実機 |

受け入れ条件：2台の実機でペアリングし、片方から `istesso apps list --all` を実行すると両方のアプリが1つの一覧で見える。片方を止めると、その端末にしかないアプリに `!` が付く。

**2026-11-16 に達成。** MacBook Air（macOS 26、M4）と Ubuntu 24.04（RTX 4090）を Wi-Fi でつないで確認しました。

## M1 遅延の検証（最重要）

進め方と体制は [m1-plan.md](m1-plan.md)、計測の方法は [measurements/README.md](measurements/README.md) にあります。

**状態（2026-11-17）：M1 は、関門を通過。受け入れは、確定の判定のあと。** 関門の判定（[記録](measurements/2026-11-17-m1-gate.md)）は、いまの形（試作のビューアーと、計測用のホストのスクリプト）で測った。確定の判定は、自前のクライアントとホストが入ったあとに測る（[計画](m1-final-verdict-plan.md)、[ADR 0002](adr/0002-latency-first.md)）。

1. **基準を取る。** 既存の配信ソフトを比較対象として動かし、遅延の体感と数値を記録する（`docs/measurements/`）。ここで合格ラインを数値で決める。
2. **縦に1本通す。** Ubuntu のアプリ1つを、Mac の窓1枚として出す。
   - Linux ホスト：仮想コンポジター → NVENC → 送信
   - Mac クライアント：受信 → VideoToolbox → 窓、カーソルは手元で描画、入力を返送
   - 遅延の常時表示

受け入れ条件：決めた合格ラインを満たす。どの窓がリモートかを当てるテストで、当てられない。

場所：Ubuntu の実機（GPU）と Mac の実機。基準の対象は有線 LAN で、Wi-Fi から測り始めるときの扱いは [m1-plan.md](m1-plan.md) に書いてあります。

**ここで基準を満たせない場合は、先へ進む前に構成を見直します。**

### 判定を待たずに始めるもの（2026-11-16 に決定）

M1 の関門は、ほぼ通る見込みになった（Wi-Fi で、手元の窓との差の中央値が 15.5 ms。有線にしたときの見込みが約 11 ms。[記録](measurements/2026-11-16-quality.md)）。そこで、映像の方式に依存しない 2 つを、判定を待たずに始める。関門を通らなかったときに作り直しになるものは、始めない。

| 流れ | 最初にやること | ブランチ |
|---|---|---|
| 音（M2） | Ubuntu で鳴った音を Mac で出す向きから。ADR 0005 に沿って設計し、短い試験まで | `m2-audio` |
| アプリマネージャー（M3） | アプリの起動と終了を頼む制御チャンネルのメッセージと、コマンド 1 つで窓が開くところまで。本線との境目（セッションの始め方）は、先に ADR で決める | `m3-app-manager` |

並行して進めるときの決まり：

- 流れごとに、`main` から切ったブランチと、別の作業ツリーで進める。ドラフトの PR を作って、CI を通す。
- 共通のクレート（`istesso-proto`、`istesso-link`）を変えるときは、先に本線（M1）と合わせる。
- 実機で遅延を測っているあいだは、ほかの流れのビルドと試験を止める。計測を最優先にする。
- 8 時間の試験のような長いものは、夜に回す。始める前に、人に知らせる。
- 人への質問と、人の手が要る作業は、流れをまたいで 1 つの一覧にまとめる。

### 将来の候補（いまは作らない）

- **ごく短い切れ目（0.5 秒未満）で、同じ窓が前に出たままなら、切れているあいだに打った文字を送り直す。** いまは、切れているあいだに打たれたものは送り直さず、落ちたことを窓に出す（[ADR 0015](adr/0015-media-transport.md) の「そのあいだのキーとボタン」、[ADR 0007](adr/0007-control-channel.md)。2026-11-17 に決定）。

## M2 オーディオ

- 「音の出口」の選択と、ホスト間の配信（非圧縮、時計のずれ補正、欠落の補完）
- Linux は PipeWire、Mac は Core Audio のタップで取り込む
- 再生中のスリープ抑止
- 映像のセッションと独立して動くこと

受け入れ条件：別のホストで再生した音楽が、選んだ出口から8時間途切れずに鳴る。窓を閉じても止まらない。

場所：オーディオ機器をつないだ実機。

## M3 アプリマネージャー

- ランチャー画面（1アプリ1アイコン、停止中の「！」、起こす操作）
- リモートのアプリの起動と終了
- 起こす手段の差し替え（最初は Wake-on-LAN）
- CPU・メモリ・GPU の一覧

受け入れ条件：アプリがどの PC にあるかを見ずに起動できる。

## M4 Mac ホスト

- ScreenCaptureKit + VideoToolbox + 入力の注入
- アプリごとの仮想ディスプレイ
- 画面収録・アクセシビリティ許可の案内

受け入れ条件：Mac Studio のアプリを MacBook Air の窓として、M1 と同じ合格ラインで使える。

場所：Mac の実機2台。

## M5 ストレージ、インストール、隔離

## M6 エージェント連携

- herdr を専用ユーザーで動かす手順

## M7 USB と Stream Deck

- 全ホストの USB 機器の一覧
- Stream Deck の直接制御モード
- USB/IP による付け替え（受け側は Linux）

## M8 AURA クライアント

- Android XR アプリ（窓1枚 = 空間パネル1枚）
- VPN 越しの接続

## M9 配布と公開

- Mac：署名と公証を通した pkg。Ubuntu：署名付きリポジトリの .deb
- リリースの自動生成、更新の仕組み
- ペアリング部分の外部レビュー
- **Wi-Fi で測る**（公開の前に）。線と測り方は、[ADR 0015](adr/0015-media-transport.md) の「Wi-Fi で測って、移るかどうかを決める線」。チャンネルを固定した試験用の SSID で判定し、ふだんの SSID でも 1 回、参考として測る。Wi-Fi での使い心地を、公開のときにどう書くかを、ここで決める
- 名前の決定、公開
