# M2 の進め方：オーディオ

M2 は「音を聴きながら作業できること」（R-08）を確かめる段階です。この文書は、最初の向き（**Ubuntu で鳴らした音を、Mac から出す**）の設計と、短いテストまでの手順です。

いまは設計の段階で、音の経路のコードはまだありません。配信の部品を替える提案（[ADR 0011](adr/0011-audio-transport.md)）が採用されることを前提に書いています。採用されなかったときは、「4.2 取り込み」から「4.5 途切れと欠落」までと、「4.9 足すもの」の依存が変わります。ほかは、そのまま使えます。

規約は先に [AGENTS.md](../AGENTS.md) を読んでください。決定の理由は [ADR 0005](adr/0005-audio-service.md) と ADR 0011、下調べの結果は [記録](measurements/2026-11-16-m2-step0-survey.md) にあります。

## 1. 確かめること

最初の向きで、短いテストまでに確かめること：

1. Ubuntu のアプリが鳴らした音が、Mac の出力の機器に届く。
2. 届いた音に、途切れと欠けがない。
3. 2 台の時計のずれを測り、補正が効いていることを数値で示す。
4. 遅延を測って、内訳と合わせて記録する。
5. 相手がペアリング済みで、音の権限を持つときだけ流れる。経路は暗号化されている。

M2 の受け入れ条件（[milestones.md](milestones.md)）は「別のホストで再生した音楽が、選んだ出口から 8 時間途切れずに鳴る。窓を閉じても止まらない」です。短いテストは、その手前の関門です。

## 2. 環境

2026-11-16 に調べた結果の要約です（[記録](measurements/2026-11-16-m2-step0-survey.md)）。

| 役 | 機材 | 音まわり |
|---|---|---|
| 音源 | Ubuntu 24.04 | PipeWire 1.0.5、48 kHz。開発用のパッケージは入っていない |
| 出口 | MacBook Air（M4、macOS 26） | 既定の出力は内蔵スピーカー（48 kHz）。ほかに、44.1 kHz で動いている USB のオーディオインターフェースなど。Roc は入っていない |

## 3. 体制と決まり

映像の作業（M1）と同じ 2 台を、同時に使います。計測の邪魔をしないことを、いちばんに置きます。

- 作業は、`main` から切った `m2-audio` ブランチの、専用の作業ツリーで行う。映像の作業の作業ツリーには触らない。
- 映像の計測が走っているあいだは、ビルドもテストも始めない（合図のファイルで確かめる）。重いコマンドは、優先度を下げて動かす。
- ホストでは、音の作業のための場所（`~/.cache/istesso-m2-audio/`）だけを使う。映像の作業の複製と作業用のファイルには触らない。
- **音は出さない。** テストは、機器に無音を渡しながら、渡すはずだった音をデジタルで確かめる（「5. 短いテスト」）。耳で聞く確認は 1 回だけ、5 秒、小さい音で、人に声をかけてから行う。
- **既定の出力先を変えない。** ホストでも Mac でも、いま鳴っている音の行き先を変えない。機器のサンプルレートや音量も変えない。
- 何も入れない。足りないパッケージは、一覧にして人に頼む（「7. 人に頼むこと」）。`sudo` は使わない。
- `istesso-proto` と `istesso-link` は、短いテストまで変えない。ほかの共有のクレートに要る変更も、「4.10 共有のクレートへの変更」に書いて、先に相談する。

## 4. 設計

### 4.1 全体

```text
 Ubuntu（音源）                                   Mac（音の出口）
 ┌─────────────────────────────┐              ┌─────────────────────────────────┐
 │ アプリ                        │              │                                 │
 │   └▶ 仮想の出力先（PipeWire） │              │  受信バッファー                   │
 │         └▶ 取り込み           │  TCP + Noise │    └▶ リサンプラー（ずれ補正）    │
 │              └▶ 送信 ────────┼─────────────▶│         └▶ Core Audio ─▶ 機器    │
 │                              │ PCM、非圧縮   │                                 │
 └─────────────────────────────┘              └─────────────────────────────────┘
      待ち受ける                                     つなぎに行く
```

音は、映像とは別のプロセス、別の接続で流れます。つなぎに行くのは出口の側です。

### 4.2 取り込み（ホスト）

- `istesso audio serve` が、PipeWire のクライアントとして**仮想の出力先**を作る（`media.class = Audio/Sink`、名前は `istesso-out`）。アプリからは、スピーカーと同じ「出力先の 1 つ」に見える。
- プロセスが作るものなので、プロセスが終われば消える。PipeWire の設定ファイルは書かず、PipeWire の再起動も要らない。
- 短いテストでは、既定の出力先を変えない。テストの音は、この出力先を名指しして流す。出口を選んだら既定の出力先を切り替え、やめたら戻す、という動きは、あとの段階で作る（「6. 手順」）。
- 形式は、PipeWire の中の形式のまま（32 ビット浮動小数、48 kHz、2 チャンネル）。
- 1 回の処理の長さ（quantum）は、256 フレーム（5.3 ms）を求める。既定は 1024 フレーム（21.3 ms）で、そのままだと取り込みだけで 21 ms 遅れる。
- 仮想の出力先だけがつながったグラフは、PipeWire がシステムの時計で回す。したがって、音源の時計はホストのシステムの時計になる（手順 3 で確かめる）。
- 取り込みのコールバックは、リアルタイムのスレッドで呼ばれる。そこでは、待たないリングバッファー（`rtrb`）に書くだけにする。送るのは別のスレッド。

Roc 用のモジュール（`roc-sink`）は使いません。取り込んだ音を自分のプロセスで受け取るには、PipeWire のクライアントになるのが素直なやり方で、そのためにビルド用のパッケージが 2 つ要ります（「7. 人に頼むこと」）。パッケージを入れずに済ませる道として、PipeWire に最初から入っている `pipe-tunnel` モジュール（出力先に流れた音を、名前つきパイプに書き出す）を別のプロセスとして動かす手があります。作りが増えるので、パッケージを入れられないときの予備にとどめます。

### 4.3 経路

ADR 0011 のとおりです。

- 音源のホストが、TCP のポート（既定 47802）で待ち受ける。出口がつなぎに行く。
- つないだら、`istesso-link` の `Channel` で、制御チャンネルと同じ手順（Noise XX、固定した鍵での相互認証。[ADR 0007](adr/0007-control-channel.md)）を行う。暗号の手順は足さない。
- 音源の側は、相手が音の権限（`Permission::Audio`）を持つときだけ送る。流しているあいだも、数秒おきにペアリング一覧を読み直し、解除や権限の取り消しがあれば止める。
- 出口の側は、つなぐ相手を指定する。別の端末が答えたら、ペアリング済みの端末でも切る（`istesso-link` の `Client` と同じ）。
- つなぐ先のアドレスは、エージェントが覚えているもの（ADR 0007 の「発見とアドレスの記憶」）を使う。違うのはポートだけ。短いテストでは、有線のアドレスを指定する。
- 切れたら、出口が間隔を空けながらつなぎ直す。
- 1 つの音源の音を受け取れる出口は、同時に 1 つ。あとから申し込んだ出口に切り替わる。

接続の最初のメッセージで、何の接続かを決めます。メッセージは `Channel` の 1 メッセージずつで、最初のやり取りは JSON です。

| 向き | 内容 |
|---|---|
| 出口 → 音源 | `{"type":"subscribe","version":1}` |
| 音源 → 出口 | `{"type":"stream","version":1,"stream_id":"…","sample_rate":48000,"channels":2,"format":"f32le","packet_frames":256}`。断るときは `{"type":"error","code":"forbidden","message":"…"}` |
| 音源 → 出口（以後くり返し） | 音のパケット（下の表） |

音のパケット（リトルエンディアン）：

| 位置 | 長さ | 内容 |
|---|---|---|
| 0 | 1 | 種類。1：音、2：音源が止まっている（無音が続いている）ことの知らせ、3：終わり |
| 1 | 1 | 旗。ビット 0：前のパケットとつながっていない |
| 2 | 2 | このパケットのフレーム数 |
| 4 | 4 | 連番 |
| 8 | 8 | ストリームの先頭から数えた、最初のフレームの位置 |
| 16 | 8 | 最初のフレームを取り込んだ時刻（音源の単調な時計、ナノ秒） |
| 24 | フレーム数 × チャンネル数 × 4 | サンプル（32 ビット浮動小数、チャンネルを交互に並べる） |

TCP の上では、連番は要りません。あとで認証つきのデータグラムに載せ替えられるように、最初から入れておきます。

遅延を測るには、2 台の時計の差が要ります。同じポートへの別の接続で、時刻を尋ねます。

| 向き | 内容 |
|---|---|
| 出口 → 音源 | `{"type":"time","t1":…}`（出口の時計） |
| 音源 → 出口 | `{"type":"time","t1":…,"t2":…,"t3":…}`（`t2` は受け取った時刻、`t3` は返した時刻。音源の時計） |

出口は、返事を受け取った時刻と合わせて、時計の差と往復時間を出します。往復時間がいちばん短かった回を使います。誤差は、往復時間の半分より小さくなります。

### 4.4 再生と、時計のずれ補正（Mac）

- `istesso audio play <ホスト>` が、Core Audio の出力ユニットを、選んだ機器で開く。指定しなければ、システムの既定の出力。
- **機器の設定は変えない。** サンプルレート、バッファーの大きさ、音量に触らず、排他的に使うこともしない。機器が 44.1 kHz で動いていれば、こちらが合わせる。
- 機器が音を引き取るコールバックの中で、受信バッファー → リサンプラー → 機器、の順に引く。リサンプラーは rubato の非同期のもの（sinc 補間）で、処理中にメモリーを確保しない。
- リサンプラーの比は「機器のレート ÷ 48000 ×（1 ＋ 補正）」。補正は、受信バッファーにたまっている量が目標から離れないように、ゆっくり動かす（比例と積分の制御）。
  - たまっている量は、届くパケットの刻みで波打つので、ならしてから使う。
  - 補正の幅は、落ち着いたあとは ±0.1%、追いつくあいだは ±0.5% まで。
  - 目標は、有線で 30 ms から始める。Wi-Fi では大きくする。数値は、模擬と短いテストで決め直す。
- 2 台の時計のずれは、ふつう数十 ppm（50 ppm は 0.005%）で、補正の幅よりずっと小さい。ずれが 50 ppm なら、補正なしでは 1 時間で 180 ms ぶんずれる。

遅延の見積もりです。測った値ではありません。短いテストで測って、置き換えます。

| 区間 | 見積もり |
|---|---|
| 取り込み（PipeWire の 1 回の処理ぶん） | 約 5 ms |
| 経路（有線） | 1 ms 未満 |
| 受信バッファー（目標） | 30 ms |
| 出力のバッファー（機器の設定のまま。512 フレームなら 10.7 ms） | 約 5〜11 ms |
| 機器が申告する遅れ | 数 ms |
| 合計 | 約 45〜55 ms |

映像の追加遅延は十数 ms が目標なので、音は映像より 30〜40 ms ほど遅れて届く見込みです。音が映像より遅れる側は、125 ms あたりまで気づかれにくいとされています（ITU-R BT.1359）。映像と音を合わせ込むことは、M2 の範囲に入れません。

### 4.5 途切れと欠落

- TCP なので、音が欠けることはない。遅れて届くだけで、遅れは受信バッファーが吸収する。
- **空になったとき：** 短くフェードして無音にし、回数と長さを数える。目標までたまり直したら、フェードして再開する。
- **たまりすぎたとき**（経路が止まったあと、まとめて届く）：少しなら、補正で戻す。目標の 2 倍を超えたら、古い分を捨てて目標に戻し、回数と長さを数える。
- **音源が止まっているとき**（何も鳴っていない）：音源は、0.5 秒おきに「止まっている」と知らせる。出口は無音を出し、途切れには数えない。鳴り始めたら、目標までためてから再開する。
- 数えた値は、動いているあいだも、終わったあとも見られる。受け入れ条件の「途切れない」は、この値が 0 であることで確かめる。

### 4.6 映像のセッションから独立していること

- 音は、映像とは別のプロセス、別の接続、別のポートで流れる。映像のセッションの状態を見ない。
- 窓を閉じても、仮想の出力先と音の接続は残る。
- 接続は「音源のホストと、出口」の組に属する。操作する端末を替えても、出口が同じなら、流れ続ける。
- 短いテストのあいだは、手で起動するコマンド（`istesso audio serve`、`istesso audio play`）。エージェントの中に入れて常駐させるのは、あとの段階（「6. 手順」）。

### 4.7 再生中は眠らせない

短いテストのあとで作ります。どちらも root は要りません。

- 出口（Mac）：音が流れているあいだ、眠りを止める（OS の電源のアサーション）。Core Audio が再生中に自分で眠りを止めているかどうかを、先に確かめる。
- 音源（Ubuntu）：出口がつながっていて、音が流れているあいだ、眠りを止める（systemd-logind の inhibitor）。
- 無音が続いたら外す。何も鳴っていないのに、PC を起こし続けないため。

### 4.8 手を入れない経路

- ホスト：いまある出力先（DAC など）と、その設定には触らない。仮想の出力先を 1 つ足すだけ。
- Mac：機器のサンプルレートを変えない。配信の音を出すために、DAC のレートを 48 kHz に切り替えることはしない。
- どちらも、導入の前後でローカル再生の音が変わらないことを、ADR 0005 の受け入れ条件として確かめる（M2 の後半）。

### 4.9 足すもの

クレート `istesso-audio`（[architecture.md](architecture.md) に名前だけある）：

| モジュール | 内容 | 実機が要るか |
|---|---|---|
| `wire` | 接続の最初のやり取りと、パケットの並び | 要らない |
| `buffer`、`sync` | 受信バッファー、ずれ補正の制御、リサンプラーの包み | 要らない。時計を模擬して確かめる |
| `session` | 送る側と受ける側。`istesso-link` の `Channel` の上で動く。つなぎ直し、権限の確かめ | 要らない（1 台の中で両方を動かせる） |
| `probe` | テストの信号を作る。録った音を調べる（途切れ、純度）。統計と記録 | 要らない |
| `capture`（Linux） | PipeWire の仮想の出力先 | Ubuntu の実機 |
| `playback`（macOS） | Core Audio の出力 | Mac の実機 |

コマンド：

| コマンド | 動かす場所 | 内容 |
|---|---|---|
| `istesso audio serve` | 音源 | 仮想の出力先を作り、音の権限を持つ出口に送る |
| `istesso audio play <ホスト>` | 出口 | つないで、機器に出す。`--output`（機器）、`--mute`（機器には無音を渡す）、`--record`（渡すはずだった音をファイルに録る）、`--seconds`、`--report`（結果を JSON で書く） |
| `istesso audio outputs` | どちらでも | その PC の出力の機器を並べる |
| `istesso audio tone` | 音源 | テストの信号を、仮想の出力先に流す。WAV に書き出すこともできる |
| `istesso audio check <ファイル>` | どちらでも | 録った音を、テストの信号と突き合わせる |
| `istesso peers allow <端末> <権限>`、`istesso peers deny …` | 音源 | 権限を与える、取り消す（いまは、その手段がない） |

依存（どれも `deny.toml` の許可リストに収まる。例外は足さない）：

| クレート | 版 | ライセンス | 入る OS |
|---|---|---|---|
| `rubato` | 4.0 | MIT OR Apache-2.0 | すべて |
| `rtrb` | 0.4 | MIT OR Apache-2.0 | すべて |
| `coreaudio-rs` | 0.14 | MIT OR Apache-2.0 | macOS |
| `pipewire` | 0.10 | MIT | Linux |

`rubato` は、ワークスペースの Rust の版（1.85）で使える 4.0 にします。最新の 5.1 は 1.87 以上を求めます。

Linux で `pipewire` クレートをビルドするには、`libpipewire-0.3-dev` と `libclang-dev` が要ります。CI の Linux のジョブにも、この 2 つを入れる手順が要ります。

### 4.10 共有のクレートへの変更

短いテストまで、`istesso-proto` と `istesso-link` は変えません。`Channel` と `LocalKeys` は、いまの公開の形のまま使えます。

**短いテストまでに要るもの（`istesso-pair` と `istesso-cli`）：** 音の権限を与える手段がありません。新しくペアリングした端末は「閲覧」と「操作」しか持たず（ADR 0006）、与えるコマンドがないためです。

```rust
// crates/istesso-pair/src/store.rs
impl PeerStore {
    /// Grants (`allowed = true`) or withdraws one permission of the peer with
    /// this id or (unambiguous) name. Returns the updated record, or `None`
    /// when no peer matches.
    pub fn set_permission(
        &mut self,
        selector: &str,
        permission: Permission,
        allowed: bool,
    ) -> Result<Option<Peer>>;
}
```

```text
istesso peers allow <device> <view|control|install_apps|usb|audio>
istesso peers deny  <device> <view|control|install_apps|usb|audio>
istesso peers list        # 権限も表示する
```

**あとの段階で相談したいもの：**

- 出口の候補を、全ホストぶん並べる（R-08「出力先の一覧には全ホストの機器を並べる」）。

  ```rust
  // istesso-proto
  /// A device that sound can come out of, on one host.
  pub struct AudioOutput {
      /// Stable on that host.
      pub id: String,
      pub name: String,
      pub channels: u16,
      pub sample_rate: u32,
      pub is_default: bool,
  }

  // istesso-link (message.rs). Needs the `view` permission.
  Request::AudioOutputs
  Response::AudioOutputs { outputs: Vec<AudioOutput> }
  ```

- 音の接続を、エージェントのポート（47801）に寄せるかどうか。寄せるなら、制御チャンネルの接続を音の配信に引き渡す口（`Session::into_channel(self) -> Channel<TcpStream>`）と、申し込みのリクエストが要る。寄せなければ、`istesso-link` は変えずに済む。
- 「4.3 経路」のメッセージの型を、`istesso-audio` に置くか、`istesso-proto` に置くか。短いテストまでは `istesso-audio` に置く。

## 5. 短いテスト

1 回の長さは 60 秒が基本です。**音は出しません。** Mac の機器には無音を渡し、渡すはずだった音をファイルに録って、デジタルで確かめます。機器の時計は本物なので、ずれ補正は実際の条件で動きます。

テストの信号は、997 Hz の正弦波（−12 dBFS）です。Ubuntu の側で、仮想の出力先を名指しして流します（`istesso audio tone`。別の再生ソフトでも確かめるために、同じ信号を WAV にして `pw-play` でも流す）。

| 測るもの | 測り方 | 目安 |
|---|---|---|
| 経路で欠けていないこと | 連番の抜けを数える。音源が送った内容と、出口が受けた内容のハッシュを比べる | 抜け 0、不一致 0 |
| PipeWire の区間で変わっていないこと | 流した信号と、取り込んだ信号を、サンプル単位で突き合わせる | 一致。差があれば、大きさを記録する |
| 途切れ | 受信バッファーが空になった回数と長さ、捨てた回数と長さ。録った音に正弦波を当てはめ、残りが跳ねる箇所を数える | 始まって 2 秒より後は、どれも 0 |
| 時計のずれ | 音源のフレームの位置と、機器が引き取ったフレーム数を、時刻に対して比べる（ppm） | 記録する。補正が 30 秒以内に落ち着くこと |
| 補正の動き | 補正の値と、たまっている量の、最小・平均・最大 | 補正が幅の中に収まり、たまっている量が目標のまわりにあること |
| 届く間隔 | パケットが届いた間隔の、中央値、95 パーセンタイル、99 パーセンタイル、最大 | 記録する。受信バッファーの目標を決める材料にする |
| 遅延 | 機器がそのサンプルを出す時刻 − 音源が取り込んだ時刻 − 2 台の時計の差。中央値、95 パーセンタイル、最大と、区間ごとの内訳 | 記録する。合格ラインは、測ってから決める |

目安は、測ったあとで見直します。結果は、1 回の計測を 1 つのファイルにして `docs/measurements/` に置きます（[measurements/README.md](measurements/README.md) の決まり）。

回数と順番：

1. Mac だけで 60 秒。送る側を同じ Mac の中で動かし、機器には無音を渡す。再生の側と、ずれ補正を、本物の機器の時計で確かめる。
2. 2 台で 60 秒を 3 回。有線のアドレスを指定する。
3. 2 台で 10 分を 1 回。補正が落ち着いたあとの安定を見る。
4. **耳で聞く確認を 1 回。** 5 秒、小さい音（−40 dBFS、前後をフェード）。システムの音量は変えない。人に声をかけ、返事をもらってから流す。

## 6. 手順

| 手順 | 内容 | 場所 | 人に頼むこと |
|---|---|---|---|
| 0 | 下調べ、設計、ADR 0011 の提案 | — | 済み。提案の採否を決めてもらう |
| 1 | 実機の要らない部分を作る（`wire`、`buffer`、`sync`、`session`、`probe`）。時計を模擬したテストを付ける：ずれ ±100 ppm、届く間隔のばらつき、経路の停止を入れて、8 時間ぶんを短い時間で回す（リサンプラーの計算は省き、フレームの数だけを追う） | どの PC でも | なし |
| 2 | Mac の再生（`playback`）。「5. 短いテスト」の 1 | Mac | なし |
| 3 | ホストの取り込み（`capture`）。権限を与えるコマンド（4.10 の変更。先に相談する） | Ubuntu | パッケージを 2 つ入れる。Mac に音の権限を与える |
| 4 | 2 台での短いテスト。「5. 短いテスト」の 2 と 3。結果を記録する | 2 台 | なし |
| 5 | 耳で聞く確認。「5. 短いテスト」の 4 | 2 台 | Mac の前で 5 秒聞く |

ここまでが、この計画の範囲です。そのあとは、短いテストの結果を見て決めます。

- エージェントの中に入れて、常駐させる。出口を選ぶ操作（選んだら既定の出力先を切り替え、やめたら戻す）。
- つなぎ直し、眠りを止める仕組み（4.7）。
- Wi-Fi での受信バッファーの目標。
- 8 時間のテスト（M2 の受け入れ条件）。
- 逆の向き（Mac の音を Ubuntu から出す）。Mac の取り込みには、OS の許可が要る。理由を ADR に残してから進める（AGENTS.md）。

## 7. 人に頼むこと

| 何を | いつまでに | 中身 |
|---|---|---|
| 提案の採否 | 手順 1 の前 | [ADR 0011](adr/0011-audio-transport.md)。配信を自前で作るか、Roc のままにするか |
| ホストにパッケージを入れる | 手順 3 の前 | `sudo apt install libpipewire-0.3-dev libclang-dev`（どちらも Ubuntu の main にある） |
| Mac に音の権限を与える | 手順 4 の前 | ホストで `istesso peers allow <Mac の名前> audio`（コマンドは手順 3 で用意する）。信頼に関わる操作なので、人が行うか、人の了承を得てから行う |
| 耳で聞く確認 | 手順 5 | Mac の前にいるときに、5 秒の小さい音を聞く |

Mac には、入れるものがありません。出力だけなので、OS の許可を求める画面も出ない見込みです。

## 8. 映像の作業の側と決めること

同じファイルに両方の作業が手を入れるところです。先に決めておくと、あとで衝突しません。

| 何を | 中身 |
|---|---|
| 権限を与えるコマンド | `istesso-pair` と `istesso-cli` への変更（4.10）。音の作業の側で作ってよいか |
| `istesso audio` の置き場所 | `crates/istesso-cli/src/main.rs` には、サブコマンドの定義と呼び出しだけを足し、中身は別のファイルに置く。映像の作業の変更が `main` に入ってから足すか、いま足すか |
| CI | Linux のジョブに、`libpipewire-0.3-dev` と `libclang-dev` を入れる手順を足す。`.github/workflows/ci.yml` は、映像の作業の側でも変えている |
| 依存の追加 | ルートの `Cargo.toml` の `[workspace.dependencies]` に 4 つ足す（4.9）。ここも、映像の作業の側で変えている |
| ポート | 音の接続を別のポート（47802）で受けるか、エージェントのポートに寄せるか（4.10）。短いテストは、別のポートで行う |

## 9. ライセンスの注意

- 足す依存は、どれも MIT か Apache-2.0 などの、許可リストにあるライセンスで使えます（[記録](measurements/2026-11-16-m2-step0-survey.md)）。依存を足すときに、`cargo deny check` を通します。
- PipeWire は MIT です。`pipewire` クレートは、ビルドのときにヘッダーからバインディングを作ります。
- 時計のずれ補正は、広く知られた手法（たまっている量を見て、リサンプラーの比を動かす）を、自分たちで書きます。GPL の実装は読みません。
- Roc Toolkit（MPL-2.0）は、ADR 0011 が採用されれば使いません。比べるために別に動かすことはあり得ますが、コードは入れません。
