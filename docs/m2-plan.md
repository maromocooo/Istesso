# M2 の進め方：オーディオ

M2 は「音を聴きながら作業できること」（R-08）を確かめる段階です。この文書は、最初の向き（**Ubuntu で鳴らした音を、Mac から出す**）の設計と、短いテストまでの手順です。

音の配信は、自前で作ります（[ADR 0011](adr/0011-audio-transport.md)。2026-11-16 に、条件つきで採用）。条件は、**映像と入力の経路と同じ仕組みで運び、音のためだけの仕組みを作らない**ことです。いまは `istesso-link` の通信路がその仕組みで、映像の運び方が決まったら、音もいっしょにそこへ移ります。自前のずれ補正が 8 時間の受け入れ条件に届かなかったときに替わるのは、「4.4 再生と、時計のずれ補正」のうち、リサンプラーと制御の部分です。

規約は先に [AGENTS.md](../AGENTS.md) を読んでください。決定の理由は [ADR 0005](adr/0005-audio-service.md) と ADR 0011、調べたことと測ったことは `docs/measurements/` の `m2-` で始まる記録にあります。

## 1. 確かめること

最初の向きで、短いテストまでに確かめること：

1. Ubuntu のアプリが鳴らした音が、Mac の出力の機器に届く。
2. 届いた音に、途切れと欠けがない。
3. 2 台の時計のずれを測り、補正が効いていることを数値で示す。
4. 遅延を測って、内訳と合わせて記録する。
5. 相手がペアリング済みで、音の権限を持つときだけ流れる。経路は暗号化されている。ペアリングを解除したら、流れている音は、すぐに止まる。
6. ホストの前に誰も座っていない状態（起動した直後、ログイン画面のまま、SSH だけ）で動く。この仕組みでは、それがふつうの状態である。動かないものがあれば、理由と、インストーラー（M9）で何を入れれば動くかを書く。

M2 の受け入れ条件（[milestones.md](milestones.md)）は「別のホストで再生した音楽が、選んだ出口から 8 時間途切れずに鳴る。窓を閉じても止まらない」です。短いテストは、その手前の関門です。

## 2. 環境

2026-11-16 に調べた結果の要約です（[記録](measurements/2026-11-16-m2-step0-survey.md)）。

| 役 | 機材 | 音まわり |
|---|---|---|
| 音源 | Ubuntu 24.04 | PipeWire 1.0.5、48 kHz。開発用のパッケージは入っていない |
| 出口 | MacBook Air（M4、macOS 26） | 既定の出力は内蔵スピーカー（48 kHz、1 回に 512 フレーム）。ほかに、44.1 kHz で動いている USB のオーディオインターフェースなど |

## 3. 体制と決まり

映像の作業（M1）と同じ 2 台を、同時に使います。計測の邪魔をしないことを、いちばんに置きます。

- 作業は、`main` から切った `m2-audio` ブランチの、専用の作業ツリーで行う。映像の作業の作業ツリーには触らない。
- 映像の計測が走っているあいだは、ビルドもテストも始めない。合図の場所、読み方、従う側がすることは、AGENTS.md の「計測の合図」に従う。重いコマンドは、優先度を下げて動かす。実機に音を流すテストのあいだは、こちらも同じ形の合図を書く。1 回は 2 分以内にする。2 分より長いものは、30 秒おきに合図を読み直し、busy になったら 10 秒以内に止める。
- ホストでは、音の作業のための場所（`~/.cache/istesso-m2-wip/`）だけを使う。映像の作業の複製と作業用のファイル、動いているエージェントには触らない。
- **音は出さない。** テストは、機器に無音を渡しながら、渡すはずだった音をデジタルで確かめる（「5. 短いテスト」）。いまの `istesso audio play` には、音を出す指定そのものがない。耳で聞く確認は 1 回だけ、5 秒、小さい音で、人に知らせてから行う。
- **既定の出力先を変えない。** ホストでも Mac でも、いま鳴っている音の行き先を変えない。機器のサンプルレートや音量も変えない。
- 何も入れない。足りないパッケージは、一覧にして人に頼む（「7. 人に頼むこと」）。`sudo` は使わない。パッケージを展開して、そこから動かすこともしない。
- ホストの設定や状態に跡が残りうる試し方をするときは、先に知らせてから行う。
- **人のペアリングで、音の権限を与えない。** テストには、そのために作った鍵とペアリングの一覧を、作業用の場所に置いて使う（`ISTESSO_CONFIG_DIR`）。
- Mac で遅延に関わるプログラムは、エージェントのシェルから直接は起動しない。優先度が低く、タイマーが延びる（[記録](measurements/2026-11-16-m2-step2-mac-playback.md)）。小さな `.app` にして `open -n -g` で起動する。
- `istesso-proto` と `istesso-link` は、短いテストまで変えない。ほかの共有のクレートに要る変更は、「4.10 共有のクレートへの変更」に書いて、先に相談する。

## 4. 設計

### 4.1 全体

```text
 Ubuntu（音源）                                   Mac（音の出口）
 ┌─────────────────────────────┐              ┌─────────────────────────────────┐
 │ アプリ                        │              │                                 │
 │   └▶ 仮想の出力先（PipeWire） │              │  待ち行列                         │
 │         └▶ 取り込み           │  TCP + Noise │    └▶ リサンプラー（ずれ補正）    │
 │              └▶ 送信 ────────┼─────────────▶│         └▶ Core Audio ─▶ 機器    │
 │                              │ PCM、非圧縮   │                                 │
 └─────────────────────────────┘              └─────────────────────────────────┘
      待ち受ける                                     つなぎに行く
```

音は、映像とは別のプロセス、別の接続で流れます。つなぎに行くのは出口の側です。

### 4.2 取り込み（ホスト）

- `istesso audio serve` が、PipeWire のクライアントとして**仮想の出力先**を作る（`media.class = Audio/Sink`）。アプリからは、スピーカーと同じ「出力先の 1 つ」に見える。プロセスが作るものなので、プロセスが終われば消える。PipeWire の設定ファイルは書かず、PipeWire の再起動も要らない。
- 短いテストでは、既定の出力先を変えない。テストの音は、この出力先を名指しして流す。
- 形式は、32 ビット浮動小数、48 kHz、2 チャンネル。アプリが別の形式で流したときは、PipeWire が変換する。
- 1 回の処理の長さ（quantum）は、こちらからは求めない（`--quantum` で求めることはできる）。仮想の出力先は、そこへ流すアプリと同じドライバーで動く。ホストでほかの音が鳴っていれば、それは、その機器のドライバーである。こちらが短い周期を求めると、その機器の周期まで変わり、手を入れない経路（4.8）に触ることになる。遅延は、周期の長さでは変わらない。仮想の出力先には、1 回ぶんの音が、処理の始まりにそろっているからである。
- 取り込んだ時刻は、処理の始まりの時刻（PipeWire の時計）にする。こちらのスレッドが遅れても、動かない。
- **取り込みのスレッドは、決して待たせない。** サウンドシステムのスレッドは、リングバッファーに書くだけにする。送るのは別のスレッドである。送るのが遅れて、リングに 100 ms を超えてたまったら、**古い音から捨てる**。位置（フレームの通し番号）は取り込んだ分だけ進むので、出口は、位置が飛んだことから音が抜けたとわかる。
- 取り込みは、cargo の機能（`pipewire`）の裏に置く。`pipewire` クレートのビルドには開発用のパッケージが要るので、それがない PC でも、ワークスペースのビルドとテストが通るようにするためである（AGENTS.md：共通コアはどの PC でも動かす）。CI では、この機能を有効にするジョブにだけ、パッケージを入れる手順を足す。

取り込みは、`istesso audio serve --source pipewire` です（`crates/istesso-audio/src/linux.rs`）。実機で動かした結果は、[記録](measurements/2026-11-16-m2-step4-real-capture.md)にあります。ほかに、テスト用の音源が 2 つあります：タイマーで刻む正弦波（`--source tone`）と、標準入力から読む生の PCM（`--source stdin`）。

セッションマネージャー（WirePlumber）は、仮想の出力先の音量を、ほかの出力先と同じように、名前で覚えます。製品として覚えさせるかどうかは、まだ決めていません。テストでは、覚える対象から外して動かしています（記録の「ホストを元のままにしておくこと」）。

ホストのサウンドシステムは、いま、リアルタイムの優先度で動いていません（PipeWire の処理のスレッドが、ふつうの時分割のクラス）。こちらの取り込みのスレッドも同じです。負荷がかかると処理が遅れうるので、待ち時間の目標を決めるときに、数に入れます。

### 4.3 経路

ADR 0011 のとおりです。音のためだけの仕組みは作らず、`istesso-link` の通信路をそのまま使います。

- 音源のホストが、TCP のポート（既定 47802）で待ち受ける。出口がつなぎに行く。どちらの側も、小さなパケットをすぐ出すために no-delay にする。
- つないだら、`istesso-link` の `Channel` で、制御チャンネルと同じ手順（Noise XX、固定した鍵での相互認証。[ADR 0007](adr/0007-control-channel.md)）を行う。暗号の手順は足さない。
- 音源の側は、相手が音の権限（`Permission::Audio`）を持つときだけ送る。流しているあいだも、音が流れていないあいだも、1 秒より長くは空けずにペアリング一覧を読み直し（指紋、公開鍵、権限の 3 つを見る）、解除や権限の取り消しがあれば切る。映像の作業が、入力の経路で採ったのと同じ形である。「ペアリングを解除した端末の接続は、すぐに切る」という決まりを、音はこれで満たす。解除した端末は、つなぎ直すこともできない。
- つないできた相手には、ハンドシェイクと最初のメッセージを合わせて 3 秒しか与えない。同時に相手をする数は、まだ誰とも分かっていない相手（16 まで）と、音の権限を持つと分かった相手（8 まで）を、分けて数える。
- 出口の側は、つなぐ相手を指定する。別の端末が答えたら、ペアリング済みの端末でも切る（`istesso-link` の `Client` と同じ）。
- つなぐ先のアドレスは、エージェントが覚えているもの（ADR 0007 の「発見とアドレスの記憶」）を使う。違うのはポートだけ。いまは、コマンドにアドレスを渡す。
- 1 つの音源の音を受け取れる出口は、同時に 1 つ。あとから申し込んだ出口に切り替わる。
- **接続が切れたら、出口が、つなぎ直す。** 接続が失敗したとき、または 0.3 秒のあいだ何も届かなかったとき（音源は、鳴らすものがなくても、1 秒に 10 回はそう知らせる）を、切れたとみなす。出口は、切れてから 5 秒のあいだは 0.1 秒おきに、そのあとは 0.25 秒おきに、ふつうの申し込みをやり直す。つなぎ直しは、新しい通信路を、いつもの手順で開くだけである。`istesso-link` の手順も、パケットの並びも、変えていない。音源は、新しい申し込みが来れば、古い接続への送信をやめて、そちらに送る（「あとから申し込んだ出口に切り替わる」の決まりのまま）。
- つなぎ直さない場合：音源が自分で終わりを知らせたとき（ほかの出口に切り替わったのかもしれない。取り返し合いにしないため）。音源に断られたとき（ペアリングか、音の権限がなくなっている）。

接続の最初のメッセージで、何の接続かを決めます。メッセージは `Channel` の 1 メッセージずつで、最初のやり取りは JSON です。

| 向き | 内容 |
|---|---|
| 出口 → 音源 | `{"type":"subscribe","version":1}` |
| 音源 → 出口 | `{"type":"stream","version":1,"stream_id":"…","sample_rate":48000,"channels":2,"format":"f32le","packet_frames":256}`。断るときは `{"type":"error","code":"forbidden","message":"…"}` |
| 音源 → 出口（以後くり返し） | 音のパケット（下の表） |

音のパケット（リトルエンディアン）：

| 位置 | 長さ | 内容 |
|---|---|---|
| 0 | 1 | この並びの版（1） |
| 1 | 1 | 種類。1：音、2：音源に鳴らすものがないことの知らせ、3：終わり |
| 2 | 1 | 旗。ビット 0：前のパケットとつながっていない |
| 3 | 1 | 予約（0） |
| 4 | 4 | 連番 |
| 8 | 8 | ストリームの先頭から数えた、最初のフレームの位置 |
| 16 | 8 | 最初のフレームを取り込んだ時刻（音源の単調な時計、ナノ秒） |
| 24 | フレーム数 × チャンネル数 × 4 | サンプル（32 ビット浮動小数、チャンネルを交互に並べる） |

フレーム数は、パケットの長さから決まります。TCP の上では、連番は要りません。あとで認証つきのデータグラムに載せ替えられるように、最初から入れておきます。知らない種類のパケットは読み飛ばし、知らない版は断ります。数でない値（NaN など）は、受け取った側で無音に替えます。

音源に鳴らすものがないときは、0.1 秒たってから、0.1 秒おきにそのことを知らせます。出口が、無音と、切れた接続を取り違えないためです。

遅延を測るには、2 台の時計の差が要ります。同じポートへの別の接続で、時刻を尋ねます。

| 向き | 内容 |
|---|---|
| 出口 → 音源 | `{"type":"time","t1":…}`（出口の時計） |
| 音源 → 出口 | `{"type":"time","t1":…,"t2":…,"t3":…}`（`t2` は受け取った時刻、`t3` は返した時刻。音源の時計） |

出口は、返事を受け取った時刻と合わせて、時計の差と往復時間を出します。往復時間がいちばん短かった回を使います。誤差は、往復時間の半分より小さくなります。

### 4.4 再生と、時計のずれ補正（Mac）

- `istesso audio play <ホスト>` が、Core Audio の出力ユニットを、選んだ機器で開く。指定しなければ、システムの既定の出力。
- **機器の設定は変えない。** サンプルレート、バッファーの大きさ、音量は、読むだけで書かない。排他的に使うこともしない。機器が 44.1 kHz で動いていれば、こちらが合わせる。
- 機器が音を引き取るコールバックの中で、待ち行列 → リサンプラー → 機器、の順に引く。そこでは待たず、メモリーも確保しない。リサンプラーは rubato の非同期のもの（sinc 補間）。
- **受信のスレッドは、機器のスレッドと同じ種類の優先度（時間の制約つきのリアルタイム）で動かす。** ふつうのスレッドは、Mac で、1 分に数回、10〜26 ms 待たされる。受信のスレッドが待たされると、その分だけ音が遅れて届き、途切れる。権限は要らない。

**待ち時間**を、パケットが届いてから、その先頭のフレームが機器に渡されるまでの時間と決めます。保つのは、**いちばん速く届いたパケットの待ち時間**です。途中で遅れたパケットは、その分だけ待ち時間が短くなります。それはネットワークの話で、時計の話ではないので、直近 1 秒でいちばん長い待ち時間だけを見ます。

- リサンプラーの比は「機器のレート ÷ 48000 ×（1 ＋ 補正）」。補正は、待ち時間を目標に保つように、ゆっくり動かす（比例と積分の制御。1 巡りに約 2 分）。
- 補正の大きさは 0.1% まで、変わる速さは 1 秒に 100 ppm まで。それより大きな誤差は、補正に任せない（4.5）。
- **再生は、ちょうど目標の時刻に始める。** いちばん速いパケットの待ち時間が、いま求められているフレームのあいだに目標に届くなら、その位置から音を出す。たまりすぎていたら、古い分を捨ててから始める。

待ち時間の目標は、既定で 40 ms です。このうち、パケットが遅れてよい分は約 12 ms しかありません。機器は、渡す時刻の約 11 ms 前に、1 回ぶん（512 フレーム、10.7 ms）をまとめて引き取りに来るからです（[Mac での計測](measurements/2026-11-16-m2-step2-mac-playback.md)）。

| 使いみち | 長さ |
|---|---|
| 機器が、渡す時刻より先に引き取りに来る分 | 11.1 ms |
| 機器が 1 回に引き取る分 | 10.7 ms |
| フェードのために手元に残す分 | 4.7 ms |
| リサンプラー | 1.4 ms |
| 残り：パケットが遅れてよい分 | 約 12 ms |

**遅延の目標：取り込みから機器に渡すまで、有線で、中央値 50 ms 以下。** 待ち時間 40 ms に、パケット 1 つぶん（5.3 ms）と、経路と送る側の処理を足した値です。Mac の中だけのテストでは 46.9 ms でした。耳に届くまでには、機器が申告する遅れ（内蔵スピーカーで 2.3 ms）がさらに足されます。2 台での値は、短いテストで測ります。Wi-Fi など、パケットが 12 ms より遅れる経路では、待ち時間の目標を上げることになり、遅延もその分だけ延びます。

映像の追加遅延は十数 ms が目標なので、音は映像より 30〜40 ms ほど遅れて届く見込みです。音が映像より遅れる側は、125 ms あたりまで気づかれにくいとされています（ITU-R BT.1359）。映像と音を合わせ込むことは、M2 の範囲に入れません。

**ずれ補正が音程に与える影響**は、時計を模擬して確かめました（[記録](measurements/2026-11-16-m2-step1-simulated-clocks.md)）。時計の差が ±100 ppm（合わせて 200 ppm まで）でも、44.1 kHz の機器でも、8 時間のあいだ途切れも飛ばしもなく、始まって 5 分たてば、聞こえる音程は音源の音程から 50 ppm（0.09 セント）以内にとどまります。静かな経路では 5 ppm 以内です。この 2 つの数値は、試験で上限として検査しています。

### 4.5 途切れと欠落

- TCP なので、音が欠けることはない。遅れて届くだけで、遅れは待ち行列が吸収する。
- **空になったとき：** フェード（3 ms）で終えて無音にし、回数と長さを数える。フェードに要る分は、いつも手元に残してある。目標までたまり直したら、フェードして再開する。そのとき、たまりすぎていた分は捨てる。
- **たまりすぎたとき：** 届いたパケットの待ち時間が、目標より 20 ms を超えて長くなったら、あいだの音を捨てて先へ進み、短いクロスフェードでつなぐ。回数と、捨てたフレーム数を数える。**遅れた分を、リサンプラーで少しずつ取り戻すことはしない。** 遅延は、経路が止まったあとも、目標のまわりに戻る。
- **音源が音を捨てたとき**（位置が飛んだパケット）：同じクロスフェードでつなぎ、数える。
- **音源に鳴らすものがないとき：** 出口は無音を出し、途切れには数えない。鳴り始めたら、目標までためてから再開する。
- **接続が切れたとき：** 待ち行列は空になり、フェードで終えて無音にする。つなぎ直したあとの最初の音は、前とつながっていない印を付けて渡し、目標までためてから、フェードして再開する。切れた回数を数える。
- 数えた値は、動いているあいだも、終わったあとも見られる。受け入れ条件の「途切れない」は、この値が 0 であることで確かめる。

### 4.6 映像のセッションから独立していること

- 音は、映像とは別のプロセス、別の接続、別のポートで流れる。映像のセッションの状態を見ない。
- 窓を閉じても、仮想の出力先と音の接続は残る。
- 接続は「音源のホストと、出口」の組に属する。操作する端末を替えても、出口が同じなら、流れ続ける。
- いまは、手で起動するコマンド（`istesso audio serve`、`istesso audio play`）。エージェントの中に入れて常駐させるのは、あとの段階（「6. 手順」）。

### 4.7 再生中は眠らせない

短いテストのあとで作ります。どちらも root は要りません。

- 出口（Mac）：音が流れているあいだ、眠りを止める（OS の電源のアサーション）。Core Audio が再生中に自分で眠りを止めているかどうかを、先に確かめる。いまは、`istesso audio play --keep-awake` が、OS に付いている道具（`caffeinate`）を、再生のあいだだけ動かす。長い確認のための仮の形である。
- 音源（Ubuntu）：出口がつながっていて、音が流れているあいだ、眠りを止める（systemd-logind の inhibitor）。
- 無音が続いたら外す。何も鳴っていないのに、PC を起こし続けないため。

### 4.8 手を入れない経路

- ホスト：いまある出力先（DAC など）と、その設定には触らない。仮想の出力先を 1 つ足すだけ。
- Mac：機器のサンプルレートを変えない。配信の音を出すために、DAC のレートを 48 kHz に切り替えることはしない。
- どちらも、導入の前後でローカル再生の音が変わらないことを、ADR 0005 の受け入れ条件として確かめる（M2 の後半）。

### 4.9 足したもの

クレート `istesso-audio`：

| モジュール | 内容 | 実機が要るか |
|---|---|---|
| `wire` | 接続の最初のやり取りと、パケットの並び | 要らない |
| `source` | 取り込みのスレッドからパケットまで。送るのが遅れたら古い音を捨てる。テストの音源（正弦波、パイプ） | 要らない |
| `session` | 接続の両端。`istesso-link` の `Channel` の上で動く。権限の確かめと読み直し、締め切り、時刻の問い合わせ | 要らない（1 台の中で両方を動かせる） |
| `fifo` | 受信のスレッドと、機器のスレッドのあいだの待ち行列（待たない） | 要らない |
| `playout` | 待ち行列を、機器の速さで再生する。始め方、途切れ、飛ばし、つなぎ | 要らない |
| `control`、`resample` | ずれ補正の制御と、リサンプラーの包み | 要らない |
| `sim` | 音源、ネットワーク、機器を、それぞれの時計つきで模擬する | 要らない |
| `probe`、`ledger` | テストの正弦波と、録った音の調べ方。両端で取ったパケットごとの指紋の突き合わせ | 要らない |
| `mac` | Core Audio の出力 | Mac の実機 |
| `linux` | PipeWire の取り込み（仮想の出力先）。機能 `pipewire` を有効にしたときだけ | Ubuntu の実機（受け取った音をリングに書く部分は、実機なしで試験している） |

コマンド：

| コマンド | 動かす場所 | 内容 |
|---|---|---|
| `istesso audio serve` | 音源 | 音の権限を持つ出口に送る。音源は、`--source pipewire`（アプリが仮想の出力先に流した音。Linux で、機能 `pipewire` を有効にしてビルドしたとき）、`--source tone`（正弦波）、`--source stdin`（標準入力の PCM） |

| `istesso audio outputs` | 出口 | その PC の出力の機器を並べる（いまは macOS だけ） |

| `istesso audio simulate` | どちらでも | 時計を模擬して再生の部分を回し、結果を JSON で出す |
| `istesso audio test-tone` | 音源（テスト用） | テストの正弦波（既定は 997 Hz、−60 dBFS）を作るノードを、PipeWire に置く。どこにも自動ではつながらない。`pw-link` で、仮想の出力先に手でつなぐ。Linux で、機能 `pipewire` を有効にしてビルドしたとき |
| `istesso peers allow <端末> <権限>`、`istesso peers deny …` | 音源 | 権限を与える、取り消す。`istesso peers list` は権限も表示する |

### 4.10 共有のクレートへの変更

`istesso-proto` と `istesso-link` は変えていません。`Channel` と `LocalKeys` を、いまの公開の形のまま使っています。

**済んだもの（`istesso-pair` と `istesso-cli`。ほかと分けた 1 つのコミット）：** 音の権限を与える手段がなかったので、足しました。先に [ADR 0006](adr/0006-pairing.md) を直しています。

```rust
// crates/istesso-pair/src/store.rs
impl PeerStore {
    pub fn set_permission(
        &mut self,
        selector: &str,
        permission: Permission,
        allowed: bool,

```

```text

istesso peers deny  <device> <view|control|install_apps|usb|audio>
istesso peers list        # 権限も表示する
```

**あとの段階で相談したいもの：**

- 出口の候補を、全ホストぶん並べる（R-08「出力先の一覧には全ホストの機器を並べる」）。

  ```rust
  // istesso-proto
  /// A device that sound can come out of, on one host.
  pub struct AudioOutput {
      /// Stable on that host.
      pub id: String,
      pub name: String,
      pub channels: u16,
      pub sample_rate: u32,
      pub is_default: bool,
  }

  // istesso-link (message.rs). Needs the `view` permission.
  Request::AudioOutputs
  Response::AudioOutputs { outputs: Vec<AudioOutput> }
  ```

- 音の接続を、エージェントのポート（47801）に寄せるかどうか。寄せるなら、制御チャンネルの接続を音の配信に引き渡す口（`Session::into_channel(self) -> Channel<TcpStream>`）と、申し込みのリクエストが要る。寄せなければ、`istesso-link` は変えずに済む。
- 「4.3 経路」のメッセージの型を、`istesso-audio` に置くか、`istesso-proto` に置くか。いまは `istesso-audio` にある。
- ハンドシェイクと最初のメッセージに 1 つの締め切りを与える部分を、`istesso-link` のものに替える。いまは `istesso-audio` の中に、小さな包みとして持っている。映像の作業の側が、同じ役目のもの（`Channel::respond_within`）を `istesso-link` に足したので、それが `main` に入ったら、こちらの包みは外す。

## 5. 短いテスト

1 回の長さは 60 秒が基本で、長くても 2 分です。**音は出しません。** Mac の機器には無音を渡し、渡すはずだった音をファイルに録って、デジタルで確かめます。機器の時計は本物なので、ずれ補正は実際の条件で動きます。

| 測るもの | 測り方 | 目安 |
|---|---|---|
| 経路で変わっていないこと | 両端で、パケットごとに連番・位置・サンプルの指紋を取り、突き合わせる（`istesso audio compare`） | 全部が同じ。連番の抜け 0 |
| 途切れ | 待ち行列が空になった回数と長さ、飛ばした回数とフレーム数。録った音の、音の谷と波形の飛び | 始まったあとは、どれも 0 |
| **届く間隔** | パケットが届いた間隔の、中央値、95 パーセンタイル、99 パーセンタイル、最大（いちばん長い停止） | 記録する。**待ち時間の目標は、これで決める**（遅れてよい分が、いちばん長い停止より長くなるように） |
| 時計のずれ | 補正が覚えた、2 つの時計の差（ppm） | 記録する |
| 補正の動き | 補正の値と、待ち時間の最小・最大。録った正弦波の音程の範囲 | 待ち時間が目標から 1 ms 以内。音程のずれが 50 ppm 以内 |
| 遅延 | 取り込みから機器に渡すまで（2 台の時計の差は、時刻の問い合わせで出す）。中央値、95 パーセンタイル、99 パーセンタイル、最大 | 有線で、中央値 50 ms 以下（待ち時間 40 ms のとき） |
| 機器の引き取り | 1 回のフレーム数と、渡す時刻の何 ms 前に引き取りに来るか | 記録する |

2 台での最初の計測は、テスト用の正弦波で行いました（[記録](measurements/2026-11-16-m2-step3-cable-test-sources.md)）。遅延は目安に収まりました（中央値 46.5 ms）。音程のずれは、始まりと再開を含む 90 秒で ±69 ppm あり、目安を超えました。90 秒に 1 度、約 50 ms の停止があり、待ち時間 40 ms では途切れになりました。どちらも、両端を不利な優先度で動かした条件での値なので、本物の取り込みで測り直してから、目安と待ち時間の目標を見直します。

本物の取り込みでの計測は、Mac の再生を低い優先度で動かした形で、2 回行いました（[記録](measurements/2026-11-16-m2-step4-real-capture.md)）。受け取ったパケットはすべて送ったものと同じで、遅延は中央値 41.2 ms でした。待ち時間 40 ms では、85 秒のあいだに 20〜41 ms の停止が 1〜2 度あり、途切れました。音程は ±94 ppm まで動きました。Mac の再生をふつうの優先度で動かして、測り直します。**待ち時間の目標は、その結果で決めます。40 ms のままでは、8 時間は途切れずに通らない見込みです。**

目安は、測ったあとで見直します。結果は、1 回の計測を 1 つのファイルにして `docs/measurements/` に置きます（[measurements/README.md](measurements/README.md) の決まり）。

### 8 時間の確認

**1 回め（2026-11-17 の夜、待ち時間 60 ms、ホストの優先度はそのまま）は、不合格でした**（[記録](measurements/2026-11-17-m2-step5-eight-hours.md)）。

- 7 時間 47 分のところで、Mac の側で接続が切られて終わった。Mac でアプリが新しく登録されると、macOS がネットワークの決まりを作り直し、つながっている接続を切ることがある（切られたのは、自分の許可を持たないプログラムだった。記録を参照）。切れたらすぐにつなぎ直す仕組みを、このあとで作った（4.3）。
- それまでに、クリックが 23 回あった。ホストの取り込みの周期が飛んだとき（51 回）に、音が失われることがある。ホストのサウンドシステムが、リアルタイムの優先度で動いていないためとみている。
- 飛ばしが 5 回あった。Mac の機器が、音を引き取りに来なかったときとみている。原因は、確かめていない。
- 受け取った 525 万個のパケットは、すべて送ったものと同じだった。待ち行列が空になる途切れは、切られるまで 0 回。遅れは、積み上がらなかった（取り込みから機器に渡すまでの中央値は、はじめの 10 分が 61.2 ms、終わりの 10 分が 61.3 ms）。
- 合格の条件を見直す案を、記録に書いた（遅れが積み上がらないこと。音程の条件を、ふだんと、音源が遅れた直後とに分けること）。

次は、ホストの優先度の効果を短い計測で確かめてから、もう 1 度行います。下は、1 回めの動かし方です。Mac の再生は、`.app` としてではなく、シェルから `nohup` で起動しました。

**何を確かめるか。** 取り込みから機器に渡すまでが、8 時間、途切れないこと（ADR 0005 の受け入れ条件）。流すのは、テストの正弦波（997 Hz、−60 dBFS）です。途切れとクリックを、耳ではなく数で確かめるためです。Mac の機器には無音を渡すので、夜のあいだ、どちらの PC からも何も鳴りません。音楽を耳で聞く確認は、別に行います。

**動かし方。** どちらの側も、SSH のログインにも、作業中のセッションにも頼らない形で起動します。

```sh
# ホスト。tmux の中で動かすので、SSH が切れても止まらない。作業用の場所で、次の 4 つを順に実行するスクリプトを動かす。
tmux new-session -d -s m2-audio-run 'bash <スクリプト>'
#   1. 音源
istesso audio serve --source pipewire --bind <有線のアドレス> --port 47822 --seconds 28890 \
    --ledger sent.txt --stop-file stop --node-name istesso-audio-test \
    --node-description "Istesso audio test" --node-property device.routes=1 > serve.json 2> serve.log &
#   2. テストの正弦波（プログラムが作る。どこにも自動ではつながらない）
istesso audio test-tone --seconds 28880 --node-property device.routes=1 --stop-file stop &
#   3. 仮想の出力先に、手でつなぐ
pw-link istesso-audio-test-tone:capture_FL istesso-audio-test:playback_FL
pw-link istesso-audio-test-tone:capture_FR istesso-audio-test:playback_FR
#   4. 2 つが終わるのを待ち、前後の音の設定を比べる

# Mac。テスト用の .app として起動する。端末やセッションの子ではないので、それらが終わっても止まらない。
open -n -g IstessoAudioTest.app --env ISTESSO_CONFIG_DIR=<作業用の場所> --stderr play.log --args \
  audio play <有線のアドレス>:47822 --peer <音源の名前> --latency-ms <待ち時間> --seconds 28800 \
  --ledger received.txt --report report.json --connect-for 180 --keep-awake --stop-file stop
```

- `--keep-awake` は、再生のあいだ、Mac が自分から眠るのを止めます。ふたを閉じたときと、電池が切れたときは止められないので、Mac は開いたまま、電源につないでおきます。
- 途中でやめるとき：Mac では、`--stop-file` に指定したファイルを作ります（`touch stop`）。そこまでの結果が書き出されます。ホストでも、同じ名前のファイルを作ります（`tmux kill-session -t m2-audio-run` でも止まりますが、送った側の記録は書き出されません）。
- 映像の計測が始まったとき（AGENTS.md の「計測の合図」が busy になったとき）は、同じやり方で両方を止めます。
- Mac が眠ったとき、接続が切れたとき：再生は、つなぎ直すまで無音になり、切れた回数と途切れが数えられます。確認は不合格になりますが、最後まで動きます。いつ切れたかは、記録でわかります。
- 待ち時間の目標：10 分の予行（[記録](measurements/2026-11-16-m2-step5-rehearsal.md)）では、40 ms で途切れなかったが、ホストの取り込みが 1 度 5 ms 遅れたときに、余裕は 4 ms しか残らなかった。ホストの優先度を変えないまま 8 時間を通すなら、60 ms（遅れてよい分は約 32 ms）を勧める。40 ms で通すなら、先に、ホストの優先度の効果を確かめる。
- 8 時間の確認の前に、2 台の時計の差を、動かしているあいだに測り直すようにする（いまは始めに 1 度だけ測るので、長い計測では、遅延の値がずれていく）。

**記録するもの。**

- Mac：1 秒ごとに、状態、待ち時間、補正、途切れと飛ばしの数。1 分ごとに、正弦波の大きさ、音程の範囲、クリックの数。終わりに、まとめ（`report.json`）：届く間隔の分布といちばん長い停止、取り込みから届くまで・機器に渡すまでの分布、補正の覚えた時計の差、正弦波の 8 時間ぶんのまとめ。受け取ったパケットごとの指紋（`received.txt`）。
- ホスト：送ったパケットごとの指紋（`sent.txt`）。音源の側で捨てた音、送るのにかかった時間、取り込みの周期のいちばん長い間隔（`serve.json`）。前後の `wpctl status` と、セッションマネージャーの状態のファイル。

**進め方（2026-11-17 に決定）。** 直すたびに 8 時間を流すことは、しません。途中は短く確かめ、最後に 1 回だけ長く流します。

短い確認：

- ホストの優先度の効果：上げる前と後を、30〜60 分ずつ。`sudo` の行は、持ち主が実行する。
- 優先度を上げられないホストのために、処理の周期を長くした場合（512、1024 フレーム）のクリックの数。遅れが増えるぶんと、引き換えで見る。
- 切れたあとのつなぎ直し：わざとアプリの登録を起こして、2 台で確かめる。

8 時間は、次の 3 つがそろってから、1 回だけ流します。そろっていなければ、流しません。

1. 受け取る側が、自分のローカルネットワークの許可を持つアプリの中で動いている。
2. 切れたあとのつなぎ直しが、2 台で確かめてある。目安は、**道がまた開いてから** 1 秒以内に、つなぎ直すこと。Mac がローカルネットワークの一覧を保存すると、システムは、そのあと 1〜2 秒のあいだ、何も通さない。そのあいだは、つなぎようがないので、数えない（2026-11-17 に、持ち主が読み方を決めた）。切れてから数えた値は、1.0〜1.8 秒で、1 秒には届いていない（[記録](measurements/2026-11-17-m2-step9-own-application-and-real-cut.md)）。
3. ホストの優先度の確認の結果を受けて、待ち時間と、ホストの優先度の扱いが決まっている。

**合格の条件（2026-11-17 に見直した）。** 次のすべてを満たすこと。クリックと飛ばしは、渡すはずだった音の正弦波を調べて数えます。

1. 28800 秒を、最後まで動いた。接続が切れたときは、つなぎ直して動き続けること。
2. 再生：途切れ 0、**飛ばし 0**、音源の側の抜け 0。
3. 受信：失われたパケット 0、つながっていないパケット 0、待ち行列に入らなかったフレーム 0、「鳴らすものがない」の知らせ 0。
4. 音源：捨てた音 0。取り込みの周期が 1 秒以上あいたこと 0。
5. `istesso audio compare sent.txt received.txt`：受け取ったパケットが、すべて送ったものと同じで、あいだに抜けがない。
6. 正弦波：音の谷 0、**クリック 0**。大きさは、8 時間を通して −60 dBFS から 0.1 dB 以内。
7. ホストの音の設定が、前後で同じ。
8. **遅れが積み上がらないこと：** 取り込みから機器に渡すまでの中央値が、はじめの 10 分と終わりの 10 分とで、2 ms 以内。
9. **音程：** ふだんは、1 分ごとのいちばん大きなずれが 100 ppm（0.17 セント）以内。音源が遅れた直後は、0.1%（1.7 セント）以内で、1 分以内に、ふだんの範囲に戻ること。
10. **負荷がかかっていても（2026-11-17 に、持ち主が決めた）：** クリックと飛ばしは、その PC でビルドが走っているあいだも 0。最後の 8 時間の確認には、負荷をかけた時間を入れる。その前に、ホストと Mac のそれぞれで、静かな 10 分と、ビルドを走らせ続けた 10 分とを比べる（負荷を記録する）。

いちばん長い停止、待ち時間の範囲、時計の差、遅延、ホストの取り込みが遅れた回数、Mac の機器が音を引き取りに来なかった回数は、記録しますが、合否には使いません。

公開のあとも、夜に流します。1 行で始まり、朝に結果が 1 つ出る形（クリック、飛ばし、切断の回数と、試した版）にして、晩ごとの数字を並べて見られるようにします。作るのは、最後の 8 時間が通ってからです。

そのあとは、短いテストの結果を見て決めます。

- エージェントの中に入れて、常駐させる。出口を選ぶ操作（選んだら既定の出力先を切り替え、やめたら戻す）。
- 切れたときのつなぎ直し、眠りを止める仕組み（4.7）。
- 待ち時間の目標を、届く間隔を見て自動で決める。
- 8 時間のテスト（M2 の受け入れ条件）。夜に行い、先に知らせる。
- 逆の向き（Mac の音を Ubuntu から出す）。Mac の取り込みには、OS の許可が要る。理由を ADR に残してから進める（AGENTS.md）。
- 入る音（マイク）は、今回は範囲に入れない（ADR 0005）。
- Windows は、今回の公開には含めない（決定）。あとから足せる作り（R-14）は保つ。音では、取り込みと再生の入出力を書けば足せる。

### `pipewire` グループで、優先度の上限を上げる試し（次の再起動のときに）

ホストの PipeWire は、リアルタイムの優先度で動いていません。こちらの取り込みがリアルタイムなのは、デスクトップにログインしている人がいるあいだだけ、とみています（[記録](measurements/2026-11-17-m2-step7-missed-cycles-and-reconnect.md) の 3.1）。製品のホストには、だれもログインしていないので、ログインに頼らない方法を、原因が何であっても、試します。PipeWire のパッケージが入れている設定（`/etc/security/limits.d/25-pw-rlimits.conf`）は、`pipewire` グループに、リアルタイムの優先度 95 まで、nice −19 まで、メモリの固定 4 GiB までを許します。この設定は、ユーザーのサービス管理が始まるときにも読まれます（その PAM の設定に、上限を読む部品が入っている）。

**順番。** 遅延の最後の判定のあと、ホストを再起動するときに、1 回だけ行います。比べるのは、ログイン画面だけの状態（デスクトップに、だれもログインしていない。ssh だけ）です。

1. 前：スレッドの状態を記録し、負荷をかけた 10 分を測る（下の 2 行）。
2. 持ち主が、ホストで 1 行を実行する：`sudo gpasswd -a "$USER" pipewire`
3. ホストを再起動する。デスクトップには、ログインしない。Mac から、ssh だけをつなぎ直す。
4. 後：同じ 2 行。そのあと、[M1 の計画](m1-plan.md) の「ホストを再起動したあとに、確かめ直すこと」（`m1-latency` のブランチ。GPU とカーネル）を確かめる。

元に戻す行：`sudo gpasswd -d "$USER" pipewire`（効くのは、次の再起動から）。

**前と後の 2 行**（作業用のスクリプト。`<名前>` は、前が `rl-before`、後が `rl-after`）。

```sh
M2_HOST_OPTS=profile bash m2-long-run.sh <名前> 600 60 lock shell 256 0 load-host-decode   # 負荷をかけた 10 分。音は出ない
bash m2-threads.sh <名前>                                                               # 上の行が動いているあいだに。読むだけ
```

**再起動のあとに見るもの**（2 行めが書き出す）。

- 持ち主が `pipewire` グループに入っている。
- PipeWire、pipewire-pulse、WirePlumber のプロセスの上限が、リアルタイムの優先度 95、nice −19 になっている。
- それぞれの処理のスレッド（`pw-data-loop`）が、リアルタイム（設定が求める優先度 88）で動いている。
- こちらの取り込みと、テストの正弦波の処理のスレッドが、ログイン画面だけでも、リアルタイムで動いている。優先度が 88 なら上限から、20 ならポータルからもらっている。
- 負荷をかけた 10 分の、取り込みの周期の遅れ、クリック、飛ばしの数。周期ごとの時刻から見た、逃した理由。

**気をつけること。**

- 前の状態は、デスクトップにログインしている人がいる状態である。前と後とでは、グループと、ログインの有無の、2 つが変わる。どちらが効いたかは、スレッドの優先度（88 か 20 か）で見分ける。
- グループに入ると、持ち主のどのプログラムも、だれにも頼まずに、リアルタイムの優先度を名乗れるようになる。RTKit の見張り（暴走したスレッドを止める）は、この経路には効かない。
- メモリを固定できる量の上限が、いまの約 23 GiB から、4 GiB に下がる。大きなメモリを固定するプログラムを使っているなら、先に確かめる。

### アプリ全体に署名して、許可が覚えられるかを確かめる試し

署名のないアプリでは、ローカルネットワークの許可の確認が、1 回で済まないことがあり、システム設定の一覧に、アプリの行が出ません（[記録](measurements/2026-11-17-m2-step9-own-application-and-real-cut.md)）。Apple の技術資料（TN3179）は、macOS がプログラムを署名で見分けること、そのために、プログラムの本体が、ほかと重ならない UUID を持つことを求めています。同じ試しを、全体に署名したアプリで、やり直します。

開発のあいだは、持ち主の Developer ID は使いません。この Mac の中だけで作った証明書（自己署名の、コード署名用）を使います。**証明書を作るのは、持ち主です**（キーチェーンに触るため）。

持ち主に頼む手順（1 回だけ）：

1. 「キーチェーンアクセス」を開く（Spotlight で探す）。メニューの「キーチェーンアクセス」›「証明書アシスタント」›「証明書を作成…」を選ぶ。
2. 名前に `Istesso Development`、固有名のタイプに「自己署名ルート」、証明書のタイプに「コード署名」を選んで、「作成」を押す。証明書は、「ログイン」のキーチェーンに入る。
3. こちらが、はじめて署名するときに、「codesign が、キーチェーンの中のキーを使おうとしています」という確認が出る。ログインのパスワードを入れて、「常に許可」を押す。

そのあと、こちらがすること（キーチェーンには、署名のために鍵を使うほかは、触らない）：

- 出口のプログラムを、`istesso` のコピーではなく、それだけの名前を持つ別のプログラムとして作る。`dwarfdump --uuid` で、ほかのプログラムと UUID が重ならないことを確かめる。
- アプリを、決まった場所（案：ホームの `Applications`。管理者の権限が要らない）に置く。
- アプリ全体に署名する：`codesign --force --sign "Istesso Development" --identifier dev.istesso.audio-exit "<アプリ>"`。署名の名前がアプリの識別子と同じで、`Info.plist` が署名に含まれていることを、`codesign -dvv` で確かめる。
- 試し：3 回続けて起動する（確認が出るのは 1 回めだけか）。一覧に、アプリの名前の行が出るか。ほかの行を切り替えたとき、こちらの接続が切れるか。プログラムを作り直して、同じ証明書で署名し直したとき、確認がもう一度出るか。

**署名したアプリに要ること：** 署名の名前がアプリの識別子と同じ。`Info.plist` が署名に含まれている（プログラムだけでなく、アプリ全体に署名する）。プログラムのファイル名が、人が見て分かる名前。置き場所が決まっている。プログラムの本体の UUID が、ほかのプログラムと重ならない。

TN3179 が確かだと言っているのは、Apple の発行した証明書で署名した場合です。自己署名の証明書で足りるかどうかは、この試しで分かります。足りなければ、開発のあいだも、Apple の発行した証明書が要ることになります。
