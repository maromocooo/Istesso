# 層 3：鍵の番人（設計の案）

- 状態：設計の案（2026-11-21）。**コードはまだ書かない**（配27）。暗号の所は【Needs Fable】。持ち主が決めていない所は【問い】。
- 調べたこと（出どころ、印の意味、「資」の番号）は [key-protection.md](key-protection.md) にある。この文書の「資n」は、その 7 章の番号である。資22（下）だけ、この文書で足した。
- 層 1 は ADR 0021（ブランチ `m5-clone-detect`）。層 2 は [key-layer2-hardware.md](key-layer2-hardware.md)。
- 仮の名前：番人＝`istesso-keeper`。

## 1. 目的

配27 の層 3：「鍵を持つ小さなプログラムを、持ち主のプログラムから読めない形で置く。鍵そのものは渡さず、『つなぐ』仕事だけをする。入れるときに sudo を 1 回使える機械で。」

| 守れること | 守れないこと |
|---|---|
| 持ち主のユーザー（と、M5 のアプリの専用ユーザー、コーディングの専用ユーザー）で動くプログラムが、身元の鍵、層 1 の値を**読む・持ち帰る** | そのプログラムが、**いるあいだに**番人に「つなぐ」を頼むこと（配27 の「正直に書くこと」） |
| 乗っ取られたエージェント（脅威モデルの攻6）や、同じ専用ユーザーのアプリ（攻1）が、鍵を持ち帰る | root。root は番人のメモリもファイルも読める |
| ディスクの写しから鍵を使う（systemd-creds の `tpm2` のとき。資11） | 番人そのものの不具合（番人が乗っ取られれば、鍵に届く） |

**層 2 と同じく、証明をつなぎごとにしないと「持ち帰れない」にならない**（key-protection.md の 0 章の 3）。番人が「この X25519 の鍵に証明を付けて」と頼まれて署名する形では、頼んだプログラムが証明を持ち帰れる。だから番人は、**証明を付ける署名を、自分で行うハンドシェイクの中でだけ作る。** 【Needs Fable】

## 2. どこで効くか

| 機械と役 | いま、鍵を読めるもの | 番人を入れると |
|---|---|---|
| Linux のホスト（M5 の形。エージェントは専用ユーザー `istesso`） | 専用ユーザーで動くすべて（エージェント、アプリ） | エージェントもアプリも読めない。いちばん効く |
| Linux の机の、手元の端末 | 持ち主のユーザーのすべて | 持ち主のプログラムは読めない |
| Mac Studio（ホストの役が持ち主のユーザーで動く） | 持ち主のユーザーのすべて | 読めない。ただし、署名した版のデータ保護キーチェーン（key-protection.md の 5 章）でも、同じ所まで守れる（推） |
| Mac の手元の端末、署名した版 | （キーチェーンなら）Istesso だけ | 増えるものは小さい（推）。署名した版は、キーチェーンと Secure Enclave を先に使う |
| Mac、自分でビルドした版 | 持ち主のユーザーのすべて | 読めない。キーチェーンの条件（プロファイル）がない版には効く |

結論（案）：**番人は、まず Linux（ホストと机）から。** Mac は、署名した版ではキーチェーンと Secure Enclave で足り、自分でビルドした版のために、あとで考える。

## 3. 形

### 3.1 ユーザーと置き場所

| もの | Linux | macOS |
|---|---|---|
| 番人のユーザー | システムのユーザー `istesso-keeper`（ログインできない） | `_istessokeeper`（推。名前の決まりは Apple の慣習に合わせる） |
| 番人の起動 | systemd のシステムのサービス | launchd のデーモン（`/Library/LaunchDaemons`、または署名した版なら `SMAppService.daemon`：資22） |
| 鍵の置き場所 | `/var/lib/istesso-keeper/`（0700、番人）。身元の鍵は systemd-creds で暗号化して置き、サービスの起動のときに `$CREDENTIALS_DIRECTORY` へ（資11）。TPM があれば `tpm2`、なければ `host` | `/Library/Application Support/Istesso/keeper/`（0700、番人）。データ保護キーチェーンはデーモンから使えない（資2）。Secure Enclave は CryptoKit で使えるが、公式に支えられていない（資4）【Needs Fable F5】 |
| 口 | Unix ドメインソケット `/run/istesso-keeper/sock` | Unix ドメインソケット、または XPC（推） |
| 番人が持つもの | 身元の鍵、層 1 の値、（【問い】1）ペアリングの一覧と権限 | 同じ |

### 3.2 だれが頼めるか

- ソケットのフォルダーは、番人と、決めたグループ（仮 `istesso-keeper-users`。持ち主、アプリの専用ユーザー `istesso`）だけが入れる。
- 番人は、頼んだ相手を、カーネルが教える資格で確かめる。Linux：`SO_PEERCRED`（つないだときの uid と pid。資22）。macOS：`LOCAL_PEERCRED` と監査トークン（推）。署名した Mac の版なら、XPC で相手のコード署名の条件を確かめられる（`setCodeSigningRequirement`、macOS 13 から：資22）。
- Linux では、頼んだのが本物の Istesso かどうかは、確かめられない（同じユーザーのどのプログラムも、同じ資格で頼める：推）。**だから、番人ができることを「つなぐ」だけにして、持ち帰れるものを渡さない。**

### 3.3 番人の仕事（これだけ）

| 仕事 | 中身 |
|---|---|
| `connect(相手の指紋, アドレス)` | 番人が TCP でつなぎ、Noise XX のハンドシェイクと、つなぎごとの証明（層 2 の 4 章の 3）と、層 1 の値の確かめ・進めを行う。済んだら、つながったソケットを、頼んだプロセスに渡す（`SCM_RIGHTS`：資22） |
| `accept`（ホストの役） | 番人が待ち受け、相手を確かめ、つながったソケットをエージェントに渡す。相手の指紋と権限を一緒に渡す |
| `pair` | ペアリング（SPAKE2 と、身元の鍵での署名。ADR 0006）を番人が行う。コードを出すのは、頼んだ側（画面のある側） |
| `status` | 指紋（公開鍵の短い形）、鍵の形（ファイル、TPM で暗号化、Secure Enclave）、層 1 の状態（値は出さない） |

番人が**しないこと**：鍵を渡す。頼まれた任意のバイトに署名する。層 1 の値を返す。鍵、トークン、コード、署名した中身を記録に書く（AGENTS.md の 4）。

### 3.4 通信の鍵をどう渡すか【Needs Fable F4】

ハンドシェイクのあとの通信の鍵（そのつなぎだけのもの）を、どう扱うか。

| 案 | 中身 | 良い所 | 悪い所 |
|---|---|---|---|
| A：番人が中継する | 頼んだプロセスと番人はソケットで話し、番人が暗号化して相手へ送る | 通信の鍵も番人の外に出ない | 映像と入力の道に、プロセスが 1 つ増える。遅れを測るまで使えない（AGENTS.md の 3） |
| B：記述子と通信の鍵を渡す | 番人は、つないだ記述子と、そのつなぎの通信の鍵を渡し、身を引く | 道は今と同じ。遅れが増えない（推） | 通信の鍵は、頼んだプロセスのメモリにある。ただし、そのつなぎだけで、ほかのつなぎには使えない |

おすすめ（案）：**B。** 持ち帰られても、使えるのは、そのつなぎのあいだだけである（「いるあいだの使用」の中に収まる）。`snow` から通信の鍵を取り出して渡す方法は、Fable と決める（ライブラリの API を確かめる）。

## 4. 入れる・上げる・外す

| 場面 | Linux | macOS |
|---|---|---|
| 入れる（sudo 1 回） | ユーザー、フォルダー、systemd のユニットを作る。**新しい鍵を番人の中で作る**（今の鍵を移さない。移すと、古いファイルとバックアップに写しが残る）。ペアリングを 1 回やり直す（11-20 の持ち主の決めと同じ考え） | ユーザー、フォルダー、launchd の plist を作る。`SMAppService` なら、ログイン項目の設定で、持ち主の許しが要る（資22）。同じく新しい鍵 |
| 上げる | パッケージの更新。鍵と層 1 の値は残す。口に版を持たせる | 同じ |
| 外す | ユーザー、ユニット、フォルダーを消す。ホストの一覧から、この端末の鍵を外す | 同じ |
| 番人が動いていない | Istesso は止まり、そう知らせる。**黙ってファイルの鍵に戻らない**（配軽1 の「囲いなしで黙って動かさない」と同じ考え） | 同じ |

## 5. 速さ

| 増えるもの | 大きさ | 印 |
|---|---|---|
| 番人のソケットの往復と、記述子の受け渡し | 1 つなぎに 1 回。0.1 ms より小さい | 推 |
| 署名（Ed25519 をソフトで） | 1 つなぎに 1 回。0.1 ms より小さい | 推 |
| 署名（Secure Enclave） | 約 4.4 ms | 実（Air） |
| 署名（TPM） | 約 100〜600 ms。だから番人は TPM で署名せず、TPM は鍵を包むのにだけ使う | 資12 |
| 案 A の中継 | メッセージごと | 測っていない。映像と入力の道では、測るまで使わない |

つなぎ直し（ADR 0007）と、短い接続の数が多い所では、Fable と、つなぎの数を減らす形（長く開けておく、1 本に束ねる）も考える。

## 6. 層 1 とのつながり

- 層 1 の値は、番人が持つ。持ち主のプログラムは、値を読めず、写せない。
- だから、番人のある機械では、層 1 が鳴るのは、番人ごと写された（root か、ディスクの写し）ときか、バックアップから戻したときになる（推）。
- 層 1 の「持ち主が確かめて戻す道」は、番人の `status` と、持ち主の手（sudo か、機械の前での確かめ）を通す（【問い】2）。

## 7. 【Needs Fable】

- F1（つなぎごとの証明）が、番人の前提である（key-protection.md の 6 章）。
- F3：番人に頼める回数の上限と、記録（回数と相手の指紋だけ。中身は書かない）。
- F4：上の 3.4。
- F5：macOS のデーモンから CryptoKit の Secure Enclave を使うこと。

## 8. 【問い】（持ち主へ）

1. **ペアリングの一覧と権限も、番人に持たせるか。** 持たせないと、同じユーザーの悪いプログラムが、一覧に自分の端末を書き足せる（いまもできる。脅威モデルの資5）。持たせると、権限を変える `istesso peers allow` などを、だれが頼めるかを決める要がある（同じユーザーのプログラムも頼めるので、機械の前での確かめか、sudo を求める）。おすすめ（案）：持たせる。権限を増やす操作とペアリングは、sudo か、層 4（指紋など）で確かめる。減らす操作は、今のまま、どこからでも（M5 の決め）。
2. 層 1 が鳴ったとき、元に戻す操作に、sudo を求めてよいか。
3. 番人を、まず Linux（ホストと机）から作り、Mac は署名した版のキーチェーンと Secure Enclave で進める、でよいか。
