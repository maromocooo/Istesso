## 0. 前提と、印の意味

持ち主の決め 1（2026-11-19）：**プロジェクトのフォルダーは、必ず 1 台の持ち物。** そこで始めたもの（シェル、エージェント、ビルド、開発サーバー）は、その機械で動く。**同期や複製はしない。** ほかの機械からは、マウントで見える・開けるだけ。

この調査が探したもの：1 台にあるフォルダーを、**全部の機械（Air、Ubuntu、Studio。のちに AURA）で同じパスに**見せる形。速さは「一覧と中身が見える」程度でよい。Mac では、追加の部品（macFUSE、カーネル拡張）を入れずにできるものに限った。

ADR 0013（提案）は、段階 3（マウント）の方式を「別の ADR で決める」としていた。この文書は、その材料でもある。ADR 0013 と決め 1 の食い違い（下の 8 章）は、計画の流れに渡す。

## 5. 安全の見方

### 5.1 マウントの認証

- **C1（ループバック NFSv3）には、マウントの認証がない。** NFSv3 の AUTH_SYS は、送る側が名乗るユーザー番号で、確かめにならない。`nfsserve` は、名乗りを見ていない。MOUNT の EXPORT の手続きが、出しているパスを誰にでも答える。
  - 実（Air）：ふつうのプロセス（カーネルの NFS クライアントではない）が、`127.0.0.1:<ポート>` につなぎ、EXPORT でパスを知り、MNT で根のハンドルを取り、ユーザー番号 4242 を名乗って LOOKUP と READ をして、ファイルの中身を読めた。
  - 推：ほかのユーザーのプロセスも同じことができる。ループバックの TCP に、ユーザーごとの区切りはない。Air には、いまふつうのユーザーが 1 人しかいない（実）ので、試していない。
  - 推：ハンドルに秘密を混ぜても、MNT が誰にでも根のハンドルを渡すので足りない。出すパスを秘密にしても、`mount` の表示（`127.0.0.1:/<パス>`）は、Mac のどのユーザーにも見える。予約ポート（1024 未満）の確かめは、macOS ではふつうのユーザーも低いポートを使えるので、効かない見込み。macOS の NFS クライアントは、UNIX ドメインのソケットを使えない（資：man mount_nfs の netid は tcp、udp、tcp6、udp6 だけ）。
  - 推：塞ぐ手は、どれも弱いか、root が要る。(a) マウントの直後に受け付けを止める（カーネルがつなぎ直すと、マウントが死ぬ）。(b) pf の `user` の決まりで、ソケットの持ち主で絞る（設定に root）。
  - **ADR 0003 の専用ユーザー（エージェントを別のユーザーで動かす形。流れ E）とぶつかる。** 見る側の機械で、専用ユーザーのエージェントが、持ち主のユーザーのループバックのポートにつなげば、マウントしたプロジェクトを読める（推）。
- **L1（Linux の FUSE）と C4（FSKit）には、ループバックのポートがない。** カーネルや OS と自前の係は、記述子か OS の仕組みでつながる（FUSE は資と実。FSKit は推）。
- C2（WebDAV）と C3（SMB）は、つなぎごとに資格を確かめられる（推）。C2 の資格の渡し方は試していない。

### 5.2 同じユーザーの線（m5-design の ADR 0021）

- ADR 0021 の【決定】：「Istesso は、OS が同じユーザーのほかのプログラムに許していないことを、Istesso を通して許さない」。その 2 は「ほかの PC に届く：ペアリングの信頼を借りて、ほかの PC の…絵や文字を受け取る」。
- **マウントは、その形からして、見る側の機械の同じユーザーのすべてのプログラムに見える。** これは、どの候補でも同じ（推。マウントは名前空間に置かれ、OS のファイルの権限で守られるだけ）。Linux では、マウントの名前空間で、決まったプロセスの木にだけ見せる手があるが、Ubuntu では特権のない名前空間が止められている（実）。macOS には、プロセスごとのマウントの名前空間がない（推）。
- だから、決め 1（ほかの機械からは、マウントで見える）と ADR 0021 の線のあいだに、【問い】がある（8 章）。

### 5.3 見る側の機械で、だれが読めるか

- マウント先の親は、0700 にしておく必要がある。Air のホームは `drwxr-x---`、グループ `staff`（実）。macOS のふつうのユーザーは、みな `staff` に入っている（推）。ホームの直下に 0755 のフォルダーを作ってマウントすると、ほかのユーザーがたどれる。
- C1 では、マウントを通さずに、ポートへ直接つなぐ道が残る（5.1）。

### 5.4 フォルダーの外へ出ないこと（パス、リンク）

- 試作の持ち主の側（`export`）は、フォルダーの記述子から、名前を 1 つずつ `openat(…, O_NOFOLLOW)` で開く。`..`、`/` を含む名前、空の名前、NUL を断る。リンクは、リンクとして一覧に出し、読むときは辿らない（`ELOOP` か `ENOTDIR` で断る）。パイプは開かない。
  - 実：Air と Ubuntu の両方で、この断り方のテストが通った（`cargo test`、8 件）。
- **リンクは、見る側で解決される。** 実（Air）：Ubuntu の `escape-rel -> ../../` は、Air の上のフォルダーを指した。`escape-abs -> /etc/hostname` は、Air の `/etc/hostname` を指した（Air にはないので、何も開かなかった）。持ち主の側のファイルは漏れない。そのかわり、見る側のアプリが、リンクを通して見る側の別のファイルを開くことがある（推。紛らわしい）。リンクを見せない、ファイルとして見せる、などの手は【問い】。
- ハードリンクは、パスでは見分けられない。プロジェクトの中のハードリンクが、外のファイルと同じ中身を指すことはありうる（推）。これは持ち主の機械の、エージェントの範囲（流れ E）の話である。

### 5.5 ファイルのロック

- 試作は `nolocks` でマウントした（読むだけ）。書くなら `locallocks`（見る側の中だけのロック）が使える（資：man mount_nfs）。機械をまたぐロックは、どの候補でも作っていない。
- 決め 1 で、ビルドとエージェントは持ち主の機械で動く。ロックが要るのは、持ち主の機械の中だけになる見込み（推）。

### 5.6 ユーザー番号

- 試作は、持ち主の側のユーザー番号を捨て、見る側のユーザーの持ち物として見せる。書く権利のビットも消す（読むだけ）。
  - 実（Air）：`ls -la` で、全部が見る側のユーザーとグループ `staff` の持ち物、`-r--r--r--` と `dr-xr-xr-x` に見えた。

### 5.7 大文字と小文字

- 実（Air ← Ubuntu）：ext4 の `CASE.txt` と `case.txt` が、Air の上で両方見え、中身もそれぞれ正しく読めた（Air の APFS は大文字と小文字を区別しないが、NFS のマウントは区別した）。
- 推：逆向き（Mac のフォルダーを Linux で見る）では、APFS が名前を区別しないので、`Readme` と `README` が同じファイルに当たる。Linux のアプリが別のファイルだと思うことがある。

### 5.8 拡張属性、リソースフォーク、`._` と `.DS_Store`

- NFSv3 には拡張属性がない。試作のマウントは読むだけなので、`xattr -w` は「Read-only file system」で断られた（実：Air）。
- 実（Air）：WebDAV のクライアントは、`._<名前>` を問い合わせた。推：書けるマウントでは、macOS が `._` のファイル（AppleDouble）と `.DS_Store` を持ち主のフォルダーに作る。書けるようにするなら、持ち主の側が、その名前を断る（または黙って捨てる）決まりが要る。

### 5.9 変更の知らせ

- 決め 1 では、開発サーバー、ビルド、エージェントは、持ち主の機械のローカルのディスクで動く。そこでは、ふつうの inotify と FSEvents が効く（推。持ち主の機械のディスクは、ふだんどおりのため）。
- 知らせが問題になるのは、見る側の機械のアプリ（Finder、エディター）だけ。
  - C1（実：Air）：FSEvents だけで見るアプリ（多くのエディターと監視の道具が使う：推）は、持ち主の側の変更を 12 秒のあいだ受け取らなかった。kqueue でそのフォルダーかファイルを見ていると、約 5 秒で知らせが来た（読み直しなしで）。そのとき、そのフォルダーについては FSEvents にも知らせが出た。推：macOS の NFS クライアントが、見張られているものの属性を、5 秒ほどごとに問い合わせている。
  - C3（SMB）は、サーバーの知らせを使う（資）。L1（FUSE）は、持ち主の側の変更を見る側の係が知って、カーネルへ知らせを送る作りが要る（推）。

### 5.10 持ち主の機械が止まったとき

- 実（Air）：持ち主の側の係を止めると、`ls` と `cat` は、すぐに（0.0 秒）「Input/output error」を返した。固まらなかった。マウントは `soft` で、試作の NFS サーバーは、持ち主の側の答えがなければ、すぐに誤りを返す。
- 推：見る側の NFS サーバーそのものが止まると、`soft` の待ち時間のあいだ、アプリが待たされる。

### 5.11 持ち主の機械のビルドに影響しないか

- 持ち主の側の係は、読むだけで、`O_NOFOLLOW` と `O_NONBLOCK` で開く。持ち主の機械のファイルを変えない（実：テスト。書く手続きを持たない）。
- 持ち主の機械のビルドは、ローカルのディスクを使い続ける（推）。係が読むぶんのディスクと CPU だけが増える。計測のあいだは、見る側の操作で持ち主の機械に読み込みが起きることに気をつける（推。計測の合図に従うかは【問い】）。

### 5.12 見る側のアプリの「ネットワーク上のボリューム」の許可（macOS）

- 実（Air）：このシェルの責任のアプリは、すでに許可されていた（`TCCAccessPreflight` が 0）。
- 資（二次）：macOS 10.15 から、アプリがネットワーク上のボリュームのファイルを開くと、許可を問う（Eclectic Light Company の記事）。推：ループバックの NFS と WebDAV のマウントも、ネットワーク上のボリュームとして扱われ、ほかのアプリ（Finder から開くエディターなど）には、最初に問いが出る。FSKit の扱いは分からない。

## 7. 試作：ループバックの NFSv3（C1）

### なぜ C1 か

1. Mac で、何も足さず、sudo なしで動くのは、C1 と C2 だけだった（実）。
2. C2 より C1：WebDAV のクライアントは、小さく読んでもファイル全体を取る（実）。リンクを表せない（推。WebDAV にリンクの種類がない）。class 1 では読むだけ（資）。NFS のクライアントは、ページごとに読み、待ち時間と `soft` の扱いが成熟している（推）。
3. ライセンスが BSD-3 で、特許の問題が小さい（1 章）。
4. C3 は特許で止まる。C4 は、署名したアプリと設定の手が要り、この流れの決まり（新しいアプリを登録しない、設定を変えない）では試せない。

**C1 の大きな弱み（5.1：マウントの認証がない）を、試作は解いていない。** 解けるかどうかが、決めるための問いの 1 つ目である。

### 何を作ったか

`research/unified-mount-proto/`（独立したワークスペース。製品の `crates/` の外）。

- `unified-mount-proto export <フォルダー>`：持ち主の機械で動く。標準入出力で、`getattr`、`lookup`、`readdir`、`read`、`readlink` の 5 つの頼みに答える。読むだけ。5.4 の断り方。
- `unified-mount-proto mount <マウント先> -- <コマンド…>`：見る側で動く。`<コマンド>` を子として起こし（持ち主の機械の `export` を動かすもの）、127.0.0.1 の空いたポートで、読むだけの NFSv3 サーバー（`nfsserve`）を開き、`/sbin/mount_nfs` でマウントする。Ctrl-C か SIGTERM で、外してから終わる。
- `unified-mount-proto serve -- <コマンド…>`：マウントせずに、サーバーだけ。
- 頼みの形（`wire.rs`）：長さ、JSON、長さ、生のデータ。Istesso の道のメッセージの代わり。

**Istesso の道（Noise の制御チャンネル）にはつないでいない。** 代わりに、持ち主の機械の `export` を、`ssh <Ubuntu> …/unified-mount-proto export …` の標準入出力で動かした（持ち主の SSH の接続に乗る）。Istesso の道につなぐには、ペアリングの鍵と権限（ADR 0013 の「ファイル」の権限）の扱いが要り、1 時間では済まないと見た。持ち主の機械では、ポートを開いていない。

### 結果（実：見る側は Air、持ち主は Ubuntu）

| 見たこと | 値 |
|---|---|
| マウントにかかった時間（ssh の起動を含む） | 0.3 秒 |
| `mount` の表示 | `127.0.0.1:/ on <マウント先> (nfs, nodev, nosuid, read-only, nobrowse, mounted by <ユーザー>)` |
| 一覧 | Ubuntu のフォルダーの名前、大きさ、時刻、リンクの行き先が、`ls -la` で見えた |
| 中身 | `cat` で読めた。3 MB のファイルを 0.10 秒で読み、SHA-256 が Ubuntu の `sha256sum` と一致した |
| 大文字と小文字 | `CASE.txt` と `case.txt` が別々に見え、別々の中身を読めた |
| 書く | `echo > 新しいファイル`、`touch`、`xattr -w` が、どれも「Read-only file system」 |
| 変更の知らせ | 5.9 のとおり |
| 持ち主の側が止まった | すぐに「Input/output error」。固まらない |
| 片づけ | SIGTERM で外れ、`mount` に残らなかった |

ローカルの代わり（Air のスクラッチのフォルダーを `export` する）でも、同じことを確かめた。テスト（`cargo test`、8 件）は Air と Ubuntu の両方で通り、`cargo clippy --all-targets -- -D warnings` は Air で通った。`cargo deny check licenses` は Ubuntu で通った（リポジトリの `deny.toml` を使った）。

### 試作の足りないところ

- マウントの認証がない（5.1）。
- 読むだけ。書くことは何もしていない。
- 頼みは 1 つずつ（同時に 1 つ）。持ち主の側で、ID とパスの表が増え続ける。名前が変わると、古い ID は別のものを指さない（`Stale` になる）が、新しい名前は新しい ID になる。
- 見る側の一覧のコピーは 1 秒だけ、メモリーにだけ置く（NFS のページ送りのため）。ディスクには何も写さない（決め 1）。
- Linux の見る側（FUSE、L1）は作っていない。Linux では `mount` を断る。

## 8. 強い候補と、決めるための問い
