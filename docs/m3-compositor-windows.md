## ビルドの分け方

コンポジターのプラグインは、`scripts/build-compositor.sh` で、自分のフォルダーにビルドします。ホストで動かします。

```sh
# 判定で測るビルド（4 つの修正。関門で測ったものと同じ）
scripts/build-compositor.sh <フォルダー>

# 試用と、毎日使う形のビルド（4 つ + trial-windows）
scripts/build-compositor.sh <フォルダー> --trial --test
```

- 切り替えは、引数の `--trial` です。**付けなければ**、当てるのは、関門で測った 4 つ（render-on-commit、cursor-messages、windows、dialogs）だけです。付けると、`gst-wayland-display-trial-*.patch` を、名前の順に足します。環境変数にしなかったのは、どこかで `export` した変数が、計測のためのビルドに、知らないうちに試用の修正を入れることがないようにです（前の版の `ISTESSO_COMPOSITOR_TRIAL` が設定されていたら、スクリプトは何もせずに止まります）。
- フォルダーに、gst-wayland-display の `1301f863e4d7db1fb4a975501c0b5dd2b3ac46fe` を取り出し、修正を当て、`--locked --features cuda` でビルドします。プラグインは `<フォルダー>/target/release` にできます。`--test` を付けると、コンポジターのテスト（`cargo test -p wayland-display-core`）も通します。
- **すでにあるフォルダーは、このスクリプトが、同じコミット、同じ修正、同じ機能（features）で作ったときだけ使い直します**（フォルダーの `.istesso-patches` に、コミット、機能、当てた修正の名前と中身のハッシュが書いてあります）。それ以外のフォルダーには、何も書きません。動いている試用や計測が使うプラグインの上に、ビルドすることはありません。
- 計測の合図（AGENTS.md）を、始める前と、cargo が動いているあいだ 5 秒おきに読みます。`busy` なら始めず、動いていれば cargo を止めます。cargo は、自分のプロセスグループで動かし、スクリプトが止められたとき（Ctrl-C、ssh の切断、TERM）は、そのグループを番号で止めます。
- 取り出し元は `ISTESSO_GWD_ORIGIN` で替えられます（そのコミットを持つ手元の複製なら、取りに行きません）。機能は `ISTESSO_COMPOSITOR_FEATURES` で替えられます（既定は `cuda`）。

計測が試用のプラグインを使わないための確かめ：`scripts/check-plugin.sh <フォルダー>`（ビルドのフォルダーか、その `target/release`）。読むだけで、何も書かない。`.istesso-patches` に `trial-` の修正があれば 1、なければ 0、分からなければ 2 で終わる。ソースがあれば、いつも、trial の修正だけが足すファイル（`tests/test_trial_windows.rs`、`wayland/handlers/xdg_activation.rs`）があるかも見る（あとで手で修正を当てたフォルダーも、試用と言う）。このスクリプトより前に手で作ったフォルダー（関門のプラグイン）には `.istesso-patches` がないので、そのときは、ソースだけで決める。ホストで見たこと：`gwd-trial7` と `gwd-trial3` は 1、`gwd-measuring2` と関門の `gwd-cursor` は 0、ないフォルダーは 2。計測を走らせるスクリプトから呼ぶのは、まとめ役の側でつなぐ。計測のスクリプト（`scripts/m1-step3-host.py` など）は、確定の判定まで変えない。

試用で使うときは、ビルドしたフォルダーを `ISTESSO_HOST_PLUGIN` で指します。

```sh
ISTESSO_HOST_PLUGIN='<フォルダー>/target/release' TRY=channel scripts/try.sh <アプリのコマンド>
```

**判定で測るビルドが変わっていないこと**の確かめ方：

- 4 つの修正のファイルは、この作業で変えていない（`git diff origin/main -- scripts/patches/gst-wayland-display-{render-on-commit,cursor-messages,windows,dialogs}.patch` が空）。
- `--trial` を付けずにビルドしたフォルダーのソースが、関門で測ったプラグインのフォルダーのソースと同じであること（`diff -r -x target -x .git` で比べる）。

## 1. ポインター、ボタン、キーボードが、同じ窓へ行く

**見たこと**（`docs/input-record.md` の最後の節）：Blender の設定の窓（親のない 2 枚目の窓）が出たとき、キーボードは設定の窓へ移り、ポインターは下の主の窓に入ったままだった。動かさずにクリックすると、ボタンは主の窓へ、キーボードは設定の窓のままで、Shift+A は設定の窓へ、Shift＋スクロールと Alt＋ドラッグは主の窓へ行った。

**原因**（この作業で、テストで再現した）：コンポジターは、窓を、最初の configure のあとの確定で絵に入れる。その確定に絵が入っていなくても入れる。Blender の 2 枚目の窓は、絵を描く前に確定する。そのときにポインターの行き先を調べ直すと、新しい窓には、まだ何もない。ポインターは下の窓へ入り、動くまでそのままだった。クリックでは、キーボードを「ポインターの位置のいちばん上の窓」へ、ボタンを「ポインターがいま入っている窓」へ渡していたので、2 つが分かれた。

**直したこと**：

- 絵に入っている窓が確定するたび（新しい絵、新しい大きさ、最初の絵）、窓が出たとき・閉じたとき、クリックで窓を上げたあとに、ポインターの行き先を、いまの位置で調べ直す。行き先が変わったときだけ、出入りを送る。
- クリックでは、ポインターの下の窓を上げ（ダイアログもいっしょに、これまでどおり）、ポインターを、いまそこでいちばん上にある窓に入れ、**キーボードを、同じ窓へ渡す**。ボタンとキーが、別々の窓へ行くことはない。1 度も動かしていないポインターでのクリックも、窓に届く（これまでは、どこにも届かなかった）。
- どの窓が「いま使っている窓」（`xdg_toplevel` の activated）かは、**キーボードだけに従う**。キーボードが移るたびに（Smithay の `SeatHandler::focus_changed` から、新しい行き先で）、全部の窓に伝える（変わったときだけ）。ポップアップ（メニュー）がキーボードを持つあいだは、その持ち主の窓が「使っている窓」。窓を上げても、絵に入れても、この状態には触れない。最初の configure では「使っている」と言わない。出力の大きさが変わっても、全部の窓を「使っている」にはしない（元のコードはそうしていた）。これまでは、どの窓にも、出たときに「使っている」と伝えたきりだった。Blender は、これを見ている：「使っていない」と言われなかった窓では、押したままの Shift や Alt が、次のキー、スクロール、ボタンに付かなかった（ホストの自己試験で見た。下の「ホストでの自己試験」）。
- **どのアプリも、人がそのアプリで何かをしないかぎり、キーボードを取らない**（持ち主の決め方）。
  - 新しい窓が出たとき、キーボードを渡すのは、だれもキーボードを持っていないか、その窓のアプリがキーボードを持っているとき（2 枚目の窓、ダイアログ。親は、いつも同じアプリの窓）だけ。ほかのアプリの窓は、キーボードを持つアプリのすべての窓の下に置き（そのアプリの窓が出ていなければ、いちばん下）、キーボードは渡さず、「見てほしい」の印を付ける。
    - なぜ下か（持ち主、2026-11-18）：いちばん上に置くと、その窓が、人が自分のアプリへのつもりでしたクリックを受けてしまう（Fable のレビューの N4。いったん「見失わないよう上に」としたのを、取り下げた）。下に置くのは macOS のやり方でもある。主の窓が絵の全体を埋めているいまは、下の窓は見えないので、印を Mac の側で見せて（ビューアーの題名と窓の一覧。別の流れ、あとで）見失わないようにする。窓を指定して前に出す・閉じる頼みも、あとで要る見込み（いまは作らない）。
  - メニュー（ポップアップ）がキーボードを取る（grab）のは、その持ち主の窓がキーボードを持っている（または、その窓のメニューを通して持っていた）ときだけ。ほかは、すぐ閉じる（`popup_done`）。頼みの番号（serial）は、シート自身の確かめのほかには見ない：grab は、使っているアプリの中でキーボードを動かすだけなので、番号を見ても守りは増えない。そして、キーボードで開いたメニュー（F10、メニューキー）や、クリックから長くたって開いたメニューは、古いボタンの番号を名乗る（Fable の N3）。
  - だれがキーボードを持っているか（窓、またはキーボードを持つメニューの持ち主の窓と、そのアプリ）は、キーボードが動くたびに覚える。キーボードを持っていたメニューが消えても、シートは次の入力までそのメニューを行き先に持ち続けるので、上と下の確かめは、覚えたほうで判断する。こうしないと、メニューの項目が開いた窓や、メニューバーの次のメニューが、ほかのアプリのものと取り違えられた（Fable の N2）。消えたメニューの grab は、そのアプリの窓が出たときと、次のメニューが grab するときに終える。
  - アプリのメニューがまだ grab しているあいだに、同じアプリの窓が出たときは、シートがキーボードをメニューに置いたままにするので、その窓には印を付ける（クリックでキーボードが移る。Fable の N5）。
  - 窓が閉じたとき、キーボードが動くのは、それがキーボードの持ち主の窓（キーボードを持つ窓、またはキーボードを持っていたメニューの持ち主の窓）だったときだけ。その親が出ていれば親へ、なければ同じアプリのいちばん上の窓へ、そのアプリの窓がもうないときだけ、いちばん上の窓へ行く（Fable の N1）。ほかの窓が閉じても（消えたメニューがまだシートの行き先のあいだに、ほかのアプリが自分の窓を閉じても）、キーボードは持ち主に残る（Fable の M1）。
  - 消えたメニューの grab を終えたときは、キーボードを持ち主の窓へ戻す（出ていれば）。これを、そのアプリの窓が出たとき、次のメニューが grab するとき、ボタンが押されたとき、窓が閉じたときにする（Fable の L2、L3）。ただし、持ち主の窓のメニューがまだ開いているあいだ（開いたメニューの下のサブメニューが閉じたとき）は、何もしない：grab はそのメニューで続き、外をクリックすれば、そのメニューが閉じる（Fable の 4 回目）。
  - 分かっていること（変えていない）：このコンポジターでは、サブメニューが grab すると、キーボードは窓に戻る（シートの pointer の grab を、keyboard の grab のあとで置き換えるので、置き換えられた pointer の grab が、新しい keyboard の grab を終える。元のプロジェクトの順。テストで見た）。
  - 最後の窓が閉じたら、だれもキーボードを持たない（シートは「だれもいない」への変化を知らせないので、こちらで消す）。次に来たアプリの最初の窓は、キーボードを取る（Fable の L1）。
  - 「最近」（xdg-activation に使う）は、このシートの最後の 64 回のキーとボタンの出来事で、それが届いたクライアントといっしょに覚え、10 秒より古いものは数えない。
- ポインターが入っている窓が、ポインターの下で動いたとき（全画面や最大化で隅へ移ったとき）も、窓の中のどこにポインターがあるかを、伝え直す。
- コンポジター自身のキー（元のコード：Ctrl+Shift+Tab でいちばん上の窓にキーボードを渡す、Ctrl+Shift+Q でキーボードを持つ窓を閉じる）は、残した。**このキーは、アプリには届かない**（変えていない）。Ctrl+Shift+Tab がキーボードを移したときは、クリックのときと同じに、「使っている窓」を伝え、ポインターの行き先を調べ直し、絵を出す。ただし、US の配列では、Shift を押すと Tab が ISO_Left_Tab になるので、この決まりは働かない（テストで見た。キーはアプリに届く）。

## 2. 「全画面」ではなく「最大化」と伝える

- 出力と同じ大きさにする窓には、**最大化**（`XdgState::Maximized`）と、出力の大きさ（上限があればそこまで）を伝える。アプリは、自分の帯（Firefox のタブとアドレスの帯）を残す。
- **全画面**は、アプリが頼んだとき（`xdg_toplevel.set_fullscreen`：動画、ゲーム、発表）だけ伝え、窓を左上の隅に置く。いちばん上に出すのは、キーボードを持つ窓のときだけ。キーボードを持たない窓は、重なりの順はそのまま（頼むだけで、人が使っている窓の上には出られない）。頼みを取り下げたら、親のない窓は最大化に戻り、ダイアログは自分の大きさに戻る。
- アプリが最大化を頼んだら、同じ決まりで最大化する。
- 出力の大きさが変わったら、出力いっぱいの窓（最大化、または頼まれた全画面）には新しい大きさを伝え、ほかの窓には、使える広さだけを伝える。これまでは、全部の窓に「全画面、大きさなし」を伝えていた。

## 3. 2 枚目の窓を見失わない（つなぎ）

- ほかの窓が出力いっぱいに出ているときに開く、**親のない窓は、出力いっぱいにしない**。使える広さだけを伝え、アプリの望む大きさのまま、出力のまん中に置く。出力いっぱいでない親のない窓（大きさの上限を言う窓など）も、まん中に置く。全画面を抜けても、最大化の頼みを取り下げても、自分の大きさに戻る。小さい窓（スプラッシュなど）しか出ていないときに開く窓は、これまでどおり出力いっぱいにする。
- 絵を描く前に出た窓は、最初の絵が来たときに、その大きさで置き直す（重なりの順は変えず、そのダイアログはその上に）。これまでは、大きさ 0 の窓として置いていたので、「まん中」が窓の角になり、残りは出力の外へはみ出していた（Blender の設定の窓。ホストの自己試験で見た）。ダイアログにも効く。
- 出力いっぱいの窓がクリックで上がったら、**同じクライアントの、親のない小さい窓を、その上に上げ直す**（もとの順のまま。そのダイアログもいっしょに）。上がった窓のダイアログは、その上に来る。ほかのクライアントの窓は、動かさない。クリックそのものは 1 のとおりで、上げ直したあとにポインターの下でいちばん上にある窓に、ボタンとキーボードが行く。
- **xdg-activation の口を出す**（持ち主の決め方、2026-11-18）。窓を前に出す頼みに従う（ダイアログといっしょに上げ、キーボードを渡す）のは、**そのときキーボードを持つ窓のアプリが、そのアプリへの最近の入力（キーかボタン）の番号（serial）から作ったトークンで頼んだときだけ**。前に出す窓は、トークンを作ったアプリの窓でなければならない（トークンをほかのプロセスに渡しても、たとえばそのアプリから開いたブラウザーでも、キーボードは動かない）。番号は、上の「最近」と照らす。ほかの頼みは、キーボードも重なりの順も動かさず、窓に「見てほしい」の印を付けるだけ（その窓がもうキーボードを持っていれば、印も付けない。その窓がキーボードを持つと消える）。印は、その窓がキーボードを持ったときと、その窓がなくなったときに消える。印が付いたり消えたりするたびに、コンポジターのログに 1 行（`window attention id=… app_id=… wants_attention=true|false`）を書き、窓の数の知らせ（windows の修正の `wayland.windows`）に、`count` と並べて `attention`（印のある窓の数）を載せる。パイプライン（`m1-step3-host.py`、変えていない）は `count` だけを出すので、印が変わったときは、同じ `count` の行がもう 1 回出る。Mac の側で見せるのは、あとで（試用の流れが、このログの行を数えて、Mac の題名に「呼んでいる窓がある」と出している）。`id` は、窓が出たときに付ける番号で、コンポジターが動いているあいだ、ほかの窓には使わない。あとで、窓を指定して前に出す・閉じる頼みに使う（いまは作らない）。窓ごとの知らせは、いまはこのログの行だけ（窓の数の知らせは、数だけ）。トークンは 10 秒のあいだ、1 回だけ効く。1 つのアプリが持てる使っていないトークンは 32 まで。古いものは、トークンが作られるときと使われるときに捨てる。覚えなかったトークンや捨てたトークンでの頼みは、Smithay が捨てるので、こちらの処理まで来ない（印も付かない）。まだ出ていない窓への頼みは、捨てる（トークンは使ったことになる）。外から 2 回目に起動されたアプリは、そういう番号を持たないので、窓を前に出せない。

分かっている不足：

- 外から窓を選ぶ手は、まだない。出力いっぱいの窓の下になった、出力いっぱいの窓（2 枚目のブラウザーの窓）は、上の窓が閉じるか、アプリが頼むまで、届かない（窓の一覧。m3-everyday-apps.md の 10 章）。
- 「同じクライアント」は、Wayland の接続 1 本のこと。窓を 2 本の接続で開くアプリは、2 つのクライアントになる。
- 全画面や最大化を抜けた窓は、そのとき置いた場所（左上の隅）のまま。最初の絵のあとで大きさが変わっても、置き直さない。
- 大きさの上限を言う、親のない窓も、全画面や最大化を抜けると、自分の大きさに戻る（2 枚目の窓と同じ印を付ける）。
- 1 枚目の窓が最大化の取り下げを頼んでも、最大化のまま答える。

## テスト

`cargo test -p wayland-display-core`（`--test` を付けたビルド）。98 本のうち、この修正で足したのは 33 本（`tests/test_trial_windows.rs`。本物の Wayland クライアント。2 つ目のクライアントをつなぐもの、メニューを開くものを含む）と 2 本（`comp/windows.rs`）。dialogs の修正のテストのうち 2 本を、3 の決まりに合わせて変えた（親のない 2 枚目の窓：出力の大きさではなく使える広さを伝え、隅ではなくまん中に置く）。

- 1：絵を描く前に出た 2 枚目の窓が、最初の絵からポインターを持つ。動かさずにクリックすると、ボタンもキーボードもその窓へ行き、その窓が「使っている窓」になる。1 度も動かしていないポインターでのクリックが、1 枚だけの窓にキーボードといっしょに届く。ダイアログの横のクリックで、ボタン、キーボード、「使っている窓」が親へ行く。出力の大きさが変わっても、「使っている窓」は変わらない。ポインターの下で動いた窓（まん中から隅へ全画面）は、窓の中のポインターの場所を伝え直される（60,40 から 160,120）。US の配列の Ctrl+Shift+Tab は、キーボードを動かさない。1 つ目のテストは、確定のたびに調べ直す処理を外すと落ちる（ポインターが下の窓のまま）ことを確かめた。
- 2：1 枚目の窓は、出力の大きさで最大化と伝えられ、全画面とは伝えられない。全画面を頼んだ窓は全画面になり、取り下げると最大化に戻る。出力の大きさが変わると、最大化の窓に新しい大きさが伝わる。キーボードを持たない窓が全画面を頼んでも、重なりの順は変わらない。

### 「Shift+A が A として効いた」の原因

**見たこと**（この作業の途中の版。trial-windows の 1〜3 から「使っている窓を伝える」を除いたもの。`selftest/run-blender` の記録）：

- 設定の窓が出たとき、主の窓には、configure が 1 回も来なかった（「使っていない」と言われなかった）。記録の主の窓（面 21）への configure は、起動のときの 3 回（`1720, 720`、状態 2 つ）だけ。
- 主の窓をクリックしてキーボードを主の窓へ戻し（キーボード：42 を出て 21 へ）、Shift+A を押すと、アプリの記録では `shift_l down`、`modifiers depressed=1`、`key down` の順に届いていた（修飾キーの状態は、正しく告げられている）。Blender のイベントでは、`LEFT_SHIFT` に `modifier={SHIFT}` が付き、続く `A` は `modifier={}`、`utf8:'A'` だった。3D View が A（すべて選ぶ）として扱い、題名に `*` が付いた。
- 「使っている窓」を伝える版（`selftest/run-blender-2` と `run-blender-4`）では、同じ操作で、主の窓に configure（状態 2 つ）、設定の窓に configure（状態なし）が届き、`A` に `modifier={SHIFT}` が付いた。

**結論**：Blender は、キーの修飾キーを、自分が「使っている」と思う窓の状態から取る。主の窓は、設定の窓が出たあとも「使っていない」と言われず、Blender の中では設定の窓が使っている窓のままだった。そのため、主の窓で押した Shift は、A に付かなかった。（Blender の中のことは、ソースを読んでいない。上の記録から、こう考えた。）

## 何も変わらないあいだのフレーム（2026-11-19 未明、ホストだけ）

AURA の試しで、動かない Blender の窓が、毎秒 36 枚、どれも 33,039 バイト（約 10 Mbit/s）で送られていた件。

見たこと（この作業の自分のコンポジター。1920×1080、72 fps、4:2:0、NVENC 30 Mbit/s、VBV 1 フレーム、GOP -1。AURA と同じ）：

- Blender（設定の窓は開かない）で何もしない 30 秒：パイプラインは 1080 フレーム（毎秒 36.0 枚、間隔の中央値 27.8 ms = 72 fps の 2 間隔）。圧縮後はどれも 33,293〜33,297 バイト（2 通り）、9.6 Mbit/s。そのあいだ、Blender は 1 回もコミットしなかった（起動から終わりまでで 13 回）。
- 同じ形で、静かな zenity の窓：毎秒 36.0 枚、どれも 195 バイト。
- Blender の窓のフレームを、圧縮の前（RGBx）でファイルに落として比べた：最後の 10 枚は、1 バイトも違わなかった。
- そのうちの 1 枚を止めて繰り返し、同じ設定のエンコーダーに入れた：CBR では 2 枚目から 42 KB、10 枚目から 34 KB で、そのまま変わらない。品質一定の VBR（上限つき）でも同じくらい。QP を固定すると 104 バイト。CBR に QP の下限（`min-qp-i/p/b`）を付けると、18 で約 880 バイト、24 で約 200 バイト（最初のキーフレームは 24 で 53 KB、付けないと 70 KB）。`min-qp-p` だけでは効かなかった。黒一色の絵は、CBR でも 80 バイト前後。
- フレームを CUDA で渡しても、メモリーで渡しても、33 KB は同じ。

結論：

- 毎秒 36 枚は、こちらの経路：「確定したら描く」の修正（計測で使っているもの）が、何も変わらないあいだも、2 フレームぶんの間隔ごとにフレームを出す（ストリームを止めないため）。Blender は描いていない。
- 1 枚 33 KB は、コンポジターではない（絵は同じ）。細かい絵（Blender の UI）を止めたまま CBR で送り続けると、エンコーダーのレート制御が、残りの予算で絵を磨き続ける（QP を下げ続ける）ため。単純な絵（zenity、黒）では、すぐに数百バイトに落ちる。

案（試用だけ。計測する 4 つの修正と `scripts/m1-step3-host.py` は変えない）：

- (a) 何も変わらないあいだの間隔を長くする。試用の修正に、`ISTESSO_IDLE_FRAME_INTERVALS`（1〜1000、既定は 2 のまま）を足した。テキストエディターで、2 秒ごとに 1 文字打つ形で測った（72 fps）：間に 150〜600 ms の空きがあったあとのフレームの圧縮（コンポジターを出てから圧縮が終わるまで）は、中央値 1.59 ms（最長 2.02）。空きが 40 ms より短いときは 1.27〜1.45 ms。この NVENC では、長く休ませても、変化の 1 フレームはほとんど遅くならない（Mac mini の記録の 4 ms のような差はない）。36（毎秒 2 枚、間隔 0.5 秒）なら、止まった Blender でも約 0.55 Mbit/s。ビューアーは 1 秒の沈黙を「切れた」とみなすので、間隔は 1 秒より十分短く（36 は、余裕が少し狭い。8〜18 くらいを勧める）。
- (b) 同じ絵を数百バイトにする：エンコーダーに QP の下限（`min-qp-i`、`min-qp-p`、`min-qp-b` を同じ値で、18〜24）を付ける。止まった Blender の絵で 880〜200 バイトになった。代わりに、止まった絵の最高の細かさ（細い文字）が少し落ちる。試用のパイプラインに、その設定を渡す口が要る（`m1-step3-host.py` は計測の道具なので、変えずに、試用のほうで包むか、試用の写しに足す。どちらにするかは持ち主が決める）。見た目は、持ち主の目で確かめる。
- (a) と (b) を合わせれば、止まった窓の帯域は、ほとんどなくなる。

### 止まった直後は細かく、そのあとは間を空ける（持ち主の決め、2026-11-19）

- 何も変わらないあいだのフレームは、最後の変化から 0.5 秒は、これまでどおり 2 間隔ごと（エンコーダーが最後の絵を磨き、止まった直後からくっきり見えるように）。そのあとは 12 間隔ごと（72 fps で毎秒 6 枚、167 ms おき。85 fps で毎秒 7 枚）。ストリームの始まりで、まだ一度も変化がないあいだも 12 間隔。12 は、勧めた 8〜18 のまん中で、ビューアーの 1 秒の沈黙の判定までに、6 倍の余裕がある。
- 試用の設定：`ISTESSO_IDLE_FRAME_INTERVALS`（広げた間隔。1〜1000、既定 12）、`ISTESSO_IDLE_RAMP_MS`（2 間隔を保つ時間。0〜10000、既定 500）。どちらも起動のときに 1 回だけ読む。計測する 4 つの修正と `m1-step3-host.py` は変えていない。「確定したら描く」の修正のテストのうち 2 本は、変化から始めるようにした（0.5 秒の内に入るように）。
- テスト：既定と範囲、変化のあと 499 ms までは 2 間隔・500 ms からは広い間隔・変化のないフレームでは数え直さないこと。全部で 110 本。

ホストで見たこと（自分のコンポジター、1920×1080、72 fps、4:2:0、AURA と同じエンコーダーの設定。Blender の 3D View で、5 秒ごとに A と Alt+A を交互に 6 回）：
