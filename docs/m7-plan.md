# M7 の進め方：USB 機器と Stream Deck

M7 は、普段使っている USB 機器を、この仕組みの中でも使えるようにする段階です。この文書は、**今週（2026-11-16 の週）に通せるものと、通せないもの**を、[ADR 0004](adr/0004-usb-devices.md) に照らして示し、手順を書いたものです。

規約は先に [AGENTS.md](../AGENTS.md) を読んでください。方針は ADR 0004（2026-11-16 に更新）と [ADR 0012](adr/0012-device-framework.md)（機器対応のフレームワーク。方針は採用、細目は提案）にあります。

この文書を書いた時点では、コードは 1 行も書いていません。2 台の実機を、何も変えずに調べただけです。手順の中のコマンドで「試していない」と書いたものは、そのとおり、試していません。

## 1. 今週通せるもの、通せないもの

今週の目標は、受け入れ条件を通すことです。通らなかったものは、公開の文面に書きません。ほかの流れは止めません。M7 には、まだ受け入れ条件がないので、「6. 受け入れの確認」の案に照らして書きます。

| 受け入れの確認（6 の案） | 今週 | 条件と理由 |
|---|---|---|
| A. 機器の一覧 | 通せる | 1 台の中は、権限も、足すパッケージも要らない。全台を合わせるには、共通のクレートにメッセージを 1 つ足す。先に本線（M1）と合わせる（手順 1、2） |
| B. Stream Deck（最初のアダプター） | Mac の分は、通せる見込み | Stream Deck Plus は、Mac につながっている。公式ソフトを止める時間が要る。「ボタンでアプリを開く」は、アプリマネージャー（M3）が `main` に入ってから。Linux の分は、人の手が 1 回要る（手順 3〜5） |
| C. 起動先の選び方 | 選ぶところまでは、通せる。窓が出るところは、まだ | 例のとおりに「Ubuntu で開いて、Mac に窓が出る」には、映像の経路（M1）とアプリマネージャー（M3）が `main` に要る（手順 6） |
| D. 声の回り込み | 基準の形だけ | 音を運ぶ形は、音の経路（M2）が `main` に入ってから（手順 7） |
| E. アダプターを外から足せる | 通せない | 口を固めるための 2 つ目の機器が、決まっていない。今週は、手順書とひな形の下書きまで |
| F. 付け替え（USB/IP） | 通せない | 下の「付け替えが今週に入らない理由」 |

- 通らない E と F は、通るまで、公開の文面に書かない。
- キーボードとマウス（入力の転送）は、映像の経路（M1）の中にある。オーディオ機器（音を運ぶ）は M2 である。M7 では、一覧に出すところまでを受け持つ。
- Windows には触らない。このリリースに含めるかが、決まっていない。

見積もり（測った値ではない）：A と、B のうち Mac の分で、今週の大半を使います。C の選ぶところは 1 日ほどです。

### 付け替えが今週に入らない理由

1. **両側に root が要る。** Linux の受け側は、仮想 USB コントローラーの読み込みと、付け替えのたびの操作に root が要ります。Mac の出す側も root が前提です。使う人に `sudo` を打たせないためには、root で動く小さな部分を設計して、インストーラーに入れる必要があります。理由も ADR に残します（AGENTS.md）。
2. **USB/IP の手順に、認証も暗号化もない。** ペアリングと USB の権限（R-13）を通す運び方を、まだ決めていません。
3. **ホストに、いまのカーネル用の道具がない。** `usbip` コマンドは、再起動後のカーネル用しか入っていません。
4. **付け替えてよい機器が、決まっていない。** いまつながっているのは、キーボード、マウス、オーディオ、カメラ、Stream Deck など、付け替えの対象でないか、試しに使うと困るものです。
5. **勧めのとおりに挿すと、出番がほとんどない。** いまの機材（Linux は 1 台。Windows は未決）で付け替えが要るのは、Mac に挿した機器を Linux のアプリで使うときだけです（ADR 0004 の「挿す場所と、使えるアプリ」）。

今週できるのは、人の手を借りた、手動の試しまでです（手順 8。任意）。

2026-11-16 に調べた結果です。どちらの PC でも、何も入れず、何も変えていません。

ほかに分かったこと：

- **同じ機器が、2 台の一覧の両方に出る。** KVM 切替器ごしのキーボードなどは、Ubuntu からも Mac からも、つながって見えます。全台を合わせた一覧で、これをどう見せるかを確かめます（手順 2）。
- **会議アプリを開く PC は、いまの機材では Ubuntu になる。** カメラとマイクが、Ubuntu に挿してあるためです。ADR 0004 の 1 つ目の例と同じ形です。
- **部品のライセンスで、2 つ気づいた。** 「7. 見つけたこと」に書きます。

## 3. 体制と決まり

映像（M1）、音（M2）、アプリマネージャー（M3）の作業と、同じ 2 台を使います。

- 作業は、`main` から切った `m7-usb-devices` ブランチの、専用の作業ツリーで行う。ほかの流れの作業ツリーには触らない。
- 映像の計測が走っているあいだは、ビルドもテストも始めない（合図のファイルで確かめる）。
- ホストで使う場所は、`~/.cache/istesso-m7-wip/` だけ。いまは、書式を確かめた udev の決まりのファイルが 1 つ置いてある。
- 何も入れない。`sudo` は使わない。パッケージを展開して、そこから動かすこともしない。足りないものは、「5. 人に頼むこと」に書く。
- **Stream Deck は、人が毎日使っている道具である。** 公式ソフトを、断りなく止めない。試したあとは、公式ソフトを起動し直して、元どおりに使えることを確かめる。
- **人のキーボードとマウスを、付け替えの試しに使わない。**
- 機器の製造番号を、記録、試験、文書、ログに入れない。
- 共通のクレート（`istesso-proto`、`istesso-link`）を変えるときは、先に本線（M1）と合わせる。`istesso-link` にメッセージを足すときは、[ADR 0007](adr/0007-control-channel.md) を先に直す（AGENTS.md）。

## 4. 手順

### 手順 0：調べる（済み）

「2. 環境」のとおりです。

### 手順 1：1 台の中の一覧

`istesso devices list` で、その PC につながっている機器を、種類と一緒に出します。

- Linux は sysfs を読む。Mac は `system_profiler` の出力を読む（`istesso doctor` と同じ作り）。読んだものを解析する部分は、OS に触らない関数にして、テストを付ける。
- 種類に振り分ける：キーボードとマウス（転送）、オーディオ（音を運ぶ）、カメラ、アダプターのある機器（直接制御）、その他（付け替え）。ハブは出さない。
- 1 台の機器が、2 つの種類を持つことがある（カメラとマイク）。
- 内蔵のマイクとカメラも出す。会議アプリを開く PC を選ぶのに使う。仮想のカメラは、数えない。
- 製造番号は、表示にもログにも出さない。同じ型の機器が 2 台あるときの区別には、挿してある場所を使う。

| 要るもの | 内容 |
|---|---|
| 機材 | 2 台の実機 |
| 権限 | なし |
| パッケージ | なし |
| 人がやること | なし |

確認：

1. Ubuntu と Mac で実行して、OS の道具（`lsusb`、`system_profiler`）と同じ機器が出る。
2. Stream Deck Plus が「直接制御」、カメラが「カメラ」と「オーディオ」、キーボードとマウスが「転送」と出る。
3. 出力に、製造番号が入っていない。

### 手順 2：全台を合わせた一覧

`istesso devices list --all` で、ペアリング済みの全端末の機器を、1 つの一覧にします。機器ごとに、どの PC に挿してあるかが分かります。

- `istesso-proto` に機器の型を、`istesso-link` に問い合わせを 1 つ足す。暗号の手順は変えない。
- 一覧を見るのは「閲覧」の権限、機器を切り替えるのは「USB」の権限とする案で始める（R-13）。
- 応答しない端末の機器には、アプリの一覧と同じ `!` を付ける。

| 要るもの | 内容 |
|---|---|
| 機材 | 2 台の実機 |
| 権限 | なし |
| パッケージ | なし |
| 人がやること | なし。本線（M1）との調整は、流れのあいだで行う |

確認：

1. どちらの PC からでも、両方の機器が 1 つの一覧で見える。
2. 片方のエージェントを止めると、その PC の機器に `!` が付く。
3. KVM 切替器ごしの機器が、両方の PC の行に出ることを記録する。まとめるかどうかは、それを見て決める。

### 手順 3：フレームワークの最初の形と、最初のアダプター（Stream Deck Plus、Mac）

ADR 0012 のとおりに、いちばん小さいフレームワークを作り、その上に、最初のアダプターとして Stream Deck Plus を載せます。細目は提案の段階なので、採用されなかったところは作り直します。

- 口は HID だけ。通知は、ボタン（8 個）、つまみ（4 個。回す、押す）、タッチ、絵を出す、明るさ、元に戻す。
- アダプターは、1 つのディレクトリに収める。機器の説明（名前、ID、公式ソフト）と、会話の部分。
- 記録を取る道具と、再生の試験。
- 機器の話し方は、components.md の「取り込める」にある実装を参考にする。写さない。
- 公式ソフトが動いているかどうかは、フレームワークが、アダプターの説明を見て確かめる。動いているあいだは、機器に触らない。

| 要るもの | 内容 |
|---|---|
| 機材 | Stream Deck Plus（Mac につながっている） |
| 権限 | 分からない。macOS が「入力監視」の許可を求めるかもしれない。求められたら、理由を ADR 0004 に足す |
| パッケージ | OS に入れるものはない。依存クレートを足す（HID と話す部品、絵の形式を変える部品）。足したら `cargo deny check licenses` を通し、components.md に書く |
| 人がやること | 公式ソフトを止めてよい時間を決める。macOS のダイアログが出たら、応える |

確認：

1. 公式ソフトを止めた状態で、8 個のボタン、4 個のつまみ、タッチが、通知として出る。
2. ボタン 1 つに絵を出せる。明るさを変えられる。
3. 記録を取り、機器なしで再生する試験が、Mac、Ubuntu、CI で通る。記録に、製造番号が入っていない。
4. **Stream Deck のための特別なコードが、本体にない。** アダプターのディレクトリを消しても、本体のビルドとテストが通る。足りないものが出たら、口を直す（ADR 0012 の決定）。
5. 公式ソフトを起動し直すと、元どおりに使える。

### 手順 4：端末のあいだを運ぶ。最初の動作

端末のあいだを運ぶのは、フレームワークの受け持ちです。Stream Deck を Mac に挿したまま、ほかの端末からも使えるようにします。

- 通知（ボタン、つまみ、タッチ、絵）を、制御チャンネルの上で運ぶ。相手が USB の権限を持つときだけ運ぶ。
- 最初の動作は、ADR 0012 の「決めてほしいこと」の 3 の案（ボタンにアプリを割り当てて、押すと開く）で始める。

| 要るもの | 内容 |
|---|---|
| 機材 | 2 台の実機と、Stream Deck Plus |
| 権限 | なし |
| パッケージ | なし |
| 人がやること | なし。ADR 0007 にメッセージを足すので、本線（M1）と合わせる |

確認：

1. Mac に挿した Stream Deck のボタンを押すと、Ubuntu の側で、その通知が見える。
2. USB の権限を持たない端末には、通知が届かない。
3. ボタンを押すと、割り当てたアプリが開く。ほかの PC のアプリを開くところは、アプリマネージャー（M3）が `main` に入ってから確かめる。

### 手順 5：Stream Deck を Linux で

- 人が、Stream Deck Plus を Ubuntu のホストに挿し替え、udev の決まりを入れる（「5. 人に頼むこと」の 4）。
- 手順 3 と同じアダプターを、Ubuntu で動かす。

この `sudo` の 3 行は、使う人に求めてよい手間ではありません。今週、インストーラーがないあいだだけの手間です。インストーラー（M9）の .deb が、同じ決まりを一緒に入れるようにします。

| 要るもの | 内容 |
|---|---|
| 機材 | Stream Deck Plus を、Ubuntu のホストに挿す |
| 権限 | 導入のときに 1 回、root（udev の決まり）。動かすときは要らない |
| パッケージ | HID と話す部品が求めるもの。`libudev-dev` は、もう入っている |
| 人がやること | 挿し替え。`sudo` のコマンド 3 行。試したあと、Mac に戻す |

確認：

1. root でないユーザーで、手順 3 の確認 1〜3 が、Ubuntu でも通る。
2. udev の決まりを外すと、機器を開けなくなる（権限が要る理由を確かめる）。

### 手順 6：起動先の選び方

`istesso-catalog` が起動先を選ぶところに、機器の条件を足します。選び方の中身は、ADR 0004 の「ねらいに照らして選んだこと」の 1〜3 の案です。

- いまの順（手元 → 起きているホスト → 負荷の低いホスト）の前に、機器の条件を見る。
- アプリが機器を使うことは、Istesso が自分で知る。今週は、手がかりのうち、機器の説明に書いてあるアプリ、アプリの種類、使う人が直した結果の 3 つを入れる。「見て覚える」は、そのあとに足す。
- 会議アプリは、挿してあるマイクとカメラの両方がある PC で開く。なければ、手元の内蔵のマイクとカメラで開く。

| 要るもの | 内容 |
|---|---|
| 機材 | 選び方の中身は、どの PC でも作って試せる。確かめるのは 2 台の実機 |
| 権限 | なし |
| パッケージ | なし |
| 人がやること | ADR 0004 の「決めてほしいこと」を決める |

確認（ADR 0004 の 2 つの例を、そのまま試験にする）：

1. マイクとカメラが Ubuntu に挿してあるとき、会議アプリの起動先に Ubuntu が選ばれる。
2. マイクとカメラがどこにも挿していないとき、会議アプリの起動先に、手元の Mac が選ばれる。
3. 機器を使わないアプリは、今までどおり、手元が選ばれる。
4. 同じアプリが Mac と Ubuntu にあり、そのアプリが使う機器が Ubuntu に挿してあるとき、Ubuntu が選ばれる。
5. 選ばれた PC が止まっているときは、`!` が付く。

窓が実際に開くところ（`istesso open`）は、M3 の流れが `main` に入ってから、M3 の側でつなぎます。

### 手順 7：声の回り込みの確認

ADR 0004 の「確認項目」の、3 つの形のうち、今週できるのは 1 つ目（基準）だけです。

- **形 1（今週、人ができる）：** Ubuntu のホストで会議を開き、ホストのスピーカーで聞く。相手に、相手自身の声が返って聞こえるかを聞く。1 人でも確かめられる：別の回線につないだスマートフォンから、イヤホンで同じ会議に入り、スマートフォンに向かって話して、自分の声が遅れて返ってくるかを聞く。
- **形 2、3（今週はできない）：** 音を運ぶ経路（M2）と、窓を映す経路（M1）が、`main` に入ってから。

| 要るもの | 内容 |
|---|---|
| 機材 | ホストのスピーカー、カメラのマイク、会議の相手（またはスマートフォン） |
| 権限 | なし |
| パッケージ | なし |
| 人がやること | 会議に入って、聞く。10 分ほど |

確認：結果を `docs/measurements/` に書く（日付、どの形か、会議のアプリ、スピーカーの音量、聞こえたか）。形 2 と 3 の結果と比べるための基準になります。

### 手順 8：付け替えの、手動の試し（任意）

ADR 0004 の「その他」の行が、いまの OS で成り立つかを、既製の道具だけで確かめます。作るのではなく、試すだけです。

- Mac で、出す側の実装（jiegec/usbip、MIT）の例のプログラムを、root で動かす。Ubuntu で、カーネルの道具でつなぐ。
- 例のプログラムが、どの機器を出すのかを、動かす前に読んで確かめる。Mac の機器を全部出す作りなら、1 台だけを出す小さなプログラムを、先に書く。
- 暗号化も認証もないので、有線の LAN で、数分だけ行う。人が席にいるときに行う。

| 要るもの | 内容 |
|---|---|
| 機材 | 付け替えてよい機器（USB メモリーなど。未定）。有線の LAN |
| 権限 | Mac で root。Ubuntu で root |
| パッケージ | Ubuntu に、いまのカーネル用の `usbip`（`linux-tools-6.17.0-19-generic`）。再起動後のカーネルなら、入っている |
| 人がやること | 機器を決めて挿す。`sudo` のコマンド（「5. 人に頼むこと」の 6） |

確認：

1. Ubuntu の `lsusb` に、Mac に挿した機器が出て、使える。
2. 外すと、Ubuntu から消え、Mac で元どおりに使える。

## 5. 人に頼むこと

質問と、人の手が要る作業を、1 つの一覧にします。

1. **決める。** ADR 0004 の「決めてほしいこと」（3 つ）と、ADR 0012 の「決めてほしいこと」（3 つ）。
2. **決める。** この文書の「6. 受け入れの確認」を、M7 の受け入れ条件にしてよいか。
3. **（手順 3）Stream Deck の公式ソフトを止めてよい時間を決める。** 止めているあいだ、普段のボタンは効きません。

## 6. 受け入れの確認（M7 の全体。提案）

[milestones.md](milestones.md) の M7 には、まだ受け入れ条件がありません。通ったものから公開の文面に書けるように、分けて提案します。

- **A. 機器の一覧。** どの PC からでも、全 PC の機器が、1 つの一覧で見える。機器ごとに、どの PC に挿してあるか、種類、使い方（転送、直接制御、音を運ぶ、付け替え）が分かる。
- **B. Stream Deck（最初のアダプター）。** Stream Deck Plus を、公式ソフトなしで、この仕組みが制御できる。公式ソフトと切り替えられる。ボタンを押すと、割り当てたアプリが開く。Stream Deck のための特別なコードが、本体にない。Mac と Linux の両方で。
- **C. 起動先の選び方。** ADR 0004 の 2 つの例が、そのとおりになる。マイクとカメラを Ubuntu に挿してあれば、会議アプリは Ubuntu で開き、Mac に窓として出る。挿していなければ、Mac でそのまま開く。使う人は、アプリごとの設定をしていない。
- **D. 声の回り込み。** スピーカーで聞く会議で、声が回り込まない（3 つの形）。
- **E. アダプターを外から足せる。** 手順書とひな形だけを渡されたエージェントが、種類の違う 2 つ目の機器のアダプターを書ける。そのプルリクエストは、本体を触らず、記録を再生する試験が通る。これが通ったら、口を固める。
- **F. 付け替え。** Mac に挿した機器を、Ubuntu のアプリから使える。使う人は `sudo` を打たない。

## 7. 見つけたこと

- **jiegec/usbip は、libusb（LGPL-2.1）を使う。** 0.9.0 は、`rusb` と `nusb` の 2 つのクレートに依存している。`rusb` は libusb を呼ぶ。クレートの表示は MIT なので、`cargo deny` はこれに気づかない。ホストには、libusb の開発用のパッケージが入っていない。その状態でビルドすると、libusb が静的に組み込まれるおそれがある（そう理解している。足すときに確かめる）。足すときは、動的リンクにして、components.md の「条件つきで使える」に書く（ADR 0001）。
- **Stream Deck の参考実装の LICENSE は、標準の MIT の文面ではない。** プロジェクトは「MIT」と名乗っているが、LICENSE の本文は、別の、同じく制限のゆるい文面である。参考にして内製するぶんには、困らない見込み。components.md の表記は、公開の前に、原文に合わせて直すのがよい。
- **ADR 0005 は、出る音だけを扱っている。** マイクの音を運ぶことは、書かれていない。会議アプリをマイクのある PC で開くので、運ぶ必要はない。
- **専用ユーザー（ADR 0003）で動かすと、手順 5 の udev の決まりでは届かない。** その PC の前でログインしている人に与える形だからである。M5 で、グループで与える形に替える。
