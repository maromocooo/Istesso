## 4. Blender

Blender 5.3 は、Linux で **Vulkan が既定**です（出典 1）。`--gpu-backend opengl` で OpenGL にもできます（`--help`）。Wayland のライブラリーは同梱しておらず、ホストのものを使います（同梱の一覧に、Vulkan のローダーだけがある）。

Blender は、ドラッグの種類ごとに、ポインターの扱いを変えます（出典 2、3。コミットの説明文から）：

- **端で折り返すドラッグ**（視点の回転、移動・回転・拡大。設定の Continuous Grab が既定で入）：ポインターを**ロック**し、**相対移動**で動きを受け取る。終わるときに、カーソルを置きたい場所をコンポジターに伝える。
- **カーソルを隠すドラッグ**（数値の欄を左右に引く）：同じくロック。
- **折り返さないドラッグ**：窓の中に**閉じ込める**。
- relative-pointer か pointer-constraints がないコンポジターでは、この扱いをしない。

### 4.4 画面の端を越えて続くドラッグ（ポインターの閉じ込めと相対移動）

| | |
|---|---|
| アプリが求めるもの | pointer-constraints（ロック、閉じ込め）と relative-pointer。ロック中は、ポインターの場所のイベントは出ず、相対移動だけが出る。ロックを解くとき、アプリが伝えた場所にカーソルを置いてよい（出典 6、7） |
| コンポジター（読んだ） | 2 つの口を出している。ロック中は、ポインターを動かさず、相対移動だけを送る（gwd `comp/input.rs` 194〜247 行）。絶対座標で来た動きは、**前の絶対座標との差**を相対移動にする（278〜293 行）。アプリが伝えた場所は、Smithay のポインターにだけ入れ、コンポジター自身が覚えている場所（`pointer_location`）には入れない（`wayland/handlers/pointer_constraints.rs` 24〜46 行） |
| プロトコル・ホスト（読んだ） | 相対移動の種類がない。ロックされたことを、クライアントに伝えるものもない（カーソルの知らせは、隠れた・名前・絵の 3 つだけ。gwd `comp/cursor.rs` 28〜38 行） |
| 古いクライアント（読んだ） | 場所を、絵の中に切りつめて送る（`gst-viewer.m` 1199〜1203 行）。Mac のポインターを捕まえない |
| 自前のクライアント（読んだ） | 同じ（`Istesso.m` 1655〜1659 行）。続けて来た場所は、最後の 1 つだけを送る（`istesso-client/src/input.rs` 231〜236 行） |
| 考えた | (a) 窓の中では、ロック中も、絶対座標の差が相対移動として届くので、動く見込み。(b) Mac のポインターが窓の端に着くと、送る場所が変わらなくなり、動きが止まる。Mac の画面の端でも止まる。(c) **ロックが解けたあと、コンポジターの思う場所は、ロックした場所のまま。Mac のカーソルは、ドラッグしたぶん先にある。次のクリックが、そのぶんずれた所に当たる見込み。** (d) アプリがカーソルを戻したい場所（数値の欄を引いたあとは、元の場所）へ、Mac のカーソルを動かす手段がない |
| **判定** | **足りない**。コンポジターの口はある。クライアントの捕まえ、相対移動の種類、ロックの知らせ、解けたあとの場所合わせがない |

見たこと（2026-11-18、あとで）：G（移動）では、立方体がポインターについてくる。Continuous Grab が切でも、入でも。**アプリが掴んでいるあいだも、動きは届いている。** これは、上の「考えた」の (a) と合う。入のときは、G を押した瞬間に飛び、そのあと動く。

この「飛び」について、読めたのは、ここまでです：

- ロックが有効になる瞬間に、コンポジターは、ポインターを動かさない。最初の相対移動は、直前の絶対座標との差で、小さい。**G を押した瞬間に飛ぶ理由になる所は、コンポジターの中には、見つからなかった。**
- 読めるのは、ロックが**解けたあと**に、コンポジターの思う場所と、Mac のカーソルの場所が、合わせ直されないこと（上の (c)）。前のロックで残ったずれが、次に G を押したときの飛びとして見えているのかは、読むだけでは言えない。「場所を合わせ直していない」という見方と、**矛盾はしない**。それ以上は、動かして確かめる（宿題 5 を入れたあと、飛びが消えるか）。

### 4.7 Option＋左ドラッグで、何も起きなかった件

見たこと（2026-11-18、持ち主の手。古いクライアント）：Emulate 3 Button Mouse（Alt）を入れた。ふつうの左ドラッグでは、選択の箱が出て、ポインターについてくる。**Option＋左ドラッグでは、何も起きない。選択の箱も出ない。** Continuous Grab を切っても、代わりのキーを「OS キー」にしても、同じだった。隅の球（X、Y、Z）をドラッグすると、視点は回る。

読んだこと：

1. **こちらの線の上に、Option だけを別に扱う所はない。** Option は、Linux のキー 56（右は 100）の「押した」「離した」として送られる（`keys.h` 52〜68 行の表、142〜165 行）。ボタンと動きの送り方は、修飾キーを見ていない（`gst-viewer.m` 1187〜1223 行）。エージェント（`serve.rs` 275〜308 行）、試用のホストのスクリプト（`scripts/m1-step3-host.py` 480〜512 行）、コンポジター（`comp/input.rs` に、Alt の決まりはない）も、同じ。
2. **アプリがロックを持っていて、こちらが絶対座標だけを送っているとき、アプリが受け取るもの**
   - `pointer_motion_absolute` は、前の絶対座標との差を作って、`pointer_motion` を呼ぶ（gwd `comp/input.rs` 278〜293 行）。**相対移動は、絶対座標の入力からも作られる。**
   - ロックが効いていると、`wl_pointer.motion` は出ない（同 209〜233 行）。相対移動（`zwp_relative_pointer_v1.relative_motion`）は、いつも出る（235〜244 行）。そのあとに `wl_pointer.frame`（246 行）。絶対座標が 1 つ届くたびに、この組が 1 つ出る。
   - 送り先は、ポインターの受け手になっている窓の面を持つクライアントの、relative-pointer（Smithay `input/pointer/mod.rs` の `relative_motion`、`wayland/relative_pointer.rs` 120〜154 行）。ボタンを押しているあいだの掴みも、相対移動をそのまま通す（`input/pointer/grab.rs` 367〜375 行）。
   - 値は、前の絶対座標との差。加速ありと加速なしに、同じ値が入る。Mac のポインターが止まるか、絵の端で切りつめられると、差は 0 になる。
   - 映像のフレームは、これとは別に出続ける。
3. **ボタンを押した瞬間に、ロックが頼まれたとき**：押しは、先にアプリへ届く。Smithay は、押した面を受け手に固定する。アプリがロックを頼むと、コンポジターは、その面がポインターの受け手なら、**その場でロックを有効にする**（gwd `wayland/handlers/pointer_constraints.rs` 10〜22 行、`comp/input.rs` 104〜128 行）。領域つきのロックは、ポインターがその中にあるときだけ。
4. **ポインターが面の上にあるとき、ロックは有効になれるか**：なれる。頼まれたとき（3）と、次にポインターが動いたとき（`comp/input.rs` 188〜189 行）の 2 か所で、有効にする。条件は、ロックを頼んだ面が、**窓の主の面**であること。コンポジターは、窓の主の面でしかロックを探さないので、子の面やポップアップの面に頼んだロックは、有効にならない。受け手でなくなると、Smithay が自分で解く（`wayland/seat/pointer.rs` 246〜256 行）。
5. **「OS キー」の試しは、いまの既定では成り立たない。** Command は、既定で Control として届く。Super（OS キー）として届くのは、クライアントを `ISTESSO_COMMAND_KEY=super` で起動したときだけ（`gst-viewer.m` 1040、1345〜1346 行）。

Blender の側（文書では、確かめられなかった）：

- 「中ボタンの代わり」の回転が、Continuous Grab の設定に関わらずロックを取る、という記述は、見つからなかった。同梱の文書は readme だけで、Wayland のことは書いていない。公開の文書（マニュアル、リリースノート、出典 2 と 3 のコミットの説明）にも、その記述はない。

### 5.1 「全画面」ではなく「最大化」として伝える（案。何も変えていない）

追記（2026-11-18）：この案は、試用と毎日使う形のビルドにだけ入れた（`scripts/patches/gst-wayland-display-trial-windows.patch` の 2。[m3-compositor-windows.md](m3-compositor-windows.md)）。アプリが頼んだときの全画面と、最大化の頼みも受ける。判定用のビルドは、下に書いたとおりのまま。

読んだこと：

- 最初の窓（親がなく、大きさの上限を言わない窓）に、出力の大きさと、**`XdgState::Fullscreen`** を伝えている：gwd `wayland/handlers/compositor.rs` 94〜114 行（113 行）。元のプロジェクトの 2023 年のコード。
- 出力の大きさが変わるたびに、全部の窓に、もう一度 `Fullscreen` と `Activated` を伝えている：gwd `comp/mod.rs` 414〜419 行（416 行）。元のプロジェクトの 2026 年 4 月のコード。
- このプロジェクトの修正は、この 2 か所を足しても変えてもいない。ダイアログの修正のテストが、「全画面と伝えられること」を確かめている（`scripts/patches/gst-wayland-display-dialogs.patch` の 312 行）。

案：

- 2 か所の `XdgState::Fullscreen` を、`XdgState::Maximized` にする。窓は出力いっぱいのまま、アプリは帯を残す。テストの 1 行も合わせる。
- 「最大化」にすると、アプリは飾り（題名の帯、「– □ ×」）を描いてよいことになる。Blender は、いまは描いていない見込みで、描くようになるかもしれない。**飾りの口（宿題 14）と一緒に入れるか、入れたあとに Blender の見え方を確かめる。**
- **関門と確定の判定に使うビルドには、当てない。** 別のビルドで試し、判定のあとに入れる。

### 6.1 宿題 6 の中身

| 順 | 作るもの | 層 |
|---|---|---|
| a | ロックと閉じ込めが、始まった・解けたことを、外へ知らせる。解けたときは、アプリが伝えた場所も付ける | コンポジターの修正（カーソルの知らせと同じ形） |

### 6.2 宿題 10 の中身：文字のコピーと貼り付け

読んだこと：コンポジターには、アプリどうしのクリップボード（`wl_data_device`）がある。Mac とのあいだで運ぶものは、どの層にもない。固定している Smithay には、コンポジター自身が選択の中身を読む・置くための部品と、外の道具が読み書きするための口（data-control）の部品が、両方ある。ホストに、クリップボードを読み書きする道具は、入っていない。

| 順 | 作るもの | 層 |
|---|---|---|
| a | 先に ADR：何を運ぶか（文字だけ）、いつ運ぶか、大きさの上限、どちら向きを許すか、記録に出さないこと | 文書 |
| b | アプリがコピーしたとき、その文字を外へ知らせる。外から渡された文字を、クリップボードに置く | コンポジターの修正 |
| c | 文字を運ぶメッセージ。鍵で守られた制御チャンネルを通す（映像の道ではない） | プロトコル、エージェント、ホスト |
| d | Mac のペーストボードとつなぐ。窓がキーの窓になったときに Mac の文字を送り、ホストでコピーされたら Mac に置く | クライアント |

- 運ぶのは、その窓を映している端末とのあいだだけにする（ADR 0010 の「入力と映像は、そのセッションを映している端末だけ」と同じ線）。

### 6.3 宿題 11 の中身：日本語（つなぎの形）

読んだこと：ホストには、入力方式（IBus）と、日本語の変換（Mozc）が、入っている。コンポジターは、入力方式のための口（text-input、input-method）を出していない。Smithay には、その部品がある。クライアントは、Mac のキーの番号を送る。Mac の「英数」「かな」のキーも、番号で送られる（`keys.h` の表）。

- 形：アプリと同じセッションの中で、ホストの入力方式を動かす。Mac のキーは、いまのとおり、番号のまま届く。変換は、ホストの側で行われ、候補の窓は、絵の中に出る。
- 道は 2 つある。どちらで動くかは、動かして確かめる。
  1. アプリのツールキットの口を使う（Firefox は GTK）。コンポジターは変えない。入力方式と話すための、セッションごとの連絡の口（D-Bus）を、ランナーが用意する。
  2. コンポジターに、text-input と input-method の口を足す。どのアプリでも効く。Blender の文字の欄は、こちらでないと効かない見込み。
- 決めること：切り替えのキー（Mac の「英数」「かな」が、ホストでどのキーとして読まれるか）。入力方式の設定と学習の置き場所（持ち主のふだんの設定に触れない。専用のフォルダー）。ホストの前にだれもいない状態で、連絡の口をどう作るか。
- 分かっている弱さ：変換中の文字と候補が、絵として届くので、遅れて見える。Mac のふだんの変換とは、辞書も癖も違う。だから、つなぎである。

### 9.2 設定の窓に、何が起きたか

考えた（いちばん起きていそうな筋）：

1. 設定の窓は、**親を言わない窓**だった。親を言う窓なら、主の窓をクリックしても、前に残る（9.1）。
2. 出たときは、いちばん上で、キーボードも持っていた。「別の窓として開いた」と合う。
3. 持ち主が、設定の窓の外、つまり主の窓をクリックした。主の窓が、いちばん上に上がった。**主の窓は出力いっぱいなので、設定の窓は、全部がその下に隠れた。**
4. メニューからもう一度開くと、Blender は、すでにある設定の窓を前に出そうとする。その口がないので、何も起きない。

分かっていないこと：

- Blender が、伝えられた「全画面、出力の大きさ」に従ったか。従っていれば、設定の窓が絵いっぱいになり、隠れるのは主の窓のほうになる。持ち主の言い方からは、従わずに、自分の大きさで出たと考えた。
- Blender が、窓を前に出すときに、xdg-activation で頼むか。

### いま、何も変えずにできること

コンポジターの側には、戻す手がありません。キーも、クリックする場所もありません（隠れた窓は、全部が主の窓の下にある。Ctrl＋Shift＋Tab は効かない）。**Ctrl＋Shift＋Q は押さないでください。** キーボードを持っている主の窓に、閉じる頼みが行きます。

Blender の側でできること（どれも、試していません。設定の名前は、アプリの中で確かめてください）：

1. **見失わない使い方**：設定を、別の窓ではなく、主の窓の中の区画で開く。区画の左上の Editor Type で、Preferences を選ぶ。
2. ファイルを選ぶ窓と、レンダーの窓も、既定では別の窓になる。Preferences の Interface にある Temporary Editors で、別の窓にしない形を選ぶ。
3. **見失った窓を閉じる**：主の窓の区画を Python Console にして、次を打つ。主の窓のほかの窓を、全部閉じる。そのあとでメニューから開けば、新しい窓として、上に出る（9.1）。

   ```python
   import bpy
   for w in list(bpy.context.window_manager.windows):
       if w != bpy.context.window:
           with bpy.context.temp_override(window=w):
               bpy.ops.wm.window_close()
   ```

4. だめなら、保存して（Ctrl＋S は、主の窓に届く）、Blender を開き直す。

| B | xdg-activation の口を出す。頼まれた窓を前に出し、キーボードを渡す | Smithay に部品がある。状態の欄、口の登録、処理で 40 行ほど | アプリがこの口で頼むとき。Blender が頼むかは、確かめていない |
| C | 2 枚目からの、親を言わない窓には、「全画面、出力の大きさ」を言わない。ダイアログと同じに、空きの広さだけを伝え、出力のまん中に置く | `wayland/handlers/compositor.rs` 94 行の条件と、`comp/mod.rs` の `place_window`。5〜10 行 | 2 枚目の窓が、アプリの望む大きさで出る |

テストは、`dialogs` の修正のテストと同じ形で、60〜80 行の見込みです。

危うさと、判定用のビルドとの分け方：

- **判定用のビルドには、入れない。** 修正は新しいファイルにする。別のフォルダーでビルドし、試用のときだけ、`ISTESSO_HOST_PLUGIN` でそのフォルダーを指す（`scripts/try.sh` の 42、74 行に、その口がある）。判定用のビルドのフォルダーには、触れない。
- フレームの経路には、入らない（重なりの順と、窓への知らせだけ）。
- A で、小さい窓は、いつも主の窓の上に残る（道具の窓のふるまい）。出力いっぱいの窓が 2 枚あるとき（2 枚目のブラウザーの窓）は、下の窓へ行く手が、ないままである。これは、窓の一覧（10 章）が要る。
- C で、出力いっぱいがふさわしい窓も、アプリの望む大きさになる。アプリが自分で最大化を頼む口は、まだ受けていない（宿題 9 と一緒に作る）。

## 10. アプリの窓 1 枚ごとに、Mac の窓を 1 枚出す（設計の提案）

**これは提案です。大きい変更なので、コードの前に、計測と ADR を置きます。この文書では、何も決めていません。**

持ち主の見る正しい形：アプリの窓（設定、ファイルの窓、2 枚目のブラウザーの窓）1 枚ごとに、Mac の窓が 1 枚。

### 10.1 いまの決まりは、どこにあるか

| 文書 | 書いてあること |
|---|---|
| [requirements.md](requirements.md) の R-02 | 「アプリごとに仮想ディスプレイを割り当てる（1アプリ = 1仮想ディスプレイ = 手元の1窓）」 |
| [ADR 0009](adr/0009-host-compositor.md) の表 | 「窓の扱い：出力は 1 つ。中のアプリの窓を、その 1 枚の絵に合成する」。「ないもの」に、「アプリの窓を 1 枚ずつ別の絵にして出すこと」 |
| ADR 0019（`m1-own-host`）のランナーの言葉 | 窓は、**数**でしか出てこない：`windows`（数）、`empty`（最後の窓が閉じた）、`close` と `close_asked`（全部の窓に、閉じる頼み。⌘Q もこれ）、`still_open`、`no_window_yet` |
| ADR 0010（`m3-app-manager`、`m3-launcher`） | 1 セッションに、仮想ディスプレイ 1 つと、映像の答え 1 つ。圧縮の枠（15）：数えるのは、同時に圧縮している映像の数。初めの値は 8。カードが許す数は、文書が 5、8、12 に分かれていて、ホストで数える計測が残っている |
| ADR 0018（`m1-own-client`）と、`m3-launcher.md` の 7 | クライアントは 1 つのプロセス。Dock と ⌘Tab は、A（Istesso 1 つ）から。C（アプリごとのプロセス）は、確定の判定のあとに決める |

### 10.2 3 つの案

- **(i)** 窓ごとに出力を 1 つ。窓ごとに、圧縮した流れと、Mac の窓。
- **(ii)** 流れは 1 つ。絵の中に窓を並べ、クライアントが、四角ごとに切り出して、Mac の窓にする。
- **(iii)** Mac の窓は 1 枚のまま。その中の重なりを、きちんと扱う。

| | (i) 窓ごとの流れ | (ii) 1 つの流れを切り出す | (iii) 1 枚のまま |
|---|---|---|---|
| コンポジター | 窓ごとに、描く先とバッファーの置き場を持つ。いまは、出力 1 つ、出口 1 つの作り。作り直しに近い。窓の大きさは、Mac の窓が決めて伝える | 出力は 1 つのまま。窓を、重ならないように並べて描く（ポップアップのための余白つき）。窓ごとの四角を、フレームと一緒に知らせる。並びが変わると、絵の大きさが変わる（大きめの絵を固定で持つ形もある） | 小さな修正だけ（9.3）。あとで、窓の一覧と、「前に出す」頼み |
| ホスト（エンコーダー） | 窓ごとに、パイプラインとエンコーダー。**設定の窓 1 枚が、アプリ 1 つぶんの枠を使う。** 窓が出るたびに、エンコーダーを開く時間がかかる（測っていない） | エンコーダーは 1 つ。枠は、アプリ 1 つぶんのまま。画素は増える（2 枚目のブラウザーの窓なら、倍）。エンコーダーの絵の上限の中に収める | 変わらない |
| プロトコル | 窓の一覧（番号、親、題名、大きさ）。窓ごとの映像の申し出と答え。入力に、窓の番号。窓ごとのフォーカスと、閉じる | 窓の一覧と、絵の中の四角。どのフレームからその並びかの番号を、フレームのヘッダーに（ADR 0015）。**入力のイベントは、いまの形のまま**（絵の座標）。フォーカスと、窓ごとの閉じるを足す | なくても動く。窓の一覧と「前に出す」を足すと、Mac の「ウインドウ」メニューから選べる |
| クライアント | 窓ごとに、復号器と Mac の窓。キーの窓が変わったら、フォーカスを送る。Dock と Mission Control に、自然に並ぶ | 復号器は 1 つ。同じ復号した面を、窓ごとに、切り出す場所だけ変えて見せる（コピーなしの見込み。確かめていない）。キーの窓とフォーカス、Dock と Mission Control は、(i) と同じ | 窓は 1 枚のまま |
| 遅延の経路 | 段も、コピーも、増えない。GPU の取り合いは、増える | 段は増えない。画素が増えるぶん、エンコードと復号が延びる。並べ直しのたびに、キーフレームが要るかもしれない | 変わらない |
| ランチャーの C、⌘Q、最後の窓 | アプリごとのプロセスが、複数の流れを持つ。セッションの形（答えが 1 つ）を変える。⌘Q と `empty` は、いまのまま。窓ごとの閉じるが要る | **セッション、枠、`windows`、`empty`、`close` は、いまのまま。** A にも C にも合う。Mac の窓の閉じるボタンは、その窓だけを閉じる頼み。⌘Q は、全部の窓 | いまのまま |
| ダイアログとポップアップ（いまは、正しく出ている） | ダイアログは、窓 1 枚になる。**ポップアップ（メニュー）は、親の四角からはみ出す。** 親の流れに入れると切れ、別の流れにすると、メニューのたびにエンコーダーを開く | どちらも、「四角がもう 1 つ」。ポップアップは、枠のない子の窓として、親の外にも出せる。エンコーダーは増えない | いまのまま |
| 弱いところ | 枠の数、ポップアップ、コンポジターの作り直し | 絵の大きさの変化、四角の境目の色のにじみ（すき間を空ける）、大きな絵の復号、並びとフレームのずれ | 持ち主の望む形ではない。設定の窓を、主の窓の横や、ほかの画面に置けない |

### 10.3 勧め（決めるのは、測ってから。2026-11-18 に決定）

- **いまは (iii) のつなぎ（9.3）で、持ち主が詰まらないようにする。目指す形は (ii) を第一の候補にして、計測と ADR から始める。**
- 理由：(ii) は、セッションの形、圧縮の枠、入力のイベント、遅延の経路を変えずに済み、ダイアログとポップアップが同じ仕組みに乗る。(i) は、(ii) の計測が合格ラインを割ったときと、出力いっぱいの窓が増えて絵の上限を超えるときの、第二の候補にする（ふだんは (ii)、あふれた窓だけ別の流れ、という混ぜ方）。

### 10.4 決める前に、測ること

1. 絵の画素を 1.5 倍と 2 倍にして、四角 1 つだけが変わるときの、エンコードと復号の時間。合格ライン（中央値 12 ms）の中に収まるか。
2. 絵の大きさを変えたあと、次のフレームが出るまでの時間。大きめの絵を固定で持つ形との比べ。
3. Mac で、1 つの面を、複数の窓が切り出して見せたとき、コピーが起きないか。窓ごとの表示の時刻がそろうか。
4. （(i) の判断のために）ホストで同時に開けるエンコーダーの数と、エンコーダーを 1 つ開くのにかかる時間。前者は、ADR 0010 の 15 に残っている計測と同じもの。
5. Blender と Firefox のメニューが、親の窓から、どれだけはみ出すか。
6. **窓の大きさを変えるときの費用**（2026-11-18 に足した）：窓を、手で引いて大きくしているあいだに、並べ直しが何回起き、キーフレームが何枚出るか。
7. **窓が 1 枚のときの遅延が、いまより悪くならないこと**（2026-11-18 に足した）。確定の判定は、窓 1 枚で測る。

### 10.5 作る順（提案）

1. つなぎの直し（9.3、宿題 3）。
2. **窓の一覧の知らせ**：番号、題名、`app_id`、親、四角、いちばん上か、キーボードを持つか。宿題 8（題名）と 9（全画面）は、この 1 つの知らせにまとめる。まず、題名と、Mac の「ウインドウ」メニューに使う。(iii) のままで役に立つ。
3. クライアントからの、窓ごとの「前に出す」と「閉じる」。
4. 計測（10.4）。そのあとで ADR：R-02 と ADR 0009 の「窓の扱い」を書き直し、ADR 0015 のヘッダー、ADR 0018 の窓、ADR 0019 のランナーの言葉を合わせる。
5. コンポジター：重ならない並べ方と、並びの番号。
6. クライアント：1 つの面から、複数の窓。ポップアップは、枠のない子の窓。
7. ランチャーの C と、⌘Q、最後の窓の決まりを合わせる。
